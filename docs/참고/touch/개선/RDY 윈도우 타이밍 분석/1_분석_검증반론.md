# IQS323 RDY 윈도우 타이밍 — 적대적 검증 반론

> **TL;DR**: IQS323 RDY 타이밍 관련 7개 명제를 원문(§8.8·§8.11·§8.12·§8.11.1·§5.2·§6.6.3)으로 판정. 핵심 오류: ① t_Low는 Transaction Timeout(기본 200 ms)이 아닌 마스터 트랜잭션 완료 시점에 닫힌다. ② 200 µs 지연은 원문 미명시(실제 원문은 MCLR switchover 150 µs). ③ 칩 reset default는 Streaming(0x0000), 동작 권장은 event mode.

## 명제별 상세 판정

### 명제_1 — "스트리밍 모드에서 RDY low 폭(t_Low)은 항상 Transaction Timeout(200 ms)이다"

**판정: [거짓]**

> [!CAUTION]
> 이 오해는 RDY low 폭을 timeout 값과 동일시하는 가장 흔한 실수다.

**원문 근거 — §8.8 I²C Transaction Timeout:**

```
"If the communication window is not serviced within the time specified in milliseconds by
the I²C Transaction Timeout register, the communications window is closed (RDY goes high)
and processing continues as normal."
                                    — §8.8 원문 (p.31)
```

Transaction Timeout은 **마스터가 응답하지 않을 때** 윈도우를 강제 닫는 watchdog의 상한선이다. 마스터가 정상 서비스(START → R/W → STOP)하면 STOP 수신 순간 윈도우가 닫혀 RDY high로 복귀한다.

**실제 t_Low 결정 요인:**

| 시나리오 | t_Low | 근거 |
|---|---|---|
| 마스터 정상 서비스 시 | 마스터 I²C 트랜잭션 소요 시간 (통상 수십~수백 µs) | §8.9: STOP이 현재 comm window 닫음 |
| 마스터 무응답 시 | Transaction Timeout 설정값 (기본 200 ms, 범위 2~230 ms) | §8.8 원문 |
| Stop Bit Disable = 1 시 | 0xFF 커맨드 전송까지 | §8.9 원문 |

**결론:** 마스터가 정상 서비스하는 환경에서 t_Low = 200 ms는 전혀 사실이 아니다. 200 ms는 "아무도 응답 안 했을 때의 최대 지속 시간"이다.

### 명제_2 — "RDY 주기는 항상 Report Rate와 정확히 같다"

**판정: [조건부]**

**원문 근거 — §8.11.1 I²C Streaming:**

```
"In I²C streaming mode data is constantly reported at the relevant power mode report rate
specified in milliseconds by the Normal Power Report Rate, Low Power Report Rate and
Ultra Low Power Report Rate registers."
                                    — §8.11.1 원문 (p.32)
```

"reported at … report rate"가 정확히 주기 일치를 보장하는가? 다음 예외 조건이 있다.

**주기 교란 가능성:**

1. **ATI 실행 중** — §8.4 원문: `"while the ATI is being performed, the I²C communication is disabled"`. ATI 동안 RDY 윈도우 생성이 중단된다.
2. **전력 모드 전환** — §5.3: 이벤트 발생 시 NP로 즉시 복귀. 전환 과정에서 한 사이클 주기가 늘어날 수 있다.
3. **측정 완료 시점 기반** — 보고 타이밍은 "report rate"로 설정된 내부 타이머 기준이지만, 측정(conversion) 자체 소요 시간 + 필터링 계산 시간이 합산된다. 데이터시트는 측정 소요 jitter를 명시적으로 0으로 보증하지 않는다.
4. **Force Comm t_wait** — §8.13: `"The minimum and maximum time between the communication request and the opening of a RDY window (t_wait) is application specific. The typical values: 0.1 ms ≤ t_wait ≤ 45 ms"`. Force Comm 직후 첫 윈도우는 t_wait 불확정성을 포함한다.

**결론:** 정상 동작 중 대부분의 윈도우는 report rate에 맞춰 열리나, ATI/전력 모드 전환/Force Comm 시 주기가 틀어진다. "항상 정확히 같다"는 과장이다.

### 명제_3 — "Report Rate 16 ms인데 Transaction Timeout 200 ms면 모순/불가능하다"

**판정: [거짓]**

두 파라미터는 **독립적이고 목적이 다르다.**

```
"The default I²C Transaction Timeout is set to 200 ms."  — §8.8 (p.31)
```

| 파라미터 | 역할 | 기본값 |
|---|---|---|
| Normal Power Report Rate | 스트리밍 모드에서 RDY를 여는 내부 주기 | 0x0000 (= 0 ms → 레지스터 기록 필요) |
| I²C Transaction Timeout | 마스터 무응답 시 강제 닫힘 watchdog 상한 | 200 ms (0x00C8) |

**공존 시나리오:**
- 마스터가 16 ms마다 열리는 윈도우를 정상 서비스하면, 각 윈도우는 수십~수백 µs 만에 닫힌다.
- Timeout 200 ms는 단 한 번도 발동하지 않는다.
- 마스터가 16 ms 주기로 서비스하는 한 "16 ms 주기 + 200 ms timeout"은 완전히 정합된다.

**결론:** 두 값이 "모순"이라는 것은 Report Rate와 Timeout의 역할을 혼동한 오해다. Timeout > Report Rate이어야 한다는 조건도 데이터시트에 없다.

### 명제_4 — "기본 세팅 = streaming 모드다"

**판정: [조건부]**

> [!WARNING]
> "기본 세팅"의 의미를 **칩 reset default**로 볼 것인가, **Sound1 적용 초기화 후**로 볼 것인가에 따라 답이 다르다.

**칩 reset default 기준:**

메모리 맵 표(p.35):

```
0xC0   System Control   0x0000   See Appendix A.30
```

Appendix A.30 §8 Bit7 Interface Selection:
```
• 0: I²C Streaming
• 1: I²C Events
```

`0x0000`의 bit7 = 0 → **칩 reset default는 Streaming 모드.**

**Sound1 초기화 후 기준:**

§8.11.2 원문:

```
"This is usually enabled since the master does not want to be interrupted unnecessarily
during every cycle if no activity occurred."
                                    — §8.11.2 원문 (p.32)
```

§8.15 Program Flow Diagram (Figure 8.3)의 Write Settings 단계에서 event mode를 명시 활성화한다. Sound1 h-file은 Interface Selection bit를 1로 기록한다. 따라서 Sound1 런타임에서는 event mode가 "기본".

**"보통 enable"의 해석:**

§8.11.2 "This is usually enabled"는 "event mode가 일반적으로 권장된다"는 의미이지, "default로 enabled"가 아니다. 권장(design recommendation)과 default(reset 후 initial value)는 다른 개념이다.

**결론:** 칩 reset default = Streaming(0), 권장 및 Sound1 적용값 = Event Mode(1). 맥락 없이 "기본 세팅"이라 말하면 답이 달라지므로 항상 어느 기준인지 명시해야 한다.

### 명제_5 — "RDY high → low 전환이 report rate 간격으로 jitter 없이 일어난다"

**판정: [거짓]**

**원문 근거:**

1. **§8.4 Communication During ATI:**
   ```
   "Unless the Reset Event bit is set in the System Status register, the I²C communication
   is disabled while the ATI is being performed."
   ```
   ATI 실행 중에는 RDY 윈도우 자체가 열리지 않는다. ATI 완료 시점이 report rate 타이머와 비동기이므로, ATI 직후 첫 윈도우까지의 간격은 불규칙하다.

2. **측정 완료 기반 트리거:**
   §8.11.1에서 "constantly reported at … report rate"라고 하지만, 내부적으로는 conversion 완료 → 처리 → RDY assert 흐름이다. conversion 소요 시간은 센서 부하(기생 C·전극 조건)와 clock에 의존하므로 미세 jitter가 존재할 수 있다.

3. **전력 모드 전환:**
   §5.3: 이벤트로 NP 복귀 직후 첫 사이클의 report rate 시작 기준이 초기화되므로 그 간격은 불규칙하다.

4. **데이터시트의 timing spec 부재:**
   §4.6 Start-Up Timings는 "Time to first RDY ≈ 25 ms"만 명시하고, 런타임 RDY 주기의 허용 jitter(tolerance)는 어디에도 명시되지 않는다.

**결론:** "jitter 없이" 일어난다는 것은 원문 미보증. ATI·전력 모드 전환 구간에서는 확실히 깨진다.

### 명제_6 — "ULP 모드 주기 = Auto Prox Cycle Select × ULP Report Rate의 함정"

**판정: [조건부]**

**원문 수식 — §8.11.1:**

```
(Auto Prox Cycle Select × Ultra Low Power Report Rate) ms

Where Auto Prox Cycle Select is defined in the Prox Input and Control register.
```

**함정 — Auto Prox Cycle Select의 실제 의미:**

Appendix A 레지스터 참조(Prox Input and Control, bit3-2):

```
> Bit 3-2: Auto Prox Cycle Select
        • Number of conversions before each interrupt is generated in Auto Mode
        • 00: 4
        • 01: 8
        • 10: 16
        • 11: 32
```

"채널 수"가 아닌 **interrupt를 생성하기 전 실행할 conversion(변환) 횟수**다.

**오해 시나리오:**

- "3채널이니까 Auto Prox Cycle Select = 3"이라고 직관적으로 해석하면 잘못된 것.
- 실제 선택 가능한 값은 4/8/16/32이며, 0/1/2/3 채널 수와 무관하다.
- ULP에서 지정 채널이 conversion을 Auto Prox Cycle Select 횟수만큼 실행한 뒤 RDY를 assert한다.

**추가 함정 — §5.2 ULP 채널 비대칭:**

```
"Intended for rapid wake-up from deep sleep on a single channel …
Other sensor channels are sampled at a slower rate"
                                    — §5.2 원문
```

ULP에서 wake-up 채널과 비 wake-up 채널의 실제 보고 주기는 다르다. 위 수식의 "report rate"는 어느 채널의 report rate인지 원문이 명시하지 않는다. §3.2 Current Consumption 표의 ULP report rate(Self-cap 160 ms, Inductive 200 ms)가 채널 타입별로 다른 것이 이를 보여준다.

**결론:** 공식 자체는 원문에 명시된 것이 맞으나, Auto Prox Cycle Select를 "채널 수"로 오해하거나 ULP에서 모든 채널이 동일 주기를 가진다고 가정하면 잘못된 계산이 나온다.

### 명제_7 — "STOP 후 RDY는 즉시 high"

**판정: [조건부]**

**원문에서 직접적인 RDY high 전환 지연 명시:**

§6.6.3(MCLR as Reset) 원문:

```
"There is a switchover delay when the pin changes back to MCLR functionality after an RDY
window is closed. … The typical time for the switchover to be completed is 150 µs from the
time when the pin is considered high to it acting as MCLR."
                                    — §6.6.3 원문 (p.23)
```

이 150 µs는 **MCLR 기능 복귀 지연**이다 — RDY 핀이 물리적으로 high로 떠오르는 시간이 아니라, high가 된 후 MCLR로서 동작 가능해지는 데 걸리는 시간이다.

**"즉시"의 수정:**

> [!CAUTION]
> md 정리본(05_i2c인터페이스.md) §8.9 노트에 `"~200 µs 후 RDY HIGH"` 및 `"STOP 후 약 200 µs 이내에 RDY가 HIGH로 복귀한다"`라고 기술되어 있으나, **이 200 µs 수치는 원문에 없다.** 원문에 있는 유일한 µs 수치는 §6.6.3의 150 µs (MCLR switchover)이다.

| 수치 | 원문 존재 여부 | 실제 내용 |
|---|---|---|
| "~200 µs 후 RDY HIGH" | **원문 미명시** | md 정리본 추정·삽입. 원문 근거 없음 |
| 150 µs | 원문 명시 §6.6.3 | MCLR 기능 복귀 지연 (RDY high→MCLR 동작 가능 시간) |

**결론:** RDY가 STOP 직후 즉시 high로 전환된다는 것을 원문이 보증하지 않는다. 내부 회로 특성상 일정 지연이 있으며, MCLR 기능 복귀 기준으로 150 µs가 명시된다. "즉시"는 과장이며, "200 µs"는 원문 미명시 수치다.

## 추가 점검 — "기본 세팅"의 두 해석

**칩 reset default vs Sound1 적용값 비교:**

| 항목 | 칩 reset default (`0x0000`) | Sound1 초기화 후 (h-file 적용) |
|---|---|---|
| Interface Mode | **Streaming** (bit7 = 0) | **Event Mode** (bit7 = 1) |
| Normal Power Report Rate | 0 ms (0x0000) | 레지스터 기록 필요 |
| I²C Transaction Timeout | 200 ms (0x00C8) | Sound1 설정값 (확인 필요) |
| Power Mode | Normal Power (bits6-4 = 000) | Automatic 계열 (확인 필요) |

**답이 달라지는 지점:**

- "IQS323은 기본적으로 어떤 모드로 동작하나?" → 칩 reset 직후 기준으로는 Streaming.
- "Sound1에서 터치 IC는 어떤 모드인가?" → Write Settings 후 Event Mode.
- "ATI 도중에도 통신 가능한가?" → No. §8.4 원문 명시. 단, Reset Event bit set 중(POR 직후)은 예외.

## md 정리본 vs 원문 Cross-Check 결과

| 항목 | md 정리본 기술 | 원문 | 일치 여부 |
|---|---|---|---|
| Transaction Timeout 기본값 | 200 ms | §8.8: `"The default I²C Transaction Timeout is set to 200 ms"` | 일치 |

| STOP 후 RDY HIGH 지연 | "~200 µs 후 RDY HIGH" (§8.9 노트) | **원문 없음** — 150 µs는 MCLR switchover | **불일치 (원문 미명시 수치 삽입)** |
| 칩 reset default 인터페이스 | 명시 없음 | 0xC0 default 0x0000 → bit7=0 = Streaming | md에서 누락 |
| ULP 공식 | §8.11.1 원문 그대로 | §8.11.1 수식 일치 | 일치 |
| Auto Prox Cycle Select 의미 | conversion 횟수 (4/8/16/32) | Appendix 비트 정의와 일치 | 일치 |
| Force Comm t_wait 범위 | 0.1 ms ≤ t_wait ≤ 45 ms | §8.13 원문 동일 | 일치 |
| MCLR switchover 지연 | 미기술 | §6.6.3: 150 µs | md에서 누락 |

> [!WARNING]
> **수정 권고 — 05_i2c인터페이스.md §8.9 노트:**
> `"~200 µs 후 RDY HIGH"` 및 `"STOP 후 약 200 µs 이내에 RDY가 HIGH로 복귀한다"` 두 문장은 원문 근거가 없다. 해당 문장을 `"원문에서 STOP 후 RDY high 전환 지연 수치는 미명시. MCLR 기능 복귀까지 전형적으로 150 µs (§6.6.3)"로 교체 권장.

## 반론 결론

가장 위험한 오해 2가지:

1. **t_Low = Transaction Timeout(200 ms)** — 마스터가 정상 동작하는 경우 실제 t_Low는 수십~수백 µs 수준이다. 200 ms는 무응답 watchdog 상한값일 뿐이다.
2. **STOP 후 RDY high 전환 "~200 µs"** — 이 수치는 원문에 없다. 원문에 존재하는 µs 수치는 MCLR switchover 150 µs (§6.6.3) 하나뿐이다. 정리본 작성 시 추정값이 원문 수치처럼 기술된 것이므로 수정이 필요하다.
