# 07. 미확정 사항과 측정 절차

**TL;DR**: 이 문서 묶음은 **코드와 데이터시트만으로** 쓴 것이다. **최대 현안이던 미확정_1(데시메이션 게인)은 2026-08-11 에 해소**됐다 — `1092` 가 SDK 가 계산한 유니티 그 자체였다(§1). **남은 미확정 4건은 전부 정밀도 문제**이고, `Addr_SharedMem->maxAudioInput` 한 값만 찍으면 대부분 한꺼번에 확정된다.

> [!NOTE]
> **2026-08-11 갱신**: 미확정_1 이 해소되어 [03 환산표](03_dBSPL-코드%20환산표.md)의 dB SPL 값이 **그대로 유효**하다. 아래 §1 은 기록으로 보존한다.

## 1. ~~미확정_1~~ - 데시메이션 게인 → **해소 (2026-08-11)**

> [!NOTE]
> **해소됐다. `1092` 는 SDK 가 계산한 유니티 값 그 자체이고, 밀림은 0 dB 다.**
> 따라서 이 문서 묶음의 모든 dB SPL 값이 **그대로 유효**하다.

### 무엇을 잘못 봤나

E8300 하드웨어 레퍼런스 **p.445** 의 인쇄된 식을 그대로 읽고 유니티를 **1979.7** 로 계산했다.

```
GF = 2^(11 + log2(SFCR)) / (SFCR + 1)      ← 실수 log2 로 읽음 → 1979.7
```

**틀렸다. SDK 구현은 `log2` 에 floor 가 들어간다.**

```c
// SDK: include/shared/analog_in.h  Sys_Calc_Gain_Factor_Val()
/* GF = round[2^(11+floor[log2(sfcr)])/(sfcr+1)] */
unsigned int log2 = 0, SFCR = adc_cfg_sample_freq;
while (SFCR != 1) { SFCR >>= 1; log2++; }          // ← 정수 몫 = floor
sys_calc_gf = ((((1 << (11 + log2)) * 10) / (adc_cfg_sample_freq + 1)) + 5) / 10;
```

`SFCR = 29` 이면 `floor(log2(29)) = 4` 이므로

```
실수 log2 : 2048 × 29 = 59,392 / 30 = 1979.7   ← 오독
floor log2: 2^15      = 32,768 / 30 = 1092.3   ← 실제 → 1092
```

### 확인

| 항목 | 값 |
|---|---|
| `Sys_Calc_Sample_Freq_Val(ADCCLK 3.84 MHz, 16 kHz)` | **29** = `ADC_MODDIV_BY30`(`0x1D`) ✓ |
| **`Sys_Calc_Gain_Factor_Val(29)`** | **1092** = `LIB_SYS_CALC_GF` ✓ |

**펌웨어 값이 SDK 계산과 정확히 일치한다.** `main.h:119` 에 남은 `SYS_CALC_GF 1979` 쪽이 오히려 잘못된 값이다(현재 미사용 경로).

### 교훈

**데이터시트의 인쇄된 수식보다 SDK 의 구현이 우선이다.** 렌더한 PDF 이미지에서 floor 괄호를 놓쳤고, SDK 에 계산 함수가 있는지 확인하지 않았다. 자산_26(«옵션 이름은 `--dump-config` 로 존재부터 확인한다»)과 같은 종류의 실수다.

**부수 확인**: 눈금이 밀려 있지 않으므로 **AGC 노이즈 게이트 29.50 dB SPL 이 마이크 잡음 바닥 29.5 와 겹치는 것은 우연이 아니라 설계**다. 정황 근거로만 남겨 뒀던 것이 확정됐다.

## 2. 미확정_2 - 말소리 파고율

[03](03_dBSPL-코드%20환산표.md) §4 의 «실제 소리 → AGC 가 읽는 자리» 표는 **파고율 12 dB 를 가정**했다.

**AGC 는 피크를 보므로 이 값이 틀리면 «어느 소리가 어느 구간에 떨어지는가» 가 통째로 이동한다.** §5 측정으로 확정된다.

## 3. 미확정_3 - 마이크 패키지 호환성

[01](01_마이크%20스펙%20상세.md) §5. **전기·음향 스펙만 대조했고 기계 도면(패키지 아웃라인·패드 배열)은 보지 않았다.** 「그대로 바꿔 끼울 수 있다」 를 말하려면 두 데이터시트의 패키지 페이지를 비교해야 한다.

## 4. 미확정_4·5 - 작은 것 둘

| # | 항목 | 내용 |
|---|---|---|
| 4 | **개체차 ±1 dB** | 감도 스펙이 −27 ~ −25 dBFS. 코드로는 ±12 %. 절대 음압 측정이 필요하면 개체 교정이 필요하다 |
| 5 | **게이트 근처 떨림** | [05](05_포화와%20절삭.md) §3 — 게이트 부근에서 1 LSB 가 1.16 dB 라 판정이 뒤집힐 수 있다. **실제로 떨리는지는 로그로 봐야 안다** |

## 5. 측정 절차 - 10분이면 끝난다

### 5.1 준비

| 필요한 것 | 대안 |
|---|---|
| 음압계 (또는 교정된 스피커) | 스마트폰 SPL 앱 (±3 dB 정도, 상대 비교용으로는 충분) |
| 1 kHz 정현파 음원 | 아무 톤 제너레이터 |
| J-Link RTT 또는 디버거 | |

### 5.2 볼 값 하나

```c
// agc.c:105 — AGC 가 매 블록(1 ms) 기록한다
Addr_SharedMem->maxAudioInput = input_audio_mix_max_value;
```

**이 값은 «믹스 도메인(`>>5` 이후)의 16샘플 절대 최대값» 이다.**

### 5.3 절차

| # | 할 일 |
|---|---|
| 1 | 조용한 곳에서 **무음** 상태의 `maxAudioInput` 을 읽는다 → **잡음 바닥 확인** |
| 2 | 마이크 앞에서 **1 kHz 정현파를 94 dB SPL** 로 낸다 (또는 음압계로 측정된 임의 레벨) |
| 3 | 그때의 `maxAudioInput` 을 읽는다 |
| 4 | 아래 §5.4 로 판정 |
| 5 | (선택) **말소리**를 정상 크기로 내고 `maxAudioInput` 을 읽어 파고율 확인 |

### 5.4 판정 - 눈금 확인

**94 dB SPL 정현파를 넣었을 때 예상되는 `maxAudioInput` = 약 13,138** (믹스 도메인).

일반화한 환산식:

```
실측 0 dBFS 음압 = 측정 SPL + 20 × log10(262143 / 읽은값)
```

**결과가 120 근처면 이 문서 묶음이 그대로 맞다.**

| 결과 | 해석 |
|---|---|
| **118 ~ 122** | **정상.** 감도 개체차 ±1 dB + 음압계 오차 범위 |
| 123 이상 | 체인 어딘가에 예상 밖 감쇠가 있다 |
| 117 이하 | 체인 어딘가에 예상 밖 증폭이 있다 |

> [!NOTE]
> **§1 이 해소됐으므로 이 측정은 «가설 판별» 이 아니라 «전체 눈금 검산» 이다.** 안 해도 문서를 쓸 수 있지만, **한 번 해 두면 표 전체가 실측으로 뒷받침된다.**

### 5.5 무음 상태로도 대략 확인된다

조용한 방에서 `maxAudioInput` 을 읽는다.

| 읽은 값 | 해석 |
|---|---|
| **7 ~ 10** | 마이크 잡음 바닥(29.7 dB SPL)이 게이트 근처 — **예상대로** |
| 그보다 큼 | 환경 소음이 마이크 잡음보다 크다(정상). 더 조용한 곳에서 재측정 |
| 그보다 작음 | 체인에 예상 밖 감쇠가 있다 |

> [!NOTE]
> 보통 방은 30~40 dB SPL 이라 환경 소음이 마이크 잡음을 덮는다. **정확히 보려면 §5.3 의 음원 방식을 쓴다.**

### 5.6 파고율 확인 (미확정_2)

정상 크기로 말하면서 `maxAudioInput` 의 **최댓값**을 기록하고, 같은 위치에서 음압계로 **평균 SPL** 을 읽는다.

```
파고율 = [20 × log10(읽은값) + 11.63] − 음압계 평균 SPL
```

(괄호 안은 믹스 코드 → dB SPL 환산식, [03](03_dBSPL-코드%20환산표.md) §5)

## 6. 측정 후 할 일

| 결과 | 조치 |
|---|---|
| **눈금 확인 (120 근처)** | [03](03_dBSPL-코드%20환산표.md) 에 «실측 확인» 을 적는다. `main.h:119` 의 죽은 `SYS_CALC_GF 1979` 는 **잘못된 값이므로 정리 대상** |
| 눈금이 어긋남 | 어긋난 폭만큼 [03](03_dBSPL-코드%20환산표.md) 을 보정하고 원인을 추적한다 |
| 파고율 확정 | [03](03_dBSPL-코드%20환산표.md) §4 표를 실측값으로 갱신 |

## 7. 이 분석이 확인한 것 / 못 한 것

| | 항목 |
|---|---|
| **코드로 확인함** | 시프트 배율(`>>5`/`<<5`) · 게인 테이블 전체 · 경로 분기 · AGC 3구간 수식 · 곡선 연속성 · 포화 여부 계산 · 클램프 도달 여부 · attack/release 계수 |
| **데이터시트로 확인함** | 두 마이크 전 스펙 · 유니티 게인 공식 · IOC 구성 |
| **계산으로 확인함** | 게이트의 dB SPL 역산 · 볼륨별 압축비 · 믹서 포화 여유 · 절삭 오차 |
| **SDK 구현으로 확인함** | **데시메이션 게인 1092 = `Sys_Calc_Gain_Factor_Val(29)`** · SFCR 29 = `Sys_Calc_Sample_Freq_Val(3.84 MHz, 16 kHz)` |
| **확인 못 함 (실측 필요)** | §2 파고율 · §3 패키지 호환 · §4 개체차 · §5 게이트 떨림 |

> [!IMPORTANT]
> **«전체가 5 dB 틀릴 수 있다» 던 미확정_1 이 해소되어, 남은 4건은 전부 정밀도 문제다.** 문서 묶음을 실무에 쓰는 데 걸림돌이 없다.
>
> **다만 «SDK 구현으로 확인함» 은 «실측으로 확인함» 이 아니다.** SDK 함수가 하드웨어의 실제 거동과 일치한다는 것 자체는 가정이다. §5 의 검산을 한 번 해 두면 그 가정까지 닫힌다.
