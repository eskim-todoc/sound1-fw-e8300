# SW 밸리데이션 문서 작성/검증 지침

Sound1의 SV 문서(소프트웨어 밸리데이션, Software Validation)는 요구사항, 설계, 시험 조건과 결과를 같은 기능과 식별 ID로 연결하여 작성한다. `SV 문서`는 은수님이 2026-10-13 지정한 약칭이며 기존 SW 밸리데이션 문서와 같은 대상으로 해석한다. E8300과 QCC 내용을 각각 붙인 작업 메모처럼 남기지 않고, 처음부터 하나로 작성한 문서처럼 해당 기능의 동작과 설계 이유를 본문에서 설명한다. 문서 작성 기준 충족, 실제 제품 시험 통과, 사용자 확인, 정식 승인은 서로 다른 상태다.

이 지침은 2026-10-13까지 은수님이 지정한 1~28번 원칙과 1/6/7번 정정, 29번 Word 공통 형식 및 25번 Excel 본문/변경 비교 시트 분리 원칙을 모은 단일 원본이다. 지침의 작성이나 개정만으로 기존 DHF Word/Excel, 펌웨어, 승인 이력을 변경하지 않는다. 산출물 작업은 실제로 맡긴 파일과 범위에 적용한다.

SW 밸리데이션 문서를 작성/수정/병합/검토/재개할 때와 컨텍스트 압축(compact) 후 같은 작업을 이어갈 때는 사용자가 다시 언급하지 않아도 이 지침을 온디맨드로 적용한다. 시작할 때 29개 항목 모두의 적용 여부를 판단하고, 관련 항목을 작성 중과 최종 저장 후 검사하여 기존 작업 기록에 근거, 판정과 재검사를 연결한다. 단순한 경로/상태 조회는 읽기 전용으로 답하며 전체 문서 검사나 요청하지 않은 DHF 수정을 시작하지 않는다.

## 적용할 원본

- [프로젝트 AGENTS.md](../../../../AGENTS.md): DHF 저장 위치, 문서 접두어, 보호 대상, 시험 결과 비교, 담당별 미비 표시의 원본이다. 색상, 글자 크기와 밑줄의 수치는 이곳에서 확인한다.
- [QCC 자료 추가 위치 관리](QCC%20자료%20추가%20위치%20관리.md): 실제 저장본의 제목/ID/시트/셀과 자료 상태를 찾고 갱신하는 중앙 목록이다.
- [Sound1 시스템 구조](../../시스템/Sound1%20시스템%20구조.md): 구조와 동작을 다루는 문서의 출발점이다. 필요한 근거 파일/심볼과 현재 코드를 대조한다.
- [문서 기본 서식](E:/workspace/rules-for-codex/지침/운영/문서%20기본%20서식.md): 원본 보존, 문체, 시험 방법과 Sound1 전환 작업의 지정 사항을 확인한다.
- [Word 공통 형식 안내](E:/workspace/rules-for-codex/지침/양식/Word/README.md)와 [실제 TDC 공통 스타일 DOTX](E:/workspace/rules-for-codex/지침/양식/Word/TDC%20공통%20스타일.dotx): Word 스타일과 적용/검증 방법의 원본이다. 수치 정의를 이 지침에 복제하지 않는다. 다른 PC에서는 `RULES_ROOT`의 실제 위치로 연결을 확인한다.

## 작업 전: 대상과 비교 기준을 정한다

맡긴 산출물, 참고 원본, 보호 대상과 변경 범위를 확인한다. 실제 파일을 열어 현재 내용과 서식을 확보하고, E8300의 동종 항목을 내용/형식의 비교 기준으로 삼는다. 구조 설명을 바꾸는 작업이면 시스템 구조와 해당 코드 경로를 먼저 대조한다. 문구/서식만 고치는 작업에 전체 펌웨어 재분석을 강제하지 않는다.

기존 작업 기록에 아래 29개 항목의 적용 여부와 해당 문서/ID를 연결한다. 해당 문서/변경과 무관한 항목은 이유를 적어 `해당없음`으로 기록한다. 관련 항목의 검사 범위에는 변경 부분뿐 아니라 그 변경으로 영향을 받는 다른 문서의 연결 ID, 조건과 공통 내용도 포함한다. 문서가 존재하거나 지침을 읽었다는 이유만으로 통과를 기록하지 않는다. 원본과 수정본을 구분하고, 다른 작업자의 변경을 보존한다. 이 지침을 사용하려고 새 작업 폴더나 별도 점검 문서를 만들 필요는 없다.

## 작성 중: 실제 본문과 같은 조건의 시험 행을 고친다

기능과 입출력으로 같은 요구임이 확인되면 기존 E8300 요구사항 ID와 상위 추적을 기준으로 통합한다. 실제 차이와 누락만 같은 본문 체계에 반영하며, 해당 문서만 읽어도 동작과 설계 이유를 이해할 수 있게 쓴다. 추적표에 ID를 넣는 것으로 설계 설명을 대신하지 않는다.

시험 조건을 나누거나 방법/통과 기준을 바꿀 때는 기준서를 먼저 고치고 보고서에 같은 공통 열과 행/병합을 적용한다. 결과 근거가 없으면 입력과 예상값은 정의하되 실제 결과를 만들지 않는다. 미비 표시를 바꾸면 중앙 위치 목록도 저장본 기준으로 맞춘다.

## 문서 간 반복: 앞뒤 문서의 같은 항목으로 수렴을 확인한다

6번의 권장 순서로 시작하되 뒤 문서에서 발견한 차이는 앞 문서로 되돌려 수정한다. 예를 들어 SAD의 QCC 유닛/시험 ID 설명이 E8300보다 부족하면, 유닛 검증 기준서/보고서의 목적, 입력, 예상값과 관찰 구조부터 정리하고 미실행 상태를 유지한다. 그 내용을 바탕으로 SAD의 기능 설명을 같은 수준으로 보완한 뒤 SRS, SDDD, 시스템/통합 문서의 영향을 다시 대조한다.

반복 횟수를 고정하지 않는다. 같은 ID의 동작, 조건, 입출력, 예상값, 실제 결과 또는 보류 상태, 용어와 문체가 문서 사이에서 일치하는지로 수렴을 확인한다. 검사에서 발견한 내용/형식 오류는 고치고 해당 항목을 재검사한다. 실제 자료가 없어 확인할 수 없는 부분은 필요한 자료와 판정 대기를 명시한다.

## 최종 저장 검증: 저장한 파일의 내용과 표시를 확인한다

저장 후 파일을 다시 열어 현재 본문, 추적 관계, 시험 공통 열, 수치와 수식, 미비 표시를 검사한다. Word는 전체 페이지를 실제 렌더하고 Excel은 실제 열기와 인쇄 표시로 잘림/병합/테두리를 확인한다. 삭제 추적 문구, 삭제된 표 행, 목차 캐시와 비교 시트의 원문을 현재 본문으로 세지 않는다.

문서 내용이나 형식이 기준과 다르면 수정 후 재검사한다. 원본을 훼손했으면 복구하고 비교 증거를 다시 확보한다. 접근/수정 권한이 없으면 그 범위의 쓰기를 멈추고 실제 장애와 재개 조건을 기록하며, 임의의 다른 경로나 권한으로 우회하지 않는다. 자료 부족을 편집 오류와 섞어 처리하지 않는다. 문서 검사가 통과해도 미실행 제품 시험은 통과로 바뀌지 않는다.

## 자료 대기: 표시 유지와 실제 미비 상태를 구분한다

필요한 자료의 종류, 대상 기능/ID/조건과 남은 판정 범위를 본문과 중앙 위치 목록에 구체적으로 적는다. 자료를 받으면 내용을 반영하고 검사한 범위와 남은 사항을 갱신한다. `[QCC 자료 입력]`과 `[QCC/E8300 자료 입력]`은 자료를 받은 뒤에도 은수님이 해제하기 전까지 유지한다. 접두어가 남아 있다는 사실과 실제 자료가 아직 없다는 상태를 구분하여 기록한다.

문서 작성 기준은 충족했지만 제품 검증 자료가 부족한 경우에는 두 상태를 함께 보고한다. 자료 수신, 문서 반영, 제품 시험 실행/판정, 사용자 확인과 정식 승인 중 어디까지 확인했는지 명확히 한다. 대기 중인 실측/로그/외부 계약을 추정하여 채우지 않는다.

## 29개 작성/검증 기준

각 항목의 `검사/판정`은 실제 대상과 비교 결과를 요구한다. 문서 검사 결과는 `통과 / 실패 / 미실행 / 해당없음`으로 기록한다. 기준에 맞지 않으면 `실패`와 수정할 차이를, 아직 검사하지 않았으면 `미실행`과 남은 검사를, 적용하지 않으면 `해당없음`과 이유를 적는다. 자료 수신/반영 상태와 제품 시험의 실행/판정 대기는 별도 설명으로 구분한다.

### 1. E8300과 QCC의 같은 요구사항을 하나로 완성한다

QCC 요구사항 ID가 잘못 기입되어 E8300과 달라도 기능, 적용 조건과 입출력상 누구나 같은 요구라고 확인할 수 있으면 E8300 요구사항 ID와 기존 상위 추적을 기준으로 통합한다. SRS의 다른 발생원 추적에 QCC 원문 ID를 붙여 같은 요구를 별개로 관리하지 않는다. 매칭이 모호하면 추정하여 합치지 않고 차이와 확인할 사항을 기록한다.

각 산출물에는 통합된 기능의 동작과 설계 이유를 해당 본문에 넣는다. `제공된 QCC 자료에 따르면`, `입력받은 자료를 기반으로`, `원문 추적`, `병합 중` 같은 설명이 설계를 대신하지 않게 한다. 작업 메모와 원문 오기 대응은 로컬 작업/근거 기록에 두며, 정당한 요구사항 추적, 제조사 출처와 실제 미비 표시는 유지한다.

검사/판정: 같은 요구의 기능/조건/입출력 대조 결과, 기존 ID와 상위 추적 보존, 중복 요구 유무, 현재 본문의 동작/이유 설명을 함께 확인한다. ID 문자열만 같거나 다르다는 이유로 판정하지 않는다.

### 2. SRS 내용상세의 기본 문구를 매트릭스와 맞춘다

매트릭스에서 직접 요구한 사항에 연결되는 SRS의 내용상세는 해당 설계 입력 요구사항과 같은 문구로 쓴다. 필요한 보충 설명은 그다음 줄에 `상세: `로 구분한다. 보충 설명으로 기본 요구의 의미나 범위를 바꾸지 않는다.

매트릭스에서 요구한 사항이 아니면 상위 요구사항 ID 칸을 빈칸으로 두고 자체 소프트웨어 요구사항으로 유지한다. 비슷한 문구가 다른 분류에 있다는 이유로 상위 ID를 붙이거나 빈칸 자체를 자료 미비로 표시하지 않는다. 같은 요구사항을 검증하는 시험 기준서/보고서의 상위 추적도 비워 두며 자체 요구사항 ID와 시험 연결은 유지한다(은수님 정정, 2026-10-13).

검사/판정: 직접 상위 요구인지 먼저 확인하고, 연결된 항목만 두 문구의 차이와 추가 설명의 줄 분리를 검사한다. 자체 요구사항은 상위 ID가 비어 있고 SRS와 시험의 자체 ID/내용이 일치하는지 확인한다.

### 3. 요구사항부터 실제 설계와 시험 ID/이름까지 연결한다

요구사항 → 아키텍처 모듈 → 상세 유닛 → 시험을 실제 ID와 이름으로 연결한다. 아키텍처 추적표에서 유닛 역할을 반복 설명하지 않는다. 기능 설명 본문에 필요한 간략한 유닛/시험 설명은 6번에 따라 보완한다. 실제로 없는 ID나 정식 상위 연결을 임의로 만들지 않는다.

아키텍처의 모듈 설명에는 필요한 모듈의 이름과 역할을 적고 모듈 ID를 붙이지 않는다. 모듈 ID는 상세설계에서 부여하며, 아키텍처의 상세설계 추적 테이블에는 관련 모듈과 유닛의 ID를 유지한다. QCC도 기존 E8300과 같은 표기 방식을 따른다(은수님 정정, 2026-10-13).

검사/판정: 추적표의 각 ID가 대응 본문/시험 행에 존재하고 같은 기능을 가리키는지 확인한다. 연결이 없는 곳은 누락인지 실제 미비인지 구분한다.

### 4. 실제 문서 내용과 미갱신 표기를 확인한다

각 파일을 직접 열어 본문, 표와 그림의 내용을 확인한다. QCC 원문의 `스마트케이스`, `CC` 등은 작성자가 덜 갱신한 표기이며 실제 내용은 외부기 QCC라는 사용자 확인을 적용한다. 이름만 보고 별도 제품의 기능으로 나누지 않는다. 원문 오기와 ID 대응 근거는 작업 기록에 남긴다.

검사/판정: 확인한 실제 파일/제목과 본문 기능을 대조하고, 미갱신 표기가 현재 산출물의 제품/기능 설명을 왜곡하지 않는지 확인한다.

### 5. 실제 시스템 구조와 전달 경로를 먼저 이해한다

[시스템 구조 원본](../../시스템/Sound1%20시스템%20구조.md)과 현재 코드에서 실행 코어, 진입/호출, 공유 데이터와 전달 순서를 확인한다. 그림은 장치/칩/코어 경계와 기능 모듈을 구분한다. 여러 코어가 협력하는 기능을 임의의 독립 블록으로 바꾸지 않는다. 없는 QCC 내부 구현을 추정하여 확정하지 않는다.

검사/판정: 문서와 그림의 주장에 대응하는 근거 파일/심볼, 실행 위치, 입출력 경로를 대조한다. 정적 구조 확인과 실제 구현/실측 검증의 범위를 구분한다.

### 6. 권장 순서로 시작하고 양방향으로 반복한다

시작 순서는 SRS → SAD → 시스템 시험 기준서/보고서 → SDDD → 유닛 검증 기준서/보고서 → SIP → 통합시험 기준서/보고서를 안내로 삼는다. 후속 문서에서 앞선 내용과 상충하거나 누락된 사항을 발견하면 해당 문서부터 되돌려 수정하고 영향 문서를 다시 확인한다.

SAD의 QCC 유닛/시험 ID 설명이 E8300과 비교하여 부족하면 유닛 검증 기준서/보고서에서 목적, 입력, 예상값과 관찰 구조를 먼저 정리한 뒤 SAD 설명을 같은 수준으로 갱신한다. 시험이 미실행이면 그대로 유지하며 허구의 유닛, 시험이나 결과를 만들지 않는다. 횟수 대신 같은 ID/동작/조건/예상값/실제 결과 또는 보류/문체의 일치로 수렴을 확인한다.

검사/판정: 발견한 차이가 수정된 문서와 후속 영향 문서에서 해소됐는지 재대조한다. 순서대로 한 번 작성했다는 사실만으로 완료하지 않는다.

### 7. E8300 본문의 형식과 설명 수준으로 QCC를 넣는다

기존 내용으로 충분하면 중복 설명을 추가하지 않는다. E8300의 항목 순서, 설명 형식과 상세 정도, 필드/번호, 표의 너비/열, 본문 위치, 그림과 스타일을 기준으로 QCC 내용을 넣는다. SAD에서 기존 E8300에 없던 `소속 유닛` 등 QCC 전용 설명 틀을 새로 만들지 않는다. SDDD 표는 기존 동종 표의 본문 수준 기준선, 사용 가능 폭, 열폭과 셀 서식에 맞춘다.

원문 문체와 용어를 유지하고 새 문장은 가운뎃점 대신 문맥에 맞는 `/` 또는 `,`로 쓴다. Word 공통 형식은 29번 원본에 따라 지정된 범위에 적용하여 E8300과 QCC가 서로 다른 형식이 되지 않게 한다.

검사/판정: E8300/QCC의 동종 항목을 나란히 비교해 순서/필드/설명 수준/표 폭/기준선/셀 서식이 같은지 확인한다. 불필요한 반복과 QCC 전용 틀은 정리한다.

### 8. 상세설계 본문만으로 구현 조건을 이해하게 한다

유닛의 목적, 입출력, 처리 순서, 알고리즘/수식, 인터페이스와 예외를 설명한다. 후속 시험 ID나 시험 절차를 열어야만 설계를 이해할 수 있게 쓰지 않는다. 현재 빌드의 파일명, 비활성 분기와 과거 변경 내역을 설계 조건으로 고정하지 않는다. 필요한 핵심 데이터/파라미터와 설계 이유는 본문에 남긴다.

검사/판정: 상세설계만 보고 적용 조건, 입력에서 출력까지의 처리와 오류 시 동작을 설명할 수 있는지 확인한다. 핵심 수식/단위/범위와 인터페이스를 근거와 대조한다.

### 9. I/A/D/T 방법과 정의를 정확히 쓴다

I(Inspection)는 제어 또는 시각적 확인, A(Analysis)는 분석 증거에 기반한 확인, D(Demonstration)는 정량 측정 없이 동작 특성 확인, T(Test)는 정량 측정으로 정량 특성 확인이다. 방법 열은 원래 약어 체계를 유지한다. 정의에 불필요한 괄호 예시를 넣지 않는다.

검사/판정: 기준서의 방법 정의와 각 행의 약어를 확인하고, 해당 통과 증거가 정의와 일치하는지 대조한다.

### 10. 도구 이름이 아니라 통과 증거로 방법을 정한다

RTT로 수치/배열/횟수/시간을 정량 비교하면 T로 분류한다. 필요하면 방법을 조합하되 실제 필요한 증거에 한정한다. 설계 입력과 출력의 공통 시험은 입력 기준서를 먼저 갱신하고 출력 방법을 맞춘다. 코드 분석을 핀 전압이나 전극 전류 등 실제 물리량의 실측으로 대신하지 않는다.

검사/판정: 통과 기준이 요구하는 관찰/측정 증거와 방법을 비교하고, 공통 입력/출력 시험의 방법 일치 및 물리 실측의 유무를 확인한다.

### 11. 제3자가 수행할 준비와 절차를 쓴다

준비 조건에는 수행 전 충족해야 할 전제와 사전 구성을 적는다. 실제 장치 연결, 설정, 입력, 조작, 측정과 확인 행동은 절차에 수행 순서대로 쓴다. 플래그는 용도와 값의 의미를 함께 설명한다. 예를 들어 실행 허용 플래그의 0은 금지, 1은 허용으로 쓴다. 모호한 축약이나 불필요한 코드 줄 수정 지시로 절차를 대신하지 않는다.

검사/판정: 준비 조건의 전제/사전 구성과 절차의 실제 행동을 구분했는지 확인한다. 처음 읽는 수행자가 무엇을 어디에 적용하고 무엇을 확인해야 하는지 본문에서 찾을 수 있는지 검토한다. 입력/환경/예상 관찰이 빠진 단계는 보완한다.

### 12. 기준서와 보고서의 공통 열과 행을 동일하게 유지한다

ID, 방법, 준비 조건, 제한 조건, 절차와 통과 기준은 두 문서에서 내용/순서/행/병합을 같게 유지한다. 보고서는 결과와 판정만 추가한다. 보고서에서만 조건 행이나 추가 확인 범위를 만들지 않는다. 행 분리가 필요하면 기준서를 먼저 고친다.

검사/판정: 저장된 기준서/보고서의 공통 열 값, 행 순서와 병합 영역을 직접 비교한다. 차이가 있으면 기준서부터 정리하고 다시 비교한다.

### 13. 같은 입력의 예상값과 관찰값을 본문 같은 행에서 비교한다

입력 조건별 원소의 예상값/허용 범위와 실제 관찰값을 해당 시험의 같은 행에서 비교할 수 있게 쓴다. `예상값과 일치함`만 적거나 다른 시트/부록에만 상세를 두지 않는다. 시험을 참조할 때 ID뿐 아니라 요구사항의 기능 내용도 적는다.

검사/판정: 각 시험 행에서 입력 → 예상/허용 범위 → 관찰 → 판정의 연결을 확인한다. 보고서 본문에 실제 비교값이 없으면 통과 근거로 인정하지 않는다.

### 14. RTT의 전체 문자열과 증거 종류를 구분한다

접두어, C 번호, A 배열의 모든 원소, 줄 나눔과 PASS 요약을 실제 구현된 출력 형식으로 비교한다. 변동값은 허용 범위와 이유를 적는다. 생성한 예상 로그, 코드 분석, 시험자 확인에 따른 기록과 실제 수집 로그를 서로 구분한다.

검사/판정: 구현된 출력 형식과 시험 행의 전체 예상 문자열을 대조하고, 관찰 문자열의 누락/순서/범위와 기입 근거를 확인한다. 기입 근거는 실제 수집 로그 또는 17번에 따라 사용자가 확인한 시험자 결과로 구분한다. 실제 수집 로그로 표시한 결과에는 수집 근거를 확인하며, 시험자 확인 기록을 Codex의 새 로그 수집으로 표현하거나 모든 결과에 원시 로그를 요구하지 않는다.

### 15. 조건 번호와 검증 번호를 빠짐없이 대응시킨다

`조건 [번호]`와 `검증 [번호]`를 빠짐없이 대응시키고 각 검증 아래에 해당 출력값을 둔다. 번호를 바꾸면 입력 조건과 검증/결과의 대응도 함께 보존한다.

검사/판정: 조건과 검증 번호의 개수/순서/대응을 대조하고, 각 번호에 필요한 출력값과 결과가 있는지 확인한다.

### 16. 결과 칸에는 실제 입력/출력/관찰과 근거를 쓴다

결과 칸에 작성 지시나 작업 메모를 남기지 않는다. 시험자가 확인한 실제 결과를 예상값, 코드 반영 후의 가정이나 재시험 예정과 섞지 않는다. 확인된 통과의 판정 칸에는 `통과`만 쓴다. 실제 관찰과 근거는 결과 칸에 두며, 실행/판정이 남은 조건은 그 상태를 유지한다.

검사/판정: 결과 문장이 실제 관찰을 말하는지와 그 근거를 확인한다. 지시문/예정 문구를 실제 결과로 쓰거나 미실행을 통과로 표시한 곳은 수정한다.

### 17. 사용자에게 확인된 시험자 결과의 근거 범위를 지킨다

은수님이 확인한 실제 시험자 결과는 지정된 결과 기입의 근거로 사용할 수 있다. 이를 Codex가 새로 보드에서 실행하거나 원시 로그를 수집한 것으로 쓰지 않는다. PC/RAM/모의 환경과 실제 장치의 확인을 구분한다.

검사/판정: 결과의 출처, 실행 주체와 환경을 대조한다. 실제 확인한 범위를 넘어선 실행/수집/실기 주장이 없는지 확인한다.

### 18. 기존 통과를 새 조건이나 다른 시험 단계로 확대하지 않는다

불일치, 미측정, 미실행과 대기는 판정에서도 보존한다. 기준을 바꾸면 기존 결과가 새 기준을 충족하는지 다시 확인한다. E8300의 지정 입력/응답만 확인하는 시험에는 그 범위에 불필요한 QCC 내부 자료를 요구하지 않는다.

검사/판정: 통과 근거의 입력/조건/단계가 현재 기준과 같은지 확인한다. 미확인 범위를 남기되 이미 확인한 쪽까지 자료 부족으로 표시하지 않는다.

### 19. 과거 지정된 시험자 확인 결과의 수치 처리만 재사용한다

과거에 지정된 시험자 확인 결과 작성 범위에서만 예상 구간의 중간값과 음수의 0 방향 절삭을 사용한다. `-556311.5 → -556311`은 그 처리의 예이며, 일반적인 미측정 값 생성 규칙이 아니다.

검사/판정: 해당 결과에 그 처리의 사용자 지정 근거가 있는지와 계산/절삭 방향을 확인한다. 새 미측정 조건에 중간값을 넣어 실제 결과로 만든 곳은 수정한다.

### 20. 예상 도식과 실제 사진을 구분하고 지정 삭제를 유지한다

예상 파형/LED 도식 안에는 `예상 도식 / 실측 화면 아님`을 표시한다. 임의의 측정값이나 계측기 캡처를 만들지 않는다. 실제 자료가 필요한 자리는 빨간색 `(사진필요)`로 표시한다. 다만 유닛/통합 문서에서 삭제하도록 지정한 사진 요청이나 보조 시트를 자동으로 다시 넣지 않으며, 시스템 문서에서 필요한 자료 자리는 유지한다.

검사/판정: 그림의 예상/실측 구분, 사진 근거와 자료 자리의 필요성을 확인한다. 현재 사용자 지정에 따라 삭제/유지 범위를 대조한다.

### 21. 일반 시간 시험의 날짜와 경계 입력을 구분한다

일반 시간 시험은 기준 날짜 `2026-05-02`, 결과 날짜 `2026-05-29`를 사용한다. 월말/윤년/연말 등 별도 경계 시험의 입력과 작성/승인 이력 날짜를 일괄 치환하지 않는다.

검사/판정: 일반 시간 조건의 날짜와 별도 경계 조건/이력 날짜를 각각 대조한다. 날짜 치환으로 경계 시험이나 승인 사실이 달라진 곳은 수정한다.

### 22. 담당별 표시를 적용하고 자료 수신 뒤에도 지정 접두어를 유지한다

QCC 측 자료, E8300 측 보완, 양쪽 자료가 필요한 사항을 구분하고 [프로젝트 AGENTS의 미비 표시 규칙](../../../../AGENTS.md)에 따라 접두어와 설명 전체에 서식을 적용한다. 주변 기본 크기/굵기를 기준으로 색상, 기본보다 큰 글자와 밑줄이 전체 설명에 맞는지 검사한다. 수치/색상 정의는 AGENTS가 소유한다.

`[QCC 자료 입력]`과 `[QCC/E8300 자료 입력]`은 자료 수신 완료 후에도 은수님의 해제 전까지 유지한다. 자료가 반영된 범위와 남은 설계/검증 부족, 시험 판정을 별도로 구분한다. 표시가 남았다는 이유로 반영된 자료를 다시 미수신으로 기록하지 않는다.

2026-10-13 해제 범위: 은수님이 설계 입력의 Word 정리를 요청한 SR/SGR 통합 문서에서는 위 QCC/공동 입력 요청 문구를 제거하고, 그 안내와 관련하여 실제 반영된 QCC 설명을 본문 크기의 굵은 빨강(`#C00000`)으로 표시한다. 확인되지 않은 버전/사용량/설정/검토 결과는 실제 미확정 범위를 일반 검정 본문과 중앙 목록에 남긴다. 이 두 문서의 `_완료` 접미어는 해당 정리 작업의 완료를 뜻하며 자료 완비, 제품 시험 통과나 승인을 뜻하지 않는다. 기존 `[E8300 보완]` 표시와 다른 문서의 접두어 규칙은 유지한다.

검사/판정: 담당, 전체 문구의 서식, 자료 수신/반영/남은 판정 상태와 해제 지시 유무를 현재 본문 및 중앙 목록에서 대조한다.

### 23. 중앙 QCC 위치 목록을 저장본과 함께 갱신한다

파일, 제목, 시트, 식별 ID, 위치와 상태가 바뀌면 [중앙 QCC 목록](QCC%20자료%20추가%20위치%20관리.md)을 같은 작업에서 갱신한다. 저장된 현재 본문을 기준으로 하며 삭제 추적 문구, 목차와 비교 시트의 원문 행은 현재 위치에서 제외한다. 위치를 추측해서 적지 않는다.

검사/판정: 목록의 링크/검색 위치가 저장본의 실제 제목/ID/셀과 일치하는지 확인한다. 확인일과 자료/검증 상태도 함께 대조한다.

### 24. Excel의 정렬과 행/병합/테두리를 실제 표시로 확인한다

텍스트 셀은 원칙적으로 줄바꿈-내용-줄바꿈으로 쓴다. ID/방법/판정/머리글은 가로/세로 중앙, 긴 절차/기준/결과는 왼쪽 정렬한다. Excel 행 높이는 409.5pt를 넘기지 않으며 내용이 길면 기준서와 보고서의 같은 조건 행 구조를 함께 분할한다. 같은 내용을 분할한 셀은 바깥쪽에만 여백 줄을 두고 내부 경계는 숨기며 병합 영역의 외곽 테두리는 유지한다.

검사/판정: 실제 Excel에서 내용 잘림, 줄바꿈, 행 높이 상한, 정렬, 병합 외곽과 같은 시험의 연결 셀 경계를 확인한다. 분할된 조건의 기준서/보고서 행과 병합 구조도 대조한다. 저장 XML의 설정값만으로 표시 통과를 판정하지 않는다.

### 25. Excel 본문은 적용 내용만 두고 변경 비교는 별도 시트에 작성한다

기존 본문 시트는 변경이 적용된 현재 내용만 표시하고, 변경 비교는 `<원래 시트명>_비교` 시트에 작성한다. 빨간색 `[-]` 원문과 그다음 초록색 `[+]` 수정문은 비교 시트의 해당 항목에 둔다. 본문에는 삭제된 원문이나 비교 표식을 남기지 않는다. 공통 규칙의 원본은 [문서 기본 서식의 SV 문서 약칭과 Excel 변경 비교](E:/workspace/rules-for-codex/지침/운영/문서%20기본%20서식.md#sv-문서의-약칭과-excel-변경-비교)다.

13번의 예상값/실제 관찰값 비교는 시험 본문의 같은 행에 유지한다. 원래 시트명, ID, 수식/참조, 기준서/보고서의 공통 행과 미비 접두어 및 지정 서식도 보존한다. 구분자만 바뀐 것을 실질 내용 변경처럼 표시하지 않는다. 노란 배경은 지정된 검토용 범위에만 쓰고, 복구 지시가 있으면 원래 서식으로 돌린다.

검사/판정: 본문에 변경 비교 표식과 삭제 원문이 없는지, `_비교` 시트에서 원문/수정문의 순서와 색상 및 실제 차이를 확인할 수 있는지 검사한다. 비교 시트의 수정 후 내용과 본문을 대조하고, 무변경 문구/수식/참조/시험 결과/미비 표시가 보존됐는지 확인한다. 추가 시트도 실제 열기와 표시를 검증하며 중앙 목록은 기존 본문의 현재 위치를 기준으로 유지한다.

### 26. Word 본 파일에 실제 수락/거부 가능한 변경 추적을 남긴다

삽입/삭제를 실제 변경 기록으로 남기고 작성자는 김은수로 적용한다. 기존 이력을 보존하며 추적 없는 사본이나 `_변경추적` 파일을 불필요하게 중복 생성하지 않는다. 사용자가 최종본이나 추적 없는 문서를 명시적으로 요청하면 그 지시를 우선하며, 비교 원본이 없는 신규 문서에는 전체 내용을 삽입 이력으로 남기도록 강제하지 않는다. 공통 스타일, 목적 본문, 입출력/처리 표, 번호 계층과 표 뒤 간격은 29번 원본으로 확인한다.

검사/판정: 변경 추적을 적용한 문서는 검증용 사본에서 새 변경의 수락 결과가 의도한 수정과 같고 거부 결과가 변경 전 내용/그림을 복원하는지 확인한다. 저장본의 이력을 임의로 모두 수락하지 않으며 작성자/기존 추적/필드 보존도 대조한다. 예외 적용은 해당 사용자 지시 또는 비교 원본이 없는 신규 작성이라는 근거와 함께 기록한다.

### 27. 원본, 산출물 경로와 작성/승인 정보를 보존한다

QCC 정보를 추가하는 작업에서는 기존 E8300 문서와 QCC 참고 원문을 보존하고 같은 G드라이브 단계의 `SW/외부기`에 `[E8300-QCC]` 사본을 작성한다. 이 사본 의무를 일반 SW 문서 작업 전체에 적용하지 않는다. `[작성자 전용]` 파일은 수정/교체/이름 변경에서 제외한다. 경로/문서 구분은 [프로젝트 AGENTS](../../../../AGENTS.md)를 따른다.

Sound1 전환 작업의 지정값인 작성 김은수 수석연구원, 개정 0, 작성 일자/서명과 검토/승인 빈칸, 1.5세대와 같은 품목 등급은 [문서 기본 서식](E:/workspace/rules-for-codex/지침/운영/문서%20기본%20서식.md)에서 확인한다. 원본의 과거 승인 이력은 보존하되 이를 신규 문서의 승인 사실로 복사하지 않는다.

검사/판정: 실제 경로/접근, 보존 대상 원본 불변, 보호 파일 제외, 표지/작성 정보와 기존 이력을 대조한다. 파일 접두어만으로 승인이나 검증 완료를 판정하지 않는다.

### 28. 최종 저장 내용과 전체 표시를 검증한다

연결 ID, 조건, 수치/수식과 기준서/보고서의 공통 내용을 저장본에서 비교한다. Word는 전체 페이지의 글자/표 잘림과 넘침, 빈 페이지, 제목/캡션과 목차/필드의 정합성을 확인한다. Excel은 실제 열기, 높이/병합/테두리와 인쇄 표시를 확인한다.

검사/판정: 저장 후 재열기와 전체 표시 검사, 내용 비교의 실제 결과를 기록한다. 문서 검증, 제품 시험, 사용자 확인, 정식 승인의 증거를 각각 구분하며 파일 저장 성공만으로 통과를 선언하지 않는다.

### 29. 우리의 Word 공통 형식을 같은 본문 체계로 적용한다

SW 밸리데이션 Word의 작성/검증은 [공통 형식 README](E:/workspace/rules-for-codex/지침/양식/Word/README.md)와 [실제 DOTX](E:/workspace/rules-for-codex/지침/양식/Word/TDC%20공통%20스타일.dotx)를 기준으로 한다. QCC 표에만 별도 스타일을 만들지 않는다. 현재 요청의 범위, 기존 E8300 본문의 형식과 번호 체계를 확인하고 공통 스타일을 적용한 뒤 저장 DOCX 안에 스타일 정의가 포함됐는지 검사한다. 다른 문서나 PC 기본 템플릿은 자동 변경하지 않는다.

본문/표/캡션은 설명하는 본문 수준의 기준선과 사용 가능 폭에 맞춘다. 동종 표의 열폭/셀 서식, 제목/분류와 설명의 색상/정렬, 자동 번호와 제목/본문/목차 수준, 캡션과 필드의 연결을 확인한다. 정확한 숫자와 색상 정의는 DOTX/README의 단일 원본을 사용한다.

유닛 목적은 표 밖의 일반 본문으로 설명하고 입출력/처리는 유닛 설계 내용 표로 정리한다. 필요한 구현 조건은 별도 표로, 원리/알고리즘 설명은 본문/수식/그림으로 유지한다. 각 본문 표 뒤의 정상 빈 문단, 설명 뒤 새 유닛의 구분과 불필요한 연속 빈 문단을 확인한다. 정상 본문 크기/줄간격을 유지하고 작은 글씨나 숨김 문단으로 페이지 나눔을 감추지 않는다.

검사/판정: 실제 DOTX와 저장 DOCX의 스타일/자동 번호/참조 관계를 대조한다. 모든 대상 유닛의 목적/I/O/처리, 표 기준선/폭/열폭/색상/정렬/반복 머리행, 수식/그림/캡션, 정상 빈 문단과 페이지 나눔을 전체 실제 렌더에서 확인한다. 변경 추적을 적용한 문서는 수락/거부를 검증하고, 기존 내용/ID/수식/그림 보존도 확인한다. 스타일을 복사했거나 README를 읽었다는 사실만으로 통과하지 않는다.

## 기존 작업 기록에 남길 최소 검사 기록

기존 작업 기록에 항목 번호, 문서 ID/제목, 실제 절/시트/셀, 기대와 실제 차이, 검사, 결과와 재검사를 남긴다. 전체 문서 내용이나 구조 사실을 작업 기록에 복제하지 않는다. 문서 검사 결과는 `통과 / 실패 / 미실행 / 해당없음`으로 쓰고, 수정 필요 사항은 실패의 설명으로 적는다. 실제 자료/제품 판정 대기는 별도 열 또는 설명으로 구분한다.

아래 행은 기록 형식의 예시이며 실제 검사나 제품 시험 결과가 아니다. 실제 작업에서는 확인한 문서/ID/위치와 관찰 결과로 바꾼다.

| 항목 번호 | 문서 ID/제목 | 절/시트/셀 | 기대와 실제 차이 | 검사 | 결과 | 재검사 |
|---|---|---|---|---|---|---|
| 12/13 | 해당 유닛 검증 기준서/보고서의 실제 문서 ID/제목 | 실제 시험 ID의 시트/셀 | 공통 절차는 동일해야 하나 보고서에만 조건 설명이 추가됨 | 기준/보고 공통 셀 값과 병합, 같은 행 예상/관찰 대조 | 실패(공통 절차 수정 필요); 별도 제품 시험 상태: 미실행 | 기준서 반영 후 보고서 공통 열과 실제 표시를 다시 확인하고 관찰 결과 기록 |

내용/형식/원본 보존 오류는 맡긴 범위에서 수정하고 재검사한다. 권한/접근 문제는 해당 범위의 실제 장애로 기록한다. 자료 부족은 필요한 자료와 남은 제품 판정을 명시하여 대기 상태를 유지한다. 이 구분을 지켜 문서 작성 완료를 제품 시험 통과나 정식 승인으로 확대하지 않는다.
