# 유닛 시험 일괄 실행 매뉴얼

**시험용으로 한 번 준비한 뒤, RTT GUI에서 `ut auto 1`을 입력하면 CM3와 CFX의 준비된 시험을 연속 실행하고 로그를 모을 수 있다.** HEAR와 부트로더는 준비 조건이 달라 각각 한 번 더 실행한다. 실제 입력이나 사진이 필요한 항목은 뒤의 순서표대로 진행한다.

이 문서는 사용 순서다. 각 시험의 입력값과 예상값 전체는 [유닛 시험 예상 입출력](유닛%20시험%20예상%20입출력/README.md), 한 줄씩 비교할 로그는 [예상 로그 전문](유닛%20시험%20예상%20입출력/예상%20로그/README.md)에 있다. 기존 유닛 번호와 기대값은 바꾸지 않았다.

장치에서 실행한 결과를 넣은 문서는 아니다. 이번에는 PC 검사와 시험 이미지 빌드까지만 수행했다. 시험 지그에서 사용하고, 착용 중인 제품에는 실행하지 않는다.

## 1. 어떤 순서로 하면 되는가

| 순서 | 할 일 | 한 번에 얻는 결과 |
|---|---|---|
| 1 | PC 전체 검사 실행 | 코드 확인, RAM 입력 시험, 검사 도구 결과 |
| 2 | 시험 이미지로 준비하고 RTT GUI 연결 | 로그 자동 저장 시작 |
| 3 | `ut auto 1` 입력 | CM3 33개 유닛/34회 실행, CFX 29개 유닛 연속 출력 |
| 4 | HEAR 준비 후 `ut hear 1` 입력 | HEAR 2개 유닛의 6개 입력과 FFT/크기 원본 배열 |
| 5 | 부트로더 시험 환경에서 `ut boot 1` 입력 | BOOT 9개 유닛 연속 출력 |
| 6 | 실제 입력/사진 순서표 실행 | 관련 상태 일괄 기록, 필요한 사진/파형 |
| 7 | 로그 파일 한 번 추출 | 유닛별 `.log`, 결과 요약, 수집 검사 결과 |

3~5번은 **73개 유닛의 준비된 자동 경로**다. 부분 시험도 포함하며 115개 유닛 전체를 자동 합격 처리하는 기능이 아니다. PC 전용 경로, 코드 확인, 실제 저장소/핀/빛/소리, QCC 내부 검증은 각각 남는다.

## 2. 처음 한 번만 준비하기

### 2.1 시험 코드와 이미지 준비

저장소 루트에서 다음을 실행한다. 아래 명령의 `python`은 Python 3 실행 파일이다. 현재 PC에서는 `C:\Users\EUNSU\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`도 사용할 수 있다. 다른 PC에서는 경로가 다르다.

```powershell

```

1. 끝의 모든 검사 결과를 확인한다. `HARNESS_OK`는 검사 도구가 예상대로 동작했다는 뜻이다. 기록 안에 남은 제품의 `FAIL`까지 통과라는 뜻이 아니다.
2. PC 결과는 `tmp/unit-tests/suite`에서 확인한다. 이 폴더를 통째로 보관한다.
3. 장치에는 아래 **test** 이미지를 평소 사용하는 디버그 다운로드 절차로 준비한다. 이 명령 자체는 장치에 다운로드하지 않는다.

| 코어 | 시험 이미지 |
|---|---|
| CFX | `tmp/unit-tests/target/CFX/test/test_image` |
| CM3 | `tmp/unit-tests/target/CM3/test/test_image.elf` |
| BOOT | `tmp/unit-tests/target/BOOT/test/test_image.elf` |

### 2.3 자동 시험을 시작할 정지 상태 만들기

이 단계는 최초 준비다. 준비가 끝나면 개별 유닛 함수를 하나씩 호출할 필요가 없다.

1. 시험 지그를 사용한다. CFX 오디오/PCM, CM3 정상 반복 처리와 시험 RAM을 바꾸는 ISR/DMA를 멈춘다. ISR 중간이나 파일 쓰기 중간이 아닌 전경의 안정된 정지점에서 시작한다.
2. CM3 공유 변수 `cfx_cm3_sharedMemoryAll.is_enabled_CFX_iteration`을 확인한다. 자동 시험에서는 **0(정상 CFX 실행 금지)**이어야 한다. 이 값만 0으로 바꿨다고 이미 실행 중인 CFX가 멈추는 것은 아니다. CFX 정상 루프도 실제로 정지해야 한다.
3. SPI 송신 버퍼가 비어 있고 I2C가 대기 상태인지 확인한다. 이전 시험의 미배출 결과가 있으면 먼저 그 로그를 끝까지 받은 뒤 해제한다. `done`만 강제로 지워 덮어쓰지 않는다.
4. CFX 계산 경로에 필요한 기존 초기화/HEAR 메모리 배치가 완료되어 있어야 한다. HEAR 시험까지 할 때는 올바른 마이크로코드와 512개 창 계수, 완료 인터럽트를 준비한다. HEAR 완료 ISR까지 막으면 HEAR 시험은 끝나지 않는다.

`ready=1`은 이 준비를 시험자가 확인했다는 표시다. 시험 코드가 모든 하드웨어를 자동으로 정지시킨다는 뜻이 아니다. 준비 여부가 불분명하면 1을 넣고 진행하지 않는다.

### 2.4 현재 빌드용 호출 명령 받기

```powershell
python tests/unit/prepare_batch_debug.py
```

`tmp/unit-tests/batch/현재-빌드-시작명령.txt`가 만들어진다. 파일의 1~4번을 순서대로 실행한다. **현재 CFX 이미지에서 계산한 주소가 들어 있으므로, 재빌드한 뒤에는 이 명령도 다시 생성한다.** 이전 빌드 주소를 복사하지 않는다.

- CFX에서 시험 worker를 준비한다. 최초 token은 1이다.
- CM3에서 해당 worker 주소를 등록한다. 주소는 CFX XMEM **워드 주소**이며 4를 곱하지 않는다.
- CFX에서 서비스 함수를 실행해 요청을 기다리게 한다.
- CM3에서 `call tdc_ut_cm3_console_serve(1)`을 실행한다. 반환을 기다리지 말고 RTT GUI로 이동한다.
- GUI에 `[UT-CONSOLE] READY`가 보이면 준비 완료다.

CFX와 CM3의 시험 함수가 함께 실행될 수 있어야 한다. 한 코어를 실행하면 다른 코어를 강제로 멈추는 디버거 설정에서는 이 전달 방식이 진행되지 않는다. READY가 안 나오거나 오류가 나오면 그룹 명령을 반복해서 넣지 말고 정지 조건/현재 이미지/코어 실행 상태를 확인한다.

HEAR 준비까지 완료한 경우에는 `python tests/unit/prepare_batch_debug.py --hear-ready`로 생성한다. 준비하지 않은 상태에서 이 옵션으로 준비 확인을 대신하지 않는다. 같은 이미지에서 worker를 다시 준비할 때는 `--token 2`처럼 이전과 다른 번호를 사용한다.

CFX 준비 없이 CM3만 시험하려면 2.3의 조건을 확인한 뒤 CM3의 `tdc_ut_cm3_console_serve(1)`만 호출하고 다음의 `ut cm3 1`을 사용한다.

## 3. 자동 시험: 명령 하나 입력하고 끝까지 받기

### 3.1 CM3와 CFX를 이어서 실행

GUI 아래 **명령 >**에 다음 한 줄을 넣고 Enter를 누른다.

```text
ut auto 1
```

CM3 결과 뒤에 CFX 결과가 이어진다. 아래 두 종료 줄과 마지막 READY를 확인한다.

```text
[UT-BATCH] CORE=CM3 END N=34
[UT-BATCH] CORE=CFX END N=29
[UT-CONSOLE] READY
```

**END는 준비된 실행과 RTT 배출을 끝냈다는 뜻이지 전체 통과가 아니다.** 그 사이에 `FAIL` 또는 `OBSERVED`가 있어도 지우지 말고 원본을 보관한다. CM3-029는 정상 입력 뒤 실패 경로 관찰도 별도로 실행하므로 유닛 수 33개와 실행 수 34회가 다르다.

다시 실행하려면 READY 이후 같은 명령을 한 번 더 넣는다. 앞 결과를 모두 내보낸 뒤 다음 유닛을 실행하므로 배열을 덮어쓰지 않는다. 실행 중 다른 그룹 명령은 대기열에 쌓지 않고 거부한다.

### 3.2 필요한 그룹만 다시 실행

| GUI 명령 | 내용 | 종료의 N |
|---|---|---:|
| `ut cm3 1` | CM3 전체 자동 경로 | 34 |
| `ut cm3 2` | CM3 계산/상태 제어, 계산 실패 관찰 포함 | 22 |
| `ut cm3 3` | CM3 I2C/SPI/기기 제어/OTA의 RAM 입력 | 12 |
| `ut cfx 1` | CFX 계산/혼합/패킷 RAM 입력 | 29 |
| `ut hear 1` | 준비된 실제 HEAR의 최대값 1입력, FFT 5입력 | 6 |

HEAR는 FFT 원본 512개, 크기 원본 256개, 블록 지수까지 출력하므로 로그가 길다. 비교 결과와 `OBSERVED` 원본을 모두 보관한다. 시각상 그래프가 비슷한지만 보고 수치 비교를 대신하지 않는다.

### 3.3 BOOT는 별도 이미지에서 한 번 실행

1. 응용 프로그램 시험을 종료한다. BOOT 시험 이미지를 별도 디버그 환경으로 준비한다.
2. RTT/UART 초기화가 끝나고 다른 부트 처리, 파일/CRC, scratch/BRAM 사용자가 멈춘 전경에서 시작한다. 다른 코어도 해당 메모리를 사용하면 안 된다.
3. 디버거에서 `call tdc_ut_boot_console_serve(1)`을 실행한다.
4. RTT의 READY를 확인하고 `ut boot 1`을 입력한다.
5. `[UT-BATCH] CORE=BOOT END N=9`와 READY를 확인하고 로그를 저장한다.

파일 관련 부분만 반복할 때는 `ut boot 2`(7개), CRC/AES만 반복할 때는 `ut boot 3`(2개)다. 실제 NVM 쓰기, 이미지 전송, 코어 점프나 리셋을 자동으로 실행하는 그룹은 아니다. CRC 장치는 준비되어 있어야 하며 시험 중 독점한다.

### 3.4 중지와 종료

- 현재 묶음을 중지: `ut stop`
- 시험 콘솔 종료: `ut quit`
- 상태 요청: `ut status`. 실행 중 요청한 상태 응답은 시험 로그 줄이 섞이지 않도록 해당 실행이 끝난 뒤 표시될 수 있다.

중지하면 이미 보낸 줄을 마무리하고 결과 소유권을 정리한다. END가 전송되기 시작한 직후의 중지는 이미 완료된 그룹의 END를 지우지 않는다. `ut auto 1`에서 CM3 종료 시점에 중지했으면 다음 CFX 그룹을 새로 시작하지 않는다.

CFX 서비스는 CM3 콘솔과 별개다. 정상 종료 후 `tdc_ut_cfx_bridge_restored()`가 1임을 확인하고 CFX의 `g_tdc_ut_cfx_batch_service_stop=1`로 서비스를 끝낸다. 시험 뒤에는 정상 신호 경로를 그대로 이어 쓰지 말고 재기동한다.

오류 줄에 **`RESTORED=0`**이 있거나 HEAR가 아직 pending이면 입력/출력 메모리를 임의 해제하지 않는다. CFX 서비스를 계속 실행해 실제 완료/복원을 기다리며, 정상 동작으로 복귀하지 않는다. 단순 RTT 연결 해제나 프로그램 카운터 강제 변경은 안전한 취소 절차가 아니다.

이때 다음 CM3 자동/관찰 그룹도 거부한다. `ut quit` 뒤 `WAITING_RESTORE`가 보이면 콘솔이 복원을 기다리는 중이다. 복원이 끝나기 전에 CFX 서비스를 끄지 않는다. 디버거에서 `g_tdc_ut_console_transport_fault=1`이면 전송 함수의 반환값이 잘못된 상태이므로 재전송/정상 복귀를 막는다. 원본 로그를 보관하고 시험 지그를 안전한 상태로 만든 뒤 재기동한다.

콘솔 대기 중에는 기존 워치독의 refresh만 수행한다. 주기/설정은 변경하지 않으며 이 콘솔로 워치독 자체를 검증하는 것은 아니다.

## 4. 사람이 입력할 시험: 한 조건당 관련 상태를 한 번에 받기

자동 그룹의 RAM 입력은 프로그램이 넣는다. 아래 그룹은 **실제 입력을 대신 만들지 않는다.** 터치, QCC 연결/명령, 실제 파일/전원 상태를 적용한 뒤 그때의 여러 상태를 함께 보관한다. 전부 `OBSERVED`이며 자동 PASS를 만들지 않는다.

| 명령 형태 | 한 번에 기록하는 상태 |
|---|---|
| `ut observe 1 101` | 장치 상태와 통신/저장 상태 24개 |
| `ut observe 2 101` | 터치/I2C/SPI/내부기/저장 요청 등 17개 |
| `ut observe 3 101` | 통신/명령/OTA 등 7개 |

마지막 수 `101`은 **입력 단계 번호**다. 다음 조건에서는 102, 103처럼 바꾼다. 여러 상태를 차례로 읽지만 생산자를 멈춘 상태에서 한 번에 보관한 뒤 출력하므로, 로그 출력 시간 때문에 원래 관찰할 상태가 바뀌지 않는다.

### 입력과 결과 취합 순서

1. 정상 시험 동작에서 아래 표의 조건을 적용한다. 자동 시험 콘솔이 실행 중인 상태에서는 정상 제품 루프가 입력을 처리하지 않으므로, 먼저 자동 시험을 종료하고 정상 동작 시험 환경으로 다시 시작한다.
2. 원하는 입력의 처리가 끝난 시점에 정상 루프/다른 코어/관련 ISR을 안정된 지점에서 정지한다. **두 코어가 실제로 정지한 뒤** `cfx_cm3_sharedMemoryAll.is_enabled_CFX_iteration`의 원래 값을 메모하고 0으로 둔다. 콘솔의 시작 조건이다. 플래그만 지워 실행 중인 CFX가 정지했다고 간주하지 않는다.
3. CM3 시험 콘솔을 열고 표의 명령을 한 번 입력한다. 이 시점에는 SPI/I2C의 사용 중 상태도 관찰할 수 있으며, 캡처가 거래를 새로 시작하지는 않는다.
4. END와 READY를 확인한다. 예: `ut observe 3 102`이면 `CORE=CM3 END N=7`.
5. `ut quit`으로 닫고, 여전히 정지된 상태에서 위 실행 허용 값을 원래 값으로 돌려놓는다. 다음 입력은 준비 상태를 확인한 정상 시험 환경에서 진행한다. 같은 원본 로그 파일을 계속 수집하면 입력 단계 C101/C102 등으로 찾을 수 있다.

| 순서 | 실제로 적용할 입력 | 기록 명령 | 같이 남길 자료 |
|---|---|---|---|
| 101 | 터치하지 않은 안정 상태 | `ut observe 2 101` | 상태 로그 |
| 102 | 터치 후 기준서에서 정한 입력 처리가 끝난 상태 | `ut observe 2 102` | 상태 로그, 표시가 판정 조건이면 LED 사진 |
| 103 | 매핑/리모콘에서 기준서의 정상 읽기 또는 설정 명령 1개 실행 | `ut observe 3 103` | 보낸 명령/인자와 실제 응답 원문 |
| 104 | 같은 명령의 기준서상 잘못된 입력 적용 | `ut observe 3 104` | 오류 응답, 이전 설정 유지 여부 |
| 105 | 실제 저장/다시 읽기 시험을 승인된 시험 저장소에서 수행 | `ut observe 1 105` | 저장 전/후 데이터와 재읽기 결과 |

이 표는 같은 준비를 반복하지 않기 위한 실행 묶음이다. 기준서의 모든 정상/경계/오류 입력을 5개 사례로 줄이라는 뜻은 아니다. 각 유닛의 [입력과 예상 결과](유닛%20시험%20예상%20입출력/README.md)에 있는 조건별로 단계 번호를 이어 사용한다. 저장소 시험은 RAM 그룹과 다르므로 실제 파일을 지우는 동작을 이 매뉴얼이 자동 승인하지 않는다.

현재 구조에서는 실제 입력을 처리하는 정상 루프와 상태를 보관하는 정지 시험을 나눠야 한다. 따라서 **이 관찰 그룹만큼은 입력마다 정지/캡처가 필요**하다. 제품 루프를 수정하지 않은 채 실행 중 상태의 동시 변경까지 안전하게 막는 기능이라고 설명하지 않는다.

### QCC 자료 추가 위치

QCC 내부 시험 자료가 오면 위 103/104에 실제 QCC 명령/응답, 오디오 연결 상태 입력을 대조해 추가한다. 현재 그룹은 E8300 측 상태를 보는 기능이다. QCC 내부 검증 완료로 바꾸지 않는다. 자료 위치는 [QCC 자료 추가 위치 관리](../../../../QCC%20자료%20추가%20위치%20관리.md)에서 관리한다.

## 5. 사진/스코프는 필요한 것만 같은 배치에서 찍기

RAM 수치와 소스 분석으로 확인하는 항목에 스코프 촬영을 추가하지 않는다. 기준서가 물리 출력을 요구하는 경우만 아래처럼 묶는다.

| 묶음 | 순서대로 할 일 | 보관할 결과 |
|---|---|---|
| LED / 기동 표시 | 정상 시험 환경에서 기동 표시 확인 → 전원/사용/매핑/오류 등 기준서의 표시 조건 적용 → 각 상태 촬영 | 입력 조건이 적힌 사진, LED 실제 색/점멸 기록. CM3-014/BOOT-004의 전체 조건표와 비교 |
| UART 송수신 | 시험 지그의 UART TX/RX와 GND 연결 → 현재 UART가 실제 활성인지 확인 → 기동 또는 지정 명령 실행 → TX/RX가 같이 보이는 화면 촬영 | 스코프 원본, 시간축/전압축/프로브 설정, 보낸/받은 데이터. 현재 소스 baud는 921600이며 이론 비트 폭은 약 1.085 us |
| OD 소리 | 자동 RAM 시험을 종료 → 정상 OD 출력 경로와 보드에 맞는 수신기 연결 확인 → 연속 1000 Hz 사인파/무음을 차례로 입력 → 들리는 소리 확인 | 입력 주파수/볼륨/출력 경로와 청취 결과를 글로 기록. 청취 사진은 불필요. CFX-020 자동 벡터는 소리를 재생하지 않음 |
| PMIC 전압 | 현재 보드에서 사용하는 전원 소자와 기준서의 전압 조건 확인 → 필요한 레벨만 측정 | 측정 위치/전압/조건. CM3-039의 비활성 구형 PMIC를 현재 보드 시험으로 취급하지 않음 |

Calibration 핀은 현재 오디오 경로에서 DMIC 클럭과 공유한다. 핀 이름만 보고 1 ms 처리 완료 신호라고 판단하지 않는다. 현재 측정 코드가 어느 시작/끝을 표시하는지 확인된 경우에만 그 조건으로 캡처한다. 이번 작업은 측정용 GPIO나 제품 동작 코드를 추가하지 않았다.

사진 파일에는 유닛/조건을 넣는다. 예: `CM3-014_C101_LED.png`. 사진을 나중에 찍을 항목은 보고서의 `(사진필요)`를 그대로 둔다. 예전 예상 그림을 실측 화면으로 대신하지 않는다.

### 5.1 OD 출력은 무엇을 확인하는가

**CFX-020의 자동 시험은 RAM 계산값, 보조 청취는 실제 소리 확인이다.** 증가 배열과 포화 경계 배열을 넣는 C1/C2가 1 kHz 사인파나 8 kHz 사인파를 재생하는 것은 아니다.

| 확인할 것 | 실행/관찰 지점 | 남길 자료 |
|---|---|---|
| 64배 확대와 24비트 포화 | 자동 그룹 실행 후 RTT의 `UT-CFX-020` C1/C2 배열과 판정 줄 | 원본 `.log`. 정수 계산에 스코프 사진은 불필요 |
| 순음과 무음의 구분 | 정상 OD 경로로 연속 1000 Hz 사인파와 무음을 입력하고 보드에 맞는 수신기로 청취 | 입력 조건과 실제 들린 소리를 글로 기록. 사진은 불필요 |
| 파형의 보조 확인 | 아래 필터 후 OUT+/OUT- 차동 출력 | 추가 측정할 때만 스코프 화면. 1 kHz의 참고 주기는 1 ms. 정확한 전압/왜곡률의 새 합격 기준은 아님 |

OD1_P/OD1_N은 차동 PDM 출력이다. 핀에서 직접 보면 고속 펄스가 나타나므로 사인파 모양을 바로 볼 수 없다. 무음에서도 두 핀이 반드시 0 V로 멈추는 것은 아니다.

스코프용 필터는 onsemi 개발 보드의 회로를 사용한다. 저항 2.2 kΩ 4개, 커패시터 560 pF 2개이며, 두 커패시터는 GND가 아니라 두 신호선 사이에 연결한다.

```text
OD1_P -- 2.2k --+-- 2.2k --+-- OUT+
               |          |
             560pF      560pF
               |          |
OD1_N -- 2.2k --+-- 2.2k --+-- OUT-
```

전원을 끈 상태에서 연결한다. 저항은 1%, 커패시터는 C0G/NP0를 권장한다. 이 필터는 고입력 임피던스 스코프 측정용이며 이어폰을 직접 연결하는 회로가 아니다.

일반 접지형 스코프는 같은 설정의 10배 프로브 두 개를 사용한다. CH1은 OUT+, CH2는 OUT-에 대고 두 프로브의 접지는 모두 보드 GND에 연결한다. 입력은 1 MΩ으로 두고 MATH의 `CH1-CH2`를 본다. OD1_N이나 OUT-에 접지 클립을 연결하지 않는다. 스코프 보호접지를 해제하지 않는다. 1 kHz 확인은 시간축 200 us/div 정도에서 시작한다.

회로 근거: [onsemi Ezairo 8310 개발 보드 설명서, 출력 필터 회로](https://www.onsemi.com/pub/Collateral/EVBUM2877-D.PDF). 출력 형식: [Ezairo 8300 데이터시트](https://www.onsemi.com/pdf/datasheet/e8300-d.pdf). 이 설명은 회로/코드 검토 결과이며 실제 보드의 파형이나 청취 결과가 아니다.

### 5.2 자료 종류를 혼동하지 않기

기준서와 보고서의 같은 시험 행에 입력 조건, 확인 위치, 남길 자료를 함께 적었다. 먼저 해당 행을 읽고 아래처럼 자료를 모은다.

| 항목 | 이렇게 수집한다 | 이 자료로 대신하지 않는다 |
|---|---|---|
| RAM 계산/패킷/상태 | 준비된 그룹 실행 후 조건별 배열과 판정 줄이 포함된 원본 `.log`를 저장 | 전극 전류, OD 파형, 실제 핀 전압, 실제 파일 저장 완료 |
| 실제 HEAR 계산 | 초기화와 완료 인터럽트를 준비하고 FFT/크기/지수 원본 배열까지 저장 | PC에서 생성한 예상 배열이나 비교 결과 `1`만 있는 기록 |
| LED | 조건별 색은 사진, 점멸/밝기 변화는 한 반복 이상 보이는 영상과 관찰 기록 | RAM의 LED 요청값이나 GPIO 쓰기 횟수 |
| 명령/앱 표시 | 보낸 명령/인자, 실제 응답 원문, 해당 표시 화면을 같은 조건으로 저장 | 명령 접수만 확인한 상태값이나 코드에 적힌 예상 ACK |
| 실제 전극 출력 | 기준서의 맵/음원/전극/부하를 적용하고 해당 전극 파형과 스코프 설정을 저장 | PCM의 Amplitude 값, 예상 파형 그림, PMIC 공급전압 |
| 실제 저장/DMA | 격리 시험 영역에서 저장/전송 전후 데이터, 재읽기, 완료 상태와 길이를 저장 | 요청 주소나 표식 한 개만 있는 PC/RAM 시험 |
| 시스템 시험 12/58의 1 ms 처리 | 시작/완료 시각을 타깃 타이머로 기록하는 계측 준비 후 수집. 현재는 준비 필요로 남김 | PC의 RTT 수신 시각, 로그 출력 간격, DMIC 클럭으로 사용 중인 Calibration 핀 |
| QCC 내부 동작 | QCC 입력/응답과 내부 결과를 담당 자료로 확인 | E8300의 상태값만으로 QCC 검증 완료 판정 |

BOOT-018의 `reboot` 확인은 PC 전용 시험이다. 실제 타깃 서비스에 보내면 재시작하므로 자료 수집 명령으로 사용하지 않는다. BOOT-015의 실제 DMA 확인도 운영 코드/스택/다른 코어 메모리와 겹치지 않는 시험 영역을 먼저 정해야 한다. 이 두 항목은 `ut boot 1`의 자동 9개 유닛에 포함되지 않는다.

보고서의 `(자료 필요)`, `(사진필요)`, `(시험 결과 기입 필요)`는 실제 자료가 남은 자리다. 알려진 불일치와 미수집 값은 지우지 않고 해당 조건의 결과/판정에 남긴다.

### 5.3 기준서 옆에 결과 붙여 넣기

1. 유닛 검증 기준서의 `기준서_유닛 검증`에서 D열 시험 ID 또는 G열 유닛 ID로 시험을 찾는다. K열에 그 시험의 입력, 원소별 예상값, 전체 예상 RTT와 필요한 관찰값 비교 기준이 모두 있다. 여러 행으로 나뉜 경우 같은 시험 안에서 이어 읽는다.
2. 유닛 검증 보고서의 `보고서_유닛 시험`에서 같은 ID를 찾는다. A~K열과 행 구성이 기준서와 같다. 해당 입력을 적용한 실제 결과 또는 수집 RTT를 같은 조건의 L열에 붙여 넣는다. K/L열의 폭을 같게 두어 옆에서 비교할 수 있다.
3. `조건 [번호]`는 비교 항목 번호이고 `RTT C번호`는 시험 코드의 벡터 번호다. 번호만 같다고 연결하지 말고 입력 내용과 RTT의 유닛/조건을 함께 확인한다. `(계속)`이나 `1/2`, `2/2`로 나뉜 값은 같은 조건의 이어지는 결과다.
4. M열의 기존 판정을 실제 수집 자료와 대조한다. 기존 시험자 확인 기록을 새 수집 원문으로 바꾸어 부르지 않는다. 오류/자료 대기는 실제로 해소됐을 때만 갱신한다. 보조 시트는 이전 기록 보존용이며, 통과 판단을 위해 따로 찾아갈 필요는 없다.

## 6. RTT 화면에서 골라 보고 복사하기

**검색 또는 Ctrl+F → 레벨 ALL → 모듈 입력 → 적용** 순서다. 모듈 칸에는 대괄호를 넣지 않는다.

| 보고 싶은 내용 | 모듈 칸 |
|---|---|
| 시험 로그 전체 | `UT-` |
| 시작/종료/오류 안내 | `UT-BATCH` |
| CM3 전체 | `UT-CM3-` |
| CFX 전체 | `UT-CFX-` |
| HEAR 전체 | `UT-HEAR-` |
| BOOT 전체 | `UT-BOOT-` |
| 유닛 하나 | 예: `UT-CM3-027` |

복사는 **화면 정지 → 필터 적용 → 필요한 줄 드래그 → Ctrl+C**다. 캡처할 때도 화면 정지 후 Windows 캡처 도구를 사용한다. 화면 정지는 수집/파일 저장을 멈추지 않는다.

CFX/HEAR의 원시 배열에는 `[UT-BATCH] ... RAW=FFT/VMAG/EXPONENT/NUMERIC` 구분 줄이 붙는다. 유닛 하나로만 화면 필터를 걸면 이 줄은 가려지므로, 원시 배열 종류까지 볼 때는 `UT-` 필터나 아래의 유닛별 추출 파일을 사용한다. 추출 파일에는 원시 배열 구분 줄도 함께 남긴다.

주의할 것은 세 가지다.

- GUI는 최근 5,000줄만 보여 준다. 전체 시험 증거는 자동 저장된 원본 `.log`다. 화면에서 안 보이는 옛 기록은 필터로 되살릴 수 없다.
- 모듈은 부분 문자열 검색이다. `CFX|CM3` 같은 정규식/여러 태그 OR 검색은 지원하지 않는다.
- GUI 오류 개수는 유닛 시험의 FAIL 개수가 아니다. 시험 결과는 `[UT-...] ... PASS/FAIL/OBSERVED` 줄로 구분한다.

## 7. 한 파일을 유닛별 결과로 나누기

시험이 끝나고 GUI에서 **끊기**를 누른 뒤 저장된 원본 로그 파일 경로를 아래에 넣는다.

```powershell
python tests/unit/collect_rtt.py "실제로 저장된 RTT 로그 파일의 전체 경로.log"
```

로그 옆에 `시험결과_날짜_시각` 폴더가 만들어진다. 이전 결과 폴더를 덮어쓰지 않는다.

| 파일 | 사용 방법 |
|---|---|
| `원본.log` | 수정하지 않은 전체 수집본. 반드시 보관 |
| `전체-시험.log` | `[UT-...]` 줄만 모아 빠르게 보기 |
| `CM3-027.log` 등 | 유닛별로 보고서/예상 로그와 대조 |
| `결과 요약.md` | 유닛별 수신 PASS/FAIL/관찰 개수, 불일치 조건 찾기 |
| `수집검사.json` | 원본 해시, 수신 배열과 불일치, 묶음 시작/끝, 형식 오류 확인 |

요약의 관찰 개수에는 FFT/크기/SDK 계산 원본 배열도 포함된다. 같은 시험 조건에서 여러 배열을 출력한 횟수이지 서로 다른 시험 ID의 수는 아니다. JSON의 `array_kind`로 일반 결과, NUMERIC, FFT, VMAG, EXPONENT를 구분한다.

추출기는 **수신한 배열의 순서/인덱스/종료 줄과 묶음 BEGIN/END를 검사**한다. 통째로 빠진 시험이나 아직 실행하지 않은 조건까지 자동으로 합격 처리하지 않는다. 아래 목록의 선택한 유닛과 해당 [예상 로그 전문](유닛%20시험%20예상%20입출력/예상%20로그/README.md)을 함께 대조한다. 예상 로그의 `legacy_current`처럼 다른 호출 방식인 블록은 이번 실행에 섞지 않는다.

## 8. 묶음에 들어 있는 유닛 찾기

유닛 번호는 각 코어 안의 현재 기준서 번호다. 물결 범위는 양 끝을 포함한다.

| 묶음 | 유닛 번호 |
|---|---|
| CFX 자동 | 007, 008, 010~013, 015~020, 022~037, 040 |
| CM3 계산/제어 | 004, 006, 007, 009, 011~013, 016~024, 027~030, 044. 029 실패 관찰 추가 |
| CM3 IO | 010, 025, 026, 034~037, 040, 045, 047, 050, 051 |
| HEAR | 001(C1), 002(C1~C5). FFT/크기/지수 원본도 함께 출력 |
| BOOT 자동 | 008~014, 019, 020 |
| CM3 장치 상태 관찰 | 002, 010, 025, 026, 031~043 |
| CM3 통신/저장 상태 관찰 | 045~051 |

자동 타깃 그룹 밖의 CFX 001~006/009/014/021/038/039/041/042, CM3 001~003/005/008/014/015/031~033/038/039/041~043/046/048/049, BOOT 001~007/015~018은 PC 검사/분석/관찰/물리 확인의 해당 범위를 사용한다. 번호가 없어진 것은 아니며 [115개 전체 목록](유닛%20시험%20예상%20입출력/README.md)에서 각 절차를 찾는다.

알려진 불일치는 별도 수리 없이 그대로 남는다. 예를 들어 CFX-015, CM3-006/028/029/030, BOOT-011의 일부 입력이 그렇다. 이번에는 CM3-051의 **시험용 SPI 완료 처리**만 보완해, 인터럽트를 막은 RAM 시험이 두 번째 응답에서 멈추지 않게 했다. 제품의 OTA 처리 결과나 기대값을 통과하도록 고친 것은 아니다.

## 9. 멈추거나 결과가 안 보일 때

| 보이는 상황 | 할 일 |
|---|---|
| `ERROR NOT_STARTED` | 그룹 번호/준비 상태/미배출 결과/CFX 주소와 token 확인. 시작되지 않은 시험을 통과로 기록하지 않음 |
| 실행 중 새 명령 뒤 `BUSY_COMMAND_REJECTED` | 앞 시험이 끝나 READY가 보인 다음 필요한 명령을 다시 한 번 입력 |
| 로그가 멎고 END 없음 | RTT 연결/저장 상태와 두 코어 실행 상태 확인. 화면 정지 여부와 실제 수신 정지를 구분 |
| `ERROR`, `ABORT`, `CANCEL`, `RESTORED=0` | 원본 로그 보관. 완료/합격으로 기록하지 않음. pending과 복원 상태 확인 |
| 값이 다르다는 `FAIL` | 해당 C 번호의 입력/기대값/실제값 비교. 기존 알려진 불일치인지 확인. 기대값을 실측에 맞춰 수정하지 않음 |
| 화면에서 앞 시험이 없어짐 | 원본 로그를 `collect_rtt.py`로 나누어 해당 유닛 파일 확인 |

현재 GUI 기능과 명령은 해당 프로젝트의 소스를 확인한 기준이다. 이 매뉴얼 작성 과정에서 실제 J-Link 연결, 다운로드, 자극 출력 또는 실기 통과 확인을 수행하지 않았다.
