# 인공와우 전기자극 파라미터 임상 검토 — Sound1 펌웨어 근거 기반 분석

**작성자 페르소나**: 인공와우 전기자극(신경자극) 임상/생리학 전문가
**근거 원칙**: 모든 코드 인용은 `src/` 소스 직접 확인 결과이며, 확인되지 않은 부분은 "추가 검증 필요"로 표시함

---

## 1. Biphasic Pulse(Negative-First)가 표준인 이유

인공와우 전기자극은 조직·전극 손상을 막기 위해 **전하 균형(charge balance)**을 반드시 지켜야 한다 — 음상으로 흘려보낸 전하량과 양상으로 되돌리는 전하량이 정확히 같아야, 전극-조직 계면에 순(net) 전하가 축적되어 발생하는 비가역적 전기화학 반응(전극 부식, 조직 손상, pH 변화)을 피할 수 있다. 음상을 먼저 주는 이유는 음전류가 신경 세포막을 직접 탈분극(depolarization)시켜 활동전위를 유발하는 데 더 효율적이기 때문이다.

**코드 근거**: `firstPulsePhase`는 0(음상 선행, `negativePulseFirst`)/1(양상 선행)로 정의되며, 라이브 자극·특정 자극·eCAP 측정 등 모든 기본 세팅 경로에서 예외 없이 `negativePulseFirst`로 초기화된다(`mappingControl.c:2347,2380,2510`).

## 2. Duration(13~255µs)이 커질 때 임상적으로 달라지는 것

### 2.1 전하량(Q=I×duration) 관점

`setting_stimulationRange()` 내부: `deliveryCharge_pico = maxStimul_uA * pulseWidth;`(`stimulationParaCal.c:218`) — 전류×duration을 그대로 계산. 이 값이 `df_MaxDeliveryCharge_pC`를 넘으면 `MaxDeliveryChargeOver=true`로 에러 처리한다(설계상).

### 2.2 ⚠️ 발견: 이 안전 로직이 라이브 자극 경로에서 비활성 상태로 보임

전하 초과 검사는 `#ifdef Df_MaxDeliveryChargeLimitation` 블록 안에 있다(`stimulationParaCal.c:216`). 그런데 실제 정의된 매크로는 `Df_MaxDeliveryChargeLimitationKKK`(`processorDirective.h:117`, "KKK" 접미사 포함)이며, "KKK" 없는 이름은 **어디에도 정의되어 있지 않다**(전체 grep 확인, 검증 단계에서 재확인 CONFIRMED). 즉 라이브/일반 매핑 자극(NofM·CIS) 경로에서는 전하 초과 검사가 컴파일에서 빠지고 `MaxDeliveryChargeOver=false` 고정 경로만 실행된다. 반면 eCAP·임피던스 측정 등 별도 함수는 동일 검사가 `#ifdef` 없이 무조건 실행된다. 의도적 비활성화인지 리팩토링 중 이름 불일치인지는 소스만으로 판단 불가 — **추가 검증 필요**.

### 2.3 duration ↔ 동적 영역(dynamic range)/slope와의 관계

DAC slope 선택은 채널 간 전류 폭(dynamic range)에만 의존하며, duration은 이 분기 로직에 관여하지 않는다. duration은 오직 전하량 계산에만 쓰인다. **"duration이 커지면 전류가 자동 조정된다"는 관계식은 코드상 찾지 못했다 — 추측하지 않는다.**

### 2.4 duration ↔ 프레임 수 관계 (확실)

`duration_token = 2×pulseWidth + 4 + 10 = 2×pulseWidth+14`(`stimulationParaCal.c:32-58`). 1프레임=41usec. duration이 커질수록 채널당 필요 프레임 수가 늘고, 결국 1ms당 처리 가능 채널 수(`24/frameNumPerChannel`)가 줄어든다 — 즉 **duration↑ → 동시 자극 가능 채널 수 및 CIS 채널당 자극 빈도 ↓**.

## 3. NofM(고정 16채널) vs CIS(가변 rate) 비교

### 3.1 NofM의 채널 선택과 지각적 이점

`stimulationStrategy_NofM_Peak_Pick()`(`stimulationStrategy.c:140-260`)는 전체 M개 대역 중 진폭이 가장 큰 상위 16개(`df_MaxNum_NofM=16`)만 자극한다(SPEAK/ACE류와 같은 원리) — 신호 대 잡음비 개선, 채널 간 상호작용(channel interaction) 완화, 고정 rate로 시간적 피치 부호화 안정화라는 이점. `calculationStimulParaN_cfxShare()`에서 `frameNumPerOneChannel=3`, `transferableChannelNum=8`로 duration 무관하게 강제 고정(`stimulationParaCal.c:597-598`)되어 "고정 rate" 설계 의도가 코드로 뒷받침된다. (500pps라는 구체 수치는 이번 검색에서 직접 확인하지 못함 — 단, 검증 단계에서 `stimulationStrategy.c`의 mod-16 wrap 로직으로 500pps가 코드로 도출 가능함이 별도 확인됨.)

### 3.2 CIS: duration에 따라 rate가 변하는 트레이드오프

CIS는 매 사이클 모든 채널을 순차 자극하며, 실제 채널당 rate는 `24/frameNumPerChannel(duration)`에 좌우된다 — **duration을 늘릴수록(더 큰 자극 강도) 1ms당 처리 채널 수가 줄고, 개별 채널의 자극 빈도가 낮아지는 trade-off**가 있다.

### 3.3 비교 요약

| | NofM | CIS |
|---|---|---|
| 채널 수 | 항상 16개(상위 진폭 선택) | 설정된 전체 채널(≤32) 순차 자극 |
| Rate | 고정(500pps, 코드로 도출 가능) | duration에 따라 가변 |
| 임상적 함의 | 채널 상호작용 감소, 타이밍 예측 가능, 낮은 진폭 채널 정보 손실 가능 | 전 채널 정보 보존, duration↑ 시 시간적 세부정보 전달력 저하 가능 |

## 4. ⚠️ 중요 검토: NofM 3프레임 강제 + 대형 duration 조합 위험

### 4.1 사실관계

`calculationStimulParaN_cfxShare()`(`stimulationParaCal.c:571-627`): ① `frameNumPerOneChannel = calculationNumFramePerOneChannle(pulseWidth)`로 실제 필요 프레임 계산 → ② NofM 분기 진입 시(`numFrequencyBand>=16`) **duration과 무관하게 `frameNumPerOneChannel=3`으로 강제 덮어씀**(`:597`). duration이 커서 실제 4프레임 이상 필요해도(raw=2p+14≥123, 즉 **p≥55usec**) 이를 막는 가드가 이 함수 안에 없다.

### 4.2 실제 발생 가능한 시나리오인가?

상위 BLE 프로토콜(`mappingControl.c:436-440`)에는 `stimulationPulsePhaseWidth`의 `13~255` 범위 검사만 있고, NofM 전략일 때 duration 상한을 더 좁히는 조건은 없다(전략 검사와 duration 검사가 완전히 독립적). 이 가드 부재는 실제 커밋 이력에도 남아있다 — `/* IMPORTANT : NofM 사용 시 프레임 수 고정. NofM 가능 여부를 판별하는 기능이 필요함 */`(`stimulationParaCal.c:587`)라는 개발자 자신의 미해결 To-Do 주석.

### 4.3 판단 및 위험도

이 갭이 실제 안전 위험인지는 FPGA/COLA 하위 동작(프레임 부족 시 잘림/타이밍 지연 등)에 달려 있어 **소스코드만으로는 확정할 수 없다 — 추가 검증 필요**. 상위 UI/피팅 소프트웨어 단에서 별도로 duration 상한을 좁히고 있을 가능성도 배제 못함(이 리포지토리 범위 밖).

**웹페이지 반영 제안**: "확정된 버그"로 단정하지 말고 **"코드로 확인된 미해결 갭(known gap)"**으로 경고 배지(노란색 ⚠) 처리 권장. duration≈55usec 부근에서 시각적 경고.

## 5. IDLE 시간 = "전력 절감"이라는 단순 대응의 타당성과 주의점

IDLE이 전력 소모를 줄이는 방향으로 기여하는 것은 일반적으로 타당하나, "IDLE=곧 저전력"으로 단순 대응하는 것은 주의가 필요하다. 실제로 `frame_3_perChannel()`에서 원래 유휴 슬롯에 넣던 `pcm_Mold_NopStandby`를 `pcm_Mold_NopBacktel`로 바꿔 **백텔 수신 실패를 막기 위해 일부러 2프레임분 회로를 추가 가동**시킨 변경 이력이 있다(`docs/tasks/signalProcessing/20260514_nofm-tuning/분석.md` §1.1). 즉 "자극 신호 없음"이 "회로가 완전히 쉼"을 의미하지 않을 수 있다 — 웹페이지에서 과도한 단순화 지양.
