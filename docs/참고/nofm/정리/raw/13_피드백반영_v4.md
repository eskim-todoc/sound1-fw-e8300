## TL;DR

2펄스 상세 그림의 간격 표현 방식이 모호해 `AskUserQuestion`으로 확인 후("채널 자신의 예약 슬롯 기준" 채택) 재설계했다. 그 외 컨트롤 레이아웃·기본값·NofM 한계 마커·hidden 버그 수정도 함께 반영했다.

## 1. 2펄스 상세 그림 재설계 (사용자 확인 완료)

기존 방식(고정 116px 예산에 pulse 전체를 욱여넣고 "// break"로 IDLE 압축 표시)의 문제:
- 매 duration마다 116px에 다시 맞추다 보니 **interphase gap이 duration에 따라 상대적으로 커졌다 작아졌다** 함 (실제로는 gap=4usec 고정인데 시각적으로 변함) → "Negative 끝나고 Positive가 붙어서 나와야지" 피드백의 원인.
- 실제 IDLE(1ms~32ms)을 압축해 "// "로 표시 → "13패킷 기준으로 만들라"는 피드백의 원인.

**재설계 (사용자가 3안 중 "채널 자신의 예약 슬롯 기준" 선택)**:
- 전역 고정 스케일 `pxPerUsec = 15px / 41usec`(패킷 1개=15px)를 채택 — duration과 무관한 절대 스케일이므로 gap(4usec)이 항상 정확히 같은 픽셀 폭으로 그려짐(왜곡 버그 해결).
- 펄스1은 자신의 예약 슬롯(`frames(p)`개 패킷, 실측 폭) 안에 실측 축척으로 그려지고, 예약 슬롯 중 파형이 차지하지 않는 나머지는 `--idle-fill`(NOP 여백)로 표시.
- 펄스2는 펄스1의 예약 슬롯이 끝나자마자(간격 없이) 동일하게 반복 — "13패킷"은 곧 `frames(255)=13`(최대 패킷 수)이 스케일의 기준.
- **실제 재자극 주기(수백 usec~32ms)는 그림에 축척으로 넣지 않고, 캔버스 아래 텍스트 캡션으로만 표기**("실제 다음 자극까지 ≈ Xms (Ypps) · 자극 후 IDLE ≈ Zms") — 그림과 완전히 분리.
- Python으로 p=13/54/55/255 각각 검산: 파형이 항상 예약 슬롯 폭 안에 들어맞고(spare 4~18px), gap 픽셀폭이 duration과 무관하게 일정함을 확인.

## 2. 그 외 반영 내역

| 요청 | 반영 |
|---|---|
| 2펄스 그림을 CIS/NofM 테이블의 하위 항목으로 | `.stats-card` 하나로 통합(통계 그리드 + 구분선 + 2펄스 그림), 개별 카드 테두리 제거해 "균형있는 박스" 하나로 |
| Duration 막대 더 길게/뚝뚝 끊기는 느낌 | `<datalist>`로 13/34/54/55/123/164/205/255 지점 눈금 추가 + 슬라이더 `min-width:260px`로 확장 |
| 표시구간·최소슬롯폭을 오른쪽으로 이동 | `.controls-secondary`(margin-left:auto)로 분리, 폰트도 더 작고 muted하게 |
| 기본값 5ms·20px | `msWindowSel` 기본 5ms 유지, `zoomRange` 기본값 14→20px(`currentSlotPx` 초기값도 동기화) |
| Duration 막대에 NofM 54 한계 위치 표시 | `.nofm-limit-mark`를 `left:16.94%`((54-13)/(255-13))에 절대배치, NofM 강조색 세로선 + "NofM 한계" 라벨 |
| NofM 2펄스 박스도 불가 시 "펄스 남겨놓지 말고" | **버그 발견·수정**: `#nofm-pulse-detail`은 `class="tl-canvas"`를 가지는데 `canvas.tl-canvas{display:block}` 규칙이 `[hidden]{display:none}` UA 기본값보다 우선 적용되어(author vs UA 오리진 규칙), `.hidden=true`로는 실제로 안 숨겨지고 있었음. `element.style.display="none"` 인라인 스타일로 직접 제어하도록 수정(인라인 스타일이 항상 최우선) — 이제 불가 시 이전 펄스 그림이 확실히 사라지고 "불가" 메시지만 표시됨 |

## 3. 한계

이번에도 브라우저 렌더링 없이 정적 코드 검토 + Python 수치 재현으로 검증했다. `nofm-limit-mark`의 `left:16.94%`는 네이티브 `<input type=range>`의 트랙 좌우 여백(썸 반지름만큼의 inset)을 보정하지 않은 근사치이므로, 실제 브라우저에서 1~3px 정도 어긋나 보일 수 있다.
