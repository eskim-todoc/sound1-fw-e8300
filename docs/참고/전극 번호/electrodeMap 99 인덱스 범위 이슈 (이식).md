# electrodeMap 99 인덱스 범위 이슈 (이식본)

> **이 문서는 이식본이다.** `sullivan-1-5-fw-hw-test-link-pwr-bt-period`에서 규명·해결한 내용을, 같은 CFX/CM3(ez8300) 코드를 공유하는 파생 프로젝트(`sullivan-1-5-fw`, `sound1-fw-e8300` 계열)가 **자기 코드에서 점검·적용**할 수 있게 경로에 의존하지 않고 정리했다. 라인 번호는 원천 프로젝트 기준 참고값이며, **자기 프로젝트에서는 심볼로 찾는다.**

**TL;DR**: 매핑 앱은 미사용 밴드의 전극번호를 **99**로 채워 보낸다. 펌웨어가 이를 걸러내지 않고 `electrodeMap[99 - 1]` = `electrodeMap[98]`을 읽으면 **32원소 배열을 68이나 넘는 미정의 동작**이고, 그 쓰레기값이 `<< 10` 되어 **PCM 자극 몰드를 파괴**한다. 방어는 인덱싱 직전에 **`1 ~ 32` 범위를 검사해 벗어나면 그 채널을 건너뛰는 것**이다. 원천 프로젝트에서도 자극 경로(testStimulation·Live)만 방어됐고 **eCAP·impedance·SpecificStimulation은 아직 무방비**다.

## 1. 문제

### 1.1 무슨 일이 일어나나

```
[SPI RX] 0x90 02 20 63 63 63 ...
                 ↑  ↑
                 │  └ stimulationElectrodeNum[0] = 0x63 = 99 (미사용 센티널)
                 └ usableElectrodeNum = 0x20 = 32   ("32채널 쓴다")
```

앱이 **"32채널을 쓴다"고 하면서 전극번호는 32개 전부 99**를 보내는 모순된 데이터가 실기에서 관측됐다. 펌웨어는 이를 그대로 인덱스로 썼다.

### 1.2 왜 위험한가

| 항목 | 값 |
|---|---|
| `electrodeMap` 크기 | **32** (`int electrodeMap[32];`) |
| 읽는 인덱스 | `99 - 1 = 98` |
| 초과량 | **+66 원소** (배열 밖 미정의 동작) |
| 읽히는 값 | **링커가 배열 뒤에 둔 무언가. 빌드마다 다르다.** 실기에서 `70378` 관측 |
| 결과 | 전극번호 필드는 5비트(`electrodIndexPositionAtPCM_Mold` 만큼 `<<`). 큰 값이 상위 비트를 침범해 **자극 몰드가 뭉개짐** |

이 값이 자극 PCM 버퍼 전체에 실려 자극 유지 시간 내내 내보내진다.

## 2. 원인

- **직접 원인**: 앱 패킷의 전극번호 필드값을 **범위 검사 없이** `electrodeMap[값 - 1]`의 인덱스로 사용
- **구조적 원인**: 바이폴라 기능이 추가되면서(원천 프로젝트 2025-12-17) 전극번호를 `electrodeMap`으로 변환하는 코드가 여러 경로에 **복사되어 퍼졌고**, 원본에 있던 `!= 99` 체크가 일부 경로에서 누락됐다

> [!WARNING]
> **`!= 99` 하나만 거르는 것은 범위 검사가 아니다.** 99만 막으면 `0`이나 `33` 이상은 여전히 통과해 배열을 넘는다. 반드시 **`1 ~ 배열크기` 범위**로 검사해야 한다.

## 3. 해결 — 인덱싱 직전 범위 검사

### 3.1 방어 패턴

```c
// 앱 전극번호를 내부 번호로 변환한 뒤(변환은 별도 문서 참조), 인덱싱 직전에 검사
internal_num = convert_app_electrode_to_internal(app_electrode_num);

if ((internal_num < 1) || (MAX_ELECTRODE_NUM < internal_num))
{
    continue;   // 범위 밖이거나 미사용(99). 이 채널은 Nop(무자극)으로 남긴다.
}

value = electrodeMap[internal_num - 1];   // 이제 안전
```

핵심 두 가지:
1. **변환 함수는 99·범위 밖 값을 숨기지 않는다** — 그대로 돌려줘 이 범위 검사가 잡게 한다 (책임 분리)
2. **루프 상한도 이중 가드** — `for (i=0; (i < usableElectrodeNum) && (i < MAX_ELECTRODE_NUM); i++)`. 앱이 `usableElectrodeNum`에 32 초과를 보내도 버퍼 밖으로 안 나간다

### 3.2 `continue`로 건너뛴 채널의 처리

건너뛰기 전에 **모든 슬롯을 Nop(무자극)으로 미리 채워** 둔다. 그러면 건너뛴 채널은 자연히 Nop으로 남아 안전하다. (자극 루프 앞에 `pcm_Mold_NopStandby` 선채움이 있는지 확인)

## 4. 원천 프로젝트의 적용 현황 (2026-08-04)

| 경로 | 상태 | 비고 |
|---|---|---|
| 테스트 자극 (`testStimulation`) | **방어됨** | 변환 + 범위검사 + 루프 이중가드 |
| 라이브 자극 (`mapping_Live`) | **방어됨** | 변환 사용 |
| 맵 초기화 (`ci_map`) | **방어됨** | 변환 사용 |
| 자극 파라미터 설정 (`stimulationParaSetting`) | 방어됨 | `continue` 방식 (루프 안) |
| 특정 자극 (`SepcificStimulation`) | **부분** | `if/else`로 일부만. PCM 자극 전극번호 계산 등 무방비 잔존 |
| eCAP 측정 (`eCAP_Measurement`) | **무방비** | ISD 레지스터에 앱값 직접 |
| 임피던스 측정 (`impedanceMeasurement`) | **무방비** | ISD 레지스터에 앱값 직접 |

> [!IMPORTANT]
> **"조사했다"와 "해결했다"는 다르다.** 원천 프로젝트도 자극 출력 경로만 방어했고 측정 경로(eCAP·impedance)와 특정자극 일부는 **잠재 위험으로 남겨** 두었다. 매핑 앱이 정상값을 보내는 동안에는 증상이 없지만, 앱 버전 변경·프로토콜 확장 시 재발할 수 있다. **이식 시 자기 프로젝트에서도 같은 무방비가 있는지 확인하라.**

## 5. 이식 체크리스트 (자기 프로젝트에서)

1. [ ] `electrodeMap`(또는 동등 배열)의 **크기**를 확인한다 (보통 32)
2. [ ] `electrodeMap[` 를 **전수 grep**한다 (`head_limit` 없이, 분모 확인)
3. [ ] 각 인덱싱의 **인덱스 출처**를 판정한다:
   - 상수·내부 루프 카운터·내부 배열값 → **안전**
   - **앱 패킷의 전극번호 필드** → 검사 필요
4. [ ] 앱값을 쓰는 곳에 **`1 ~ 배열크기` 범위 검사**가 있는지 본다. `!= 99` 만 있으면 **불충분**
5. [ ] 무방비 지점에 §3.1 패턴을 적용한다:
   - 루프 안이면 `continue`로 완전 방어
   - 단일 흐름(`switch`)이면 대입을 `if/else`로 감싸되, **같은 필드를 쓰는 다른 case도 함께** 막는다 (한 곳만 막으면 다른 case가 남는다)
6. [ ] 건너뛴 채널이 **Nop으로 남는지** 확인한다 (선채움 여부)
7. [ ] 루프 상한이 `usableElectrodeNum`만 보는지, `&& (i < MAX)` 이중가드가 있는지 확인한다

## 6. 대안 (원천 프로젝트에서 검토됨, 미적용)

| 대안 | 장점 | 단점 |
|---|---|---|
| 지점마다 `if` 검사 (현재 방식) | 선례와 일치, 지점별 처리 가능 | 여러 곳에 흩어짐, 새 경로 누락 위험 |
| **접근자 함수** `electrode_map_safe(num)` — 범위 검사 후 무효면 더미(31) 반환 | 한 곳에서 막음, 새 경로 자동 보호 | 무효값에 자극이 나갈 수 있어 자극 출력 영향 (HW 검증 필요) |
| 패킷 수신 시 1회 검증·거부 | 가장 근본적 | 매핑 프로토콜 동작 변경, 앱 호환성 확인 필요 |

> [!NOTE]
> 접근자 함수 방식은 무효값에서 **자극을 생략하는 것**이 더미 전극으로 대체하는 것보다 안전하다. 적용 시 HW 게이트·자극 출력 검증이 필요하다.
