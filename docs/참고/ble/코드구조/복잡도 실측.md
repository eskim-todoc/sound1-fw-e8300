# BLE 복잡도 실측

**TL;DR**: `tdc_ble_mapping.c`(2,196줄)는 사실상 함수 6개뿐이고 그중 `fetch_packet` 1개가 1,724줄(78%)을 차지한다. 데이터 인덱스 분기는 비-라이브 구간만 봐도 결정 포인트의 약 59%를 차지해 복잡도의 최대 단일 요인이지만, 20바이트 MTU 제약의 필연적 귀결이라 제거가 아니라 흡수 대상이다. 진짜 고칠 수 있는 근인은 함수 분해 부재·상태 4층 분산·프로토콜 파서의 자극 FSM 구동 셋이다.

## 1. `tdc_ble_mapping.c` 함수 인벤토리

파일 전체에 **함수가 6개뿐**이다(static 데이터 2개 제외). 복잡도가 여러 함수에 분산된 게 아니라 함수 1개에 응축돼 있다는 것 자체가 핵심 발견이다.

| 함수명 | 라인 범위 | 줄 수 | 역할 | 호출하는 곳 |
|---|---|---|---|---|
| `tdc_ble_mapping_fetch_packet` | `:52-1775` | **1,724** | Rx 20워드 SPI 패킷을 명령별로 파싱해 `mappingPacket`에 적재, 범위 검사, 필요 시 loop-back 응답 | `tdc_ble_communication.c:309` |
| `tdc_ble_mapping_step` | `:1777-2171` | **395** | 매 tick `mappingPacket.command`를 실행 - 대부분 `tdc_isd_map_*` 모듈로 위임 | `tdc_ble_communication.c:404` |
| `tdc_ble_mapping_clear_command` | `:26-32` | 7 | `command`를 IDLE로, 라이브 subCommand를 Standby로 리셋 + PCM 모드 정지 | 파일 내부 11곳 + 외부 `isd/` 5개 모듈 약 30곳 이상 |
| `tdc_ble_mapping_change_command_ble_disconnected` | `:34-37` | 4 | `command`를 `en__mapping_ble_disconneted`(0x10)로 설정 | `tdc_ble_communication.c:459` |
| `tdc_ble_mapping_change_command_waiting_ble_off` | `:39-42` | 4 | `command`를 `en__mapping_waiting_for_BleOff`로 설정 | `tdc_isd_map_data.c:182` |
| `tdc_ble_mapping_get_packet` | `:45-48` | 4 | `mappingPacket`의 **가변** 포인터 반환(`const` 버전은 `:44`에 주석 처리돼 죽어있음) | `isd/` 6개 모듈 |

**함수 6개가 파일의 2,138/2,196줄(97.3%)**을 차지하며, `fetch_packet` 하나가 그중 78%(1,724/2,196)다. 사실상 이 파일에는 "함수 분해"라는 개념이 없고, `fetch_packet` 내부의 `switch(tempCommand)` → `switch(subCommandData_Num_index)`/`switch(liveSubCommand)` 중첩 스위치가 함수 분해를 대신한다.

`tdc_ble_mapping_get_packet()`이 `const`가 아닌 원본 포인터를 그대로 반환한다는 점은 `isd/` 6개 인접 모듈이 `mappingPacket`을 자유롭게 직접 수정할 수 있음을 뜻한다 - 상세는 [`결합도와 계층 경계.md`](결합도와%20계층%20경계.md).

## 3. 데이터 인덱스 분기가 차지하는 비중

`BLE_DataPacketSize=20`(헤더 1 + 페이로드 19)이라는 고정 패킷 크기 제약 때문에, 한 번에 다 못 보내는 명령은 패킷 [1]번 바이트를 "데이터 인덱스"로 써서 여러 패킷에 걸쳐 순차 전송한다. 데이터 인덱스를 쓰는 매핑 명령은 4개(0x66·0x68·0x6C·0x6D)이며, 그 스위치문 합계가 847줄(`fetch_packet` 1,724줄의 49.1%)이다.

| 기준 | 데이터 인덱스 스위치 내 결정 포인트 | 대상 구간 결정 포인트 | 비중 |
|---|---|---|---|
| `fetch_packet` 전체(0x66 포함) | if 50 + case 56 + for 28 = 134 | 226 | **약 59%** |
| `fetch_packet` **비-라이브**(0x68·0x6C·0x6D만) | if 27 + case 41 + for 14 = 82 | 140 | **약 59%(58.6%)** |

라이브를 완전히 배제하고도 데이터 인덱스 분기가 비-라이브 `fetch_packet`의 결정 포인트 약 59%, 줄 수의 약 48%(519/1,079줄)를 차지한다 - 단일 최대 항목이다.

> [!NOTE]
> 위 백분율은 정적 라인 패턴(`if`/`case`/`for`/`while`) 자동 계수 기준이며 단일 실측이라 **소수점 정밀도는 보증되지 않는다**. 다만 "데이터 인덱스 분기가 지배적"이라는 정성적 결론 자체는 코드에서 직접 확인된다. 이 수치에 정밀하게 의존하는 결정(예: 임계값 비교)은 내리지 않는다.
>
> 데이터 인덱스 분기는 매핑만의 문제가 아니라 **BLE 전역 패턴**이다 - 리모콘 0x4C·0x4D도 동일한 다중 패킷 재조립 구조(`subCommandData_Num_index` 변수명까지 동일)를 쓴다(`tdc_ble_remote.c:101-338`, `:372-573`).

## 4. 순환 복잡도 추정치

정적 라인 패턴(`if`/`case`/`for`/`while`) 매칭 기준 자동 계수다. 정식 CC 분석 도구(lizard/pmccabe 등)를 실행하지 않았으므로 **어디까지나 추정치이며 도구로 검증되지 않았다.**

| 범위 | if | case | for | while | 결정 포인트 합 | 순환복잡도 추정(합+1) |
|---|---|---|---|---|---|---|
| 파일 전체 | 129 | 104 | 36 | 2 | 271 | **272(추정)** |
| `fetch_packet` 전체 | 109 | 83 | 34 | 0 | 226 | **227(추정)** |
| `fetch_packet` 중 라이브(0x66) case | 44 | 24 | 18 | 0 | 86 | 87(추정) |
| `fetch_packet` 중 비-라이브 | 65 | 59 | 16 | 0 | 140 | **141(추정)** |
| `step()` 전체 | 20 | 21 | 2 | 2 | 45 | **46(추정)** |

통상 함수 단위 CC 10 초과를 "복잡", 50 초과를 "고위험"으로 보는 관행치에 비추면, `fetch_packet` 하나(추정 227)만으로도 관행치의 4배가 넘는다. 라이브 구간을 빼고도(추정 141) 여전히 압도적으로 크다.

## 6. `ST__MAPPING_PACKET` 구조체 분석

8종 페이로드 구조체가 **union 없이** 동시에 필드로 존재한다(`tdc_ble_mapping.h:109-121`). 멤버 개수 기반 추정치이며(4바이트 정렬 가정, `bool` 패딩 등 실제 컴파일러 정렬은 미검증), `df_MaxNumOfElectrode=32` 기준이다.

| 페이로드 구조체 | 추정 크기 | 근거 |
|---|---|---|
| `ST__MAPPINGPAYLOAD_IMPEDANCE` | 20B | int 5개(`:10-18`) |
| `ST__MAPPINGPAYLOAD_eCAP` | 56B | int 14개(`:20-36`) |
| `ST__MAPPINGPAYLOAD_SPECIFIC_STIMULATION` | 32B | int 8개(`:38-48`) |
| `ST__MAPPINGPAYLOAD_LIVE_STIMULATION` | **944B** | 스칼라 12개(48B) + 배열 7개×32×4B(896B)(`:50-75`) |
| `ST__MAPPINGPAYLOAD_READWRITEDATA_FLASH` | 8B | int 2개(`:77-81`) |
| `ST__MAPPINGPAYLOAD_ORIGINAL_ISD_INFO` | 약 108~112B | int 2개 + `userName[25]`(100B) + `bool` 2개(패딩 미확정)(`:83-90`) |
| `ST__MAPPINGPAYLOAD_TEST_STIMULATION` | 292B | 스칼라 4개(16B) + 배열 2개×32×4B(256B) + 스칼라 5개(20B)(`:92-107`) |
| **합계(현재, union 아님)** | **약 1,464B** + `fetched_command`/`command` 8B ≈ **1,472B** | |
| 만약 8종을 union했다면 | max(...) = 944B(LIVE 지배) + 8B ≈ **952B** | 절감 약 520B(약 35%) |

> [!NOTE]
> union화하지 않은 것은 **메모리 비용**이지 코드 복잡도(분기 수·줄 수)의 원인은 아니다. 동시 생존이 필요한 두 페이로드 필드가 참조되는 지점도 이 파일 범위에서는 발견되지 않았다(`isd/tdc_isd_map_*.c` 내부까지의 전수 확인은 별도 - 미확인).

## 7. `fetched_command`/`command` 이중 상태의 불일치 사용

`fetched_command`/`command` 분리 자체는 의도적 설계다 - `fetch_packet`이 파싱을 즉시 끝내되, `step()`의 tick에서 "ISD backtel 연결확인이 진행 중이면 명령 실행을 늦춘다"(`tdc_ble_mapping.c:1798-1816` 주석)는 게이팅을 위해 깊이 1의 생산자-소비자 버퍼가 필요했던 것으로 읽힌다. 문제는 **이 파이프라인이 명령마다 일관되게 쓰이지 않는다**는 점이다.

| 명령 | 완료 시점 동작 | 근거 |
|---|---|---|
| 0x68 쓰기(최초등록 ISD/사용자) | **`command`에 직접 기록**(정상 파이프라인 우회) | `tdc_ble_mapping.c:1129` |
| 0x6C 쓰기(슬롯 ISD/사용자) | **`command`에 직접 기록**(정상 파이프라인 우회) | `tdc_ble_mapping.c:1377` |
| 0x6D 쓰기(맵 자극파라미터) | `fetched_command`에 정상 기록, `step()`의 승격 경로(`:1803`)를 거침 | `tdc_ble_mapping.c:1695` |

세 명령 모두 구조적으로 동형(다단계 데이터 인덱스 쓰기, 마지막 인덱스 완결 시 커밋)임에도 0x68·0x6C는 승격 경로를 우회한다. 이는 `:1798-1799`의 "backtel 연결확인 중이면 승격을 늦춘다"는 가드를 **건너뛴다**는 뜻이다. 우회가 의도된 것인지 정리 대상 불일치인지는 이 파일만으로는 판단할 근거가 없다 - **미확인**(`tdc_isd_is_connection_check_with_mapping()`의 0x68/0x6C 실행 시점 안전성은 `isd/` 쪽 확인 필요).

## 8. 복잡도 원인 정리

> [!IMPORTANT]
> **데이터 인덱스 분기는 없앨 수 없다.** 프로토콜이 앱·리모콘과 공유된 규약이고, 20바이트 MTU는 바뀌지 않는다. §3의 실측이 보여주듯 이것이 복잡도의 최대 단일 요인인 것은 맞지만, 목표는 **분기를 제거하는 것이 아니라 흩어진 분기를 한 곳의 데이터(테이블·디스크립터)로 흡수해 코드에서 걷어내는 것**이다.

같은 양의 분기라도 아래 세 가지가 없었다면 이만큼 복잡해지지 않았다 - 이것들이 진짜 고칠 수 있는 근인이다.

| 순위 | 근인 | 근거 | 성격 |
|---|---|---|---|
| 근인_1 | **함수 분해 부재** | §1 - 함수 6개뿐, `fetch_packet` 1,724줄(78%)이 함수 1개 | 순수 구조 문제. 고치기 쉽고 위험 낮음 |
| 근인_2 | **상태가 4개 층에 분산**(BLE 명령 층 / 라이브 서브커맨드 층 / ISD 하드웨어 층 / CFX PCM 출력 층) | 층간 관계가 코드 어디에도 명시되지 않고 각 case 안의 조건문으로만 암묵적으로 존재 | 이해 난이도의 주범 |
| 근인_3 | **프로토콜 파서가 자극 FSM을 구동** | `tdc_ble_mapping_step()`의 switch가 매 tick `tdc_isd_map_*_step()` 4종을 직접 호출(`:1902`·`:1919`·`:1943`·`:1956`) | 계층 혼재. 재구조화의 핵심 대상이자 최대 위험 - 상세는 [`결합도와 계층 경계.md §3`](결합도와%20계층%20경계.md) |

근인_1과 §3의 데이터 인덱스 분기는 사실상 동전의 양면이다 - 데이터 인덱스 분기들이 별도 함수로 추출되지 않고 `fetch_packet` 하나의 중첩 `switch` 안에 그대로 눌어붙어 있기 때문에, 분기 자체의 비중(근인_2가 아니라 §3)이 그대로 파일 복잡도로 직결된다.
