# 바이폴라 전극번호 경계 결함

**TL;DR**: 매핑 앱이 미사용 밴드의 전극번호를 **99** 로 채워 보내는데, 바이폴라 기준전극 설정 코드가 이를 거르지 않고 `electrodeMap[99-1]` 을 읽었다. 배열은 **32원소**라 범위 밖이며, 인접 전역(`s_tdc_table`)의 값을 집어와 자극 레지스터에 기록했다. 2026-07-27 범위 검사를 넣어 수정했고 **1차 실기에서 정상 동작을 확인**했으나, **정밀 재측정이 필요한 상태로 남겨 둔다**(§5).

> [!IMPORTANT]
> **이 문서는 미완결 항목이다.** 수정은 적용됐고 증상은 사라진 것으로 보이나, **인과 관계가 완전히 확정되지 않았다**(§4 미확인_1). 나중에 §5 절차로 정밀 측정할 것.

## 1. 증상

매핑 앱에서 **bipolar 모드로 동작 시 에러**. 실측 로그 [`매핑로그 - 바이폴라 에러.md`](../매핑로그%20-%20바이폴라%20에러.md).

```
[PARA] (1 BASE), BAND : 29, STIM ELEC NUM : 29 (PCB : 24), REF ELEC NUM : 99 (PCB : 70378)
[PARA] BIPOLAR REF READ BACKTEL COUNT IS 0
[SPI TX] (LSB) 0xF0 66 06 01 00 A5 ...        <- 에러 응답 송신
```

`PCB : 70378` 이 결정적 증거다. 정상이라면 1~32 범위여야 한다.

## 2. 원인

> [!IMPORTANT]
> **초기 설명 정정 (2026-07-28).** 처음에는 "쓰레기값이 그대로 자극 레지스터에 기록되어 설정이 깨졌다" 고 적었으나 **부정확했다.** 은수님 지적으로 재검토한 결과, 레지스터에 쓸 때 `0x1F` 마스킹이 적용되므로(`:549`) **칩에 기록되는 값 자체는 0~31 범위로 정리된다.** 실제 문제는 §2.1 의 두 가지다.

`isd/tdc_isd_stim_para_setting.c` 의 바이폴라 기준전극 버퍼 구성부.

```c
// 수정 전
bipolarReferenceElectrodeNum[electrodeMap[p_mapdata->usableStimulationElectrodIndex[i] - 1]] =
    electrodeMap[p_mapdata->usableReferenceElectrodIndex[i] - 1];
```

`usableReferenceElectrodIndex[i]` 가 **99**(미사용 표식)이면 `electrodeMap[98]` 을 읽는다. `electrodeMap` 은 32원소다(`board/electrodeMapping.h:5`).

### 2.1 진짜 문제는 두 가지다 (2026-07-28 규명)

`0x1F & 70377` = **9** 이므로 칩에는 9 가 기록된다. 값은 유효 범위다. 그럼에도 문제인 이유는 아래 둘이다.

| # | 문제 | 성격 |
|---|---|---|
| 문제_1 | BAND 29 는 REF 가 99(미사용)라 `unusedReferenceElectrode_DummyNum`(**31**)이 유지돼야 하는데 **9** 가 들어간다. 즉 **PCB 24번 전극을 자극할 때 PCB 10번이 기준전극으로 붙는다** | **자극 정확성.** 값은 유효 범위지만 전극쌍이 틀렸다 |
| 문제_2 | 검증부(`:794`)가 **좌변을 마스킹하지 않는다**. 칩에 9 를 쓰고 9 를 읽어왔는데 비교는 `70377 != 9` 라 **반드시 불일치** | **에러 발생 기전.** 자극 설정은 (틀리게나마) 됐는데 검증만 실패한다 |

```c
w_isd_registerValue | (0x1F & bipolarReferenceElectrodeNum[i]);       // :549  쓸 때는 마스킹
if (bipolarReferenceElectrodeNum[i] != ((0x1F) & (backtelBuff[i])))   // :794  비교는 좌변 무마스킹
```

> [!NOTE]
> **`:794` 의 마스킹 비대칭은 의도적으로 존치한다 (2026-07-28 은수님 판단).**
>
> 언뜻 버그로 보이지만, 좌변에 `0x1F &` 를 넣어 대칭으로 만들면 **32 이상의 오염값이 들어와도 검증을 통과해 버린다.** 지금의 비대칭이 실질적으로 **범위 밖 값을 잡아내는 탐지기** 역할을 하며, 이번 결함도 그 덕분에 에러로 드러났다.
>
> **상류(버퍼 구성)에서 막고 하류(검증) 탐지기는 살려 둔다**는 것이 이 코드의 방침이다.

### 2.2 검토했으나 기각된 가설 2건

은수님이 제기한 대안 가설을 검증한 결과다.

| 가설 | 판정 | 근거 |
|---|---|---|
| `bipolarReferenceElectrodeNum[]` 인덱스가 오염돼 메모리를 덮어썼다 | **이번 케이스는 아님** | 좌변 인덱스는 **STIM** 쪽(`electrodeMap[stim-1]`)이고 BAND 29 의 STIM 은 29(정상)라 인덱스 23 으로 범위 내다. 99 가 들어간 것은 **우변(REF)** 뿐이다. 루프도 `i < numFrequencyBand`(29)라 STIM=99 인 BAND 30~32 는 진입하지 않는다 |
| PCB 채널 순서와 레퍼런스 전극 PCB 번호가 겹쳐 덮어썼다 | **기각** | `electrodeMap` 은 0~31 이 각각 한 번씩 나오는 **순열**이다. 서로 다른 STIM 은 반드시 서로 다른 인덱스로 매핑되므로 충돌이 없다 |

> [!WARNING]
> **다만 인덱스 오염은 잠재 위험으로 실재한다.** `numFrequencyBand` 범위 **안에** STIM=99 가 섞여 들어오면 `bipolarReferenceElectrodeNum[70377]` 이 되어 **진짜 범위 밖 쓰기**가 발생한다. 이번 맵에서 안 터졌을 뿐이다. §4 수정은 STIM 도 함께 검사하므로 이 경로까지 막는다.

### 2.3 무엇을 읽고 있었나 (실측)

`nm` 으로 확인한 메모리 배치:

| 심볼 | 주소 | 크기 |
|---|---|---|
| `electrodeMap` | 0x200080D0 | 128바이트 (32 x 4) |
| **`electrodeMap[98]` 접근 주소** | **0x20008258** | (+392) |
| `s_tdc_table` | 0x200081D0 | 384바이트 |

`electrodeMap[98]` 은 **`s_tdc_table` 의 offset 136**(35번째 원소)을 읽는다. `s_tdc_table` 은 UI 명령 핸들러 테이블(`ui/tdc_ui_command.c:120`)로 **함수·문자열 포인터**가 들어 있어, 읽힌 값 70377(0x112E9)은 플래시 주소다.

> [!CAUTION]
> **`s_tdc_table` 은 런타임에 채워진다.** UI 명령 등록 개수·순서에 따라 값이 달라지므로, 이 결함의 증상은 **빌드마다·실행 시점마다 다르게 나타날 수 있었다.**

## 3. 왜 하필 지금 발현됐나

**구버전(Sullivan1.5)에는 `s_tdc_table` 이 없다.** UI 명령 테이블은 Sound1 에서 추가된 것이다(grep 으로 구버전 저장소 확인, `command_entry_t`·`s_tdc_table` 0건).

구버전에서는 `electrodeMap[98]` 이 다른 메모리를 읽었고 우연히 무해한 값이었을 것으로 추정된다. Sound1 에서 그 자리에 포인터 배열이 배치되면서 **큰 쓰레기값**이 읽히게 됐다.

### 3.1 배제된 가설 2건

| 가설 | 판정 | 근거 |
|---|---|---|
| SPI 8비트 전환(B1~B3a)이 `.data` 배치를 바꿔 발현시켰다 | **기각** | `electrodeMap` <-> `s_tdc_table` 상대 거리가 전환 전후 **모두 0x100**. `electrodeMap[98]` 은 전환 전에도 같은 위치를 읽었다. B1 이전 커밋(`0761dcb`)을 빌드해 `nm` 으로 실측 대조 |
| 구버전 대비 로직 회귀 | **기각** | `isd_interface_stimulationParaSetting.c` <-> `tdc_isd_stim_para_setting.c` 바이폴라 경로 전수 대조 결과 **동작 차이 0**. 상세 [`에이전트-로그/05`](../../../tasks/ble/20260727_ble-8bit-packet-redesign/에이전트-로그/05_bipolar-회귀-대조.md) |

**즉 원래부터 잠복해 있던 미정의 동작이다.**

## 4. 수정 (2026-07-27)

99 만 걸러내는 대신 **범위 검사로 일반화**했다. 0 이나 33 이상도 함께 막힌다.

```c
if ((p_mapdata->usableStimulationElectrodIndex[i] < 1)
    || (df_MaxNumOfElectrode < p_mapdata->usableStimulationElectrodIndex[i])
    || (p_mapdata->usableReferenceElectrodIndex[i] < 1)
    || (df_MaxNumOfElectrode < p_mapdata->usableReferenceElectrodIndex[i]))
{
    TDC_PRINTF_I("... (PCB : XX), UNUSED \r\n");
    continue;
}
```

미사용 밴드는 바로 앞 루프에서 이미 `unusedReferenceElectrode_DummyNum`(31)로 초기화되므로, 건너뛰면 그 더미값이 유지되어 의도대로 동작한다.

구버전 `isd_interface_stimulationParaSetting.c:484-490` 의 **`#if 0` 블록에 있던 99 체크**와 같은 취지다. 그 체크가 비활성 쪽에만 있고 활성 쪽(`#else`)에는 없었던 것이 이 결함의 뿌리다.

### 4.1 미확인 사항 (재측정 대상)

| # | 항목 | 상태 |
|---|---|---|
| ~~미확인_1~~ | ~~쓰레기값이 검증 실패의 원인인지~~ | **규명 완료 (2026-07-28).** §2.1 문제_2 참조. 검증부가 좌변을 마스킹하지 않아 `70377 != 9` 로 **반드시 불일치**한다. 읽힌 값이 **32 이상이면 검증 100% 실패**, 32 미만이면 조용히 통과하고 잘못된 전극쌍으로 자극된다 |
| 미확인_2 | **`BIPOLAR REF READ BACKTEL COUNT IS 0` 자체의 원인** | **여전히 미확정.** 이 메시지는 `PRE-SETTING ... REF INDEX` 불일치와 **다른 지점**이다(`:812` vs `:796`). 로그에서 첫 시도는 COUNT 32 로 성공했다가 이후 0 이 되는 패턴이라 별개 요인이 겹쳐 있을 수 있다 |
| 미확인_3 | 1차 실기에서 "정상 동작하는 것처럼 보인다" 수준의 확인만 이뤄졌다 | 정밀 측정 필요 |

## 5. 재측정 절차 (나중에 정밀 확인할 때)

### 5.1 수정이 먹혔는지 (1차 확인)

| # | 확인 | 기대 결과 |
|---|---|---|
| 확인_1 | bipolar 맵으로 라이브모드 진입 후 `[PARA]` 로그 | `REF ELEC NUM : 99 (PCB : 70378)` 이 사라지고 **`(PCB : XX), UNUSED`** 로 출력 |
| 확인_2 | 동 시나리오에서 에러 응답 | `BIPOLAR REF READ BACKTEL COUNT IS 0` 과 `0xF0` 응답이 없어야 함 |

**확인_1 은 되는데 확인_2 가 남으면** 미확인_1 이 별개 원인이라는 뜻이다. 그때 §5.2 로 넘어간다.

### 5.2 인과 관계 규명 (미확인_1)

| # | 방법 |
|---|---|
| 방법_1 | 수정 전 바이너리로 되돌려(`git revert` 또는 해당 커밋 이전 빌드) **에러 재현성**을 먼저 확보. 재현이 안 되면 타이밍 의존이므로 반복 시행 필요 |
| 방법_2 | `bipolarReferenceElectrodeNum[]` 전체를 백텔 쓰기 **직전에 덤프**해 32개 값이 전부 1~32 또는 31(더미)인지 확인 |
| 방법_3 | 백텔 FIFO 카운트를 읽는 `tdc_isd_fpga_read_fifo_counter()`(`isd/tdc_isd_fpga.c:220`) 호출 전후로 I2C 반환값·소요시간을 로깅해 **COUNT 0 이 I2C 실패인지 FIFO 미충전인지** 구분 |
| 방법_4 | 첫 시도(COUNT 32 성공)와 재시도(COUNT 0) 사이에 무엇이 달라지는지 추적. FIFO 클리어 타이밍 의심 |

### 5.3 회귀 감시

수정 후에도 아래를 정기적으로 확인한다.

- bipolar 모드 라이브 진입 시 `[PARA]` 로그에 **PCB 번호가 1~32 범위**를 벗어나는 줄이 없는지
- `UNUSED` 로 표시되는 밴드 수가 `numFrequencyBand` 와 정합하는지

## 5.4 레거시(Sullivan) 영향 여부

**결함은 Sullivan 에도 동일하게 존재한다.** `isd_interface_stimulationParaSetting.c:492-493` 의 활성 코드가 Sound1 과 같고, 99 체크는 마찬가지로 `#if 0` 안에만 있다.

차이는 **범위 밖에서 무엇을 읽느냐**뿐이다. 두 프로젝트의 `.elf` 를 `nm` 으로 실측한 결과다.

| 프로젝트 | `electrodeMap` | `electrodeMap[98]` 이 읽는 것 |
|---|---|---|
| Sound1 | 0x200080D0 | `s_tdc_table` (UI 명령 핸들러 테이블) offset 136 -> **함수·문자열 포인터** |
| Sullivan1.5 | 0x20008128 | **`s_ci_ctx`** (tiny-AES-c 의 `struct AES_ctx`, `Gen1_5/tiny-AES-c/aes.c:116`) offset 164 -> **AES 라운드 키** |

> [!WARNING]
> **Sullivan 에서도 오동작할 수 있다.** AES 라운드 키는 의사난수 값이므로 32 이상일 확률이 높고, 그 경우 Sound1 과 같이 검증 실패로 드러난다.
>
> 더 주의할 점은 `s_ci_ctx` 가 `.bss` 라 **AES 초기화 전에는 0** 이라는 것이다. 그 타이밍에는 읽힌 값이 0 이라 **검증을 통과해 버리고, 전극 0 이 기준전극으로 조용히 설정된다.** 에러 없이 잘못된 전극쌍으로 자극되므로 오히려 발견이 어렵다.

**조치 방침**: Sullivan 은 이미 출하된 레거시이므로 **수정하지 않는다.** 이 문서에 사실만 기록해 둔다. 다만 Sullivan 기기에서 바이폴라 관련 이상이 보고되면 이 항목을 최우선으로 확인할 것.

## 6. 함께 점검한 경로

| 대상 | 판정 |
|---|---|
| `isd/tdc_isd_map_specific_stim.c:224-225` (특정자극 바이폴라) | **정상 경로에서는 안전.** 모노폴라면 `stimulatonMode != en__bipolar` 검사로 바이폴라 루틴(`case 3`)을 통째로 건너뛰고(`:206-213`), 바이폴라면 기준전극이 1~32 로 검증된다(`ble/tdc_ble_mapping.c:274-276`) |

> [!WARNING]
> **잔여 위험**: 파싱이 기준전극 **99 를 명시적으로 허용**한다(`ble/tdc_ble_mapping.c:277`, "99인 경우 예외 (for 모노폴라)"). 따라서 **"바이폴라 모드 + 기준전극 99"** 라는 비정상 조합이 앱에서 오면 `specific_stim` 도 같은 범위 밖 읽기가 발생한다. 정상 앱은 보내지 않을 조합이라 이번에는 손대지 않았다. 방어를 넣을지는 별도 판단 사항이다.
>
> 마찬가지로 `:258` 의 레지스터 조합에는 `0x1F` 마스크가 없어(`stim_para_setting.c:549` 에는 있음) 큰 값이 들어오면 레지스터가 더 크게 오염된다.
