# BLE 명령 카탈로그

**TL;DR**: `tdc_ble_protocol.h` 에 정의된 BLE 명령 상수 63개(내부 상태값 · 순수 센티널 제외)를 헤더값 오름차순으로 전수 수록한다. 52개는 정상 처리되고, 4개(0x51·0x53·0x58·0x90)는 핸들러가 없으며, 그룹 경계(주로 매핑 0x60~0x72+0x91)는 문서상 정의와 실제 디스패치 조건이 다르다. 명령을 추가·변경하기 전에 반드시 이 문서에서 헤더값 충돌 여부를 먼저 확인한다.

> [!IMPORTANT]
> **참조는 라인 번호가 아니라 함수 이름으로 적는다** (2026-07-29 전환).
>
> 이전에는 `tdc_ble_mapping.c:1832` 같은 라인 참조를 썼으나 **리팩토링마다 통째로 깨졌다.** 2026-07-28 단계_1a·1b 폴더 개편으로 매핑 핸들러가 4파일로 분산되면서 참조 73건이 한꺼번에 무효가 됐고(최대 참조가 662줄 파일의 `:1885` 를 가리켰다), 2026-07-29 단계_3 에서 또 바뀌었다.
>
> 함수 이름은 개명할 때만 바뀌므로 훨씬 안정적이고 `grep` 으로 바로 찾아갈 수 있다. **소스 라인 번호 참조는 이 문서에 0건이다.** 헤더 정의 위치(`tdc_ble_protocol.h:NN`)만 라인으로 남겼다 — enum 선언이라 잘 움직이지 않는다.

> [!NOTE]
> **핸들러 열이 함수 분해 상태를 그대로 드러낸다.** 명령마다 자기 함수를 가진 그룹과, 거대 함수 안의 `case` 로만 존재하는 그룹이 눈에 띄게 갈린다.
>
> | 그룹 | 상태 |
> |---|---|
> | 매핑 0x62~0x71 | 명령별 함수로 분해 완료 (2026-07-28 단계_1b) |
> | **매핑 0x66** | 하위 명령 · 데이터 인덱스까지 계층 분해 (2026-07-29 단계_3) |
> | **매핑 0x65** | 계층 네이밍 · 명령 단위 파일 (2026-07-30 이월_1). 하위 계층이 없어 `subNN_idxKK` 없음 |
> | **리모콘 0x40~0x59** | 전부 `tdc_ble_remote_fetch_packet()` 안 — 이 함수 하나가 **약 1,340줄** |
> | **Ezairo 0x33~0x36** | 전부 `setting_nrf_ble_adv_info()` 안 — 이름과 달리 배터리 · 전원 · LED · 클래식 상태 응답을 모두 담은 **183줄** 함수 |
>
> 아래 두 그룹이 다음 분해 대상 후보다.

## 1. 그룹 체계 (확정)

| 그룹명 | 헤더 범위 | 주체 | CM3 처리 | 정의 위치 |
|---|---|---|---|---|
| Ezairo_BT_30 | 0x30~0x36 | QCC <-> E8300 | O (0x30, 0x33~0x36) | `tdc_ble_protocol.h:26-46` |
| 통신 프로토콜_40 | 0x40~0x59 | 리모콘 앱 | O | `tdc_ble_protocol.h:48-82` |
| 매핑 프로토콜_60 | 0x60~0x72 + 0x91 | 매핑 프로그램 | O | `tdc_ble_protocol.h:84-113` |
| SOUND1_80 | 0x8C, 0x8F | 앱 -> QCC -> E8300 | O (이 2값만 도달) | `tdc_ble_protocol.h:115-119` |
| OP_C0 | 0xC0~0xC3 | QCC (OTA) | O | `tdc_dfu_ble_ota.h` · `tdc_dfu_ble_boot.h` |
| 믹싱 게인_A0 | 0xA0~0xAF | E8300 | **X — 코드 미실재** | 전체 grep 0건 |
| Security | 0xE0~0xEF | QCC <-> 폰/크래들 | X (QCC 전용, CM3 도달 없음) | 전체 grep 0건 |
| 공통 에러 | 0xF0 | 전 인터페이스 | O (송신 전용) | `tdc_ble_protocol.h:23,37` |

> [!IMPORTANT]
> **매핑 프로토콜_60 의 실제 경계는 0x60~0x72 + {0x91} 이다.** `en__mapping_waiting_for_BleOff` 가 명시적 hex 값 없이 `en__mapping_recover_ALL_SlotData_ManufactureData`(0x71) 다음 정수로 계산되어 0x72 가 되고(`tdc_ble_protocol.h:110`), 그 뒤 0x90(`en__mapping_testStimulation`)·0x91(`en__mapping_read_Connected_ISD_id`)이 별도 대역에 이어진다. 디스패처는 `0x60 <= header <= 0x72` **OR** `header == 0x90` **OR** `header == 0x91` 조건으로 매핑 핸들러에 보낸다(`tdc_ble_communication_step()` 디스패처 조건). 이 중 **0x91 은 완전히 처리되므로 매핑 프로토콜_60 그룹에 편입 확정**, **0x90 은 핸들러가 없어 그룹 밖으로 남는다**(§4 참조).
>
> "0x60~0x7F" 처럼 라운드 숫자로 그룹 경계를 잡는 사전 정의가 있었다면 이는 실제 코드와 다르다 — 0x73~0x7F 구간은 enum 에 값 자체가 없다.

## 3. 그룹별 성격

### 3.1 Ezairo_BT_30 (0x30~0x36) — QCC 연동 상태 정보

QCC(블루투스 클래식/오디오 담당 칩)가 E8300 에 배터리·전원·LED·클래식 연결 상태를 알리는 채널이다. 명령이라기보다 **상태 통지**에 가깝고, 응답은 대부분 "수신 확인(ack=1)" 한 바이트뿐이다. 0x30 만 예외적으로 앱(매핑/리모콘) 초기 연결 시점에 ISD 정보(수술위치·사용자이름)를 반환하는 조회형이며, 이 응답은 헤더를 생략한다(§2 문서). 0x31 은 그룹 범위 안인데 디스패치에서 완전히 누락돼 실질적으로 죽어 있다.

### 3.2 통신 프로토콜_40 (0x40~0x59) — 리모콘 앱

리모콘 앱이 보내는 명령군. 패스키 검증(0x40, 사실상 무효화됨) · 외부기기/맵 정보 조회 · 볼륨/텔레코일/LED on-off · 슬롯·맵 데이터 R/W · 자극 묵음 설정(0x59, 2026-01-20 추가)까지 폭넓다. **핸들러가 없는 3건(0x51·0x53·0x58)이 모두 이 그룹에 몰려 있다** — §4 참조. 디스패치 경계(`0x40 <= header < 0x60`)는 그룹 정의와 정확히 일치한다(`tdc_ble_communication_step()` 디스패처 조건).

### 3.3 매핑 프로토콜_60 (0x60~0x72 + 0x91) — 매핑 프로그램

내부기(ISD) 연결·임피던스 측정·자극(특정/라이브)·맵 데이터 R/W·공장 초기화를 담당하는 가장 큰 그룹이다(핸들러 코드 기준 `tdc_ble_mapping.c` 2,196줄, 전체 BLE 모듈의 절반 가까이). 헤더만으로 라우팅되는 것이 아니라 0x66(라이브 자극)은 서브커맨드 1~9, 데이터 인덱스 1~15 조합으로 구조가 세분화된다. 0x63·0x64(eCAP 측정)는 "현재 버전 매핑 앱에서 사용 X"라는 헤더주석이 있으며, 0x64 는 실행부 자체가 주석 처리돼 case 는 있어도 아무 동작을 하지 않는다.

### 3.4 SOUND1_80 (0x8C, 0x8F) — 앱 -> QCC -> E8300 특수 경로

이름은 "SOUND1_80" 이지만 그룹 전용 디스패처는 없다. 0x8C(게인 제어)·0x8F(범용 디버그) 단 2개 값만 개별 등호 비교로 걸러지고, 그 처리는 **리모콘 인프라(`tdc_ble_remote_fetch_packet()`)로 위임**된다(`tdc_ble_communication_step()` 디스패처 조건). 즉 그룹 이름이 가리키는 "출처"(앱→QCC→E8300)와 실제로 그 값을 소비하는 코드 모듈(리모콘 핸들러 → 각각 `tdc_ble_gain_control.c`/`tdc_ble_general_debug.c`로 재위임)이 다르다.

### 3.5 믹싱 게인_A0 (0xA0~0xAF) — 코드에 존재하지 않음

이 대역은 CM3 코드 어디에도 없다(전체 grep 0건). 게인 제어 기능 자체는 0x8C(SOUND1_80 그룹) 하나로 전담된다(`tdc_ble_gain_control_handle()` `tdc_ble_gain_control_handle()`이 Read/Write·Gain_A/B·인덱스 0~255를 받아 `cfx_cm3_sharedMemoryAll.gain_table_index_a/b`에 반영). "믹싱 게인_A0"이라는 그룹명이 가리키는 기능은 실재하되, 그 그룹의 헤더 대역 자체는 빈 대역이다.

### 3.6 OP_C0 (0xC0~0xC3) — DFU(OTA)

부트로더 선택(0xC2)과 OTA 시작/종료/데이터 전송(0xC0/0xC1/0xC3)을 담당한다. 디스패치 경계가 그룹 정의와 정확히 일치하는 몇 안 되는 그룹이다. 0xC3 값이 이름이 다른 enum 2개에 중복 정의돼 있으나 실사용에는 영향이 없다.

### 3.7 Security (0xE0~0xEF) — QCC 전용, CM3 도달 없음

CM3 소스에 이 대역을 다루는 정의가 전혀 없다. QCC와 폰/크래들 사이에서만 처리되고 E8300(CM3)까지 도달하지 않는 것으로 추정되나, 이는 CM3 저장소 범위 밖의 QCC 쪽 구현에 대한 추정이며 **미확인**이다.

### 3.8 공통 에러 (0xF0)

인바운드 명령이 아니라 CM3 가 앱에 에러를 통지할 때 쓰는 아웃바운드 전용 헤더다. 상세 규약은 [`패킷 구조와 응답 규약.md`](패킷%20구조와%20응답%20규약.md) §4 참조.

## 4. 핸들러가 없는 명령 (4건)

디스패처는 이 4개 헤더를 모두 정상 핸들러로 라우팅하지만, 그 핸들러의 switch/if 안에는 해당 case 가 없다. 다만 **결과는 서로 다르다.**

| 헤더 | 열거값 이름 | 디스패치 목적지 | 실제 결과 | 근거 |
|---|---|---|---|---|
| 0x51 | `en__remoteControl_read_OwnerNameOfExternalDevice` | `tdc_ble_remote_fetch_packet()` → 리모콘 `default:`(`tdc_ble_remote_fetch_packet()` 의 `default:` 절)가 값을 그대로 저장 | **응답 없음.** `tdc_ble_remote_step()`의 switch에 이 값의 case 도, `default:` 절도 없어 `remoteDataPacket.command`가 계속 남는다 | `tdc_ble_remote_fetch_packet()` 의 `default:` 절, (default 없음, 본 문서에서 까지 확인) |
| 0x53 | `en__remoteControl_read_NRF_FirmwareInfo` | 위와 동일 | **응답 없음.** 0x51 과 동일 구조 | 상동 |
| 0x58 | `en__remoteControl_readSystemErrorCode` | 위와 동일 | **응답 없음.** `tdc_ble_protocol.h:75` 주석 자체가 "NOTE: 실제 사용되고 있나? 이거 보내면 묵묵 부답으로 시간 초과 타임아웃 발생함"이라고 이미 증언한다 — 코드 조사 결과(case 없음)와 정확히 일치 | `tdc_ble_protocol.h:75`, `tdc_ble_remote_fetch_packet()` 의 명령 디스패치 `switch` |
| 0x90 | `en__mapping_testStimulation` | `tdc_ble_mapping_fetch_packet()` → 매핑 fetch 의 switch 에 case 없음 → `default:` 낙하 | **에러 응답은 나간다.** `[0]=0x90`(수신 헤더 그대로 loop-back, 0xF0 아님) `[1]=en__UndefinedCommand` 2바이트 | `tdc_ble_mapping_fetch_packet()` 의 `default:` 절 |

> [!IMPORTANT]
> **0x51·0x53·0x58 은 "무응답"에 그치지 않고 이후 명령 전체를 멈출 수 있다.** `remoteDataPacket.command`가 해제되지 않은 상태에서 다음 명령이 들어오면 `tdc_ble_remote_fetch_packet()` 상단의 "이전 명령 미완료" 검사에 걸려 `en__PreviouCommnadIsNotCompleted` 에러가 나며 새 명령까지 함께 무시된다. 이 상태는 BLE 연결이 끊겨 `en__BLE_Disconnected_Flag`(0x32) 경로가 `tdc_ble_remote_clear_command()`를 호출할 때(`tdc_ble_communication_step()` 내 상시 검사 블록)까지 풀리지 않는다.
>
> **0x90 은 성격이 다르다.** `docs/참고/cm3-소스-트리-규약.md §2.1`이 명시하듯, 2026-07-27 리팩토링에서 `en__mapping_testStimulation`의 **핸들러는 의도적으로 제거**하고 프로토콜 정의(열거값·`ST__MAPPINGPAYLOAD_TEST_STIMULATION` 페이로드 구조체, `tdc_ble_mapping.h:117`)만 남기기로 확정했다. 즉 0x90 이 에러로 응답하는 것은 "발견된 버그"가 아니라 **확인된 설계 결정의 결과**다. 이 명령을 되살리려면 프로토콜 정의는 이미 있으므로 핸들러만 새로 작성하면 된다.

## 5. 헤더 주석 "확인 완료" 이력과 코드의 불일치

`tdc_ble_protocol.h`의 다수 enum 멤버에는 원 작성자가 남긴 "확인 완료: ..." 검증 주석이 붙어 있다(§2 표의 "헤더주석 검증이력" 열). 표본 검증 결과 **0x70 한 건만 코드와 어긋난다**:

- `en__mapping_recover_mppingData_exceptSlot_1`(0x70, `tdc_ble_protocol.h:108`)의 주석은 "확인 완료: 헤더 only 패킷"이지만, 실제 fetch 핸들러(`tdc_ble_map_flash_recover_except_slot1()` (`map_flash.c`))는 헤더 뒤에 `slot_index`·`map_index` 2바이트를 추가로 읽는다.
- 그 외 "헤더 only" 표기 건(0x43·0x60·0x61·0x67·0x69·0x71)과 "범위 검사" 표기 건(0x44~0x49·0x62·0x68 등)은 모두 코드와 일치한다.

즉 이 검증 주석은 대체로 신뢰할 수 있으나 전수 보증은 아니며, 새 주석을 추가하거나 이 문서를 갱신할 때 0x70 과 같은 사례가 더 있을 수 있다는 점을 감안해야 한다.
