# BLE 패킷 구조와 응답 규약

**TL;DR**: nRF <-> CM3 SPI 패킷은 21바이트 고정 프레임이다. `[20]`은 TX 에서는 실제 전송 바이트 수(`dataSize`)로 확정되지만, RX 에서는 CM3 파싱 로직이 20바이트 배열까지만 채워 **유효 데이터가 아니다** — RTT 로그의 `[SPI RX] ... 01`은 배열 범위 밖 읽기로 강하게 의심된다. 정상 응답은 대부분 헤더를 그대로 반사하나 0x30 은 생략하고, 에러 응답은 정식 6바이트 경로(0xF0)와 매핑 default 낙하 2바이트 경로(0xF0 없음)가 공존한다.

## 1. 21바이트 패킷 레이아웃

```mermaid
flowchart LR
    B0["[0] 헤더<br/>명령 코드"] --> B1["[1] 서브커맨드<br/>또는 첫 페이로드"]
    B1 --> B2["[2] 데이터 인덱스<br/>또는 페이로드"]
    B2 --> B3["[3..19] 페이로드<br/>17바이트"]
    B3 --> B20["[20] TX=dataSize<br/>RX=미확인·미사용"]
```

| 위치 | 이름 | 의미 |
|---|---|---|
| `[0]` | 헤더 | 명령 코드([`명령 카탈로그.md`](명령%20카탈로그.md) 전체 대상) |
| `[1]` | 서브커맨드 또는 첫 페이로드 | 명령에 서브구조가 있으면 서브커맨드(예: 0x66 라이브 자극의 `liveSubCommand`, `tdc_ble_mapping.c:312`), 없으면 첫 페이로드 바이트 |
| `[2]` | 데이터 인덱스 또는 페이로드 | 분할 전송 명령이면 순번(예: 0x66 서브1의 `subCommandData_Num_index`, `tdc_ble_mapping.c:345`), 아니면 페이로드 |
| `[3..19]` | 페이로드 | 최대 17바이트 |
| `[20]` | (아래 §2 참조) | TX 는 확정, RX 는 미확인 |

SPI 프레임 크기 자체는 `TDC_HAL_SPI_COMM_PACKET_SIZE = 21`로 고정이며 DMA 가 매 트랜잭션 21바이트를 통째로 주고받는다(`tdc_hal_spi.c:223,232` DMA 채널 설정에서 `TDC_HAL_SPI_COMM_PACKET_SIZE` 사용).

## 2. `[20]` 바이트의 진실

### 2.1 TX 방향 — 확정: 전송 바이트 수(`dataSize`)

`tdc_hal_spi_write_tx_buffer(int *source, int dataSize)`(`tdc_hal_spi.c:287-305`)는 호출자가 넘긴 `dataSize`만큼 버퍼에 쓰고 나머지를 0으로 채운 뒤, 마지막 인덱스에 그 값을 그대로 기록한다.

```c
for (int i = 0; i < dataSize; i++)               { SPI_Tx_Buffer[i] = source[i]; }
for (int i = dataSize; i < TDC_HAL_SPI_COMM_PACKET_SIZE; i++) { SPI_Tx_Buffer[i] = 0; }
SPI_Tx_Buffer[TDC_HAL_SPI_COMM_PACKET_SIZE - 1] = dataSize;  // tdc_hal_spi.c:305
```

즉 TX `[20]`은 그 응답 호출에서 넘긴 "헤더+페이로드 유효 바이트 수" 그 자체다. `tdc_ble_communication.c:80-82`의 코드 주석도 동일하게 진술한다 — ISD 미연결 시 0x30 응답을 `tx_index=0`으로 보내면 "전송 크기가 0이므로 ... `[20]` 인덱스도 0으로 채워져서 보내질 것"이라고 명시한다.

### 2.2 RX 방향 — 미확인, 배열 범위 초과 읽기로 강하게 의심

> [!CAUTION]
> **RTT 로그의 `[SPI RX] ... [20]` 값을 프로토콜 데이터로 해석하지 마라.**
>
> - 명령 파싱에 실제로 쓰이는 배열은 `Rx_DataPacket[BLE_DataPacketSize]`, 즉 **20개짜리 배열**이다(`tdc_hal_spi.c:22`, `BLE_DataPacketSize=20`).
> - DMA 수신 복사 루프도 `for (int i = 0; i < BLE_DataPacketSize; i++) Rx_DataPacket[i] = SPI_Rx_Buffer[i];`로 **인덱스 0~19만** 채운다(`tdc_hal_spi.c:159-162`). nRF 가 실제로 보낸 21번째 바이트는 CM3 명령 처리 로직에 전혀 반영되지 않는다.
> - 그런데도 디버그 출력부는 `p_Rx_dataPacket[20]`까지 21개를 찍는다(`tdc_ble_communication.c:275-283`, 특히 `:282`). `p_Rx_dataPacket`은 `tdc_hal_spi_get_rx_packet_addr()`가 반환하는 `&Rx_DataPacket[0]`(`tdc_hal_spi.c:44-47`)이므로, 이 `[20]` 읽기는 **20개짜리 배열의 인덱스 20을 읽는 배열 범위 초과(out-of-bounds) 읽기**다.
> - 2026-07-27 실측 RTT 로그 7종(연결·라이브·특정자극·라이브+알람+볼륨·연결해제·임피던스 개별·전체) 전체에서 이 값은 헤더·페이로드와 무관하게 **예외 없이 `01`**이었다. `Rx_DataPacket` 바로 뒤에 오는 정적 변수 `TxBufferEmpty`(`tdc_hal_spi.c:23`, 초기값 `true`=1)를 우연히 읽고 있을 가능성이 높다는 정황이나, nRF 가 실제로 보내는 21번째 바이트의 진짜 의미는 CM3 코드만으로는 **미확인**이다(nRF 펌웨어 소스는 이 저장소 범위 밖).
> - 기능 동작에는 영향이 없다(파싱 로직은 `[0..19]`만 사용) — 이는 **로그 신뢰성 문제**로만 분류한다.

## 3. 데이터 인덱스 분할 전송

20바이트 MTU 제약 때문에 한 번에 못 보내는 큰 페이로드(32전극 맵 데이터 등)는 `[2]` 데이터 인덱스를 순번으로 삼아 여러 패킷에 걸쳐 분할 전송된다. 각 패킷은 직전 인덱스+1 인지 검사하고, 어긋나면 `en__DATA_Order` 에러를 보낸다(예: `tdc_ble_mapping.c:352-357`).

| 명령 | 그룹 | 분할 단계 | 근거 |
|---|---|---|---|
| 0x66 서브1(`en__allParameter`) | 매핑 | 데이터 인덱스 1~15 | `tdc_ble_mapping.c:345-364`, 순차 검증 `:352-357` |
| 0x68(`en__mapping_write_original_ISD_N_USER`) | 매핑 | 다단계(순차 검증 `en__DATA_Order`, 총 단계 수 미확인) | `tdc_ble_mapping.c:971-990` |
| 0x6C(`en__mapping_write_SlotData_ISD_N_USER`) | 매핑 | 다단계 | `tdc_ble_mapping.c:1163` 이하 |
| 0x6D(`en__mapping_write_Mapdata_STIMUL_PARA`) | 매핑 | 15단계 | `tdc_ble_mapping.c:1422` 이하 |
| 0x4C(`en__remoteControl_write_SlotData_ISD_N_USER`) | 리모콘 | 3단계 서브패킷 | `tdc_ble_remote.c:101` 이하 |
| 0x4D(`en__remoteControl_write_Mapdata_STIMUL_PARA`) | 리모콘 | 15단계 서브패킷 | `tdc_ble_remote.c:372` 이하 |

> [!NOTE]
> 이것과 겉보기에 비슷하지만 다른 메커니즘이 하나 더 있다. **0x62(임피던스 측정) 응답은 CM3 → 앱 방향(TX)으로 한 요청에 여러 TX 패킷을 나눠 보낸다**(`Max_ImpedanceReturnDataSize=4`, `tdc_ble_protocol.h:121` 단위로 4측정치+나머지 측정치, 실측 dataSize 19바이트+7바이트 2건 — 2026-07-27 RTT 로그 임피던스 개별/전체에서 확인). 이는 RX 측 "데이터 인덱스 분할 수신"이 아니라 **TX 측 응답 분할**이므로 위 표와 구분해야 한다.

## 4. 정상 응답 규약

| 패턴 | 설명 | 근거 |
|---|---|---|
| 헤더 에코 | `TX[0] = RX[0]`(수신 헤더 그대로 반사) + `TX[1]` = 서브커맨드/성공플래그 | 매핑 0x60~0x67(`tdc_ble_mapping.c` 각 case), 리모콘 0x44(`tdc_ble_remote.c:879` `command loop-back`), 0x8C 게인 제어(`tdc_ble_gain_control.c:67` `packet->command`) |
| 헤더 생략 | `TX[0]`이 `RX[0]`과 무관 — 헤더를 반사하지 않고 페이로드부터 바로 씀 | **0x30 만의 예외**: `tdc_ble_communication.c:70-77`, 응답이 수술위치(1바이트)+사용자이름(10바이트)으로 시작하고 0x30 이 어디에도 없다 |

> [!IMPORTANT]
> **비일관성은 사실이다.** "헤더를 그대로 반사한다"는 관례가 매핑·리모콘·게인제어·범용디버그 그룹 전반에 걸쳐 있지만, `setting_nrf_ble_adv_info()`(0x30 응답 조립 함수, `tdc_ble_communication.c:48-91`)만 이 관례를 따르지 않는다. 명령마다 처리 함수가 다르고 공용 응답 빌더가 없기 때문으로 보이며(구조적 비일관성), 버그로 볼 근거는 없다.

## 5. 에러 응답 규약 — 두 경로의 공존

### 5.1 정식 경로 — `tdc_sys_error_send_to_app()` (6바이트, 0xF0 헤더)

`tdc_sys_error.c:147-173`:

| 인덱스 | 내용 |
|---|---|
| `[0]` | `en__ERROR_Response`(0xF0) |
| `[1]` | 원 명령 loop-back(`command` 인자) |
| `[2]` | 대분류 에러(`tdc_sys_error_major_t`) |
| `[3]` | 소분류 에러(해당 대분류의 세부 enum) |
| `[4]` | 발생 라인번호 상위 바이트(`lineNumber >> 8`) |
| `[5]` | 발생 라인번호 하위 바이트(`lineNumber & 0xFF`) |

리모콘·매핑 대부분의 범위 검사 실패가 이 경로를 쓴다(예: `en__EN__BLE_PROTOCOL_ERROR` + `en__OutOfDataRange`).

**대분류(`tdc_sys_error_major_t`, `tdc_sys_error.h:111-125`)**:

| 값 | 이름 |
|---|---|
| 0 | `en__NA` |
| 1 | `en__CFX_ERROR` |
| 2 | `en__dataProcessing_ERROR` |
| 3 | `en__ACCELEROMETER_ERROR` |
| 4 | `en__RF_PowerIC_ERROR` |
| 5 | `en__FPGA_COMMUNICATION_ERROR` |
| 6 | `en__FPGA_CONFIGUARATION_ERROR` |
| 7 | `en__EN__ISD_ERROR` |
| 8 | `en__EN__BLE_PROTOCOL_ERROR` |
| 9 | `en__EN__PCM_GEN_ERROR` |
| 10 | `en__MAJOR_ERRORCODE_DATA_LOGGING_ERROR` |

**BLE 프로토콜 소분류(`tdc_sys_error_ble_protocol_error_t`, `tdc_sys_error.h:85-94`, 대분류 8 과 함께 쓰임)**:

| 값 | 이름 | 의미(카탈로그 근거) |
|---|---|---|
| 1 | `en__PreviouCommnadIsNotCompleted` | 이전 명령 미완료(§핸들러 없는 명령 4건의 정체 결과) |
| 2 | `en__NO_SECURITY` | 보안 미충족 |
| 3 | `en__Command_Order` | 명령 순서 오류 |
| 4 | `en__DATA_Order` | 데이터 인덱스 순서 오류(§3 분할 전송 검증) |
| 5 | `en__UndefinedCommand` | 정의되지 않은 명령(§5.2 default 경로와 동일 값) |
| 6 | `en__OutOfDataRange` | 필드 범위 초과 |

다른 대분류(가속도계·전원IC·FPGA 등)에도 각자의 소분류 enum이 있으나 BLE 프로토콜 카탈로그와 직접 관련된 것은 위 표다. 전체 목록은 `tdc_sys_error.h:10-109` 참조.

### 5.2 예외 경로 — 매핑 fetch `default:` 낙하 (2바이트, 0xF0 없음)

`tdc_ble_mapping.c:1763-1772`(매핑 fetch 스위치의 `default:`, 0x90 을 포함해 매핑 그룹에 case 가 없는 헤더가 걸렸을 때):

| 인덱스 | 내용 |
|---|---|
| `[0]` | **수신 헤더 그대로 loop-back(0xF0 이 아님)** |
| `[1]` | `en__UndefinedCommand`(값 5) |

```c
bufferForSPI_tx[buffer_tx_index++] = tempCommand;             // 수신 헤더 그대로, 0xF0 아님
bufferForSPI_tx[buffer_tx_index++] = en__UndefinedCommand;    // tdc_ble_mapping.c:1766,1768
```

### 5.3 두 경로의 공존이 뜻하는 것

앱 입장에서는 "정상 응답처럼 보이는 2바이트 패킷"(§5.2)과 "0xF0 으로 시작하는 6바이트 정식 에러 패킷"(§5.1)이라는 서로 다른 두 신호가 같은 "정의되지 않은 명령"이라는 의미로 혼재한다. 이것이 의도된 설계인지 리팩토링 잔재인지는 정적 코드 판독만으로는 **미확인**이다.
