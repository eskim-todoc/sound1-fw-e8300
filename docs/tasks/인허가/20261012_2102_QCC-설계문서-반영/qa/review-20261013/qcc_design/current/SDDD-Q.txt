[55 P 2] System management module
[56 P ] 외부 시스템의 전체적인 동작을 제어하는 모듈이다. 먼저, 시스템의 설정에 따라 다른 모듈들 설정하고 초기화한다. 또한, 주요 상태를 수집하여 다른 모듈들에게 전달하거나, 직접 제어한다. 특히, 사운드 처리기(Sound processor, SP)의 상태가 가장 중요한 상태이다. 그리고, 시스템 상태에 따라 블루투스를 설정하고 제어를 수행한다.

[84 P ] <그림 1. System control module 동작 흐름도>
[85 P ] <그림 1>은 설계된 System management module의 동작 및 제어 흐름을 표현하고 있으며, 흐름도 전체가 System management module이다. 이 모듈에 포함된 유닛들은 파란색으로 표현되었으며, 시스템 상태 유닛은 System management module 뿐만 아니라 다른 모듈들 간의 상호작용을 제어한다. 이를 위해서 각각의 상태에 따른 시스템의 설정이 다르게 되어야 하며, 그 내용은 다음과 같다.

[87 P 3] SW-BT-DS-ID-001, 시스템 초기화와 설정 유닛
[88 P ] 시스템을 초기화하기 전에 초기화에 필요한 설정이 먼저 되어 있어야 한다. 시스템 설정은 시스템 동작 중에 지속적으로 설정을 수행하는 것이 아니라, 초기화 전에 모두 설정이 되면, 이후에는 변하지 않는다. 하지만, 전체 시스템의 각 부분에 대한 설정은 수와 고려해야 할 사항이 많아 별도로 유닛에 추가하였다.
[89 P ] 시스템 초기화는 위의 초기 설정에 기반하여 시스템의 각 부분을 차례대로 초기화하고 Application은 먼저 초기화된 시스템의 각 부분을 기반으로 제일 마지막에 수행하도록 한다.
[90 P ] 중요한 시스템 설정은 다음과 같다.
[91 P a8] HW interface 설정
[92 P a8] SPI 설정 – SPI에서 사용하는 Port pin과 클럭 속도
[93 P a8] I2S 설정 – Data bits과 sampling rate
[94 P a8] General port pin – 일반적인 디지털 입력과 출력 설정
[95 P a8] Charger case communication 설정: 통신에 사용되는 Port pin들과 data rate
[96 P a8] NVM mapping: 저장할 데이터의 크기와 위치 설정
[97 P a8] Security 설정
[98 P a8] Bluetooth Classic – 오디오가 스피커가 아닌 I2S로 출력되도록 설정한다.
[99 P a8] BLE Service – Characteristic의 property에 Authentication을 추가한다.
[100 P a8] Auth service – 자체 인증에서 사용할 Auth service를 구성한다.

[129 P a8] 사운드 처리기의 shutdown_ind 신호 처리
[130 P a8] 시스템의 동작은 사운드 처리기의 상태에 크게 의존하므로 이를 어떻게 처리하는지 설명한다.
[131 P a8] 초기화 완료 후 shutdown_ind의 신호가 off 될 때까지 미리 정의된 시간동안 기다린다. 이는 사운드 처리기가 초리화를 완료하고 정상 동작 상태가 되기를 기다리는 것이다. 만일, 대기 시간이 지나면 바로 시스템을 종료하고 Deep sleep 모드에 들어간다.
[132 P a8] 동작 중에도 shutdown_ind의 신호가 off가 되면 미리 정의된 시간동안 기다린다. 대기 시간이 지나면 바로 시스템을 종료하고 Deep sleep 모드에 들어간다. 이는 특정 조건 때문에(예로 Idle 상태의 소모전류 감소 목적) Deep sleep에 들어가도록 요청이 오는 것이다.

[146 P a8] 사운드 처리기의 inter_dev_conn_ind 신호 처리

[150 P 3] SW-FW-DS-ID-003, 장치 상태 유닛
[151 P ] 외부장치는 편이 모드와 양이 모드에 대응하는 Standalone 모드와 TWS 모드로 설정되며 이에 따라 오디오와 데이터 처리가 달라진다. 이러한 장치 설정은 제품 생산시에 결정되며 동작 중에는 변경할 수 없다. 시스템의 모든 부분은 이러한 장치 설정에 따라 Audio와 데이터를 처리하게 된다.
[152 P a8] Standalone 모드
[153 P a8] 외부 장치는 1대로 동작하며, Bluetooth audio는 L/R을 모두 처리하며 데이터도 별도의 구분없이 처리한다.
[154 P a8] TWS 모드
[155 P a8] 외부 장치는 2대 1세트로 동작하며, 장치는 Bluetooth audio의 L/R을 각기 처리하며 데이터도 별도의 구분하여 처리한다.
[156 P a8] 이 상태에서도 1대로 단독 사용 가능하다.
[157 P a8] 이 모드는 흔히 Earbud 형태라 하며, 칩의 제조사인 Qualcomm 사에서 제공하는 자체 기능이며, 오디오의 처리와 데이터 전달은 Buil-in library와 시스템에서 수행하므로 Application에서는 별도의 처리를 하지 않아도 된다.

[311 P ] <그림 6>은 Bluetooth module의 전체적인 흐름도를 나타낸 것이다. Bluetooth Transport는 Classic과 BLE로 나누어지며, 별도의 처리가 요구된다. Bluetooth Classic의 Data는 표준 Bluetooth 규격에 정의된 사항만 처리하므로, 이는 Built-in Library에서 처리되고 외부장치의 처리 대상이 아니다. BLE의 데이터에서는 외부장치의 주요 정보(상태, Bluetooth 제어 명령)를 처리해야 하므로 별도의 추가 처리가 요구된다.

Security module
[396 P ] 외부장치의 외부 인터페이스는 Bluetooth 통신이며, 이 중 주요 데이터는 BLE 통해 송수신된다. BLE에서는 표준 규격으로 BLE pairing을 하여 인증과 암호화를 제공하지만, 이를 더 보강하여 외부장치에서는 자체 인증과정을 추가하였다. 자체 인증과정은 CRA 방식을 따르며, BLE AUTH service를 이용하여 처리한다. BLE AUTH service의 정의는 Bluetooth module에서 설명하였고, 여기에서는 실제 어떻게 사용되고 처리되는지 설명한다.
[397 P a8] CRA (Challenge – Response Authentication)의 개요
[398 P ] CRA는 네트워크 및 시스템 보안을 강화하기 위해 사용되는 인증 방식으로, 사용자가 비밀번호를 직접 전송하지 않고 보안 검증을 수행할 수 있도록 설계되었다.
[399 P ] CRA는 사용자와 인증 서버 간에 임의의 질문(Challenge)을 생성하고, 사용자가 이에 대한 적절한 응답(Response)을 제공해야 하는 방식으로, 비밀번호 노출을 방지하는 강력한 인증 기법입니다.
[400 P a8] CRA 용어
[401 TABLE 5 rows]
용어 | 설명
Challenge | 요청자가 상대방에게 임의로 생성한 질문 또는 난수를 전송
Response | 상대방이 해당 Challenge에 대한 암호화된 응답을 생성하여 요청자에게 전송
Nonce | 재사용 공격(Replay Attack)을 방지하기 위해 사용되는 일회성 숫자
HMAC(Hash-based Message Authentication Code) | Challenge와 비밀 키를 기반으로 응답을 생성하는 알고리즘
[402 P a8] CRA 기본적인 절차
[403 P a8] Challenge 생성: 요청자가 난수(Challenge)를 사용자에게 전송
[404 P a8] Response 생성: 상대방이 자신의 비밀 키를 사용하여 Challenge에 대한 응답을 생성
[405 P a8] Verify: Response를 검증하는 단계. 요청자가 상대방의 Response를 확인하여 인증 여부 결정
[406 P a8] Confirm: Response가 일치하면 인증 완료
[407 P ] CRA에서 사용되는 암호화 Key는 NVM에 저장되는데, 보안과 무결성을 위하여 암호화되어 저장된다. Security module은 이러한 NMV 데이터에 대한 처리도 수행한다.

[426 P 3] SW-FW-DS-ID-012, 보안 처리 유닛
[427 P ] BLE data 통신을 통해 기기 제어나 기기 및 의료 정보같은 민감한 정보가 송수신될 수 있으므로,  연결하고 통신하려는 상대방이 적법한지를 확인해야 한다. BLE 표준 규격에서도 Pairing이라는 인증 방법을 제공하지만, 보안을 더욱 강화하기 위해 별도의 CRA 인증 방식을 사용한다. 그리고 암호화는 BLE 표준 규격에서 제공하는 암호화를 사용한다. 따라서, BLE pairing이 완료된 후에만 CRA 인증을 시작할 수 있다.
[428 P ] 먼저, BLE가 연결이 시작되면, CRA 인증을 시작하는데 타이머를 시작하여 일정 시간내에 CRA 인증이 완료하지 못하면 실패로 간주하여 연결을 끊는다.
[429 P ] 인증 절차는 BLE AUTH service를 통해 인증 요청하는 상대방과 정보를 주고받는다. 실제 오가는 정보의 처리는 보안 처리 유닛에서 이루어 지며, BLE AUTH service는 일종의 인터페이스를 제공한다. 그리고, 위에서 설명한 것처럼 BLE pairing을 수행한 후에 CRA 인증을 시작할 수 있으므로 BLE pairing이 완료되지 않으면 BLE AUTH service에 접근할 수 없다.
[430 P ] 아래 <그림 11>은 CRA 인증 절차를 보여주는 것으로, Server는 외부장치가 되고 Client는 인을 요청하는 상대방이 된다. 그리고 NONCE나 HMAC와 같은 인증 절차에 사용되는 알고리즘 등은 보안 툴박스 유닛을 통해 값을 생성하고 얻는다.
[431 P ] 추가로, BLE는 1:1 연결만 지원하여 한 사용자가 외부장치를 사용할 시, 다른 사용자의 간섭을 방지한다.

[451 P ] <그림 11>의CRA 인증 절차는 다음과 같다.
[452 P a8] CRA 인증을 시작하기 위해서는 서버와 클라이언트 사이에 BLE 연결과BLE Pairing이 완료되어 있어야 한다.
[453 P a8] 클라이언트는 AUTH service의 Challenge characteristic에 auth_type과 NOUNCE_A를 쓰므로 해서 CRA 인증을 시작한다.
[454 P a8] Challenge characteristic에 데이터가 써지면, 서버는 auth_type가 적당한 값인지 확인한다. 허용되지 않은 값이면, 인증은 실패로 간주하고 인증을 종료하고 BLE 연결을 끊는다. 적법한 값이면 먼저 Status characteristic에 in_progress로 클라이언트에게 알린다. 그리고 NOUNC_B와 HMAC_B를 Response characteristic를 통해 생성하여 클라이언트에게 알린다.
[455 P a8] 클라이언트에서 Response characteristic에 데이터가 들어오면, HMAC_B’를 생성한 수에 HMAC_B와 비교한다.
[456 P a8] HMAC_B = HMAC_B’ 이면, 클라이언트는 HMAC_A을 생성하여 Confirm characteristic 통해 서버에 전송한다.
[457 P a8] HMAC_B ≠ HMAC_B’ 이면, 인증은 실패가 되고 종료된다.
[458 P a8] 서버는 HMAC_A를 받은 후에, HMAC_A’를 생성하고 HMAC_A와 비교한다.
[459 P a8] HMAC_A와 HMAC_A’가 같다면, 서버는 Status characteristic을 통해 인증이 성공했음을 알리고 인증은 종료한다.
[460 P a8] HMAC_A와 HMAC_A’가 같지 않으면, 서버는 Status characteristic을 통해 인증이 실패했음을 알리고 인증은 종료한다.
[461 P a8] 그림에는 나와있지 않지만, 인증 타이머가 동작하여 절차에 시간제한을 둔다. 이는 인증이 완료되지 않은 상태에서 BLE의 연결을 계속 유지하게 되면, 데이터 통신도 되지 않은 상태에서 오랜 시간 BLE 연결을 유지하지 않기 위함이다.
[462 P a8] BLE 연결이 완료되면 서버는 타이머를 시작한다.
[463 P a8] 주어진 시간동안 성공이든 실패든 인증 절차가 완료되지 않으면, 인증은 실패로 간주한다. 인증은 실패하면 BLE의 연결이 해제된다.
[464 P 3] SW-FW-DS-ID-013, 보안 툴박스 유닛
[465 P ] 보안 툴박스 유닛은 보안 모듈에서 사용하는 보안 알고리즘의 처리에 대한 인터페이스 제공한다. 이러한 툴박스는 알고리즘을 사용하는 유닛이 복잡한 내용을 알 필요없이 인터페이스를 통해 쉽게 알고리즘의 결과값을 얻는다. 또한, 기존과 다른 알고리즘을 사용하게 되면, 보안 툴박스 유닛만 수정해도 다른 유닛들은 기존 인터페이스를 사용하여 변경없이 알고리즘을 사용할 수 있을 수 있다.
[466 P ] 알고리즘에 필요한 데이터는 보안 NVM 유닛을 통해 얻을 수 있으며, 보안 NVM 유닛 또한 보안 툴박스 유닛을 통해 NVM의 데이터를 복호화한다.
[467 P ] 그리고, 알고리즘에 사용하는 각 키는 보안 NVM 유닛을 통해 얻는다. 리모콘 앱과 매핑 앱이 사용하는 키 생성 알고리즘을 다르게 하여 해당 장치에 원하는 데이터를 전송할 수 있다.

[480 P 3] SW-FW-DS-ID-014, 보안 NVM 유닛
[481 P ] 보안 모듈에서 사용하는 데이터 중에 NVM에 저장된 데이터를 읽거나 쓸 때 NVM의 접근을 처리한다. 다른 유닛들은 NVM의 직접적인 접근의 처리없이 보안 NVM이 제공하는 접근 인터페이스를 통해 쉽게 NVM을 데이터를 사용할 수 있도록 한다. 또한 NVM 데이터의 위치나 데이터 길이, 아니면 전체 NVM 타입이 바뀌더라도 보안 NVM 유닛만을 수정하여, 다른 유닛들은 기존 인터페이스를 통해 변경을 최소화하여 NVM 데이터를 사용할 수 있을 수 있다.
[482 P ] 또한, 보안 NVM 유닛은 하드웨어 인터페이스 모듈의 NVM 처리 유닛을 통해 실제 데이터를 얻는다.
[483 P ] 그리고, 보안 모듈에서 사용하는 모든 NVM 데이터는 암호화가 되어있기 때문에, 이는 보안 툴 박스를 통해 복호화하거나 암호화한다. 이 키에 대한 설명은 보안 툴박스 유닛에서 하였다.
