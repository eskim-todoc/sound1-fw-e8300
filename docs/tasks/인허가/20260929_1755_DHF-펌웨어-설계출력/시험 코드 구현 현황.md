# 유닛 시험 코드 구현 현황

2026-10-02 기준. 115개 ID의 시험 지원 범위를 정리했다. 실제 장치에서 시험한 횟수는 0회다. 이 문서는 유닛 검증 보고서가 아니며, 번호가 등록된 사실을 시험 완료 또는 합격으로 취급하지 않는다.

## 실행 범위

### 일괄 실행 보완 (2026-10-02)

개별 유닛 번호와 기대값은 그대로 두고 코어별 실행기, RTT 명령 콘솔과 로그 추출기를 추가했다. [쉬운 실행 매뉴얼](../../../참고/인허가/사운드1/DHF/04_설계%20검증/SW/펌웨어/유닛%20시험%20일괄%20실행%20매뉴얼.md)을 먼저 사용한다.

- `ut auto 1`: CM3 33유닛/34회 실행 다음 CFX 29유닛. CM3-029 실패 관찰을 별도 실행한다.
- `ut hear 1`: HEAR 2유닛/6입력. 원시 FFT/크기/지수를 같이 보관한다.
- 별도 부트로더의 `ut boot 1`: RAM 파일/CRC/AES 9유닛. 실제 NVM 갱신/리셋/코어 점프는 실행하지 않는다.
- `ut observe 1/2/3 단계번호`: 실제 입력 후 정지 상태에서 24/17/7개 상태를 보관한다. 입력을 만드는 기능이나 자동 합격 기능은 아니다.
- 자동 타깃 경로는 총 73유닛이며 부분 시험을 포함한다. 115개 전체의 시험 완료가 아니다. 실제 입력/물리 출력/저장소/QCC 검증은 기존 범위를 유지한다.

CM3-051은 시험 경계의 SPI 완료 처리를 보완하여 R17/R18의 두 번째 응답에서 기다리던 문제를 해소했다. 23개 조건과 오류 응답 4필드 불일치는 그대로 유지한다. 아래 과거 작업의 대기/차단 설명은 이 보완 전 상태이며 제품 OTA의 오류 처리를 수정한 것은 아니다.

제품 원본 보존, 반복/역순/부분 전송/취소, CFX 응답 게시 순서, 늦은 HEAR 복원, 정상 이미지 분리는 [일괄 실행 검증 근거](qa/batch-tests/checks.json)에서 확인한다. 실제 J-Link 연결이나 보드 실행은 하지 않았다.

### 기존 지원 범위

- 현재 기준서: CFX 42, HEAR 2, CM3 51, BOOT 20개. 방법 I 1/A 31/D 34/T 49.
- PC에서 실제 제품 함수에 고정 입력을 넣은 ID는 CFX 29, CM3 45, BOOT 16개로 총 90개다. 이전 79개에서 CM3의 11개 ID를 확장했다. 부분 시험과 비활성 구형 보드용 드라이버도 포함한 수이며, 90개 전체 합격을 뜻하지 않는다. 모의 드라이버/SDK 연산 경계가 있으므로 실기 결과와 구분한다.
- 이번 추가 보완은 제품 원본을 수정하지 않는 조건이다. 제품 소스/헤더/어셈블리/링커/프로젝트 설정 279개를 시작 기준과 비교한다. 기존 사용자 수정도 보존하며 실제 보드 시험은 보류한다. Word/Excel 기준서와 필수성능시험 기준서는 이번에 수정하지 않는다.
- CM3 4/6/30의 기본 입력을 추가했다. 4는 하드웨어 준비 경계의 부분 시험, 6은 실제 맵 변경 함수/RAM 파일 경계, 30은 실제 상태 설정과 플래그 해제다. 별도의 수동 gateway는 선택 사항이다.
- HEAR 2개는 실기 시작/완료/캡처 코드가 있다. 512개 창 계수, 5입력의 독립 DFT 기준, FFT 9개 bin의 실수/허수와 vMag 256개 전량 비교를 준비했다. 원시 FFT 512단어/크기 256개/블록 지수도 남긴다. 장치 실행은 아직 하지 않았다. vAbsolute 중간값은 체인 분석이며 완료 뒤 최대값과 구분한다.
- 준비한 벡터만 일치해도 부분 시험, 물리 출력, 실제 저장소 유지, QCC 내부까지 합격으로 확대하지 않는다.

CFX-015 완료 플래그, CM3-006 동일 맵 재요청, CM3-030 같은 상태 재설정은 먼저 설계 의도를 확인할 항목이다. 같은 맵을 다시 읽는 것이 의도된 동작일 수 있고, 같은 상태에도 변경 알림을 반복하는 계약일 수 있다. 이 세 항목을 확정 결함 수에 더하지 않는다. 판정에 사용할 호출 시점과 의도를 정한 뒤 기대값 또는 제품 동작 중 무엇을 고칠지 결정한다.

우선 검토할 것은 계산 실패의 완료 게시, 전하량 제한 적용 범위, 작은 밴드 CIS 패킷이다. 그다음 저장/기동 실패 전달과 통신 응답을 정리한다. 이것은 수정 우선순위 제안이며 제품 소스를 고치라는 승인이나 실기 안전 확인을 대신하지 않는다.

추가 관찰도 오류와 구분한다. CFX-033의 3밴드/1프레임/12채널 조합은 정상 CM3 계산이 만들지 않는 조합이며, 그 2개 불일치는 강건성 자료로만 남긴다. CFX-011의 주파수 대역 불일치 후 갱신 완료 알림, 잘못된 전략에서 PCM을 쓰지 않는 동작, CM3-002의 버스 오류/시간 초과 후 준비 상태 전환은 처리 정책 확인 대상이다. 범위 밖 볼륨의 배열 접근이나 초기화되지 않은 값을 읽는 경로를 억지로 실행하지 않는다.

감사기록 보충 시험은 [검사기](../../../../tests/unit/check_event_log.py)에서 제품 함수 본문을 그대로 사용한다. RAM 파일/고정 시간을 이용한 25개 조건, 93개 비교를 `-O0`/`-O2`로 실행했다. 열기/읽기/쓰기 실패, 짧은 읽기/쓰기, 손상된 식별자/인덱스/개수, 정상 기록의 시간/주소/이벤트, 255개 기록의 순환 저장을 확인했다. case 24/25의 실제 반환 0/기대 -1은 실패로 보존한다. SDK의 close는 내부에서 다시 sync를 호출하므로 case 24는 앞선 sync 오류 무시를 확인한 것이지 최종 저장 유실을 증명한 것은 아니다. case 25는 마지막 close 실패도 성공으로 처리하는 경우다. 초기화와 연결 기록 호출자도 반환값을 사용하지 않으므로 반환만 고쳐서는 상위 알림까지 해결되지 않는다. 실제 파일시스템의 저장 실패나 전원 차단을 시험한 결과는 아니다. 해제 이벤트가 실제 호출되는지, QCC 인증/암호화 전송과 시간의 신뢰성은 별도 범위다.

| 감사기록 | O0/O2 각각 25조건, 93개 비교/2개 불일치 | 파일/시간 모의 입력. 실제 저장 실패/시간 신뢰성/외부 접근 보호의 합격이 아님 |

표의 불일치는 비교 값 수다. 같은 결함이 여러 값이나 반복 실행에 나타나므로 모두 더해 제품 결함 개수로 표현하지 않는다. 실행 결과의 실제값/기대값, 소스 해시, 원문 로그는 각 검사기의 JSON에 보존한다.

- CM3-004는 실제 기동 함수의 준비 전/후 순서만 실행한다. 실제 Initialize와 CFX의 허용 조회는 통합/실기에서 확인한다.
- HEAR-002의 사전 기대값은 현재 기준서의 `HEAR 기대값` 시트에도 모두 넣었다. 오차는 실행 전에 정한 기술 검토 구간이지 제조사의 보장값이 아니다. 장치에서 실제 창/스케일/연산 결과를 읽어 타당성을 확인해야 한다.
- 일부 시험은 기준의 일부 입력만 준비했다. CFX-011/033과 CM3 선택/주변장치/저장/계산 실패의 남은 범위는 coverage 원본의 missing/limitation을 따른다. CM3-029는 실제 상위 호출자도 실행해 실패 후 완료 게시를 재현했다. 초기화되지 않은 지역 T/C 배열 읽기만 기존 시험 경계에서 생략하므로, 남은 공유값을 제품의 보존 동작으로 해석하지 않는다.
- CM3-002/031/032/033/038/039/041/042/043/046/048/049에는 이제 PC 입력이 있다. 다만 안전하게 격리한 타깃 자동 입력 경로는 추가하지 않았다. 제품 원본에 새 시험 경계를 넣지 않는 조건이므로 PC 입력과 타깃 관찰을 구분한다. BOOT-002/007/017도 PC 범위이며 실제 타이머/트림/NVM/서비스 명령을 임의로 실행하는 방식으로 채우지 않았다.
- 수동 관찰은 시험자가 실제 입력을 적용한 전/후 상태를 기록하는 경로다. 실제 저장소 유지, 핀/전압, LED 사진, RF/전극 출력 및 QCC 내부 결과는 PC 벡터로 대체하지 않는다.
- SDK FIL의 약 4KB 지역 객체로 스택을 초과하던 BOOT 시험 4곳은 시험 전용 BRAM 작업 공간 하나로 바꿨다. 기존 RTT 제어 주소는 유지하고 객체는 매 사용 전 초기화한다. 정상 빌드에는 이 공간이 없다. SDK 정적 프레임 검사에서 선택한 ARM 12파일의 최대 단일 프레임은 1,184바이트다. 전체 호출 깊이/IRQ와 정상 RTT 래퍼의 호출별 256바이트를 포함한 최악 스택은 실기에서 확인해야 한다.
- 따라서 115개 ID가 연결돼 있다는 것과 모든 입력의 시험 코드/실기 판정이 완료됐다는 것은 다르다. 부족한 벡터를 없애거나 분석 방법으로 바꿔 완료 수를 늘리지 않는다.

## 검토 의견 반영과 검증 근거

- 이전 단계에서 설계 입력의 요구사항 사양서/시스템 기준서부터 갱신하고 출력의 공통 시험을 맞췄다. 1ms +/-5% 처리 주기, 자극 볼륨 증가, 감사기록 생성, 오류 정보 노출과 접근/전송 보호 조건을 정리했다. 이번에는 기준서의 기존 번호/서식/병합과 문자별 `[-]/[+]` 비교를 수정하지 않았다.
- 상위 요구사항 50개, 소프트웨어 요구사항 81개가 시스템 시험 입력/출력 양쪽에서 추적되는지 병합 셀까지 확인했다. 유닛 115개와 통합 17개 ID도 유지한다. 외부 상위 매트릭스의 원본 값은 수정하지 않았다.
- 최종 `run_suite.py --sdk --preserve-source tmp/unit-tests/source-preservation/before-complete.json`의 33항이 종료 코드 0이다. SDK 정상/시험 6개 링크, 시험 심볼의 정상 빌드 제외, 공유 메모리 주소, 현재 소스/헤더/링커 입력, 정적 메모리와 선택한 ARM 함수의 단일 스택 프레임을 검사했다. 최대 단일 프레임은 1,184바이트이며 전체 호출 깊이의 안전성을 증명한 결과는 아니다. 종료 코드 0은 알려진 제품 실패까지 통과했다는 뜻이 아니다.
- 시작 기준과 최종 결과는 [소스 보존 결과](qa/source-preserving-tests/suite/source-preservation.json)와 [최종 검사 결과](qa/source-preserving-tests/suite/checks.json)에 보존했다. 같은 QA 폴더에 14개 JSON과 33개 실행 로그를 복사해 두었다. 제품 279개 파일은 시작 내용과 동일하며 호스트 시험 C/H 33개도 UTF-8/CP949 검사를 통과했다. 원시 결과의 `tmp/unit-tests` 경로는 실행 당시 경로이며, 보존본은 QA 폴더 아래 같은 하위 경로에서 읽는다.
- 문서 보존/사전 수치/문자별 비교 및 화면 검토 근거는 `qa/validation-review`에 보존했다. 기존 5개 파일만 갱신했으며 `[작성자 전용]`과 필수성능시험 기준서는 해시 불변이다. 보고서를 실기 결과처럼 작성하거나 Git 커밋/병합/장치 다운로드를 하지 않았다.
