# 부트로더 단계 LED 조기 점등 — 이력

**TL;DR**: 2026-04-27 조사 시작 ~ 2026-04-30 구현·검증 완료. Step 3 SLOWCLK_DIV32 보정 후 가드 ON+UART 비활성에서 SKYBLUE fade cycle 정상. 첫 LED 인지 1,670 → 약 540 ms (단축 ~1,130 ms, 68%). 가드 OFF 디폴트 회귀 — 기존 부트로더 동작 영향 없음. 사후 갱신으로 cycle 540→360 ms(OFF 180→0)로 부트로더 종료~CM3 진입 추가 ~100 ms 단축.

## 1. 결과 요약

- **사용자 검증**: Step 3 보정 후 정상 동작 (가드 ON + UART 비활성 시 SKYBLUE fade cycle 정상)
- **회귀**: 가드 OFF 디폴트 회귀 — 기존 부트로더 동작 (UART, 디버그 LED, CM3 부팅) 영향 없음
- **정량 효과** (요구사항.md §1.2 timeline 기반):
  - 기존: 첫 LED 인지 = 1,670 ms (ROM 500 + 부트로더 440 + CM3 730)
  - 본 작업: 첫 LED 인지 ≈ 540 ms (ROM 500 + 부트로더 T-B = 수십 ms 후)
  - **단축: ~1,130 ms (약 68%)**
  - 사후 갱신 (2026-05-07, §8): 부트로더 cycle 540 → 360 ms (OFF 180 → 0). 첫 LED 인지 시점은 동일 (ON portion 360 ms 그대로), 부트로더 종료 후 CM3 진입까지 **추가로 ~100 ms 단축**
- **빌드 가드**: `TDC_BOOT_LED_ENABLE` (Step 4 시점 디폴트 = 1, 정식 채택). 비활성화는 `-DTDC_BOOT_LED_ENABLE=0` 으로 override

## 4. 사용자 측정 1 차 오동작 → Step 3 보정 (학습 큰 사건)

### 4.1 현상

Step 1/2 commit 후 사용자 빌드·측정: 동작 가시성 모호. 사용자 진단:
> "동작을 하는 건지 안 하는 건지 모르겠다. CM3에서 시스템 클럭 설정한 후에 관련 클럭들에 대한 div 설정하는 항목을 부트로더에서도 동일하게 해야할거 같아. 타이머 클럭에 문제가 있는거 같아."

### 4.2 원인 진단

이중 문제:

#### a. RSL10 General Timer 의 클럭 체인 — Step 2 의 가설 잘못

[`ci_timer.h:56`](../../../../src/2__cm3/Gen1_5/common/ci_timer.h):
```
공식: T = 2^prescale × (tick + 1) / 40 kHz   (SLOWCLK = 1.28 MHz 기준)
```

즉 **General Timer = SLOWCLK / 32 = 40 kHz** 가 base clock. SYSCLK 30.72 MHz 가 아님.

Step 2 의 reload = 307 (30.72 MHz / 100 kHz - 1 가정) 은 무의미한 값. (40 kHz 기반에서 reload 307 → 7.7 ms 주기 ISR — fade 시간 모두 7.7 배 늘어남).

#### b. 부트로더에 D_CLK 분주 설정 자체 부재

[`ci_power.c:154-156`](../../../../src/2__cm3/Gen1_5/common/ci_power.c) (CM3 측):
```c
// SLOWCLK은 반드시 1.28 MHz로 설정
D_CLK->CFG_1 = (ADCCLK_PRESCALE_8 | ADCCLK_SRC_SYSCLK | SDMCLK_PRESCALE_2
              | SLOWCLK_PRESCALE_24 | SLOWCLK_SRC_SYSCLK | UARTCLK_SRC_SYSCLK);
D_CLK->CFG_2 = (UCLK_PRESCALE_8 | UCLK_SRC_ADCCLK);
delay_ms(5);
```

부트로더에는 이 분주 설정이 없어 SLOWCLK 가 디폴트값 (불명) 으로 동작. SYSCLK 30.72 MHz 변경 후에도 SLOWCLK 분주 미설정 → Timer base clock 불명.

### 4.3 보정 (Step 3, commit `27f2c28`)

`tdc_boot_led_init()` 안에:

1. **D_CLK 분주 설정 추가 (CM3 와 동일)**: `SLOWCLK_PRESCALE_24` → SLOWCLK = 1.28 MHz → Timer = 40 kHz 보장. UARTCLK_SRC_SYSCLK 유지 → UART baud 영향 없음.
2. **`tdc_delay_ms(5)` 안정화 대기** (CM3 ci_power.c:158 동일).
3. **PWM 매개변수 재계산** — Timer 25 us tick (= 1/40 kHz, 분해능 한계):
   - reload 307 → **0**
   - PWM 주기 = 100 bin × 25 us = **2.5 ms = 400 Hz** (깜빡임 안전)
   - 1 ms 단위 phase tick 은 별도 카운터로 ISR 40 회 마다 호출 (`s_tdc_boot_led_isr_in_ms`)

duty G:B = 30:40 그대로 유지 (k_led_mix[en__LED_SKYBLUE] 비율).

### 4.4 검증

사용자 재측정: **"정상동작하는거 같아"** — Step 3 보정 후 의도 형태 동작 확인.

### 4.5 학습 (회고 후보)

- **Cortex-M MCU 의 peripheral 은 시스템 클럭 직결이 아니라 분주된 sub-clock 기반인 경우가 많다.** General Timer 가 그 예 — SLOWCLK 분주값에 의존.
- **CM3 측 클럭 분주 설정을 부트로더가 안 하면 같은 peripheral 동작이 다르게 나온다.** 부트로더는 보통 polling 기반이라 분주에 둔감하지만, ISR 기반 신규 모듈을 부트로더에 추가하면 분주 설정도 옮겨와야 한다.
- **SDK 함수의 인자 단위 (cycles vs us vs ms)** 는 헤더 주석으로 확인. ci_timer.h:56 같은 공식 주석이 결정적 단서.

## 8. 사후 변경 — OFF phase 0 (2026-05-07)

부트로더 SW PWM `TDC_BOOT_LED_T_OFF_MS` **180 → 0** ([`tdc_boot_led.c:54`](../../../../src/0__bootloader/source/led/tdc_boot_led.c)). cycle = 540 → **360 ms**. 부트로더 종료 후 CM3 진입까지 **약 100 ms 단축**.

근거: OFF 180 ms 의 wait 는 CM3 진입 직후 자체 초기화 시간 (현재 측정 ~730 ms, [`power-on-early-lighting`](../power-on-early-lighting/) 으로 단축 중) 으로 자연 흡수됨. 사용자가 보는 LED 패턴 (SKYBLUE fade in/peak/out → OFF → 정식 LED_ST_POWER_ON) 은 동일.

phase machine 자체는 그대로 유지 (FADE_OUT 후 OFF phase 진입 → t ≥ TOTAL=360 즉시 만족 → DONE → 다음 1 ms tick 에서 wait 탈출). D-5 결정 행은 유지하고 본 항목으로 사후 갱신만 표기.

영향:
- [`bootloader.c:1376`](../../../../src/0__bootloader/source/bootloader.c) wait 주석 540 → 360 갱신
- [`tdc_boot_led.h:19,27`](../../../../src/0__bootloader/include/led/tdc_boot_led.h) 주석 540 → 360 갱신
- [`power-on-early-lighting/이력 및 결과.md §5`](../power-on-early-lighting/이력 및 결과.md) V10 분석의 절대 시간 정렬 (이전: T_PowerOn = ROM 500 + 부트로더 540 = 1040, cycle 가 작업 ≈440 보다 길어 cycle 가 종료 결정) → (변경 후: ROM 500 + max(작업 ~440, cycle 360) = ROM 500 + ~440 = **~940 ms**, 작업이 종료 결정). 약 **100 ms 단축**. V10 결론 (영향 없음) 자체는 변하지 않음 (QCC 자체 schedule + 안전 마진 충분)
- **CM3 측 보상** (2026-05-07): [`LedOutput.c`](../../../../src/2__cm3/Cortex-M3-src/systemControl/LedOutput.c) 에 `LED_BOOT_HANDOFF_OFF_MS = 100 ms` 매크로 + `LED_TX_LEAD_OFF` phase 추가. `LED_ST_POWER_ON` reset 분기에서 leading OFF 100 ms 후 FADE_IN 진입. 부트로더 자체 잔여 ~100 ms + 본 leading 100 ms ≈ 200 ms 자연 OFF 로 변경 전 부트로더 OFF gap (~180 ms) 보전. [`power-on-early-lighting/이력 및 결과.md §5.7`](../power-on-early-lighting/이력 및 결과.md) 참조.
- **CM3 측 보상 갱신** (2026-05-07 (2)): 100 ms leading OFF 가 사용자 체감 부족 (첫 OFF gap 200 ms 가 burst OFF 180 ms 와 비슷해 분리감 X). `LED_BOOT_HANDOFF_OFF_MS` (100) → **`LED_POWER_LEAD_OFF_MS` (400)** rename + POWER_OFF 도 적용 + cross-fade 전용 `LED_DIMMING_TX_FADE_MS = 60 ms` 분리 + POWER_ON burst 5 → 4. [`power-on-early-lighting/이력 및 결과.md §5.8`](../power-on-early-lighting/이력 및 결과.md) 참조.

## 1. 작업 개요

### 1.1 목표
사용자가 전원 입력 직후 "켜졌다" 를 빨리 인지할 수 있도록 **CM3-Bootloader 진입 직후 LED 점등**. 이후 정식 `LED_ST_POWER_ON` 버스트는 "다 켜졌다" 의미로 그대로 사용 → **두 단계 피드백** 제공.

### 1.2 부팅 타임라인 (실측 — 오실로스코프)

| 구간 | 길이 | 손댈 수 있는가 |
|---|---|---|
| 전원 입력 → 부트로더 첫 시작 | **500 ms** | ❌ Ezairo 내부 ROM 부트로더 (Flash 로드) — 물리적 한계 |
| 부트로더 첫 시작 → CM3 첫 시작 | **440 ms** | ✅ `0__bootloader/main.c` (우리 영역) |
| CM3 첫 시작 → Power On LED | **730 ms** | ✅ CM3 앱 — 기존 `power-on-early-lighting` 작업 대상 |
| **합계 (전원 → 첫 LED)** | **1,670 ms** | |

측정 단서: JTDO 디버그 핀 토글로 부트로더 시작/끝 마킹.

### 1.3 정량적 가치
- 현재: 첫 LED 인지 = 1,670 ms
- 부트로더 LED 적용 시: **500 ms** (ROM 영역만 남음)
- **단축: 약 1,170 ms (~70 %)**
- 부트로더 LED ↔ 정식 LED 사이 텀: **1,170 ms**
  - `power-on-early-lighting` 으로 730 ms 구간을 단축하면 이 텀도 함께 줄어듦 (보완적)

## 3. 미해결 조사 항목

### 3.1 LED G 미스터리 (Q-A) — ✅ 자연 해소 (2026-04-27 2회차)

> [!NOTE]
> A 작업 사후 fix (`LED/20260427_non-blocking-fade-off/이력 및 결과.md §8`, commit `85c250f`) 로 **첫 이상 펄스가 사라짐**. cross-fade Phase A (FADE_OUT) 가 fade-off cancel 시점 잔존 `LED_outputColor` 를 prev 색으로 보고 가동되던 것이 본 미스터리의 정체였음. 별개 HW/SDK 이슈가 아니었음.
>
> V1/V2/V3 측정은 **불필요**. 후보 1 (`ci_dio_configure_normal` 잔존값) / 후보 2 (`Sys_DIO_CM3JTAGConfig` 누설) 모두 기각. 단 새 세션에서 재측정 시 첫 띡- 14 펄스 정상 출력 확인을 한 번 더 검증할 것.

**현상 (역사적 기록)**: 오실로스코프에서 부트로더 실행 구간(JTDO HIGH = 부트로더 → CM3 사이의 440 ms 윈도우, 또는 CM3 → Power On LED 730 ms 윈도우 중) LED G 채널에 의도하지 않은 ON 펄스 발견.

**기각된 가설**
- ❌ UART RX 핀(DIO15 = LED G) 공유로 인한 `Sys_UART_DIOConfig` 재설정 → `DIO_NUM_UART_ENABLE` = 1 로 `gs_tdc_uart_enable` = false → 해당 코드 경로 스킵 확정

**남은 가설**
- ⏳ **후보 1**: CM3 `ci_dio_configure_normal()` 이 LED 핀을 GPIO_OUT으로 (재)설정할 때 출력 데이터 reg 잔존값으로 잠시 LOW(=ON for active low)
- ⏳ **후보 2**: CM3 `Sys_DIO_CM3JTAGConfig(true, false)` (`Cortex-M3-src/main.c:274`) 가 SWJ-DP 그룹에 DIO15 포함 시 LED G 핀 점유 (JTDO 토글이 LED G 신호로 누설)

**검증 미실시 — 다음 세션에서 측정 필요**
| ID | 방법 | 해석 |
|---|---|---|
| V1 | CM3 main 진입 직후·`Sys_DIO_CM3JTAGConfig` 직전·직후·`ci_dio_configure_normal` 직후 별도 디버그 핀 토글 | 펄스 시점 매칭 |
| V2 | CM3 main 진입 직후 `Sys_GPIO_Write(LED_G, 1)` 한 줄 추가 | 사라짐 = 후보 1 |
| V3 | `Sys_DIO_CM3JTAGConfig(true, false)` 일시 제거 (RTT 디버깅 일시 포기) | 사라짐 = 후보 2 |

**LED 엔진 초기값 검증 결과 (이 세션에서 코드 분석 완료)**:
타이머 핸들러(`CFX_0_IRQHandler` → `led_arbiter_tick` → `LED_OUT`)는 첫 tick부터 모든 GPIO OFF로 정상 출발. LED G ON 경로는 핸들러 외부.

### 3.2 SDK 확인 필요
`Sys_DIO_CM3JTAGConfig` 정의가 SDK 영역에 있어 Sound1 repo 내에는 없음. 후보 2 정확 판단을 위해 SDK 경로 확인 후 SWJ-DP 핀 매핑 조사 필요.

### 3.3 SKYBLUE 색감 매칭 (Q-C 후속)
부트로더는 PWM 미지원 → 풀밝기 GPIO ON/OFF만 가능. 정식 LED는 PWM dimming + RGB cap (`k_led_mix[en__LED_SKYBLUE] = {0, 30, 40}`).

| 옵션 | 부트로더 출력 | 정식 LED 와 차이 |
|---|---|---|
| C1 | G+B 풀밝기 (시안) | 색 가깝되 풀밝기 vs PWM dimming 밝기 점프 |
| C2 | R+G+B 풀밝기 (백색) | 색 다름, 풀밝기 |
| C3 | 단일 LED (B 또는 G) 풀밝기 | 색·밝기 둘 다 차이 |
| C4 | 부트로더 SW PWM | 매칭 정확, 부트로더 코드↑ + 440 ms 부담 |

**잠정 권고: C1 + 정식 LED 첫 사이클 fade-in 생략** (밝기 점프 최소화). 단 결정 전 확인 필요:
1. CM3 SKYBLUE의 R:G:B 비율 — 위 코드(`k_led_mix`)에서 확인됨: `{0, 30, 40}` (G 30%, B 40%)
2. 정식 LED 첫 사이클 fade-in 생략 가능 여부 — 미조사

## 4. 발견된 별도 버그 — `turnOffLED()` / `led_force_fade_off()` 폴링

이 세션 도중 사용자가 발견. **본 작업과 별개 이슈, 별도 task로 분리 필요.**

### 4.1 위치
- `projects/Sound1/src/2__cm3/Cortex-M3-src/systemControl/LedOutput.c:632-662` — `turnOffLED()`
- 같은 파일 `:363-391` — `led_force_fade_off()`

### 4.2 문제
둘 다 `for (...) { LED_OUT(); delay_ms(1); }` 폴링 패턴.
- `turnOffLED`: 30 ms 블로킹 (`LED_DIMMING_FADE_MAX_MS = 30`)
- `led_force_fade_off`: 40 ms 블로킹 (`LED_DIMMING_FADE_MAX_MS + 10`)

타이머 ISR 기반 LED 설계의 **"메인 코어가 LED 처리에 갇히지 않는다"** 전제를 정면 위반. 게다가 `s_led_isr_suspended = true` 로 ISR을 멈춰놓고 직접 폴링하는 거꾸로 된 구조.

### 4.3 수정 방향
ISR 기반 fade-off 상태머신:
```c
/* 호출자: 즉시 return */
void turnOffLED(void) {
    s_fade_off_state = LED_FADE_OFF_ACTIVE;
    s_fade_off_t     = 0;
}

/* led_arbiter_tick() 내부에서 매 tick 1 step */
void led_arbiter_tick(void) {
    if (s_fade_off_state == LED_FADE_OFF_ACTIVE) {
        /* perceived 감소 → LED_OUT() → t++ → 완료 시 IDLE */
        return;
    }
    /* ... 기존 arbiter 로직 ... */
}
```

**Initialize-time 호출 케이스**: 이 시점엔 CFX FIFO IRQ 미활성 → ISR이 안 돌아 위 상태머신이 진행 안 됨. `LED_outputColor = BLACK` (data init) 이므로 fade 자체가 무의미. → "ISR 활성 검사 → 비활성이면 즉시 OFF 1회" 분기 필요.

### 4.4 `LED_DIMMING_FADE_MAX_MS` 변경 영향
이 세션 직전 commit `5240bf2`에서 15 → 30 으로 상향. 위 폴링 블로킹도 15 → 30 ms 로 늘어난 상태. 수정이 더 시급해진 셈.
