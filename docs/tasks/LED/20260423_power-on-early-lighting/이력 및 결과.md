## 4. 사후 fix history (학습 큰 사건)

### 4.1 Fix A — tdc_touch_init_begin() 위치 (2026-05-04)

#### 현상
V10 검증에서 워치독 리셋 (3초 터치 슬립 → 깨움) 시 SPI 에러 회귀 (`DMA0/1_CNTS->TRANSFER_WORD_CNT_SHORT`).

#### 1차 가설 (사후 무효 확인)
P11 (`tdc_touch_init_begin()`) 이 init_I2c 직후라 `init_cm3_SPI()` 시점이 늦어져 NRF 잔존 SPI 통신과 race.

#### 적용
P11 위치를 `init_cm3_SPI()` 직후로 이동 (commit `8803e29`).

#### 사후 분석 (2026-05-06)
- **가설 약점 확인**: I2C 와 SPI 는 별개 버스라 P11 위치 (`init_I2c()` 직후) 가 직접 `init_cm3_SPI()` 와 race 경로 없음
- **NRF 코드 모두 dead** ([`ResetNRF()`](../../../../src/2__cm3/Cortex-M3-src/systemControl/initialize.c#L74), [`NRF_Off_Command()`](../../../../src/2__cm3/Cortex-M3-src/systemControl/systemControl.c) 의 `Sys_GPIO_Set_*` 모두 주석)
- **근본 원인은 별개**: 사용자 피드백 (NRF→QCC 교체 레거시, SPI master = QCC, ISD_CHECK 와 batt/charge 송신 게이트 불명) 조합 분석 결과 V10 SPI race 의 본질은 **QCC wakeup 후 첫 SPI burst timing** 이며 CM3 측 fix 만으로는 해결 못 함

#### 결과
- Fix A 의 가설은 무효이지만 **코드 변경 자체는 더 안전한 시점으로 정착** — `init_cm3_SPI()` 직후 = SPI bus init 직후이므로 터치 MCLR 펄스 발생 시 SPI line 영향 가능성 최소화. 보수적 위치 유지
- V10 SPI 에러 자체는 본 작업 외부 이슈로 분리 (§5)

### 4.2 Fix B-LED — POWER_OFF burst race 시리즈 (2026-05-06)

#### 발견 경위
사용자 V10 재테스트 중 부수적으로 POWER_OFF 양상 변화 보고. 본 작업의 **ISR 책임 분리 (commit `cecbc3d`) 가 도입한 race**.

#### Root cause
`led_arbiter_tick()` 가 CFX_0 ISR 에서 제거되어 TIMER3 ISR 단독 실행 → main loop iter 와 비동기 → `LedOutputPattern` 이 1-tick stale 상태 → systemControl 의 burst 종료 검출 (`current_led_pattern != en__LED_POWER_Off`) 이 stale=`en__LED_NA` 시 즉시 true → systemOff 트리거 → `led_force_fade_off()` → POWER_OFF burst 미표시.

#### 적용 단계

| Fix | Commit | 변경 |
|---|---|---|
| Fix B-LED-1 | `dcd1204` | systemControl 의 burst 종료 검출을 `!led_is_power_burst_in_progress()` 함수로 변경. burst flag 는 `led_engine_run()` 이 직접 set/clear 하므로 ISR phase 무관 정확 |
| Fix B-LED-2 | `211cc15` | LedOutput.c `led_engine_run()` reset 분기 시작에서 `if (p->burst_cnt > 0) s_power_burst_in_progress = true;` 즉시 set — fade-out Phase A 동안에도 burst 진행 중으로 표현. **검증 전 본질 전환** |
| Fix B-LED-3 (최종) | `9876044` | timer/tick 기반 set 의 race risk 회피 — flag set/clear 책임 명확 분리. **set**: `led_request()` 가 burst 패턴 (`burst_cnt > 0`) 요청 시점 즉시 (외부 호출). **clear**: `led_engine_run()` 이 burst 자가 해제 시 (LED 핸들러 내부). + 네이밍 컨벤션 적용 (`s_tdc_burst_pending`, `tdc_led_is_burst_pending()`). 호출처 4곳 갱신 (systemControl.c × 2, tdc_ui_command.c × 2) |

#### 검증
사용자 재측정 OK — POWER_OFF 패턴 일관 표시 확인.

#### 학습 (회고 후보)
- **ISR 책임 분리 시 main loop 와 동기화 가정 의존성 확인 필수** — 한 ISR 에서만 갱신되던 상태가 분리 후 stale 보일 수 있음
- **타이머/tick 기반 flag 갱신은 race 잠재** — flag 의 set/clear 주체를 외부/내부로 명확 분리하면 timer 무관 정확
- **Fix 의 근본 분석 = 가설 단일화 회피** — Fix A 의 첫 가설 약점을 추후 발견. 처음부터 가설 3 개 cross-check 했으면 더 좋았음 ([분석·디버깅 규칙](../../../../../docs/지침/코딩/분석·디버깅%20규칙.md) §2 적용 사례)

## 5. V10 SPI 잔존 이슈 — 본 작업 외부 (현재 형태로 수용)

### 5.1 현상

ULP wakeup (사용자 의도적 트리거) 또는 watchdog reset 시 SPI1_COM_IRQHandler CS_RISE 검사에서 partial burst detect: `DMA0_CNTS->TRANSFER_WORD_CNT_SHORT (1)` + `DMA1_CNTS->TRANSFER_WORD_CNT_SHORT (3)` (3 clock CS toggle, 정상 21-word 패킷 아님). 자가 복구 후 정상 통신.

### 5.2 분석 결과

**부트로더 시간 정렬** (출처: [`bootloader-power-on-indicator/이력 및 결과.md:15`](../bootloader-power-on-indicator/이력 및 결과.md)):

- ROM 500 ms + 커스텀 bootloader 540 ms = **CM3 main 진입 (t3=0) = _전원 인가 후 약 1040 ms_ (T_PowerOn 기준)**

**사용자 오실로 측정 (DIO33 + SPI CS)**:

- 부트로더 진입 시 DIO33 HIGH (~T_PowerOn 500 ms) → **862 ms 후** SPI CS LOW 340 µs 토글 (T_PowerOn ~**1362 ms**)
- **service_mode (부트로더에서 CM3 진입 차단, QCC_CTRL=0 유지) 에서도 CS LOW 토글** → **QCC 자체 schedule 확정** (QCC_CTRL trigger 무관)

**측정 결과 (절대 시간 정렬)**:

| 시나리오 | 핵심 시점 | t3 (ms) | T 절대 (ms) | race detect |
|---|---|---|---|---|
| POR (cold) — 1단계 partial burst (오실로) | CS LOW 340 µs | _-322_ | T_PowerOn ~1362 | _CM3 SPI not-ready 라 detect 못 함_ (사용자 변경 코드의 흡수) |
| POR (cold) — 2단계 정상 RX | `[FAKE_0x34 EXIT-DMA]` | 776~781 | T_PowerOn ~1816~1821 | 정상 (사용자 가설 1.7s + 120 ms 오차) |
| Watchdog (warm) — partial burst | `[SPI] DMA-MISMATCH` | **1577** | T_watchdog 2617 | **있음** (RX_CNT=1, TX_CNT=3) |
| Watchdog (warm) — 정상 RX | (자가 복구 후) | ~1592 | T_watchdog ~2632 | 정상 (partial burst +14 ms) |

**QCC 동작 모델**:

- POR 1단계 (partial burst): _전원 인가_ 후 자체 schedule, T_PowerOn + ~1.36 s, **QCC_CTRL trigger 무관** (service_mode 측정 확정)
- POR 2단계 (정상 21-word): T_PowerOn + ~1.82 s (= 사용자 가설 1.7 s + 120 ms 오차)
- Wakeup (sleep → QCC_CTRL HIGH): SET-NORMAL trigger, SET-NORMAL + ~0.86 s (cold 보다 빠른 wake)

partial burst signature (RX_CNT=1, TX_CNT=3, RX=`00`, TX=`01 02 03` = init 초기값) 는 _정상 21-word 시퀀스 아님_ → **QCC 측 비정상 동작** (wake 완료 직전 transient 구간 SPI 시도). QCC 펌웨어 영역.

**CM3 측 race 처리 (완벽 정상)**:

| 단계 | t3 (ms) | 소요 시간 |
|---|---|---|
| QCC partial burst detect | 1577 | — |
| `SPI1_COM_IRQHandler` mismatch dump + SPI/DMA re-init | 1577~1578 | **1 ms** |
| `bleCommunication SPI_CMMM_ERROR` recovery (NVIC + DMA + SPI 재초기화) | 1578 | (next iter) |
| QCC 정상 21-word 송신 → CM3 RX | ~1592 | 14 ms 후 |
| CM3 RX 처리 + TX 응답 | 1592~1594 | **2 ms** |
| **Total recovery + 정상 통신** | | **~17 ms** |

→ **CM3 측 추가 코드 변경 불필요**.

### 5.3 사용자 영향 평가

| 시나리오 | 영향 |
|---|---|
| Cold (POR) | partial burst 잠재 (T_PowerOn ~1362) 하지만 CM3 측 detect 안 됨 (변경 코드 흡수). **무 영향** ✅ |
| Watchdog | 첫 batt 정보 ~810 ms 지연 (cold 56 ms vs warm 803 ms). 그러나 **POWER_ON 패턴 종료 (t3=1800) 208 ms 전** 정상 batt 정보 도착 → BATT LED 정확 표시 ✅ |

→ **사용자 영향 없음**. 안전 마진 충분 (race latency 가 10 배 이상 튀지 않는 한 안전).

### 5.4 결정

**V10 SPI race 는 본 작업 외부 분리 + 현재 형태 수용**. 본 작업 (LED 조기 점등 + 터치 병렬화) 의 V1~V9 목표 달성 + V10 검증으로 노출된 잠재 이슈 정확히 분석 + CM3 측 추가 변경 불필요로 결론.

→ 별도 task 신설 없이 본 이력 + [`진행상황.md` V10 분석 노트](진행상황.md) 시발점으로 향후 재개 가능. QCC 측 fix 는 담당자 영역 (옵션).

### 5.6 사후 변경 (2026-05-07) — 부트로더 cycle 540 → 360 ms

[`bootloader-power-on-indicator/이력 및 결과.md §8`](../bootloader-power-on-indicator/이력 및 결과.md) 의 OFF phase 180 → 0 변경에 따라 본 §5 절대 시간 정렬의 _전제값_ 갱신:

- 이전: T_PowerOn = ROM 500 + 부트로더 cycle 540 ≈ **1040 ms** (cycle 가 작업 ~440 보다 길어 cycle 가 종료 결정, t3=0 기준)
- 변경 후: T_PowerOn = ROM 500 + max(작업 ~440, cycle 360) ≈ **~940 ms** (작업이 종료 결정). 약 -100 ms 시프트

§5.2 표의 T 절대값은 본 변경 후 측정 시 약 -100 ms 시프트되지만 V10 결론 (CM3 측 영향 없음, QCC 자체 schedule 무관) 은 그대로. 향후 V10 작업 재개 시 재측정값으로 §5.2 표 갱신 필요.

### 5.7 사후 변경 (2026-05-07) — CM3 측 leading OFF 보상 (LED_BOOT_HANDOFF_OFF_MS)

§5.6 의 부트로더 OFF 0 변경에 대응한 CM3 측 보상 — [`LedOutput.c`](../../../../src/2__cm3/Cortex-M3-src/systemControl/LedOutput.c) 에 `LED_BOOT_HANDOFF_OFF_MS = 100 ms` 매크로 + `LED_TX_LEAD_OFF` phase 추가. `LED_ST_POWER_ON` reset 분기에서 leading OFF 100 ms 후 FADE_IN 진입 (cross-fade FADE_OUT 진행 중인 경우는 기존 분기 유지). 부트로더 자체 잔여 ~100 ms + CM3 100 ms = ~200 ms 자연 OFF 로 변경 전 부트로더 OFF 180 ms 이상 보전. POWER_ON 패턴 시작 시점은 100 ms 늦어지지만 부트로더 wait 100 ms 단축으로 사용자 인지 OFF gap 거의 동일 (~180 ms 유지).

⚠ 사후 갱신 (§5.8): 100 ms 가 체감상 짧아 첫 OFF gap 가 burst 내부 OFF 와 비슷하게 보이는 문제 → 400 ms + POWER_OFF 일반화 + cross-fade 분리 + burst 4 회로 갱신.

### 5.8 사후 변경 (2026-05-07 (2)) — LED 시퀀스 인지 종합 개선

§5.7 의 100 ms leading OFF 가 사용자 체감 부족 (첫 OFF gap ~200 ms 가 burst 내부 OFF 180 ms 와 비슷해 두 단계 분리감 X — "띠---, 이, 띠, 이, 띠, 이..." 6 깜빡 단일 시퀀스로 인식). 다음 종합 개선:

| 변경 | 이전 | 신규 | 효과 |
|---|---|---|---|
| leading OFF 매크로 | `LED_BOOT_HANDOFF_OFF_MS = 100` | **`LED_POWER_LEAD_OFF_MS = 400`** | rename + 값 증가. burst OFF (180) 의 ~2.2 배 → 두 시퀀스 명확 분리 (음악 ~1 박자 휴식) |
| LEAD_OFF 진입 조건 | POWER_ON 만 | POWER_ON \|\| POWER_OFF | POWER_OFF 도 직전 색 fade-out 후 400 ms 쉼표 → BLUE burst |
| cross-fade 매크로 | (`LED_DIMMING_FADE_MAX_MS = 30` 공유) | `LED_DIMMING_TX_FADE_MS = 60` (신규, cross-fade 전용) | 점멸 패턴 매 cycle fade (30 ms) 와 분리. 색상 전환 부드러움 ↑ (BATT 변화 등) |
| `s_fade_off_max` | `LED_DIMMING_FADE_MAX_MS + 10 = 40` | `LED_DIMMING_TX_FADE_MS + 10 = 70` | sleep 진입 fade-off 마진 cross-fade 와 일관 |
| POWER_ON burst | 5 회 (1.8 s) | **4 회 (1.44 s)** | 5 회 길다는 사용자 체감 + POWER_OFF 와 대칭 |

체감: 부트로더 띠--- → ~500 ms 쉼표 → CM3 burst 4 회. POWER_OFF 도 직전 색 fade-out → 400 ms 쉼표 → BLUE burst 4 회. 두 시퀀스 모두 시각적 분리 명확. 일반 색상 전이 (BATT 등) 는 cross-fade 60 ms 로 부드러움.

## 7. 후속 작업

- **systemControl `StartFlag` 분기 cleanup** — 본 작업에서 분기 골격은 보수적 유지. 변수 (`StartFlag`, `PowerOn_StartCounter`) read 가 dead 임을 확인했으므로 별도 cleanup task 후보
- **NRF dead code 정리** — `ResetNRF()` / `NRF_Off_Command()` / `NRF_On_Command()` 의 `Sys_GPIO_Set_*` 모두 주석. NRF51 → QCC 교체 (사용자 피드백) 의 잔재. 별도 정리 task 후보 (`legacy/nrf-cleanup` 같은 이름)
- **V10 SPI race (필요 시 재개)** — §5 분석을 시발점으로. QCC 담당자 펌웨어 시퀀스 (특히 wakeup 후 첫 SPI burst timing, ISD_CHECK 게이트 가정) 확인 후 진행
- **`ci_timer.c` 전체 `tdc_timer.c` 리팩토링** — Q10=A 결정의 trade-off (`g_ci_*` / `g_tdc_*` 혼재) 해소

- BLE pairing latch (`ci_timer_get_tick()` 호출 2곳, line 358/563) 는 CFX iteration 활성 후 동작이라 main_tick 기준이 의미적으로 적절. t3_tick 으로 바꿔도 의미 동등이지만 어색.
- LED arbiter 자체 ms 카운터들 (`timer_ms`, `burst_done_cnt`, `s_tx_ms`, `s_fade_off_t`) 은 이미 `led_arbiter_tick()` 호출 주기 (TIMER3 1ms) 기준으로 증가 → t3_tick 절대값으로 변경 시 fade/burst 리팩토링 회귀 위험만 큼, 의미상 동등.

### 커밋 4 보수적 옵션 채택 사유

구현계획 §3.6 의 "분기 자체 삭제" 의도와 달리 분기 골격 (if/else) · `systemStatus.Led_Pattern` 셋업 · `StartFlag` · `PowerOn_StartCounter` 변수는 보수적으로 유지. 분기 내 LED·터치 init 호출 (`turnOffLED` · `led_request` · `tdc_touch_init_begin`) 만 제거. 변수 자체 cleanup 은 별도 작업으로 위임 (현재 사용처 dead 확인 — `PowerOn_StartCounter` read 없음, `batteryNPowerControl.updateBatteryLevel` 호출이 main.c:378 에서 주석 처리).

## V10 SPI 분석 노트 (이후 필요 시 재개용)

본 작업 마무리 시점 (2026-05-06) V10 SPI race 분석 결과. 별도 task 신설 없이 본 진행상황·이력에만 기록. 이후 필요 시 새 작업의 시발점으로 활용.

### 1. 요약

POR (보드 전원 인가) 또는 watchdog reset 시 QCC → CM3 SPI 통신 초기에 partial burst (3 clock CS toggle, 정상 21-word 패킷 아님) 가 발생. 부트로더 시간 정렬 + 사용자 오실로 측정 + RTT 트레이스 측정 결과:

- **원인**: QCC 자체 wake-up 시퀀스의 transient 구간 SPI 시도 (펌웨어 결함 시그너처 — 담당자 영역)
- **CM3 측 처리**: 17 ms 내 자가 복구 (mismatch detect → SPI/DMA re-init → 정상 RX → TX 응답) — **완벽 정상**
- **사용자 영향**: 없음 (POWER_ON 패턴 종료 208 ms 전 정상 batt 정보 도착, BATT LED 정확 표시 보장)

→ **현재 형태로 수용 결정**. CM3 측 추가 변경 불필요. QCC 측 fix 는 담당자 영역 (옵션).

### 2. 핵심 사실

#### 2.1 회로 + 외부 칩 동작

- **DIO24 (QCC_CTRL)**: 외부 풀-다운 10 KΩ. CM3 측 GPIO INPUT 시 자동 LOW (QCC SHUTDOWN). NORMAL 시 CM3 가 HIGH driving
- **IQS323 (터치)**: warm boot 시 전원 유지 → 잔존 ATI (TOUCH ELAPSED 짧음, 33 ms 수준)
- **`snd_qcc_set_mode()`**: 단순 GPIO toggle (DIO24). NORMAL=HIGH, SHUTDOWN=LOW. SPI 통신 자체는 없음 ([snd_qcc.c:77-90](../../../src/2__cm3/Cortex-M3-src/QCC/snd_qcc.c))
- **`snd_qcc_init()`**: `ci_dio_configure_normal()` 안에서 호출 ([ci_dio.c:93](../../../src/2__cm3/Gen1_5/common/ci_dio.c)). DIO24 OUT 설정 + 초기 SHUTDOWN(LOW)

#### 2.2 부트로더 시간 정렬

[`bootloader-power-on-indicator/이력 및 결과.md:15`](../bootloader-power-on-indicator/이력 및 결과.md):

- ROM bootloader: **500 ms**
- 커스텀 bootloader (SW PWM 포함): **540 ms** (1 cycle 보장 — 본 부트로더 작업 결과)
- **→ CM3 main 진입 (t3=0) = 전원 인가 후 약 1040 ms (T_PowerOn 기준)**

본 작업의 모든 t3 값에 1040 ms 를 더하면 _전원 인가 기준_ 절대 시간.

#### 2.3 QCC 측 동작 (담당자 피드백)

- SYS_CTRL=0 → 약 2 초 후 딥슬립 진입
- SYS_CTRL=1 → 깨어남 (전원 cycle 과 동일한 wakeup)
- 깨어나면 기본 시스템 정보 (배터리·충전 상태 등) SPI 송신
- **wakeup → 첫 SPI 패킷 송신까지 ≈ 1.7 초** (담당자 후속 피드백)

#### 2.4 사용자 V10 검증 코드 변경

- `main.c:361 snd_qcc_set_mode(NORMAL)` 삭제 → `initialize.c` 끝으로 이동
- `init_cm3_SPI()` 도 `initialize.c` 끝 (`snd_qcc_set_mode` 직전) 으로 이동
- `ci_dio.c:ci_dio_configure_normal()` 에서 `Sys_SPI_DIOConfig` 주석 + `NRF_SPI_CS_PIN` 을 GPIO output HIGH 로 사전 설정
- `DIO_PIN_Config.h` `SPI_DIO_PIN_CFG` 풀업 약화 (60K → WEAK)
- 효과: CM3 SPI ready 시점이 t3=731 (T_PowerOn 1771 ms) 로 늦춰짐 → POR 1단계 partial burst 흡수 (CM3 측 detect 못 함)

#### 2.5 사용자 오실로 측정 (DIO33 + SPI CS)

- 부트로더 시작 시 **DIO_NUM_ELAPSE_TIME_CHECK (DIO33) HIGH** 설정 → T_PowerOn ~500 ms 시점
- DIO33 HIGH 후 **862 ms** 시점에 SPI CS LOW **340 µs** 토글 → T_PowerOn ~**1362 ms**
- CS HIGH idle 도달 시점 = DIO33 HIGH 시점 = QCC self power-up ≈ ROM time (500 ms) 와 우연 일치
- **service_mode (부트로더에서 CM3 진입 차단, QCC_CTRL=0 유지) 에서도 CS LOW 토글 발생** → **QCC 자체 schedule 확정** (QCC_CTRL trigger 무관)

### 3. 측정 결과 (절대 시간 정렬)

#### 3.1 POR (cold) — Log 1·2

| 시점 | t3 (ms) | T_PowerOn (ms) | 비고 |
|---|---|---|---|
| 전원 인가 (QCC + EZ8300 동시) | — | 0 | |
| ROM + 커스텀 bootloader | — | 0 ~ 1040 | |
| CM3 main 진입 `[POWER-ON START]` | 0 | 1040 | |
| **QCC 1단계 partial burst** (오실로) | _-322_ | **~1362** | CS LOW 340 µs. CM3 측 SPI not-ready 라 detect 못 함 (사용자 변경 코드의 흡수 효과) |
| `init_cm3_SPI()` + `[QCC SET-NORMAL]` | 731~732 | 1771~1772 | DIO24 HIGH |
| **QCC 2단계 정상 21-word RX** | 776~781 | **1816~1821** | (= 사용자 가설 1.7 s + 120 ms 오차) |
| `[POWER-ON END]` | 1800 | 2840 | LED 5 burst 종료 |

→ **race 잠재 (T_PowerOn 1362) 하지만 CM3 측 detect 안 됨** (사용자 변경 코드 효과). 정상 통신.

#### 3.2 Watchdog (warm) — Log 3 (RTT 1000 kHz)

전제: 이전 보드 동작 끝에서 `[QCC] MODE: SHUTDOWN` + CFX SLEEP 진입 → long touch → CM3 만 watchdog reset (QCC SHUTDOWN 상태에서 sleep 유지).

| 시점 | t3 (ms) | T_watchdog (ms) | SET-NORMAL 기준 (ms) |
|---|---|---|---|
| watchdog reset trigger | — | 0 | — |
| ROM + 커스텀 bootloader | — | 0 ~ 1040 | — |
| CM3 main 진입 `[POWER-ON START]` | 0 | 1040 | — |
| `init_cm3_SPI()` + `[QCC SET-NORMAL]` HIGH | 731~733 | 1771~1773 | **0** (wake trigger) |
| **partial burst** (DMA-MISMATCH RX_CNT=1, TX_CNT=3) | **1577** | 2617 | **+844** |
| SPI ERROR HANDLED (recovery) | 1578 | 2618 | +845 |
| **정상 21-word RX** | ~1592 | ~2632 | **+859** |
| TX 응답 완료 | 1594 | 2634 | +861 |
| `[POWER-ON END]` | 1800 | 2840 | +1067 |

→ **race 발생 + 17 ms 내 recovery + 정상 통신**. POWER_ON 패턴 종료 208 ms 전 정상 batt 정보 도착.

#### 3.3 partial burst signature

```
[SPI] DMA-MISMATCH t3=1577 ms / RX_CNT=1 / TX_CNT=3
[SPI] RX_BUFF (LSB->): 00
[SPI] TX_BUFF (LSB->): 01 02 03
```

해석:

- **TX_CNT=3, RX_CNT=1**: SCK 3 clock 토글 후 CS RISE → **정상 21-word 패킷 시퀀스 아님**
- **TX_BUFF = `01 02 03`**: `init_cm3_SPI()` 직후 `SPI_Tx_Buffer[i] = 1+i` 초기값 그대로 ([driver_SPI.c:224](../../../src/2__cm3/Cortex-M3-src/systemControl/driver_SPI.c)) — CM3 측 미준비 상태에서 SCK 3 clock 들어와 의미 없는 초기값 빠져나감
- **RX_BUFF = `00`**: QCC 가 MOSI 에 0x00 1 word 만 띄움 (dummy / NUL)

### 4. QCC 동작 모델 (분석 결론)

세 측정 시점 (POR 1단계 / POR 2단계 / Wakeup) 모두 **QCC 측 자체 schedule** 로 일관 설명:

| 시나리오 | trigger | 첫 SPI 시점 | 비고 |
|---|---|---|---|
| **POR 1단계 (partial burst)** | _전원 인가_ 후 자체 schedule | T_PowerOn + ~1.36 s (= bootloader 시작 + 862 ms) | 오실로 측정으로 직접 확인. service_mode 에서도 발생 → **QCC_CTRL trigger 무관 확정** |
| **POR 2단계 (정상 21-word)** | (1단계 후 재시도 또는 자체 schedule) | T_PowerOn + ~1.82 s (= 1.7 s 가설 + 120 ms 오차) | RTT log 측정 |
| **Wakeup (sleep → QCC_CTRL HIGH)** | _SET-NORMAL HIGH_ trigger | SET-NORMAL + ~0.86 s (cold 보다 빠른 wake) | RTT log 측정 |

QCC 가 _두 모드_ (cold-start vs wake-from-sleep) 에서 _다른 init 시간 + 다른 trigger_ 동작.

partial burst signature (RX_CNT=1, TX_CNT=3) 는 정상 21-word 시퀀스 아닌 **QCC 측 비정상 동작** — wake 완료 직전 transient 구간의 SPI 시도 추정. _QCC 펌웨어 분석은 담당자 영역_ 이라 본 작업 외부.

### 5. CM3 측 race 처리 (완벽 정상)

| 단계 | t3 (ms) | 동작 | 소요 시간 |
|---|---|---|---|
| QCC partial burst detect | 1577 | CS_RISE IRQ → `SPI1_COM_IRQHandler` mismatch 분기 | — |
| 에러 dump + SPI/DMA re-init | 1577~1578 | `clear_SPI_Tx_Buffer` + `ci_SPI_enable_DMA` + SPI re-enable | **1 ms** |
| `bleCommunication SPI_CMMM_ERROR` recovery (next iter) | 1578 | NVIC + DMA + SPI 완전 재초기화 + IDLE 복귀 | (next iter) |
| QCC 정상 21-word 송신 + CM3 RX | ~1592 | DMA0 RX 완료 → `SPI_CMMM_FETCH` | 14 ms 후 |
| CM3 0x34 처리 + TX 응답 | 1592~1594 | `snd_charger/batt_set` + `writeDataToSpiTxBuff` | **2 ms** |
| **Total recovery + 정상 통신 시작** | | | **~17 ms** |

이 흐름은 §8 측정 트레이스로 직접 검증.

### 6. 사용자 영향 평가

#### 6.1 Cold (POR)

- partial burst (T_PowerOn ~1362) 는 CM3 측 SPI not-ready 구간에 흡수 → **사용자 영향 없음**
- 정상 RX (T_PowerOn ~1820) → main loop 정상 동작
- POWER_ON 패턴 (T_PowerOn 1040~2840) 진행 중 정상 batt 정보 도착 → 패턴 종료 후 BATT LED 정확 표시 ✅

#### 6.2 Watchdog

- partial burst (t3=1577) → CM3 detect → 17 ms 내 recovery → 정상 RX (t3=~1592)
- POWER_ON 패턴 종료 (t3=1800) **208 ms 전** 정상 batt 정보 도착 → BATT LED 정확 표시 ✅
- 첫 batt 정보 지연 ~810 ms (cold WAIT=56 ms vs warm WAIT=803 ms) — 사용자 인지 불가 (POWER_ON 패턴 안에 흡수)

#### 6.3 안전 마진

- POWER_ON 1800 ms 윈도우 안에 batt 정보 도착하면 안전. 현재 worst case 여유 208 ms (= 1800 - 1592)
- race latency 가 _10 배 이상_ 으로 튀지 않는 한 사용자 영향 없음 (현재 측정 일관성: cold ±5 ms, watchdog partial burst 시점 일관)

### 7. 결정

**V10 SPI race 는 본 작업 외부 분리 + 현재 형태 수용**:

| 영역 | 결정 |
|---|---|
| **CM3 측 코드 변경** | 불필요 (race 처리 메커니즘 완벽) |
| **QCC 펌웨어 fix** | _옵션_ — 담당자 영역. partial burst 자체는 비정상이지만 사용자 영향 없으므로 우선순위 낮음 |
| **본 분석 작업** | 마무리. 이후 필요 시 본 노트 + [`이력 및 결과.md §5`](이력 및 결과.md) 시발점으로 재개 |

#### 7.1 향후 재개 시 검증 실험 (1건)

`init_cm3_SPI()` 를 다시 Initialize 앞쪽 (예: `init_I2c()` 직후, t3 ≪ 100 ms = T_PowerOn ~1100 ms) 으로 옮긴 빌드로 cold 측정 → t3 ≈ 322 ms (T_PowerOn ~1362 ms) 부근에 **partial burst dump 출력** 되는지 확인. detect 시 _POR 1단계 partial burst 가 watchdog partial burst 와 동일 메커니즘_ 이라는 직접 증거.

#### 7.2 QCC 담당자 추가 질문 (옵션)

1. POR 시 QCC 가 자체 schedule 로 두 단계 SPI 시도 (1단계 +1.36s, 2단계 +1.82s) — 펌웨어 동작과 일치?
2. partial burst (3 clock 후 CS RISE) 가 QCC 어떤 펌웨어 분기에서 발생? (handshake? wake-detection? 펌웨어 결함?)
3. Wake-from-sleep 시 SET-NORMAL+~860 ms 가 정확한 wake-to-first-data 시간?
