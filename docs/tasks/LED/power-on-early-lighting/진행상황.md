# POWER_ON LED 조기 점등 및 초기화 병렬화 — 진행상황

최종 갱신: 2026-05-06 (LED 마무리)

## 현재 단계

**✅ 완료 — LED·터치 V1~V9 통과 + POWER_OFF (Fix B-LED-3) 검증 OK. 머지 승인 대기**

LED·터치 영역의 본 작업 목표 (G1~G5) 달성:
- LED_ST_POWER_ON 조기 점등 (P3-Early, `ci_dio_configure_normal()` 직후) ✅
- Initialize 나머지를 LED 버스트와 병렬 진행 ✅
- TIMER3 ISR 책임 분리 + `g_tdc_timer_t3_tick` 도입 (다른 모듈 영향 0) ✅
- 터치 초기화 FSM 명시화 + 시간 기준 t3_tick 통일 ✅
- 1 ms 틱 중복/손실 없음 (V3·V4·V5) ✅
- POWER_OFF burst pending 책임 분리 (Fix B-LED-3) ✅

V10 SPI 에러 (ULP wakeup 시) 는 본 작업 외부 이슈로 분리 — 본 작업이 도입한 회귀 아니라 V10 검증 강화로 노출된 잠재 이슈. 회로 (DIO24 풀-다운 10K) + QCC 동작 (담당자 피드백) cross-check 결과 **QCC NORMAL 진입 직후 internal wakeup + SPI master init 도중 첫 burst race** 가 본질. CM3 측 fix 만으로는 해결 못 하며 **QCC 펌웨어 시퀀스 명확화 (담당자 영역)** 이 필요. 별도 task 신설 없이 종결, 이후 필요 시 본 진행상황 §"V10 SPI 분석 노트" + [`이력.md §5`](이력.md) 를 시발점으로 새 작업을 다시 열 수 있음.

### 커밋 5 skip 사유

LedOutput.c 검토 결과 t3_tick 통일의 의미 있는 적용 지점이 없음.
- BLE pairing latch (`ci_timer_get_tick()` 호출 2곳, line 358/563) 는 CFX iteration 활성 후 동작이라 main_tick 기준이 의미적으로 적절. t3_tick 으로 바꿔도 의미 동등이지만 어색.
- LED arbiter 자체 ms 카운터들 (`timer_ms`, `burst_done_cnt`, `s_tx_ms`, `s_fade_off_t`) 은 이미 `led_arbiter_tick()` 호출 주기 (TIMER3 1ms) 기준으로 증가 → t3_tick 절대값으로 변경 시 fade/burst 리팩토링 회귀 위험만 큼, 의미상 동등.

### 커밋 4 보수적 옵션 채택 사유

## V10 SPI 분석 노트 (이후 필요 시 재개용)

본 작업 마무리 시점 (2026-05-06) 의 V10 SPI race 분석 결과. 별도 task 신설 없이 본 진행상황·이력에만 기록. 이후 필요 시 새 작업의 시발점으로 활용.

### 1. 핵심 사실 (Grep / 회로 / QCC 담당자 cross-check 후)

- **DIO24 (QCC_CTRL) 외부 풀-다운 10K** — warm reset 시 GPIO INPUT fallback 으로 자동 LOW. **CM3 측 GPIO 잔존 HIGH 가설은 폐기**
- **IQS323 전원 유지** (warm boot 시) — 33 ms ELAPSED (chip 잔존 ATI 즉시 done) 의 자연 설명
- **`snd_qcc_set_mode()` 동작** = 단순 GPIO 토글 (DIO24): NORMAL=HIGH, SHUTDOWN=LOW. SPI 통신 자체는 없음 ([snd_qcc.c:77-90](../../../src/2__cm3/Cortex-M3-src/QCC/snd_qcc.c))
- **`snd_qcc_init()` 호출** = `ci_dio_configure_normal()` 안 ([ci_dio.c:93](../../../src/2__cm3/Gen1_5/common/ci_dio.c)). DIO24 OUT 설정 + 초기 SHUTDOWN(LOW). Initialize 단계 5 시점에 자동 적용
- **QCC 동작 (담당자 피드백 2026-05-06)**:
  - SYS_CTRL=0 → 약 2 초 후 딥슬립 진입
  - SYS_CTRL=1 → 깨어남 (전원 cycle 과 동일한 wakeup)
  - 깨어나면 기본 시스템 정보 (배터리·충전 상태 등) SPI 송신 — 그러나 송신 게이트 시퀀스 (ISD_CHECK 와의 의존) 가 담당자 본인도 헷갈림
- **사용자 의도적 cold/wakeup 측정 (#1 / #2)**:
  - cold (#1): TOUCH ELAPSED=178 ms (chip 새 ATI), FAKE WAIT=55 ms (즉시 batt 정보), SPI 정상
  - wakeup (#2): TOUCH ELAPSED=33 ms (chip 잔존), FAKE WAIT=931 ms (자가 복구 후 정상), SPI 에러 (DMA0=1, DMA1=3)

### 2. Root cause 가설 (회로 사실 정정 후)

`init_cm3_SPI()` 시점이 아니라 **`snd_qcc_set_mode(NORMAL)` 직후 (main.c:361)** 에서 race:

1. warm reset → DIO24 풀-다운으로 자동 LOW → QCC SHUTDOWN
2. CM3 부팅 진행 → `init_cm3_SPI()` 정상 (QCC 송신 없음)
3. main loop 진입 → `snd_qcc_set_mode(NORMAL)` → DIO24 HIGH
4. **QCC internal wakeup + SPI master init (수십 μs ~ 수 ms) 진행 도중 CS / clock line 첫 burst 가 짧게 잡힘**
5. CS 의 짧은 toggle 한 번이 SPI1 transfer 로 잡혀 DMA0=1, DMA1=3 같은 부분 카운트
6. CS_RISE IRQ → 에러 출력 + SPI 재초기화 (driver_SPI.c:82-90)
7. QCC internal init 완료 후 정상 21-word 패킷 송신 → 자가 복구

### 3. CM3 측 mitigation 후보 (필요 시)

| Fix | 내용 | 한계 |
|---|---|---|
| F-A | `main.c:361 snd_qcc_set_mode(NORMAL)` 직후 `Sys_Delay(5~20 ms)` — QCC internal wakeup + SPI init 안정화 대기 | 임시 mitigation. QCC 측 wakeup timing 변경 시 또 노출 가능 |
| F-B | `SPI1_COM_IRQHandler` 첫 transfer 에러 silent (자가 복구 동작 정상화) | 진단 가시성 저하 |
| F-C | 코드 변경 0 — 자가 복구 (~931 ms) 수용 | 첫 응답 지연 잔존 |

### 4. 진짜 fix 영역 (QCC 측 — 본 task 외부)

- QCC NORMAL 진입 후 **첫 SPI burst timing** 명확화 (internal wakeup 완료 후 송신 시작)
- ISD_CHECK 게이트 가정 vs 실제 송신 게이트 일치성 검토
- wakeup 후 첫 패킷 길이 보장 (SPI_COMM_PACKET_SIZE = 21)

### 5. 재개 시 시발점

본 노트 + [`이력.md §5`](이력.md) 를 출발점으로 새 작업 폴더 (예: `comms/qcc-spi-wakeup-race/`) 신설. QCC 담당자 답변 후 fix 방향 결정.
