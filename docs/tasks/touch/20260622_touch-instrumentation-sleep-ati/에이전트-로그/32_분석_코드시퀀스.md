# 코드 시퀀스 정밀 분석 — read_debug 영구 FORCE WINDOW OPEN TIMEOUT

> **TL;DR**: read_status의 마지막 wait_window_closed(20ms)가 완료되어도 RDY는 곧바로 다음 측정 주기의 Low로 내려온다. 이 상태에서 read_debug가 force_window_open()을 부르면 RDY가 이미 Low이므로 즉시 true를 반환한다 — 여기까진 맞다. 문제는 그 직후 i2c_write(addr)가 실행되는 사이 IC가 Transaction Timeout(0.4~0.5ms 트랜잭션 또는 200ms 무응답) 또는 다른 내부 상태에 의해 RDY를 High로 올리고(윈도우를 닫고) 45ms 동안 다시 Low를 내리지 않을 때다. 이 상황을 만드는 핵심 원인은 **read_status 자체가 윈도우를 2번 열고 닫는 과정에서 발생시키는 I2C STOP의 연쇄**와 **read_debug의 첫 force_window_open이 직전 read_status STOP 직후의 '과도기 Low'(아직 닫히지 않은 윈도우)를 잡아 i2c_write를 실행하지만 해당 윈도우가 IC 내부에서 즉시 닫혀버리는 타이밍 충돌**에 있다.

## 1. 1 tick 내 RDY/윈도우 상태 전이 단계별 추적

### 1.1 read_status (tdc_touch_iqs323_read_status → read_register(0x10))

`read_register`는 2-윈도우 시퀀스다(tdc_touch_iqs323.c:185~215).

```
[단계 A] force_window_open() — 1번째
  전제: IC는 Report Rate=0 Streaming으로 매 측정 사이클 후 RDY를 Low로 당김.
  200ms 폴링 간격 동안 IC는 수십 회 RDY를 Low↔High 토글하고 있음.
  → GPIO 읽을 때 RDY == Low(WIN_OPEN=0)이면 즉시 true 반환.
    (아니면 force_comm(0xFF) i2c_write 후 Low 45ms 대기 — 정상 구간에선 이미 Low라 즉시 true)

[단계 B] i2c_write(addr=0x10, len=1) — 레지스터 주소 전송
  I2C START → 0x10 → STOP
  STOP 순간 IC는 RDY를 High로 올림(윈도우 닫힘).

[단계 C] wait_window_closed(20ms) — 1번째
  RDY가 High(WIN_CLOSED=1)로 올라올 때까지 최대 20ms 폴링.
  정상: STOP 직후 수백 µs 이내 RDY High 확인 → return true.
  soft timeout 시 return false지만 반환값 미사용 → 무조건 다음 단계 진행.

[단계 D] force_window_open() — 2번째
  IC가 다음 측정 사이클을 끝내면 RDY를 다시 Low로 당김.
  → RDY == Low 확인 → 즉시 true 반환.
  (측정 주기가 실측 미확인이나 ~수 ms 이내 예상 — Report Rate=0 + 1MHz conv freq)

[단계 E] i2c_read(buf, 2) — 2바이트 data read (System Status 0x10)
  I2C START → read 2byte → STOP
  STOP 순간 IC는 RDY를 High로 올림.

[단계 F] wait_window_closed(20ms) — 2번째 ★핵심★
  read_register:214 → wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS)
  → RDY High 확인 또는 20ms soft timeout.
  반환값 미사용. 어떤 결과든 read_register는 true를 반환하고 종료.
```

read_status 종료 후 IC의 RDY 상태:
- **경우 1 (정상)**: [단계 F]에서 RDY High 확인 완료 후 종료. IC는 이미 다음 측정 사이클을 시작. 종료 시점에 RDY는 High(측정 중) 또는 Low(측정 완료, 다음 윈도우 오픈).
- **경우 2 (20ms timeout)**: [단계 F]에서 20ms 대기 중 RDY가 High가 되지 않음. soft timeout으로 return false, 반환값 무시. 이 경우 read_status 종료 시점에 RDY는 **여전히 Low(윈도우 열린 상태)**.

### 1.2 #if 블록 진입 조건 (tdc_touch.c:150~167)

```c
// tdc_touch.c:144
in.read_ok = tdc_touch_iqs323_read_status(&st);

// tdc_touch.c:150~167
#if (TDC_TOUCH_DEBUG_PRINT_ENABLE)
    if (in.read_ok)
    {
        tdc_touch_iqs323_debug_t dbg;
        if (tdc_touch_iqs323_read_debug(&dbg) && dbg.ok)
        { ... }
    }
#endif
```

`in.read_ok == true`여야 read_debug가 호출된다. 로그에서 read_status 실패 로그('READ 0x10 WINDOW OPEN FAIL')가 없으므로 22번째 tick 이후에도 read_status는 계속 true를 반환 중 → read_debug는 매 tick 호출됨.

### 1.3 read_debug (tdc_touch_iqs323.c:343~370)

```
[단계 G] force_window_open() — read_debug 1번째 (tdc_touch_iqs323.c:353)
  read_status [단계 F] 종료 직후 즉시 진입.
  경우 1: RDY가 High → force_comm(0xFF) i2c_write 후 Low 45ms 폴링 → 정상이면 Low 확인.
  경우 2: RDY가 Low → 즉시 true 반환. ★22회 전환 직전까지의 정상 경로★

[단계 H] i2c_write(reg=0x13, len=1) — read_debug 주소 전송
  [단계 G]에서 true를 얻었을 때 실행.

[단계 I] wait_window_closed(20ms)
  tdc_touch_iqs323.c:358

[단계 J] force_window_open() — read_debug 2번째 (tdc_touch_iqs323.c:360)

[단계 K] i2c_read(buf, 4) — 4바이트 data read (0x13+0x14)

[단계 L] wait_window_closed(20ms) — 마지막
  tdc_touch_iqs323.c:365
```

## 2. 왜 read_status는 성공하고 read_debug의 force_window_open은 영구 timeout인가

### 2.1 read_status와 read_debug의 force_window_open 진입 시점 차이

**read_status의 첫 번째 force_window_open (단계 A)**:
- tdc_touch.c의 폴링 주기는 TDC_TOUCH_POLL_INTERVAL_MS(200ms)다.
- 200ms 대기 중 IC는 Report Rate=0 Streaming으로 RDY를 수십 회 Low↔High 토글.
- force_window_open 진입 시점에 RDY가 Low일 가능성이 높음(IC가 고속 토글 중이므로 다음 Low까지 최대 T_주기 ≈ 수 ms 대기 가능, 45ms timeout 내).
- 따라서 정상 구간에서 read_status의 force_window_open은 항상 성공.

**read_debug의 첫 번째 force_window_open (단계 G)**:
- read_status 종료(단계 F) **직후** 진입.
- 단계 F(wait_window_closed 20ms)는 RDY를 High로 확인했거나 timeout.
- **정상 케이스**: 단계 F가 성공(RDY High 확인) → 단계 G 진입 시 RDY High. → force_comm(0xFF) 전송 후 Low 45ms 대기.
  - 이것이 정상 구간(1~21회)에서 동작한 경로: IC가 수 ms 내 다음 측정 완료 → RDY Low → 단계 G 성공.
- **실패 케이스**: 단계 G에서 force_comm(0xFF)을 보냈으나 45ms 내 RDY Low가 오지 않음 → TIMEOUT.

### 2.2 22회째부터 45ms timeout이 되는 핵심 원인 후보

#### 원인 후보_1: IC가 force_comm으로 인한 윈도우 혼란 상태에 빠짐 (가장 유력)

`force_comm(0xFF)`은 IQS323 데이터시트 §8.9에 정의된 "Communication Window Force Open" 바이트다. 이것은 **윈도우가 닫힌 상태에서** IC에게 "지금 윈도우를 열어라"고 요청하는 명령이다.

문제: read_status [단계 E]의 i2c_read STOP 직후, read_status [단계 F]의 wait_window_closed가 실행된다. **이 20ms 대기 동안 IC는 이미 다음 측정 사이클을 돌리고 있고, 다음 RDY Low가 올 수도 있다**.

- [단계 F]가 20ms timeout으로 return false한 경우: 실제 RDY는 여전히 Low인 채다. read_status는 이를 무시하고 true 반환.
- 즉시 read_debug [단계 G] 진입: GPIO 읽으면 RDY == Low → 즉시 true 반환.
- [단계 H] i2c_write(0x13) 실행. STOP 후 RDY High.
- [단계 I] wait_window_closed: RDY High 확인.
- [단계 J] force_window_open: RDY High → force_comm(0xFF) i2c_write.
  
  **여기서**: IC가 연속으로 이미 3번의 STOP을 받은 상태(단계 B, E, H). 각 STOP마다 IC는 윈도우를 닫고 다음 측정 사이클을 시작하려 한다. force_comm이 이 사이클 중간에 도착하면 IC는 해당 사이클을 포기하고 즉시 윈도우를 열어야 한다.
  
  그러나 일부 IQS 계열 IC는 force_comm을 **윈도우가 완전히 닫힌 상태**(RDY High 안정화 후)에서 받아야 정상 처리한다. STOP 직후 RDY 전환 과도기(수백 µs RC 지연)에 force_comm이 도달하면 IC가 명령을 무시하거나 혼란 상태에 빠질 수 있다.

#### 원인 후보_2: read_status [단계 F] soft timeout → RDY가 Low인 채 read_debug 진입 → i2c_write 시점에 IC가 윈도우를 닫음

이 경로를 단계별 추적:

```
[단계 F] wait_window_closed 20ms → timeout(RDY 아직 Low), return false, 무시
  → read_status true 반환, in.read_ok = true
[단계 G] force_window_open 진입: RDY == Low → 즉시 true 반환
[단계 H] i2c_write(0x13, 1) 실행 시작
  → 이 시점에 IC는 이미 다음 측정 완료 또는 진행 중
  → Transaction Timeout(200ms) 안이지만, i2c_write 실행 중 IC가 내부 상태 변화로
     현재 열린 윈도우의 서비스를 종료할 수 있음
  → i2c_write 완료 후 wait_window_closed OK
[단계 J] force_window_open: RDY High → force_comm 전송
  → ★이 force_comm이 IC의 측정 사이클 중간 도착 → RDY Low가 오지 않음 → 45ms timeout★
```

이 경우도 결론은 동일: force_comm이 IC의 비정상 상태에서 처리 불가.

#### 원인 후보_3: 측정 사이클이 ATI 후 변화하여 T_주기가 45ms 초과

데이터시트 §3.4에서 측정 주기의 상한은 채널 수·ATI Target·conv freq에 의존. 부팅 ATI 완료 후 IC가 정상 운용에 진입하면 측정 사이클 시간이 바뀔 수 있다.

그러나 conv freq=0x057F(1MHz, self-cap 최고속)로 설정되어 있고 단일 채널(CH0만)이므로 T_주기가 45ms를 초과할 가능성은 낮다. 또한 21회는 모두 성공했으므로 이것만으로는 설명 불충분.

#### 원인 후보_4: 누적 상태 latch — wait_window_closed 반환값 무시가 IC 상태를 오염

tdc_touch_iqs323.c:181, 200, 213, 358, 365 모두 wait_window_closed의 반환값을 무시한다. 특히 read_debug의 [단계 L] wait_window_closed가 **timeout으로 false를 반환해도 다음 tick의 read_status [단계 A] force_window_open은 이 RDY 상태를 그대로 받는다**.

그러나 이것은 read_status [단계 A]가 RDY Low를 보면 즉시 true 반환하므로 read_status 자체 실패로 이어지지 않는다. 로그 ground truth와 일치: read_status는 계속 성공.

## 3. force_comm(0xFF)을 read_status STOP 직후 즉시 보내는 부작용

### 3.1 시퀀스 재구성 (1 tick 전체)

```
200ms 게이팅 통과
  ↓
read_status:
  [A] force_window_open: RDY Low 확인(즉시 또는 잠시 대기) → true
  [B] i2c_write(0x10, 1byte) → STOP → RDY High
  [C] wait_window_closed(20ms): RDY High 확인
  [D] force_window_open: IC 다음 사이클 후 RDY Low → true
  [E] i2c_read(2byte) → STOP → RDY High
  [F] wait_window_closed(20ms): 반환값 무시 → read_status 종료
  ↓
read_debug (in.read_ok == true인 경우):
  [G] force_window_open
      └─ RDY가 High → force_comm(0xFF) i2c_write 후 45ms 폴링
         ★ 이것이 timeout → 영구 실패의 시작점★
```

### 3.2 연속 force_comm의 IC 부작용

read_status 단계에서 이미 두 번의 정상 I2C 트랜잭션(write addr + read data)이 발생했다. 각각 STOP으로 윈도우가 닫혔다. IC는 이후 자체 측정 사이클을 돌리면서 RDY를 Low로 내린다.

force_comm(0xFF)은 I2C WRITE 1바이트 트랜잭션이다. IC는 이것을 **정상 윈도우에서의 레지스터 write 시도**로 해석할 수 있다. 0xFF는 정의되지 않은 레지스터 주소이므로 IC가 무시하거나 NACKを 반환한다. 그러나 STOP 생성 시점에 IC가 이미 RDY를 High로 올린 상태가 아니라면(= 다음 사이클 도중), IC가 혼란을 겪는다.

**핵심**: IQS323 데이터시트 §8.9는 force_comm을 "End of Window Force Communication"이라 설명하며, **호스트가 윈도우가 닫혔을 것으로 예상할 때 사용**하는 것이다. 윈도우가 이미 열려 있는 상태에서 force_comm을 보내는 것은 비정상이다.

- read_debug [단계 G]: RDY Low(윈도우 열림) → force_window_open이 즉시 true 반환 → force_comm 미실행(정상 경로). 이 경우는 문제없음.
- read_debug [단계 G]: RDY High(윈도우 닫힘) → force_comm 실행. **이것이 read_status [단계 F] wait_window_closed 성공 후의 정상 경로**. 이때 force_comm이 IC에게 다음 사이클을 중단하고 즉시 윈도우를 열라고 요청한다. **IC가 이 요청에 응답하지 않으면(측정 진행 중, 또는 혼란 상태) 45ms timeout 발생**.

### 3.3 wait_window_closed 반환값 미사용의 구체적 영향

```c
// tdc_touch_iqs323.c:181, 200, 213, 358, 365
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);   // 반환값 void처럼 버림
```

이 패턴이 문제가 되는 시나리오:

```
[단계 F] wait_window_closed 20ms timeout → RDY 여전히 Low
  → read_status는 무조건 true 반환 (wait_window_closed 실패 체크 없음)
  → in.read_ok = true
  → read_debug 호출
[단계 G] force_window_open: RDY Low → 즉시 true (STOP 전 이미 열린 윈도우)
[단계 H] i2c_write(0x13): 이 write가 "read_status가 끝내지 못한 윈도우"에서 실행됨
  → IC 입장: 아직 System Status(0x10) read에 대한 윈도우인데 0x13 write가 들어옴
  → IC 혼란: 프로토콜 오염
[단계 I] wait_window_closed: 어떻게 되든 진행
[단계 J] force_window_open: force_comm
  → IC가 프로토콜 오염 후 정상 동작 불가 → RDY Low를 내리지 않음 → 45ms timeout
```

이 시나리오에서 **read_status 자체는 프로토콜 오염 전에 완료되므로 로그 없음**, **read_debug의 [단계 J] force_window_open에서 timeout 발생** — 로그 패턴과 정확히 일치한다.

## 4. 영구화 메커니즘 — read_debug 실패 후 누적 영향

### 4.1 실패 경로 코드 추적

```c
// tdc_touch_iqs323.c:353~356
if (!force_window_open() || !i2c_write(&reg, 1))
{
    ci_printw("[TOUCH] DEBUG READ FAIL (addr) \r\n");
    return false;   // ← 여기서 즉시 반환
}
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);   // ← 건너뜀
```

force_window_open timeout → i2c_write 실행 안 됨 → `return false`.

**건너뛰어지는 것**: wait_window_closed([단계 I])와 이후 모든 단계([J][K][L]).

### 4.2 IC 상태 분석 — return false 직후

force_window_open이 45ms timeout으로 실패했다는 것은:
- force_comm(0xFF)이 IC로 전송됨 (i2c_write 성공, tdc_touch_iqs323.c:143).
- 45ms 동안 RDY Low가 오지 않음 → IC가 force_comm에 응답하지 않은 상태.
- IC 내부 상태: **알 수 없음**. 정상 측정 사이클 계속? 또는 내부 오류?

**RDY 상태**: 45ms timeout 경과 시점에 RDY는 High(IC가 응답 안 하고 있음) 또는 Low(IC가 뒤늦게 Low를 내렸으나 이미 timeout). 실제로는 timeout이 발동했으므로 RDY == High.

### 4.3 다음 tick에 미치는 영향

다음 tick에서 tdc_touch.c 폴링 게이팅 통과 후:

```
read_status:
  [A] force_window_open 진입: RDY High → force_comm(0xFF) i2c_write 후 45ms 폴링
```

만약 IC가 **이전 tick의 force_comm으로 인해 혼란 상태**에 있지 않다면:
- IC는 자체 측정 사이클을 계속하고 있음 → 다음 사이클 완료 시 RDY Low → read_status [단계 A] 성공.

만약 IC가 혼란 상태라면:
- read_status도 실패할 것 → 그러나 로그에 'READ 0x10 WINDOW OPEN FAIL' 없음.

**결론**: IC는 read_debug 실패 후에도 자체 측정 사이클을 정상적으로 계속하고 있다. read_status는 이 사이클의 RDY Low를 잡아서 성공한다. read_debug의 force_window_open이 매번 45ms timeout이 되는 이유는 **read_status 내부 시퀀스가 완료된 직후(단계 F 직후) IC가 특정 상태에 있어서 force_comm에 응답하지 않기 때문**이다.

### 4.4 영구화의 결정적 메커니즘

**영구화 조건**: 매 tick마다 다음 패턴이 반복:

```
tick N:
  read_status: [A→F] 성공 (4번의 force_window_open 내지 자연 Low 획득)
  read_debug [G]: RDY High(단계 F 성공 후) → force_comm → 45ms timeout → return false
  wait_window_closed 건너뜀 → IC 상태 미동기화

tick N+1:
  (200ms 게이팅 통과)
  read_status [A]: force_window_open
    → IC는 정상 측정 계속 → RDY Low → 성공 (IC가 정상이므로)
  read_status [B~F]: 성공
  read_debug [G]: 또 RDY High → force_comm → 45ms timeout
  ...영구 반복
```

**영구화의 핵심**: read_status [단계 F] wait_window_closed가 성공적으로 RDY High를 확인하고 종료하면, read_debug [단계 G]에서 반드시 RDY High 상태로 진입한다. 여기서 force_comm을 보내는데, **이 force_comm이 IC에서 45ms 내 응답을 받지 못하는 것이 매 tick 반복**된다. IC 자체는 정상이고(read_status 성공), 측정 사이클을 돌리고 있지만, **read_status [단계 F] 완료 → read_debug [단계 G] force_comm 도달 사이의 극히 짧은 시간** 동안 IC가 다음 RDY Low를 내리지 않고 있다.

**더 정확한 설명**: read_status 마지막 i2c_read STOP(단계 E) 후 wait_window_closed(단계 F)가 RDY High를 확인한다. 이 시점 IC는 이제 **새 측정 사이클을 시작하는 초기**다. IC가 새 사이클을 완료하기까지(T_주기) 시간이 걸린다. force_comm은 "측정 사이클 도중 강제 중단 + 윈도우 열기"다. T_주기 > 45ms라면 force_comm이 새 사이클 도중에 전송되고, IC가 사이클 완료 전에 force_comm에 응답하지 않으면 timeout이 된다.

그러나 conv freq=1MHz + 단일 채널로 T_주기 < 45ms가 기대된다. 따라서 T_주기 문제만으로는 설명 불충분. **추가 원인**: 연속 force_comm으로 인한 IC 내부 상태 혼란(윈도우 프로토콜 오염, §3.2 설명)이 IC로 하여금 force_comm에 대한 RDY Low 응답 자체를 차단하게 만들었을 가능성.

## 5. '21회 정상 후 영구 실패' 전환을 코드로 설명

### 5.1 부팅 ATI 완료 직후 상태 변화

`tdc_touch_iqs323_apply_settings()` 내부에서:
1. `write_register(REG_SYSTEM_CONTROL, 0x54, 0x07)` — Re-ATI 트리거 (tdc_touch_iqs323.c:398)
2. `wait_ati_done_blocking()` — ATI 완료 대기 (tdc_touch_iqs323.c:402)
3. `write_register(REG_SYSTEM_CONTROL, 0x58, 0x07)` — RESEED (tdc_touch_iqs323.c:404)

ATI 완료 직후 IC는 정상 측정 사이클로 진입한다. **ATI 중 IC의 RDY 패턴은 일반 측정과 다를 수 있다** — ATI 중에는 RDY 토글 주기가 불규칙하거나, ATI 완료 보고를 위해 특별 윈도우를 열 수 있다.

### 5.2 21회 정상의 물리적 설명

폴링 주기 200ms. 21회 = 약 4.2초 후 전환.

부팅 ATI 완료(`wait_ati_done_blocking` 25회 × 50ms = 최대 1.25s) 후 IC가 정상 Streaming NP 모드로 안정화되는 데 수 사이클이 걸릴 수 있다. **이 과도기 동안**:
- IC의 T_주기가 짧거나 불규칙.
- force_comm에 대해 빠르게 응답.
- read_debug [단계 G]에서 force_comm이 성공.

**안정화 후**(21회 이후):
- IC가 완전 Streaming NP 정상 모드로 진입.
- 측정 사이클이 안정적이고 규칙적.
- read_status [단계 F] 완료 시점이 IC 사이클의 특정 phase와 일관되게 맞물림.
- 이 phase에서 force_comm을 보내면 IC가 45ms 내에 응답하지 않는 조건이 성립.

### 5.3 대안 설명: 21회째 tick의 타이밍 우연 + 이후 IC 상태 latch

21회째까지는 read_status [단계 F] wait_window_closed가 **20ms timeout**으로 끝나는 경우가 없었거나, 끝났어도 read_debug [단계 G]에서 RDY가 Low여서 force_comm 없이 성공했다. 

22회째에 처음으로 read_status [단계 F]가 RDY High를 확인하고 종료 → read_debug [단계 G]에서 RDY High 만남 → force_comm 전송 → IC가 응답하지 않음(45ms timeout) → IC가 이 상태 이후 force_comm에 대한 응답 능력을 상실(상태 latch).

## 6. 종합 결론

### 6.1 root cause 계층

| 계층 | 내용 |
|---|---|
| 직접 원인 | read_debug [단계 G] force_window_open: force_comm(0xFF)에 IC가 45ms 내 응답하지 않음 |
| 구조적 원인 | read_status [단계 F] wait_window_closed 성공 후 RDY High 상태에서 즉시 read_debug가 force_comm을 보내는 설계 — IC가 새 측정 사이클 초기 상태에서 force_comm을 받아 처리 불가 |
| 누적 원인 | wait_window_closed 반환값 전부 미사용 → IC 상태 비동기화 → 프로토콜 오염 가능성 |
| 영구화 원인 | 실패 후 wait_window_closed 건너뜀(early return) → 다음 tick read_status는 성공하지만 read_debug는 동일 조건 반복 → 탈출 불가 |

### 6.2 은수님 모델 검증

> "conversion이 1MHz 수준으로 빠르므로 STOP 직후 다음 conversion이 끝나 RDY가 곧 다시 Low로 내려가야 한다. 그런데 왜 45ms 영구 timeout인가?"

**부분 타당, 부분 불충분**:
- 1MHz conv freq + 단일채널 → T_주기 < 45ms는 합리적 기대. T_주기 자체가 45ms를 넘어서 timeout이 발생한다는 설명은 맞지 않을 가능성이 높다.
- **놓친 것**: force_comm은 "윈도우가 닫힌 상태에서 IC에게 열라고 요청"하는 것인데, IC가 이 요청을 **무시하거나 처리 불가한 상태**에 빠질 수 있다. 특히 read_status가 2번의 STOP으로 두 번의 윈도우를 닫고 종료한 직후 — IC가 새 사이클 초기(RDY High → 측정 중)일 때 force_comm이 도착하면, IC가 "현재 측정 중이라 윈도우를 열 수 없음"으로 판단하고 사이클 완료 후 자연적으로 RDY Low를 내릴 때까지 force_comm 응답을 보류하는 것으로 보인다. T_주기가 45ms를 넘지 않더라도, IC 내부 상태가 force_comm 처리를 45ms 이상 지연시키는 시나리오가 있다.
- **결정적 차이**: "STOP 직후 다음 conversion이 끝나 RDY Low가 온다"는 맞다. 그러나 이 자연적 RDY Low는 force_window_open이 감지하는 시점에 이미 force_comm의 응답을 기다리는 중이다. force_comm이 전송된 후 IC가 **자연적 RDY Low를 억제하고 force_comm 응답을 준비하는 동안** 45ms가 지나버리는 것이다. 또는 IC가 이미 오염된 프로토콜 상태에서 어떤 STOP도 정상 윈도우 닫힘으로 인식하지 못하는 상태에 빠진 것.

### 6.3 fix 방향

1. **read_debug 제거 또는 read_status와 분리**: 폴링당 read_status → 별도 낮은 빈도 read_debug(매 N tick마다).
2. **read_debug 전 명시적 대기**: read_status 완료 후 IC 다음 사이클 완료를 보장하는 대기(T_주기 상한). 단, T_주기 미확인이 문제.
3. **force_window_open 대신 자연 RDY 폴링**: force_comm 없이 RDY Low를 기다리는 것만으로 read_debug의 첫 번째 윈도우를 얻는 방식. 이미 [단계 G]에서 RDY가 Low면 즉시 true 반환하므로, 단순히 RDY Low까지 폴링(force_comm 없이)으로 변경하면 IC 혼란 없이 다음 자연 윈도우를 기다릴 수 있다.
4. **wait_window_closed 반환값 체크**: 실패 시 상태를 로그하거나 재시도 로직 추가.
