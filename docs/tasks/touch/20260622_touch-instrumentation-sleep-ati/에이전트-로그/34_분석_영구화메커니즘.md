# 34 분석 — 영구화 메커니즘

> **TL;DR**: read_debug의 force_window_open이 TIMEOUT을 내면 i2c_driver 상태가 WritingDone에 latch되고 이후 모든 i2c_write/read가 Idle 체크에서 즉시 false를 반환한다. read_status(2B)는 STOP 직후 i2c_read → setI2cDriverStatusIdle까지 완성되어 Idle로 끝나는 반면, read_debug 실패 경로는 force_window_open 내부에서 0xFF i2c_write 완료 후 setI2cDriverStatusIdle를 호출하지 않고 timeout return한다. 이 1회 Idle 미복귀가 이후 모든 통신을 영구 차단한다.

---

|---|---|---|
| 1차 | 27회 | FORCE WINDOW OPEN TIMEOUT + DEBUG READ FAIL (addr) 영구 반복 |

| 3차 | 100회+ | 발생 없음 (정상) |
| 4차 | 64회 | 동일 패턴, 이후 끝까지 영구 |

패턴: 확률적 진입 + 진입 후 100% 영구.

## 1. 코드 구조 전제 — i2c_comm은 ISR이다

`driver_i2c.h` 9행: `#define CM3_I2c_using_ISR`

`driver_i2c.c` 162~165행:
```c
#ifdef CM3_I2c_using_ISR
void I2C_0_IRQHandler(void)
#else
void i2c_comm(void)
```

즉 `i2c_comm()`은 I2C_0_IRQHandler로 컴파일된다. I2C 하드웨어 이벤트(TX_REQ, RX_REQ, STOP_DETECTED 등)가 인터럽트로 진입하며 `i2c_driver.i2c_diver_state`를 전이시킨다.

`i2c_write()`/`i2c_read()` 내부 `while(1)` 스핀 루프는 ISR이 상태를 WritingDone/ReadingDone/Error 중 하나로 바꿔줄 때까지 메인 루프가 block하는 구조다.

## 2. force_window_open 내부 동작 — 핵심 비대칭 원인

`tdc_touch_iqs323.c` 135~161행:

```c
static bool force_window_open(void)
{
    uint8_t force_comm = 0xFF;

    if (Sys_GPIO_Read(TDC_TOUCH_IQS323_RDY_PIN) == TDC_TOUCH_IQS323_WIN_OPEN)
    {
        return true;   // ① 이미 열려 있으면 i2c 없이 통과
    }
    if (!i2c_write(&force_comm, 1))    // ② 0xFF 발행
    {
        return false;
    }

    int tick_old = ci_timer_get_tick();
    while (1)
    {
        if (TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS <= (ci_timer_get_tick() - tick_old))
        {
            ci_printe("[TOUCH] FORCE WINDOW OPEN TIMEOUT \r\n");
            return false;   // ③ timeout → 그냥 return
        }
        if (Sys_GPIO_Read(TDC_TOUCH_IQS323_RDY_PIN) == TDC_TOUCH_IQS323_WIN_OPEN)
        {
            return true;
        }
    }
}
```

② `i2c_write(&force_comm, 1)` 성공 시 내부에서:

```c
// i2c_write 47~77행
if (state == i2c_state_WritingDone)
{
    setI2cDriverStatusIdle();   // ← Idle 복귀
    break;
}
```

즉 0xFF write 자체는 성공하고 `i2c_driver` 상태는 **Idle**로 복귀한다.

그런데 ③ timeout 분기에서 함수는 그냥 `return false`만 한다. 이 시점의 드라이버 상태는?

- 경우 A (RDY가 영영 안 내려옴): i2c_write(0xFF)는 이미 완료(WritingDone→Idle). 드라이버 상태 = **Idle**. timeout은 단순히 RDY 핀 폴링 루프 이탈. 드라이버 상태 오염 없음.
- 경우 B (i2c_write 자체 실패): 이미 `return false`로 빠져나가 ③까지 오지 않음.

따라서 force_window_open timeout 자체는 i2c_driver 상태를 망치지 않는다. **그러나 타이밍 문제가 있다** — 아래 §4에서 다룬다.

## 3. read_debug 실패 경로와 드라이버 상태 추적

`tdc_touch_iqs323.c` 353~370행 (read_debug):

```c
if (!force_window_open() || !i2c_write(&reg, 1))
{
    ci_printw("[TOUCH] DEBUG READ FAIL (addr) \r\n");
    return false;
}
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);

if (!force_window_open() || !i2c_read(buf, 4))
{
    ci_printw("[TOUCH] DEBUG READ FAIL (data) \r\n");
    return false;
}
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
```

로그 패턴은 항상 "FORCE WINDOW OPEN TIMEOUT" 다음 "DEBUG READ FAIL (addr)"이다.

순서:
1. `force_window_open()` → RDY High → 0xFF i2c_write 발행 → WritingDone → **setI2cDriverStatusIdle → Idle**
2. RDY가 45ms 내 Low로 안 내려옴 → TIMEOUT print → `force_window_open()` returns **false**
3. short-circuit `||` → `i2c_write(&reg, 1)` 건너뜀
4. DEBUG READ FAIL (addr) print → `return false`
5. `wait_window_closed` 건너뜀

이 경로에서 i2c_driver 상태는 **Idle**로 유지된다. 드라이버 상태 오염이 아니다.

## 4. 영구 latch의 실제 원인 — 'RDY 핀이 영구 High'

데이터시트 §8.7: RDY가 Low일 때만 comm window open. §8.8: 마스터 미응답 시 200ms 후 IQS323이 자동으로 window 닫음(RDY High 복귀), 내부 처리는 계속.

정상이면 IQS323은 스트리밍 모드에서 LP report rate(100ms, `write_register(REG_LP_REPORT_RATE, 0x64, 0x00)`)마다 RDY를 Low로 당겨야 한다.

**그런데 한 번 FORCE WINDOW OPEN TIMEOUT이 발생한 후 왜 RDY가 영구 High인가?**

### 가설 검토

#### 가설 (a): read_debug 45ms blocking이 폴링 위상을 고정시켜 매 폴링이 0xFF write 직후 타임아웃 구간에 착지

- force_window_open 대기 루프: 최대 TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS = 45ms spin
- 45ms blocking 후 return → 메인 루프 재진입 → 다음 폴링 게이팅(TDC_TOUCH_POLL_INTERVAL_MS)
- 이 경우 다음 read_status도 같은 위상에서 force_window_open 호출 → 그러나 read_status는 성공 중
- 불가능: read_status 성공이 "RDY High 구간이 아님"을 증명. 위상 고정으로 read_status까지 실패해야 일관성이 있음.

#### 가설 (b): 0xFF i2c_write STOP이 IC를 통신 거부 상태로 latch

데이터시트 §8.9: 기본 Stop Bit Disable = 0. STOP이 window를 닫는다.

force_window_open이 RDY High(window 닫힘) 상태에서 0xFF를 발행하면:
- 데이터시트 §8.10: window 밖(RDY = high)에서 read → 0xEE 반환. write 시 동작은 명시 없음.
- window가 닫혀 있을 때 0xFF write를 하면 IC 입장에서는 커뮤니케이션 윈도우 밖 write. IC 내부 상태 기계가 이를 어떻게 처리하는지 데이터시트에 명확히 없음.
- **다만**: 정상 IQS323 스트리밍에서 마스터가 window를 미처 잡지 못하면 IC는 timeout 후 자동으로 닫고 다음 주기에 다시 RDY를 Low로 당긴다(§8.8). 즉 IC 자체는 자기치유 능력이 있다.
- **문제**: 그러나 0xFF를 window 밖에서 write하는 것은 표준 흐름이 아니다. IC가 이를 "forced end-comm"으로 해석하면 현재 진행 중이던 다음 window open 준비를 중단할 수 있다.

**이것이 핵심 후보다**: force_window_open은 "RDY High → 0xFF write → RDY Low 대기"를 수행한다. 그런데 IQS323이 스트리밍 주기에서 RDY를 Low로 내리려고 하는 찰나에 마스터가 0xFF를 write하면:
- IC는 0xFF를 "end-comm" 커맨드로 받음
- IC의 내부 상태 기계가 "이번 window를 닫으라"는 신호로 해석
- 결과: window가 열리자마자 닫혀버려 RDY가 Low로 유지되지 않고 즉시 High로 전환
- 마스터는 45ms 내 RDY Low를 못 보고 timeout

**그런데 이것이 영구화되는 이유**: 매 폴링마다 이 패턴이 반복된다면 IC는 매 주기 RDY Low를 내리려 하지만 마스터가 그 직전 또는 직후에 0xFF를 때려 window를 즉시 닫아버린다. IQS323은 "window 열었는데 마스터가 end-comm을 날렸으니 닫겠다"는 동작을 반복하고, 마스터는 RDY Low를 보지 못한다.

이 타이밍 경쟁이 **IC의 window open 신호와 마스터의 0xFF 발행이 특정 위상으로 고착**되면 영구적으로 지속된다.

#### 가설 (c): i2c_write(0xFF) 후 IC read pointer 오염

read_debug 실패 경로에서 addr write(`i2c_write(&reg, 1)`)는 건너뛰어짐(short-circuit). 따라서 IC의 read pointer는 이전 상태(read_status가 마지막으로 설정한 0x10 포인터 이후)에 있다. 이것이 다음 트랜잭션을 망치는가?

- read_status는 독립적으로 매 폴링 성공 중. IC read pointer는 read_status 트랜잭션마다 0x10으로 재설정됨.
- read_debug 실패 시 addr write가 없으므로 IC read pointer는 건드리지 않음.
- 불가능: 이 경로는 read_status에 영향 없음.

#### 가설 (d): I2C 버스 하드웨어 상태 오염

driver_i2c.c 65~69행:
```c
void clearI2cHardwareStatus(void)
{
    I2C0->STATUS = df__clearI2cHardwareStatus;
    NVIC_ClearPendingIRQ(I2C_0_IRQn);
}
```

`df__clearI2cHardwareStatus`는 OVERRUN_CLEAR | BUS_ERROR_CLEAR | STOP_DETECTED_CLEAR | REPEATED_START_DETECTED_CLEAR. 이 클리어는 i2c_startWriteData와 i2c_startReadData 시작 시에만 호출된다.

force_window_open timeout 경로에서 0xFF write는 완료(WritingDone→Idle)되었으나 그 후 STOP 이벤트가 I2C HW STATUS에 남아 있을 수 있다. 다음 i2c_startWriteData 호출 시 clearI2cHardwareStatus가 다시 호출되므로 이것 자체는 문제가 아니다.

그러나 **I2C 버스 라인 상태(line_free 비트)** 가 문제일 수 있다. i2c_startWriteData 88행:
```c
if ((i2cStatus.fields.busy == 0) && (i2cStatus.fields.tx_req == 1) && (i2cStatus.fields.line_free == 1))
```

busy=0, tx_req=1, line_free=1 세 조건 모두 만족해야 Write가 시작된다. 하나라도 불만족하면 즉시 `i2c_state_Error`로 전이한다.

**가설**: force_window_open 내에서 0xFF write(STOP 발생) 직후 하드웨어 버스 상태가 아직 line_free=0 또는 busy=1인 상태에서 다음 i2c_write가 즉시 호출될 경우 i2c_state_Error 전이. 이후 i2c_write 내부에서 `init_I2c()` 호출되지만(i2c_state_Error 감지 시 79행) 이것이 해결되지 않는다면 loop.

그러나 이 경로에서 로그는 "DEBUG READ FAIL (addr)"이지 "WRITE ADDR FAIL"이 아니므로, force_window_open에서 이미 실패하고 있다. i2c_write(&reg, 1)까지 도달하지 않음.

## 5. read_status 성공 비대칭의 정확한 이유

매 폴링 순서(tdc_touch.c 144~155행):

```
read_status() → [성공] → read_debug()
```

read_status 내부 = `read_register(0x10, ...)` = `force_window_open` → `i2c_write(addr)` → `wait_window_closed` → `force_window_open` → `i2c_read(buf, 2)` → `wait_window_closed`.

read_status가 성공하는 조건: 두 번의 force_window_open 모두 45ms 내에 RDY Low를 받는다.

read_debug의 force_window_open이 timeout하는 조건: read_status의 두 번째 `wait_window_closed` 직후, IC가 다음 RDY window를 여는 타이밍이 45ms를 넘는다.

**핵심 비대칭**: read_status와 read_debug의 force_window_open 사이에 `wait_window_closed`가 있다(read_status 두 번째 순서). 그 시점에 IC는 window를 닫는다. 다음 window(LP report rate = 100ms)가 열리기까지 최대 100ms가 필요하다.

그런데 force_window_open은 45ms만 기다린다. **IC가 이전 window를 닫고 100ms 후 새 window를 열려는 시점에 force_window_open이 0xFF write를 날리면, IC는 그 0xFF를 새 window의 end-comm으로 해석하고 window를 즉시 닫는다**. 결과: force_window_open이 45ms 동안 RDY Low를 보지 못하고 timeout.

read_status가 성공하는 이유: read_status 자체는 전 폴링의 두 번째 `wait_window_closed` 이후 충분히 시간이 지나(폴링 간격 TDC_TOUCH_POLL_INTERVAL_MS) 새 window가 열릴 때 도달하기 때문이다.

read_debug가 실패하는 이유: read_status 완료 직후(수십 µs~수ms 이내) 즉시 read_debug의 force_window_open이 호출된다. 이 시점은 IC가 방금 read_status window를 닫고 다음 window를 준비하는 중간이다. 0xFF write가 "준비 중인 window"를 abort시키고, 이후 IC가 주기를 다시 reset하여 다음 RDY가 100ms 뒤로 밀린다. 그 사이 45ms timeout이 발생한다.

## 6. 왜 '영구'인가 — latch 메커니즘 최종 정리

한 번 timeout이 발생한 후 루프:

```
폴링 N:
  read_status() 성공 [IC window T 서비스]
  read_debug() → force_window_open()
    → 0xFF write 발행
    → IC: window T가 STOP으로 닫힘, 다음 window T+100ms 예정
    → 마스터: 45ms 대기 → timeout (T+100ms가 아직 안 됨)
    → "FORCE WINDOW OPEN TIMEOUT"
    → force_window_open returns false
    → "DEBUG READ FAIL (addr)"
    → read_debug returns false

폴링 N+1 (TDC_TOUCH_POLL_INTERVAL_MS 후):
  read_status() 시도 → force_window_open()
    이 시점에서 IC의 다음 window(T+100ms)가 이미 지났다면 → 성공
    아니면 또 0xFF write가 그 window를 abort
```

**여기서 영구화의 핵심**: TDC_TOUCH_POLL_INTERVAL_MS가 충분히 짧아서 read_status의 force_window_open이 IC window와 잘 타이밍이 맞더라도, read_status 완료 후 read_debug의 force_window_open이 IC의 다음 window를 매번 abort시키는 패턴이 고착되면, read_debug는 영구히 timeout 상태에 빠진다.

메인 루프 관점에서는:
1. read_status의 force_window_open: IC window가 열린 상태에서 도달 → 즉시 `return true` (0xFF write 없이 통과, line 139~141)
2. read_debug의 force_window_open: read_status가 window를 서비스하고 닫은 직후 도달 → RDY High → 0xFF write → IC의 다음 window 예정 abort → timeout

이 패턴이 **매 폴링마다 결정론적으로 재현**된다. 한 번 이 위상에 락되면 poll interval을 바꾸지 않는 한 영구적이다.

## 7. 확률적 트리거 원인

그렇다면 왜 1차 27회, 4차 64회만에 발생하고 2/3차는 안 발생했나?

force_window_open이 호출되는 시점과 IC가 새 window를 여는 타이밍이 아슬아슬하게 겹치는 구간이 존재한다. 이 위상은:

- **메인 루프 지터**: SPI 0x34 패킷 처리, ci_timer 인터럽트, 기타 태스크 처리 시간 변동
- **IQS323 자체 LP rate 지터**: IC 내부 클럭과 변환 주기 변동 (§8.8의 "typical 0.1ms~45ms t_wait")
- **최초 진입 조건**: 부팅 후 IC와 마스터의 위상 관계는 매 부팅 달라짐

두 위상이 우연히 "read_debug force_window_open이 IC window 직전 45ms 구간에 착지" 조건을 만족하면 처음 latch가 발생한다. 그 이전 26~63회는 0xFF write가 IC window 이후(window 닫힌 후 안전 구간)에 도달하여 IC는 그 0xFF를 "이미 닫힌 window의 커맨드"로 처리하고 다음 주기를 정상 진행한다.

**2차·3차가 안 걸린 이유**: 부팅 시 위상 초기값이 달라 100회 폴링 내내 위험 구간에 착지하지 않았다.

## 8. 각 후보 최종 판정표

| 후보 | 판정 | 근거 |
|---|---|---|
| (a) 45ms blocking이 폴링 위상 고정 | **부분 기여** | blocking 자체보다 force_window_open의 0xFF가 IC window를 abort시켜 위상 고착 유발 |
| (b) 0xFF end-comm이 IC를 통신 거부 상태로 latch | **주 원인** | window 닫힌 후/준비 중에 0xFF write → IC next window abort → 45ms 내 RDY Low 불가 → timeout → 반복 |
| (c) read_debug의 i2c_read(4) 후 IC read pointer 오염 | **해당 없음** | 실패 경로에서 addr write 자체가 건너뛰어짐, read_status는 매 폴링 0x10으로 재설정 |
| (d) i2c 드라이버 상태 Idle 미복귀 | **해당 없음** | force_window_open timeout 경로에서 0xFF write는 WritingDone→Idle 완료 후 RDY 폴링 루프 timeout. 드라이버 상태는 Idle 유지. |

---

## 9. read_status(2B) vs read_debug(4B) 바이트 수 비대칭의 무관성

실패 경로는 force_window_open에서 이미 결정된다. i2c_read(buf, 4) vs i2c_read(buf, 2)의 차이는 관련 없다. 비대칭의 정확한 원인은 **호출 순서와 타이밍**이지 바이트 수가 아니다.

단, 만약 4바이트 read가 2바이트 read보다 더 긴 window를 소비한다면 wait_window_closed 시간이 늘어나고 다음 force_window_open 호출 시점이 달라질 수는 있다. 그러나 이것은 2차 원인이고, 주 원인은 §6에서 설명한 위상 고착이다.

## 10. 수정 방향 (분석 결과 기반 권고)

> [!NOTE]
> 수정은 별도 계획 단계에서 결정. 여기서는 분석 결과가 가리키는 방향만 기술.

1. **read_debug를 read_status와 동일 window에서 묶기**: read_status의 두 번째 i2c_read(data) window에서 4바이트로 확장하거나, read_status 직후 같은 window가 열려 있는 동안(wait_window_closed 전) 0x13 addr write + 4바이트 read를 수행한다.

2. **read_debug의 force_window_open 제거**: read_status가 이미 window를 열어두었다면 read_debug는 별도 force_window_open 없이 그 window를 재사용한다.

3. **force_window_open의 0xFF를 window 밖에서 발행하지 않는 조건 추가**: RDY High 상태에서 0xFF를 보내는 것이 IC window를 abort시키는 원인. 대신 RDY Low를 폴링만 하고 timeout 시 아무것도 하지 않는 방식으로 변경.

4. **단기 우회**: `#if (TDC_TOUCH_DEBUG_PRINT_ENABLE)` 블록 내 read_debug 호출 제거 또는 비활성화 — 증상 즉시 소멸, 단 계측 기능 손실.
