# 에이전트 31 — IQS323 데이터시트 타이밍 정밀 분석

> **TL;DR**: 은수님 모델("1MHz conversion이면 STOP 직후 다음 RDY가 45ms 안에 온다")은 **절반만 맞다**. 측정 사이클 소요가 10ms 이하이므로 STOP 후 다음 RDY Low는 45ms 내에 올 수 있다. 그러나 `read_debug`가 영구 실패하는 진짜 원인은 다른 곳에 있다: **read_status STOP → read_debug force_comm(0xFF) 발행 순서가 Streaming 모드에서 0xFF를 "end-communications command"로 오인시키거나, STOP 직후 IC가 다음 conversion 사이클 도중(RDY Low 유지)인 상태를 force_window_open이 WIN_OPEN으로 오판해 0xFF를 I2C 주소 위상에서 전송, IC를 불확정 상태로 진입시킨다.** 이것이 한 번 꼬이면 영구화되는 메커니즘이다.

---

## 0. 분석 입력 요약

- **실기 로그 ground truth**: 21회 정상 → 22회째부터 영구 `FORCE WINDOW OPEN TIMEOUT` + `DEBUG READ FAIL (addr)`.  
  `read_status(0x10)` 실패 로그(`READ 0x10 WINDOW OPEN FAIL`) 전혀 없음 → read_status 경로 force_window_open은 계속 성공.  
  read_debug 경로 force_window_open만 45ms 영구 timeout.

- **설정값**: Streaming 모드, Normal Power, Report Rate 0ms, Transaction Timeout 200ms, Conversion Frequency 0x057F (Period=5 → 1MHz), self-cap 단일채널 CH0 only, ATI Full Mode.

- **코드 경로** (tdc_touch.c:154→tdc_touch_iqs323.c):
  1. `read_status(0x10)` → `[force_window_open → i2c_write(addr) → wait_window_closed → force_window_open → i2c_read → wait_window_closed]`
  2. (직후 `#if TDC_TOUCH_DEBUG_PRINT_ENABLE`) `read_debug(0x13)` → 동일 2-윈도우 시퀀스

## 1. 1 측정(conversion) 사이클 실제 소요 시간 추정

### 1.1 데이터시트 § 6.5 — Conversion Frequency Period=5 → 1MHz

데이터시트 §6.5 Table A.1/A.2 (Dead Time ON, self-cap):

> **`Conversion Frequency Period = 5` → f_xfer ≈ 1.00 MHz** (자기용량 최대 권장, 데이터시트 §6.5 NOTE 표)

이 의미는 **charge-transfer 한 사이클의 클럭**이 1MHz, 즉 1µs/사이클이다.

### 1.2 charge-transfer 횟수 × 사이클 → conversion 시간

ATI Target = ATI Base × (ATI Resolution Factor / 16). 코드 REG_SENSOR0_ATI_SETUP = 0x040C:
- `0x040C` MSB=0x04, LSB=0x0C → Full Mode(bits[1:0]=00), ATI Base 영역 비트 구조는 데이터시트 §5.9 기준.
- 로그에서 LTA=402, CNT~400~402 → ATI Target ≈ 402 counts.

ATI Target이 402이면 noTouch 상태에서 한 번의 conversion에서 **약 402번의 charge-transfer 사이클**이 수행된다(Counts ∝ 사이클 수, §5.4).

```
1 conversion 순수 charge-transfer 시간:
  402 사이클 × 1µs/사이클 = ~402µs ≈ 0.4ms
```

### 1.3 Dead Time 오버헤드 및 housekeeping

데이터시트 §6.4에 따르면 Dead Time은 self-cap에서 **enable** 필수. Dead time은 charge→transfer 전환 시 삽입되는 짧은 휴지 구간이다. 각 사이클에 수십~수백ns 추가된다.

CH1, CH2는 `disable` 설정(REG_SENSOR1_SETUP=0x00, REG_SENSOR2_SETUP=0x00)이므로 단일 채널 처리만 있다.

Housekeeping(필터 연산·LTA 갱신·threshold 비교·RDY 어설션 준비): 수십µs 수준.

### 1.4 1 측정 사이클 실제 소요 추정

```
1 conversion = charge-transfer(~0.4ms) + dead time 오버헤드(수십~100µs) + housekeeping(수십µs)
             = 대략 0.5ms ~ 2ms 범위 (단일채널, ATI Target~400, f_xfer=1MHz)
```

> [!NOTE]
> 데이터시트 §3.4(전류 특성표) 예시: "self-cap 3채널 NP 16ms" → **3채널** 기준이고, ATI Target=512, f_xfer=500kHz 조건이다. Sound1은 단일채널 + f_xfer=1MHz로 이보다 훨씬 빠르다.
>
> Streaming + Report Rate=0이면 IC는 conversion 완료 즉시 RDY Low를 내린다. 즉 **RDY 주기 ≈ 1 conversion 시간 ≈ 0.5~2ms 수준**.

### 1.5 은수님 모델 Part 1 검토

> "conversion이 1MHz 수준으로 빠르므로 STOP으로 윈도우가 닫혀도 타임아웃(45ms) 전에 다음 conversion이 끝나 RDY가 다시 Low로 내려가야 한다."

**데이터시트 근거상 맞다.** 1 conversion이 ~0.5~2ms이면, STOP 직후 최대 2ms 이내에 다음 RDY Low가 도착한다. 45ms timeout 이전에 RDY Low가 올 것이 거의 확실하다.

따라서 **force_window_open이 45ms timeout을 맞는다는 것은 RDY 자체가 Low로 내려오지 않고 있다는 의미**다.

## 2. Streaming 모드에서 force_comm(0xFF) 발행 시 IC 반응

### 2.1 데이터시트 §8.9 — STOP 이 "end communications" 이다

> **§8.9**: "Standard I²C STOP closes the current communication window."

> "If `Stop Bit Disable` = 0 (default), device responds normally to STOP."

Sound1 설정에는 `Stop Bit Disable` 를 명시적으로 set하는 코드가 없으므로 **기본값 0 (STOP이 window 닫음)** 상태다.

### 2.2 force_comm(0xFF)의 올바른 사용 맥락

데이터시트 §8.13:

> "Force Communication: Communication request to force-open an RDY window. Typical t_wait: **0.1 ms ≤ t_wait ≤ 45 ms**."
>
> "A communication request sequence is shown in Figure 8.2."

Figure 8.2의 force_comm은 **SCL 없이 SDA를 4회 이상 토글하는 특수 패턴**이다. 이것은 `0xFF` 바이트를 I²C 프로토콜로 전송하는 것과 **다르다**.

### 2.3 코드의 force_comm이 실제로 하는 일

```c
// tdc_touch_iqs323.c:137~143
static bool force_window_open(void)
{
    uint8_t force_comm = 0xFF;
    if (Sys_GPIO_Read(TDC_TOUCH_IQS323_RDY_PIN) == TDC_TOUCH_IQS323_WIN_OPEN)
        return true;
    if (!i2c_write(&force_comm, 1))  // ← i2c_write로 0xFF를 전송
        return false;
    // 45ms timeout 폴링
```

`i2c_write(&force_comm, 1)`는 **START + 슬레이브 주소(0x44<<1|0) + 0xFF 바이트 + STOP** 을 전송한다. 이것은 데이터시트 §8.13 Figure 8.2의 SDA 토글 패턴이 아니라, **I²C 표준 쓰기 트랜잭션이다**.

> [!IMPORTANT]
> **§8.9**: "`Stop Bit Disable` = 1인 상태에서 `end communications command(0xFF)`를 STOP 없이 전송하면 window를 닫는다." 그런데 `Stop Bit Disable` = 0(기본값)에서는 **이미 STOP이 window를 닫는다**. 따라서 `Stop Bit Disable` = 0 상태에서 0xFF 바이트를 I²C로 전송하는 것은 데이터시트에 명시된 어느 사용 케이스에도 해당하지 않는다.

이 0xFF I²C 쓰기는:
- **window가 열려 있는(RDY Low) 경우**: IC가 이를 레지스터 주소 0xFF로 해석하거나 end-communications로 해석한다. 0xFF는 존재하지 않는 레지스터이므로 §8.10("0xEE 반환" 조건: "invalid address")에 해당할 수 있다. 또는 `Stop Bit Disable`=0에서 STOP이 이미 window를 닫으므로 이 쓰기 자체가 window-closed 상태에서 발생해 0xEE를 반환한다.
- **window가 닫혀 있는(RDY High) 경우**: §8.10: "host가 comm window 밖(RDY=high)에서 read" → 0xEE 반환. **write의 경우도 window 밖 접근이므로 무시되거나 NACK된다.**

## 3. STOP 직후 RDY 상태와 force_window_open의 오판 가능성

### 3.1 STOP 후 RDY High 복귀 지연

데이터시트 §8.9 NOTE (종합결론 3_종합결론.md §1 인용):

> "정상 통신 시 STOP 후 RDY High 복귀: 원문 미명시 (open-drain RC 의존). ~200µs 추정."

Open-drain RDY는 IQS323이 LOW 드라이버를 해제한 후 **pull-up RC 시정수에 따라 High로 올라간다**. pull-up 저항과 기생 정전용량에 따라 수십~수백µs 지연이 있다.

### 3.2 read_status STOP → read_debug force_window_open 사이의 시간

tdc_touch.c:154에서 read_status 직후(`in.read_ok=true` 확인 후) read_debug를 호출한다. `read_status` 내부 마지막 동작은 `wait_window_closed(20ms)`다(tdc_touch_iqs323.c:214):

```c
// read_register 마지막
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);  // 20ms 대기
```

그러나 `wait_window_closed`는 **RDY가 TDC_TOUCH_IQS323_WIN_CLOSED(=1, GPIO High) 될 때까지 폴링**하다가 **즉시 return true**한다. 즉 RDY가 High로 올라가는 순간 return하고, 곧바로 read_debug의 `force_window_open()`이 호출된다.

### 3.3 문제: Streaming 모드에서 RDY는 STOP 직후 얼마나 High를 유지하는가?

Streaming + Report Rate=0에서:
- STOP → RDY High 복귀: ~수십~200µs (RC 시정수)
- RDY High 유지 시간: 다음 conversion 완료까지 = ~0.5~2ms 중 **이미 경과한 conversion 시간을 뺀 나머지**

**결정적 문제**: `wait_window_closed`가 RDY High를 감지하는 순간은 RC 상승의 어느 지점이다. 그러나 Streaming 모드에서 IC는 STOP을 받고 window를 닫자마자 **곧바로 다음 conversion을 시작한다**. 다음 conversion 완료 후 IC는 다시 RDY Low를 구동한다.

만약 pull-up RC 상승 중 또는 RDY High가 아직 충분히 안정되지 않은 시점에 IC가 다시 RDY Low를 구동하기 시작하면, GPIO 읽기 값이 **IC의 실제 상태와 불일치**할 수 있다.

> [!WARNING]
> **더 중요한 시나리오**: Streaming 모드에서 STOP 직후 IC는 window를 닫고 즉시 다음 conversion을 시작한다. Conversion이 끝나면 RDY Low를 다시 구동한다. 이 경우 `wait_window_closed`가 RDY High를 감지했을 때, **이미 다음 측정 사이클의 RDY Low를 기다리는 상태**다. 즉 `force_window_open`이 호출되는 시점에는 **이미 RDY가 Low(다음 window open 상태)** 일 수 있다.

그렇다면 `force_window_open`의 첫 줄:
```c
if (Sys_GPIO_Read(TDC_TOUCH_IQS323_RDY_PIN) == TDC_TOUCH_IQS323_WIN_OPEN)
    return true;  // 즉시 true
```
이 조건이 성립해 **즉시 true를 반환하고 0xFF를 전송하지 않는다**. 이것이 정상 21회 성공의 원인이다.

## 4. Transaction Timeout 200ms와 45ms(MAX_WAIT_OPEN)의 관계 — 영구화 메커니즘

### 4.1 21회 정상 이후 갑자기 영구 실패하는 전환점

**핵심 관찰**: read_status 경로의 force_window_open은 계속 성공. read_debug 경로만 실패.

`read_debug(tdc_touch_iqs323.c:353)` 내부:
```c
if (!force_window_open() || !i2c_write(&reg, 1))  // force_comm + addr 쓰기
{
    ci_printw("[TOUCH] DEBUG READ FAIL (addr) \r\n");
    return false;
}
wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
```

이 코드는 `force_window_open()`이 true를 반환한 **직후** `i2c_write(&reg, 1)`(주소 0x13 전송)을 한다. `||` 단락 평가이므로 force_window_open이 false면 i2c_write를 건너뛴다.

로그: `force_window_open() 153` 출력 직후 `FORCE WINDOW OPEN TIMEOUT`. 즉 **force_window_open 내부 45ms 폴링에서 timeout**하고 있다. RDY가 45ms 동안 Low로 내려오지 않는다.

### 4.2 데이터시트 §8.8 — Transaction Timeout과 반쪽-서비스 상태

데이터시트 §8.8:

> "After communication with IQS323 begins (START condition on I²C bus), **the I²C Transaction Timeout is disabled and the closed window watchdog timer controls** (§7.6)."

> "Communication window opens (RDY low) → if not serviced within Transaction Timeout → window closes, processing continues."

**§7.6 closed-window watchdog**: 데이터시트 원문 §7.6 참조. START condition 이후 마스터가 트랜잭션을 완료하지 않으면 IC의 closed-window watchdog이 발동해 I²C 상태 머신을 리셋한다.

### 4.3 영구화 트리거 가설 — 반쪽 트랜잭션

`read_status` 시퀀스를 보면:

```
force_window_open → i2c_write(addr=0x10) → wait_window_closed → 
force_window_open → i2c_read(2바이트) → wait_window_closed
```

"addr write 단계"에서 IC는 주소(0x10)를 받고 **wait_window_closed가 호출되는 시점에 STOP이 발행**된다. 이것이 `read_register` 함수 흐름이다:

```c
// read_register:
force_window_open();        // window 1 열기
i2c_write(&reg, 1);        // START + 0x44 + 0x10 + STOP  ← STOP이 window 1 닫음
wait_window_closed(20ms);   // window 1 닫힘 확인
force_window_open();        // window 2 열기 (다음 RDY Low 대기)
i2c_read(buf, 2);          // START + 0x44|1 + 2바이트 read + STOP
wait_window_closed(20ms);
```

이 흐름에서 **window 1에서 addr만 write하고 STOP**을 발행한다. 이것은 IQS323 관점에서 **완전한 트랜잭션이 아니다**. 데이터시트의 정상 read 시퀀스는 START→addr→Repeated START→read→STOP이거나, 별도 window에서 addr write + 다음 window에서 read다.

현재 구현은 addr write STOP → 다음 window에서 read로 두 window를 사용한다. 이것은 IQS323이 Streaming + Force Comm 맥락에서 지원하는 방식이나, **STOP 후 IC의 내부 레지스터 포인터가 다음 window까지 유지된다는 보장이 데이터시트에 명시되어 있지 않다**.

### 4.4 결정적 영구화 메커니즘 — 데이터시트 §8.4

데이터시트 §8.4:

> "**Communication During ATI**: If `System Status` `Reset Event` bit is NOT set, **I²C communication is disabled during ATI**."

FullATI 모드(ATI Mode=Full)에서 Re-ATI 트리거 후 ATI가 진행 중이면 **I²C 통신 전체가 disabled**된다. RDY는 이 기간 동안 Low로 내려오지 않는다.

**그러나 22회째 실패 시점에 ATI가 진행 중인가?** 코드를 보면:

```c
// tdc_touch.c:171
if (in.read_ok && in.ati_error && !in.ati_active)
{
    ci_printw("[TOUCH] ATI ERROR (drift) \r\n");
}
```

로그에 `ATI ERROR` 출력이 없다. 그러나 더 중요한 것은: **read_status가 계속 성공**하고 있다는 점이다. ATI 중 I²C가 disabled되면 read_status도 실패해야 한다. 따라서 §8.4는 이 증상의 직접 원인이 아니다.

### 4.5 실제 영구화 메커니즘 — read_debug 내 force_window_open과 STOP 의 순서 충돌

**재구성**: `read_debug`의 `force_window_open()` 호출 시점에서 정확히 무슨 일이 일어나는가?

`read_status`의 마지막 `wait_window_closed`가 완료(RDY High 감지)된 직후 `read_debug`의 `force_window_open`이 호출된다.

Streaming + Report Rate=0 환경에서, read_status STOP 이후 IC가 다음 conversion을 완료하는 시간(~0.5~2ms) 내에 `read_debug` 코드가 진입하면:

**케이스 A** (정상 — 21회): `force_window_open` 진입 시 RDY가 이미 Low(다음 window가 열림) → 즉시 true return → `i2c_write(0x13, 1)` 성공 → wait_window_closed → 다음 force_window_open으로 4바이트 read → 성공.

**케이스 B** (영구 실패 트리거): 어느 순간 read_status의 `wait_window_closed`가 RDY High를 감지했는데, 그것이 **RC pull-up 상승의 일시적 High**이고 실제 IC는 아직 window를 완전히 닫지 않은 과도 상태이거나, 반대로 IC가 이미 다음 RDY Low를 구동 시작한 직후(but GPIO 샘플링 타이밍으로 High로 읽힘)라면:

`force_window_open`에서 RDY가 **High로 읽힘** → 0xFF를 `i2c_write`로 전송 → 이 시점에 IC는 **window가 닫힌 상태이거나 다음 window를 막 열려는 시점** → IC가 0xFF를 window-closed 상태 I²C 시도로 처리해 **NACK 또는 무시**.

그런데 0xFF를 전송하는 `i2c_write`는 START + 0x44 write 주소 + 0xFF + STOP이다. **IC가 이 트랜잭션 도중에 RDY Low를 구동하기 시작하면**, 즉 window가 이 트랜잭션 중간에 열리면:

- START condition이 있으므로 §8.8에 따라 **Transaction Timeout은 비활성화**되고 **closed-window watchdog(§7.6)이 활성화**된다.
- 그러나 마스터는 STOP을 발행하고 트랜잭션을 완료했다. IC 관점에서는 START→STOP이 완료되었으나, 전달한 0xFF가 **주소 위상이 아닌 데이터 위상**에서 처리되거나 **end-communications command**로 해석된다.
- `Stop Bit Disable`=0이므로 STOP이 window를 닫는다. 이 시점에 IC는 새 window를 열었는데 즉시 닫히는 충돌이 발생한다.

**그 이후**: IC 내부 상태 머신이 불확정 상태에 진입한다. 구체적으로:

1. IC가 window를 열었는데 0xFF 트랜잭션이 window open 직후 STOP으로 닫아버림 → IC는 다음 conversion으로 진행하려 하지만, 내부 레지스터 포인터나 통신 상태 머신이 비정상 상태에 있음.
2. 다음 conversion 완료 후 IC는 RDY Low를 시도해야 하는데, **이전 window의 Transaction이 완전히 서비스되지 않은 채로 닫힌 경우** §7.6 watchdog이 발동해 I²C 상태 머신을 리셋하면서 **일정 시간 RDY가 High로 유지**될 수 있다.

### 4.6 read_status vs read_debug 경로의 비대칭

**왜 read_status는 계속 성공하고 read_debug만 실패하는가?**

`read_status`의 force_window_open이 호출되는 시점:
- 폴링 주기 `TDC_TOUCH_POLL_INTERVAL_MS` 이후 호출된다(tdc_touch.c:135~136). 폴링 간격이 충분히 길면 IC는 이미 안정된 window 상태에 있다.
- `read_debug`의 force_window_open은 **read_status 완료 직후** 연속으로 호출된다. 이 타이밍이 Streaming 모드의 RDY 토글 주기(~0.5~2ms)와 충돌하는 레이스 조건을 만든다.

**read_status 성공 → read_debug force_window_open에서 0xFF 전송 → IC 상태 오염 → 이후 모든 read_debug 실패**의 영구화 루프가 형성된다.

더 구체적으로: **read_debug의 force_window_open이 한 번 0xFF를 잘못된 타이밍에 전송하면, IC의 I²C 상태 머신이 비정상 상태에 진입해 이후 RDY를 더 이상 Low로 내리지 않거나 매우 다른 주기로 내린다.** 그러나 read_status는 폴링 주기(200ms?) 이후 호출되므로 IC가 watchdog으로 자체 복구한 window를 만날 수 있다.

### 4.7 데이터시트 §8.8 — 반쪽 서비스된 window 처리

> "If comm window is not serviced within Transaction Timeout: window closes, **normal processing continues**."
>
> "After START: Transaction Timeout disabled, §7.6 watchdog controls."

§7.6는 데이터시트 본문에서 "closed window watchdog"으로 언급되지만 상세 타이밍이 명시되지 않는다. **watchdog 발동으로 I²C 상태 머신 리셋 시 RDY가 High를 유지하는 시간이 불확정**이다.

코드의 45ms timeout이 이 watchdog 리셋 시간보다 짧으면 영구 timeout이 발생한다. **그러나 §7.6 watchdog 리셋 시간은 데이터시트에 수치가 없다.** 이것이 45ms 영구 timeout의 데이터시트적 설명 가능 메커니즘이다.

## 5. 은수님 모델 검증 — 최종 판정

### 5.1 모델 원문

> "conversion이 1MHz 수준으로 빠르므로, I2C STOP으로 윈도우가 닫혀도 타임아웃(45ms) 전에 다음 conversion이 끝나 RDY가 곧 다시 Low로 내려가 윈도우가 열려야 한다. 한 번 윈도우가 닫힌 뒤 conversion 타임아웃은 최대 ~200ms다. 그러니 STOP 직후 곧 윈도우가 열릴 것으로 예상했는데 왜 45ms 영구 timeout인가?"

### 5.2 판정: **절반 맞고 절반 틀림**

**맞는 부분**:
- 1MHz conversion에서 1 사이클은 ~0.5~2ms이다(§1 분석). STOP 직후 정상 상황에서 다음 RDY Low는 45ms 이내에 도착한다. **정상 Streaming 환경에서 모델이 예측한 대로 동작했고, 그래서 첫 21회는 성공했다.**
- Transaction Timeout 200ms는 **마스터가 window를 아예 서비스하지 못했을 때** 발동하는 안전장치이며, force_window_open의 45ms timeout과는 별개 레이어다.

**틀린 부분 (분석 결론)**:
- **45ms 영구 timeout은 "RDY가 다음 Low를 안 내린다"는 의미**이며, 이것은 "conversion이 완료됐지만 IC가 RDY Low를 구동하지 못하는 상태"를 뜻한다.
- 이 상태의 원인은 **conversion 속도 문제가 아니라 IC 내부 I²C/통신 상태 머신이 비정상 상태에 진입한 것**이다.
- 트리거는 **read_debug의 force_window_open이 0xFF를 I²C 쓰기로 전송하는 타이밍**이다. Streaming 모드에서 RDY 토글이 빠르기 때문에(~1~2ms 주기), read_status STOP 후 RC pull-up 과도 구간 + read_debug force_window_open 호출 사이에 **레이스 조건**이 발생한다.
- 0xFF I²C 쓰기가 **window-open/transition 시점에 잘못된 타이밍으로 발행**되면 IC 상태 머신이 오염되어 이후 RDY Low 구동이 중단된다.
- **이것이 영구화되는 이유**: 한 번 IC 상태 머신이 오염되면 read_debug 경로의 force_window_open은 매번 45ms 폴링 → timeout → `i2c_write(0xFF)` 재시도의 루프에 빠진다. 그러나 read_status 경로는 폴링 간격(200ms) 후 IC가 watchdog으로 자체 복구한 window를 만나 성공한다.

### 5.3 데이터시트 근거 요약

| 근거 포인트 | 데이터시트 조항 | 내용 |
|---|---|---|
| 1 측정 사이클 ~0.5~2ms | §6.5 Table A.1 (Period=5 → 1MHz) + §5.4 (Counts ∝ 사이클 수) | conversion 1회 = ATI Target 횟수 × 1µs + overhead |
| Streaming Report Rate=0 → 즉시 RDY Low | §8.11.1, §8.7 | 측정 완료 즉시 window 오픈 |

| 0xFF = end-comm (Stop Bit Disable=1에서만) | §8.9 | Stop Bit Disable=0에서는 undefined 동작 |
| window 밖 접근 → 0xEE | §8.10 | RDY=High에서 read/write → 무시/NACK |

## 6. 결론 요약

1. **1 측정 사이클 소요**: ~0.5~2ms (ATI Target~400, f_xfer=1MHz, 단일채널). STOP 직후 다음 RDY Low는 45ms 이전에 도착한다 — 은수님 모델의 이 부분은 **맞다**.

2. **force_comm(0xFF) 오용**: 코드의 `force_window_open`은 데이터시트 §8.13 Figure 8.2의 SDA 토글 방식이 아니라 **I²C 쓰기 트랜잭션으로 0xFF를 전송**한다. `Stop Bit Disable=0` 기본값에서 0xFF의 I²C 쓰기는 데이터시트에 정의된 동작이 없다. Window-open 직후 또는 transition 시점에 발행되면 IC 상태 머신을 오염시킨다.

3. **RDY 고판정 오판**: `force_window_open`의 첫 줄은 RDY=Low이면 즉시 true를 반환한다. Streaming 모드에서 RDY 주기가 ~1~2ms이므로, read_status 완료 직후 read_debug force_window_open 호출 시 **이미 다음 window가 열려있어 0xFF 전송 없이 즉시 true 반환**이 정상 케이스(21회 성공)다. 그러나 특정 타이밍(RC 과도 구간, window 경계)에서 RDY High를 읽어 0xFF를 발행하면 레이스가 발생한다.

4. **영구화 메커니즘**: 0xFF I²C 쓰기가 window transition 타이밍에 발행 → IC I²C 상태 머신 오염 → 이후 RDY Low 구동 중단 → force_window_open 45ms timeout 영구 → `DEBUG READ FAIL (addr)` 영구 반복. read_status는 폴링 주기(200ms) 덕에 IC watchdog 복구 후 window를 만나 계속 성공.

5. **은수님 모델 최종 판정**: **모델의 전제("conversion이 빠르니 STOP 후 45ms 내 RDY Low가 온다")는 맞다. 그러나 45ms 영구 timeout의 원인이 "다음 conversion이 느린 것"이 아니라 "IC 상태 머신이 0xFF 오용으로 오염되어 RDY Low 자체를 구동하지 않는 것"이므로, 모델의 예측("45ms 내 RDY Low가 와야 한다")과 현실("오지 않는다") 사이의 불일치는 모델이 0xFF 오용의 부작용을 고려하지 않은 데서 발생한다.** 모델은 정상 Streaming 타이밍 이론으로는 올바르나, IC 상태가 이미 오염된 상황을 설명하지 못한다.

## 7. 수정 방향 (참고)

1. **`force_window_open` 재구현**: RDY=High일 때 0xFF I²C 쓰기를 시도하지 말고, 단순히 RDY Low를 폴링 대기하는 방식으로 변경. Streaming 모드에서 force_comm이 필요 없다(RDY가 자동으로 토글됨).
2. **`read_debug`를 별도 폴링 주기로 분리**: read_status 직후 연속 호출이 아니라 독립 주기(예: 1초 간격)로 호출해 RDY 레이스 조건 회피.
3. 또는 **`read_debug` 비활성화**: `TDC_TOUCH_DEBUG_PRINT_ENABLE=0`으로 운용하면 문제 경로 자체가 제거된다.
