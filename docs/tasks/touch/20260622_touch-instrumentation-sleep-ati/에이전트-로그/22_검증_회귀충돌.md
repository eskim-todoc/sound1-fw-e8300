# 검증_회귀충돌 — 터치 계측·절전 Full ATI 정합 계획 회귀 점검

**TL;DR**: P0~P4 계획 전반을 FSM 무영향·절전 시퀀스 부작용·RDY 윈도우 타이밍·I2C 부하·boot_ignore 디바운스 영향 5축으로 점검. 치명 1건(RDY 윈도우 내 다중 read_register 직렬 호출 → 윈도우 1개로 처리 불가 위험), 경계 주의 2건(reseed Power Mode 덮임 의도 명시·부팅 디바운스 채터 리셋 미완전 경계) 발견. 나머지 FSM/절전 경로는 회귀 없음.

---

## 1. 점검 범위

점검 대상 계획: `11_계획_통합설계.md` §2~3 (P0~P4, 6파일, 변경 목록).

점검 축:
1. 기존 FSM(NOT_TOUCH/TOUCH 천이·read 실패 HOLD·stuck·Re-ATI 게이트) 무영향 보장
2. 절전 시퀀스(func_sleep 진입→ULP 루프→재부팅) 변경의 부작용
3. RDY 윈도우·스트리밍 타이밍: 200ms 폴링에 read 2~3건 추가 시 윈도우 놓침·블로킹 시간 증가
4. I2C 부하·절전 전력(절전 임계 변경으로 sensing 활성도 변화)
5. boot_ignore 디바운스가 boot_5s 경고·부팅 터치 억제에 미치는 영향

---

## 2. 회귀 점검 결과

### 2.1 기존 FSM 무영향 보장

#### Claim 1: NOT_TOUCH↔TOUCH 즉시 천이(1 tick) 불변 보장

**verdict**: real (무영향 확인)

**evidence**:
- `tdc_touch_logic.c:108-111` — boot_ignore=false 경로의 curr_state 결정 로직:
  ```c
  curr_state = in->pressed ? TDC_TOUCH_STATE_TOUCH : TDC_TOUCH_STATE_NOT_TOUCH;
  ```
  이 분기는 `if (st->boot_ignore)` 블록(계획 P4 변경 대상, tdc_touch_logic.c:117)보다 앞의 공통 경로.
- P4가 교체하는 블록은 오직 `if (st->boot_ignore)` 분기 내부(계획 §2.4.3) — boot_ignore=false일 때 진입 불가.
- 따라서 일반 천이(boot_ignore=false)는 P4 변경과 완전 배타. 즉시 천이 불변.

#### Claim 2: read 실패 HOLD 동결(10회, 2000ms) 불변 보장

**verdict**: real (무영향 확인)

**evidence**:
- `tdc_touch_logic.c:94-105` — read 실패 hold 블록:
  ```c
  if (!in->read_ok)
  {
      st->read_fail_cnt++;
      if (st->read_fail_cnt <= TDC_TOUCH_READ_FAIL_HOLD_CNT)
      {
          out->action = TDC_TOUCH_ACT_HOLD;
          out->curr_state = st->prev_state;
          return;    // ← 조기 return. 이하 boot_ignore·stuck·게이트 전부 건너뜀
      }
      ...
  }
  ```
- 이 블록은 P0~P4 어느 변경도 건드리지 않음. 계획 §2.4.3의 boot_ignore 교체 코드는 이 블록 **이후**(tdc_touch_logic.c:117)에 위치.
- TDC_TOUCH_READ_FAIL_HOLD_CNT = TDC_TIME_TO_CNT(2000, 200) = 10 (tdc_touch_time.h:30-31). P0는 새 상수 추가만, 기존 상수 미변경.

#### Claim 3: stuck 에스컬레이션(RESEED→Re-ATI→MCLR) 불변 보장

**verdict**: real (무영향 확인)

**evidence**:
- `tdc_touch_logic.c:17-59` — `stuck_eval()` 함수 전체 및 `tdc_touch_logic.c:148-155` 호출 위치. 계획 어느 단계도 이 함수를 변경하지 않음 (계획 §2.4 참조: init·set_boot_ignore·boot_ignore 블록만 변경 대상).
- `tdc_touch_logic.c:148-155`:
  ```c
  {
      tdc_touch_act_t sa = stuck_eval(st, curr_state, in->now_ms);
      if (sa != TDC_TOUCH_ACT_NONE)
      {
          out->action = sa;
      }
  }
  ```
  이 코드는 boot_ignore 블록의 `return;`을 통과한 이후에만 도달 — boot_ignore=true 구간에서 stuck 평가가 원래 없었으므로 P4의 boot_ignore 블록 교체 후에도 동일하게 boot_ignore=true 구간에서 stuck 비활성.

#### Claim 4: Re-ATI 게이트 조건(NOT_TOUCH && !ati_active && ati_error && cooldown) 불변 보장

**verdict**: real (무영향 확인)

**evidence**:
- `tdc_touch_logic.c:139-146`:

  if (curr_state == TDC_TOUCH_STATE_NOT_TOUCH

### 2.2 절전 시퀀스 부작용

#### Claim 5: apply_sleep_settings()의 touch_settings(255,255) 제거 후 절전 중 터치 정상 감지

**verdict**: real (정상 감지 확인)

**evidence**:
- 현재 `tdc_touch_iqs323.c:409-425`: `touch_settings(255, 255)` → REG_CH0_TOUCH(0x62)=0xFFFF.
  - 06_레지스터레퍼런스.md §A.17: `Touch Threshold = (Threshold × LTA) / 256`. threshold=255이면 절대 임계 ≒ LTA, self-cap delta(LTA−Counts)가 LTA에 도달하려면 Counts≈0이어야 — 사실상 무감.
- 제거 후 0x62는 apply_settings()에서 기록한 threshold=16, hyst=8(0x0810, tdc_touch_iqs323.c:341-343) 그대로 유지. 절대 임계 = 16×LTA/256 ≈ LTA/16 — 적정 감도로 절전 중 터치 감지 가능.
- ULP 루프의 `tdc_touch_get_state()`(main.c:912) → `tdc_touch_iqs323_read_status()`(tdc_touch.c:222) → 0x10 read → pressed 비트로 판정. 이 경로는 threshold 레지스터와 무관하게 IC가 내부적으로 판정한 결과를 읽음 — threshold 제거가 직접 영향을 줌(IC가 내부 threshold=16으로 터치 판정 → pressed 비트 set).

---

#### Claim 6: reseed()의 Power Mode 덮임이 절전 기능을 해치지 않음

**verdict**: uncertain (의도적 수용이나 명시 필요)

**evidence**:
- `main.c:881` `apply_sleep_settings()` → 0xC0 write: `write_register(REG_SYSTEM_CONTROL, 0x00, 0x07)` (tdc_touch_iqs323.c:418-421). bits[6:4]=000 = Normal Power Mode 고정.
- `main.c:885` `ci_power_sleep()` — SYSCLK 강하.
- `main.c:889` `tdc_touch_iqs323_reseed()` → `write_register(REG_SYSTEM_CONTROL, 0x58, 0x07)` (tdc_touch_iqs323.c:381-383). bits[6:4]=101 = Automatic No ULP 복원. RESEED(bit3) 동시 트리거.
- 계획은 이 순서를 "Power Mode 덮임 — 의도적 수용"으로 주석 처리(계획 §2.5.3)하며 수용. 결과적으로 절전 중 IC는 Automatic No ULP(자동 NP→LP 강하, ULP 불진입) 상태. 이것은 IC 내부 전력 절감이지 CM3 ULP와는 별개 축이므로 ULP 루프 기능에 영향 없음.
- **주의**: apply_sleep_settings()에서 0xC0를 000(Normal)으로 썼다가 reseed()가 101(Auto No ULP)로 덮는 이중 write가 짧은 구간 존재. RDY 윈도우가 이 사이에 열릴 경우 000 상태에서 한 번 read가 들어올 수 있으나, CM3가 ci_power_sleep() 이후 I2C 클럭을 재설정(main.c:887)하고 reseed()를 연속 호출하는 구조라 실질 노출 구간이 수십 us 수준 — 허용 범위.

---

#### Claim 7: ULP 루프 롱터치 재부팅(2.2s, 11회) 불변 보장

**verdict**: real (무영향 확인)

**evidence**:
- `main.c:895-954` — ULP 루프. `touch_cnt` 카운터 및 `TDC_TOUCH_ULP_LONG_TOUCH_CNT`(tdc_touch_time.h:38, @200ms=11) 기반 재부팅 로직. 계획에서 main.c는 변경 없음(계획 §2.7: "변경 없음").
- `tdc_touch_get_state()` 경로(main.c:912): `tdc_touch_iqs323_read_status()` → 0x10 1회 read. P2에서 추가되는 `tdc_touch_iqs323_read_debug()`는 tdc_touch.c 폴링 루프에서만 호출 — ULP 루프는 `tdc_touch_process()`를 호출하지 않으므로 debug read 완전 비개입.

### 2.3 RDY 윈도우·스트리밍 타이밍

#### Claim 8 [치명]: 200ms 폴링 1회에 read_register 직렬 3회 추가 시 RDY 윈도우 충돌 위험

**verdict**: uncertain (치명 경계 — 설계 검토 필요)

**evidence**:
- 현재 `tdc_touch_process()` 1 tick당 `read_register(REG_SYSTEM_STATUS, ...)` 1회(tdc_touch.c:144 → tdc_touch_iqs323_read_status() → read_register 1회, 내부적으로 force_window_open → write addr → force_window_open → i2c_read).
- 계획 P2+P3: `tdc_touch_iqs323_read_debug()` 추가 — 동일 tick 내에 `read_register(REG_CH0_COUNTS, ...)` + `read_register(REG_CH0_LTA, ...)` 2회 추가(계획 §2.5.2).
- `read_register()` 구현(tdc_touch_iqs323.c:177-208):
  1. `force_window_open()` — RDY LOW(윈도우 열림) 확인 또는 force_comm(0xFF) 전송 후 대기(최대 45ms, tdc_touch_iqs323.h:32).
  2. `i2c_write(&reg, 1)` — 주소 전송.
  3. `wait_window_closed(20ms)`.
  4. `force_window_open()` — 두 번째 윈도우.
  5. `i2c_read(buf, 2)`.
  6. `wait_window_closed(20ms)`.
- **핵심 문제**: 05_i2c인터페이스.md §8.7에 의하면 IQS323은 **데이터를 읽으면 윈도우가 닫힌다**(STOP → window 닫힘). 다음 read_register 호출은 새 윈도우가 열릴 때까지 force_window_open()에서 최대 45ms 대기. 총 3회 read_register(status 1 + counts 1 + lta 1) × 최대 (45+I2C 전송+45+I2C 전송+20)ms = 최악 ~300ms 이상 블로킹 가능.
- **폴링 주기 200ms(tdc_touch_time.h:18) 초과 위험**: 매 tick에서 read_register 3회가 블로킹 합산 시 다음 tick이 200ms 후에 와야 하는데, 이전 tick 처리가 200ms보다 길면 폴링 게이팅(`now - s_poll_tick_old > 200ms`)이 즉시 통과 → 사실상 폴링 밀도 증가가 아닌 직렬 처리로 흡수되지만, **ISR/main loop 다른 작업에 미치는 블로킹 영향** 및 **RTT 버퍼 포화**는 별도 위험.
- **더 심각한 경우**: 이벤트 모드에서 RDY 윈도우는 이벤트 발생 시만 열림(05_i2c인터페이스.md §8.11). status read로 첫 윈도우를 소진하면 다음 counts/lta read를 위해 force_comm이 필요. force_window_open()이 0xFF force comm을 전송하고 최대 45ms 대기(tdc_touch_iqs323.h:32 MAX_WAIT_OPEN_MS=45). **이 45ms 대기가 비블로킹이 아닌 polling busy-wait**(tdc_touch_iqs323.c:140-152) — 200ms 폴링 루프 내 최악 135ms(3×45ms) 블로킹 가능. CM3가 단일 스레드이면 이 구간 watchdog refresh 지연 위험.
- **계획의 완화**: 계획 §2.6.2는 `if (in.read_ok)` 조건으로 read_debug를 게이팅 — read 실패 시 debug read 건너뜀. 그러나 read_ok인 정상 경우에도 force_window_open 45ms×2 블로킹 발생.

> [!IMPORTANT]
> 치명 경계: `read_register` 1회 호출이 최악 90ms(force×2 + write + wait_close)를 소비. tdc_touch.c 폴링 1 tick에 3회 직렬 → 최악 270ms. 200ms 폴링 주기를 초과하는 tick이 발생할 수 있으며, cm3 단일 스레드에서 기타 서브시스템(배터리·LED·BLE 상태) 처리 지연이 누적될 수 있다.
>
> **완화 방안(계획 미포함)**: ① LTA·Counts를 status read와 동일 윈도우 내 연속 레지스터 read로 통합(단, read_register 구조상 각 register read마다 윈도우 재오픈 필요 — 구조적 한계). ② 별도 ULP 외 주기(예: 5폴링=1초마다)로 debug read 게이팅 — `TDC_TOUCH_DEBUG_PRINT_EVERY_N` 제안이 Q2에 존재하나 블로킹 자체는 완화 안 됨. ③ read_debug 자체를 비블로킹 상태머신으로 분리(이번 범위 초과). 실기 검증(RTT에서 폴링 간격 타임스탬프) 필수.

#### Claim 9: 스트리밍 모드에서 200ms report rate와 폴링 경쟁

**verdict**: real (기존 구조 유지, 추가 위험 없음)

**evidence**:
- 현재 코드는 이미 event mode + force_window_open polling 방식. P2/P3는 force_window_open 호출 횟수를 status(2회) + counts(2회) + lta(2회) = 6회로 늘림 — 이미 Claim 8에서 분석.
- 스트리밍 vs 이벤트 모드 구분: events_enable()(tdc_touch_iqs323.c:267-271)에서 0xD3=0x0052(ati_error|ati_event|touch_event 활성화). 이는 이벤트 모드로 동작 — 이벤트 발생 시만 RDY. 폴링 간 터치 변화 없으면 RDY 침묵 → force_comm 필수. 기존 구조가 이미 이를 수용하고 있어 P2/P3로 인한 **모드 변화**는 없음. 단 횟수 증가(Claim 8) 분리.

### 2.4 I2C 부하·절전 전력

#### Claim 10: threshold 제거로 절전 중 sensing 활성도 변화 → 전력 증가

**verdict**: uncertain (실측 필요, 설계상 허용 범위 추정)

**evidence**:
- IC 내부 sensing 활성도(변환 주기)는 Power Mode(NP/LP) 및 Conversion Frequency(0x31=0x057F, tdc_touch_iqs323.c:283)에 의존. threshold 값은 IC가 touch 판정 후 RDY를 assert할지 결정하는 로직 레벨 — sensing 자체의 클럭/전류에 영향 없음.
- threshold=255(무감) 상태에서는 RDY assert 빈도가 낮았을 수 있으나(이벤트 발생 조건 매우 높아 touch 이벤트 미발생), 이는 IC내부 전력이 아닌 I2C 통신 빈도에 영향. cm3가 폴링을 force_comm으로 트리거하는 구조라 RDY 빈도와 무관하게 200ms마다 접근.
- 절전 전력 예산: IC는 ULP/LP 모드에서 µA 수준(02_proxfusion동작.md §5.2 참조). IQS323 자체는 CM3 ULP 진입과 무관하게 reseed 이후 Automatic No ULP(bits[6:4]=101)로 자체 절전 관리. threshold 제거는 IC 자체 전력에 영향 없음.

---

#### Claim 11: read_debug 추가로 I2C 부하 증가

**verdict**: real (측정 가능한 부하 증가 — 운용 허용 범위)

**evidence**:
- 추가 I2C 트랜잭션: 200ms 폴링 1회당 counts(0x13) + lta(0x14) 각 1회 read_register = 2건 추가.
- read_register 1회 = addr write(1byte) + data read(2byte) = 3byte × 2회 force_window. I2C 400kHz 기준 수십 µs/transaction — 배터리·전력 영향은 무시 가능.
- CM3 블로킹 시간 증가(Claim 8)가 더 중요한 부작용. 전류 자체는 허용.

### 2.5 boot_ignore 디바운스 영향

#### Claim 12: boot_5s_warned 경고 타이밍이 디바운스 도입으로 지연되지 않음

**verdict**: real (무변화 확인)

**evidence**:
- 계획 §2.4.3의 교체 코드 TOUCH 분기:
  ```c
  else    /* curr_state == TOUCH */
  {
      st->boot_release_cnt = 0;   /* 채터 리셋 */
      if (!st->boot_5s_warned
          && TDC_TOUCH_BOOT_WARN_MS <= (in->now_ms - st->boot_ready_ms))
      {
          st->boot_5s_warned = true;
          out->boot_event    = TDC_TOUCH_BOOT_WARN_5S;
      }
      else
      {
          out->boot_event = TDC_TOUCH_BOOT_IGNORING;
      }
  }
  ```
- TOUCH 상태에서의 boot_5s 경고 조건(`TDC_TOUCH_BOOT_WARN_MS <= (in->now_ms - st->boot_ready_ms)`)은 현재 코드(tdc_touch_logic.c:124-129)와 동일. 타이밍 변화 없음.

---

#### Claim 13: 부팅 직후 NOT_TOUCH로 시작하는 정상 케이스에서 boot_ignore가 설정되지 않으면 디바운스 코드가 진입 안 됨

**verdict**: real (정상 케이스 무영향 확인)

**evidence**:
- `tdc_touch.c:92-98`: `tdc_touch_logic_set_boot_ignore()`는 부팅 시 `st.pressed=true`일 때만 호출.
- pressed=false로 부팅하면 boot_ignore=false → P4 변경 블록(`if (st->boot_ignore)`) 미진입. 완전 배타.

#### Claim 14: 디바운스 카운터가 부팅 채터 시나리오에서 올바르게 리셋됨

**verdict**: uncertain (경계 케이스 — 카운터 최대값 점검 필요)

**evidence**:
- 계획 §2.4.3의 TOUCH 분기: `st->boot_release_cnt = 0` 리셋 — 채터(뗌→재터치) 시 카운터 0 복귀 정상.
- **경계**: boot_release_cnt가 `uint8_t`(계획 §2.3, tdc_touch_logic.h 필드 타입). TDC_TOUCH_BOOT_RELEASE_DEBOUNCE_CNT=2로 오버플로 위험 없음(0→1→2 해제).
- **미검토 시나리오**: read 실패 동결 분기(`!in->read_ok`)에서는 boot_release_cnt를 증가시키지 않고 IGNORING 반환. 이 설계는 read 실패 중 조기 해제 방지로 올바름(계획 §2.4.3 주석 확인). 다만 read 실패가 장기 지속될 경우 boot_ignore=true 구간이 연장 — read 실패 HOLD(tdc_touch_logic.c:94-104)는 boot_ignore 블록보다 **앞에서 return** 하므로 read 실패 시 boot_ignore 블록 자체에 진입 안 함. boot_release_cnt 동결 코드(계획 §2.4.3의 `!in->read_ok` 분기)는 실제로 **도달 불가**다.

> [!NOTE]
> 계획 §2.4.3의 `if (!in->read_ok)` 분기는 dead code: read 실패 시 logic.c:94-104에서 이미 `return;`하므로 boot_ignore 블록에 도달하지 않음. 코드는 무해하나 혼란을 줄 수 있어 주석 또는 제거 권고.

#### Claim 15: boot_ignore 구간 중 게이트·stuck·롱터치 억제가 디바운스 후에도 유지됨

**verdict**: real (무영향 확인)

**evidence**:
- 계획 §2.4.3 교체 후에도 `if (st->boot_ignore)` 블록 마지막에 `st->prev_state = curr_state; return;`이 존재(계획 §2.4.3 교체 코드 꼬리). 이 return이 tdc_touch_logic.c:139(Re-ATI 게이트)·148(stuck_eval)·157(롱터치)에 도달하지 않도록 차단. 기존 억제 동작 불변.

## 3. 치명 이슈 목록

### CRIT-01: read_register 3회 직렬 호출 — 블로킹 270ms 가능, 200ms 폴링 주기 초과

- **위치**: 계획 P2+P3 — tdc_touch.c `tdc_touch_process()` 내 read_debug() 삽입.
- **메커니즘**: `tdc_touch_iqs323_read_status()` 1회 + `tdc_touch_iqs323_read_debug()` 내 read_register 2회 = 총 read_register 3회 직렬. 각 read_register의 `force_window_open()`은 최악 45ms 폴링 busy-wait(tdc_touch_iqs323.h:32 MAX_WAIT_OPEN_MS=45) × 2회/read = 최악 270ms 블로킹.
- **영향**: 200ms 폴링 주기(tdc_touch_time.h:18) 초과, CM3 단일 스레드에서 배터리·LED·BLE 서브시스템 처리 지연, watchdog refresh 누락 위험(tdc_touch_iqs323.c:408, 424의 SYS_WATCHDOG_REFRESH는 apply/sleep 함수 내에만 존재 — 폴링 루프 내 없음).
- **완화 방안**:
  1. `TDC_TOUCH_DEBUG_PRINT_EVERY_N` Q2(계획 §7)로 down-sample하더라도 호출 시 블로킹 자체는 동일 — 빈도 감소일 뿐.
  2. 실기 검증에서 폴링 간격 타임스탬프로 실제 블로킹 측정 후 허용/불허 결정 필수.
  3. 이상적으로는 debug read를 별도 저속 타이머로 분리(이번 범위 초과) 또는 status read와 동일 윈도우 내 연속 read(register pointer auto-increment 여부 데이터시트 확인 필요 — 미확인).

## 4. 경계 주의 항목

### WARN-01: reseed()의 apply_sleep_settings() 0xC0 Normal Mode 설정 덮임 — 의도적 수용이나 문서화 필수

- `main.c:881` apply_sleep_settings()에서 0xC0=0x0007(Normal Mode bits[6:4]=000) 기록, `main.c:889` reseed()에서 0xC0=0x5807(Auto No ULP bits[6:4]=101) 덮임.
- 계획은 이를 "의도적 수용"으로 주석(계획 §2.5.3). 이 순서에서 짧은 구간 Normal Mode(000) 상태 — 감지에 영향 없으나 IC 내부 Power Mode transition이 발생.
- 계획이 이미 인라인 주석 추가로 처리 예정 → 수용 가능.

### WARN-02: `tdc_touch_logic_step()` boot_ignore 내 `!in->read_ok` 분기 — dead code

- `tdc_touch_logic.c:94-104`의 read 실패 HOLD return이 boot_ignore 블록(tdc_touch_logic.c:117) 도달 전 return → 계획 §2.4.3의 `if (!in->read_ok)` 분기는 도달 불가.
- 코드가 무해하지만 논리 혼란 가능. 구현 시 제거하거나 `/* 도달 불가: read 실패는 상단 read_fail_cnt return으로 처리 */` 주석 추가 권장.
