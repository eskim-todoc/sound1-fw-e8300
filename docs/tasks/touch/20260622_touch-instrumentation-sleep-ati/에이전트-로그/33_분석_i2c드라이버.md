# driver_i2c 상태머신 분석 — IQS323 read_debug 영구 latch 관련

> **TL;DR**: 드라이버는 ISR 기반 비동기. `WritingDone`/`ReadingDone` 상태는 ISR 모드에서 Idle로 전이하는 코드가 `#ifndef CM3_I2c_using_ISR` 가드 안에 있어 **실제로는 dead code** — `setI2cDriverStatusIdle()` 명시 호출이 없으면 드라이버는 `WritingDone`/`ReadingDone`에 영구 멈춘다. 그러나 `tdc_touch_iqs323.c`의 `i2c_write`/`i2c_read`는 이를 직접 호출하므로 정상 경로는 안전하다. 4바이트 read는 드라이버 레벨에서 2바이트와 구조적으로 동일하게 처리되며 별도 버퍼/FIFO 한계 없음. **영구 latch의 드라이버 원인**: `i2c_startWriteData`/`i2c_startReadData` 진입 시 하드웨어 STATUS가 `busy==1`이면 즉시 `i2c_state_Error`로 전이 — `init_I2c()`가 Error ISR에서 호출되지만 하드웨어 버스 자체가 frozen이면 그 후에도 동일 Error 반복으로 `i2c_state_Error` latch가 가능하다. 단 실측에서 `read_status`가 계속 성공하므로 드라이버 latch는 read_debug 영구 timeout의 1차 원인이 아니며, 1차 원인은 이미 39_판정에서 확인된 "RDY High 상태에서 0xFF 발행 → IC 무응답" 이다.

## 1. 동기 vs 비동기 — ISR 기반 확인

### 1.1 컴파일 분기 결정

`driver_i2c.h` 9번줄:
```c
#define CM3_I2c_using_ISR
```

`driver_i2c.c` 162~166번줄:
```c
#ifdef CM3_I2c_using_ISR
void I2C_0_IRQHandler(void)
#else
void i2c_comm(void)
#endif
```

`CM3_I2c_using_ISR`이 정의되어 있으므로 `I2C_0_IRQHandler`가 활성 — **드라이버는 ISR 기반 비동기**. DMA 없음.

`init_I2c()` (driver_i2c.c:132~143):
```c
void init_I2c(void)
{
    Sys_I2C_Reset(I2C0);
    Sys_I2C_Config(I2C0, CM3_I2C_CFG_VAL_AsMaster);
    clearI2cDriverStatus();
    enableI2cInterface(true);

#ifdef CM3_I2c_using_ISR
    NVIC_ClearPendingIRQ(I2C_0_IRQn);
    NVIC_EnableIRQ(I2C_0_IRQn);
#endif
}
```

ISR 모드에서 `init_I2c`는 NVIC 인터럽트도 활성화한다. 인터럽트 설정 구성은 `CM3_I2C_CFG_VAL_AsMaster` 매크로(driver_i2c.h:25~30):

```c
#define CM3_I2C_CFG_VAL_AsMaster   ( I2C_MASTER_PRESCALE_240            \
                                   | I2C_STOP_INT_ENABLE                \
                                   | I2C_OVERRUN_INT_ENABLE             \
                                   | I2C_BUS_ERROR_INT_ENABLE           \
                                   | I2C_RX_INT_ENABLE                  \
                                   | I2C_TX_INT_ENABLE                  )
```

TX/RX/STOP/OVERRUN/BUS_ERROR 모두 인터럽트로 처리 — 폴링 없음, 전적으로 ISR 기반.

### 1.2 호출 흐름 (tdc_touch_iqs323.c → driver_i2c.c)

`i2c_write` (tdc_touch_iqs323.c:47~77):
1. `i2c_startWriteData(...)` 호출 → 드라이버 상태 `i2c_state_WriteTriggered` + `Sys_I2C_StartWrite()` 하드웨어 트리거
2. `while(1)` 스핀 폴링: `get_i2cDriverStatus()` 반환값 확인
3. `i2c_state_WritingDone` → `setI2cDriverStatusIdle()` 호출 후 break
4. `i2c_state_Error` → `init_I2c()` 호출 후 `return false`

ISR이 TX/STOP 이벤트마다 상태를 전진시키고, 호출처(tdc_touch_iqs323.c)가 `get_i2cDriverStatus()`로 스핀하며 완료를 기다리는 구조. **호출처 관점에서는 동기적으로 보이지만 드라이버 내부는 ISR 기반 비동기.**

## 2. 상태 전이 완전 지도

### 2.1 상태 열거 (driver_i2c.h:136~142)

```c
typedef enum
{
    i2c_state_Idle = 0,
    i2c_state_WriteTriggered,
    i2c_state_WritingDone,
    i2c_state_ReadTriggerd,
    i2c_state_ReadingDone,
    i2c_state_Error,
} EN__I2C_DRIVER_STATE;
```

### 2.2 전이 다이어그램 (ISR 모드 기준)

```
Idle
 ├─[i2c_startWriteData: busy==0 && tx_req==1 && line_free==1]──→ WriteTriggered
 ├─[i2c_startReadData:  busy==0 && tx_req==1 && line_free==1]──→ ReadTriggerd
 ├─[i2c_startWriteData: 조건 불만족]──→ Error
 └─[i2c_startReadData:  조건 불만족]──→ Error

WriteTriggered  (ISR에서 처리)
 ├─[stop_detected==1 && bus_error==0 && remainedLen==0]──→ WritingDone
 ├─[stop_detected==1 && (bus_error==1 || remainedLen!=0)]──→ Error
 └─[조건 불만족]──→ WriteTriggered 유지 (i++ 카운트만)

WritingDone     ★DEAD CODE in ISR mode★
 ├─[#ifndef CM3_I2c_using_ISR] WritingDone──→ Idle  (폴링 모드 전용, ISR에선 컴파일 안 됨)
 └─ ISR 모드: WritingDone 상태에서 ISR가 도착해도 switch-default(no-op) → 영구 WritingDone
    (단, tdc_touch_iqs323.c i2c_write가 WritingDone 감지 후 setI2cDriverStatusIdle() 명시 호출 → 정상)

ReadTriggerd  (ISR에서 처리)
 ├─[주소 ACK 수신: clk_stretch==1 && rx_req==0 && addr_data==(어떤 값)]──→ ACK 전송, ReadTriggerd 유지
 ├─[데이터 수신: rx_req==1 && addr_data==0 && remainedLen>1]──→ ACK + 데이터 저장, ReadTriggerd 유지
 ├─[데이터 수신: rx_req==1 && addr_data==0 && remainedLen==1]──→ NACK+STOP, ReadTriggerd 유지
 ├─[stop_detected==1 && bus_error==0 && remainedLen==0]──→ ReadingDone
 ├─[stop_detected==1 && (bus_error==1 || remainedLen!=0)]──→ Error
 └─[조건 불만족]──→ ReadTriggerd 유지 (i++ 카운트만)

ReadingDone     ★DEAD CODE in ISR mode★
 ├─[#ifndef CM3_I2c_using_ISR] ReadingDone──→ Idle  (폴링 모드 전용)
 └─ ISR 모드: ReadingDone 유지 (tdc_touch_iqs323.c i2c_read가 setI2cDriverStatusIdle() 호출)

Error
 └─[ISR 진입 시] Error──→ init_I2c() 호출 → clearI2cDriverStatus() → Idle
```

### 2.3 WritingDone/ReadingDone dead code 상세

`driver_i2c.c` 231~236번줄:
```c
#ifndef CM3_I2c_using_ISR
        case i2c_state_WritingDone:
        {
            ST__I2C_DRIVER.i2c_diver_state = i2c_state_Idle;
        }
        break;
#endif
```

`driver_i2c.c` 295~300번줄:
```c
#ifndef CM3_I2c_using_ISR
        case i2c_state_ReadingDone:
        {
            ST__I2C_DRIVER.i2c_diver_state = i2c_state_Idle;
        }
        break;
#endif
```

`CM3_I2c_using_ISR`이 정의된 상태에서 `#ifndef CM3_I2c_using_ISR` 블록은 컴파일되지 않는다. **ISR 모드에서 `WritingDone`→`Idle`, `ReadingDone`→`Idle` 자동 전이 코드가 존재하지 않는다.** ISR이 `WritingDone` 또는 `ReadingDone` 상태에서 다시 트리거되어도 switch-default(no-op)로 처리되어 상태가 유지된다.

**구제 경로**: `tdc_touch_iqs323.c`의 `i2c_write`(64~69번줄)와 `i2c_read`(95~101번줄)가 각각 `WritingDone`/`ReadingDone` 감지 후 `setI2cDriverStatusIdle()` 명시 호출 → 정상 경로에서 Idle 복귀 보장. 단 이것은 호출처가 반드시 스핀 폴링을 완주해야만 동작한다.

## 3. i2c_startWriteData / i2c_startReadData 진입 조건 및 실패 경로

### 3.1 하드웨어 STATUS 확인 (driver_i2c.c:79~99)

```c
void i2c_startWriteData(const int slaveAddress, int* p_sourcedata, const int dataLength)
{
    OTE_1_5gen_I2C_STATUS_T i2cStatus;
    ...
    i2cStatus.status = getI2cHardwareStatus();   // I2C0->STATUS 직접 읽기

    if ((i2cStatus.fields.busy == 0) && (i2cStatus.fields.tx_req == 1) && (i2cStatus.fields.line_free == 1))
    {
        i2c_driver.i2c_diver_state = i2c_state_WriteTriggered;
        clearI2cHardwareStatus();
        Sys_I2C_StartWrite(I2C0, i2c_driver.slaveAddress);
    }
    else
    {
        i2c_driver.i2c_diver_state = i2c_state_Error;
        i2c_driver.i2c_Error_Code  = I2C_SLAVE_DEVICE_NO_REACTION;
    }
}
```

`i2c_startReadData`도 동일 조건(driver_i2c.c:118):
```c
if ((i2cStatus.fields.busy == 0) && (i2cStatus.fields.tx_req == 1) && (i2cStatus.fields.line_free == 1))
```

**진입 조건**: `busy==0 && tx_req==1 && line_free==1`. 하드웨어가 이 조건을 만족하지 않으면 드라이버 상태 체크(get_i2cDriverStatus Idle 확인)를 통과한 후에도 즉시 `i2c_state_Error`로 간다.

### 3.2 "드라이버 Idle이지만 하드웨어 busy" 경로

`tdc_touch_iqs323.c`의 `i2c_write`/`i2c_read`는 진입 전 소프트웨어 상태만 확인(52~55번줄):
```c
if (get_i2cDriverStatus() != i2c_state_Idle)
{
    return false;
}
```

소프트웨어 상태 Idle → `i2c_startWriteData` 호출 → 하드웨어 STATUS 확인 → `busy==1` (이전 트랜잭션이 하드웨어에서 아직 진행 중이거나 버스 오류) → **`i2c_state_Error` 즉시 전이**.

이후 ISR이 `i2c_state_Error`에서 `init_I2c()` 호출 → `clearI2cDriverStatus()`(소프트웨어 Idle 복귀) + `Sys_I2C_Reset` + 재설정.

단 `init_I2c()` 호출이 **ISR 컨텍스트에서** 일어나며, `Sys_I2C_Reset(I2C0)` 이후 하드웨어가 즉각 line_free가 된다는 보장은 하드웨어 사양에 의존한다. 버스 SDA/SCL이 물리적으로 Low에 묶인 경우(슬레이브 clock stretch 또는 half-byte 수신 후 stuck) `line_free==0`이 유지될 수 있다.

## 4. 0xFF 1바이트 write와 4바이트 read의 드라이버 처리 차이

### 4.1 0xFF 1바이트 write (force_window_open → i2c_write)

`force_window_open` (tdc_touch_iqs323.c:135~161):
```c
static bool force_window_open(void)
{
    uint8_t force_comm = 0xFF;

    if (Sys_GPIO_Read(TDC_TOUCH_IQS323_RDY_PIN) == TDC_TOUCH_IQS323_WIN_OPEN)
    {
        return true;   // RDY Low면 즉시 반환 — i2c_write 호출 없음
    }
    if (!i2c_write(&force_comm, 1))
    {
        return false;
    }
    // 45ms RDY Low 폴링 ...
```

`i2c_write(&force_comm, 1)`:
- `buf[0] = 0xFF`
- `i2c_startWriteData(0x44, &buf[0], 1)`
- ISR 흐름: `WriteTriggered` → TX_DATA=0xFF + I2C_LAST_DATA → stop_detected → `WritingDone`
- 호출처 스핀: `WritingDone` 감지 → `setI2cDriverStatusIdle()` → return true

드라이버 레벨에서 0xFF는 다른 1바이트 write와 동일하게 처리. **하드웨어는 슬레이브 주소(0x44) 뒤에 0xFF를 데이터로 전송하고 STOP.** IC(IQS323)가 이 0xFF를 어떻게 해석하는지는 드라이버 관점 밖의 문제.

### 4.2 2바이트 read vs 4바이트 read

`i2c_read` (tdc_touch_iqs323.c:79~113):
```c
static bool i2c_read(uint8_t *p_buf, int len)
{
    EN__I2C_DRIVER_STATE state;
    int                  buf[4];   /* 최대 4바이트. 호출처 len <= 4 보장 */

    if (len < 1 || len > (int) (sizeof(buf) / sizeof(buf[0])))
    {
        return false;
    }
    ...
    i2c_startReadData(TDC_TOUCH_IQS323_SLAVE_ADDR, &buf[0], len);
    ...
```

`i2c_startReadData`는 `i2c_driver.i2cTxRx_RemaindedDataLength = len`(driver_i2c.c:108)을 설정.

ISR `ReadTriggerd` 처리(driver_i2c.c:261~273):
```c
if ((i2c_driver.i2cTxRx_RemaindedDataLength - 1) == 0)
{
    I2C0->CTRL = I2C_NACK | I2C_STOP;
}
else
{
    I2C0->CTRL = I2C_ACK;
}

*(i2c_driver.p_i2cRx_Destination) = I2C0->RX_DATA;
i2c_driver.p_i2cRx_Destination++;
i2c_driver.i2cTxRx_RemaindedDataLength--;
```

**2바이트 read**: ISR 2회. 1회째: remainedLen=2, (2-1)!=0 → ACK. 2회째: remainedLen=1, (1-1)==0 → NACK+STOP.

**4바이트 read**: ISR 4회. 1~3회: ACK. 4회째: NACK+STOP.

드라이버 구조는 `remainedLen` 카운터로 동적 처리 — **2바이트와 4바이트 사이에 별도 버퍼 한계, FIFO 경계, 코드 분기가 없다.** ISR 호출 횟수가 다를 뿐이며, 메커니즘은 완전히 동일.

**중요 관찰**: `i2c_read` 내부 버퍼 `buf[4]`는 int 배열(4 × 4바이트 = 16바이트). `i2c_startReadData`에 `&buf[0]`와 `len`을 넘기므로 `p_i2cRx_Destination++`가 int 포인터 증가(+4바이트 이동)다. IQS323의 레지스터 자동증가(auto-increment)로 0x13→0x14 순서로 총 4바이트(각 2바이트씩)가 오는데, ISR에서 `*(i2c_driver.p_i2cRx_Destination) = I2C0->RX_DATA`로 int[0]~int[3]에 하나씩 저장된다. 이후 `i2c_read` 반환 전(108~110번줄):

```c
for (int i = 0; i < len; i++)
{
    p_buf[i] = (uint8_t) (buf[i] & 0xFF);
}
```

`buf[i]`는 int(RX_DATA는 1바이트 데이터), `& 0xFF`로 하위 8비트 추출 → uint8_t 배열로 정상 복사. **4바이트 경로에 버그 없음.**

### 4.3 4바이트 read에서 잠재적 타이밍 차이

4바이트 read는 ISR 4회 호출이 필요하므로 버스 점유 시간이 길다. 100kHz 기준 1바이트(9비트) ≈ 90µs → 4바이트 ≈ 360µs. 2바이트는 ≈ 180µs. IC(IQS323)가 각 바이트 전송 후 ACK 응답에 clock stretching을 사용하는 경우 4바이트 구간이 더 길어진다.

**중요**: 드라이버 `ReadTriggerd` 케이스에서 clock stretching 처리는 `clk_stretch==1` 조건 확인으로 이루어진다(driver_i2c.c:244~249):

```c
if ((i2cStatus.fields.bus_error        == 0)
    && (i2cStatus.fields.busy          == 1)
    && (i2cStatus.fields.stop_detected == 0)
    && (i2cStatus.fields.clk_stretch   == 1)   // ← clock stretch 확인
    && (i2cStatus.fields.read_write    == 1)
    && (i2cStatus.fields.rx_req        == 0)
    && (i2cStatus.fields.ack           == 0))
{
    I2C0->CTRL = I2C_ACK;
```

ICQ323가 SCL을 잡고 있을 때(ACK 또는 데이터 준비 중 stretch) ISR이 이 조건으로 처리한다. stretch 기간 동안 추가 ISR이 발생하지 않으면 정상적으로 대기한다. **4바이트 read가 드라이버 레벨에서 특별히 취약한 clock stretch 경로는 없다.**

## 5. '영구 latch' 드라이버 경로 분석

### 5.1 후보 경로_1: i2c_startWriteData에서 하드웨어 busy → Error → init_I2c 후에도 버스 frozen

시나리오:
```
i2c_write(0xFF, 1) [force_window_open 내부]
  → i2c_startWriteData
  → I2C0->STATUS: busy==1 (이전 트랜잭션 잔여)
  → i2c_state_Error 전이
  → ISR 도착 → init_I2c() → Sys_I2C_Reset → clearI2cDriverStatus → Idle
  → i2c_write 스핀: Error 감지 → init_I2c() 한 번 더? [아님]
```

`i2c_write`의 Error 처리(tdc_touch_iqs323.c:70~74):
```c
if (state == i2c_state_Error)
{
    init_I2c();
    return false;
}
```

**중요**: ISR 내 `init_I2c()`(Error case, driver_i2c.c:304)와 스핀 루프 내 `init_I2c()` 두 번 호출 가능성. 그러나 ISR에서 Error→`init_I2c()`→`clearI2cDriverStatus()`→`Idle`이 되면 스핀 루프가 `i2c_state_Idle`을 보게 되는데, `i2c_state_Idle`에 대한 처리가 스핀 루프에 없으므로 무한 스핀이 된다.

**실제 검토**(`i2c_write` 스핀, tdc_touch_iqs323.c:63~76):
```c
while (1)
{
    state = get_i2cDriverStatus();
    if (state == i2c_state_WritingDone)
    {
        setI2cDriverStatusIdle();
        break;
    }
    if (state == i2c_state_Error)
    {
        init_I2c();
        return false;
    }
}
```

ISR이 Error→`init_I2c()`→Idle로 먼저 가버리면 스핀 루프는 `i2c_state_Idle`만 보게 되어 WritingDone도 Error도 아니므로 **무한 스핀**. 단, `i2c_startWriteData`에서 Error로 갔다면 ISR은 `WriteTriggered`가 아닌 `Error` 상태에서 트리거된다. Error ISR은 `init_I2c()`를 호출하고 끝난다 — 이 시점 스핀은 Error 감지 가능.

**타이밍 경쟁**: ISR이 Error→Idle 전이를 마치기 전에 스핀이 Error를 읽으면 `init_I2c()` 두 번 호출 + `return false`. 이후 상태 = Idle. `force_window_open`은 `i2c_write` 실패로 `return false` → `force_window_open` 반환 false. `read_debug` 첫 번째 force_window_open 실패 → `ci_printw("[TOUCH] DEBUG READ FAIL (addr)")` → `return false`. **이 경로는 영구 latch가 아니다** — 다음 tick에서 read_status가 정상 진행하고 버스가 회복되면 재시도 가능.

### 5.2 후보 경로_2: ReadTriggerd 중 윈도우 닫힘 → remainedLen != 0 → Error

4바이트 read 도중 IC가 RDY를 High로 올려(윈도우 닫음) I2C 트랜잭션을 중단하는 경우:

드라이버 `ReadTriggerd` stop_detected 처리(driver_i2c.c:275~283):
```c
else if (i2cStatus.fields.stop_detected == 1)
{
    if ((i2cStatus.fields.bus_error == 1) || (i2c_driver.i2cTxRx_RemaindedDataLength != 0))
    {
        i2c_driver.i2c_diver_state = i2c_state_Error;
        i2c_driver.i2c_Error_Code  = I2C_SLAVE_DEVICE_NO_REACTION;
    }
    else
    {
        i2c_driver.i2c_diver_state = i2c_state_ReadingDone;
        ...
```

4바이트 read 중 2바이트만 수신하고 STOP이 오면(remainedLen=2 ≠ 0) → `i2c_state_Error`. ISR에서 `init_I2c()` 호출. `i2c_read` 스핀: Error 감지 → 또 `init_I2c()` + `return false`.

이것이 **2바이트 read(read_status)에서는 일어나지 않지만 4바이트 read(read_debug)에서 일어날 수 있는 추가 실패 경로**다. IQS323가 4바이트 전부를 auto-increment로 제공하지 않는 레지스터 구간이거나, 3번째 바이트 전송 도중 윈도우가 닫히면 이 경로가 트리거된다.

그러나 이 경우도 Error→init_I2c→Idle 복귀이므로 **드라이버 자체의 영구 latch는 없다.** 다음 read는 Idle에서 재시작 가능.

### 5.3 setI2cDriverStatusIdle 호출 누락 경로

`WritingDone`/`ReadingDone`은 ISR에서 Idle로 자동 전이되지 않는다(§2.3 dead code). `tdc_touch_iqs323.c`의 `i2c_write`/`i2c_read` 외부에서 직접 `i2c_startWriteData`/`i2c_startReadData`를 호출하고 스핀하지 않으면 WritingDone/ReadingDone에서 영구 멈춤 가능. 그러나 현재 코드에서 `i2c_startWriteData`/`i2c_startReadData`는 `tdc_touch_iqs323.c`의 `i2c_write`/`i2c_read` 래퍼를 통해서만 호출되고, 두 래퍼 모두 스핀 후 `setI2cDriverStatusIdle()` 명시 호출 — **누락 경로 없음.**

## 6. read_status(2바이트) 성공 / read_debug(4바이트) 영구 실패 비대칭 — 드라이버 레벨 설명 가능성

### 6.1 드라이버 레벨에서 설명 불가한 이유

드라이버 코드 분석 결과:
- 2바이트/4바이트 read 처리는 `remainedLen` 카운터 차이만 있고 구조적으로 동일.
- 4바이트 read에서 추가로 실패할 수 있는 경로는 "중간 STOP + remainedLen!=0 → Error" 이나, 이것도 Error→Idle 복귀이므로 영구 latch 아님.
- 드라이버 자체 버퍼 한계, FIFO 오버플로, 상태 미복귀 경로 없음.

**드라이버 레벨만으로는 "read_status 매번 성공 / read_debug 매번 실패" 비대칭을 설명할 수 없다.** 드라이버가 정상 복귀하면 다음 read가 성공해야 하고, 실제 read_status가 매 tick 성공하는 것이 이를 뒷받침한다.

### 6.2 비대칭의 실제 원인 (39_판정과 일치)

비대칭의 원인은 드라이버 아래/위 두 층에 있다:

**드라이버 위(응용 레이어)**:
- `read_status` 완료 후 `read_debug`의 첫 번째 `force_window_open`이 RDY High 상태에서 진입 → 0xFF i2c_write 발행 → **IC(IQS323)가 응답하지 않아 45ms timeout**.
- 이 timeout은 `force_window_open` 폴링 루프에서 발생 — `i2c_write` 자체는 성공하고 드라이버는 Idle 복귀.
- 단, `force_window_open` timeout 후 `read_debug`가 early return(tdc_touch_iqs323.c:353~356) → `i2c_write(&reg, 1)`이 실행되지 않으므로 실제 드라이버 Error는 발생하지 않음.

**즉**: 로그 `[TOUCH] DEBUG READ FAIL (addr)`는 드라이버 Error가 아니라 `force_window_open` 내부 45ms 타임아웃 후 `force_window_open`이 false를 반환하고, `i2c_write`(논리곱의 두 번째 항)가 short-circuit으로 실행 안 된 결과다.

```c
// tdc_touch_iqs323.c:353
if (!force_window_open() || !i2c_write(&reg, 1))
{
    ci_printw("[TOUCH] DEBUG READ FAIL (addr) \r\n");
    return false;
}
```

`force_window_open()` false → `||` short-circuit → `i2c_write` 미실행 → 드라이버 상태 Idle 그대로 → `return false`.

**드라이버는 완전 정상 상태다.** 실패는 IC 응용 프로토콜(RDY High 상태에서 0xFF 발행 → IC 무응답)에서 발생한다.

## 7. clock stretching 처리 및 NACK 시 드라이버 행동

### 7.1 clock stretching

`WriteTriggered` 처리(driver_i2c.c:192~209):
```c
if (   (i2cStatus.fields.bus_error      == 0)
    && (i2cStatus.fields.busy           == 1)
    && (i2cStatus.fields.stop_detected  == 0)
    && (i2cStatus.fields.clk_stretch    == 1)   // stretch 시 이 조건으로 처리
    && (i2cStatus.fields.read_write     == 0)
    && (i2cStatus.fields.ack            == 0)
    && (i2cStatus.fields.tx_req         == 1))
{
    if (0 < i2c_driver.i2cTxRx_RemaindedDataLength)
    {
        I2C0->TX_DATA = *(i2c_driver.p_i2cTx_Source++);
        i2c_driver.i2cTxRx_RemaindedDataLength--;
    }
    if (i2c_driver.i2cTxRx_RemaindedDataLength == 0)
    {
        I2C0->CTRL = I2C_LAST_DATA;
    }
}
```

clock stretch는 ISR 진입마다 STATUS를 읽어 `clk_stretch==1`이면 처리. stretch 기간이 ISR 호출 없이 지나가지 않는다(하드웨어가 stretch 해제 시 ISR 재트리거). **드라이버 레벨에서 clock stretch로 인한 타임아웃 없음** — 무한 대기 가능하나 워치독(3.28s)이 상한.

슬레이브 NACK(bus_error 또는 ACK absent)는 `stop_detected==1 && bus_error==1` 경로 → `i2c_state_Error`.

### 7.2 윈도우 닫힘(I2C STOP 외부 발행) 처리

IQS323이 통신 도중 RDY를 High로 올리는 것은 I2C 레벨에서 slave가 STOP을 강제하는 것이 아니다(IQS323은 슬레이브로서 SCL만 stretch할 뿐 SDA를 제어해 STOP을 발행하지 않음). 윈도우 닫힘 후 IC가 ACK를 거부하거나 데이터 전송을 중단하면 master(CM3)는 bus_error를 받거나 tx_req가 변하지 않는 상태에 빠진다. 이 경우 `WriteTriggered`/`ReadTriggerd`에서 `else { i++; }` 분기(driver_i2c.c:226, 290)로 ISR 카운트만 증가하고 상태가 진행되지 않는다 — 이것도 워치독 상한까지 대기.

## 8. 종합 — 규명 5항목 답변

| 항목 | 결론 |
|---|---|
| **1. 동기/비동기** | ISR 기반 비동기. `#define CM3_I2c_using_ISR`(h:9)로 `I2C_0_IRQHandler` 활성. 호출처는 스핀 폴링으로 동기적으로 대기. |
| **2. 4바이트 read 차이** | 드라이버 내부 `remainedLen` 카운터만 차이 — 2바이트/4바이트 동일 ISR 코드 경로. 별도 버퍼/FIFO 한계 없음. 4바이트 read에서 추가 실패 가능 경로: STOP 수신 시 remainedLen!=0 → Error. 이것도 Error→Idle 복귀, 영구 latch 아님. |
| **3. clock stretching** | `clk_stretch==1` 비트로 ISR 내 처리. stretch 기간 추가 ISR 대기. 드라이버 레벨 타임아웃 없음(워치독 상한). NACK → Error 전이. |
| **4. 영구 latch 후보** | `WritingDone`/`ReadingDone`이 ISR 모드에서 Idle 자동 전이 dead code — 그러나 호출처(`i2c_write`/`i2c_read`)가 `setI2cDriverStatusIdle()` 명시 호출로 구제. `i2c_startWriteData` 진입 시 `busy==1` → Error → init_I2c → Idle이 이론상 경로이나, 이후 정상 복귀됨. **드라이버 자체의 영구 latch 경로는 현재 코드에서 발견 안 됨.** |
| **5. 비대칭(read_status 성공 / read_debug 실패) 드라이버 레벨 설명** | **불가.** 비대칭은 드라이버 위(응용 레이어): `read_debug`의 `force_window_open`이 RDY High에서 0xFF를 발행하고 IC가 45ms 내 RDY Low로 응답하지 않음. 드라이버는 0xFF i2c_write 성공 후 Idle 복귀. `force_window_open` 폴링 루프의 45ms timeout → `read_debug` early return. 드라이버 Error 없음. 1차 원인은 39_판정 결론 그대로: IC 응용 프로토콜 위반(RDY High 상태에서 undefined 0xFF I2C 트랜잭션 발행). |
