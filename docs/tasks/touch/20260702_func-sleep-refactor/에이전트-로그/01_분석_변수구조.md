# 01_분석_변수구조 — `func_sleep()` 지역변수 목록 및 최상단 이동 안전성 검토

## 최상단 이동 시 안전성 검토

**영속 상태 6종(`sleep_ignore`~`ati_error_reboot_cnt`)**: 현재 위치(L95~100)는 이미 루프 진입 직전이며, 그 사이에 이름 충돌·부수효과를 일으키는 코드가 없다. 함수 최상단으로 옮겨도 "루프 시작 전 1회 초기화"라는 의미가 그대로 보존된다. **핵심 회귀 위험은 이 6개를 "매 iteration 재초기화"로 착각해 `while(1)` 바디 안으로 옮기는 것** — 이러면 상태머신(게이트 해제, 재부팅 카운트)이 매 100ms마다 리셋되어 완전히 붕괴한다. 계획 단계에서 "함수 최상단 = 루프 진입 전 1회"임을 명시해야 한다.

**매 iteration 임시 3종(`st`, `ok`, `state`)**: 현재도 루프 바디 안에서 매회 새로 선언되어 즉시 대입되므로, 최상단으로 옮겨 선언만 밖으로 빼고 대입 로직은 그대로 두면 동작 동일하다. 단 하나 짚어야 할 점: `read_status()`가 실패(`ok == false`)할 때 `st`는 현재 "새로 선언된 미초기화 스택 쓰레기값"이지만, 최상단 선언 시엔 "이전 iteration의 stale 값"이 된다. 이 차이가 관측 가능한지 확인한 결과, `state`(즉 `st.pressed` 기반 값)를 소비하는 세 곳(L159, L185, L209)이 전부 `ok && ...`로 게이트되어 있어 `ok == false`일 때 `state`/`st` 값은 어디서도 읽히지 않는다. 따라서 안전하나, **이 `ok` 게이트가 계획·구현 단계에서 실수로 제거되지 않도록** 검증 페르소나(21)가 재확인해야 할 포인트로 남긴다.

## `#if (TDC_TOUCH_DEBUG_PRINT_ENABLE)` 게이트 변수(`dbg`/`delta`/`abs_thr`/`pabs_thr`) 처리안

이 4종은 계산 즉시 소비(같은 블록 내 write-then-read)이므로 최상단 이동 자체는 안전하다. 문제는 게이트 비활성(`TDC_TOUCH_DEBUG_PRINT_ENABLE == 0`) 시 "선언은 있는데 사용이 없는" 미사용 변수 경고다.

**권장안: 게이트를 선언까지 확장.** 즉 "함수 최상단 = 선언이 물리적으로 한 줄에 모여야 한다"가 아니라 "선언 구역이 함수 상단에 위치한다"로 해석하고, 그 구역 안에 아래처럼 조건부 선언 블록을 그대로 둔다.

```c
#if (TDC_TOUCH_DEBUG_PRINT_ENABLE)
tdc_touch_iqs323_debug_t dbg;
uint16_t                 delta;
uint16_t                 abs_thr;
uint16_t                 pabs_thr;
#endif
```

이렇게 하면 게이트 비활성 컴파일 단위에서는 이 변수들이 애초에 **존재하지 않으므로** "미사용 변수" 경고 자체가 발생할 수 없다. 루프 바디 쪽 사용부는 현행대로 동일 매크로로 게이트된 채 남고, 다만 `tdc_touch_iqs323_debug_t dbg;` 같은 인라인 선언 줄만 제거해 최상단에서 선언한 변수를 재사용하도록 고친다.

**비권장 대안**: 게이트 밖에 무조건 선언 후 `(void)dbg;` 류 캐스팅으로 경고를 억제하는 방식은, 게이트가 꺼진 릴리즈 빌드에서도 불필요한 스택 공간을 점유하고 `read_debug()` 호출 구조를 조건부로 유지해야 하는 등 코드가 더 지저분해지며, 이미 프로젝트 전역에서 쓰이는 매크로 게이팅 관례와도 어긋난다. 채택하지 않는다.
