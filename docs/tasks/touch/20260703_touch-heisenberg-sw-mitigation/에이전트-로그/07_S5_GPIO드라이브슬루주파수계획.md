# 07 · S5 — GPIO 드라이브·슬루·주파수계획 (해법 레버 후보)

**TL;DR**: 터치 I2C0 버스 DIO 드라이브가 최고단계(8X)로 고정 유지됨을 코드로 확인 — 이를 4X로 낮추는 것이 근거 기반 1순위 SW-only 후보다. SPI 클럭 주파수 선택은 CM3가 SPI 슬레이브라 e8300 SW로 불가함을 확인해 기각한다. 부수적으로 `fake_func_sleep()` 실측 결과 C1의 "I2C SCL 5.12MHz 초과" 가설이 이 경로에서는 반증됨을 새로 확인했다.

---

## 0. 사전 확인 — 코드 실측으로 C1 가설 일부 갱신

C1(`01_C1_실패메커니즘.md` §3.1)은 "프로파일링이 SYSCLK 30.72MHz를 유지한 채 절전용 I2C 프리스케일(÷6)을 그대로 쓰면 SCL이 5.12MHz로 사양(1MHz) 5배 초과"를 [가설-강, 미확인]으로 제기했다. 본 노드에서 `fake_func_sleep()`(main.c:810~, 은수님이 설명한 "QCC 안 재우고 SYSCLK 유지+BLE" 시나리오와 C2 §11이 지목한 실제 코드)을 직접 읽었다.

```c
// main.c:862~864, fake_func_sleep() 내부
ci_fake_power_sleep();                              // SYSCLK 유지 (30.72MHz)
i2c_set_master_prescale(I2C_MASTER_PRESCALE_240);   /* 본래 노말 모드 설정 그대로 */
```

**[확립, 코드 직접 확인]**: `fake_func_sleep()`은 SYSCLK를 낮추지 않는 대신, I2C 프리스케일도 **정상모드와 동일한 240**(30.72MHz/240=128kHz)으로 명시적으로 되돌린다. 즉 C1 §3.1이 우려한 "클럭은 높은데 프리스케일은 절전용" 조합은 이 경로에 **존재하지 않는다** — 그 가설은 이 경로에 한해 반증. (별개로, 진짜 `func_sleep()`의 "÷6=426.7kHz vs 의도 ÷21=121.9kHz" FIXME는 여전히 유효하지만 SYSCLK도 같이 2.56MHz로 내려가 있어 5.12MHz 시나리오와는 무관 — main.c:1221 주석·§3 동일 확인.)

**함의**: I2C SCL 주파수 자체는 프로파일링과 평시 정상모드에서 **동일(128kHz)** — "I2C가 비정상적으로 빨라져서" 깨진다는 설명은 약해졌다. 반면 **DIO 드라이브 강도(전극 결합에 영향)는 평시·프로파일링 구분 없이 상시 8X 최고값**이라는 사실은 그대로 유효하며(§1), 오히려 "왜 하필 프로파일링만 깨지는가"의 차이는 I2C 자체보다 SPI/BLE 트래픽·QCC 활성 쪽에 있을 가능성이 커진다(C1 §3 SPI 애그레서 가설과 정합, 판단은 C1/오케스트레이터 몫).

## 1. e8300 SW 지렛대 지도 — 실제로 조정 가능한 것

| 대상 | 현재값(코드 확인) | 적용 함수·위치 | 부팅 후 재설정 여부 |
|---|---|---|---|
| 터치 I2C0(SCL/SDA) DIO 드라이브 | **`DIO_8X_DRIVE`**(+LPF_ENABLE+NO_PULL) — `I2C_PIN_CFG_VAL_forDIO` | `Sys_I2C_DIOConfig(I2C0,...)`, `ci_dio.c:76`(`ci_dio_configure_normal()`) | **없음** — 부팅 1회, `func_sleep()`/`fake_func_sleep()` 모두 미재설정 |
| SPI1(QCC/NRF CLK·CS·MOSI·MISO) DIO 드라이브 | **`DIO_2X_DRIVE`**(+LPF_DISABLE+WEAK_PULL_UP) — `SPI_DIO_PIN_CFG` | `Sys_SPI_DIOConfig(SPI1, SPI_SELECT_SLAVE,...)`, `driver_SPI.c:256`(`init_cm3_SPI()`) | 없음 — 부팅 1회(재부팅 시 `Initialize()` 재실행으로 동일값 재적용) |
| IQS323 RDY 핀 드라이브 | OUTPUT `DIO_2X_DRIVE` / INPUT `DIO_1X_DRIVE` | `tdc_touch_iqs323.h:38~39`, `.c:476~479`(MCLR 시퀀스에만 OUTPUT 전환) | 없음(매크로 고정) |
| I2C SCL 주파수(프리스케일) | 노말·프로파일링(`fake_func_sleep`) 128kHz / 진짜 절전 426.7kHz(FIXME) | `i2c_set_master_prescale()`, `driver_i2c.c:145` | **런타임 재설정 가능**(유일하게 이미 동적) |
| **SPI 클럭 주파수/비트레이트** | **CM3는 SPI1 슬레이브**(`SPI_SELECT_SLAVE`) | `driver_SPI.h`, `driver_SPI.c:256` | **e8300 SW로 조정 불가** — NRF/QCC가 마스터로 SCLK 생성 |

**핵심 제약 확인 [확립]**: `Sys_SPI_DIOConfig(SPI1, SPI_SELECT_SLAVE, ...)`가 명시하듯 CM3는 SPI1에서 **슬레이브**다. SPI 비트레이트는 상대(QCC/NRF, board.h 주석 "NET: QCC_SPI_CLK")가 결정하며 e8300 FW·레지스터로는 손댈 수 없다. 따라서 초점에 제시된 "SPI 클럭 주파수 선택" 자체는 **e8300 단독 SW-only 범위에서 실현 불가**로 확인한다(억지로 후보화하지 않음). 남는 것은 (a) CM3 자신이 구동하는 MISO 엣지의 드라이브/슬루(§3 후보_2), (b) e8300이 실제로 마스터인 I2C 쪽 주파수·드라이브(§3 후보_1, §3 후보_4)뿐이다.

**IQS323 쪽 확인**: 데이터시트 §6(하드웨어설정) 원문 어디에도 I2C/RDY 핀 자체의 드라이브·슬루레이트 SW 레지스터는 없다(Inactive Rxs·Prox Control·Engine Bias·Dead Time·Charge Transfer Freq·Reset만 존재). **드라이브/슬루 레버는 전적으로 e8300 DIO 페이스 쪽에만 존재**하는 것으로 확인된다[확립, 03_하드웨어설정.md 전문 대조].

**드라이브 강도값의 절대 의미 [미확인]**: `DIO_1X/2X/4X/8X_DRIVE`의 실제 mA 값은 벤더 SDK 헤더(`sk5_hw_cid101.h` 계열, 본 저장소에 미포함, `driver_i2c.h` 주석에서 존재만 언급)에 정의되어 있어 이 세션에서 확인 불가. 코드 전반의 사용 패턴(입력·저속 용도엔 1X, 활성 마스터 버스엔 8X)으로 볼 때 1X<2X<4X<8X 순으로 강도가 커진다는 것은 명명 규칙상 사실상 확실하나, 절대 전류값·정확한 슬루 개선 폭은 실측/SDK 확인 필요.

## 3. 후보 상세

### 후보_1 — 터치 I2C0 DIO 드라이브 하향 (8X → 4X, 1차)

- **메커니즘**: `Z_결합=1/(2π·f·C기생)`(관측교란.md §4 메커니즘_1)에서 결합 전하량은 `C기생×ΔV`뿐 아니라 실제로는 엣지의 dV/dt(고주파 성분)에 비례한다. 드라이브 강도를 낮추면 동일 부하 커패시턴스 대비 상승/하강 시간이 늘어나(슬루 완만화) 엣지의 고주파 하모닉 에너지가 줄어 결합 전하가 감소한다. 이 버스(I2C0 SCL/SDA)는 CM3가 IQS323과 직접 통신하는 유일한 경로이자, C1이 지목한 두 자체발견(§3.1 SCL 스펙, §3.2 `read_debug()` 추가 트랜잭션) 모두가 물리적으로 통과하는 신호선 — 전극(CRX0)과 가장 가까운 반복적 스위칭원 중 하나로 추정된다[가설-강, PCB 인접도 실측 미확인].
- **필요 변경**: `2__cm3/99_includeBoard/DIO_PIN_Config.h:54`의 `I2C_PIN_CFG_VAL_forDIO`를 `(DIO_8X_DRIVE | DIO_LPF_ENABLE | DIO_NO_PULL)` → `(DIO_4X_DRIVE | DIO_LPF_ENABLE | DIO_NO_PULL)`. IQS323 레지스터 변경 없음. 매크로 1줄, 코드 로직 변경 0줄.
- **근거 있는 대안**: 이미 정의돼 있으나 미사용(dead code)인 `CM3_I2C_MASTER_PIN_CFG_VAL = (DIO_4X_DRIVE | DIO_LPF_ENABLE | DIO_1K_PULL_UP)`(DIO_PIN_Config.h:61)를 재사용하는 방법도 있으나, 이는 `NO_PULL→1K_PULL_UP`까지 동시에 바꾸는 **두 변수 동시 변경**이 되어 순수 드라이브 단독 실험이 아니게 된다 — 위 권장안(드라이브만 4X로, PULL은 NO_PULL 유지)이 더 통제된 변경이다.
- **주의**: 이 I2C0 버스는 IQS323 전용이 아니라 PMIC(ISL9122)·가속도계(MIS2DH) 등도 함께 얹혀 있을 가능성이 있는 공용 버스로 보인다(동일 `Sys_I2C_DIOConfig(I2C0, ...)` 단일 호출로 SCL/SDA 전체를 설정, `i2c_startWriteData/ReadData` 하나의 드라이버로 전 슬레이브 공용). 드라이브 하향은 **터치 8개 불변식 범위 밖의 부수 영향**(PMIC/가속도계 통신 여유도)까지 걸치므로, C2 체크리스트 통과와 별개로 그쪽 통신 신뢰성도 확인 필요[미확인].

### 후보_2 — SPI1(QCC/NRF) DIO 드라이브 하향 (2X → 1X)

- **메커니즘**: 후보_1과 동일 논리를 SPI1(board.h 주석상 물리 net명 `QCC_SPI_CS/CLK/MOSI/MISO`)에 적용. CM3는 슬레이브라 CLK·CS·MOSI는 QCC/NRF가 구동(입력)하지만, **MISO는 CM3가 구동**하는 유일한 출력이며 `Sys_SPI_DIOConfig()`는 4핀을 단일 설정값으로 묶어 적용하므로 MISO의 드라이브를 낮추려면 CLK/CS/MOSI도 같은 값으로 낮아진다(구조상 개별 분리 불가, `driver_SPI.c:256` 함수 시그니처 확인).
- **필요 변경**: `DIO_PIN_Config.h:13`의 `SPI_DIO_PIN_CFG`를 `(DIO_2X_DRIVE | DIO_LPF_DISABLE | DIO_WEAK_PULL_UP)` → `(DIO_1X_DRIVE | DIO_LPF_DISABLE | DIO_WEAK_PULL_UP)`.
- **한계**: CLK·CS·MOSI는 QCC/NRF가 구동하는 입력 핀이라, CM3 쪽 드라이브 강도 설정이 그 신호들의 실제 엣지 속도에 영향을 주는지 자체가 불확실하다(입력으로 구성된 핀에 "드라이브"값이 어떤 의미를 갖는지는 이 저장소에 문서화되어 있지 않음)[미확인] — 확실히 영향받는 것은 MISO뿐일 가능성이 있다. 즉 이 후보의 실효 저감 범위는 후보_1보다 좁을 수 있다.
- **주의**: SPI1은 터치 전용이 아니라 BLE 매핑·페어링·OTA 등 QCC/NRF 전 기능이 공유하는 버스다(`ble_communication.c`, `mappingControl.c`, `remoteControl.c`, `ci_ble_control_ota.c` 등 전부 `driver_SPI.h` 포함) — 드라이브를 과도히 낮추면 터치와 무관하게 BLE/OTA 신뢰성에 영향을 줄 수 있어, 회귀 확인 범위가 C2의 8개 터치 불변식 밖까지 넓어진다.

### 후보_3 — IQS323 RDY 핀 출력 드라이브 하향 (2X → 1X, 부차)

- **메커니즘**: `TDC_TOUCH_IQS323_RDY_PIN_CFG_OUTPUT`(2X)는 MCLR 하드리셋 시퀀스에서만 짧게 쓰이고(`tdc_touch_iqs323.c:476~479`), 평상시 폴링(100ms마다 `read_status()`)에는 항상 INPUT(이미 1X, 최저값)으로 IQS323이 구동하는 신호를 읽기만 한다. 즉 CM3가 이 핀에 반복적 스위칭 애그레서를 얹는 경우 자체가 드물다(MCLR은 예외적 이벤트).
- **필요 변경**: `tdc_touch_iqs323.h:38`의 `TDC_TOUCH_IQS323_RDY_PIN_CFG_OUTPUT`을 2X→1X.
- **평가**: 변경은 안전하지만(INV-⑦-1이 이미 "노말·절전 양쪽 동시 적용" 명시, 회귀 위험 낮음) **효과는 미미**하다고 솔직히 평가한다 — 상시 반복 애그레서가 아니므로 메커니즘_1 저감 기여가 후보_1·2 대비 작다. "손대는 김에 정리" 수준의 낮은 우선순위 후보.

### 후보_4 — I2C 프리스케일 방어 코드화 및 진짜 절전 FIXME 정정 (낮은 우선순위, 프로파일링 직접 원인 아님)

- **배경**: §0에서 확인했듯 `fake_func_sleep()`의 I2C 프리스케일(128kHz)은 이미 정상이라 이 자체가 프로파일링 실패의 원인은 아니다. 다만 (a) 매직넘버 `I2C_MASTER_PRESCALE_240`을 SYSCLK 실측값에서 역산하는 헬퍼로 바꾸면 향후 누군가 `ci_fake_power_sleep()`을 다른 클럭값으로 바꿀 때도 SCL이 자동으로 사양(1MHz) 이내로 유지되는 회귀 방지 효과가 있고, (b) 진짜 `func_sleep()`의 `I2C_MASTER_PRESCALE_6`(426.7kHz, 의도 121.9kHz)는 관측교란.md 메커니즘_1과 직결되는 기존 미해결 FIXME이므로 `I2C_MASTER_PRESCALE_21`로 정정하면 **진짜 절전** 중 결합 전하도 줄어드는 부가 이득이 있다(단, 이는 "프로파일링"이 아닌 "정상 절전" 경로 개선이라 이번 문제의 직접 해법은 아님 — C2 §7 인용).
- **필요 변경**: `main.c:1223`의 `I2C_MASTER_PRESCALE_6` 주석 처리된 의도값 `_21`로 교체(1줄, 기존 FIXME 주석이 이미 정정안을 명시해 둠). `fake_func_sleep()` 쪽은 SYSCLK 상수를 참조해 프리스케일을 계산하는 인라인 함수/매크로 추가(수 줄).
- **평가**: 근거는 있으나(§0 재확인), **본 프로파일링 실패의 1차 원인 후보는 아니다** — 억지로 "메커니즘_3 회피"로 포장하지 않는다. IQS323 변환주파수(1MHz, 0x31 추정치[미확인])와 I2C 128kHz/121.9kHz 사이 정수배 관계 여부도 확인하지 않았다(에일리어싱 실질 기여는 [가설-불확실]).

## 4. C2 불변식 8개 영향 매트릭스 (가장 중요)

## 핵심 결론 (3~5줄)

1. 실제 코드 확인 결과 **터치 I2C0 버스 DIO 드라이브가 최고단계(8X)로 부팅 시 1회 고정되어 프로파일링 내내(그리고 평시에도) 유지**됨을 확인했다 — 이를 4X로 낮추는 것(`DIO_PIN_Config.h:54` 1줄)이 메커니즘_1 근거가 가장 강한 1순위 SW-only 후보다.
2. SPI1(QCC/NRF) 드라이브 하향(2X→1X)은 2순위이나, CM3가 SPI 슬레이브라 **"SPI 클럭 주파수 선택" 자체는 e8300 SW로 실현 불가**함을 코드로 확정했다 — 초점에 제시된 항목 중 이 부분은 기각한다.
3. 부수적으로 `fake_func_sleep()`(사용자가 설명한 프로파일링 시나리오와 정확히 일치하는 코드 경로) 실측 결과, C1이 제기한 "I2C SCL 5.12MHz 초과" 가설은 **이 경로에서는 반증**되었다 — 프리스케일이 이미 정상모드와 동일(128kHz)로 맞춰져 있어, "I2C가 비정상적으로 빨라서" 깨진다는 설명력은 약하다. 이는 C1/오케스트레이터의 재종합이 필요한 새 사실이다.
4. 생성한 4개 후보 전부 C2의 8개 불변식을 **직접 위반(충돌)하지는 않는다** — 다만 ③·④·⑦(ATI에러/터치판정/공통폴링)에서 "통신 마진 자체가 변경되는가"라는 동일 성격의 실측 필요 유보가 반복되며, 이는 코드 재검토가 아니라 벤치 계측으로만 해소 가능하다.
5. 모든 후보는 매크로 값 1줄 수준의 최소 침습 변경이라 구현 리스크는 낮으나, **저감 효과의 정량적 크기는 코드·데이터시트 조사만으로 확정할 수 없다** — "재부팅이 멈추는가"는 실측 게이트를 통과해야 답할 수 있는 질문이다.
