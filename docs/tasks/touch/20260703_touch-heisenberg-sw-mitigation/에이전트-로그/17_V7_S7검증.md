# 17 · V7 — S7 검증 (관측 방식 재설계 5종 반증)

**TL;DR**: S7 후보_1의 근거인 "발견_1"(TIMER3가 1ms tick으로 게이팅되어 관측 루프가 실제로 ~1kHz 실행)을 코드로 직접 대조한 결과 **반증**된다 — `fake_func_sleep()`·`func_sleep()` 둘 다 ULP 루프 진입 직전 동일한 `ci_timer_init_prescaled(TDC_TOUCH_ULP_TIMER_PRESCALE, TDC_TOUCH_ULP_TIMER_TIMEOUT_VALUE)`로 **TIMER3 그 자체를(별도 타이머 아님)** 100ms 등가로 재설정하며, SLOWCLK도 세 전력모드(노말·진짜절전·페이크절전) 전부 1.28MHz로 보정되어 있어 관측 루프는 이미 ~100ms 주기로 동작 중이다. 이는 후보_1의 핵심 수치 주장("최대 100배 감소")을 근거 소멸시키고, 오히려 이 (틀린) 전제를 믿고 "tick=1ms"로 오인해 새 카운터를 구현하면 **FSM 판정이 100배 느려지는(10초 주기) 심각한 회귀** 위험이 새로 드러난다. 후보_3(BLE 레이트리밋)·후보_4(RTT)는 발견_1과 무관해 상대적으로 견고하나, 후보_4는 "BLE 프로파일링을 RTT로 대체"가 측정 대상 자체를 바꾼다는 운용 정합성 문제가 남는다.

## 1. 결정적 반증 — "발견_1"(TIMER3 1ms 게이팅설)을 코드로 직접 대조

### 1.1 09번 노드의 주장

> "`fake_func_sleep()`의 관측 루프는 `TDC_TOUCH_ULP_TIMER`(100ms, HW)가 아니라 TIMER3의 1ms tick 변화 여부로 게이팅된다 ... TIMER3는 '1ms 주기' 명시... 로 ... 어디서도 disable되지 않는다." (09번 §0 발견_1, 근거: main.c:887~899, ci_timer.c:19~29, initialize.c)

이 주장은 **"TDC_TOUCH_ULP_TIMER"가 TIMER3와 별개의 하드웨어**라는 암묵적 전제 위에 있다. 코드로 직접 대조한 결과 이 전제가 틀렸다.

### 1.2 반증 증거 사슬 (전부 [확립: 코드])

| 단계 | 사실 | 근거 |
|---|---|---|
| ① 유일한 HW 타이머 | `TDC_TOUCH_ULP_TIMER_PRESCALE`/`TIMEOUT_VALUE`가 넘겨지는 함수(`ci_timer_init_prescaled`)는 `OTE_1_5_GEN_TIMER_INSTANCE`(=**TIMER3**, `TIMER_3_IRQn`)만 조작한다. "TDC_TOUCH_ULP_TIMER"라는 별도 물리 타이머는 존재하지 않는다 — 이름만 다를 뿐 **동일한 TIMER3 레지스터를 재설정하는 것** | `ci_timer.h:18~19` `#define OTE_1_5_GEN_TIMER_INSTANCE TIMER3` / `ci_timer.c:153~166` `ci_timer_init_prescaled()` 구현이 `Sys_Timer_Stop/Config/Start(OTE_1_5_GEN_TIMER_INSTANCE, ...)`만 호출 |
| ② 부팅 시 1ms 설정 | `initialize.c:280` `ci_timer_init(OTE_1_5_GEN_TIMER_TICK_1MS_PM_NORMAL)` — 주석 "TIMER3 ISR 활성 (1ms tick)". `ci_timer_init(tick)`은 내부적으로 `ci_timer_init_prescaled(TIMER_PRESCALE_1, tick)` 호출(`ci_timer.h:56~57` 주석) | `initialize.c:279~281`, `ci_timer.h:56~58` |
| ③ **ULP 진입 시 재설정** — 여기가 09번이 놓친 지점 | `fake_func_sleep()`(main.c:**868**)와 `func_sleep()`(main.c:**1224**) 둘 다, ULP `while(1)` 루프 시작 **직전**(각각 line 894/1233의 게이팅 조건보다 위)에 **동일한** `ci_timer_init_prescaled(TDC_TOUCH_ULP_TIMER_PRESCALE, TDC_TOUCH_ULP_TIMER_TIMEOUT_VALUE)`를 호출 — 즉 **동일 레지스터(TIMER3)를 다시 프로그램**한다 | main.c:868 `/* ? 200 ms 주기 */`(주석은 낡았으나 매크로는 최신), main.c:1224 `/* 100.0ms 정확 (tdc_touch_time.h 공식 확인) */` |
| ④ 그 결과값이 100ms라는 근거 | `tdc_touch_time.h:51~56` 자체 주석: "T[ms] = PRESCALE분주 × (TIMEOUT+1) / 40(SLOWCLK 40kHz) ... PRESCALE_1 × (3999+1) / 40 = 4000/40 = **100.0ms 정확 일치**". `ci_timer.h:60~64` 주석도 동일 공식을 "긴 주기 타이머(예: ULP 모드 500ms)용"이라고 **명시적으로 이 용도라고 밝힘** | `tdc_touch_time.h:51~56`, `ci_timer.h:60~64` |
| ⑤ 프리스케일 비율로 재확인(외부 가정 불필요) | 부팅 1ms 설정의 tick=**39**(`OTE_1_5_GEN_TIMER_TICK_1MS_PM_NORMAL`, PCM_CLK_SRC_USRCLK 분기), ULP 설정의 tick=**3999**. 두 호출 모두 동일 prescale_field(`TIMER_PRESCALE_1`)이므로 절대 클럭값을 몰라도 **비율만으로 100배**: (3999+1)/(39+1) = 4000/40 = **정확히 100** | `ci_timer.h:22~23`, `tdc_touch_time.h:55~56` |
| ⑥ SLOWCLK가 세 모드에서 전부 동일 — 위 ④·⑤ 계산이 `fake_func_sleep()`에도 그대로 성립함을 보증 | 노말(`SLOWCLK_PRESCALE_24`, SYSCLK 30.72MHz) → 1.28MHz / 진짜절전 `ci_power_sleep()`(`SLOWCLK_PRESCALE_2`, SYSCLK 2.56MHz) → 1.28MHz / **페이크절전** `ci_fake_power_sleep()`(`SLOWCLK_PRESCALE_24`, SYSCLK 30.72MHz **유지**) → 1.28MHz — **셋 다 정확히 1.28MHz로 보정**되어 있다 | `ci_power.c:148~161`(normal), `:163~174`(fake_power_sleep), `:176~184`(power_sleep) — D_CLK->CFG_1 레지스터 3종 직접 대조 |

**결론**: `fake_func_sleep()`은 `func_sleep()`과 **동일한 TIMER3 재설정 호출·동일한 SLOWCLK 1.28MHz**를 쓴다. C1 노드가 이미 `func_sleep()`에 대해 "100ms 웨이크... 정확히 100.0ms 확인"(01번 §2.1)이라고 명시했고, C2 노드도 §8 INV-⑦-3에서 "절전=HW 타이머 인터럽트 100ms"라고 이미 적어두었다 — **본 검증에서 그 사실이 `fake_func_sleep()`에도 동일하게 적용됨을 SLOWCLK 대조로 직접 확인**했다. 09번의 "관측 루프가 ~1kHz로 실행되고 있을 개연성"은 **같은 리포지토리, 같은 두 함수 안에서 스스로 반증**되는 주장이며, 09번이 인용한 main.c:887~899 범위가 바로 위 line 868(fake_func_sleep) / line 1224(func_sleep)의 재설정 호출을 누락한 데서 비롯된 코드 추적 공백으로 판단된다.

> [!WARNING]
> 09번은 stage1에서 "01·02 노드를 읽고" 후보를 도출한다고 편성(00번 §Explore+Verify)돼 있었음에도, C1이 이미 명시한 "정확히 100.0ms 확인"(01번 §2.1)과 C2가 이미 명시한 "절전=HW 타이머 인터럽트 100ms"(02번 §8 INV-⑦-3)를 발견_1이 정면으로 반박하면서도 그 모순을 언급하지 않았다 — 파이프라인 내부 정합성 결여.

### 3.1 신규 발견 — "발견_1을 참으로 믿고 구현"하면 생기는 역방향 회귀

09번은 후보_1을 "터치 read만 `TDC_TOUCH_ULP_WAKE_MS`(100) 경과를 명시 검사하는 게이트로 재구성 ... `tdc_touch_time.h`의 `TDC_TOUCH_ULP_WAKE_MS` 재사용"이라고 서술했다. 만약 구현자가 (반증된) 발견_1을 사실로 믿고 "t3_tick 1증가 = 1ms"라는 가정으로 "100회 tick 누적 시 실행" 식 카운터를 짠다면 — 실제로는 **1 tick이 이미 100ms**이므로 새 카운터는 **100 × 100ms = 10초**마다 실행되는 결과를 낳는다. 이는:

- 터치 FSM 입력(read_status) 주기가 100ms → **10초**로 100배 느려짐 → ④ 터치판정 반응성 붕괴.
- ati_error 5회 재시도 문턱(의도 ≈500ms)이 **50초**로 늘어남 → ③ Re-ATI 복구가 사실상 무력화.
- 게이트 해제 후 터치 24연속(의도 2400ms) 문턱이 **40분**으로 늘어남 → ⑤·⑥ 재부팅 안전망(하이젠베르크 교란이 실제 발생했을 때 마지막 방어선) 자체가 사실상 사라짐.

이는 09번 원문이 명시적으로 지시한 결과는 아니지만("ms 재사용"이라는 표현 자체는 올바름), **발견_1의 서술("1ms tick 게이팅") 자체가 구현자를 이 오인으로 유도할 개연성이 높다** — 잘못된 진단이 낳을 수 있는 실장 위험으로 반드시 별도 경고가 필요하다. **결론: 후보_1은 (a)에서 이미 반증되었으므로 채택 자체를 권고하지 않으며, 혹시라도 구현을 강행할 경우 "ms 카운터는 반드시 절대시간(예: `ci_timer_get_tick()`류 SW ms 틱) 기반이어야 하고 `tdc_timer_get_t3_tick()` 증가량을 1ms로 취급하면 안 된다"는 조건을 명시해야 한다.**

## 6. 후보_4 관련 신규 지적 — "관측 채널 교체"가 측정 대상 자체를 바꾼다

09번은 후보_4를 "BLE 요청 자체를 끄거나 최소화"하는 운영 정책으로 제안한다. 그러나 은수님의 원 문제 정의는 "**BLE·SPI로 터치 상태를 프로파일링**할 때"의 교란이다. 만약 실제 현장/양산 진단 절차가 **무선(BLE)** 프로파일링을 요구하는 것이라면(유선 디버그 프로브가 배제된 시나리오), RTT로 전환하는 순간 유선 SWD 프로브가 상시 부착되어야 하므로:

1. 애초에 재현하려는 "BLE+SPI 프로파일링" 시나리오 자체를 검증할 수 없게 되고,
2. SWD 프로브 부착 자체가 §1(관측교란.md)의 **경로_1(접지 결합)**을 새로 끌어들일 수 있다(디퍼런셜 프로브가 아닌 한).

따라서 후보_4는 "실험실 코드 검증용 저교란 채널"로는 유효하나, "**양산 진단/현장 프로파일링 대체**"로는 09번이 다루지 않은 새로운 트레이드오프가 있다 — 09번의 "효과 크기 미확인" 리스크에 이 운용정합성 문제를 추가해야 한다.

## 7. refuted 판정 요약

- **후보_1**: **refuted** — 핵심 근거(발견_1)가 코드 대조로 직접 반증됨. "실제 저감"이 존재하지 않고, 오히려 나이브 구현 시 100배 역방향(둔화) 회귀를 유발할 잠재 위험이 새로 확인됨. 채택 비권고.
- **후보_2**: **조건부** — 발견_1 의존 부분(수치 과장)은 재작성 필요하나 메커니즘 자체(저빈도 배치)는 독립적으로 살아있음. SRAM/패킷 크기 미확인 게이트 여전.
- **후보_3**: **생존, 가장 견고** — 발견_1과 무관, 자기완결적, 회귀 위험 최저.
- **후보_4**: **조건부** — 방향은 맞으나 효과크기·PCB인접도 미확인 + 신규 지적(운용정합성) 존재.
- **후보_5**: **조건부/보강 성격 유지, 근거 더 약화** — 상위 후보_1 붕괴로 "얹을 대상"이 후보_2로 축소.

## 핵심 결론 (3~5줄)

1. S7 노드의 가장 신뢰도 높다고 자평된 근거(발견_1: "관측 루프가 TIMER3 1ms tick에 게이팅되어 실제 ~1kHz")는 코드 직접 대조로 **반증**된다 — `fake_func_sleep()`·`func_sleep()` 모두 ULP 루프 진입 직전 동일한 `ci_timer_init_prescaled(TDC_TOUCH_ULP_TIMER_PRESCALE, TDC_TOUCH_ULP_TIMER_TIMEOUT_VALUE)`로 **같은 TIMER3**를 100ms 등가로 재설정하며, 세 전력모드(노말·진짜절전·페이크절전) SLOWCLK가 전부 1.28MHz로 일치해 이 계산이 `fake_func_sleep()`에도 그대로 적용된다.
2. 이 반증으로 **후보_1**("최대 100배 감소")은 근거를 잃는다 — 관측 루프는 이미 설계 의도대로 ~100ms 주기이며, ati_error/notouch/롱터치 디바운스도 이미 의도한 시간창으로 동작 중이다(훼손된 적이 없다). 오히려 이 틀린 전제를 믿고 "tick=1ms"로 구현하면 FSM 판정이 10초 주기로 100배 느려지는 **신규 심각 회귀**가 생길 수 있어 채택하지 않을 것을 권고한다.
3. **후보_3**(BLE 응답 레이트리밋)은 발견_1과 무관한 독자 근거(GD option=1 요청-응답 구조, 본 검증에서 코드 재확인)를 가져 5개 후보 중 가장 견고하며, 조건부 채택을 검토할 만하다.
4. **후보_2**(배치 텔레메트리)는 수치 주장만 정정(100ms 기준 20~50배 저빈도화)하면 방향은 유효하고, C2 불변식 8종 전부 무손상이 유지된다. **후보_4**(RTT)는 저침습성 자체는 타당하나 "BLE 프로파일링 대체"가 측정 대상을 바꾼다는 새 지적이 있어 "실험실 검증용" 한정으로 좁혀야 한다.
5. C1·C2가 이미 명시한 사실("정확히 100.0ms 확인", "절전=HW 타이머 인터럽트 100ms")과 09번의 발견_1이 정면 모순되는데도 09번이 이를 언급하지 않은 것은 fan-out 파이프라인 내부 정합성 점검(교차 인용)이 누락된 사례로, 향후 stage1 산출물은 선행 노드의 상반 주장 유무를 의무적으로 대조해야 한다.
