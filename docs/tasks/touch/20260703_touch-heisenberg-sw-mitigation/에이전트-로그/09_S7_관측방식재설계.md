# 09 · S7 — 관측 방식 재설계 (SW-only 후보)

**TL;DR**: 코드 추적으로 `fake_func_sleep()`의 관측 루프가 TIMER3(1ms tick)에 게이팅되어 있어, 의도된 100ms 카덴스가 아니라 **실제로는 ~1kHz로 실행되고 있을 개연성**을 새로 발견했다([가설-강], §0). 이를 근거로 (1) 터치 I2C 폴링을 BLE/SPI1 하우스키핑에서 분리해 100ms로 정합화, (2) 계측 read_debug 배치화, (3) BLE 응답 레이트리밋+이벤트 트리거, (4) 이미 존재하는 RTT 인프라 우선 활용, (5) 관측 타이밍 지터링(위상 고정 회피) — 5개 SW-only 후보를 도출했다. 전 후보 **IQS323 레지스터 변경 0건**(e8300 SW만), C2 불변식 8종 중 ④·⑦만 후보_1에서 "주의" 등급이고 나머지는 전부 무손상이다.

---

## 0. 선행 발견 — 관측 경로 실제 구조 (코드 재확인, C1/C2 범위 확장)

C1/C2가 다루지 않은 세부까지 코드로 직접 추적한 결과, 세 가지 구조적 사실을 새로 확인했다. 이하 후보들의 근거 기반이다.

| 발견 | 근거 | 표기 |
|---|---|---|
| **발견_1**: `fake_func_sleep()`의 관측 루프(read_status+read_debug+bleCommunication)는 `TDC_TOUCH_ULP_TIMER`(100ms, HW)가 아니라 **TIMER3의 1ms tick 변화 여부**로 게이팅된다(`if (last_t3_tick < tdc_timer_get_t3_tick())`, main.c:894). TIMER3는 "1ms 주기" 명시(`ci_timer.c` 주석, `initialize.c` "TIMER3 는 stop 안 함")로 LED arbiter와 겸용이며 어디서도 disable되지 않는다. 반면 노말 모드 `tdc_touch_process()`(tdc_touch.c:296)는 `TDC_TOUCH_POLL_INTERVAL_MS(100) > (now - s_poll_tick_old)` 형태의 **명시적 ms-경과 게이트**를 쓴다. 세 폴링 경로(노말/func_sleep/fake_func_sleep) 중 **fake_func_sleep만 이 패턴에서 벗어나 있다** | main.c:887~899, ci_timer.c:19~29, tdc_touch.c:296 | [가설-강] — TIMER3 실제 프리스케일 레지스터값은 미확인, 정황(주석 2건+타 경로 대조)상 근거는 강함 |
| **발견_2**: "BLE·SPI로 터치 상태를 프로파일링"의 실체는 `EN__SND_BT_CMD_GENERAL_DEBUG`(0x8F) 원격 명령의 **option=1**(`gd_handle_touch_debug`) — **요청-응답형**이다. CM3는 `tdc_touch_debug_get_recent_*()`로 **로컬 폴링 루프가 이미 채워둔 캐시값**을 그대로 실어 12바이트 응답만 만든다. 즉 BLE 트래픽 발생 빈도는 **하네스가 얼마나 자주 요청을 보내는지에 달려 있고 e8300 펌웨어가 직접 정하지 않는다**(C1 "프로파일링 하네스 소스 미확인"과 정합 — 이 요청 주기 자체는 여전히 미확인). 반대로 I2C `read_debug()` 자체는 이 BLE 요청과 **무관하게 로컬 루프 자기 주기로** 실행된다 | tdc_remote_general_debug.c:33~102 | [확립: 코드] |
| **발견_3**: 터치 디버그 프린트(`ci_printd("[T] LTA=...")`)는 이미 **SEGGER RTT** 백엔드다(`SEGGER_RTT_Init()` main.c:313, `RTT_printf` 실사용 확인 ci_ble_control_ota.c). RTT는 일반적으로 타겟이 SRAM 링버퍼에 쓰고 디버그 프로브(J-Link)가 SWD로 **비동기 폴링**하는 구조라 원칙적으로 로그 자체가 별도 GPIO/버스 토글을 만들지 않는다[확립: SEGGER RTT 일반 특성. 단 SWD 핀-CRX0 물리적 이격은 스키매틱 필요, 미확인] | main.c:47,313 / ci_ble_control_ota.c:171~361 | [확립: 코드] + [미확인: PCB 인접도] |

**함의**: 발견_1이 맞다면, 절전 프로파일링 중 애그레서 강도(SPI·클럭)뿐 아니라 **관측 루프 자체의 실행 빈도**가 노이즈 내성 예산을 이미 갉아먹고 있다 — ati_error 재부팅 문턱("5회 초과")이 의도한 ≈600ms가 아니라 ≈6ms 만에 도달할 수 있다는 뜻이다. 이는 "애그레서를 줄이는" 접근과 별개로 "관측 자체의 판정 시간창을 정상화"하는, 순수하게 관측측 버그 정정에 가까운 레버다.

> [!WARNING]
> 발견_1·2는 **C2 §11의 가설(프로파일링=fake_func_sleep 경로)이 맞다는 전제** 위에 있다. 은수님의 실제 프로파일링이 `func_sleep()`(진짜 절전)을 별도 하네스로 변형한 것이라면 후보_1의 대상 코드 자체가 다르다 — 우선 실경로 확인을 권고한다(C2와 동일 요청, 본 노드에서 재확인 필요성 강조).

## 2. 후보_1 — 관측-센싱 폴링 분리 · 카덴스 정합화

**메커니즘**: `fake_func_sleep()` 루프를 "터치 read(read_status, FSM 입력)"와 "계측+BLE 하우스키핑(read_debug, bleCommunication)" 두 갈래로 나누고, **터치 read만** `TDC_TOUCH_ULP_WAKE_MS`(100) 경과를 명시 검사하는 게이트로 재구성한다. bleCommunication()의 호출 빈도는 SPI1/NRF 링크 요구사항이 불확실하므로(§4 리스크) **건드리지 않고 그대로 유지**한다. 효과: 발견_1이 맞다면 read_status/read_debug의 I2C 윈도우 발생률이 최대 ~100배(1kHz→10Hz) 감소 — 메커니즘_1(노출시간·평균결합에너지 ↓)과 메커니즘_2(윈도우 겹칠 기회 자체가 100배 줄어듦) 모두에 직접 작용. 부수적으로 ati_error/notouch 디바운스가 **의도한 시간창(≈600ms~10s)으로 복원**되어, 순간적 글리치가 "충분히 긴 지속"으로 오판되는 취약점이 없어진다.

**필요 변경**: main.c `fake_func_sleep()` 내 `if (last_t3_tick < tdc_timer_get_t3_tick())` 블록을, 터치 read 부분만 별도 ms 누적 카운터(`tdc_touch_time.h`의 `TDC_TOUCH_ULP_WAKE_MS` 재사용)로 분리. IQS323 레지스터 변경 없음. **[미확인]**: TIMER3 실제 프리스케일/클럭소스 값(발견_1의 "1ms" 전제 확정에 필요) — 실측 또는 벤더 SDK 헤더 확인 권고.

**C2 불변식 영향**: ④·⑦ "주의"(§3 표 참조) — read_status 호출 빈도 자체를 바꾸는 유일한 후보라서. 나머지는 무손상.

**실현성·트레이드오프·리스크**: 긍정적이나 조건부(§0 경고 — 실경로 확인 선행 필요). 구현 자체는 소규모(게이팅 조건 교체)이나 "터치 read"와 "BLE 서비스"를 정확히 분리하는 리팩토링 꼼꼼함이 필요하다. 리스크: (a) TIMER3가 실은 이미 다른 방식으로 100ms 등가로 동작한다면(가설이 틀리면) 효과가 없음(코드 명확성 개선 정도만 남음) — 실측 게이트. (b) bleCommunication()을 그대로 1ms로 유지하는 설계이므로 SPI1 자체 리스크는 없으나, 만약 향후 이 서비스도 늦추고 싶어진다면 SPI1 오버런(`SPI_CMMM_ERROR`) 위험 재평가 필요(본 후보 범위 밖, 후보_1은 명시적으로 이 위험을 피하도록 설계함).

## 3. 후보_2 — 배치 텔레메트리(RAM 버퍼링 → 일괄 덤프)

**메커니즘**: `read_debug()`가 채우는 캐시(LTA/Counts/delta/thr/pressed/ati_*)를 매 폴링 즉시-소비 대신, 절전 중 저빈도(예: 1~2초 간격)로 RAM 링버퍼(N샘플)에 누적하고, **신규 GD 서브프로토콜**(예: option=5 "최근 N샘플 버스트 조회")로 기상 시 또는 저빈도 시점에 일괄 응답한다. §0 발견_2로 확인했듯 현재 BLE 응답은 이미 "요청 시 최신 1개 캐시값 반환"이라 하네스가 자주 pull하지 않으면 자연히도 낮은 실효 duty를 갖는다 — 이 후보의 부가가치는 **캐시 갱신 자체(I2C read_debug 호출)를 저빈도화**하고 **응답을 다건 배치로 압축**하는 데 있다.

**필요 변경**: (a) e8300: RAM 링버퍼 자료구조 + read_debug 호출 주기를 후보_1과 별개로 추가 하향(예: 1~2s), (b) `tdc_remote_general_debug.c`에 신규 option 추가(BLE 패킷 포맷 확장, `SPI_COM_PACKET_SIZE` 상한 내 N 결정 필요 — **[미확인]** 패킷 크기 상수). IQS323 레지스터 변경 없음. 선택 사항으로 0xC2(LP Report Rate)를 read_debug 저빈도화에 맞춰 조정하는 것도 고려 가능하나 **필수 아님**(현재 0xC5=0으로 NP 고정 유지 중이라 손대지 않는 편이 안전).

**C2 불변식 영향**: 전부 무손상(§3 표) — read_status 경로·판정 로직·0xC0 write 패턴을 전혀 건드리지 않는다.

**실현성·트레이드오프·리스크**: 조건부 — 오케스트레이터 문구("RAM 버퍼링 후 일괄 덤프")에 가장 직접 대응하지만, 신규 BLE 프로토콜 추가라 **하네스(외부, 소스 미확인)도 함께 바뀌어야 실사용 가능**하다는 점에서 후보_1·3보다 구현·검증 범위가 크다. 가용 SRAM 여유 **[미확인]** — N 크기 결정에 필요. 은수님이 "실시간에 가까운" 프로파일링을 원한다면 배치 지연 자체가 트레이드오프(단, 목적이 "절전 중 터치정보 획득"이지 "즉각성"이 아니라면 문제 없음).

## 4. 후보_3 — BLE 응답 레이트리밋 · 이벤트 트리거 인코딩

**메커니즘**: `gd_handle_touch_debug()`에 "직전 응답 이후 최소 간격 미경과 시 캐시값 재사용(또는 응답 스킵)" 가드를 추가하고, 상태 불변(±작은 delta) 구간에서는 풀 4바이트 대신 압축 상태만 보내는 정책을 검토한다. 하네스가 아무리 자주 pull해도 **firmware측이 자기방어적으로 응답 빈도 상한을 강제**하므로, 후보_1·2 없이도 독립적으로 적용 가능한 안전판이다.

**필요 변경**: `tdc_remote_general_debug.c` `gd_handle_touch_debug()`에 최소-간격 검사 한 줄 추가. IQS323 레지스터 변경 없음.

**C2 불변식 영향**: 전부 무손상 — BLE 응답 레이어만 건드리고 터치 판정/FSM에는 입력도 출력도 없다(§10 INV-X-3과 동일 원리: 계측 전용 경로).

**실현성·트레이드오프·리스크**: 긍정적, 가장 작은 변경. 리스크는 낮음(e8300 단독 자기완결적 — harness 무변경이어도 안전, 응답이 stale하거나 조금 늦어질 뿐). 다만 하네스가 "즉시 응답"을 기대하는 프로토콜이면 타임아웃/재시도를 유발할 가능성 **[미확인: 하네스 타임아웃 정책]**.

## 5. 후보_4 — RTT 우선 관측 채널

**메커니즘**: §0 발견_3대로 RTT 인프라는 이미 존재·사용 중이다. "BLE·SPI 프로파일링"이 GD option=1 폴링만을 가리킨다면(발견_2), 이미 나오고 있는 `[T] LTA=...` RTT 라인만으로 동일 정보를 얻을 수 있어 **BLE 요청 자체를 끄거나 최소화**할 여지가 있다. RTT는 SWD 비동기 폴링 구조상 원칙적으로 타겟측 추가 전기적 스위칭이 없어(확립: 일반 RTT 특성) 이론상 가장 낮은 침습성을 갖는다.

**필요 변경**: 없음(인프라 기 구현) 또는 운영 정책 변경(하네스가 BLE GD 폴링 대신 RTT 로그를 파싱하도록 전환). e8300 코드 변경 최소.

**C2 불변식 영향**: 전부 무손상 — 로깅 채널 선택 문제이지 판정/타이밍 로직 무관.

**실현성·트레이드오프·리스크**: 방향은 긍정적이나 **효과 크기 미확인** — "BLE·SPI로 프로파일링"이 GD option=1 폴링 이외의 별도 커스텀 텔레메트리를 의미할 가능성을 배제 못 함(코드에서 발견 못 함, 미확인). 또한 RTT의 SWD 핀과 CRX0의 실제 PCB 인접도는 스키매틱 확인이 필요(미확인) — "당연히 더 낫다"고 단정하지 않는다. BLE 연결 자체를 다른 목적(원격 제어·기상 커맨드)으로 유지해야 한다면 BLE를 완전히 끌 수는 없고 "응답 폴링만 줄이기"가 현실적 결론(후보_3과 결합).

## 6. 후보_5 — 관측 타이밍 지터링(위상 고정 회피)

**메커니즘**: 후보_1·2로 이미 저빈도화된 관측(read_debug/BLE 서비스) 스케줄에 소폭의 의사난수 지터(±α ms)를 추가해, 그 스케줄이 IQS323 내부 변환/LTA 주기와 우연히 고정된 정수배 관계(메커니즘_3, 에일리어싱/맥놀이)를 맺지 않도록 한다. **범위 한계를 명확히 한다**: "관측 클럭을 센싱에서 분리"의 문자 그대로의 의미(별도 발진기로 물리적 클럭 도메인 분리)는 HW 영역이라 SW-only로는 불가능하다 — e8300과 IQS323은 원래도 서로 다른 물리 발진기를 쓰는 두 개의 칩이므로(이미 비동기), SW로 할 수 있는 것은 "그 비동기 관계가 우연히 정수배로 잠기는 것을 지터로 회피"하는 근사뿐이다.

**필요 변경**: 관측 스케줄 호출부에 소규모 의사난수 가감. read_status()(FSM) 카덴스는 절대 건드리지 않음(고정 100ms 유지). IQS323 레지스터 변경 없음.

**C2 불변식 영향**: 전부 무손상 — read_status 미변경, 판정 로직 무관.

**실현성·트레이드오프·리스크**: 조건부/보강용 — 단독으로는 근거가 약하다(메커니즘_1·2엔 효과 없음, 메커니즘_3에만 유효하며 그마저도 "가끔 더 나쁜 타이밍에 걸릴" 확률도 함께 생김 — 다만 고정 주기가 보장하는 "매번 반복되는 정렬"보다는 평균적으로 낫다는 정도의 논증). 디버깅 시 로그 타이밍 예측이 어려워져 관측 재현성이 다소 떨어지는 부작용도 있다. 독자적 채택보다는 후보_1/2에 얹는 보강 옵션으로 권고.

## 핵심 결론 (3~5줄)

1. §0에서 새로 확인한 사실 — `fake_func_sleep()`의 관측 루프가 의도된 100ms가 아니라 TIMER3의 1ms tick에 게이팅되어 있을 개연성 — 이 맞다면, 절전 프로파일링의 노이즈 취약성 상당 부분은 "애그레서가 세다"가 아니라 "관측 루프 자신이 관측 대상(read_status/read_debug)까지 함께 100배 빠르게 흔들고 있다"는 점에 있다. 이는 이번 조사에서 가장 구체적이고 즉시 검증 가능한 발견이다.
2. 이를 근거로 한 후보_1(터치 read를 BLE 하우스키핑에서 분리해 100ms로 정합화)이 가장 신뢰도 높고 실현성 있는 SW-only 레버다. 나머지(후보_2~5)는 오케스트레이터가 제시한 4개 하위주제(배치·듀티최소화·RTT·클럭분리)에 각각 대응하되, 후보_2(신규 BLE 프로토콜)는 구현 범위가 크고, 후보_4(RTT)는 실제 효과 크기가 하네스 실체 확인 전엔 미정이며, 후보_5(지터링)는 단독 근거가 약한 보강책이다.
3. 5개 후보 전부 **IQS323 레지스터를 전혀 건드리지 않는 e8300 SW-only** 변경이며, C2 불변식 8종 중 ④·⑦(둘 다 후보_1 한정)만 "주의" — 나머지는 전부 무손상으로 판정된다. HW 무수정 제약과 기존기능 보존 제약 둘 다 만족하는 후보군이다.
4. 다만 전 후보가 §0 경고(C2 §11 가설 — 프로파일링=fake_func_sleep 경로)에 의존한다. 이 전제가 틀리면 후보_1의 적용 대상 코드 자체가 달라지므로, **실경로 확인이 다른 어떤 세부 구현보다 선행되어야 한다**.
5. 후보_1·3은 즉시 실현 가능한 소규모 변경, 후보_2는 하네스 협조가 필요한 중규모 변경, 후보_4·5는 운영 정책/보강 성격 — S8(조합 레버)에서 후보_1+3을 기본 조합으로, 후보_4를 정책적 병행, 후보_2·5를 선택적 확장으로 검토할 것을 제안한다.
