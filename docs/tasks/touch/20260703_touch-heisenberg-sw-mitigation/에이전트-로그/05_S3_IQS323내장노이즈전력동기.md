# 05 · S3 — IQS323 내장 노이즈/전력/동기 기능 (SW-only 후보)

**TL;DR**: 데이터시트 전수 검토 결과 RF/노이즈 검출 플래그·외부 동기 입력·주파수 호핑·ati_error 자동재시도는 전부 **부재 확인**(네거티브, §1). 실효 후보 4건 도출 — 후보_1 Prox 채널 HW 디바운스를 Touch 1차 게이트로 활용(단 S6 FSM 협조 필수), 후보_2 NP Report Rate(0xC1) 명시 설정, 후보_3 Interface Selection→Events 모드 전환, 후보_4(약함) I2C Transaction Timeout 단축. LP/ULP Automatic 재도입은 **기존 코드 주석상 이미 확정된 회귀의 재현**이라 강하게 반대(§7).

## 2. S1 미해결 질문 해소 — Auto Prox Cycle Select

S1(`03_S1_변환전하전달오실레이터.md` §6 리스크표)이 "0x33 Auto Prox Cycle Select(reset=32)가 CH0 경로에 실제 적용되는지 미확인 — 최대 32배 시간추정 오차 우려"로 남긴 질문을 본 노드 자료로 해소한다.

**확인(PDF A.9 원문, L.3108-3113)**: "Auto Prox Cycle Select = Number of conversions before each interrupt is generated **in Auto Mode**." §5.2에서 이 "Auto Mode"는 ULP의 단일 웨이크채널 고속 재확인 동작("AutoProx"라고도 불림)에 결부된 필드다.

**결론**: Power Mode Timeout(0xC5)=0으로 LP/ULP 진입이 원천 차단된 현재 설정(§7)에서는 이 필드가 CH0 NP 폴링 경로에 **적용되지 않는다** — S1이 우려한 32배 오차 리스크는 **현재 설정 기준으로는 기각 가능**(단, LP/ULP가 미래에 재도입되지 않는 한이라는 조건부).

## 3. 후보_1 — Prox 채널 HW 디바운스를 Touch 1차 게이트로 활용

**메커니즘**: §1에서 확인했듯 Touch는 IC 내부에 debounce가 없어 **코히런트 노이즈 1샘플만으로 즉시 CH0 Touch bit가 set**된다(C1 §2.2 자기강화 메커니즘의 근본 원인과 정합). Prox는 4비트 Enter/Exit debounce(최대 15연속)를 IC **실리콘 레벨**에서 지원한다(§5.7). Prox Threshold를 Touch Threshold보다 낮게(먼저 반응하도록) 설정하고 Enter=2~3으로 debounce를 걸면, "노이즈 1샘플 vs 진짜 접촉(수십 ms 이상 지속)"을 IC 자체가 1차로 걸러줄 여지가 생긴다.

**필요 변경**:
- 0x61(Ch0 Prox Settings): LSB=Prox Threshold를 현재 255(사실상 무력화)에서 Touch Threshold(80)보다 낮은 값으로(예시 50~65, **정확한 값은 미확인·실측 게이트**). MSB=Debounce(상위4비트 Exit·하위4비트 Enter, 예 Enter=2·Exit=2 → 0x22).
- SW: `tdc_touch_iqs323_status_t.prox` 필드는 이미 존재하나 **현재 RTT 계측 출력에만 쓰이고 판정 로직 0곳에서 소비**(`tdc_touch.c:323` 확인, `tdc_touch_logic.c`/`main.c` ULP 핸들러 grep 결과 소비처 없음). "Prox 없이 Touch만 단독으로 선 것"을 의심 신호로 취급하는 신규 로직은 **S6(FSM 강건화) 영역** — 본 후보는 그 전제 레지스터 활성화까지만 제공한다.

**실현성**: 조건부 긍정 — 레지스터 변경 자체는 안전하나(§9 매트릭스), **독자적으로는 미완성**(S6 협조 없이는 아무 효과 없음). 트레이드오프: Prox Threshold 재정의로 "255=무력화"라는 기존 서술이 바뀌므로 문서화 필요. ATI 에러 leg에는 무관(Touch/Prox는 ati_error와 별개 판정 경로).

## 4. 후보_2 — NP Report Rate(0xC1) 명시 설정

**현황(발견)**: `tdc_touch_iqs323.c` 레지스터 목록에 **0xC1(Normal Power Mode Report Rate)이 없다** — POR 기본값 0x0000이 그대로 유지 중이다(LP Report Rate 0xC2=100ms는 명시 설정되어 있으나, PM Timeout=0으로 LP에 도달하지 못해 사실상 죽은 값 — §2와 동일한 성격의 미사용 설정).

**메커니즘(가설)**: 리뷰한 범위 내에서 "Report Rate=0"의 정확한 의미를 명문화한 문장을 찾지 못했다(Power Mode Timeout의 "0=강하 없음"과 달리 Report Rate 0의 의미는 **미확인**). 만약 0이 "지연 없이 최대속도로 연속 변환"을 뜻한다면, CH0 프론트엔드가 상시 conversion 중이라는 뜻이 되어 메커니즘_2(샘플링 윈도우 일치)가 사실상 항상 충족되는 구조(회피할 idle gap 자체가 없음)가 된다. 값을 명시하면(예 100ms, SW 폴링 주기와 정합) conversion 사이 idle 구간이 생겨 애그레서 회피 여지가 생긴다.

**필요 변경**: 0xC1 신규 write, 예 LSB=0x64·MSB=0x00(100ms). **정확한 최적값·실제 효과는 미확인** — 오실로스코프로 CTx0 duty cycle을 직접 관측하거나 Azoteq 문의로 "0"의 의미를 확인하는 것이 선행 과제.

**실현성**: 긍정(C2 8대 불변식 중 어느 것도 0xC1을 참조하지 않아 회귀 위험 거의 없음, §9). 다만 효과 근거는 가설 단계.

## 5. 후보_3 — Interface Selection → I2C Events 모드 전환

**현황**: 현재 0xC0 LSB=0x50(bit7=0=Streaming) — IQS323이 Report Rate 주기마다 **활동 유무와 무관하게** 자체적으로 RDY 윈도우를 자동 오픈한다(§8.11.1). 반면 현재 SW의 `force_window_open()`은 **RDY가 이미 열려있지 않은 한** 매 폴링 0xFF 강제통신 요청을 먼저 보내는 구조다(코드: `if(RDY==OPEN) return true;` 우회 후에만 `#if 1` 0xFF write 블록 실행) — 즉 IC의 자동 오픈 여부와 무관하게 SW 스스로 창을 강제로 열 수 있는 경로가 이미 확보돼 있다.

**메커니즘**: bit7=1(Events)로 바꾸면 IQS323은 활성화된 이벤트(0xD3, 현재 ati_error·ati_event·touch_event)가 실제 발생했을 때만 자동으로 윈도우를 연다. SW는 이미 강제개방 방식이라 **동작 변화가 없고**, 없어지는 것은 "이벤트 없이 IC가 스스로 자동 오픈하던 부수적 RDY/윈도우 토글"뿐이다 — 이는 CRX0 인접 회로(RDY=DIO16)에서 발생하는 **한 종류의 부수 스위칭 애그레서 후보**를 제거하는 효과다(단, DIO16의 실제 PCB 근접도는 미확인).

**필요 변경**: 0xC0 LSB 0x50→0xD0(bit7 추가, Power Mode·CH timeout 비트 불변). **기존 0xC0 write 4곳 전부**(부팅 `beta_power_settings()`·boot Re-ATI·boot RESEED·공개 `tdc_touch_iqs323_re_ati()`/`reseed()`)에 빠짐없이 bit7을 반영해야 한다 — 하나라도 누락하면 그 write가 Streaming으로 되돌리는 조용한 회귀다(INV-X-1이 경고하는 정확히 그 패턴, §9 각주⁶).

**실현성**: 긍정이나 구현 시 4개 write 동시 수정이 필요해 누락 리스크가 있다. 효과는 부수 애그레서 제거 수준(간접) — 주 전선(CH0 자체 conversion 활동)에는 영향 없음(후보_2와 상호 보완 관계, 배타적이지 않음).

## 6. 후보_4(약함) — I2C Transaction Timeout(0xD1) 단축

**현황**: 0xD1 미기록, POR 기본값 200ms(§8.8) 유지 중.

**메커니즘**: SPI/BLE 부하로 CM3측 서비스가 지연되면 IQS323은 최대 200ms간 통신 윈도우를 열어둔 채 대기하다 스스로 닫는다(§8.8, "master가 응답하지 않아도 시스템은 계속 진행"). 이 값을 줄이면(예 50ms) 미서비스 윈도우가 더 빨리 닫혀 "열린 통신 윈도우 상태"의 총 노출시간이 줄어들 수 있다. **단, 이것은 전하주입(analog coupling) 메커니즘과는 무관한 프로토콜 계층 완화**이며, 근거는 간접적이고 약하다.

**필요 변경**: 0xD1 신규 write(범위 2~230ms), 예 LSB=0x32·MSB=0x00(50ms). 너무 짧으면(예 2ms) `read_debug()`의 4바이트 연속 read 같은 정상 트랜잭션도 잘릴 위험 — 실제 트랜잭션 소요시간보다 여유 있게 설정 필요.

**실현성**: 안전하나 효과 근거가 약함(참고용 하위 후보로만 제시).

## 7. 반대 권고 — LP/ULP Automatic 재도입 (Power Mode Timeout ≠ 0)

이론상 LP/ULP는 Report Rate를 늘려 duty cycle을 낮추므로 노이즈 노출 감소 여지가 있어 보이지만, **이미 실기로 반증되어 되돌려진 이력이 있다**. `tdc_touch_iqs323.c` `beta_power_settings()`의 0xC5 write 주석 원문:

> "PM timeout 0 = 자동 강하 차단 → 노말 운용 중 NP 유지. (LP 전환 시 report rate 100ms 로 RDY 윈도우가 느려져 force_window_open 45ms 폴링이 윈도우를 놓쳐 timeout 발생. 터치=이벤트→NP 복귀로 회복되던 증상의 근본 차단. DS §5.3)"

`관측교란.md` §6도 이를 "이전 작업에서 확정한 root cause 'PM Timeout 자동 LP 강하'"로 재확인한다. **재도입은 이미 고친 회귀의 재현**이므로 명확히 반대한다(§9 매트릭스 "충돌" 표기 유일 항목).

## 핵심 결론 (3~5줄)

1. IQS323은 RF/노이즈 검출 플래그·외부 동기 입력·주파수 호핑·ati_error 자동재시도가 **전부 부재**하다 — 사용자가 지정한 조사 초점 중 다수가 "이 칩에는 애초에 없는 기능"으로 판명됐다(§1, PDF 원문 전수 대조로 확인).
2. 가장 근거가 탄탄한 발견은 **Touch에는 debounce가 없고 Prox에만 있다**는 비대칭(§1·§3)이다 — 이것이 "코히런트 노이즈 1샘플이 즉시 오탐을 만든다"는 C1 관찰과 정합하는 유일한 IC 레벨 구조적 원인이나, 활용하려면 S6(FSM)의 협조가 반드시 필요해 S3 단독으로는 미완성 해법이다.
3. 두 번째로 유망한 것은 **Report Rate(0xC1)·Interface Selection(0xC0 bit7)이 둘 다 사실상 미사용 상태로 방치**돼 있었다는 발견(§4·§5)이다 — C2 8대 불변식과 충돌하지 않는 저위험 레버지만, "0"의 정확한 의미와 twait 여유가 미확인이라 실측이 선행돼야 한다.
4. **LP/ULP Automatic 자동모드는 명확히 반대**한다 — 이미 코드 주석과 관측교란.md §6이 확정한 과거 회귀(PM Timeout 자동강하 → RDY 지연 → 오탐 복귀)의 재현이기 때문이다. 이 결론은 S1이 남긴 "Auto Prox Cycle Select 미확인" 리스크도 함께 해소한다(§2, 현재 설정에서는 적용되지 않음).
5. 종합하면 S3 단독으로는 "결정적 해법"이 아니라 **저위험 보조 레버 3~4건**을 제공한다 — 실질적 저감 효과는 S1(변환주파수)·S4(타이밍 협조)·S6(FSM 판정)과의 조합에서 나올 가능성이 높으며, 이는 S8(조합·시스템 전략)의 몫이다.
