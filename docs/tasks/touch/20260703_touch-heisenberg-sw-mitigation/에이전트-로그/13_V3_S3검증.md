# 13 · V3 — S3(IQS323 내장 노이즈/전력/동기 기능) 적대적 검증

**TL;DR**: 후보_2(Report Rate)는 코드+데이터시트(`02_proxfusion동작.md` NP행) 교차 확인으로 근거가 오히려 강화됐으나 ATI 버스트 타이밍 간섭이라는 신규 위험을 찾았다. 후보_3(Events 모드)은 §8.11~8.13 원문으로 핵심 주장은 확인되지만, `force_window_open()`의 "RDY 이미 열림 시 생략" 분기 때문에 상시 Force Comm으로 바뀌며 이것이 데이터시트 부록C "I²C Lock Up" 에라타(Force Comm 사용 시 발생 확률 증가, 임의 상수값 반환·기존 0xEEEE 검사로 못 거름)와 충돌하는 미검토 중대 위험을 발견했다 — "저위험" 재분류가 필요하다. 후보_1은 코드 확인상 prox 필드가 판정에 전혀 미소비되어 단독 효과 없음(문서도 인정). 0xC0 write 지점은 문서 주장(4곳)보다 실제 1곳 많은 5곳이다.

## 1. 후보_1 — Prox HW 디바운스 게이트

- **(a) 실제 저감**: **없음(단독으로는)**. `tdc_touch.c:302~309`(`in.pressed`/`in.ati_error`/`in.ati_active`만 채움, prox 미포함) + `main.c` 908~1153행(prox는 932·1047행 `ci_printd` 로그 전용, 조건문 0곳)으로 **직접 확인** — prox 비트는 FSM·ULP 판정 입력 어디에도 연결되지 않는다. 레지스터만 바꾸면 시스템 동작은 아무 변화 없음(S3 문서도 "독자 효과 0" 자인).
- **(b) 기존기능**: 무손상(0x61 write 자체는 범위 내 안전한 변경).
- **(c) SW-only**: 예.
- **(d) 실현성**: `TDC_TOUCH_IQS323_PROX_THRESHOLD=255`(iqs323.h:52) 확인 — "255=사실상 무력화" 주장은 매크로값으로 **확인**됨. 단 iqs323.c:420 인접 주석("Prox=Touch 동일 계수")은 실제 write 값(255)과 문면이 어긋나는 코드 내 기존 주석 오기로 보인다 — 본 검증 범위 밖의 별건이라 참고로만 남긴다.

**판정**: 등록 단독으로는 REFUTED(무효과). S6 FSM 소비 로직이 실제로 구현되기 전까지는 "후보"가 아니라 "선행 조건"에 불과하다.

## 2. 후보_2 — NP Report Rate(0xC1) 명시 설정

- **(a) 실제 저감**: 문서는 "가설"로 낮춰 잡았으나 `02_proxfusion동작.md:100~101`을 직접 확인하면 — "**NP: 매 Report Rate마다 모든 채널 전체 conversion**" / "LP: Report Rate 간격이 NP보다 길어 **아날로그 블록 off 시간 증가**". Report Rate가 단순 보고 주기가 아니라 **실제 아날로그 변환 카덴스를 게이팅**한다는 근거이며, 원문서 인용보다 강한 확인이다.
  - **신규 위험 1(미검토)**: Full ATI 버스트도 "동일 프런트엔드"(C1 §5)를 쓴다. Report Rate가 ATI 버스트 자체의 내부 반복 주기에도 적용되는지, ATI 완료 후 정상 상태 보고에만 적용되는지가 **미확인**이다. 전자라면 `wait_ati_done_blocking()`(iqs323.c:328, 25×50ms≈1.25s 상한)·`try_finish_init()`(tdc_touch.c:153, 2500ms 타임아웃)이 Report Rate 도입으로 실제 ATI 소요시간이 늘어나 타임아웃을 초과할 잠재 위험 — S3·C2 모두 이 항목을 검토하지 않았다.
  - **신규 위험 2(자기지시적)**: 문서가 제안한 구체값 "100ms, SW 폴링 주기와 정합"은 관측교란.md 메커니즘_3(에일리어싱/맥놀이)이 정확히 경계하는 조건이다. SW 폴링(CM3 클럭 기준)과 IQS323 Report Rate(IQS323 자체 발진기 기준)는 서로 다른 독립 발진기이므로, 주기를 일치시키면 위상이 서서히 표류하는 느린 맥놀이가 자체적으로 생긴다 — 항상 신선한 값을 읽거나 항상 stale(최대 1주기 지연) 값을 읽는 국면이 번갈아 나타날 수 있다. Heisenberg 회피책이 같은 부류의 문제를 자기 안에 재도입하는 셈 — 100ms 동일값보다 의도적으로 이격된 값(예 137ms) 검토를 권고한다. (심각도는 낮음: 최악의 경우도 검출 지연 증가 수준.)
- **(b) 기존기능**: 위 신규위험 1로 INV-①(Full ATI)·INV-⑥(절전 진입/기상)을 "무손상"에서 "주의(미확인)"로 하향한다. 나머지(②③④⑤⑦⑧)는 0xC1 전용 레지스터라 무손상 유지.
- **(c) SW-only**: 예.
- **(d) 실현성**: `06_레지스터레퍼런스.md` §9 "0xC1 Normal Power Mode Report Rate, 16-bit(ms), Range 0-3000" 확인 — 존재·범위 확인됨. "0"의 정확한 의미는 여전히 **미확인**(§8.11.1 원문도 0을 명시 정의하지 않음).

**판정**: NOT refuted — 4건 중 유일하게 근거가 강화된 후보다. 단, 신규 게이트(ATI 버스트 타이밍 영향 실측) 통과 전엔 "저위험" 단정을 보류해야 한다.

## 3. 후보_3 — Interface Selection → Events 모드(0xC0 bit7)

- **(a) 실제 저감**: 핵심 동작 주장은 `05_i2c인터페이스.md` §8.11.1~8.11.2 원문 다이어그램으로 **확인**된다 — Streaming은 이벤트 무관 매 Report Rate마다 RDY assert("ISR: 발생 발생 발생 발생 발생 (항상)"), Event는 이벤트 시에만("이벤트 없는 구간: RDY 침묵"). 데이터시트는 "펌웨어 권장: event mode를 기본으로, streaming은 개발·디버깅 단계 임시용"(§8.11.2 NOTE)이라고 명시한다 — 현재 제품 코드가 제조사 권장과 반대로 설정돼 있다는, S3 원문서가 인용하지 않은 강한 지지 근거를 추가로 확인했다.
  - **신규 중대 위험(반증 핵심, 문서 미검토)**: `force_window_open()`(iqs323.c:145~152)은 `RDY==OPEN`이면 0xFF 강제write를 **생략**한다. Streaming은 Report Rate마다 IC가 자체적으로 RDY를 열어주므로 이 생략 분기가 자주 히트되지만, Events 모드는 이벤트(정상 대기 중엔 사실상 미발생) 없이는 RDY가 계속 닫혀있다(§8.11.2, §8.13 "event mode에서 이벤트 없이 레지스터를 변경하거나 즉시 상태를 query할 때 사용" — 우리 시스템의 100ms 상시 폴링이 정확히 이 경우다). 즉 Events 전환은 "동작 변화 없음"이 아니라 **매 폴링 강제-오픈(0xFF write)이 사실상 상시화**되는 실질적 트래픽 증가다. `read_status()`+`read_debug()`(`TDC_TOUCH_DEBUG_PRINT_ENABLE` 기본값 1, config.h:22 확인) 조합 시 100ms마다 최대 4회의 force_window_open 호출이 전부 강제-오픈 경로를 타게 된다.
  - 이 강제-오픈(0xFF)이 `08_개정이력·이슈.md` 부록C **"I²C Lock Up"** 에라타의 트리거 조건과 정확히 일치한다: "Issue: IQS323이 I²C로 read하는 모든 byte가 상수 값을 반환하는 상태 진입 가능. **§8.13 force communications 방법 사용 시 발생 가능성↑**"(적용 버전: IQS323-00x v1.3 이하·A0x v1.4 이하). 이 상수값이 0xEE로 고정되어 있다는 보장이 없어 기존 글리치 판정(`lsb==0xEE && msb==0xEE`, iqs323.c:357)이 **못 거를 수 있다** — 걸러지지 않은 고정 touch/ati_error 비트가 그대로 판정에 들어가면 INV-③·④·⑦·X-3을 동시에 위협하는 영구적 오염이며, 이는 원래 잡으려던 일시적 전하주입보다 **더 나쁜** 실패 모드다. 현재 보드 실장 IC가 에라타 적용 버전에 해당하는지는 **미확인**(Hardware ID/Major-Minor Version 0x00~0x02 실측 필요, 본 세션 데이터 없음) — 이 확인 전에는 후보_3을 "저위험"으로 분류할 근거가 없다.
- **(b) 기존기능**: 위 에라타 상호작용으로 INV-③(ATI에러)·INV-④(터치판정)·INV-⑦(공통폴링)·INV-X-3(디버그계측 무해)을 "무손상"에서 "주의(신규 중대)"로 하향한다.
- **(c) SW-only**: 예(레지스터 비트 write만).
- **(d) 실현성/정확도**: 0xC0 write 지점 재카운트 — `ack_reset()`(iqs323.c:237, 0x01/0x00)은 물리 MCLR 직후 POR 기본값(bit7=0)과 이미 같은 값을 쓰는 것이라 수정 불필요. 나머지는 `beta_power_settings()`(318행)·boot Re-ATI(447행)·boot RESEED(453행)·`re_ati()`(465행)·`reseed()`(471행) = **5곳**(문서의 "4곳" 주장보다 1곳 많다 — re_ati/reseed를 한 항목으로 뭉뚱그려 세면서 누락된 것으로 보인다). 5곳 중 하나라도 bit7 누락 시 조용한 Streaming 회귀 — 문서 스스로의 경고("하나라도 누락하면 조용한 회귀")를 문서 자신의 카운트가 충족하지 못한 셈이다.

**판정**: 핵심 동작 주장은 확인되지만 **에라타 상호작용 미검토로 "저위험" 재분류가 필요**하다. 신규 게이트(IC 버전 실측 + 필요시 부록C 워크어라운드 "매 트랜잭션 끝 미존재 레지스터 1byte read" 구현, 이는 candidate 3에 딸린 추가 코드 변경으로 스코프가 확장됨) 통과 전엔 채택을 보류할 것을 권고한다.

## 4. 후보_4(약함) — I²C Transaction Timeout(0xD1) 단축

`05_i2c인터페이스.md` §8.8 확인 — Transaction Timeout은 "닫히지 않은(unserviced) 오픈 윈도우"에만 적용되고 "master와 통신 시작(START) 후에는 비활성화, §7.6 워치독이 대신 제어"(§8.8 NOTE) — 즉 전하주입 메커니즘과 무관한 프로토콜 계층이라는 문서의 "근거 약함" 자기평가가 **정확함을 재확인**했다. 값 과소 설정 시 정상 트랜잭션 손실 위험도 §8.8 NOTE("너무 짧게 설정 시 터치 이벤트 누락")로 재확인. 추가 위험 발견 없음.

**판정**: NOT refuted, 문서의 "약함/보조용" 평가 그대로 유지.

## 핵심 결론 (3~5줄)

1. 후보_1(Prox 게이트)은 코드 직독으로 prox 필드가 판정 로직에 전혀 연결되지 않음을 재확인했다 — 등록 단독으로는 REFUTED(무효과), S6 없이는 존재 의미가 없다.
2. 후보_2(Report Rate)는 4건 중 유일하게 검증으로 근거가 **강화**됐다(NP=매 Report Rate당 전체 conversion, 데이터시트 명문 확인). 다만 ATI 버스트 타이밍 간섭과, 제안값(100ms=SW 폴링 주기 일치)이 메커니즘_3(에일리어싱)을 자기 안에 재도입할 수 있다는 신규 위험 2건을 찾았다.
3. 후보_3(Events 모드)은 핵심 동작(제조사도 이 모드를 권장)은 확인되나, `force_window_open()`의 생략분기 구조상 Force Comm이 상시화되며 이것이 데이터시트 부록C "I²C Lock Up" 에라타의 트리거 조건과 정확히 일치한다는 **미검토 중대 위험**을 발견했다 — "저위험" 재분류가 필요하며 IC 버전 실측 전엔 채택을 보류해야 한다.
4. 0xC0 write 지점은 문서의 "4곳"이 아니라 실제 **5곳**이다(re_ati/reseed 별도 카운트 누락) — 사소하지만 "누락 시 조용한 회귀" 경고를 문서 스스로 충족하지 못한 정확도 결함이다.
5. 후보_4(I2C Timeout)와 LP/ULP 반대권고는 반박 근거를 찾지 못해 문서 판정 그대로 지지한다.

## 리스크 · 불확실성

| 항목 | 상태 |
|---|---|
| 현재 보드 실장 IQS323 Major/Minor Version(에라타 적용 버전 여부) | **미확인** — Hardware ID(0xE1)/Version(0x01~0x02) 실측 게이트, 본 세션 데이터 없음 |
| NP Report Rate=0의 정확한 의미(연속무한 vs 다른 기본동작) | 근거는 강화됐으나 여전히 **미확인**(§8.11.1 원문도 "0"을 명시 정의하지 않음) |
| Report Rate가 ATI 버스트 내부 주기에도 적용되는지 | **미확인** — 신규 항목, 원문에서 별도 언급을 찾지 못함 |
| force_window_open()의 RDY-already-open 히트율(현재 Streaming에서 실제로 얼마나 자주 생략되는지) | **미확인** — 실측(오실로스코프/RDY GPIO 트레이스) 필요, 후보_3 위험 크기 정량화의 핵심 |
| I2C Lock-Up 에라타의 "임의 상수값"이 실제로 touch/ati_error 비트를 우연히 set시킬 확률 | **미확인** — 정성적 위험만 확인, 정량 확률 계산은 하지 않음 |
| 0xC0 write 5곳 전부 수정 시 실제 누락 없는지 | 구현 단계 실측/코드리뷰 게이트 |
