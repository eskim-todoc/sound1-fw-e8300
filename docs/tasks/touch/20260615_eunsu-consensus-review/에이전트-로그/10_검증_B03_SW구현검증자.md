# B03 · SW 구현 가능성 adversarial 검증자

> **TL;DR**: M2("터치 해제 대기")는 현행 `s_boot_touch_ignore`와 사실상 동일 효과지만 Reseed 게이트와 달리 LTA 오염을 원천 차단하지 못한다. timeout 강제 진행이 없어 무한 대기 위험이 현재도 실재한다. M3 Beta 단일 상향은 약터치 흡수 위험이 명백하며 비대칭 Fast Filter Band 구현만이 올바른 경로다. autoATI 재활성화 시 방전(`0x30` write), 절전(`apply_sleep_settings` 내 ATI_SETUP 덮어쓰기), 상태머신(re-ATI 오인 위험), I2C 무응답 네 곳에서 기존 코드와 충돌한다. 은수님 M2·M3는 방향은 옳으나 단독 구현 시 위험하다.

---

## 1. 검증 전제: 실제 코드 현황 확인

### 1.1 `s_boot_touch_ignore` 현행 구현 (tdc_touch.c)

코드 확인 결과 현행 부팅 터치 무시 로직:

- **탐지 위치**: `try_finish_init()` 완료 → `TDC_TOUCH_INIT_STATE_READY` 전이 직후, `tdc_touch_get_state()`로 즉시 상태 읽음 (tdc_touch.c:318~325)
- **무시 구간**: `s_boot_touch_ignore == true`이면 `tdc_touch_process()`에서 `return false` — 상위 레이어에 터치 이벤트를 전달하지 않음
- **해제 조건**: `got_state && curr_state != TDC_TOUCH_STATE_TOUCH` → `s_boot_touch_ignore = false`
- **경고만 있고 강제 해제 없음**: 5초 경과 시 `s_boot_5s_warned = true` + LED 점멸, **그러나 `s_boot_touch_ignore`는 여전히 true 유지**
- **방전 호출**: `tdc_touch_get_state()` 내부(tdc_touch.c:422) — 매 100ms 폴링 시 `discharge_crx0()` 호출

### 1.2 방전 코드 레지스터 확인 (tdc_drv_iqs323.c / .h)

- `TDC_DRV_IQS323_REG_ADDR_SENSOR0_SETUP` = **0x30** (tdc_drv_iqs323.h:47)
- `TDC_DRV_IQS323_INACTIVE_RXS_CRX0_VSS` = **0x02** (tdc_drv_iqs323.h:89)
- `discharge_crx0()`: 0x30 레지스터에 0x02→0x01 쓰기 — **Sensor0 Setup 레지스터**임

A02가 "0x30 0x02 = Linearise bit"라고 표현했으나, 실제 코드에서 `0x30` = `REG_ADDR_SENSOR0_SETUP`이고 `0x02`는 `INACTIVE_RXS_CRX0_VSS`로 정의되어 있음. 레지스터 구조상 이 필드가 진짜 CRX0→VSS인지 Linearise 비트인지는 데이터시트 §A.20 Sensor Setup 레지스터 구조 실측 확인이 여전히 필요하다(이전 분석 미해소 실측 게이트).

### 1.3 Beta 레지스터 현황

`tdc_drv_iqs323.c` 전체에서 0xB0~0xB4 레지스터 write 없음 — **POR default(0x0000) 그대로 사용 중**. M3 구현 시 Beta 레지스터를 처음으로 명시 write하는 코드가 추가되어야 한다.

## 2. M2 검증 — "터치 해제 대기 코드"

### 2.1 은수님 M2와 현행 코드의 관계

| 항목 | 은수님 M2 ("터치 해제 대기 코드") | 현행 `s_boot_touch_ignore` |
|---|---|---|
| **설명** | 부팅 시 터치 인식 → 해제될 때까지 대기 | 동일 |
| **구현 상태** | "구현 필요"로 제시 | **이미 구현되어 있음** |
| **보호 대상** | 상위 레이어 터치 이벤트 출력 차단 | 동일 |

**결론**: 은수님 M2는 현행 코드에 이미 존재하는 로직과 동일하다. "추가 구현"이 필요한 것이 아니라 현재 동작 중이다.

### 2.2 M2와 이전 분석 "Reseed 노터치 게이트"의 결정적 차이

```
현행 M2 (s_boot_touch_ignore) 타임라인:
  [MCLR] → [autoATI 완료] → [apply_settings()] → [RESEED @ drv.c:1134] (← 이미 실행됨)
  → [READY 전이] → [boot_state 확인] → [s_boot_touch_ignore=true]
  → [이후 폴링에서 터치 이벤트 출력 차단]

이전 분석 "Reseed 노터치 게이트" 타임라인:
  [MCLR] → [autoATI 완료] → [apply_settings()] → [RESEED 직전 ch0_touch==0 게이트 확인]
  → (터치 해제 후) → [RESEED 실행] (← LTA가 노터치 counts로 seed됨)
  → [READY 전이]
```

**핵심 차이**: M2는 Reseed가 먼저 실행된 후 터치 이벤트를 상위 레이어에서 차단하는 **사후 방어**다. 이전 분석 권고 A의 노터치 게이트는 **Reseed 발행 자체를 지연**해 LTA baseline이 터치 counts로 오염되는 것을 원천 차단한다.

M2만으로는: LTA = (터치 상태 counts) → 오염된 baseline → 손 뗀 후 IIR이 자기 수렴(수렴 과도기간 발생)
노터치 게이트: LTA = (노터치 counts) → 정상 baseline → 즉시 정상 감도

**M2는 LTA 오염 자체를 막지 못하고, autoATI의 자기정상화(손 뗀 후 IIR 수렴)에 의존한다.** autoATI Full이 복귀되면 수렴은 이루어지지만 수렴 과도기간(LTA가 노터치로 돌아오는 동안) 동안 재터치 미인식 위험이 존재한다.

### 2.3 경계 조건: 손을 절대 안 떼는 경우

**현행 코드 동작**:
- 5초 경과: 경고 LED (`s_boot_5s_warned = true`) — **대기 계속**
- 10초 후: 아무 일도 없음 — **대기 계속**
- 1분 후: 아무 일도 없음 — **대기 계속**
- **timeout 강제 해제 로직: 코드에 존재하지 않음**

**위험 시나리오**:
- 충전기에 올려놓고 부팅 (충전 접촉부가 터치패드에 지속 압력)
- 케이스 안에서 밀착되어 부팅
- 사용자가 기기를 쥔 채로 부팅 → 인지하지 못한 채 터치가 해제되지 않음

`s_boot_touch_ignore == true`인 동안 모든 터치 이벤트는 차단되어 **제품 기능 전체가 불능** 상태가 된다. 전원 버튼 겸용 터치이므로 전원 OFF도 불가능할 수 있다.

**반론 시도**: autoATI Full 복귀 시 자기정상화가 일어나면 오히려 터치가 인식되기 시작해 `s_boot_touch_ignore`가 해제될 수 있지 않은가?

**반론 반박**: `try_finish_init()`에서 READY 전이 직후 한 번 상태를 확인할 뿐, 이후 폴링에서 `s_boot_touch_ignore == true`이면 `tdc_touch_get_state()` **내부에서 방전은 실행**되지만 상태 비교는 `got_state && curr_state != TOUCH`가 되어야 해제된다. autoATI Full로 LTA가 수렴하면 결국 `curr_state == NOT_TOUCH`가 반환되어 해제는 될 것이다. 그러나 Beta=0(POR default)이면 수렴이 사실상 무한대로 걸릴 수 있다 → Beta 레지스터 미설정 상태에서 autoATI Full만 복귀시키면 이 해제도 불명확.

**결론**: timeout fallback 없이 M2만으로는 경계 조건 미처리. 최소한 N초 이후 강제 해제 + dirty baseline 플래그 처리가 필요하다.

## 3. M3 검증 — Beta 단일 상향의 부작용

### 3.1 Beta 단일 상향이 약터치를 흡수하는 메커니즘

IQS323 LTA 갱신식:
```
LTA_new = LTA_old + (Counts − LTA_old) × (Beta / 256)
```

self-cap에서 터치 시 Counts **감소**, 노터치 시 Counts **증가**.

Beta를 단순히 높이면:
- **노터치→터치 전환 시**: LTA가 아직 노터치 기준인 상태에서 Counts가 감소 → delta = LTA − Counts 증가 → 터치 인식 (정상)
- **약터치 또는 느린 터치 진입 시**: Counts가 서서히 감소 → 동시에 LTA도 Beta/256 속도로 Counts를 따라 감소 → delta = LTA − Counts가 threshold에 도달하기 전에 LTA가 따라옴 → **터치 미인식**

이것이 "약터치 흡수"다. Beta가 클수록 LTA가 counts를 빠르게 추적하므로 약한 터치나 천천히 누르는 터치의 delta 축적이 방해된다.

**인공와우 사용자 터치 특성**: 기기를 귀에 착용한 채로 조작하거나, 손가락 감각이 제한된 사용자(노인·장갑 착용·피부 건조)의 경우 접촉 강도가 낮거나 누름 속도가 느릴 수 있다. Beta 단일 상향은 이 사용자 집단에서 터치 미인식 빈도를 높인다.

### 3.2 Fast Filter Band 비대칭 설계가 올바른 이유

IQS323 데이터시트 §5.6:
> "If counts drift from LTA in the **opposite direction to sensing** by more than the **Fast Filter Band**, fast filtering is applied."

self-cap: sensing 방향 = Counts **감소**. 반대 방향 = Counts **증가** = 손을 **뗄 때**.

따라서 Fast Filter Band는 오직 손을 뗄 때(Counts 증가 구간)에만 빠른 LTA Beta를 활성화한다. 터치 진입 방향(Counts 감소)에서는 fast filtering이 발동되지 않아 약터치 흡수가 일어나지 않는다.

**비대칭 설계 레지스터 구성**:

| 레지스터 | 현재값 | M3 올바른 구현 | 역할 |
|---|---|---|---|
| 0xB1 하위 바이트 (LTA Beta NP) | 0x00 (POR) | **소값 유지** (예: 2~4) | 일반 드리프트 추적 — 보수적 |
| 0xB2 하위 바이트 (LTA Fast Beta NP) | 0x00 (POR) | **대값 설정** (예: 10~15) | 손뗌 후 빠른 수렴 |
| 0xB4 (Fast Filter Band) | 0x00 (POR) | **적정 Band 설정** | 노이즈 < Band < 약터치delta 창 |

현재 세 레지스터 모두 0x00이므로 **POR default 상태**다. Beta=0이면 `alpha = 0/256 = 0` → `LTA_new = LTA_old` → LTA 완전 동결 가능성이 있다(실측 미확인). M3 구현은 이 세 레지스터를 처음으로 명시 write하는 작업을 수반한다.

**단일 Beta 상향 구현의 오류 패턴**:
```c
// 잘못된 M3 구현 (단순 Beta 상향)
write_register(0xB1, 0x08, 0x08);  // LTA Beta NP=8, LP=8
// → 약터치 시 LTA가 터치를 따라가 delta가 threshold 미달 → 미인식
```

**올바른 M3 구현 (비대칭)**:
```c
// 올바른 M3 구현 (Fast Filter Band 비대칭)
write_register(0xB1, 0x02, 0x02);  // LTA Beta NP=2(보수적), LP=2
write_register(0xB2, 0x0C, 0x0C);  // LTA Fast Beta NP=12(공격적), LP=12
write_register(0xB4, 0x1E, 0x00);  // Fast Filter Band — 실측 후 결정
```

Fast Filter Band 값은 실측 없이 코드로 결정할 수 없다. "노이즈 < Band < 약터치 delta" 창의 실제 수치는 RTT 실측이 선행되어야 한다.

## 4. autoATI 재활성화 + 방전 코드 공존 충돌

### 4.1 레지스터 덮어쓰기 분석

현재 `discharge_crx0()` (drv.c:938~951):
```c
// Step 1: CRX0=VSS로 방전
write_register_discharge(0x30, TDC_DRV_IQS323_INACTIVE_RXS_CRX0_VSS, 0x00);
// → Sensor0 Setup LSB = 0x02 (CRX0 VSS), MSB = 0x00

// Step 2: 복원
write_register_discharge(0x30, 0x01, 0x01);
// → Sensor0 Setup LSB = 0x01 (enable_channel=1?), MSB = 0x01
```

ATI Full 재활성화 시 충돌 경로:

1. `write_ati_compensation()`에서 ATI_SETUP(0x36) 레지스터에 ATI Mode=Full 설정을 write
2. 200ms 폴링마다 `discharge_crx0()`가 Sensor0 Setup(0x30) 레지스터를 write

이 두 레지스터는 **서로 다른 주소(0x36 vs 0x30)**이므로 직접적인 비트 덮어쓰기 충돌은 없다.

**그러나 실제 충돌 위험은 다음 경로에서 발생한다**:

- ATI Full 진행 중(`ATI Active bit=1`) Sensor0 Setup(0x30) 레지스터를 변경하면 **ATI 수렴 계산 도중 하드웨어 파라미터가 변경**되어 ATI가 비정상 MULT/COMP 값으로 수렴하거나 ATI Error로 중단될 수 있다.
- ATI Full 실행 중에는 IC가 내부적으로 CH0 Sensor Setup을 읽어 MULT/COMP를 탐색하는데, 방전이 0x30 LSB를 0x02→0x01로 토글하면 ATI 탐색 기준이 중간에 바뀐다.

**검증 판정**: 레지스터 주소 충돌은 없으나 ATI 진행 중 Sensor Setup 변경으로 인한 ATI 수렴 오류는 실재한다. ATI Active bit 감시 후 방전 일시 정지 로직이 필요하다.

### 4.2 ATI 진행 중 방전 일시 정지 미구현 시 위험 시나리오

```
1. write_ati_compensation()으로 ATI Mode=Full 활성화
2. IC가 ATI 탐색 시작 (ATI Active bit=1, 수~수십ms 소요)
3. 100ms 후 폴링 → tdc_touch_get_state() → discharge_crx0() 호출
4. 0x30 LSB=0x02 write → ATI 탐색 중 CH0 Sensor Setup 변경
5. ATI가 변경된 파라미터 기준으로 MULT/COMP 설정 → 잘못된 baseline
6. 최악: ATI Error → IC ATI Error bit set → I2C 통신 무응답
```

## 5. I2C 통신 관리 미선행 시 ATI Full 재활성 위험

### 5.1 현행 코드의 I2C 통신 구조

현재 코드는 `ATI Active bit(bit5)` 폴링과 ATI Error 후 수동 Re-ATI 트리거 로직이 없다. `try_finish_init()` 내 `is_auto_ati_done()` 폴링은 초기화 1회에만 사용되고, 이후 운용 중 ATI 재실행을 위한 polling 로직은 없다.

RDY 핸드셰이크: `force_window_open` + 45ms 타임아웃 구조가 있으나, ATI Full 진행 중 RDY가 점유되어 타임아웃이 연속 발생하면 I2C 통신 실패 상태가 계속된다.

### 5.2 ATI Full 재활성화 시 무응답 재현 경로

이전 분석(개선 문서, 펌웨어 분석)에서 확인된 이력:
- ATI Mode=Full 상태에서 Stuck-Touch 발생 → IC 자동 Re-ATI 발동
- ATI Active bit set → COMP 급변 → ATI Error bit set
- 이 구간 동안 I2C 통신 무응답
- 현 코드: ATI Error = "ATI Disabled + 고정 보상값" 전략으로 회피 중

ATI Full 재활성화 시 이 경로가 다시 활성화된다. `is_auto_ati_done()` 폴링이 INIT 단계 외에도 동작하도록 확장하고, ATI Error 발생 시 수동 Re-ATI 트리거 에러 핸들러를 추가하지 않으면 **이전에 경험했던 I2C 무응답 현상이 재현된다**.

### 5.3 은수님 M2·M3 정리에서 I2C 통신 관리의 부재

M2("터치 해제 대기"), M3("Beta 빠른 수렴"), M8("autoATI + Beta로 해결")에는 I2C 통신 관리 항목이 없다. 이것이 이번 검증에서 발굴한 **은수님 정리에서 가장 큰 누락 항목**이다.

I2C 통신 관리 없이 ATI Full을 재활성화하면:
- 정상 상황에서는 동작하다가
- Stuck-Touch 발생 시 → IC 자동 re-ATI → 통신 무응답 → 먹통 재발

## 6. 명제별 adversarial 판정표

| 검증 항목 | 판정 | 근거 |
|---|---|---|
| **M2 "터치 해제 대기" = 이전 분석 "Reseed 노터치 게이트"와 동일?** | ❌ 동일하지 않음 | 위치 차이: M2는 READY 이후 이벤트 출력 차단, 노터치 게이트는 Reseed 발행 직전 LTA 오염 원천 차단. LTA 오염 방지 효과 없음 |
| **M2 단독으로 P1(부팅 터치 먹통) 해결 가능?** | △ 부분 완화, 완전 해결 아님 | autoATI 자기정상화에 의존. 수렴 과도기간 동안 재터치 미인식 가능 |
| **M2 손 안 떼는 경계 조건 처리** | ❌ 미처리 | 현행 코드 timeout 강제 해제 없음. 5초 경고만 있고 무한 대기 지속 |
| **M3 Beta 단일 상향 구현 가능성** | ⚠️ 가능하나 위험 | 레지스터 3개 write로 구현 용이하나 약터치 흡수 부작용 발생 확실 |
| **M3 Fast Filter Band 비대칭 구현** | △ 올바른 방향, 실측 필요 | 레지스터 경로 존재(0xB1/B2/B4). Fast Filter Band 값은 실측 없이 결정 불가 |
| **Beta 레지스터 현재 상태** | ⚠️ POR default 0x0000 | M3 구현 시 최초 write 필요. Beta=0 동작(LTA 동결 여부) 실측 필수 |
| **autoATI 재활성 + 방전 코드 레지스터 비트 충돌** | △ 주소 충돌 없음, ATI 수렴 방해 위험 있음 | 0x36 vs 0x30 분리. 그러나 ATI 진행 중 0x30 변경 → ATI 수렴 오류 가능 |
| **ATI 진행 중 방전 일시 정지 로직** | ❌ 미구현 | ATI Active bit 감시 후 방전 skip 로직 없음. 구현 필요 |
| **I2C 통신 관리 선행 필요성** | ❌ 은수님 정리에서 누락 | ATI Full 재활성 시 이전 무응답 재현 경로 존재. 가장 큰 누락 항목 |
| **M8 "autoATI + Beta만으로 해결"** | △ 방향 옳으나 단독 불가 | 노터치 게이트·비대칭 Beta·I2C 관리·방전 ATI 충돌 처리 없이는 회귀 위험 |

## 7. 핵심 위험 우선순위

| 순위 | 위험 | 발생 확률 | 영향 | 선행 필요 조건 |
|---|---|---|---|---|
| **1** | I2C 통신 무응답 (ATI Full 재활성 시 Stuck-Touch → 자동 re-ATI) | 높음 (이전 실제 발생 이력) | 제품 먹통 | ATI Active 폴링 + 에러 핸들러 구현 |
| **2** | 무한 대기 (손 안 떼는 케이스, timeout 없음) | 중간 (충전/케이스 시나리오) | 모든 터치 기능 불능 | timeout fallback 구현 |
| **3** | ATI 수렴 중 방전 레지스터 간섭 | 중간 (ATI 진행 중 폴링 충돌) | 잘못된 baseline 설정 | ATI Active bit 감시 후 방전 skip |

## 8. adversarial 검증 종합 결론

### 8.1 M2 최종 판정

은수님 M2("터치 해제 대기 코드")는 **현행 코드에 이미 존재**하는 `s_boot_touch_ignore` 로직과 동일하며 추가 구현이 필요하지 않다. 단, 이 로직은 이전 분석의 "Reseed 노터치 게이트"와 다음 점에서 다르다:

- **M2 / s_boot_touch_ignore**: LTA 오염 후 사후 차단. autoATI 자기정상화로 복구 기대. timeout 없어 무한 대기 위험.
- **노터치 게이트 (권고 A)**: LTA 오염 원천 방지. Reseed 직전 ch0_touch==0 N tick 확인. 두 번째 실행 경로(func_sleep reseed)도 처리.

autoATI Full이 복귀되면 M2만으로도 결과적으로 자기정상화가 일어나지만, **수렴 과도기간 동안의 감도 이상**과 **timeout 없는 무한 대기**는 M2 단독으로 해결되지 않는다.

### 8.2 M3 최종 판정

Beta 조정 자체는 올바른 방향이나 구현 형태에 따라 결과가 정반대다:
- **단일 LTA Beta 상향**: 약터치 흡수 위험 — 금지
- **Fast Filter Band 비대칭 (0xB1 보수적 + 0xB4 Band + 0xB2 공격적)**: 올바른 구현
- Fast Filter Band 값은 RTT 실측 없이 코드로 결정 불가 — 실측 게이트 통과 필수

### 8.3 autoATI 재활성화 필요 선행 작업

단순히 `ATI_SETUP_LSB`의 bits[2:0]를 `000(Disabled)` → `100(Full)` 또는 다른 Full 모드로 변경하는 것만으로는 안 된다. 다음이 모두 선행되어야 한다:

1. **I2C 통신 관리**: ATI Active 폴링 + ATI Error 에러 핸들러 + Re-ATI 수동 트리거
2. **ATI 진행 중 방전 일시 정지**: `ATI Active bit` 확인 후 `discharge_crx0()` skip
3. **절전 모드 분기**: `apply_sleep_settings()` 내 ATI_SETUP write가 Full 설정을 덮어쓰지 않도록 처리
4. **상태머신 분기**: 초기화 후 re-ATI를 `try_finish_init()`이 오인하지 않도록 처리
5. **Reseed 노터치 게이트**: M2(이미 구현)에 추가로 drv.c:1134 Reseed 앞에 게이트 추가

> **한 줄 결론**: M2·M3는 방향 옳으나 단독 구현은 미완 — M2는 이미 존재하나 노터치 게이트로 승격·timeout 추가 필요, M3는 Fast Filter Band 비대칭만 허용·실측 필수, autoATI 재활성화는 I2C 통신 관리·방전 ATI 충돌 처리·절전 분기를 모두 선행해야 기존 코드 회귀 없이 작동한다.
