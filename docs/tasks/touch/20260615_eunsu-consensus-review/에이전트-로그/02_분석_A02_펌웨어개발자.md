# A02 분석 — 임베디드 펌웨어 SW 개발자

> **TL;DR**: M2(터치 해제 대기 코드)는 현재 `s_boot_touch_ignore` 로직과 거의 동일하나 Reseed 직전 게이트로 승격하는 구조 차이가 핵심이다. M3(Beta 조정)는 LTA/Counts Filter Betas 레지스터 2~3개 변경으로 코드 범위는 좁으나 단일 Beta 상향은 약터치 흡수 위험이 있어 비대칭 Fast Filter Band 설계가 필수다. autoATI 재활성화 시 방전·절전·상태머신에 구체적 충돌 지점이 존재하며 각각 추가 처리가 필요하다. 손을 안 떼는 케이스는 timeout fallback 없이 무한 대기 위험이 있다.

---

## 1. 분석 범위

집중 항목:
- **M2**: 터치 해제 대기 코드의 구현 복잡도와 이전 분석 "Reseed 노터치 게이트"와의 관계
- **M3**: Beta 조정의 실제 코드 변경 범위와 Fast Filter Band 비대칭 구현 방법
- **autoATI 재활성화**: 기존 코드베이스(방전·절전·상태머신)에 미치는 영향
- **무한 대기 방어**: timeout fallback 필요성

---

## 2. M2 — 터치 해제 대기 코드 분석

### 2.1 현재 코드 상태 (`tdc_touch.c`)

현재 코드에는 이미 부팅 직후 터치 무시 로직이 구현되어 있다:

```c
// tdc_touch.c:46
static bool s_boot_touch_ignore = false;

// READY 전이 직후 (line 318~325)
tdc_touch_state_t boot_state = TDC_TOUCH_STATE_RESET;
tdc_touch_get_state(&boot_state);
if (boot_state == TDC_TOUCH_STATE_TOUCH) {
    s_boot_touch_ignore = true;
}

// 폴링 루프 (line 352~366)
if (s_boot_touch_ignore) {
    if (got_state && curr_state != TDC_TOUCH_STATE_TOUCH) {
        s_boot_touch_ignore = false;  // 해제 감지
    } else if (!s_boot_5s_warned && 5000 <= (curr_tick - s_boot_ready_tick)) {
        s_boot_5s_warned = true;     // 5초 경고 (LED), 그러나 대기 계속
    }
    return false;
}
```

은수님 M2("터치 인식 시 터치 해제 대기 코드")는 이 로직과 **거의 동일한 효과**를 이미 구현한다. 터치 이벤트를 상위 레이어에 전달하지 않으며, 해제 확인 후 정상 동작을 재개한다.

### 2.2 이전 분석 "Reseed 노터치 게이트"와의 차이

| 항목 | 현재 `s_boot_touch_ignore` (= M2 유사) | 이전 분석 "노터치 게이트" |
|---|---|---|
| **위치** | READY 전이 후 터치 이벤트 출력 차단 | **Reseed 발행 직전** 노터치 확인 |
| **보호 대상** | 상위 레이어 long-touch 판정 | **LTA baseline 오염 방지** |
| **적용 시점** | apply_settings() 호출 **이후** | apply_settings() 내 Reseed **이전** |
| **절전 모드** | func_sleep의 reseed()는 별도 처리 없음 | func_sleep reseed도 게이트 대상 |

**핵심 차이**: `s_boot_touch_ignore`는 Reseed가 먼저 실행된 후(drv.c:1134) 터치 판정만 막는다. 이전 분석의 "노터치 게이트"는 **Reseed 발행 자체를 지연**해 터치 상태 counts가 LTA seed로 들어가는 것을 원천 차단한다.

은수님 M2 구현만으로는 **LTA baseline 오염은 방지하지 못한다**. M2는 오염된 baseline 위에서 터치 이벤트 출력을 억제할 뿐이다. 자기정상화(손 떼면 LTA가 노터치로 수렴)를 통해 결과적으로 복구되지만, 수렴 과도구간 동안 감도 이상이 발생할 수 있다.

### 2.3 구현 복잡도 비교

**M2 유사 구현 (현행과 동일, 이미 존재)**:
- 코드 변경 거의 없음 — 현재 `s_boot_touch_ignore`가 이미 이 역할
- 단, timeout 처리가 5초 경고만 있고 강제 해제 없음 → 무한 대기 위험 잔존

**이전 분석 "Reseed 노터치 게이트" 구현**:
- `apply_settings()` 내 Reseed 호출(drv.c:1134) 앞에 `ch0_touch==0` 폴링 삽입
- `func_sleep` 내 `reseed()` 호출(main.c:880) 앞에도 동일 게이트 추가
- timeout 강제 시딩 + dirty 플래그 관리 필요
- 복잡도: 중간 — 구조 변경은 크지 않으나 두 호출 경로(부팅/절전) 모두 처리 필요

## 3. M3 — Beta 조정 코드 변경 범위

### 3.1 레지스터 위치 (데이터시트 §5.6)

Beta 관련 레지스터는 3종이다:
- **Counts Filter Betas** (레지스터 주소 미코드화, 추정 0x35~0x36 범위)
- **LTA Filter Betas** — LTA IIR 속도
- **LTA Fast Filter Betas** — Fast Filter Band 초과 시 적용되는 빠른 Beta

현재 코드(`tdc_drv_iqs323.c`)에서 Beta 관련 레지스터를 직접 설정하는 코드가 확인되지 않는다. `sensor_setup()`, `touch_settings()`, `write_ati_compensation()` 어디에도 Beta 레지스터 write가 없다 — **현재는 IC power-on reset 기본값을 그대로 사용 중**이다.

### 3.2 코드 변경 범위

Beta 단순 상향 (M3 문자 그대로 구현):
- `sensor_setup()` 또는 `apply_settings()`에 Beta 레지스터 write 1~2개 추가
- `tdc_drv_iqs323.h`에 Beta 상수 정의 추가
- 변경 범위: **매우 좁음** (파일 2개, 10줄 미만)

### 3.3 Fast Filter Band 비대칭 구현 (올바른 M3 구현)

단일 Beta 상향의 문제: LTA Beta를 높이면 손 뗀 방향(counts 증가 방향)뿐 아니라 터치 방향(counts 감소)도 빠르게 추적해 약터치가 LTA에 흡수되어 미인식된다.

올바른 구현은 **Fast Filter Band** 활용이다:

```
데이터시트 §5.6:
"If counts drift from LTA in the opposite direction to sensing by more than 
 the Fast Filter Band, fast filtering is applied."

self-cap(Sound1): 터치 방향 = counts 감소
→ 반대 방향 = counts 증가 (손 뗄 때)
→ Fast Filter Band는 손 뗄 때만 빠른 LTA 추적 적용
```

비대칭 설계:
- **일반 LTA Beta**: 보수적 유지 (약터치 흡수 방지)
- **Fast Filter Band**: 적절히 설정 (손뗌 방향 drift 감지 기준)
- **LTA Fast Filter Beta**: 크게 설정 (손뗌 후 빠른 LTA 수렴)

코드 변경 범위: `sensor_setup()` 또는 초기화 시퀀스에 Fast Filter Betas + Band 레지스터 3개 write 추가. 상수 정의 포함 약 15~20줄 추가.

**주의사항**: Beta 방향성(클수록 빠름)은 데이터시트에서 `alpha = Beta/256`으로 명시하며, 이는 현재 실칩 동작과 대조 확인이 필요하다(이전 분석 실측 게이트 항목).

## 4. autoATI 재활성화 — 기존 코드 충돌 분석

### 4.1 방전 코드(`discharge_crx0`)와의 충돌

현재 방전 코드(drv.c:938~951):
```c
write_register_discharge(0x30, TDC_DRV_IQS323_INACTIVE_RXS_CRX0_VSS, 0x00);
// 0x30 LSB = 0x02 (Linearise bit?)
write_register_discharge(0x30, 0x01, 0x01);  // CH0 복원
```

ATI Full 재활성화 시:
- ATI 진행 중 방전 write가 CH0 Sensor Setup을 덮어쓰면 ATI 수렴이 방해됨
- `write_ati_compensation()`에서 ATI Mode를 Full로 바꾸면, 200ms마다 실행되는 방전이 ATI 진행 중 레지스터를 건드린다

**충돌 해결 방안**: ATI 진행 중(`ati_active==1`) 방전 일시 정지 로직 필요. `tdc_touch_process()` 내 방전 호출 앞에 ATI 상태 확인 분기 추가.

### 4.2 절전 모드(`func_sleep`)와의 충돌

현재 절전 진입 시퀀스(main.c):
1. `apply_sleep_settings()` — threshold 255/255(둔감)
2. `ci_power_sleep()` — 클럭 전환
3. `reseed()` — threshold 100/80 복원 + LTA reseed

ATI Full 재활성화 후 절전 시:
- `apply_sleep_settings()`가 ATI FIXED 값(0x5C82/0x63EF)으로 MULT/COMP를 덮어씌움 → ATI Full과 모순
- 절전 중 ATI Full이 실행될 경우 ULP 전력 예산(200ms 폴링) 초과 가능성
- `reseed()` 호출이 ATI Full 진행 중이면 baseline 이중 조작 발생

**충돌 해결 방안**:
- `apply_sleep_settings()`에서 ATI Full 유지 경로 분기 추가
- 절전 모드에서 ATI Full을 일시 비활성하거나, 절전 중 Re-ATI를 차단하는 레지스터 설정 추가
- 이 부분은 상당한 코드 변경이 수반됨(절전 로직 전면 검토 필요)

### 4.3 초기화 상태머신과의 충돌

현재 `try_finish_init()`(tdc_touch.c:216):
```c
// is_auto_ati_done() 폴링 — ati_active bit(0x10 bit2) 감시
// INIT_TIMEOUT_MS(2500) 초과 시 강제 진행
```

ATI Full 재활성화 후 `write_ati_compensation()`이 ATI Full을 켜면:
- 초기화 완료 후에도 ATI가 다시 실행될 수 있음
- `try_finish_init()`의 `is_auto_ati_done()` 폴링이 re-ATI를 초기화 미완료로 오인할 위험
- 해결: 초기화 완료 후 ATI Full을 켜는 순서 또는, re-ATI 차단 플래그를 별도 관리

### 4.4 I²C 통신 중단 위험

이전 분석에서 "ATI Full 재활성 시 RDY 무응답" 위험을 명시했다. 현재 코드의 RDY 핸드셰이크(force_window_open, 45ms 타임아웃)가 ATI Full 실행 중 RDY가 점유되면 타임아웃 + 통신 실패 상태가 연속될 수 있다.

ATI Full 재활성화 구현 시 **I²C 통신 관리 선행이 필수**이며, 은수님 정리(M2·M3)에는 이 항목이 빠져 있다.

## 5. 무한 대기 처리 — timeout fallback 필요성

현재 `s_boot_touch_ignore` 로직:
- 5초 경과 시 경고 LED(`s_boot_5s_warned=true`) — 단 대기는 계속됨
- **무한 대기 해제 없음**: 손을 절대 안 떼면 `s_boot_touch_ignore`가 영구히 true 상태 유지

M2 구현에 추가 필요한 timeout fallback:

```c
// 제안 구조 (pseudo)
if (s_boot_touch_ignore) {
    if (got_state && curr_state != TDC_TOUCH_STATE_TOUCH) {
        // 정상 해제
        s_boot_touch_ignore = false;
        trigger_reseed_now();  // 이전 분석 "해제 순간 recapture"
    } else if (BOOT_TOUCH_TIMEOUT_MS <= elapsed) {
        // timeout fallback: 손 안 뗀 채로 강제 진행
        s_boot_touch_ignore = false;
        // 이 시점 LTA는 터치값 기준 — dirty 플래그로 표시
        s_baseline_dirty = true;
    }
    return false;
}
```

timeout 값 선택 기준: 인공와우 착용 특성상 부팅 중 손이 닿은 채 5초 이상 방치하는 시나리오가 실재한다(충전 중 부팅, 케이스 속 부팅). timeout은 사용자 불편(초기 감도 이상)과 무한 대기(먹통) 사이 균형.

## 6. 명제별 판정

| 명제 | 판정 | SW 구현 관점 근거 |
|---|---|---|
| M2 (터치 해제 대기 코드) | △ | 현행 `s_boot_touch_ignore`와 동일 효과. LTA 오염 방지를 위해선 Reseed 게이트(이전 분석 권고 A)로 승격 필요 |
| M3 (Beta 조정으로 빠른 수렴) | △ | 코드 범위 좁음(레지스터 3개). 단일 Beta 상향은 약터치 흡수 위험 → Fast Filter Band 비대칭 구현 필수 |

| 손 안 떼면? | ⚠️ | 현행 코드 무한 대기. timeout fallback 필수 |

## 7. 결론

은수님 M2와 M3는 구현 복잡도 자체는 낮으나, 이전 분석 결론과의 관계를 정확히 이해해야 올바른 구현이 된다:

1. **M2는 이전 분석 "Reseed 노터치 게이트"의 부분 구현**이다. LTA 오염 방지를 완전히 달성하려면 Reseed 발행 위치로 게이트를 이동해야 한다. 현행 `s_boot_touch_ignore`만으로는 오염 후 자기정상화를 기다리는 수동적 전략에 머문다.

2. **M3의 올바른 구현은 Fast Filter Band 비대칭 설계**다. 단일 LTA Beta 상향은 약터치 흡수 부작용이 있으므로 손뗌 방향(counts 증가)에만 빠른 필터가 적용되도록 Fast Filter Band를 활용해야 한다.

3. **autoATI 재활성화는 방전·절전·I²C 통신 세 곳에서 기존 코드와 충돌**한다. 단순히 `write_ati_compensation()`의 ATI Mode 비트를 Disabled→Full로 바꾸는 것만으로는 안 되며, 각 충돌 지점에 대한 처리가 선행되어야 한다. I²C 통신 관리(RDY 핸드셰이크 강화)는 그 중 가장 중요한 선행 항목이다.

4. **손 안 떼는 케이스에 timeout fallback**이 없으면 현행 코드는 무한 대기 상태가 된다. timeout 값과 강제 진행 시 dirty baseline 처리 정책이 명시적으로 설계되어야 한다.

> **한 줄 결론**: M2·M3는 방향 옳으나 단독 구현은 미완 — Reseed 게이트 승격·비대칭 Fast Filter Band·I²C 관리·timeout fallback을 함께 설계해야 기존 코드 회귀 없이 완전한 해결이 된다.
