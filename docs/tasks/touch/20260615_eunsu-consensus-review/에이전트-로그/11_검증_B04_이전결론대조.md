# B04 · 이전 결론 대조 검증 — 은수님 정리 vs 이전 분석 충돌 발굴

> **TL;DR**: 은수님 정리(M1~M9)를 이전 분석 결론(제어 재설계 분석·권고, 방전·autoATI 공존 권고, 은수님 안 평결·하이브리드 권고)과 1:1 대조한다. 발굴된 핵심 충돌 4건: ① I²C 무응답 위험 완전 누락(M1·M8), ② "터치 해제 대기"(M2) vs "Reseed 노터치 게이트"(권고 A) — 연결 대상이 다른 별개 해결책, ③ "autoATI Full 상시"(M8 묵시적)와 이전 권고("부팅 1회 + auto Re-ATI 끔")의 구조적 차이, ④ 방전 코드 0x30=Linearise(VSS 아님) 사실이 M4·M5 드리프트 원인 판단에 미치는 영향.

## 3. 충돌별 상세 분석

### C1 — I²C 무응답 위험: 완전 누락

#### 이전 결론의 핵심 경고

방전·autoATI 공존 권고 §2-라:

> "Full auto-ATI = I²C 무응답(현 펌웨어가 ATI Disabled 택한 실증 이유). I²C hang 중 방전 disable(0x02)만 들어가고 복원(0x01)이 막히면 **CH0 영구 disable + 터치 먹통**(verify 없어 SW 감지 불가)"

은수님 안 평결 §3 하이브리드 권고 표:

| 구성 | 출처 |
|---|---|
| **I²C 통신관리(RDY 핸드셰이크·타임아웃)** | 검증 V3 — ATI Full = I²C 무응답 재현 방지 |

#### 은수님 정리에서의 누락

M1~M9 전체에서 "I²C", "무응답", "hang", "통신 관리" 관련 언급이 일절 없다.

#### 누락의 의미

이 누락은 단순 생략이 아니다. 이전 분석에서 ATI Full 재활성의 **최대 실증 위험**으로 분류된 항목이다 — 현 펌웨어가 FIXED(ATI Disabled)를 택한 이유 자체가 바로 이 I²C 무응답 문제의 실제 경험이었다. M8에서 "autoATI + Beta만으로 모든 문제 해결"이라는 결론이 I²C 통신 관리를 전제로 하지 않는다면, 은수님 안은 과거 문제의 재현 경로를 열어두는 셈이다.

**판정**: M8의 "모든 문제 해결 예상"은 I²C 통신 관리(ATI Active 폴링, RDY 핸드셰이크 강화, 타임아웃 처리)를 사전 이행 조건으로 명시하지 않는 한 채택 불가.

### C2 — "터치 해제 대기 코드"(M2) vs "Reseed 노터치 게이트"(권고 A): 같은가 다른가

#### 은수님 M2의 의미

M2: "터치 중 LTA 업데이트 안 됨 → **부팅 터치 인식 시 터치 해제 대기 코드**로 해결"

이 표현이 가리키는 것: 부팅 시 터치가 인식된(ch0_touch==1) 상태라면 손을 뗄 때까지 대기하는 코드를 삽입하겠다는 것.

#### 이전 권고 A의 의미

권고 A: "`ch0_touch==0` 연속 N tick 확인 **후 Reseed 발행**"

이 권고가 연결하는 것: **Reseed(LTA 시딩) 시점**을 노터치 확인 후로 미루는 것. `tdc_drv_iqs323.c:1134`의 `apply_settings` Reseed와 `main.c:880`의 `func_sleep` reseed가 대상.

#### 차이점 분석

| 항목 | 은수님 M2 "터치 해제 대기" | 이전 권고 A "Reseed 노터치 게이트" |
|---|---|---|
| **연결 대상** | 부팅 초기 터치 인식 진입 로직 | Reseed(LTA 시딩) 타이밍 |
| **전제 조건** | ch0_touch==1 감지 후 대기 | ch0_touch==0 N tick 확인 후 시딩 |
| **기존 코드 활용** | `s_boot_touch_ignore` 확장(현재 READY 전이 직후 터치 체크) | `boot-touch-ignore`를 "baseline 확정 게이트"로 승격 |
| **해결하는 뿌리** | 뿌리 A(진입 baseline 오염) — 단 autoATI 맥락에서 | 뿌리 A 동일 — FIXED+Reseed 맥락에서 |
| **누락** | Reseed 타이밍 제어 명시 없음(LTA가 언제 시딩되는지) | 부팅 초기 대기 로직 명시 없음 |

#### 판정

**방향은 동일하나 완전히 겹치지 않는다.** M2는 "부팅 터치 상태에서 손 뗄 때까지 대기"를 의미하는 것으로 보이고, 권고 A는 "Reseed 발행 전 노터치 확인"이다. 두 개를 결합해야 완전한 보호가 된다:

- autoATI 시나리오(M2 전제): LTA가 Reseed 없이 IIR 추적으로 수렴하더라도, 손을 절대 안 떼는 경우의 안전망은 "N tick 노터치 게이트 + 강제 timeout fallback + dirty 플래그"이다.
- M2 단독으로는 "손을 안 떼면 무한 대기"라는 경계 조건이 미처리다. 이전 권고 A는 이 경계를 `timeout 강제 시딩 + dirty 플래그 + 해제 순간 1회 recapture`로 처리한다.

**∴ M2는 권고 A를 대체하지 못하고, 권고 A가 M2를 포함하는 상위 구현이다.**

### C3 — "autoATI Full 상시"(M1·M8 묵시)와 이전 권고 "부팅 1회 + Re-ATI 끔"의 구조적 차이

#### 은수님 안의 묵시적 전제

M1: "autoATI는 LTA→카운터 수렴 구조" → autoATI가 상시 활성화된 상태를 전제
M8: "autoATI + Beta 빠른 수렴만으로 모든 문제 해결" → autoATI 상시 활성 유지

#### 이전 결론이 구체화한 구조

방전·autoATI 공존 권고 §2:

> "'auto-ATI Full 상시'로는 공존 불가(Re-ATI 진동·I²C hang·0x30 비트 충돌)"
>
> "'부팅 1회 ATI + auto Re-ATI 끔(Disabled 고정) + LTA 추적'이면 공존 가능"

**충돌 4축**:
- 가: 방전이 0x30 LSB를 blind write → 매 200ms Re-ATI 관련 비트 클리어
- 나: 방전 복원 카운트 튐 → LTA ATI Band 이탈 → auto Re-ATI 재트리거 → 진동
- 다: ATI 수렴 중 채널 disable 토글이 수렴 교란
- 라: Full auto-ATI = I²C 무응답

#### 판정

"autoATI Full 상시"와 "부팅 1회 + auto Re-ATI 끔"은 **같은 autoATI 복귀 방향이지만 구현 구조가 다르다.** 방전을 유지하는 한 Full 상시는 4축 충돌로 불가하고, Re-ATI 억제(Disabled 고정) + 필요 시 수동 Re-ATI 방식이 이전 분석의 결론이다.

은수님 안이 "방전 불필요(autoATI가 드리프트 해결)"로 방향을 잡는다면(M8의 함의), 방전을 폐기하는 전제에서 Full 상시가 가능해지는데, 이는 **"0x30=VSS 실측" + "ESD 정체(드리프트 vs 물리누적) 실측"** 두 게이트가 선행되어야 한다.

**∴ 방전 폐기 없이 "autoATI Full 상시" = 이전 결론과 구조적 충돌. 방전 폐기를 전제한다면 두 실측 게이트 필수.**

### C4 — 0x30 방전 코드 = Linearise 사실이 M4·M5 드리프트 원인 판단에 미치는 영향

#### 이전 결론의 치명 발견

방전·autoATI 공존 권고 §3:

> "`discharge_crx0`의 `0x30 LSB 0x02`는 데이터시트 A.5상 **'Linearise=1 + Enable=0'이지 CRX0 VSS가 아니다**. 핀 VSS 단락은 `0x34`(Inactive Rxs). → 현재 코드는 '채널 disable→enable + Linearise flip'일 뿐, 핀-VSS 물리 단락이 일어난다는 보장이 없다."

#### 은수님 M4·M5의 전제

- M4: "DC 블로킹 캡(C51 100pF) 때문에 터치패드보다 **IC 내부 드리프트**가 주원인 예상"
- M5: "먹통 상태 + 충전기 연결 → 터치 복귀 (DC 블로킹 캡 있어 터치패드 주원인 아님)"

이 판단의 논리 구조:
1. 방전이 실제로 전하를 방전시키고 있다고 전제
2. 방전에도 불구하고 드리프트가 발생 → 터치패드 외부 물리 전하가 아닌 IC 내부 LTA 드리프트가 주원인

#### 충돌 지점

만약 현재 방전 코드(0x30 0x02)가 실제 핀-VSS 단락이 아니라면:

- 방전 효과가 없었을 가능성 → M4의 "방전에도 드리프트 발생 → IC 내부 드리프트가 주원인" 추론이 성립하지 않을 수 있음
- 진짜 VSS 방전(`0x34` 경로)을 한 번도 시도하지 않았다면, "DC 블로킹 캡으로 인한 외부 전하 누적" 가설이 여전히 열려 있음

#### M5 "충전기 연결 → 복귀" 해석에 미치는 영향

M5의 "복귀"는 충전기 연결 시 무언가가 달라졌기 때문인데, 방전이 실제 방전이 아니었다면:
- IC VCC/GND 변동 → IC 내부 리셋 유발 가능성
- 방전 물리효력과 무관하게 전원 변화로 복귀했을 가능성

이 경우 "방전이 효과 없다(DC 블로킹 캡으로 외부 전하 차단됨)"는 M5의 방향 추론은 강화되나, **"방전이 실제로 방전하고 있다"는 전제 자체는 실측 없이 확인 불가**하다.

#### 판정

M4·M5의 결론 방향(IC 내부 드리프트 주원인)이 옳을 가능성이 높으나, 이 결론은 "현재 방전이 실제 방전 효과를 낸다"는 전제 위에서만 완전한 논거가 성립한다. 0x30=Linearise라는 이전 결론이 맞는다면, M4·M5의 추론 경로에 전제 결함이 있고 "방전 물리효력 실측"이 M4·M5 신뢰 전 선행 필요하다.

### C5 — M9 "Max Counts 증가"와 "Max Counts stuck" 위험 미고려

#### 은수님 M9

"카운터 최대값 4096보다 크게 하면 더 안정적일까?"

#### 이전 분석의 Max Counts 맥락

A01 분석 §5.3: `§5.4.2: "정상 동작 예상 max counts 위의 가장 작은 max counts 설정 선택 권장."` Max Counts 초과 시 **conversion 정지, max value가 read됨** — 이는 stuck-at-max 상태로, 터치 감지 완전 불가가 된다.

데이터시트 A.7 bits[7:6]: 4095(현재) → 16383으로 1단계 상향 가능.

#### 충돌

M9는 "크게 하면 더 안정적"이라는 방향을 묻는데, **stuck-at-max 위험이 오히려 감지 범위를 넓혀서 비정상 하드웨어 상태를 조기에 차단하는 기능을 약화시킬 수 있다**는 역효과를 고려하지 않았다.

단, autoATI 활성화 시 터치 counts를 ATI Target(400)으로 정규화하면 손 뗄 때 noTouch counts가 배율만큼 상승하므로 Max Counts 4095 충돌 위험이 실재한다. 이 맥락에서 16383은 완충 효과가 있다.

**판정**: M9 방향(16383으로 상향)은 기술적으로 가능하고 autoATI 활성 시 보조 안전망으로 유효하나, 근본 해결책이 아니라 보조 안전망 수준이며 stuck 위험 역효과와의 트레이드오프 검토가 누락됐다.

### C6 — "frozen 덕분" vs "frozen 부재 덕분": 메커니즘 반전

#### 은수님 M2의 기저 논리

M2: "터치 중 LTA 업데이트 안 됨 → 부팅 터치 인식 시 터치 해제 대기 코드로 해결"

기저 가정: "터치 중에는 LTA frozen → 손 떼면 LTA가 정상값으로 복귀"

#### 이전 결론의 수정

은수님 안 평결 §1-1:

> "frozen은 '터치로 **인식된** 후'에만 걸리는데, 부팅 시 baseline이 터치값이면 delta≈0이라 **터치로 인식 자체가 안 돼 frozen이 안 걸립니다.** 자기정상화는 'frozen **덕분**'이 아니라 'frozen이 **없어서**' 손 떼면 LTA가 자유롭게 noTouch를 추적하는 것."

#### 판정

M2의 결과(손 뗀 후 수렴)는 성립하나, 원리 설명이 데이터시트와 반대다. 이 반전이 실행 시 문제를 일으키는 경우:

- "터치 해제 대기 코드"가 "ch0_touch==1 감지 후 대기"로 구현된다면, 부팅 시 baseline 오염 상태에서는 **ch0_touch==1이 절대 set되지 않는다** — 즉 대기 조건이 발동하지 않아 코드가 무의미해진다.
- 올바른 구현: ch0_touch==0을 N tick 확인하는 형태여야 하며(권고 A 방식), ch0_touch==1 대기는 이 시나리오에서 무의미하다.

**∴ "frozen 부재" 원리를 이해하지 못하면 터치 해제 대기 코드를 잘못 구현할 위험이 있다.**

## 5. 결론: 누락의 의미와 통합 방향

### I²C 무응답 누락의 의미

이것은 "은수님이 간과한 항목"이 아니라 이전 분석이 새로 발굴한 항목이다. 현 펌웨어가 ATI Disabled를 택한 근본 이유가 이 경험이었으므로, M8("autoATI + Beta만으로 해결")이 성립하려면 반드시 I²C 통신 관리를 전제 조건으로 명시해야 한다.

### "터치 해제 대기"와 "Reseed 노터치 게이트"의 통합

M2의 의도(손 뗀 후 정상화 대기)와 권고 A(Reseed 노터치 게이트)는 상호 보완 관계다. M2 단독으로는 autoATI 시나리오에서 "손을 절대 안 떼면 무한 대기" 경계 조건이 미처리다. 통합 구현:

```
ch0_touch==0 N tick 확인(권고 A 방식)
  → 손 떼지 않으면: timeout 강제 시딩 + dirty 플래그 + 해제 순간 recapture(권고 A §1)
  → 손 뗀 후: 정상 LTA 수렴 진행(M1·M2 의도 달성)
```

### 최종 판정

은수님 정리는 **방향 정합성은 높다.** 그러나 이전 결론 대조 관점에서 다음 4개 사항이 M8의 "모든 문제 해결" 주장을 조건부로 만든다:

1. **I²C 통신 관리 선행** — 생략하면 과거 문제 재현
2. **"터치 해제 대기" 구현을 ch0_touch==0 확인 방식으로** — frozen 원리 반전 이해 필수
3. **방전 유지 시 "Full 상시" 불가** — "부팅 1회 + Re-ATI 끔" 구조 채택
4. **0x30 방전 실측 선행** — M4·M5 드리프트 판단의 전제 결함 해소

이 4개가 해소되면 은수님 안과 이전 결론은 **상호 보강 하이브리드**로 수렴한다.

> **은수님 정리에서 이전 결론 대조 최대 누락은 I²C 무응답 위험(C1)이며, "터치 해제 대기"(M2)와 "Reseed 노터치 게이트"(권고 A)는 같은 방향이나 대상이 달라 중복이 아니고(C2), "autoATI Full 상시"와 이전 권고 "부팅 1회 + Re-ATI 끔"은 방전 공존 전에 구조적으로 다르며(C3), 0x30=Linearise 사실이 M4·M5 드리프트 원인 판단의 전제를 흔든다(C4). 네 충돌을 처리하면 은수님 안과 이전 결론은 하이브리드로 통합된다.**
