# A01 · IC전문가 분석 — 은수님 명제 M1~M9 데이터시트 검토

> **TL;DR**: 은수님 명제 M1~M9를 IQS323 데이터시트(§5.5·5.6·5.9·5.10·5.11, A.7·A.12·A.26~A.30) 원문으로 검토한다. 핵심 판정: M1(수렴 가능하나 조건부), M2(부분 성립—동결이 아닌 자유 추적이 원인), M3(성립, 단 Fast Filter Band 설정 필수), M8(방향 옳음, 단 노터치 게이트 안전망 필수), M9(16383 가능, 그러나 부작용 있음).

## 2. M1 — autoATI + LTA 수렴 메커니즘

### 판정: 조건부 지지 (수렴은 가능, Max Counts 충돌·ATI Error 게이트 통과 필요)

### 2.1 autoATI의 실제 역할

§5.9는 ATI 알고리즘이 "각 채널의 divider·multiplier·compensation을 선택"하며 "ATI 트리거 시 먼저 divider·multiplier로 counts를 ATI Base에 최대한 근접시키고, 그 다음 Compensation Value·Compensation Divider로 ATI Target에 근접"시킨다고 명시한다.

**중요한 사실**: ATI 알고리즘은 입력 counts의 절대값에 무관하게 그 시점 counts를 ATI Target으로 정규화하는 것이 목적이다(§5.9 개념해설). 따라서:

- 부팅 시 손가락이 올려진 채로 autoATI가 실행되면, 터치 counts(낮은 값)를 기준으로 MULT/COMP가 설정된다.
- 손을 떼면 noTouch counts가 터치 counts보다 높아지므로 LTA(IIR로 noTouch 추적)가 noTouch 방향으로 수렴한다.
- M1의 "autoATI + 손 떼면 수렴" 흐름은 **메커니즘상 가능**하다.

### 2.2 LTA 수렴의 실제 경로

**결정적 사실**: ATI 알고리즘(§5.9) 자체는 LTA를 건드리지 않는다. ATI는 MULT/COMP만 조정한다. LTA 갱신은 §5.5 IIR이 담당한다.

```
LTA_new = LTA_old + (Counts − LTA_old) × (Beta / 256)
```

부팅 시 터치 상태라도 `(LTA − Counts) ≈ 0` → delta 미달 → CH0 Touch bit 미set → LTA frozen 조건 미충족 → LTA는 계속 갱신된다. 손을 떼면 counts 상승 → LTA가 IIR로 noTouch 값 추적 → 수렴.

**∴ M1의 "autoATI → 수렴"은 성립하나, LTA 수렴의 실제 엔진은 autoATI가 아니라 IIR(Beta/256)이다.**

### 2.3 Max Counts 충돌 위험

터치 중 autoATI가 터치 counts(낮은 값)를 ATI Target으로 정규화하면, 손 뗄 때 noTouch counts가 그 배율만큼 상승한다. A.7 bits[7:6] Max Counts(기본값 0x1290의 bits[7:6]=10 → 4095)가 있으나, 정규화 비율에 따라 초과 위험이 있다.

§5.4.2: "ATI 설정·하드웨어가 한계 초과 count를 유발하면 **conversion 정지, max value가 read됨**."

실측 게이트: 터치/noTouch raw counts 비율로 Max Counts 충돌 여부 확인 필요.

## 3. M2 — 터치 중 LTA 업데이트 안 됨 (데이터시트 근거)

### 판정: 부분 성립 — "이미 인식된 터치"에만 적용, 부팅 터치는 적용 불가

### 3.1 데이터시트 원문 (§5.5)

> "LTA는 환경 변화 추적 위해 천천히 갱신되며 **touch·proximity 이벤트 중에는 frozen**."

§5.5 개념해설: "터치 상태에서 LTA가 계속 갱신되면 터치된 counts(낮은 값)를 기준선으로 학습해버린다. … 이를 막기 위해 터치·근접 이벤트 중에는 LTA 갱신을 멈춘다."

### 3.2 frozen의 전제 조건 (결정적)

frozen은 `CHx Touch bit` 또는 `CHx Prox bit`가 set된 상태에서만 발동된다(A.2 System Status bit9 CH0 Touch, §5.7 "상태 진입 시 bit set").

**부팅 직후 터치 시나리오**:

- 부팅 시 LTA가 터치 counts로 시딩되면 `LTA ≈ Counts` → `delta = LTA − Counts ≈ 0`
- 터치 진입 조건 `(LTA − Counts) > Touch Threshold` 미충족 → CH0 Touch bit = 0
- CH0 Touch bit = 0 → frozen 미발동 → LTA 갱신 계속

**결론**: M2의 "터치 중 LTA 업데이트 안 됨"은 데이터시트 사실이나, 부팅 직후 baseline이 터치값으로 오염된 경우 터치가 인식되지 않으므로 frozen이 적용되지 않는다. 즉 **"터치로 인식된 후"에만 frozen이 보장된다.**

손 뗐을 때의 자기 정상화가 가능한 이유도 "frozen 덕분"이 아니라 "frozen이 안 걸려서 LTA가 noTouch를 자유롭게 추적하기 때문"이다. **메커니즘 설명이 데이터시트와 반대이나 결과(손 뗀 후 수렴)는 성립한다.**

## 4. M3 — Beta 파라미터 의미 및 Fast Filter Band 비대칭

### 판정: 지지 — 단 비대칭 설계가 필수, 단일 상향은 약터치 흡수 위험

### 4.1 Beta 파라미터의 의미

§5.6 데이터시트 원문:

$$\text{Damping factor} = \frac{\text{Beta}}{256}$$

```
LTA_new = LTA_old + (Counts − LTA_old) × (Beta / 256)
```

**Beta가 클수록 빠르다**: Beta=15(최대)이면 alpha≈5.9%로 현재 측정값이 5.9% 반영된다. Beta=1이면 alpha≈0.4%로 느리게 추적한다.

| Beta | alpha (Beta/256) | 특성 |
|---|---|---|
| 1 | ≈0.4% | 매우 느린 추적, 강한 스무딩 |
| 4 | ≈1.6% | 느린 추적 |
| 8 | ≈3.1% | 중간 |
| 15 | ≈5.9% | 가장 빠른 추적 (4비트 상한) |

**중요**: Beta 레지스터는 4비트(0~15)이므로 최대 alpha≈5.9%. 즉 항상 강한 스무딩이 적용되고 즉시 수렴은 불가하다. 90% 수렴에는 Beta=15에서도 약 38 샘플이 필요하다.

### 4.2 Beta=0의 특수 상황

현재 코드에서 0xB0~0xB4 레지스터 write가 전무하므로 POR default 0x0000 상태다. Beta=0이면 `alpha = 0/256 = 0` → `LTA_new = LTA_old` → **LTA 완전 동결** 상태로 해석된다(데이터시트가 Beta=0 동작을 명시하지 않아 IC 내부 해석에 따라 다를 수 있음 — 실측 필요).

### 4.3 Fast Filter Band 비대칭 설계

§5.6: "counts가 LTA로부터 **sensing 반대 방향으로 Fast Filter Band 이상** drift하면 fast filtering 적용."

self-cap에서 sensing 방향 = counts **감소**(터치). 따라서 "sensing 반대 방향" = counts **증가** = **손을 뗀 직후 구간**이다.

**비대칭 설계 원리**:

```
[일반 LTA Beta] 보수적 (Beta 작게): 약하거나 느린 터치를 LTA가 흡수하는 것을 방지
[Fast Filter Beta] 공격적 (Beta 크게): 손 뗀 직후 counts 증가 시에만 빠른 수렴 가속
[Fast Filter Band (0xB4)]: 노이즈 < Band < 약터치 delta 창으로 설정
```

이 비대칭 설계는 은수님의 "빠른 수렴" 의도를 달성하면서 약터치 흡수 부작용을 회피하는 유일한 경로다.

### 4.4 단일 LTA Beta 상향의 위험

LTA Beta를 단순히 크게 올리면 "약하거나 천천히 누르는 터치"를 LTA가 따라가 delta가 threshold에 도달하기 전에 수렴 → **터치 미인식**이 발생한다. 인공와우 사용자 특성(약한/느린 접촉 가능)과 충돌한다.

## 5. M9 — Max Counts 4096 이상 설정의 데이터시트 지원 여부

### 판정: 지원됨 (16383까지 가능), 단 실용적 이득은 제한적이고 부작용 있음

### 5.1 데이터시트 지원 여부

A.7 Prox Control bits[7:6] Max Counts:

| bits[7:6] | Max Counts |
|---|---|
| 00 | 1023 |
| 01 | 2047 |
| 10 | 4095 (Sound1 현재 설정: 0x1290 → bits[7:6]=10) |
| **11** | **16383** |

Sound1 현재 설정(0x32=0x1290, bits[7:6]=10)은 4095. M9가 묻는 "4096보다 크게" = 16383(bits[7:6]=11)으로 변경하면 데이터시트상 지원된다.

### 5.2 효과

Max Counts를 16383으로 올리면 counts가 이 범위 내에서 더 자유롭게 변동할 수 있다. ATI 정규화 후 noTouch counts가 더 높게 안착하더라도 conversion이 정지하지 않는다.

**단 실용적 이점의 한계**:

- ATI Target(현재 400)은 MULT/COMP로 정규화되는 목표값이다. Max Counts는 상한 가드이므로, 정규화가 잘 되면 노터치 counts가 400 부근에 머무르고 Max Counts를 올려도 실질 효과는 없다.
- M1에서 분석한 것처럼 터치 중 autoATI가 터치 counts를 Target=400으로 정규화하면 손 뗄 때 noTouch counts가 배율만큼 상승한다. 이때 Max Counts가 4095이면 conversion 정지 위험이 있고, 16383으로 올리면 이 위험을 완충한다.

### 5.3 부작용

§5.4.2: "정상 동작 예상 max counts 위의 가장 작은 max counts 설정 선택 권장."

Max Counts를 과도하게 높이면:
1. 비정상 하드웨어/설정 오류로 인한 비정상 counts를 조기에 차단하지 못한다.
2. §5.9 ATI 알고리즘이 넓은 탐색 범위에서 수렴하는 데 더 많은 시간을 소비할 수 있다.

**∴ M9는 "4096보다 크게(=16383)"로 설정 가능하며, M1의 Max Counts 충돌 위험 완충에 유효하다. 단 근본 해결책은 autoATI + 노터치 게이트 조합이고, Max Counts 상향은 보조 안전망이다.**

## 6. ATI Full 재활성 시 I²C 동작 — M8 관련

### 판정: 무응답 위험 실재 — 통신 관리 선행 필수

### 6.1 데이터시트 메커니즘

A.2 System Status bit5: **ATI Active** — "0 not active · 1 ATI active"

ATI 실행 중에는 IC가 내부적으로 MULT/COMP 탐색을 수행하며, 이 기간 동안 통상 I²C 통신 응답이 지연될 수 있다.

§5.11 IMPORTANT: "ATI Error 발생 시 re-ATI가 자동 트리거되지 않는다. master가 System Control의 Re-ATI bit set으로 수동 트리거해야 함."

### 6.2 I²C 무응답 메커니즘

기존 분석(개념 종합가이드 §5.6, 펌웨어 구현 분석)에서 확인된 사례:

```
Stuck-Touch 발생
  → IC 내부 자동 re-ATI 발동 (ATI Mode=Full 상태)
  → COMP 값 급변
  → ATI Active bit set (bit5 = 1)
  → ATI_Error bit set (bit6 = 1)
  → 이 구간 동안 I²C 통신 무응답
```

§5.11에 "master가 Re-ATI bit set으로 수동 트리거"가 필요하다는 것은 IC가 ATI Error 후 자동으로 복구하지 않는다는 것을 의미한다.

### 6.3 Sound1이 ATI Disabled를 선택한 이유 재확인

개념 종합가이드 §5.6: "이전 펌웨어에서 ATI Mode=Full(autoATI 허용) 사용 시 I²C 무응답 발생. 원인: Stuck-Touch → re-ATI → COMP 급변 → ATI_Error → 통신 이상."

M8에서 은수님이 제안하는 autoATI 복귀는 이 위험을 재현할 가능성이 있다. **따라서 ATI Full 재활성 시에는 반드시 RDY 핸드셰이크 강화 + ATI Active 폴링 + 타임아웃 처리가 선행되어야 한다.**

## 8. 집중 항목 정밀 판정

### 8.1 M1 — autoATI의 LTA 수렴 구조

**결론**: autoATI 자체는 LTA를 직접 건드리지 않는다. 수렴 경로는 다음이다:

```
부팅 + 터치 상태
  → autoATI 실행: 터치 counts를 ATI Target으로 MULT/COMP 조정
  → 손 뗌: noTouch counts 상승
  → LTA frozen 미발동(delta≈0이므로 터치 미인식)
  → IIR(Beta/256)이 noTouch counts를 추적
  → LTA가 noTouch 수렴 (수렴 속도는 Beta·Fast Filter Band 의존)
  → 이후 터치 시 delta = LTA − Counts 증가 → 정상 인식
```

은수님 M1("autoATI → 수렴")의 방향은 옳으나 "autoATI가 LTA를 잡는다"는 인과는 부정확하다. 실제 수렴은 IIR이 담당한다.

### 8.2 M2 — 터치 중 LTA 업데이트 근거

데이터시트 §5.5 명시: "touch·proximity 이벤트 중에는 frozen." 단 이 frozen은 CH0 Touch bit(A.2 bit9)가 set된 상태에서만 발동된다.

부팅 시 터치 상태에서는 delta≈0으로 Touch bit가 미set → frozen 미발동 → LTA 갱신 계속 → 터치 counts를 학습. 이것이 이전 분석에서 "진짜 뿌리: Reseed가 부팅 시 터치 counts로 LTA seed → baseline 오염"으로 귀결된 이유와 동일한 메커니즘이다.

### 8.3 M3 — Beta 값과 Fast Filter Band 비대칭 구현 필요성

데이터시트 §5.6의 비대칭 설계 근거:

- **Fast Filter Band(0xB4)**: sensing 반대 방향(self-cap에서 counts 증가=손 뗌 방향)에서만 fast beta 발동
- **일반 LTA Beta(0xB1 하위 바이트 NP)**: 보수적 (약터치 흡수 방지)
- **LTA Fast Filter Beta(0xB2 하위 바이트 NP)**: 공격적 (손 뗌 후 빠른 수렴)

이 비대칭 구조는 "일반 환경 드리프트 추적은 느리게, 손 뗀 직후 복귀는 빠르게"를 물리적으로 분리 달성한다.

현재 코드에서 0xB0~0xB4 모두 미write(POR default 0x0000)이므로 은수님 안 구현 시 이 레지스터들을 명시적으로 write해야 한다.

### 8.4 M9 — Max Counts 16383 설정

A.7 bits[7:6]=11 → Max Counts=16383. 기술적으로 가능하며 autoATI 활성화 시 터치 counts 정규화 후 noTouch counts가 상승할 때 conversion 정지를 방지하는 완충 역할을 한다.

단 데이터시트 §5.4.2의 "정상 동작 예상 max counts 위의 가장 작은 max counts 설정 선택 권장"에 따르면 과도한 상향은 하드웨어 이상 감지 능력을 낮춘다. 필요 최소값 선택이 원칙이다.

### 8.5 ATI Full 재활성 시 I²C 위험

A.2 bit5 ATI Active가 set되는 동안 통신 창이 정상적으로 열리지 않을 수 있다. §5.11 ATI Error 발생 시 자동 재시도가 없으며 SW가 수동 트리거해야 한다. 이 구간 동안 CM3의 I²C 통신이 타임아웃되거나 무응답 상태가 된다.

**대응 필수 항목**:
1. ATI Full 진입 전 RDY 상태 확인
2. ATI Active bit(bit5) 폴링으로 완료 대기
3. ATI Error bit(bit6) 확인 및 Re-ATI 수동 트리거 에러 핸들러
4. I²C 타임아웃 및 재시도 로직

## 9. 종합 결론

### 9.1 은수님 분석의 핵심 가치

은수님의 M1·M8("autoATI + 빠른 수렴으로 부팅 터치 문제 해결")의 방향은 데이터시트상 성립한다. "잘못 시딩돼도 자기 정상화" 통찰은 올바르다. 단:

1. **메커니즘 설명 수정 필요**: 자기 정상화는 "frozen 덕분"이 아니라 "frozen이 안 걸려서(delta≈0으로 터치 미인식) LTA가 자유롭게 noTouch를 추적하기 때문"이다.
2. **손 안 떼면 LTA 고착**: 손을 계속 대고 있으면 LTA가 터치 counts를 영구 학습 → 노터치 게이트(boot_touch_ignore 승격) 안전망 필수.
3. **Beta 비대칭 설계**: 단일 LTA Beta 상향은 위험. 일반 Beta 보수적 + Fast Filter Band 활용으로 비대칭 구현해야 한다.
4. **I²C 통신 관리**: ATI Full 재활성 전 통신 관리 코드 선행 필수.
