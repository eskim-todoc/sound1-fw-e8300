# B01 · 데이터시트 검증자 — 은수님 명제 adversarial 검증

> **TL;DR**: M1은 방향 옳지만 "autoATI가 LTA를 직접 seed"한다는 인과가 데이터시트와 불일치(LTA는 IIR이 담당). M2는 frozen 조건이 "이미 인식된 터치"에만 적용되므로 부팅 시나리오에서 적용 불가. M3는 "Beta 클수록 빠름"이 데이터시트 정확히 일치하나 단일 상향은 약터치 흡수 위험. M9는 16383까지 데이터시트 지원 가능하나 보조 역할에 그침.

---

## 1. 검증 범위와 방법

이 문서는 **데이터시트 원문 조항**만을 근거로 판정한다. SW 코드·회로 분석·실측 추론은 인용하되 판정 근거로 삼지 않는다. 틀린 주장은 어느 문장이 틀렸는지 데이터시트 인용과 함께 명시한다. 맞는 주장도 인정한다.

집중 항목:
- **M1**: autoATI의 LTA seed 인과 — "LTA→카운터 수렴 구조"가 데이터시트와 일치하는가?
- **M2**: "터치 중 LTA 업데이트 안 됨" — frozen 조건이 부팅 시나리오에 적용되는가?
- **M3**: Beta 값 방향 — 클수록 빠른가 느린가?
- **M9**: ATI Target Counts 4096 초과 설정 — 데이터시트가 지원하는가?

---

## 2. M1 — autoATI + LTA 수렴 구조

### 2.1 은수님 주장 원문

> "autoATI는 LTA→카운터 수렴 구조 → 터치된 채 부팅이어도 손 떼면 수렴함"

### 2.2 데이터시트 조항 인용

**§5.9 ATI (Automatic Tuning Implementation)**:
> "ATI 알고리즘이 각 채널의 divider·multiplier·compensation을 선택."
> "ATI 트리거 시 먼저 divider·multiplier로 counts를 ATI Base에 최대한 근접시키고, 그 다음 Compensation Value·Compensation Divider로 ATI Target에 근접."

**§5.5 LTA**:
> "LTA는 환경 변화 추적 위해 천천히 갱신되며 touch·proximity 이벤트 중에는 frozen."
> LTA 갱신 공식: `LTA_new = LTA_old + (Counts − LTA_old) × (Beta / 256)`

### 2.3 판정: 부분 성립 — 인과 연결이 부정확

**옳은 부분**: 결과("손 떼면 수렴")는 성립한다.

**틀린 부분**: "autoATI가 LTA를 수렴시킨다"는 인과 연결이 데이터시트와 불일치한다.

데이터시트에 따르면:
- §5.9: ATI 알고리즘은 **MULT/COMP만 조정**한다. LTA를 직접 seed하거나 갱신하는 메커니즘이 없다.
- §5.5: LTA 갱신은 **IIR(Beta/256) 필터**가 담당한다.

수렴의 실제 경로는 다음과 같다:

```
부팅 + 터치 상태
  → autoATI: 터치 counts(낮은 값)를 기준으로 MULT/COMP 조정
  → 결과: noTouch counts가 ATI Target보다 훨씬 높아짐
  → delta = LTA − Counts ≈ 0 (부팅 시 LTA seed = 터치 counts)
  → Touch bit 미set → frozen 미발동 → LTA IIR 갱신 계속
  → 손 떼면: noTouch counts 상승 → LTA가 IIR로 따라가며 수렴
  → 수렴 완료 후 delta = 정상 값 → 이후 터치 정상 인식
```

**수렴의 엔진은 autoATI가 아니라 §5.5 IIR(Beta/256)이다.** autoATI는 이 과정에서 MULT/COMP를 터치 기준으로 왜곡시켜놓은 전제 조건에 불과하다. "autoATI는 LTA→카운터 수렴 구조"라는 표현은 이 인과를 뒤섞은 것이다.

> [!WARNING]
> **추가 위험**: §5.4.2 Max Counts 조항. ATI가 터치 counts(낮은 값)를 ATI Target으로 정규화하면 손 뗄 때 noTouch counts가 배율만큼 상승한다. 현재 Max Counts 설정(0x1290 bits[7:6]=10 → 4095)을 초과하면 §5.4.2에 명시된 "conversion 정지, max value가 read됨" 상태가 된다. 이 경우 수렴 자체가 불가능해진다.

## 3. M2 — 터치 중 LTA 업데이트 안 됨

### 3.1 은수님 주장 원문

> "터치 중 LTA 업데이트 안 됨 → 부팅 터치 인식 시 터치 해제 대기 코드로 해결"

### 3.2 데이터시트 조항 인용

**§5.5 LTA** 원문:
> "LTA는 환경 변화 추적 위해 천천히 갱신되며 **touch·proximity 이벤트 중에는 frozen**."

**§5.7 Proximity and Touch Thresholds**:
> "상태 진입 시 `System Status`의 `CHx Prox`·`CHx Touch` bit가 set되어 이탈까지 유지."
> Touch 진입 조건: `(LTA − Counts) > Touch Threshold`

**A.2 System Status** bit9: `CH0 Touch` — "0 not in Touch · 1 in Touch"

### 3.3 판정: 조건부 성립 — frozen 전제 조건이 부팅 시나리오에서 미충족

**옳은 부분**: "터치 중 LTA 업데이트 안 됨"은 §5.5 데이터시트 사실이다.

**문제**: 이 frozen은 `CH0 Touch bit = 1`(터치로 인식된 상태)에서만 발동된다.

부팅 시 시나리오를 추적하면:

```
[부팅 + 터치 상태]
  1. LTA가 터치 counts로 seed됨 (Reseed 시점의 counts)
  2. LTA ≈ Counts → delta = LTA − Counts ≈ 0
  3. Touch 진입 조건: (LTA − Counts) > Threshold → 0 > Threshold → FALSE
  4. CH0 Touch bit = 0 (터치로 미인식)
  5. frozen 조건 미충족 → LTA 갱신 계속됨
```

**결론**: 부팅 시 터치 상태에서는 IC가 "터치"로 인식하지 않으므로(delta≈0) frozen이 발동되지 않는다. "터치 중 LTA 업데이트 안 됨"이 이 상황을 해결하는 근거가 되지 않는다.

은수님이 제안하는 "터치 해제 대기 코드"의 방향은 옳다. 다만 이것이 동작하는 이유는 "frozen 덕분"이 아니라 **손을 떼면 LTA IIR이 자유롭게 noTouch counts를 추적할 수 있기 때문**이다. frozen은 오히려 이 시나리오에서 작동하지 않는 것이 수렴을 가능하게 한다.

> [!NOTE]
> 이전 분석(A01)에서도 동일한 지적이 있었다: "자기 정상화는 'frozen 덕분'이 아니라 'frozen 부재 덕분'이 맞음." B01도 동일 판정이다.

## 4. M3 — Beta 값 방향 (클수록 빠른가 느린가)

### 4.1 은수님 주장 원문

> "Beta 값 조정으로 빠른 수렴 가능"

### 4.2 데이터시트 조항 인용

**§5.6 Filter Betas** 원문:
> "Damping factor = Beta / 256"
> LTA 갱신: `LTA_new = LTA_old + (Counts − LTA_old) × (Beta / 256)`

**§5.6 개념해설**:
> | Beta | alpha (= Beta/256) | 특성 |
> |---|---|---|
> | 1 | ≈ 0.4% | 매우 느린 추적, 강한 스무딩 |
> | 4 | ≈ 1.6% | 느린 추적 |
> | 8 | ≈ 3.1% | 중간 |
> | 15 | ≈ 5.9% | 상대적으로 빠른 추적 |
> "Beta가 클수록 현재 측정값이 더 많이 반영되어 빠르게 변화를 추적한다."

**§5.6 Fast Filter Band**:
> "counts가 LTA로부터 **sensing 반대 방향으로 Fast Filter Band 이상** drift하면 fast filtering 적용."
> "LTA Fast Filter Betas(0xB2)": NP_LTA_FAST_FILTER

### 4.3 판정: 방향 성립 — 단 단독 상향은 위험

**옳은 부분**: "Beta 클수록 빠른 수렴"은 §5.6 데이터시트와 정확히 일치한다.

**문제**: 레지스터 범위 제약과 약터치 흡수 위험.

첫째, Beta 레지스터는 4비트(0~15)이므로 최대 alpha = 15/256 ≈ 5.9%다. 90% 수렴에는 Beta=15에서도 약 38 샘플이 필요하다. "빠른 수렴"의 한계가 있다.

둘째, LTA Beta를 단일하게 크게 올리면:

```
[약터치·천천히 누르는 터치]
  → Counts가 LTA보다 서서히 감소 (self-cap: 터치 = counts 감소)
  → 빠른 LTA Beta가 이 감소를 따라감
  → (LTA − Counts)가 Threshold에 도달하기 전에 LTA가 추적 완료
  → delta 미달 → 터치 미인식
```

§5.6의 **Fast Filter Band**가 이 문제의 해결책이다:

- "sensing 반대 방향" = self-cap에서 counts **증가** 방향 = **손을 뗀 후 구간**
- 즉 Fast Filter는 손을 뗀 후 counts가 LTA보다 올라갈 때만 발동된다
- 터치 중(counts 감소)에는 Fast Filter가 적용되지 않는다

올바른 구현:
- `0xB1 NP_LTA_FILTER` (일반 LTA Beta): 보수적(작게) — 약터치·느린 터치 흡수 방지
- `0xB2 NP_LTA_FAST_FILTER` (Fast Filter Beta): 공격적(크게) — 손 뗀 후 빠른 수렴
- `0xB4 Fast Filter Band`: 노이즈 < Band < 약터치 delta 창으로 조율

은수님의 "Beta 값 조정으로 빠른 수렴 가능"은 방향은 옳으나, **어떤 Beta를 올려야 하는지**가 중요하다. LTA Beta 단독 상향은 역효과를 낳을 수 있다.

## 5. M9 — ATI Target Counts 4096 초과 설정

### 5.1 은수님 주장 원문

> "카운터 최대값 4096보다 크게 하면 더 안정적일까?"

### 5.2 데이터시트 조항 인용

**§5.4.2 Max Counts** 원문:
> "각 채널은 Max Counts(Prox Control) 한계 미만으로 제한. ATI 설정·하드웨어가 한계 초과 count를 유발하면 **conversion 정지, max value가 read됨**."
> "**정상 동작 예상 max counts 위의 가장 작은 max counts 설정 선택 권장.**"

**A.7 Prox Control bits[7:6] Max Counts**:
| bits[7:6] | Max Counts |
|---|---|
| 00 | 1023 |
| 01 | 2047 |
| 10 | 4095 |
| **11** | **16383** |

Sound1 현재 설정: 0x32 = 0x1290 → bits[7:6] = `10` → Max Counts = **4095**

**A.12 ATI Setup bits[2:0] ATI Mode**:
> "000 Disabled · 001 Compensation Only · 010 ATI from Compensation Divider · 011 ATI from Fine Fractional Divider · 100 Full"

ATI Target 공식: `ATI_TARGET = ATI_BASE × (ATI Resolution Factor / 16)` (§5.9)

### 5.3 판정: 기술적 지원됨 — 근본 해결이 아닌 보조 완충

**옳은 부분**: Max Counts 16383(bits[7:6]=11) 설정은 데이터시트가 명시적으로 지원한다. M9의 설정 자체는 가능하다.

**중요한 혼동**: "카운터 최대값"과 "ATI Target Counts"는 다른 개념이다.

- **Max Counts**: §5.4.2, A.7 — conversion 정지 방지용 상한. bits[7:6]=11로 16383 설정 가능.
- **ATI Target**: §5.9, A.12 — ATI 알고리즘이 수렴 목표로 삼는 counts 값. `ATI_BASE × (Resolution Factor / 16)`. Sound1 현재값 100 × (64/16) = 400.

은수님의 "카운터 최대값"이 어느 것을 가리키는지에 따라 판정이 달라진다:

**경우 1 — Max Counts를 16383으로 올리는 경우**:
- 데이터시트 지원: YES
- 효과: autoATI가 터치 counts를 ATI Target으로 정규화 후 손 뗄 때 noTouch counts 급상승 시 conversion 정지 방지
- 단, 데이터시트 §5.4.2 권고: "정상 동작 예상 max counts 위의 가장 작은 max counts 선택" — 과도한 상향은 비정상 오류 감지 능력 저하

**경우 2 — ATI Target(ATI Resolution Factor 조정)을 올리는 경우**:
- ATI Target = ATI_BASE × (Resolution Factor / 16). Resolution Factor를 올리면 Target이 높아진다.
- 단, Target을 높이면 delta(LTA − Counts)의 절대값이 커지는 대신 Threshold도 LTA 비율이므로 상대 감도는 변화 없다. "더 안정적"이 되는 것은 ATI 수렴 범위 여유가 생기는 측면이다.

**결론**: M9는 기술적으로 가능하다. 단 근본 문제(autoATI + 노터치 게이트)를 해결한 뒤의 보조 안전망이며, 그 자체로 안정성을 보장하지 않는다.

## 7. A01 분석과의 비교

A01(IC전문가) 분석과 B01(데이터시트검증자) 분석은 동일한 데이터시트 원문을 참조했으며 판정이 일치한다.

- **M1 일치**: A01 §2.3 "M1의 방향은 옳으나 autoATI가 LTA를 잡는다는 인과는 부정확하다. 실제 수렴은 IIR이 담당한다."
- **M2 일치**: A01 §3.2 "부팅 직후 delta≈0이면 Touch bit=0 → frozen 미발동. 메커니즘 설명이 데이터시트와 반대이나 결과(손 뗀 후 수렴)는 성립."
- **M3 일치**: A01 §4.3 "비대칭 설계 원리 — 일반 LTA Beta 보수적, Fast Filter Beta 공격적. 단일 상향 위험."
- **M9 일치**: A01 §5.2 "Max Counts 16383 가능, 단 보조 안전망 수준. 근본 해결책은 autoATI + 노터치 게이트."

## 8. 최종 결론 (B01 단독 판단)

은수님의 4개 명제 중 **완전히 틀린 것은 없다**. 그러나 **인과 설명에 오류가 있는 것이 2개(M1·M2)** 있고, **구현 방법이 중요한 것이 1개(M3)**, **효과가 제한적인 것이 1개(M9)** 있다.

**데이터시트가 명확히 반박하는 주장**:
1. M1의 "autoATI가 LTA를 수렴시킨다" — §5.9 ATI는 MULT/COMP만 조정. §5.5 LTA 갱신은 IIR(Beta/256)이 담당.
2. M2의 "frozen 덕분에 수렴한다" — §5.5 frozen 조건이 부팅 시 미충족(Touch bit=0). 수렴은 "frozen 부재" 덕분.

**데이터시트가 지지하는 주장**:
1. M3의 "Beta 클수록 빠른 수렴" — §5.6 Damping factor = Beta/256, 클수록 빠름 명시.
2. M9의 "4096 초과 가능" — A.7 bits[7:6]=11 → 16383 지원.

**실질 권고 (데이터시트 근거)**:
- M2 구현 시 "터치 해제 대기" 방향은 옳으나, 이것이 작동하는 이유를 "frozen" 대신 "IIR 자유 추적"으로 설명해야 코드가 올바르게 설계된다.
- M3 구현 시 반드시 비대칭 Beta(0xB1 보수적 + 0xB2 공격적 + 0xB4 Fast Filter Band)를 사용해야 약터치 흡수를 방지할 수 있다.
