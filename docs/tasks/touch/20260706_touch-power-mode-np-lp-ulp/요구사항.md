# 요구사항 — IQS323 전력모드(NP/LP/ULP) 딥다이브

**TL;DR**: 은수님이 IQS323 자체 내장 전력모드(NP/LP/ULP)를 새로 딥다이브하도록 지시했다 — ① 3모드 소비전력 비교, ② 현재 SW 동작 시나리오에서 LP/ULP가 동일 기능(터치 판정·ATI에러 처리·첫터치해제 감지)을 수행할 수 있는지(예시: ULP는 터치 발생 시에만 RDY가 0이 되어 통신 가능하므로 평상시 I2C 통신이 실패할 수 있다는 가설 검증 포함), ③ 각 모드의 센싱 주기(Report Rate) 차이와 현재 100ms SW 폴링 주기와의 정합성·전력효율 관점 최적화 방향. 새 작업 폴더, 여러 페르소나(그라운드·후보·검증)로 딥다이브.

## 1. 배경

- 선행 `20260703_touch-heisenberg-sw-mitigation`(S3 노드)이 **LP/ULP Automatic 자동모드 재도입에 명확히 반대**한 이력이 있다 — 코드 주석 근거: `tdc_touch_iqs323.c` `beta_power_settings()`의 `Power Mode Timeout=0` 설정 주석 "PM timeout 0 = 자동 강하 차단 → 노말 운용 중 NP 유지. (LP 전환 시 report rate 100ms 로 RDY 윈도우가 느려져 force_window_open 45ms 폴링이 윈도우를 놓쳐 timeout 발생. 터치=이벤트→NP 복귀로 회복되던 증상의 근본 차단. DS §5.3)" — 즉 **과거에 LP/ULP 자동전환을 실제로 시도했다가 회귀가 발생해 지금의 PM Timeout=0(강하 차단) 설정으로 고정한 이력**이 있다.
- 그 이후 이번 시리즈(`20260703_touch-heisenberg-config-reexplore`, `20260705_touch-event-mode-adoption` 1·2차)에서 force_window_open() 프로토콜, Report Rate 의미, RDY 윈도우 타이밍, 유휴구간 폴링 최적화 등에 대한 이해가 훨씬 깊어졌다 — 이 새 이해를 바탕으로 과거 회귀 진단이 지금도 유효한지, 혹은 회귀를 피하면서 LP/ULP를 활용할 SW 설계가 가능한지 재검토할 가치가 있다.
- 데이터시트 §3.4(Current Consumption, 원문 p.11) 확인된 수치(측정조건: self-cap **3채널**·Event mode·ATI Target 512·Fxfer 500kHz — 우리 구성인 **1채널**·Fxfer 1MHz와는 조건이 다름, 근사 필요):

| Power mode | Report rate | 3.3V 소비전류 |
|---|---|---|
| Normal Power | 16ms | 125µA |
| Low Power | 60ms | 37.5µA |
| Ultra Low Power | 160ms | 4.00µA |
| Halt | 3000ms | 2.00µA |

## 2. 은수님의 질문 (스코프)

1. **NP/LP/ULP 전력소모 비교** — 데이터시트 정량 수치를 우리 실제 구성(CH0 단일채널, Fxfer 1MHz, Streaming/Events 등)에 맞게 근사해 비교.
2. **현재 SW 동작 시나리오에서 LP/ULP가 동일 기능을 수행할 수 있는지** — 구체 예시(은수님 제시): "ULP는 터치가 발생해야 RDY가 0으로 내려가고 이때만 I2C 통신이 가능하므로, 평상시(터치 없을 때) I2C 통신이 실패한다 → SW 처리 로직을 바꿔야 한다" — 이 가설이 사실인지(force communication §8.13이 파워모드 무관하게 항상 창을 열 수 있는지 등) 정밀 검증하고, 만약 SW 로직 변경이 필요하다면 구체적으로 무엇을 바꿔야 하는지 도출.
3. **센싱 주기(Report Rate) 차이와 현재 100ms 폴링의 정합성** — 각 모드 Report Rate가 현재 SW의 100ms 폴링 주기와 어떻게 어긋나는지, 전력효율 관점에서 그 주기에 SW를 맞추는 것이 유리하다면 어떻게 해야 하는지.

## 3. 불변식 (계승)

`20260705_touch-event-mode-adoption` 시리즈와 동일한 INV-CTRL-1~3을 계승한다 — Full ATI·ATI에러 시 Re-ATI·첫 터치 해제 감지 3거동은 유지해야 하며, 그 외(레지스터·채널·측정방식·폴링 프로토콜)는 자유.

## 4. 제약

- SW-only, HW 무수정.
- 브랜치 `claude_feature_touch-mutual-cap-review` 유지.
- 코드 변경은 사용자 승인 후(④단계). 본 작업은 ①~③까지, 제품 소스 변경 0건 유지.
- 과거 회귀 이력(PM Timeout=0 결정)을 존중하되, "재도입 절대 반대"라는 과거 결론을 맹신하지 말고 지금 시점의 깊어진 이해로 독립 재검토한다.

## 5. 페르소나 구성 (그라운드3·후보3·검증4)

- **그라운드**: G1(NP/LP/ULP/Halt 전력소비 정량 재확인·우리 구성 근사), G2(각 모드 RDY/통신 동작 정밀 확인 — force communication의 파워모드 무관성이 핵심), G3(과거 회귀 정밀 재구성·현재 유효성 판단)
- **후보**: C1(LP 활용 시나리오), C2(ULP 활용 시나리오, 은수님 가설 정밀 검증 포함), C3(현재 100ms SW 폴링과 IC 파워모드 최적 매칭 설계 — 선행 `20260705` 시리즈의 "유휴 폴링주기 연장" 권고와의 관계 명확화)
- **검증**: V1(전력수치 반증), V2(force communication 파워모드 무관성 반증 — 최우선), V3(과거 회귀 재현여부 반증), V4(완전성비평+할루시네이션감사)
