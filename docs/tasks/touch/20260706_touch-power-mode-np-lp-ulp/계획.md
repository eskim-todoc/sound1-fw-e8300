# 계획 — IQS323 전력모드(NP/LP/ULP) 딥다이브 권고

**TL;DR**: 은수님 가설은 표면적으로는 반박되나("통신 자체는 항상 가능"), 그 우려의 본질(LP/ULP에서 SW가 못 따라감)은 Auto Prox Cycle Select라는 다른 메커니즘으로 되살아난다. 이번 라운드가 제안한 3개 활용 설계는 전부 미완결(조건부 해소·죽은 코드·설계 공백)이며, 무엇보다 선행 라운드가 확정한 255ms 워치독 공백을 통합하지 못했다 — **지금 바로 구현 승인할 단계가 아니다.** 권고는 실측(force comm 타이밍·Auto Prox Cycle 실제값·클럭 공차)을 먼저 하고, 그 결과로 후보_1·2·3을 통합·재설계하는 것이다. 본 계획은 방향 결정이며 코드 변경은 승인 후 별도 작업(④).

> [!IMPORTANT]
> 제품 소스 변경 0. 아래는 방향 결정이며, 실제 구현은 승인한 경로를 별도 작업으로 착수한다.

## 1. 결론 요약

- 은수님의 가설("ULP는 터치 시에만 통신 가능")은 **틀렸다** — Force Communication은 파워모드와 무관하게 항상 통신 창을 열 수 있다.
- 그러나 은수님이 걱정하신 "SW 로직을 바꿔야 한다"는 방향은 **맞다** — 진짜 원인은 통신 차단이 아니라 **Auto Prox Cycle Select(POR 기본값 32배, 현재 코드 미설정)로 인해 ULP의 실제 리포트 주기가 SW의 타임아웃 가정보다 수십 배 느려질 수 있다**는 것이다.
- 과거 LP/ULP 회귀(현재 PM Timeout=0으로 전면 차단 중)는 재구성됐으나, "전면 영구 차단"이 최선이었는지는 실측 없이 판단할 수 없다.
- 이번 라운드의 3개 활용 설계(LP·ULP·SW폴링매칭)는 전부 부분적으로만 완성됐다 — 그대로 조합해 구현하면 새로운 결함(죽은 코드, 안전장치 무효화)을 남긴다.
- 상세: [`분석.md`](분석.md)·[`에이전트-로그/99_종합.md`](에이전트-로그/99_종합.md).

## 3. 정직한 한계

- 이 라운드의 모든 활용 설계(후보_1·2·3)는 **"force comm 지연이 Report Rate에 paced된다"는 미확인 전제** 위에 서 있다 — 데이터시트를 문자 그대로 읽으면 반대 해석(파워모드 무관하게 항상 45ms 안에 열림)도 똑같이 자연스럽다. 이 전제가 틀리면 세 설계 전부 다시 검토해야 한다.
- fake_func_sleep()(BLE 프로파일링 경로)은 리부트 분기가 주석 처리돼 있어 "리부트=안전망"에 기대는 설계가 이 경로에서는 성립하지 않는다 — 별도 처리 필요.
- 3채널 벤치마크를 1채널로 환산하는 근거가 약해(§5.2 원문상 ULP 이득의 상당 부분이 "다른 채널을 늦추는" 데서 옴), CH0 단일채널 구성에서 ULP의 정확한 절감폭은 실측 전까지 알 수 없다.

## 4. 은수님 결정 요청

1. **순위 1(실측 게이트) 착수 동의 여부** — force comm 타이밍·Auto Prox Cycle 실효값·클럭 공차. 이것 없이는 이번 딥다이브의 어떤 활용안도 구현 단계로 갈 수 없습니다.
2. **순위 2(255ms 워치독 공백 해소)를 병행할지** — 이번 라운드가 방향(LP/ULP·절전연장)으로 갈수록 이 위험이 커진다는 것을 재확인했습니다.
3. **현행 유지(아무 조치 없음)도 유효한 선택지임을 인지하시는지** — 과거 회귀를 막고 있는 현재 설정(PM Timeout=0)은 전력 최적은 아니지만 안전합니다. 전력 절감이 시급하지 않다면 실측 게이트만 먼저 하고 활용 설계는 보류해도 됩니다.
4. **후보_2에서 재발한 할루시네이션(§8.11.2 오귀속) 정정 여부** — 이미 선행 라운드에서 한 번 정정됐던 오류가 재발한 것이므로, 향후 인용 시 원본 정정 사실을 명시적으로 참조하도록 관행화가 필요합니다.

승인 후, 선택한 경로를 별도 작업(④)으로 착수하겠습니다.
