# 99 · 종합 평결 — IQS323 전력모드(NP/LP/ULP) 딥다이브

**TL;DR**: 은수님의 가설("ULP는 터치 시에만 통신 가능, 평상시 I2C 실패")은 원문(Force Communication은 파워모드 무관하게 항상 작동)으로 **반박**됐다. 그러나 검증 결과 "가설의 정신"은 다른 메커니즘으로 부활한다 — Auto Prox Cycle Select(POR 기본값 32배, 코드 미설정)로 인해 ULP 실효 리포트 주기가 SW 타임아웃 가정보다 수십 배 느려질 수 있어 "체감상 죽은 것처럼 보이는" 동일 증상이 재현될 수 있다("틀린 진단, 맞는 걱정"). 과거 LP/ULP 회귀(PM Timeout=0으로 전면 차단)의 인과사슬은 재구성됐으나 비례성(전면 차단이 최선이었는지)은 의문이 남았고, 이번 라운드가 제안한 두 활용 설계(LP·ULP)는 각각 조건부 해소·설계 공백(wake-write 죽은 코드)이 확인돼 그대로 채택하기엔 이르다. 완전성 검증에서 이 라운드가 선행 `20260705` 시리즈의 확정 사실(I2C Lock-Up 에라타, 255ms 내장 워치독 미점검 공백)을 재인용하지 않고 각자 재발명했으며, 후보_2에서 이미 한 차례 정정된 할루시네이션이 재발한 것도 확인했다.

## 1. 은수님 가설의 최종 판정 — "틀린 진단, 맞는 걱정"

| 층위 | 판정 | 근거 |
|---|---|---|
| 표면적 주장(통신 자체가 안 됨) | **반박** | Force Communication(§8.13)은 파워모드 무관하게 항상 창을 강제로 열 수 있음(Halt 탈출에도 동일 기전 사용). Sound1은 애초에 Streaming이라 터치 무관하게 주기적으로 창이 열림 |
| 근저의 우려(LP/ULP에서 SW가 못 따라간다) | **다른 메커니즘으로 부활** | Auto Prox Cycle Select(0x33 bit[3:2], POR 기본값 `11`=32배, 코드 미설정)로 ULP 실효 리포트 주기가 raw 설정값의 최대 32배까지 벌어질 수 있음 — SW의 고정 타임아웃(45ms/100ms) 전제가 무너져 "체감상 응답 없음"이 재현 가능 |

## 2. 과거 회귀 재구성 — 확정된 것과 남은 것

- **확정**: `REG_PM_TIMEOUT`(0xC5)=0 설정(현재도 유효)과 그 코드 주석의 인과사슬("LP report rate 100ms → force_window_open 45ms 타임아웃 충돌")은 레지스터 실값(LP Report Rate 0xC2=100ms 직접 write)으로 뒷받침된다.
- **정교화**: SW 폴링주기(100ms)와 LP Report Rate(100ms)가 우연히 일치해 두 독립 발진기 사이 위상표류(맥놀이)가 실패를 몰아서 발생시켰을 가능성이 신규 발견됐다 — 단 "피피엠 단위·매우 천천히"라는 최초 정량화는 데이터시트 자체 마스터클럭 공차(±5.5%, Table 4.3)와 모순되며, 검증 결과 실제 맥놀이는 초~수십 초 규모로 재추정된다(원 주장의 자기모순 — 그라운드_3가 스스로 경계한 "근거 재확인 없는 서술 강화" 패턴이 같은 문서 안에서 재발).
- **미확정**: force comm의 개방 지연이 실제로 Report Rate에 paced되는지(하위메커니즘_B) 자체가 데이터시트만으로는 확정 불가 — AZD004가 "product-specific, sampling/processing duration에 의존"이라고만 답한다. 이 전제가 틀리면 과거 회귀의 진짜 원인도 여전히 미상으로 남는다.
- **비례성 재검토**: "전면 영구 차단"이 확인된 위험 대비 과도한 조치였을 가능성은 방향은 타당하나, 근거 없는 즉시 완화(전환)에는 반대 — 실측 없이는 결론 낼 수 없다.

## 3. 후보 3종 최종 판정

| 후보 | 핵심 내용 | 최종 판정 |
|---|---|---|
| **후보_1** LP 활용 | PM Timeout 0→5000, MAX_WAIT_OPEN_MS 45→150 | **조건부 해소** — 최악값 계산(150ms > 105.5ms 공차반영 최악치)은 견고하나, (a) 전제(하위메커니즘_B) 자체 미확인 (b) 두 상수 간 정적 결합장치 없어 재발 가능 (c) 전역 적용이 후보_3의 "노말모드 타임아웃 불변" 원칙과 충돌 |
| **후보_2** ULP 활용 | Auto Prox Cycle 명시 설정, Manual 010 고정, 리부트=안전망 | 은수님 가설 정면판정(틀림) 정확, wake-write 불필요 정확히 인지(§4.1 검증 확인). 단 §8.11.2 "펌웨어 권장" 할루시네이션 재발(1차 검증 확인), 에라타 워크어라운드 재발명 |
| **후보_3** SW폴링+IC파워모드 매칭 | 국면분리(노말=SW폴링만, func_sleep중만 IC Manual LP) | 핵심 프레이밍(보완관계) 타당·데이터시트로 재확인됨. 단 **wake-write 스텝이 죽은 코드**(func_sleep 탈출은 항상 하드리셋, apply_settings가 101로 덮어씀), Manual모드 선택 시 §5.3 자동NP복귀 무효화를 인지하지 못함(설계 공백), 에라타 완전 누락 |

## 4. 완전성 검증이 발견한 공백 (전 후보 공통)

- **[최중요]** 선행 `20260705_touch-event-mode-adoption` 라운드가 이미 확정한 **255ms 내장 통신 워치독 + Reset Event 비트 런타임 미점검 공백**을 이번 라운드 01~06번 어디서도 언급하지 않았다. 이번 라운드가 제안하는 LP/ULP·func_sleep 체류시간 연장은 이 노출 시간을 실질적으로 늘리는 변경이라 — 특히 후보_2·3의 Manual 모드 선택은 §5.3 자동 NP복귀도 포기하므로, "자동복귀도 없고 리셋 감지도 없는" 상태가 되어 상황을 악화시킬 수 있다.
- I2C Lock-Up 에라타(부록C) + LP/ULP로 자연개방 빈도가 줄어 강제개방 의존도가 높아지는 결합 위험도, 선행 라운드가 이미 구체 스펙(IC버전 실측·워크어라운드)을 만들어 뒀음에도 이번 라운드 3개 후보가 각자 독립적으로 재발명했다 — 특히 후보_3(force-comm 의존도가 가장 큰 옵션_3을 제안)은 에라타 자체를 한 번도 언급하지 않았다.
- `fake_func_sleep()`의 리부트 분기가 주석 처리(실제 리셋 안 됨)돼 있어, "리부트=안전망"에 의존하는 후보_2·3 설계 전제가 이 경로에서는 성립하지 않는다 — 어느 후보도 분석하지 않은 엣지케이스.

## 5. 할루시네이션 감사

01~06번 인용 전수 대조 결과 정확도는 높았으나, 후보_2에서 **확정 할루시네이션 1건**을 발견 — "§8.11.2가 펌웨어 권장: Event mode라고 명시"라는 서술은 원문에 없고 참고 md의 사내 해설이다. 이는 신규 오류가 아니라 `20260705_touch-event-mode-adoption/99_종합.md §4`가 **이미 확정·정정한 동일 오류의 재발**이다 — 인용 위생(citation hygiene) 실패 사례로 기록한다. 경미 오차 1건(페이지 표기)은 영향 없음.

## 6. 종합 결론

1. 은수님의 표면적 가설은 반박되나, 그 우려의 본질은 다른 메커니즘(Auto Prox Cycle Select)으로 부활한다 — "SW 처리 로직을 바꿔야 한다"는 은수님의 직관은 방향이 맞았다.
2. 과거 회귀는 "전면 영구 차단"보다 정교한 대응(예: 후보_1의 타임아웃 상향 + Report Rate 인지형 설계)이 가능했을 수 있으나, 지금 시점에도 핵심 전제(force comm 지연이 파워모드에 실제로 연동되는지)가 실측 없이는 확정되지 않는다.
3. 이번 라운드의 두 활용 설계(후보_1·2)는 부분적으로 견고하나 완결되지 않았고, 후보_3은 실행 불가능한 스텝(죽은 wake-write)을 포함한다 — **어느 것도 지금 그대로 구현 승인할 수준은 아니다.**
4. 가장 중요한 발견은 개별 후보의 완성도가 아니라, 이번 라운드 전체가 선행 라운드의 확정된 안전장치 공백(255ms 워치독)을 놓쳤다는 것이다 — LP/ULP+절전 연장 방향으로 갈수록 이 공백의 위험이 커지므로, 실측·설계 착수 전에 반드시 통합해야 한다.
