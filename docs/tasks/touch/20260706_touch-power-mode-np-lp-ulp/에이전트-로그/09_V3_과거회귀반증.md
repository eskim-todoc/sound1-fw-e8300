# 검증_3 — 과거 회귀 재구성 적대적 검증: 위상표류의 물리적 타당성과 회귀 방지책의 실효성

**TL;DR**: 그라운드_3의 위상표류(맥놀이) 발견은 정성적으로는 재확인된다 — 독립된 두 발진기가 영구히 고정된 위상을 가질 수는 없다. 그러나 그 근거로 든 "피피엠 단위·매우 천천히"는 데이터시트 자신이 명시하는 마스터클럭 공차(±5.5퍼센트, 크리스탈 핀 자체가 없음)와 정면으로 어긋나며, 실제로는 초에서 수십 초 규모의 훨씬 빠른 맥놀이일 개연성이 높다. 후보_1의 방지책(백오십 밀리초·오천 밀리초)은 재구성된 메커니즘이 맞다면 구조적으로 견고하나, 그 메커니즘 자체가 미확인이고 결합되지 않은 상수쌍을 재생산하며 후보_3의 국면분리 설계와 충돌한다. 비례성 재검토는 방향에 동의하되 실측 게이트 없는 즉시 전환에는 반대한다.

2. 코드(`tdc_touch_iqs323.c`/`.h`, `tdc_touch.c`, `tdc_touch_time.h`, `ci_timer.c`)를 직접 재대조해 그라운드_3·후보_1이 인용한 라인·값에 오류가 없는지 확인했다.

4. 선행 검증 문서(`20260703_touch-heisenberg-sw-mitigation/에이전트-로그/13_V3_S3검증.md`)를 직접 열람해 그라운드_3의 인용 계보 주장을 재검산했다.

**결론 먼저(BLUF)**: 그라운드_3·후보_1이 인용한 레지스터값·라인번호·원문 문구는 전부 재확인되어 오류를 찾지 못했다(할루시네이션 없음). 다만 두 문서 모두 **검토하지 않은 데이터시트 한 표(§4.3 Miscellaneous Timings)** 가 이번 반증의 핵심 근거가 되었다.

## 1. 반증_1 — "위상표류(맥놀이)"는 물리적으로 성립하는가, "고정"이 더 정확한가

### 1.1 두 가설의 정확한 형태

- **가설_A(그라운드_3)**: SW 폴링(100ms)과 LP Report Rate(100ms)가 서로 다른 독립 발진기 기준이라, 상대위상이 시간에 따라 서서히 회전(맥놀이)한다. 나쁜 위상 구간에 들어가면 상당 시간 뭉쳐서 실패하다가, 위상이 회전해 나오면 자연 회복된다.
- **가설_B(오케스트레이터 제시 대안)**: 두 값이 똑같이 100ms로 설정되어 있으니, 실제로는 매 사이클 같은 상대위치에서 반복 실패하는 **고정** 관계일 수 있다 — 이 경우 한번 나쁜 상태에 들어가면 위상 자체가 변하지 않으므로 자연 회복이 없고, 터치 이벤트가 강제로 개입해야만(§5.3 NP 복귀) 풀린다.

### 1.2 관련된 두 클럭 도메인 재확인 (코드 직접 대조)

**SW측**: `tdc_touch.c:295~296`(직접 재확인) — `int now = ci_timer_get_tick(); if (TDC_TOUCH_POLL_INTERVAL_MS > (now - s_poll_tick_old)) return false;`. `ci_timer_get_tick()`의 소스는 `ci_timer.c:10`(직접 재확인) — `static volatile int g_ci_timer_main_tick = 1; /* CFX FIFO 가 증가 — 시스템 시간 전담 */`. 즉 **SW의 100ms 폴링 게이트는 CFX(오디오 DSP 코어) FIFO 인터럽트가 증가시키는 틱을 기준으로 한다.** 오디오 처리 코어의 인터럽트는 통상 오디오 샘플레이트에 결부된 크리스탈/PLL 기준일 개연성이 높다 — 다만 이 프로젝트의 실제 크리스탈 사양(정확한 ppm 공차)은 본 세션에서 직접 확인하지 못했다 **[미확인, 정황상 강한 추정]**.

**IC측**: LP Report Rate(0xC2=100ms)는 IQS323 내부 타이밍이다. 데이터시트 Table 2.4 "Signal Descriptions"(원문 p.7, `iqs323_datasheet_layout.txt:373~393`, 전체 핀 나열 직접 재확인)를 보면 IQS323의 핀은 CRx0~2/CTx0~2·TxA·OutA·RDY/MCLR·SDA·SCL·VDD·VREG·VSS뿐이다. **XTAL·OSC_IN 등 외부 크리스탈 입력 핀이 존재하지 않는다.** 즉 IQS323은 태생적으로 외부 정밀 클럭을 참조할 방법이 없고, 모든 내부 타이밍은 온칩 발진기에서 나올 수밖에 없는 구조다.

### 1.3 신규 근거 — 데이터시트가 명시하는 마스터클럭 공차

`docs/참고/touch/iqs323_datasheet_layout.txt:740~741`(Table 4.3 "Miscellaneous Timings", 원문 p.12) 원문 그대로:

> "fOSC · Master CLK frequency tolerance 14 MHz · Min 13.23 · Typ 14 · Max 14.77 · MHz"

이는 **±5.5퍼센트**(14.77÷14−1 ≈ +5.5%, 14÷13.23−1 계산과 대칭) 공차다. 같은 표 바로 위 행(`:740`)은 "fxfer · Charge transfer frequency (derived from fOSC)"라 명시해, **센싱 변환 주파수 자체가 이 fOSC에서 파생됨**을 확인시켜준다. Report Rate의 ms 카운터가 이 fOSC를 그대로 분주해 쓰는지는 데이터시트가 별도 문장으로 명시하지 않는다 — 그러나 (a) 크리스탈 핀이 없어 대안 클럭원 자체가 없고, (b) `oscillat`·`accuracy`·`tolerance`·`trim`·`ppm` 키워드로 원문 전체를 재검색한 결과 이 fOSC 외에 별도 저속 타이머의 공차를 명시한 표는 발견하지 못했다는 점에서, **Report Rate 타이밍도 이 fOSC(±5.5%) 공차를 그대로 물려받을 개연성이 높다**고 판단한다 **[미확인이나 강한 정황 근거]**.

### 1.4 판정_1 — "영구 고정"은 기각, 그러나 "피피엠 단위·매우 천천히"도 기각

**가설_B(고정) 기각 근거**: 두 개의 물리적으로 독립된(서로 다른 다이·서로 다른 발진기 회로) 오실레이터가 정확히 동일한 주파수를 가질 확률은 사실상 0이다. 온도·전압·개체차 어느 것 하나만 달라도 두 클럭 사이에는 항상 유한한 잔여 주파수차가 존재하고, 이 잔여차가 있는 한 상대위상은 (얼마나 느리든) 반드시 변한다 — "영구 고정"은 물리적으로 성립하지 않는다. **가설_A(표류)의 정성적 방향이 맞다.**

**그러나 그라운드_3의 "피피엠 단위" 정량화는 데이터시트와 정면으로 어긋난다.** §3.4의 원문 재확인 결과 공차는 ±5.5%(=55,000ppm)이며, "피피엠 단위"라는 표현이 통상 의미하는 규모(수십~수백 ppm)보다 **3~4자리 배 크다**. 이 차이는 맥놀이 주기 추정치를 근본적으로 바꾼다.

간단한 예시 계산(공칭 주기 100ms, SW측은 상대적으로 정밀하다고 가정한 근사 — §1.2의 미확인 전제 위에 있음을 유의):

| 가정한 상대 주파수차 Δ | 사이클당 위상 밀림 | 맥놀이(전체 위상회전) 주기 |
|---|---|---|
| ±5.5%(공차 최악값) | 약 5.5ms/사이클 | 100÷5.5 ≈ 18사이클 ≈ **약 1.8초** |
| ±1%(전형적 트림 가정) | 약 1ms/사이클 | 100사이클 ≈ **약 10초** |
| ±0.1%(매우 잘 트림된 개체 가정) | 약 0.1ms/사이클 | 1,000사이클 ≈ **약 100초** |
| 피피엠 단위(예: 100ppm) | 약 0.01ms/사이클 | 10,000사이클 ≈ **약 17분** |

그라운드_3의 "매우 천천히·상당 시간(초 단위 이상)"이라는 서술은 표의 마지막 행("피피엠 단위")과 정합되는 표현인데, 데이터시트가 실제로 보증하는 것은 최상단 두세 행(초~수십 초 규모)에 가깝다. 즉 **"위상이 드리프트한다"는 정성적 결론은 살아남지만, "그래서 한번 나쁜 위상에 들어가면 오래 갇힌다"는 함의는 과장되었을 가능성이 높다** — 오히려 데이터시트 근거대로면 실패가 **초 단위로 반복 재발·재복구하는 패턴**(수 초 나쁨 → 수 초 좋음 → 반복)에 더 가까울 것으로 재추정한다.

### 1.5 부가 확인 — 이 논의 전체가 서 있는 미확인 전제

§8.7~8.9 원문(`iqs323_datasheet_layout.txt:1756~1790`, 원문 p.30~31, 직접 재확인)을 대조하면: 통신창은 IC가 데이터를 준비하면 열리고(RDY low), 표준 I2C STOP 또는 "I2C Transaction Timeout"(기본 200ms, 0xD1 레지스터)이 만료되면 닫힌다. 즉 **SW가 정상적으로 한 번 읽으면(STOP으로) 창이 닫히고, 다음 창은 IC의 다음 리포트 사이클까지 기다려야 다시 열린다** — "위상"이라는 개념 자체가 여기서 나온다.

그러나 §1.4의 맥놀이 계산 전체와 그라운드_3·후보_1·후보_2·후보_3이 공통으로 세운 회귀 재구성은 모두 **하위메커니즘_B**(force comm의 개방 지연이 활성 Report Rate에 의해 사실상 paced된다)를 전제한다. §8.13 원문을 문자 그대로 읽으면 오히려 **하위메커니즘_A**(force comm은 인터페이스 모드 축으로만 설명되고 전력모드 조건절이 없어, Report Rate와 무관하게 0.1~45ms 안에 열려야 정상)가 더 자연스러운 독해다. 이 둘 중 어느 쪽이 맞는지는 이 저장소 어디에도 실측 근거(오실로스코프·RTT 타임스탬프)가 없다 — 그라운드_2·후보_1·후보_2·후보_3 전원이 독립적으로 이를 [미확인]으로 남겼고, 본 검증도 이를 뒤집을 근거를 찾지 못했다. **따라서 §1.4의 맥놀이 재계산은 "하위메커니즘_B가 맞다면"이라는 조건부 위에서만 의미를 가진다** — 이 조건 자체가 무너지면 "위상"이라는 말 자체가 무의미해진다(하위메커니즘_A에서는 force comm이 매번 45ms 안에 열려 애초에 실패가 없어야 한다).

### 1.6 메타 발견 — "피피엠 단위" 표현의 출처 재추적

그라운드_3는 §4에서 이 맥놀이 통찰이 "13_V3_S3검증.md §2 '신규 위험 2(자기지시적)'가 이미 지적한 것과 동일한 물리 메커니즘"이라고 밝힌다. 해당 문서를 직접 열람해 원문을 대조했다:

> "SW 폴링(CM3 클럭 기준)과 IQS323 Report Rate(IQS323 자체 발진기 기준)는 서로 다른 독립 발진기이므로, 주기를 일치시키면 위상이 서서히 표류하는 느린 맥놀이가 자체적으로 생긴다"(`13_V3_S3검증.md:42`, 2026-07-03)

이 인용은 정확하다 — 그러나 **이 원문 어디에도 "피피엠 단위"라는 표현이나 구체적 규모 추정은 없다.** "서서히"·"느린"이라는 정성적 표현뿐이다. 즉 "피피엠 단위"라는 특정 정량화는 2026-07-03 문서에서 물려받은 것이 아니라 **그라운드_3(금번 문서, 2026-07-06)가 스스로 새로 추가한 근거**다. 그라운드_3는 같은 문서 §6에서 "관측교란.md → S3 → V3로 이어지는 3중 확인이 전부 동일 출처의 재확인이었다"는 것을 예리하게 지적했는데, 정작 자신이 새로 도입한 이 "피피엠 단위" 정량화는 — 자신이 같은 세션에서 이미 열어 보고 있던 데이터시트 §4.3(Table 4.3)과 대조하지 않은 채로 — 도입되었다. 그라운드_3가 §6에서 스스로 경계한 바로 그 패턴("근거를 재확인하지 않고 서술만 강화")이 §4의 신규 주장 내부에서 그대로 재발한 셈이다.

## 2. 반증_2 — 후보_1의 회귀 방지책은 메커니즘을 해소하는가, 증상만 가리는가

### 2.1 두 변경의 역할 분리 재확인

후보_1은 ① `REG_PM_TIMEOUT` 0→5000ms, ② `TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS` 45→150을 "회귀 방지책"으로 묶어 제시한다. 코드 재대조 결과 이 둘은 **서로 다른 축**이다:

- **① PM Timeout**: "언제 자동 강하가 일어나는가"를 결정한다 — 이 값을 0에서 5000으로 바꾸는 것은 회귀 메커니즘을 **해소하는 것이 아니라, 그 메커니즘이 다시 노출될 문(자동 강하)을 여는 조치**다.
- **② MAX_WAIT_OPEN_MS**: "LP에 진입한 뒤 안전한가"를 결정한다 — 그라운드_3이 재구성한 45ms-vs-100ms 충돌에 **실제로 대응하는 변경은 오직 이것뿐**이다.

후보_1 문서 자체도 §3~§4에서 이 둘을 별도 절로 서술해 두었으나, TL;DR과 "회귀 방지" 라는 표제 아래 한 묶음으로 제시되어 독자가 "두 변경이 함께 회귀를 막는다"고 오해할 여지가 있다 — 정확히는 **①이 위험을 다시 열고, ②가 그 위험에 대응한다**는 구조다.

### 2.2 150밀리초가 구조적으로 견고한 이유 (worst-case 논증 재확인·강화)

§1.5의 조건(하위메커니즘_B) 위에서, 최악의 경우 SW가 통신창이 막 닫힌 직후에 도착하면 다음 창까지 최대 한 Report Rate 주기를 기다려야 한다. §1.3에서 확인한 공차(±5.5%)를 반영하면 LP의 실제 물리 주기는 최악 약 105.5ms(100ms×1.055)까지 늘어날 수 있다. `MAX_WAIT_OPEN_MS=150`은 이 최악값 대비 약 44.5ms(≈42%) 여유를 확보한다.

**핵심 논증**: 이 여유 계산은 §1의 "표류냐 고정이냐" 논쟁과 **무관하게** 성립한다 — 최악 대기가 한 주기(약 105.5ms)를 넘지 않는 한, SW가 어떤 위상에서 시작하든 150ms 예산 안에 반드시 다음 창을 만난다. 표류하는 위상이든 우연히 고정된 위상이든, 예산이 최악의 단일 주기보다 크면 두 가설 모두에서 안전하다. 후보_1도 §4.4에서 "가설이 틀려도 손해 없다"는 취지로 유사하게 논증했는데, 본 검증은 **공차까지 반영한 정밀한 최악값 계산으로 그 논증을 한 단계 더 강하게 뒷받침한다** — 이 정밀화(오실레이터 공차 반영)는 후보_1 원문에는 없던 것이다.

### 2.3 그럼에도 "완전 해소"라 부를 수 없는 세 가지 이유

**이유_1 — 전제(하위메커니즘_B) 자체가 미확인**: §1.5에서 확인했듯 이 모든 계산은 force comm의 개방 지연이 Report Rate에 paced된다는 전제 위에 있다. 데이터시트 §8.13을 문자 그대로 읽으면 오히려 반대(하위메커니즘_A, 전력모드 무관하게 항상 0.1~45ms) 쪽이 더 자연스러운 독해다. 만약 A가 맞다면 애초에 과거 회귀의 원인이 "45ms-vs-100ms 충돌"이 아니었다는 뜻이 되고, 150ms 상향은 실제로 있었던 문제와 무관한 변경이 되어 진짜 원인은 여전히 미상으로 남는다 — "고쳤다고 믿었지만 실제로는 다른 곳에서 우연히 재발하지 않았을 뿐"인 상태와 구분이 안 된다.

**이유_2 — 결합되지 않은 상수쌍의 재생산**: 150ms의 타당성은 오직 "LP Report Rate=100ms"라는 특정 값에 대해서만 성립한다(150 > 105.5). 이 상호관계를 코드가 강제하는 장치(예: `#if MAX_WAIT_OPEN_MS <= LP_REPORT_RATE_MS ... #error`류의 정적 검증, 혹은 상수 자체를 서로 파생시키는 매크로)는 **전혀 없다** — 두 상수는 여전히 서로 다른 파일(`iqs323.h`의 매크로, `iqs323.c`의 레지스터 write 리터럴)에 독립적으로 존재한다. 이는 그라운드_3 자신이 재구성한 원래 회귀의 정확한 구조("SW의 타임아웃 상수가 그때 도입된 Report Rate에 맞춰 함께 조정되지 않은 파라미터 불일치", 후보_1 §2.2도 동일하게 재확인)를 **동일한 형태로 반복**하는 것이다. 후보_2(ULP 활용안)는 Auto Prox Cycle Select를 그대로 두면 실효 ULP 주기가 최대 5.12초까지 늘어날 수 있음을 별도로 이미 지적했다 — 이런 시나리오가 채택되며 MAX_WAIT_OPEN_MS 동기화를 잊으면 동일 계열의 회귀가 형태만 바꿔 재발한다. **이번 수정은 "사례"를 고쳤을 뿐 "부류"를 제거하지 않았다.**

**이유_3 — 후보_3의 설계원칙과 정면 충돌 (코드로 재확인)**: `MAX_WAIT_OPEN_MS`는 `write_register()`(`:184`)·`read_register()`(`:204,216`)·읽기전용 디버그 경로(`:380,387`, 코드 직접 재확인 결과 각각 force_window_open을 2회씩 호출)가 전부 공유하는 단일 상수다 — 150ms 상향은 **NP 국면(일반 운용)에도 무차별 적용**된다. 그런데 후보_3은 독립적으로 "국면_1(노말)은 오디오·자극·BLE 처리와 같은 `while(1)` 루프를 공유하므로 블로킹 타임아웃 확대가 실시간성 리스크를 낳는다"는 이유로 "국면_1은 SW 폴링 주기만 바꾸고 IC·타임아웃은 불변으로 두는 옵션만 권고"한다고 명시했다(후보_3 §5·§7). 후보_1의 전역 150ms 적용은 정확히 후보_3이 국면_1에서 피하라고 명시한 바로 그 종류의 변경이다. 실제로 폴링 1회당 read_status+read_debug 조합으로 최대 4회 force_window_open() 호출이 가능함을 코드로 재확인했고(위 인용 라인), 이론상 최악 600ms 블로킹이라는 후보_1 자신의 §6.3 계산도 코드와 정합한다. 다만 후보_1 §4.4는 "이 여유 상한은 손해가 없다"고 서술하면서 같은 문서 §6.3은 이를 [실측 게이트]가 필요한 리스크로 별도 인정한다 — **두 절 사이에도 다소 어긋남이 있고, 후보_1·후보_3 두 문서는 서로 대조되지 않은 채(둘 다 상대방 문서 부재 상태에서) 병렬 작성되어 이 충돌이 노출되지 않았다.** 오케스트레이터 단계의 조정이 필요하다.

### 2.4 판정_2

"메커니즘을 해소하는가, 증상만 가리는가"라는 이분법에는 **"조건부 해소"**가 가장 정확한 답이다. 하위메커니즘_B가 맞다면 150ms는 확률적 완화가 아니라 해당 실패모드를 구조적으로 제거하는 결정론적 조치이며, 이는 "증상 가리기"로 폄하할 수준이 아니다(§2.2). 그러나 그 전제 자체가 미확인이고(이유_1), 고쳐진 것은 이번에 알려진 특정 수치 조합뿐이며 재발을 막는 잠금장치가 없고(이유_2), 전역 적용이 같은 라운드의 다른 후보안(후보_3)의 설계원칙과 충돌한다(이유_3)는 점에서, **"완전히 해소했다"고 승인하기에는 이르다.**

## 3. 그라운드_3의 비례성 재검토 권고에 대한 최종 의견

### 3.1 동의 지점

- 재구성된 원인(45ms-vs-100ms 파라미터 불일치)이 사실이라면, "LP가 원천적으로 못 쓰는 모드"라는 결론은 과도하며 좁은 파라미터 정합으로 대응 가능하다는 그라운드_3·후보_1·후보_2·후보_3의 공통된 방향성에 동의한다.
- §5.2 Halt 탈출 규정(force comm으로만 탈출 가능)이 force comm을 파워모드 무관 설계로 시사한다는 것도 여러 문서가 각기 다른 각도(G2의 원문 대조, 본 문서의 §8.7~8.9 재확인)로 수렴해 확인되므로, "전면 원천 차단"이 데이터시트가 요구하는 최소 안전장치는 아니라는 점에도 동의한다.
- git 고고학 결과(그라운드_3·후보_1 독립 확인, 본 문서가 커밋 재확인으로 재검증) 원래 회귀의 정확한 수치·재현 로그가 이 저장소에 없다는 것, 그리고 "이미 여러 번 독립검증된 확정사실"이라는 인상이 과장이었다는 §6 지적에도 동의한다 — 13_V3_S3검증.md §5("반박 근거를 찾지 못했다 — 반대 권고 그대로 지지한다")가 정확히 두 문장짜리 무비판적 재확인이었음을 본 문서가 직접 대조로 재검증했다(§1.6).

### 3.2 유보 지점

- 재구성된 메커니즘의 핵심 전제(하위메커니즘_B)가 근본적으로 미확인이며, §8.13 원문을 곧이곧대로 읽으면 오히려 반대(하위메커니즘_A) 쪽이 자연스러운 독해일 수 있다(§1.5). 이를 가를 실측 데이터는 이 저장소 어디에도 없다 — "터치 무선 계측 준비"(commit `929ab16`) 단계까지만 진행되었고 실제 계측 데이터는 아직 없음을 git 이력으로 재확인했다.
- I2C Lock-Up 에라타(부록C)의 적용 여부(실리콘 리비전)도 미확인 상태다. 이는 force comm 의존도가 늘어나는 모든 LP/ULP 활용안(후보_1·2·3 전부)에 공통으로 걸리는 별개의 위험이며, "45ms-vs-100ms 충돌"과는 무관한 축이다.
- 그라운드_1 스스로 Sound1 실제 구성(1채널·1MHz·스트리밍)에서의 절대 전력절감치를 "범위로만 제시 가능, 실측 필요"로 결론지었다 — **비용(리스크)뿐 아니라 편익(절감폭)도 둘 다 미확정**인 상태다. 이런 상태에서 "영구 차단은 과도하다"는 진단이 자동으로 "그러니 지금 켜자"는 결론으로 이어지는 것은 근거의 비약이다.
- 회귀 당시의 정확한 파라미터가 이 저장소에서 추적 불가능하다는 것은 현재의 재구성이 **유일하게 남은 최선의 설명**이라는 뜻이지, **검증된 설명**이라는 뜻은 아니다. "가장 정합적인 사후 스토리"와 "확인된 원인"은 서로 다른 인식론적 지위를 갖는다.

### 3.3 최종 의견

그라운드_3의 비례성 재검토 제안 **방향에는 동의**하되, 이번 라운드의 데스크 분석(데이터시트 재독·코드 대조·git 고고학)만으로 프로덕션 코드를 "PM Timeout=0 유지"에서 "LP Automatic 재활성화"로 바로 전환하는 것에는 **반대**한다. 권고 순서는 다음과 같다.

1. 벤치 보드에서 RTT 타임스탬프(또는 오실로스코프)로 `force_window_open()` 진입~반환 시각과 실제 RDY 토글을 계측 — 하위메커니즘_A/B 중 어느 쪽이 사실인지, 그리고 실측 맥놀이 주기가 몇 초 규모인지 확정한다.
2. Hardware ID/Major·Minor Version 레지스터(0x00~0x02) 판독으로 I2C Lock-Up 에라타 해당 여부를 확정한다.
3. 위 두 게이트를 통과한 뒤에야 `MAX_WAIT_OPEN_MS`·`REG_PM_TIMEOUT` 변경을 코드에 반영하고, 그때 §2.3-이유_2가 지적한 상수 결합(예: 컴파일타임 정적 검증 또는 상호 파생 매크로)도 함께 도입해 동일 계열 회귀의 재발을 구조적으로 차단한다.

이 순서 자체는 후보_1이 §6.3에서 이미 자인한 [실측 게이트]와 결론이 같다 — 본 검증은 "그 게이트가 왜 반드시 필요한지"를 데이터시트의 오실레이터 공차라는 별도의 물리적 근거로 한 번 더 보강하는 역할을 한다.
