# 00 · 오케스트레이터 입력 — IQS323 전력모드(NP/LP/ULP) 딥다이브

**TL;DR**: 은수님이 NP/LP/ULP 전력소모 비교·SW 호환성(예: "ULP는 터치시에만 통신 가능해 평상시 I2C 실패" 가설)·센싱주기 정합성을 질문. 과거 S3(sw-mitigation)이 LP/ULP 자동전환에 명확히 반대한 이력이 있어(PM Timeout=0으로 강하 차단), 이번 딥다이브는 그 결론을 지금 시점의 깊어진 이해로 독립 재검토한다. 그라운드3·후보3·검증4, 10페르소나(Workflow, model:sonnet effort:max).

## 공통 입력 (전 페르소나 공유)

### 배경
- Sound1 E8300, IQS323 셀프캡 터치(CRX0 단일채널 활성). 현재 `beta_power_settings()`(`tdc_touch_iqs323.c:318`)에서 `REG_PM_TIMEOUT`(0xC5)=0 설정 — Power Mode Automatic 강하를 원천 차단해 항상 NP 유지.
- **과거 회귀 이력(반드시 숙지)**: 코드 주석 원문(`tdc_touch_iqs323.c` `beta_power_settings()` 인근) — "PM timeout 0 = 자동 강하 차단 → 노말 운용 중 NP 유지. (LP 전환 시 report rate 100ms 로 RDY 윈도우가 느려져 force_window_open 45ms 폴링이 윈도우를 놓쳐 timeout 발생. 터치=이벤트→NP 복귀로 회복되던 증상의 근본 차단. DS §5.3)". 즉 과거에 LP/ULP Automatic을 실제 시도했다가 이 회귀로 되돌린 이력이 있다. 선행 문서 `docs/tasks/touch/20260703_touch-heisenberg-sw-mitigation/에이전트-로그/05_S3_...md`(§7 반대권고)·`13_V3_S3검증.md`(§5)가 이를 재확인·지지했다.
- 데이터시트 §3.4(Current Consumption, `docs/참고/touch/데이터시트/01_개요·전기·타이밍.md:176~191`) 확정 수치(측정조건: self-cap **3채널**·Event mode·ATI Target 512·Fxfer 500kHz — 우리 구성인 1채널·Fxfer 1MHz와 조건 다름, 근사 필요):
  - NP: report rate 16ms, 125µA(3.3V)
  - LP: report rate 60ms, 37.5µA
  - ULP: report rate 160ms, 4.00µA
  - Halt: report rate 3000ms, 2.00µA
- §5.2·5.3(`02_proxfusion동작.md:75~144`): NP=일반, LP=NP보다 느린 report rate, ULP="하나의 wake-up 채널만 짧은 주기, 나머지는 훨씬 긴 주기"(단, 우리는 이미 CH0 단일채널이라 "나머지 채널" 개념이 적용되는지 확인 필요). Power Mode Timeout 경과 시 NP→LP→ULP 단계적 강하, 이벤트 발생 시 즉시 NP 복귀. Halt는 RDY 고정, Force Communications(§8.13)로만 진입 가능.
- 이번 시리즈(`20260705_touch-event-mode-adoption`)에서 이미 확정된 관련 사실: force_window_open()(`tdc_touch_iqs323.c:145~175`)은 RDY==OPEN이면 즉시 반환, 아니면 0xFF write 후 최대 45ms(`MAX_WAIT_OPEN_MS`) 대기. Report Rate가 Streaming 전용이 아니라 Events 모드에서도 유효한 독립 축임(전류표 교차확인, `20260705.../06_C3_ReportRate결합.md`). 유휴 시 SW 폴링주기를 늘리는 것이 가장 낮은 리스크로 실질 이득을 준다는 것이 직전 라운드 결론.

## 역할 분담 (10페르소나, 3단)

| 단 | 페르소나 | 역할 |
|---|---|---|
| 그라운드 | G1 | NP/LP/ULP/Halt 전력소비 정량 재확인 — §3.4 원문 대조, 우리 실제 구성(1채널·1MHz)에 맞는 근사치 도출, 측정조건 차이 명시 |
| 그라운드 | G2 | 각 모드의 RDY/통신 동작 정밀 확인 — force communication(§8.13)이 파워모드(NP/LP/ULP/Halt) 무관하게 항상 창을 열 수 있는지, ULP의 "wake-up 채널" 개념이 우리 단일채널(CH0) 구성에 어떻게 적용되는지, 각 모드 Report Rate 레지스터(0xC1/0xC2/0xC3) 확인 |
| 그라운드 | G3 | 과거 회귀(S3/V3) 정밀 재구성 — "PM Timeout=0" 코드 주석의 정확한 인과사슬(LP report rate→RDY 윈도우 지연→force_window_open 45ms 타임아웃)을 데이터시트·코드로 재검증, 이 진단이 지금(force communication 이해 심화 이후)도 유효한지 판단 |
| 후보 | C1 | LP 모드 활용 시나리오 — Report Rate 값, SW 변경사항, 과거 회귀 재발 방지책 설계 |
| 후보 | C2 | ULP 모드 활용 시나리오 — 은수님 가설("평상시 I2C 통신 실패") 정밀 검증 기반 설계, 필요한 SW 로직 변경 구체화 |
| 후보 | C3 | 현재 100ms SW 폴링과 IC 파워모드/Report Rate 최적 매칭 설계 — 선행 `20260705` "유휴 폴링주기 연장" 권고와의 관계(대체/보완/중복) 명확화 |
| 검증 | V1 | G1 전력수치 반증 — 원문 재대조, 근사 타당성 |
| 검증 | V2 | **최우선**: force communication의 파워모드 무관성(은수님 가설의 핵심 판정) 반증 시도 |
| 검증 | V3 | 과거 회귀 재현여부·현재 유효성 반증, C1/C2 회귀 방지책 충분성 검토 |
| 검증 | V4 | 완전성 비평 + 할루시네이션 감사 |

## 실행 방식

Workflow, phase(그라운드→후보 barrier, 검증 barrier), 전부 model:sonnet effort:max.
