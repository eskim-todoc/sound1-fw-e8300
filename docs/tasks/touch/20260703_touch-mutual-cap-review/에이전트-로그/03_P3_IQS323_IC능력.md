# 03 · P3 IQS323 IC 능력 (전문가: IQS323 데이터시트·레지스터)

**TL;DR**: IQS323는 mutual(projected) 모드를 레지스터로 완전 지원한다 — Azoteq 공식 예제 `IQS323_3PROJ_BUTTONS_EV_KIT.h`를 비트 단위 역산한 결과 `PXS Mode=0x13(Mutual)`·`Invert=1`·`Wav Pattern0=0x0E(Mutual)`가 **정확히 일치**함을 확인(할루시네이션 아님, 3중 교차검증). CRX0(CTx0 겸용 물리핀)→Tx, CRX1(CRx1)→Rx 페어링은 두 핀 모두 이미 D패드에 배선되어 있어 **레지스터만으로 시도 가능**하나, 기존 수동소자값은 mutual 용도로 검증된 바 없고 Azoteq 자체 예제도 전용 Tx핀(TxA, Sound1 미배선)만 사용해 "겸용 CTx" 방식의 참조례는 없다.

## 0. 답변 요약표 (오케스트레이터 (a)~(e) 대응)

| # | 질문 | 답 | 확실성 |
|---|---|---|---|
| a | Channel Mode(0x70)가 self/mutual을 결정하는가 | **아니오.** Channel Mode(Independent/Follower/Reference)는 self/mutual 선택과 **무관**한 별개 축 | 확립 |
| b | CTx/CRx 할당 레지스터 | `Sensor Setup`(0x30/40/50) 상위바이트 TX_SELECT + `Prox Input and Control`(0x33/43/53) 상위바이트 RX_SELECT | 확립 |
| c | mutual 모드 ATI 거동 | Azoteq 공식 mutual 예제도 **ATI Mode=Full**(자동) 그대로 사용. mutual 전용 ATI 알고리즘 분기는 문서상 없음 | 확립(예제 근거)+미확인(엣지케이스) |
| d | 현 HW서 CRX0-CRX1 페어링이 레지스터만으로 가능한가 | **배선은 이미 존재**(둘 다 D패드에 인출) + **레지스터 조합은 데이터시트상 허용**. 단 기존 수동소자·전극 역할 변화는 미검증 | 사실+가설 혼재 (아래 §5) |
| e | 3채널 IC에서 페어링 1건의 채널 소모 | **1채널**(Sensor+Channel 1세트) — Tx/Rx가 물리적으로 분리돼도 "채널"은 늘지 않음 | 확립(예제 근거) |

## 1. 핵심 근거 — Azoteq 공식 예제가 "mutual"임을 비트로 증명

`IQS323_3PROJ_BUTTONS_EV_KIT.h`(경로: `.../iqs323-example-code/src/IQS323/IQS323_3PROJ_BUTTONS_EV_KIT.h`)의 Sensor0 블록을 데이터시트 A.5~A.10 비트 정의로 역산:

| `#define` | 값 | 비트분해 | 데이터시트 대응 | 판정 |
|---|---|---|---|---|
| `S0_SETUP` | 0x09 | `0000_1001`: bit3=1, bit0=1 | A.5 bit3=Invert | **Invert=1 SET** |
| `S0_TX_SELECT` | 0x08 | `0000_1000`: bit3=1(TxA), bit0-2=0(CTx0-2=0) | A.5 bits11/10/9/8=TxA/CTx2/CTx1/CTx0 | **TxA만 Tx로 사용, CTx0-2 전부 비활성** |
| `S0_RX_SELECT` | 0x02 | `0000_0010`: bit1=1(CRx1) | A.9 bits10/9/8=CRx2/CRx1/CRx0 | **CRx1을 Rx로 사용** (S1은 CRx0, S2는 CRx2 — 셋 다 다른 Rx) |
| `S0_PRX_CTRL_0` | 0x93 | `1001_0011`: bits5-0=`010011`=0x13 | A.7 PXS Mode: 0x10=Self·**0x13=Mutual** | **PXS Mode = Mutual-Capacitance** |
| `S0_PATTERN_SETUP`(0x34 상위) | 0x0E | 하위니블(Wav Pattern0)=0xE | §5.12.1 Table 5.2: Self=0x03·**Mutual=0x0E**·Inductive=0x0B | **Wav Pattern0 = Mutual 권장값과 정확히 일치** |
| `S0_ATI_SETUP_0` | 0x8C | bits2-0=`100`=4 | A.12 ATI Mode: 100=Full | **ATI Mode = Full** |
| `CH0_REF_UI_SETUP` | 0x00 | bits3-0=`0000` | A.15 Channel Mode: 00=Independent | **Channel Mode = Independent** |

세 가지 독립 필드(`PXS Mode=0x13`, `Wav Pattern0=0x0E`, `Invert=1`)가 **동시에** mutual을 가리키고, 같은 파일철의 자매 헤더(`INDUCTIVE_OPTIONS`는 Wav Pattern0=0x0B, `SLIDER`는 0x03)까지 Table 5.2와 각각 정확히 대응한다([`03_EV_KIT설정·레지스터.md`](../../../../참고/touch/IQS323%20예제코드/03_EV_KIT설정·레지스터.md) §3.1). 파일명("3PROJ_BUTTONS"="3 Projected/Mutual Buttons")·비트값·Table 5.2 세 갈래가 교차 일치 — **가설이 아니라 확립된 사실**로 분류한다.

> 근거: [`데이터시트/02_proxfusion동작.md`](../../../../참고/touch/데이터시트/02_proxfusion동작.md) §5.12.1 Table 5.1/5.2, §5.7(Invert); [`데이터시트/06_레지스터레퍼런스.md`](../../../../참고/touch/데이터시트/06_레지스터레퍼런스.md) A.5·A.7·A.9·A.12·A.15; `iqs323-example-code/src/IQS323/IQS323_3PROJ_BUTTONS_EV_KIT.h` 원문.

## 2. (a) Channel Mode는 self/mutual과 무관 — 과업 문구 정정

`Channel Setup`(0x60/0x70/0x80) 하위바이트 bits3-0 "Channel Mode"는 **Independent/Follower/Reference** 3택이며, 이는 채널 간 UI 로직 연동(다른 채널을 따라가는지·기준으로 삼는지) 축이다(A.15). self-cap/mutual-cap 선택은 전적으로 **Sensor Setup의 CTx 선택 + Prox Input의 CRx 선택이 같은 핀인지 다른 핀인지**, 그리고 **Prox Control의 PXS Mode 필드**로 결정된다(§5.12.1). 위 예제에서도 mutual 채널이 `Channel Mode=Independent`를 그대로 쓴다(§1 표). 즉 **"Channel Mode(0x70) Independent vs 다른 모드"라는 과업 문구의 전제(Channel Mode가 mutual 여부를 가른다)는 데이터시트 근거상 성립하지 않는다** — 명확히 정정해 둔다.

---

## 3. (b) CTx/CRx 할당 레지스터 — 과업 문구의 주소 표기 정정

과업 지시문의 "(0x40 Prox Settings, 0x44 CalCap/Rx-Tx)"는 실제 데이터시트 명칭과 어긋난다. 정확한 주소·명칭(§9 Memory Map, A.5/A.9):

| 실제 레지스터 | 주소(S0/S1/S2) | 담당 |
|---|---|---|
| **Sensor Setup** | 0x30 / **0x40** / 0x50 | 상위바이트 TX_SELECT: CTx0/CTx1/CTx2/TxA 선택 + CalCap Tx/Rx |
| **Prox Input and Control** | 0x33 / 0x43 / 0x53 | 상위바이트 RX_SELECT: CRx0/CRx1/CRx2 선택 |
| **Pattern Definitions** | 0x34 / **0x44** / 0x54 | Wav Pattern0/1(파형 선택) + CalCap 크기 + Inactive Rxs |
| Prox Settings (참고: 실제 이 이름의 레지스터) | 0x61/0x71/0x81 | Channel별 **Prox Threshold/Debounce** — CTx/CRx 할당과 무관 |

0x40은 "Prox Settings"가 아니라 **Sensor 1 Setup**(TX_SELECT 포함)이고, 0x44는 "CalCap/Rx-Tx"가 아니라 **Pattern Definitions**(Wav Pattern·CalCap 크기·Inactive Rx)다. CalCap의 Tx/Rx 지정 비트(CalCap Tx=bit13, CalCap Rx=bit14) 자체는 0x40(Sensor Setup) 안에 있으므로 과업 문구가 완전히 틀린 것은 아니나, "Prox Settings"라는 이름은 다른(0x71) 레지스터를 가리키므로 혼동 방지를 위해 정정한다.

## 4. (c) mutual 모드에서 ATI 거동

- §5.9(ATI)는 self/mutual/inductive를 구분하지 않고 "Counts를 ATI Target에 수렴시키는" 동일 2단계(MULT→COMP) 알고리즘으로 기술한다. **mutual 전용 ATI 모드·알고리즘 분기는 원문에 없음**(확인 범위 내 미기재).
- Azoteq 자체 mutual 예제(3PROJ_BUTTONS)가 `ATI Mode=Full`(§1 표)을 그대로 사용 — mutual이라고 ATI를 disable하거나 다른 모드를 강제하지 않는다는 **직접 증거**.
- §5.9 노트: conversion frequency > 2MHz일 때 Compensation 최소화 권고가 있으나, 이는 주파수 조건부이지 self/mutual 조건부가 아니다.
- A.6: self-capacitive 최대 권장 변환주파수 1MHz, **mutual-capacitive는 2MHz까지 허용** — mutual이 더 높은 conversion frequency를 쓸 수 있다는 차이는 있으나(대역폭 여유), ATI 수렴 로직 자체는 동일하다.
- **미확인**: Sound1이 이미 겪은 "Full ATI 모드에서 stuck-touch 시 auto re-ATI → I2C 무응답"([`IQS323-레지스터-맵.md`](../../../../참고/touch/레퍼런스/IQS323-레지스터-맵.md) §9 핵심 함정) 문제가 mutual 모드에서도 동일하게 재현되는지는 self-cap 사례로만 확인됐고 mutual에 대한 재현성은 **문서 근거 없음** — mutual 도입 시 동일 리스크를 기본 가정해야 한다(실측 필요).

## 5. (d) 현 HW(CRX0 중앙·CRX1 외곽)에서 레지스터만으로 페어링 가능한가

### 5.1 물리 핀 구조 (사실 — 회로도 근거)

[`IQS323-회로-구성.md`](../../../../참고/touch/레퍼런스/IQS323-회로-구성.md) 회로도 기준, IQS323001CSR의 아날로그 핀은 **TxA·CRX0·CRX1·CRX2 4개뿐**이며 별도의 "CTx0/CTx1/CTx2" 물리핀은 없다. §5.12.1 SW구현관점 노트("CRx bit와 CTx bit를 **동일 핀 번호**로 함께 set")와 결합하면, **CTx0/CRx0는 물리적으로 같은 핀(CRX0)을 논리적으로 겸용**한다는 뜻이다(추론이지만 두 근거가 정합적으로 수렴 — 신뢰도 높은 해석).

Sound1 현재 배선([`IQS323-회로-구성.md`](../../../../참고/touch/레퍼런스/IQS323-회로-구성.md) §2·§5):

| 핀 | 배선 | 현재 SW 역할 |
|---|---|---|
| CRX0(B2) | R31(100Ω)→C51(100pF)→**J3**(터치패드, 중앙) | CH0 활성 self-cap |
| CRX1(A1) | C52(100nF)→R32(0Ω)→**J4**(터치패드, 외곽) | CH1 비활성(CalCap 더미) |
| TxA(B6) | R30(0Ω)→**No Connect(미배선)** | 완전 미사용 |

### 5.2 레지스터만으로 되는가 — 사실 기반 판단

- **CRX0을 Tx(CTx0), CRX1을 Rx(CRx1)로 재정의**하는 것은 데이터시트 문구("Mutual-cap은 CRx와 CTx를 서로 다른 핀으로 설정") 및 §1 예제의 레지스터 패턴(한 Sensor 블록 안에서 TX_SELECT·RX_SELECT를 독립적으로 아무 핀이나 선택 가능함을 실증)에 **비추어 레지스터 설정만으로 시도 가능** — CRX0·CRX1 둘 다 **이미 D패드 전극에 물리적으로 연결되어 있어 새 배선(HW 개조)이 필요 없다.**
- 필요 레지스터 변경(추정 조합, 사실 근거는 각 필드 정의): Sensor0 `TX_SELECT`=CTx0 bit set, `RX_SELECT`=CRx1 bit set, `PXS Mode`=0x13, `Wav Pattern0`=0x0E(+Wav Pattern Select=0x00), `Invert`=1, S/H Bias(§6.2 권고 10µA — 단 예제는 7µA 사용, §1 표 참고), 변환주파수 ≤2MHz(A.6).
- **단, 이것은 "레지스터 필드가 논리적으로 허용한다"는 뜻이지 "Sound1 HW에서 실측 검증됐다"는 뜻이 아니다** — 아래 §5.3 리스크 참조.

### 5.3 리스크·미검증 사항 (가설/추정 — 명확히 구분)

1. **기존 수동소자값 미검증**: R31(100Ω)+C51(100pF, CRX0측)과 C52(100nF)+R32(0Ω, CRX1측)는 원래 "CH0 self-cap 활성 / CH1 CalCap 더미" 설계 의도로 결정된 값이며 mutual Tx-구동/Rx-수신 용도로 특성화된 적이 없다. 간이 계산(가설, 실측 아님)으로는 두 값 모두 수백 kHz~2MHz 대역에서 임피던스가 낮아(C51 저역통과 코너 ≈15.9MHz, C52는 500kHz에서 ≈3Ω) 신호를 심하게 막지는 않을 것으로 추정되나, **이는 계산 추정이지 실측이 아니다.**
2. **CRX0의 역할 근본 변화**: mutual Tx로 쓰면 CRX0(현재 "중앙 채움"의 활성 self-cap 감지점)는 더 이상 자신의 정전용량을 직접 보고하지 않고 **순수 Tx 구동 전극**이 된다 — 터치 감지 원리가 "중앙 전극 자체 용량 변화"에서 "중앙→외곽 결합용량 변화"로 근본 전환된다. 이는 전극·패드 물리설계(P4) 영역과 직결되므로 그쪽 검토와 반드시 합류해야 한다.
3. **Azoteq 참조례 공백**: 공식 mutual 예제(3PROJ_BUTTONS)는 **전용 Tx핀 TxA만 사용**하고 CTx0/1/2(=CRx와 겸용되는 핀)를 Tx로 쓰는 조합은 예제에 없다. 즉 "겸용 핀을 mutual Tx로 쓰는" 패턴 자체가 Azoteq의 실증된 참조 설계가 아니다 — 데이터시트 문구상 허용되어 보이나 **검증된 선례가 없다는 공백**은 남는다(미확인).
4. Sound1 TxA를 살리는 대안(회로 재작업으로 R30에 실배선)은 Azoteq 참조 패턴과 완전히 일치하지만 **HW 개조(R30 재작업 + 트레이스 라우팅)가 필요**해 "레지스터만으로"의 범위를 벗어난다 — (d)의 "혹은 HW 배선 제약"에 해당하는 경로다.

## 6. (e) 3채널 IC에서 mutual 페어링의 채널 소모

IQS323은 Sensor0/1/2(0x3x/4x/5x) 각각이 독립된 TX_SELECT+RX_SELECT를 갖고, 이것이 Channel0/1/2(0x6x/7x/8x)에 1:1 대응한다. §1 예제에서 확인했듯 **Tx 핀과 Rx 핀이 물리적으로 분리돼도 그 페어링은 "하나의 Sensor+Channel 슬롯"에 담긴다** — 3개 버튼 예제가 정확히 3개의 서로 다른 Sensor/Channel(TxA 공유 + CRx0/CRx1/CRx2 개별 Rx)을 쓰는 것이 그 증거다.

따라서 **CRX0-CRX1 mutual 페어링 1건은 채널 1개(예: Sensor0/Channel0)만 소모**한다 — Tx·Rx가 두 물리핀에 걸쳐 있다고 채널이 2개 드는 것이 아니다. 나머지 Sensor1/Channel1(CRX1 자리, 이미 Rx로 소모됨에 유의)·Sensor2/Channel2(CRX2)는 이 페어링과 무관하게 별도 용도로 여유가 있다 — 단 CRX1 핀 자체는 위 페어링에서 Rx로 이미 점유되므로, CRX1을 동시에 다른 독립 채널의 Rx로 중복 사용할 수는 없다(핀 자원은 1개, 채널 자원은 별개 축).

## 핵심 결론 (5줄)

1. IQS323는 mutual(projected) 모드를 레지스터로 완전 지원 — Azoteq 공식 예제가 `PXS Mode=0x13`·`Wav Pattern0=0x0E`·`Invert=1`을 정확히 사용함을 비트 단위로 확인(확립).
2. self/mutual 선택은 Channel Mode(0x70)가 아니라 Sensor Setup의 CTx 선택 + Prox Input의 CRx 선택(같은 핀=self, 다른 핀=mutual) + PXS Mode 필드가 결정한다(과업 문구 (a)(b) 정정).
3. mutual 전용 ATI 알고리즘 분기는 없음 — Azoteq 자체가 mutual에도 Full ATI를 그대로 씀(확립). 단 self-cap에서 확인된 "Full ATI stuck-touch → I2C 무응답" 리스크가 mutual에서도 재현되는지는 미확인.
4. CRX0(중앙)-CRX1(외곽) 페어링은 두 핀 다 이미 D패드에 배선돼 있어 **레지스터 설정만으로 시도는 가능**하나, 기존 수동소자값·전극 역할 변화·Azoteq 참조례 공백이라는 세 가지 미검증 항목이 남는다.
5. 채널 소모는 페어링당 1개 — 3채널 예산에서 여유가 있다는 점은 명확(확립).

## 이 페르소나가 본 리스크·불확실성

- **실측 게이트 필요**: §5.3의 수동소자 특성·전극 감도는 계산 추정일 뿐, 벤치 측정(Cm 실측, Counts 응답) 없이는 "된다"고 단정할 수 없다.
- **참조 선례 공백**: Azoteq 자체 예제가 "겸용 CTx→Rx핀 재사용" 방식을 실증한 적이 없다는 점은, 이 조합이 알려지지 않은 부작용(누화·Tx 구동력 부족 등)을 가질 가능성을 완전히 배제하지 못한다.
- **CRX0 역할 전환의 파급**: mutual 도입 시 현재 "중앙 활성 self-cap"이라는 검증된 동작 원리 자체가 바뀐다 — 이는 순수 IC 능력 문제를 넘어 P4(전극·패드 물리설계)·P5(현설계 이력)·P6(대안 결정) 페르소나의 판단과 반드시 합류해야 할 지점이다.
- **S/H Bias 불일치**: 데이터시트 프로즈(§6.2)는 10µA 권고, Azoteq 예제 실제값은 7µA(코드 "10") — 사소하지만 "권장값"과 "예제 실제값"이 다르다는 점은 명시해 둔다.
