# 00-v2 오케스트레이터 입력 — RDY 윈도우·스트리밍·ATI/LTA 재검증 (Workflow)

**TL;DR**: v1(01~08, Agent 폴백)은 내용 유효하나 지침 §5 위반(Workflow 우선). 본 v2는 은수님 추가 입력 3건(통신 윈도우 비용·스트리밍 윈도우·ATI=Re-ATI/FIXED LTA delta 유효성)을 신규 명제 G~J로 추가하고 **`Workflow` 도구(effort 실제 적용)**로 재실행한다.

---

## 1. 은수님 추가 입력 (원문 보존)

1. **참조 추가**: `docs/참고/touch/개선/RDY 윈도우 타이밍/` 폴더 + `RDY 윈도우 타이밍.md` — RDY 윈도우 타이밍 분석이 추가됨.
2. **통신 윈도우 의문**:
   - **2-1**: 터치 상태를 읽기 위해 I2C로 읽을 레지스터를 지정하는 순간 stop 신호 발생 → 통신 윈도우 닫힘? 그럼 실제 터치 상태를 읽으려면 다음 통신 윈도우가 열릴 때까지 대기해야 하나? 시간을 엄청 소모하는 것 같다.
   - **2-2**: 스트리밍 모드에서 약 200ms 동안 통신 윈도우가 열려 있다면, 굳이 내가 통신 윈도우를 (force로) 열 필요가 있나?
3. **ATI 용어·LTA 의문**:
   - **3 (큰 맥락)**: Auto ATI = Re-ATI 같은 말인가? 그렇다면 전원 켜질 때 터치한 상태로 켜지면 켜지자마자 auto ATI가 수행된다.
   - **3-1 (핵심)**: 이 상태에서 Re-ATI를 안 해도 LTA가 자동으로 카운터에 수렴한다고 했다. **auto ATI를 비활성화해서 LTA가 ATI 밴드를 벗어나더라도, Re-ATI를 안 할 뿐 터치 자체는 카운터와 LTA의 차이(delta)니까 threshold 설정은 계속 유효한가?**

---

## 2. 신규 검증 명제 (v1 명제 A~F에 추가)

| ID | 명제 | 핵심 |
|---|---|---|
| 명제_G | 통신 윈도우 폐쇄·재개방 비용 (2-1) | read 명령→stop→윈도우 닫힘. 다음 윈도우 대기 시간 정량. force_window_open 실제 비용 |
| 명제_H | 스트리밍 모드 윈도우 (2-2) | 스트리밍 시 윈도우 ~200ms 열림이 사실인가, force_window_open 불필요한가, 스트리밍 read로 충분한가 |
| 명제_I | auto-ATI = Re-ATI 동일어 여부 (3) | 용어 정리. 전원 ON 터치 상태에서 auto-ATI 발동 메커니즘 |
| 명제_J (핵심) | FIXED + LTA delta 터치 판정 유효성 (3-1) | ATI 비활성으로 LTA가 ATI 밴드 이탈해도 Re-ATI만 스킵, 터치=counts−LTA delta로 threshold 계속 유효한가? → "FIXED 충분" 갈림길의 기술 근거 |

> 명제_J가 입증되면 ATI Full·retry-count 논의 전체의 상위 분기(분석.md §8 갈림길)가 "FIXED 유지"로 기운다.
