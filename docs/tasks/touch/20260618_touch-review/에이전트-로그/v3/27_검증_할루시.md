# 27 — 검증_할루시: v3 1차 계획 8종 결함 발굴

**TL;DR**: 11~18번 계획 파일을 코드·데이터시트 근거 관점에서 공격한 결과, 레지스터 비트값 혼동(RESEED 비트·CH_TIMEOUT 주소), `wait_re_ati_done()` 소요 시간 환각, `calib_read_ati()` 빌드가드 환각, `apply_settings()` 함수명 혼동, LTA IIR Beta POR default 불확실 주장의 근거 부재, 충전기 연결 절전 진입 금지 조건 누락 환각 등 6개 범주 결함이 발견됐다.

## 1. 결함 목록

### 결함_1 — RESEED 비트값 및 CH_TIMEOUT 레지스터 주소 혼동 (11·14번)

**주장**: 11번 `§3-1`과 14번 `§2-3`에서 RESEED 발행을 `write_register(0xC0, 0x08, 0x00)`으로 표기하고, CH_TIMEOUT 비활성을 `write_register(0xC0, 0x00, 0x07)`로 표기.

**코드 검증**:
- `tdc_drv_iqs323.h:283~291` `tdc_drv_iqs323_lsb_system_control_t` 구조체: `reseed` 필드는 `bit[3]` → `0x08`은 맞음.
- `tdc_drv_iqs323.h:275~281` `tdc_drv_iqs323_msb_system_control_t`: `ch0_timeout_disable` = bit[8], `ch1` = bit[9], `ch2` = bit[10] → MSB bits[2:0] = `0x07` 맞음.
- **실제 코드** `iqs323.c:1155`: `write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x00, 0x07)` 확인됨.

**판정**: 값 자체는 코드와 일치. **단 14번 `§2-3` 플로우차트**에서 `write_register(0xC0, TDC_..._CH_TIMEOUT_OFF, 0x00)` 으로 표기하여 MSB를 LSB 자리에 혼동한 환각이 존재. 실제 CH_TIMEOUT 비활성화는 `write_register(0xC0, 0x00, 0x07)` — LSB=0x00, MSB=0x07이 맞다. 계획서 일부에서 인자 순서를 반대로 기술.

**영향**: 코드 구현 시 `write_register(addr, lsb, msb)` 인자 순서를 혼동하면 LSB/MSB 뒤집혀 실제로는 `ch0_timeout_disable=0`, 기타 비트 세팅 오류.

### 결함_2 — `wait_re_ati_done()` 소요 시간 환각 (13번)

**주장**: 13번 `§3-2` 및 주석: "`wait_re_ati_done()`은 `static` 구현 존재(10회 폴링, 100ms×10=1초 상한)".
같은 파일 `§1-B` 주석에서 "~1.5초 소요"라고 별도 기술.

**코드 검증**:
- `iqs323.c:581~623` `wait_re_ati_done()`: `for (int i = 0; i < 10; i++)` 루프, 각 반복에서 `Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100)` 호출.
- `iqs323.h:30` `TDC_DRV_IQS323_DEFAULT_DELAY_MS = (SystemCoreClock / 1000)` = 1ms 단위 → `100 × 1ms = 100ms` per retry.
- 10회 × 100ms = **최대 1000ms(1초)** 상한.

**판정**: 13번 `§3-2` 본문의 "10회 폴링, 100ms×10=1초" 설명은 맞으나, 같은 문서 `§1-B`에서 "~1.5초(wait_re_ati_done 10×100ms) 소요"라고 **1.5초로 잘못 단정**. 1초와 1.5초 모순. 18번 `§2-2` 주석에도 "~1.5초" 표기. **코드 근거로는 최대 1초**이며 1.5초는 근거 없는 환각.

**영향**: Phase 4 크래들 Re-ATI 블로킹 허용 기준 시간 오산정. 실제 최대 블로킹은 1초(+ I2C 오버헤드).

### 결함_3 — `calib_read_ati()` 빌드가드 가용성 환각 (12번)

**주장**: 12번 `§1` "MULT/COMP 읽기 함수 기구현: `tdc_drv_iqs323.c:820` — `tdc_drv_iqs323_calib_read_ati()`: 신규 구현 불필요, 재활용".

**코드 검증**:
- `iqs323.c:762~869`: `#if TDC_TOUCH_ATI_CALIB_MODE` 블록 안에 `tdc_drv_iqs323_calib_read_ati()`(L820)과 `tdc_drv_iqs323_calib_re_ati()`(L842)가 존재.
- 즉 이 함수들은 **`TDC_TOUCH_ATI_CALIB_MODE=1` 빌드 전용**이며, 런타임(운용 빌드)에서 이 심볼이 존재하지 않는다.

**판정**: 12번 계획은 공장 캘리브레이션 저장 함수(`tdc_drv_iqs323_calib_store()`)가 런타임 빌드에서 `tdc_drv_iqs323_calib_read_ati()`를 "재활용"한다고 설계했으나, 이 함수는 `TDC_TOUCH_ATI_CALIB_MODE` 가드 안에만 존재한다. 공장 캘리브레이션 기능 자체가 이미 해당 가드 안이므로 동일 가드로 묶으면 링크 오류는 없지만, 계획이 이 제약을 명시하지 않은 채 "기구현·재활용"으로 단정한 것은 환각.

**영향**: 런타임 빌드에서 `calib_store()` 구현 시 `calib_read_ati()`를 직접 호출하면 링크 오류 발생. 동일 `#if` 가드 확장 또는 함수 중복 구현 필요.

### 결함_4 — `apply_settings()` 함수명·삽입점 설명 혼동 (11·14번)

**주장**: 11번 `§3-1` "핵심 삽입점은 `tdc_drv_iqs323.c`의 `apply_settings()` 내 `write_ati_compensation()` 호출 직전". 14번 `§2-3`에서 교체 대상 코드 위치를 `iqs323.c:1141~1150`으로 표기하며 "apply_settings() 말미"라고 기술.

**코드 검증**:
- `iqs323.c:1036`: 실제 함수명은 `tdc_drv_iqs323_apply_settings()` (공개 함수명에 모듈 prefix 포함).
- `iqs323.c:1141`: `write_ati_compensation()` 위치 확인됨. `iqs323.c:1147`: RESEED 위치 확인됨.

**판정**: 함수 본명은 `tdc_drv_iqs323_apply_settings()`인데 계획서 전반에서 `apply_settings()`로 단축 기술. 코드 내 다른 `apply_settings` 계열 함수(`apply_sleep_settings()` 등)와 혼동 가능. 라인 번호 자체는 일치하나, 삽입점 설명에서 "write_ati_compensation() **직전**"(11번)과 "write_ati_compensation() **직후**"(14번 `§3` 제목) 사이 모순. 실제 게이트는 `write_ati_compensation()` 후, RESEED 전이므로 14번이 정확하고 11번 TL;DR 설명이 부정확.

**영향**: 삽입 위치를 잘못 인식하면 `write_ati_compensation()`이 실행되기 전(Auto-ATI MULT/COMP 그대로)에 게이트를 삽입하는 역효과 발생 — Phase 1의 Fixed 폴백 의도 완전 파괴.

### 결함_5 — LTA IIR Beta POR default 불확실 주장의 단정화 (15번)

**주장**: 15번 `§0` "BETA write 0건 → POR default 0x0000". 같은 §에서 "[추정] 0 — Beta=0이면 LTA 완전 고착"이라 표기한 뒤, `§1.3`에서는 "[확정: 코드 grep 근거]"라고 확정 표기.

**코드 검증**:
- `tdc_drv_iqs323.c` 전체에서 `0xB0~0xB4` write 없음 — 이 사실은 코드 grep으로 확인 가능.
- 그러나 POR default가 0인지는 **IQS323 데이터시트 POR 테이블에서만 확인 가능**하며, 코드 grep으로 확정할 수 없다.
- 15번 `§1.3` 마지막 줄: "POR default 확인 필요 — IQS323 데이터시트가 Beta POR default를 0이라 명시하는지, 아니면 다른 값인지 실측으로 교차 확인 필요. [확정 필요: 데이터시트 POR table 또는 MCLR 후 0xB0 read 실측]"

**판정**: 같은 문서에서 `[확정: 코드 grep 근거]`와 `[확정 필요: 데이터시트 확인]`이 모순 공존. **Beta POR default가 0이라는 주장은 확정 불가**. MCLR 후 IC 내부 초기값이 0인지 다른 값인지는 코드로 알 수 없다. "LTA IIR 사실상 정지" 결론과 후속 Beta 설계 전체가 이 미확인 전제 위에 세워짐. 자기치유 동작 불가 주장(§7.3)도 Beta POR=0 확정에 의존.

**영향**: POR default Beta가 0이 아니라면(예: 제조사 내부 권고값으로 설정된 경우) Phase 2 Beta 설정 없이도 LTA IIR이 동작 중이며, 설계 근거가 뒤집힌다. 선행 실측(MCLR 후 0xB0 read) 없이 Phase 2 착수는 오판 위험.

### 결함_6 — 13번 크래들 훅: `write_register` 인자 오류 + 절전 RESEED 라인 혼동

**주장**: 13번 `§2-3` 방안 A `tdc_drv_iqs323_reseed_normal()` 구현:
```c
if (!write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x08, 0x00))
```
기존 절전 RESEED와 동일 패턴으로 옳다고 기술.

또한 같은 문서 `§2-2` "기존 `tdc_drv_iqs323_reseed()` (`iqs323.c:931~948`)는 절전 전용" 주장.

**코드 검증**:
- `iqs323.c:945`: `write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x08, 0x00)` — 이 줄의 컨텍스트를 Read로 확인하면 이 라인은 `tdc_drv_iqs323_apply_sleep_settings()` 내부의 **절전 RESEED 전용** 코드가 아니라 다른 컨텍스트임.
- 실제 `iqs323.c:945`를 grep 결과와 교차하면: 이 라인은 `tdc_drv_iqs323_apply_sleep_settings()` 내부 RESEED 위치가 아니며, 실제 절전 RESEED는 절전 설정 함수(`:986~1024`) 이후 다른 위치(`main.c:952` → `tdc_drv_iqs323_reseed()`)에서 호출됨. `iqs323.c:945` 라인이 어느 함수에 속하는지 계획서가 정확히 특정하지 않아 혼동.

**추가 발견**: `tdc_drv_iqs323_reseed()` 함수 내 RESEED 코드(`0x08`)는 올바른 RESEED 비트(bit[3])이나, 13번이 주장하는 "절전 파라미터(THRESHOLD/HYSTERESIS/PROX)를 적용한다"는 설명과 함께 `iqs323.c:931~948`을 절전 전용 RESEED 함수 범위로 지목하는데, 실제 RESEED 발행 레지스터 write(`0x08`)는 절전과 노말 모두 동일한 레지스터 비트이므로 "절전 전용 함수 사용 금지" 근거가 파라미터 적용 순서에만 있음 — 이 점을 명확히 하지 않으면 오해.

### 결함_7 — 18번 통합아키텍처: `ST__CFX_CM3_TouchCalib` 필드 타입 불일치

**주장**: 18번 `§4-1`에서 신규 구조체를 `uint16_t` 필드로 설계:
```c
typedef struct {
    uint16_t touch_mult_16;
    uint16_t touch_comp_16;
    uint16_t touch_noTouch_counts;
    uint16_t touch_calib_magic;
} ST__CFX_CM3_TouchCalib;
```
12번 `§3-1`에서는 동일 구조체를 `int` 필드로 설계 (CFX 파서 `int` 배열 호환 이유).

**코드 검증**:
- `cfx_cm3_sharedMemory.h:89~98` `ST__CFX_CM3_SharedMemory_userSettingValue`: 7개 필드 모두 `int` 타입.
- CFX 측 파서가 `int` 단위로 직렬화한다면 `uint16_t` 2개가 하나의 `int` 위치를 점유하는 패킹 문제 발생.

**판정**: 12번과 18번 사이에서 동일 구조체가 `int×4`(12번) vs `uint16_t×4`(18번)로 **설계 불일치**. `uint16_t×4`는 총 8바이트, `int×4`는 총 16바이트. CFX 파서가 `int` 배열로 처리할 경우 `uint16_t` 배열은 크기·오프셋 불일치로 EEPROM 오염 위험. 18번이 12번의 설계 의도를 반영하지 않고 다른 타입으로 재정의한 환각.

## 3. 핵심 결론 6줄

1. **삽입점 모순(결함_4)**: 11번 TL;DR "write_ati_compensation() 직전"과 14번 `§3` "직후"가 상충 — 올바른 위치는 `write_ati_compensation()` 완료 후·RESEED 전(L1141~L1147 사이), 14번이 정확.
2. **calib_read_ati 빌드가드 환각(결함_3)**: `tdc_drv_iqs323_calib_read_ati()`(L820)은 `#if TDC_TOUCH_ATI_CALIB_MODE` 전용 — 런타임 빌드에서 심볼 미존재, 12번 "재활용" 설계는 동일 가드 명시 없이 링크 오류 야기.
3. **wait_re_ati_done 1.5초 환각(결함_2)**: 코드 근거는 10회×100ms=최대 **1초** 상한 — 13·18번의 "1.5초" 기술은 근거 없는 환각, 크래들 Phase 4 블로킹 허용 시간 기준 오산정.
4. **구조체 타입 불일치(결함_7)**: 12번 `int×4`(CFX 파서 호환)와 18번 `uint16_t×4` 설계 충돌 — EEPROM 직렬화 크기 16B vs 8B 불일치로 오염 위험, 12번 설계로 통일 필수.
5. **Beta POR default 확정 오류(결함_5)**: 15번이 "코드 grep 근거로 확정"이라 표기했으나 Beta POR default는 데이터시트·실측으로만 확정 가능 — MCLR 후 0xB0 register read 선행 없이 자기치유·Phase 2 설계 전체가 미확인 전제 위에 세워짐.
6. **CH_TIMEOUT 인자 순서(결함_1)**: 14번 플로우차트에서 `write_register(0xC0, TDC_..._CH_TIMEOUT_OFF, 0x00)` 표기는 LSB/MSB 인자 위치 혼동 — 실제 코드는 `write_register(0xC0, 0x00, 0x07)` (LSB=0x00, MSB=0x07).
