# 54 — 재검증2: adversarial (통신전력 관점)

**TL;DR**: 49_종합-재검증1을 통신·전력 예산 관점에서 공격. wait_re_ati_done() 1.9초 주장의 산술 재검증에서 wait_rdy_window_closed 비용이 2회 추가 누락된 신규 오류 발견. R3_CHARGING 비블로킹 설계의 ATI_Active 폴링 구조가 코드에 존재하지 않는 경로임을 확인. write_register 1회 = force_window_open 1회(쓰기)임을 코드로 확인해 44_재검증1 일부 주장이 과대계산임을 역공격. 나머지 4항목은 수렴 또는 이미 블로킹으로 올바르게 분류됨.

## 1. 새 약점 1 — wait_re_ati_done() 1.9초 주장에 wait_rdy_window_closed 비용 누락 [치명도: 중간]

### 1-1. 49_종합의 주장

> "wait_re_ati_done() 블로킹 시간 정정: Sys_Delay 기준 최대 1초 + force_window_open 포함 최악 **~1.9초**" (`49_종합-재검증1 §4 Phase 3`, `§핵심10줄.7`)

### 1-2. 코드 실제 구조 (tdc_drv_iqs323.c:581~623)

```
wait_re_ati_done() 루프 1회:
  read_register() 호출:
    (1) force_window_open()      — 최악 45ms  [코드 :143~172]
    (2) i2c_write(addr, 1)      — ~0.2ms
    (3) wait_rdy_window_closed() — 최악 MAX_WAIT_MS_FOR_WINDOW_CLOSE  ← 44_재검증1 누락
    (4) force_window_open()      — 최악 45ms
    (5) i2c_read(buf, 2)        — ~0.2ms
    (6) wait_rdy_window_closed() — 최악 MAX_WAIT_MS_FOR_WINDOW_CLOSE  ← 44_재검증1 누락
  Sys_Delay(100ms)
```

`wait_rdy_window_closed(TDC_DRV_IQS323_MAX_WAIT_MS_FOR_WINDOW_CLOSE)`가 **read_register 1회당 2번** 호출된다(코드 `:244`, `:261`). 44_재검증1의 force_window_open 비용 계산이 `wait_rdy_window_closed` 비용을 누락했고, 49_종합이 이 값을 그대로 흡수했다.

`TDC_DRV_IQS323_MAX_WAIT_MS_FOR_WINDOW_CLOSE` 실제값은 코드에서 grep 미확인 [확정 필요]. 데이터시트 §8.13 기준 t_Low ≈ 0.5ms(일반), 최악 20ms(28_검증_전력 §0 기준값 인용).

**보정 계산**:
```
read_register 1회 최악:
  force_window_open × 2 = 45+45 = 90ms
  wait_rdy_window_closed × 2 = 20+20 = 40ms (최악, 28번 §0 기준)
  i2c overhead = ~0.5ms
  합계 ≈ 130.5ms

wait_re_ati_done 10회 최악:
  (130.5ms + 100ms) × 10 = 2305ms ≈ 2.3초
```

> [!IMPORTANT]
> 49_종합의 "Sys_Delay 1초 + force_window_open 최악 ~0.9초 = ~1.9초"는 wait_rdy_window_closed × 20회 = 최악 400ms를 누락한다. **실제 최악은 ~2.3초**다. 단, MAX_WAIT_MS_FOR_WINDOW_CLOSE가 실제로 20ms인지 확인 필요 [확정 필요].

**수정 방향**: Phase 3 §4 "블로킹 최악 ~1.9초"를 "~2.3초(wait_rdy_window_closed 포함)"로 정정. 실제값 확정은 `tdc_drv_iqs323.h`에서 MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수 확인으로 해소.

## 2. 새 약점 2 — 44_재검증1의 force_window_open 비용 역공격: write_register는 1회만 [해명 필요]

### 2-1. 44_재검증1의 주장 (49_종합이 흡수한 전제)

> "read_register 1회 = force_window_open 2회 (주소-write STOP 후 re-open + data-read re-open)" (44_재검증1 §1-3, `v2 명제_G`)

### 2-2. 코드 검증 (tdc_drv_iqs323.c:178~198)

```c
static bool write_register(uint8_t addr, uint8_t lsb, uint8_t msb)
{
    if (!force_window_open())   /* 1회만 */
    {
        ...
    }
    i2c_write(buf, 3);
    wait_rdy_window_closed(...);
    return true;
}
```

`write_register`는 `force_window_open` **1회**만 호출한다. 44_재검증1이 "각 루프 반복에서 read_register = force_window_open × 2 최악 90ms"라고 계산한 것은 **read_register에 한해 맞으나**, wait_re_ati_done 루프 내 각 트랜잭션이 read_register임은 코드(`:590`)로 확인된다. 따라서 force_window_open × 2 주장 자체는 read_register 경로에서 **정확**하다.

그러나 **49_종합이 Re-ATI 시퀀스 기술 중 "write_register 비용"과 "read_register 비용"을 혼용하는 설명**이 있다. Phase 3 비블로킹 설계(§2-4)의 `re_ati_trigger()` = write_register 1회이므로 최악 45ms, `wait_re_ati_done()` 내 각 read_register 최악 130ms — 이 두 값을 구분하지 않고 "1.9초"로 단일화한 기술이 추후 구현 시 혼란을 야기할 수 있다.

**공격 포인트**: 49_종합 §4 Phase 3의 비블로킹 설계 설명에서 `re_ati_trigger()` 비용(write 1회 ≈ 45ms)과 `ATI_Active 확인 1회`(read 1회 ≈ 130ms)의 총 비블로킹 오버헤드가 명시되지 않았다. 비블로킹 1회 왕복 = 최악 175ms — 이것이 200ms 폴링 주기 내에 반드시 완료됨을 보장하는 근거가 없다 [확정 필요].

## 3. 새 약점 3 — R3_CHARGING 비블로킹 "ATI_Active 확인" 경로가 현 코드에 존재하지 않음 [치명도: 높음]

### 3-1. 49_종합의 주장

> "비블로킹 구조 선호 — re_ati_trigger() 발행 후 다음 폴링에서 ATI_Active 확인" (`49_종합-재검증1 §2-4`)

> "R3_CHARGING: ... 비블로킹 선호 — re_ati_trigger() 발행 후 다음 폴링에서 ATI_Active 확인 (블로킹 wait_re_ati_done()은 1초 race 창으로 사용 금지)"

### 3-2. 코드 검증

`re_ati_trigger()`(`:569`)는 `write_register(SYSTEM_CONTROL, ...)` 1회이며 존재한다. 그러나 **비블로킹 "다음 폴링에서 ATI_Active 확인"** 경로는:

- `tdc_drv_iqs323_read_status()` (`:1166`)는 `ati_error`와 `pressed`만 반환하며, **ATI_Active 비트는 읽지 않는다**.
- `is_auto_ati_done_single_read()` (`:312`)는 `ati_active == 0`을 확인하나 이 함수는 `static`이고 부팅 초기화 경로 전용이다 — 런타임 폴링 루프(`tdc_touch_process`)에서 호출되지 않는다.
- 런타임 Re-ATI 완료를 비블로킹으로 확인할 수 있는 **public API가 현재 존재하지 않는다**.

49_종합이 제안한 R3_CHARGING 비블로킹 구조는 **현재 코드에 존재하지 않는 경로를 전제**로 한다. 구현하려면:

1. `tdc_drv_iqs323_read_status()`를 확장해 ATI_Active 비트를 출력 파라미터로 추가하거나,
2. `is_auto_ati_done_single_read()`를 extern 노출해 런타임에서 호출 가능하게 해야 한다.

이 신설 없이 "다음 폴링에서 ATI_Active 확인"은 구현 불가능한 설계다.

> [!IMPORTANT]
> **R3_CHARGING 비블로킹 설계가 전제하는 ATI_Active 읽기 API가 존재하지 않는다.** Phase 3 구현 착수 전 `tdc_drv_iqs323_read_status()` 확장 또는 별도 `tdc_drv_iqs323_is_ati_done()` 신설이 필수 선행 사항으로 추가돼야 한다. 이것이 없으면 비블로킹 구조가 불가능해 blocking wait_re_ati_done()으로 후퇴하거나, ATI_Error 핸들러 경로에만 의존하는 취약한 설계가 된다.

**블로킹_H(신규) 제안**: `tdc_drv_iqs323_is_ati_active()` 또는 `read_status()` ATI_Active 확장 — Phase 3(R3_CHARGING) 착수 전 필수.

## 4. 새 약점 4 — 크래들 FPGA 절전 지연 전력 미정량화 여전히 미해결 [치명도: 중간]

### 4-1. 49_종합의 처리

49_종합 §5 블로킹 미지수 목록에 FPGA 활성 전력 정량화 항목이 **여전히 없다**. 44_재검증1 §2(새2: FPGA 절전 지연 비용 미정량화)는 "블로킹_G 신설 필요"로 발굴됐으나, 49_종합의 블로킹_G는 **"MCLR 후 전 레지스터 POR 완전 초기화 여부"**로 완전히 다른 내용을 담는다.

44_재검증1 발굴 항목 중 "Phase 4 FPGA 절전 지연 비용"은 49_종합에서 **흡수 확인 없이 사라졌다**. §8 미해결 목록에도 없고, §5 블로킹 목록에도 없으며, §6 확인 항목에도 없다.

이는 44_재검증1의 새2 공격이 49_종합에 명시적으로 반영되지 않은 **누락**이다. 크래들 Phase 4 Re-ATI 중 FPGA 활성 전력 × ~2.3초가 배터리 소진 직전 케이스에서 유의미하게 작용하는지는 여전히 미정량화 상태다 [추정].

**수정 방향**: §5 블로킹 목록 또는 §6 확인 목록에 명시적으로 추가:

| ID | 항목 | 블로킹 Phase |
|---|---|---|
| **확인_11(신규)** | Phase 4 크래들 Re-ATI 중 FPGA 활성 전력 × ~2.3초 정량화 — 배터리 소진 케이스에서 유의미한지 | Phase 4 착수 전 |

## 5. 미검증 주장 1 — 비블로킹 Re-ATI가 200ms 폴링 주기 내 완료를 보장하는가 [치명도: 중간]

### 5-1. 49_종합의 주장

> "비블로킹 구조(trigger → 다음 폴링에서 ATI_Active 확인)" (`§2-4`, `§핵심10줄.7`)

### 5-2. 공격

IQS323 Re-ATI 소요 시간(t_ATI)은 데이터시트에서 확정되지 않았다(블로킹_D 격상 이전 항목). 49_종합은 t_ATI가 200ms 폴링 1주기 내에 완료된다고 암묵적으로 가정한다.

그런데 Auto-ATI 1회 소요 시간은 "~1.5초"(오케스트레이터 입력 §1 전제 4 세부, 블로킹_K @v3 18_통합아키텍처 §6 실측_K)로 기술돼 있다. Re-ATI와 Auto-ATI는 동일 알고리즘(명제_I: 조건부 참)이므로 t_ATI ≈ 1.5초가 가능하다.

비블로킹 구조에서 trigger 발행 후 200ms 후 ATI_Active를 읽으면 ATI가 아직 진행 중일 확률이 높다. 이 경우:
- 다음 폴링(200ms × N회)에서도 ATI_Active=1 → 완료 전까지 터치 폴링이 ATI 진행 중에 read_status()를 호출 → ATI_Active 중 I2C 응답이 어떻게 동작하는지 [확정 필요: DS §8.4 "I²C disabled during ATI" 상세].
- 충전 중 Re-ATI 도중 사용자 터치 → read_status()가 정상 응답하는가, 아니면 I²C disabled 기간에 걸리는가 [확정 필요].

비블로킹이 blocking보다 낫다는 전제는 이 불확실성을 해소해야 성립한다.

## 8. 핵심 6줄

1. **wait_re_ati_done() 최악 시간이 ~2.3초다** — 49_종합이 흡수한 "~1.9초"는 read_register 1회당 2번 발생하는 wait_rdy_window_closed(최악 20ms×2=40ms)를 10회 누락했다. MAX_WAIT_MS_FOR_WINDOW_CLOSE 확정 후 Phase 3 WDT·FPGA 지연 계산을 재수행해야 한다 [확정 필요].
2. **R3_CHARGING 비블로킹 설계가 존재하지 않는 API를 전제한다** — `tdc_drv_iqs323_read_status()`는 ATI_Active를 노출하지 않으며, `is_auto_ati_done_single_read()`는 static 부팅 전용이다. "다음 폴링에서 ATI_Active 확인" 비블로킹 구조는 현재 구현 불가능하며, 블로킹_H(신규)로 Phase 3 착수 전 필수 해소 항목을 추가해야 한다.
3. **비블로킹 Re-ATI 중 I2C 동작이 미확인이다** — t_ATI ≈ 1.5초 기간 중 DS §8.4 "ATI 중 I²C disabled" 적용 여부가 불명확하며, 비블로킹이 blocking보다 안전하다는 전제가 이 확인 없이 성립하지 않는다.
4. **44_재검증1 발굴(FPGA 절전 지연 전력)이 49_종합에서 증발했다** — 블로킹_G 명칭을 "MCLR POR 확인"이 선점하면서 "Phase 4 크래들 Re-ATI 중 FPGA 활성 전력 × 블로킹 시간 정량화"가 블로킹·미해결·확인 목록 어디에도 없는 상태다. 확인_11(신규)으로 §6에 추가해야 한다.
5. **수렴 확인**: read_register=force_window_open 2회(코드 `:232`·`:246`), write_register=1회(코드 `:182`)는 코드로 확인됐다. RESEED·ATI_Error 핸들러 위치·블로킹_D 격상·#error 가드는 재검증2에서 공격 불가로 수렴.
6. **수렴도 판정**: 통신전력 관점 부분 수렴 — 아키텍처 원리는 유지되나 Phase 3 착수 전 블로킹_H(ATI_Active API 신설)·최악 시간 정정(~2.3초)·DS §8.4 확인·확인_11(FPGA 전력)이 신규 해소 필요 항목으로 추가된다.
