# 63 — 재검증 라운드3: 완전성 adversarial 공격 (59_종합-재검증2 대상)

**TL;DR**: 59_종합-재검증2를 완전성 관점에서 공격. 신규 치명 5건·고위험 4건·중간 3건 발굴. 치명 최상위: ① CH_TIMEOUT 이중 차단 이유가 코드에 명시돼 있음에도 59 종합이 "미명시"로 잘못 처리 → 이유 발굴 가능. ② wait_re_ati_done() 안에 이미 tdc_drv_iqs323_is_auto_ati_done()이라는 공개 래퍼가 존재해 블로킹_H가 거짓 블로킹임. ③ re_ati_trigger() 내 SYSTEM_CONTROL MSB=0x00 write가 CH_TIMEOUT(0x07)을 덮어쓰는 연쇄를 코드로 확인 가능한데 미분석. ④ 확인_14 R3_CHARGING 게이트 기준 문제가 59 종합에 등록만 됐고 Phase 3 계획 본문에 반영이 없음. ⑤ 53_완전성·56_할루시가 발굴한 핵심 약점이 59 종합에서 일부 누락됨.

## 1. 치명 — CH_TIMEOUT 이중 차단 이유가 코드 주석에 이미 명시됨 — "미명시" 판정이 오류

### 1-1. 59 종합의 처리 (§2-8)

> "CH_TIMEOUT 이중 차단 이유: 커밋 이력 또는 원저자 확인 선행 (확인_12 신규)"

### 1-2. 공격 — 코드 주석으로 이미 확인 가능

`iqs323.c:1152~1155`를 직접 읽으면:

```c
/* CH0~CH2 stuck-touch timeout 비활성화 → auto-reATI 트리거 경로 차단
 * ATI Mode=Disabled(0x08)와 이중 방어. MSB bit[0..2] = ch0/ch1/ch2_timeout_disable */
ci_printv("[TOUCH] DISABLE CH TIMEOUT \r\n");
if (!write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x00, 0x07))
```

이중 차단 이유는 **코드 주석에 이미 명시**돼 있다:

> "stuck-touch timeout 비활성화 → **auto-reATI 트리거 경로 차단**. ATI Mode=Disabled(0x08)와 이중 방어."

즉 CH_TIMEOUT을 비활성화한 목적은 "CH_TIMEOUT 만료 시 자동 Re-ATI(Auto-ReATI)가 트리거되는 경로"를 막기 위한 것이다. ATI Mode=Disabled가 첫 번째 방어, CH_TIMEOUT 비활성화가 두 번째 방어.

**59 종합의 오류**:
1. "이중 차단 이유: 커밋 이력 또는 원저자 확인 선행"(확인_12)이라고 기술했으나, 이유는 코드 주석에서 **지금 당장** 확인 가능하다 — 블로킹·확인 항목 추가가 불필요하다.
2. §2-8에서 "CH_TIMEOUT 이중 차단 이유 미명시 상태에서 재활성하면 회귀 위험"이라 했으나, 이유가 명시돼 있으므로 재활성 여부 결정 선행조건(확인_12)이 이미 해소됐다.

**이유 해소 후 함의**:
- CH_TIMEOUT이 Auto-ReATI 트리거를 막기 위해 비활성화됐다 → ATI Mode=Disabled(Fixed) 아키텍처 하에서는 의도적 이중 차단이다.
- Phase 3에서 ATI Full을 활성화하면(ATI_FULL_ENABLE=1) Auto-ReATI가 다시 허용되므로, **CH_TIMEOUT 재활성도 Phase 3에서 함께 검토**해야 한다 — Phase 0이 아닌 Phase 3에 연결돼야 한다.
- 59 종합 §2-8에서 "Phase 0 즉시 실행 또는 Phase 1 착수 시 재활성 여부 결정"이라 했으나, 이중 차단 이유를 알면 **Phase 3(ATI Full 활성) 이전에는 재활성 불필요**라는 결론이 나온다.

**판정**: [치명] — 확인_12를 "커밋 이력 또는 원저자 확인"이라는 별도 작업으로 설정한 것은 오류이며, 블로킹·확인 목록에서 즉시 해소·제거돼야 한다. 아울러 §4 Phase 0·1에 포함된 "CH_TIMEOUT 재활성 검토" 항목을 Phase 3으로 재이관해야 한다.

## 2. 치명 — 블로킹_H가 거짓 블로킹: tdc_drv_iqs323_is_auto_ati_done() 공개 API 이미 존재

### 2-1. 59 종합의 처리 (§5 블로킹_H)

> "블로킹_H: tdc_drv_iqs323_is_ati_active() API 신설 또는 read_status() ATI_Active 필드 확장 — Phase 3(R3_CHARGING) 착수 전 필수"
>
> "is_auto_ati_done_single_read()를 extern 노출하거나 tdc_drv_iqs323_read_status() 반환 구조체에 ati_active 필드 추가"

### 2-2. 공격 — 코드 확인 결과 공개 래퍼가 이미 존재

`iqs323.c:926~928`을 직접 읽으면:

```c
bool tdc_drv_iqs323_is_auto_ati_done(void)
{
    return is_auto_ati_done_single_read();
}
```

`tdc_drv_iqs323_is_auto_ati_done()`은 이미 **공개(extern) 함수**로 선언돼 있으며, 내부에서 `is_auto_ati_done_single_read()`를 그대로 호출한다. `is_auto_ati_done_single_read()`가 `static`이지만 이 공개 래퍼를 통해 외부 호출이 가능하다.

**59 종합의 오류**:
1. "`is_auto_ati_done_single_read()`는 static 부팅 전용 함수다. '다음 폴링에서 ATI_Active 확인'은 현재 구현 불가 설계다"(§2-6)라고 기술했으나 공개 래퍼(`tdc_drv_iqs323_is_auto_ati_done()`)가 존재해 외부 접근이 이미 가능하다.
2. 블로킹_H는 **코드 확인 없이 발굴된 거짓 블로킹**이다. 이미 해소된 상태로, Phase 3(R3_CHARGING) 착수 전 블로킹 목록에서 제거해야 한다.

**단, 주의사항**:
- `tdc_drv_iqs323_is_auto_ati_done()`이 반환하는 것은 `ati_event`(ATI 완료 이벤트) 비트이지 `ati_active`(ATI 진행 중) 비트가 아니다 [확정 필요: 데이터시트 §5.9 ati_event vs ati_active 의미 구분]. "ATI 진행 중" 판별과 "ATI 완료" 판별은 다를 수 있다.
- 기존 `is_auto_ati_done_single_read()` 로직이 ATI_Active 비트를 확인하는지 ATI_Event 비트를 확인하는지 코드 내용 추가 확인 필요 [확정 필요].

**판정**: [치명] — 블로킹_H는 이미 존재하는 API(`tdc_drv_iqs323_is_auto_ati_done()`)를 간과한 거짓 블로킹이다. 제거하되, ati_event vs ati_active 구분이 R3_CHARGING 설계에 충분한지 [확정 필요]로 대체 등록해야 한다.

## 3. 치명 — re_ati_trigger() 내 MSB=0x00 write가 CH_TIMEOUT 비활성(0x07)을 덮어쓰는 연쇄 — 코드 확인 가능한데 미분석

### 3-1. 59 종합의 처리 (§2-8, 확인_13)

> "re_ati_trigger() MSB=0x00 write로 CH_TIMEOUT 비활성화(0x07) 덮어쓰기 여부 — 확인_13"

### 3-2. 공격 — 코드에서 직접 확인 가능

`iqs323.c:570~578` `re_ati_trigger()`를 읽으면:

```c
reg.bytes[1] = 0x00;
reg.bytes[2] = 0x00;
reg.elements.lsb.re_ati = TDC_DRV_IQS323_TRIGGER_RE_ATI;
return write_register(reg.bytes[0], reg.bytes[1], reg.bytes[2]);
```

SYSTEM_CONTROL 레지스터에 `(LSB=re_ati_bit, MSB=0x00)`를 write한다. 그런데 `iqs323.c:1155`에서:

```c
write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x00, 0x07)
```

으로 CH_TIMEOUT을 비활성화할 때 MSB=0x07을 write했다. `re_ati_trigger()`가 SYSTEM_CONTROL에 MSB=0x00으로 write하면 **CH_TIMEOUT 비활성화(MSB 0x07)가 0x00으로 클리어된다** — CH_TIMEOUT이 다시 활성화될 수 있다.

**확인 상태**: 이미 코드 두 라인(`re_ati_trigger():578`, `apply_settings:1155`)만 대조하면 확인 가능하다. 59 종합이 "분석 필요"로 미룬 것은 코드를 보지 않은 채 확인 항목으로 설정한 것이다.

**중요 함의**:
1. Phase 3에서 R3_CHARGING Re-ATI를 실행(`re_ati_trigger()` 호출)할 때마다 CH_TIMEOUT이 재활성화된다.
2. CH_TIMEOUT이 만료되면 Auto-ReATI가 트리거된다 — ATI Mode=Disabled 아키텍처에서는 Auto-ReATI가 의도치 않게 실행된다.
3. 현재 운용 코드에서 `apply_settings()` 내 `re_ati_trigger()`는 호출되지 않으므로 잠재 문제이지만, Phase 3 R3_CHARGING 구현 시 현실화된다.

**수정 방향**: `re_ati_trigger()` 내부에 CH_TIMEOUT 재비활성화 write(`MSB=0x07`)를 포함하거나, Phase 3에서 `re_ati_trigger()` 호출 후 명시적으로 `write_register(SYSTEM_CONTROL, 0x00, 0x07)` 재호출 필요.

**판정**: [치명] — 코드 두 라인 대조로 확인 가능한 부작용을 "확인_13"으로 미룬 것은 완전성 공백이다. Phase 3 구현 전 반드시 해소해야 하며, 59 종합 §4 Phase 3 계획에 수정 방향이 포함돼야 한다.

## 4. 치명 — 확인_14(R3_CHARGING 게이트 기준 정책)가 §4 Phase 3 계획에 반영 없음

### 4-1. 59 종합의 처리 (§6 확인_14)

> "R3_CHARGING 게이트 기준: 공장값 정적 vs 마지막 Re-ATI 후 counts 동적 업데이트 정책 결정 — Phase 3 착수 전"

### 4-2. 공격

58_대안비교(공격_5)가 발굴하고 59 종합이 확인_14로 등록했으나, §4 Phase 3 계획 본문에는 이 정책 결정이 일절 포함되지 않았다. §4 Phase 3는 다음을 기술한다:

> "① re_ati_trigger() 발행 → s_ati_in_progress=true (신규 플래그)
> ② 폴링 중 s_ati_in_progress=true이면 터치 판정 결과 NOT_TOUCH 강제
> ③ tdc_drv_iqs323_is_ati_active() 확인 → false이면 ..."

R3_CHARGING 게이트 비교 시 어떤 기준값을 사용하는지가 §4 Phase 3 계획에 전혀 없다. "30초 주기 도달 시 현재 counts로 게이트 통과 확인"이라는 문구가 있지만 "무엇과 비교하는가"가 없다.

**완전성 공백**: 공장값(FACTORY_NOTOUCH_COUNTS)을 게이트 기준으로 사용하면, Re-ATI가 MULT/COMP를 갱신한 이후 정상 noTouch counts가 다른 절대값을 갖게 되어 게이트가 영구 실패한다. 이 점이 58_대안비교(공격_5)의 핵심이었으나 59 종합이 확인_14로 등록만 하고 Phase 3 계획에 연결하지 않았다.

**구체 위험**: Phase 3 구현자가 §4를 보고 "현재 counts를 FACTORY_NOTOUCH_COUNTS와 비교"를 기본 선택할 경우, 첫 Re-ATI 이후 충전 중 Re-ATI 트리거가 영구 차단된다. 이는 "드리프트 보정 경로 완전 단절"로 Phase 3 전체를 무력화한다.

**판정**: [치명] — 확인_14를 등록하면서 Phase 3 계획 본문에 연결하지 않은 것은 구현자가 이 정책을 독자 결정해야 하는 위험을 방치한다. §4 Phase 3 착수 전 확인_14 해소를 명시적 게이트로 삽입해야 한다.

## 5. 치명 — 53_완전성이 발굴한 "All-or-Nothing 대안 기각 미명시"가 59 종합에서도 미해소

### 5-1. 59 종합의 처리

53_완전성(§4)이 발굴한 "공장 캘리브 전제로 인한 All-or-Nothing 구조, 런타임 추정 기준값 대안 명시적 기각 없음"을 59 종합이 어느 항목에도 명시적으로 처리하지 않았다. 53_완전성의 판정은 [고위험]이었으나, 59 종합 §9 수렴 확정 항목에도, 잔존 미해소 핵심에도 이 항목이 없다.

### 5-2. 공격

59 종합 §5 블로킹 목록을 전체 검토하면 블로킹_C(CFX 파서 크기 확인)가 Phase 2 착수 전 필수이며, 블로킹_C가 지연되면 Phase 1도 All-or-Nothing 구조에 의해 영향받는다. 그러나 59 종합 어디에도 "블로킹_C 지연 시 Phase 1을 부분 운용할 중간 경로"가 없다.

**누락 확인**: 59 종합 §9 잔존 미해소 핵심 표에 블로킹_C는 있지만 "블로킹_C 미해소 시 Phase 1 착수 여부"에 대한 조건분기가 없다. 53_완전성이 제시한 "런타임 추정 기준값 대안"(공장 캘리브 없이 통계적 기준값으로 임시 운용)이 채택도 기각도 되지 않은 채 두 라운드를 통과했다.

이것은 완전성 공백이다. "공장 캘리브 완료 전까지 아무것도 개선하지 않는" 전략적 선택을 의도적으로 한 것인지, 대안을 검토하지 않아 그렇게 된 것인지가 59 종합 어디에도 명시되지 않았다.

**판정**: [치명] — All-or-Nothing 구조 채택·기각 결정이 3라운드를 통과하도록 방치됐다. §8 미해결 또는 §9 잔존 항목에 "공장 캘리브 미완료 시 Phase 1 운용 불가 = 의도적 선택"임을 명시하거나, 런타임 추정 기준값 대안을 명시 기각(이유 포함)해야 한다.

## 6. 고위험 — tdc_touch_config.h 실제 구조와 59 종합 빌드가드 세트 간 충돌

### 6-1. 59 종합의 처리 (§3 빌드가드 최종 세트 v2)

59 종합은 `tdc_touch_config.h`에 새로운 `#define`과 `#error` 세트를 추가하는 것으로 설계를 확정했다.

### 6-2. 공격

실제 `tdc_touch_config.h`를 읽으면 이미 정의된 `#define` 목록이 있다:

- `TDC_BOARD_VARIANT`(항목 1) · `TDC_DRV_IQS323_ATI_DUMP_ENABLE`(2) · `TDC_TOUCH_ATI_CALIB_MODE`(3) · `TDC_TOUCH_ATI_CALIB_LED_ENABLE`(3-1) · `TDC_TOUCH_SLEEP_MEASURE_MODE`(4) · `TDC_TOUCH_CRX1_VSS_ENABLE`(5) · `TDC_TOUCH_CRX1_REF_ENABLE`(6) · `TDC_TOUCH_CRX1_DUMMY_ENABLE`(6-1) · `TDC_TOUCH_CRX0_DISCHARGE_ENABLE`(7) · `TDC_TOUCH_CRX0_DISCHARGE_LOG`(8) · `TDC_TOUCH_MARGIN_LOG_ENABLE`(9) · `TDC_TOUCH_MARGIN_LOG_INTERVAL`(9-1) · `TDC_TOUCH_PROX_THRESHOLD_ENABLE`(10)

총 13개 define과 1개 기존 `#error`(CRX1 상호배타 가드)가 이미 존재한다.

**59 종합이 새로 추가하려는 define 세트**: `SATURATE_DETECT_ENABLE` · `SATURATE_MAX_COUNTS` · `NOTOUCH_GATE_ENABLE` · `FACTORY_NOTOUCH_COUNTS` · `NOTOUCH_MARGIN_STRICT` · `NOTOUCH_MARGIN_UP` · `FACTORY_CALIB_ENABLE` · `REATI_ON_NOTOUCH_ENABLE` · `ATI_FULL_ENABLE` · `CRADLE_REATI_ENABLE` · `TDC_TOUCH_RTT_TUNING`(신규 등록)

**완전성 공백**:
1. `TDC_TOUCH_RTT_TUNING`은 현재 `tdc_drv_iqs323.c:15`에서 `#if TDC_TOUCH_RTT_TUNING`로 참조되지만 `tdc_touch_config.h`에는 없다. 59 종합이 `#error "NOTOUCH_GATE와 RTT_TUNING 동시 활성 불가"`를 추가하려면 `tdc_touch_config.h`에 `TDC_TOUCH_RTT_TUNING` define을 먼저 추가해야 한다 — 그렇지 않으면 `TDC_TOUCH_RTT_TUNING`이 정의되지 않은 환경에서 `#error` 비교식이 의미 없거나 항상 false다.

**판정**: [고위험] — `tdc_touch_config.h` 실제 구조와 59 종합 빌드가드 설계를 대조하지 않았다. `TDC_TOUCH_RTT_TUNING`의 `#error` 가드가 작동하려면 이 define의 `tdc_touch_config.h` 내 존재가 선행 조건이다 — 59 종합 §3 빌드가드 세트에 미기술.

## 7. 고위험 — 59 종합 §4 Phase -1 이미 현재 코드에 WDT 갱신이 없다는 주장 검증 필요

### 7-1. 59 종합의 처리 (§2-1)

### 7-2. 공격 — 실제 코드 확인

```c
static bool wait_re_ati_done(void)

        if (!read_register(...)) {
            Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
            continue;
        }
        ...
        Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
    }
    ...
}
```

루프 내 `SYS_WATCHDOG_REFRESH()` 호출이 없는 것은 **코드 확인으로 사실**이다. 이 부분은 59 종합이 정확히 기술했으므로 수렴 항목으로 유지.

`iqs323.c:860` 근방을 확인하지 않아 [확정 필요] — ATI_CALIB_MODE 경로에서 `wait_re_ati_done()`을 호출하는 라인 번호가 860인지 주변인지 확인이 필요하다.

**판정**: [고위험] — Wait_re_ati_done() WDT 미삽입 사실 자체는 수렴이지만, ATI_CALIB_MODE 경로 라인 번호와 `DEFAULT_DELAY_MS` 상수값이 [확정 필요]로 남아 ~2.3초 계산의 정확도가 미보장이다.

## 8. 고위험 — "비블로킹 ATI 중 I²C disabled" (DS §8.4) 가 §8 미해결에 등록됐지만 Phase 3 계획에 반영 없음

### 8-1. 59 종합의 처리 (§8 미해결)

> "비블로킹 Re-ATI 중 I2C disabled (DS §8.4) — ATI 진행 중 I²C 응답 보장 여부 미확인 — Phase 3 착수 전 DS §8.4 확인"

### 8-2. 공격

이 항목이 §8 미해결에는 등록됐으나 §5 블로킹 목록에 없다. §4 Phase 3 계획 본문의 R3_CHARGING 비블로킹 3단계 구조는 "ATI 진행 중 폴링에서 ATI_Active 확인"을 전제하는데, DS §8.4가 "ATI 중 I²C disabled"를 명시하면 ATI 진행 중 I²C read 자체가 불가능하다 — 블로킹 3단계 구조의 ②·③ 단계 전체가 무의미해진다.

이 미확인 전제가 §8 미해결로만 표기돼 블로킹_K(블로킹 목록) 수준으로 취급되지 않은 것은 완전성 공백이다. Phase 3 착수 전 블로킹으로 격상해야 한다.

**판정**: [고위험] — DS §8.4 ATI 중 I²C disabled 여부는 비블로킹 3단계 R3_CHARGING 구조의 실현 가능성을 결정하는 핵심 전제다. §5 블로킹 목록에 추가하고 Phase 3 착수 전 해소를 강제해야 한다.

## 9. 고위험 — 53_완전성 §8-1 발굴 "TDC_TOUCH_BOOT_WAIT_MS 미정의"가 59 종합에서 흡수됐는지 불명

## 10. 중간 — 사후 검증 counts 이탈 방향 정정이 59 종합 §4에서 재역전됐는지 불명

### 10-1. 56_할루시의 지적 (§3-1)

56_할루시(§3-1): 49 종합 §2-2의 "counts < lo = race 가능성"은 오설계 — self-cap에서 터치 = counts 감소 = counts < lo가 정상 터치다. RTT 경보는 counts > hi(상한 이탈) 방향에서만 발행해야 한다.

59 종합 §4 Phase 1이 이를 수정한 코드:

```
counts < lo (터치 중 = counts 감소 방향): 정상 터치 진행 중, RTT 경보 불필요
counts > hi (상한 이탈): 이상 상태, RTT 경보 발행
```

이것은 수렴된 것처럼 보이나, §4 Phase 1의 실제 `tdc_notouch_gate_check()` 코드 스니펫은 반환값만 있고 사후 검증 분기 로직이 없다. "사후 검증" 상세는 설명 텍스트로만 있고 코드 스니펫으로 명시되지 않았다.

**판정**: [중간] — 사후 검증 방향 정정(counts < lo = 정상 터치, counts > hi = 경보)이 텍스트로는 수렴됐으나 코드 스니펫에 반영되지 않아 구현자가 텍스트를 읽지 않으면 오구현할 수 있다. §4 Phase 1 gate_check() 코드 스니펫에 사후 검증 분기를 포함시켜야 한다.

## 15. 핵심 6줄

1. **[치명] CH_TIMEOUT 이중 차단 이유는 `iqs323.c:1152` 주석에 이미 명시** — "auto-reATI 트리거 경로 차단"이 목적이다. 확인_12는 즉시 해소되며, 재활성 검토 시점은 Phase 0·1이 아닌 **Phase 3(ATI Full 활성화) 시점**으로 재이관해야 한다.

2. **[치명] 블로킹_H는 거짓 블로킹** — `tdc_drv_iqs323_is_auto_ati_done()`이 `iqs323.c:926`에 공개 API로 이미 존재한다. ati_event vs ati_active 의미 구분은 [확정 필요]로 대체 등록하되, "API 미존재" 블로킹은 즉시 제거 가능하다.

3. **[치명] re_ati_trigger() MSB=0x00 write가 CH_TIMEOUT 비활성(0x07)을 덮어쓴다** — `re_ati_trigger():578`과 `apply_settings:1155` 두 라인 대조로 확인 가능하다. Phase 3 R3_CHARGING 구현 시 `re_ati_trigger()` 내부 또는 호출 후 CH_TIMEOUT 재비활성화 write가 필수이며, 이를 Phase 3 계획 본문에 추가해야 한다.

4. **[치명] 확인_14 R3_CHARGING 게이트 기준 정책이 §4 Phase 3 계획 본문에 없다** — Re-ATI 반복 후 noTouch counts 절대값이 달라지면 공장값 기준 게이트가 영구 실패해 드리프트 보정 경로가 차단된다. 이 정책 결정을 Phase 3 착수 전 블로킹으로 §4에 삽입해야 한다.

5. **[치명] All-or-Nothing 구조의 대안 기각이 3라운드 통과** — 공장 캘리브 미완료 시 Phase 1 착수 불가를 의도적으로 선택한 것인지, 런타임 추정 기준값 대안을 검토하지 않아 결과적으로 그렇게 된 것인지 §8 미해결 또는 §9에 명시해야 3라운드가 수렴한다.

6. **[고위험] `tdc_touch_config.h` 실제 구조 미대조** — `TDC_TOUCH_RTT_TUNING`이 `tdc_touch_config.h`에 존재하지 않아 59 종합 §3의 `#error "NOTOUCH_GATE와 RTT_TUNING 동시 활성 불가"` 가드가 작동하지 않는다. 빌드가드 세트를 파일에 추가하기 전 `TDC_TOUCH_RTT_TUNING`의 `tdc_touch_config.h` 정의를 선행해야 한다.
