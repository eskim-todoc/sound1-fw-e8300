## 2. 신규 약점 발굴 — 종합이 놓친 엣지

### 약점_1 — 충전 중 Re-ATI blocking race 처리가 종합에 구조적으로 미흡하다 [치명]

**종합 §2-1 Phase 3**: "Re-ATI 채택: write_ati_compensation() 이후 RESEED 대신 re_ati_trigger() + wait_re_ati_done()"로만 기술. 충전 중 runtime Re-ATI(`R3_CHARGING`)는 §4 달성도 표에서 "✅ (Phase 3 + Beta 실측 후)"로 처리.

**엣지 공격**: 25_검증_엣지의 결함_4(충전 중 Re-ATI 1초 blocking 중 터치 시작 race)가 종합 §5(핵심 쟁점)에 **블로킹 미지수나 확인 항목으로 수록되지 않았다**.

종합 §5-1(블로킹 미지수)에는 실측_A~F만 있고, "충전 중 Re-ATI blocking call 비블로킹 전환 또는 수행 중 터치 감시" 요구사항이 없다.

구체 시나리오:

```
df_Connected=true → 30초 주기 Re-ATI 트리거
→ re_ati_trigger() + wait_re_ati_done() 최대 1초 blocking
→ 0.5초 경과 시점 사용자 터치 시작
→ IQS323이 터치 중 ATI 수렴 시도 → ATI_Error 또는 게인 왜곡
→ ATI_Error 핸들러 → 재시도 → 여전히 터치 중 → 영구 폴백
```

이 경로는 부팅 게이트 race(판별~실행 μs~ms)보다 **확률이 100배 이상 높다** — 1초짜리 blocking이므로 인공와우 착용 사용자가 그 구간에 전극을 터치할 가능성이 통계적으로 무시 불가다.

종합 §4 달성도 표에서 "게이트 race → ✅ 충분히 낮은 확률 [추정]"으로 일괄 처리됐는데, **충전 중 1초 blocking race는 저확률 [추정] 근거가 성립하지 않는다**.

**요구 조치**: 블로킹_G 추가 — 충전 중 runtime Re-ATI를 비블로킹 구조로 전환(re_ati_trigger 발행 후 다음 폴링에서 ATI_Active 폴링)하거나, wait_re_ati_done() 내 매 100ms마다 counts를 샘플링해 터치 감지 즉시 Re-ATI 중단·폴백하는 인터럽트 가능 구조 명세를 Phase 3 계획에 추가.

### 약점_2 — Phase 3 자기치유 전제가 "LTA freeze 해제 방향"에 대해 붕괴 경로를 숨기고 있다 [치명]

**종합 §1-1 층위 3**: "사후 검증·자기치유는 현재 내장(Beta POR [확정 필요])"으로 처리.

**엣지 공격**: 종합은 "race로 터치 상태가 캡처돼도 손 떼면 LTA IIR 추적으로 복구"를 자기치유로 정의한다. 그런데 이 자기치유 경로에는 다음 전제가 숨어 있다:

**전제**: RESEED 후 LTA = 터치 counts (예: 400). 손 뗌 후 counts = 550 (noTouch). 이때 counts > LTA → delta = LTA - Counts = 400 - 550 = **-150 (음수)** → 터치 미인식.

이 상태에서 LTA IIR이 "빠른 방향(noTouch 복귀, Counts > LTA)"으로 동작해야 자기치유가 일어난다. IQS323 데이터시트 §5.6 Fast Filter Band: Counts가 LTA 대비 **노터치 방향**(Counts > LTA + FastBand)으로 벗어날 때 Beta Fast 적용.

**그러나** 현재 Beta POR이 0이라면(22번 결함_7·25번 결함_6이 확정 필요로 남긴 항목), LTA IIR이 동작하지 않아 자기치유 복구가 **수렴하지 않는다** — LTA가 터치 counts에 고착된 채 counts가 noTouch 값이 돼도 delta 음수이므로 터치 인식 없음·노터치 인식 없음의 **기이한 침묵 상태**가 발생한다.

종합 §1-1 층위 3에서 "자기치유는 현재 내장(Beta POR [확정 필요])"이라 했으나, 이 [확정 필요]가 "확정되지 않으면 자기치유가 동작하지 않을 뿐만 아니라 RESEED 오염 후 delta 역전(음수) 상태에서 복구 불가"라는 함의를 명시하지 않았다.

즉 **Beta POR=0 확정 시, 자기치유 다층 방어 중 가장 핵심 층위가 동작하지 않는다** — 게이트 race 자기 치유는 "확률 낮음 + 자기치유"의 두 겹인데, 두 번째 겹이 Beta 실측 전에는 미보장.

**요구 조치**: §4 달성도 표 "게이트 race → ✅ 충분히 낮은 확률 [추정]" 항목에 "단 Beta POR=0 시 자기치유 층 무효화 → race 치명도 격상" 주석 추가. 블로킹_D(Beta POR 실측)를 "Phase 3 착수 전"이 아닌 **"Phase 1 착수 전"**으로 격상해야 함 — 이 실측 없이는 게이트 race 치명도 평가 자체가 불가능하다.

### 약점_3 — Phase 2→3 순서 의존이 빌드가드 구조로 강제되지 않았다 [고위험]

**종합 §2-2 빌드가드 최종 세트**:

```c
#define TDC_TOUCH_NOTOUCH_GATE_ENABLE        0u  /* 실측_A + 실측_B 완료 후 1로 */
#define TDC_TOUCH_FACTORY_CALIB_ENABLE       0u  /* 공장 공정에서만 1로 */
#define TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE    0u  /* Phase 2 검증 후 1로 */
```

**엣지 공격**: 종합은 "#error 컴파일 타임 의존성" 가드를 두 쌍(REATI_ON_NOTOUCH + ATI_FULL, CRADLE_REATI + REATI_ON_NOTOUCH)에 대해서만 추가했다.

그런데 `REATI_ON_NOTOUCH_ENABLE=1` + `NOTOUCH_GATE_ENABLE=0` 조합이 **가능하다** — 즉 노터치 게이트 없이 Re-ATI가 활성화되는 경우. 이 상태는 Re-ATI를 터치/노터치 구분 없이 매 부팅마다 실행하는 것으로, 기존 auto-ATI의 부팅 터치 게인 왜곡 문제를 그대로 복원한다.

종합 §2-2의 컴파일 타임 #error 세트에 다음 가드가 누락됐다:

```c
#if TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE && !TDC_TOUCH_NOTOUCH_GATE_ENABLE
#error "REATI_ON_NOTOUCH_ENABLE requires NOTOUCH_GATE_ENABLE"
#endif
```

이 가드 없이 배포 시 Phase 3가 Phase 1 없이 활성화되어 **아키텍처 핵심 원리(노터치 게이트 후에만 Re-ATI)가 컴파일 수준에서 파괴**된다.

**코드 ground truth 확인**: 현재 `tdc_touch_config.h`에는 NOTOUCH_GATE, REATI 관련 빌드가드가 아직 없다(항목 3~9까지 다른 기능). 따라서 이 #error 가드는 신규 추가 시점에 반드시 포함돼야 한다.

**요구 조치**: 종합 §2-2 빌드가드 세트에 `REATI_ON_NOTOUCH + !NOTOUCH_GATE → #error` 가드 추가.

### 약점_4 — 종합 빌드가드 세트가 현재 tdc_touch_config.h의 CRX1_DUMMY 의존성을 완전히 무시했다 [고위험]

**종합 §7 구현 파일 변경 목록**: `tdc_touch_config.h`에 "빌드가드 6개 + 단일 FACTORY_NOTOUCH_COUNTS + 컴파일 타임 #error" 추가로 기술.

**엣지 공격**: 현재 `tdc_touch_config.h`에는 이미 기능성 빌드가드가 있고, 그 중 **7번 CRX0_DISCHARGE_ENABLE=1이 6-1번 CRX1_DUMMY_ENABLE=1을 전제**로 한다(코드 주석 명시: "[전제] 6-1과 반드시 함께 사용"). 그리고 현재 `TDC_TOUCH_CRX1_DUMMY_ENABLE=1`이 기본값으로 활성화돼 있다.

Phase 1 노터치 게이트가 구현되면, 부팅 시 counts 읽기 과정에서 `discharge_crx0()`이 이미 실행된 상태인지 확인이 필요하다. `apply_settings()` 내에서 counts를 읽을 때(`tdc_drv_iqs323_notouch_gate_reseed()` 내부) CH0이 일시 비활성(방전 직후 복원 중)이라면, 읽은 counts가 방전 효과로 낮아진 값일 수 있다.

그런데 종합은 `discharge_crx0()`이 `tdc_touch_process()` 내 매 200ms 폴링 말미에 호출되는 것과, `apply_settings()`가 부팅 시 폴링 루프 진입 전에만 실행된다는 사실로 인해 이 충돌이 **부팅 Phase 1에서는 없다**고 판단할 수 있다.

그러나 Phase 3 Runtime Re-ATI(충전 중 30초 주기) 시나리오에서는 `discharge_crx0()`과 Re-ATI counts 읽기가 **동일 폴링 루프에서 충돌 가능**하다(22번 결함_13 논거). 종합 §5-2 확인 항목에는 이 확인이 없다 — `discharge_crx0()` 순서 강제를 Phase 3 구현 게이트로 명시해야 한다.

더 나아가 CRX1_DUMMY가 꺼진 빌드(`TDC_TOUCH_CRX1_DUMMY_ENABLE=0`, `TDC_TOUCH_CRX0_DISCHARGE_ENABLE=1`)는 현재 코드에서 `#error`로 차단되지 않는다 — 빌드가드 불완전. 이 조합은 "CH0 유일 활성 채널 상태에서 방전"으로 measurement cycle 중단을 야기한다. Phase 신규 빌드가드 추가 시 기존 CRX0_DISCHARGE + CRX1_DUMMY 의존 가드와 충돌·중복 검사를 수행해야 한다.

**요구 조치**: 종합 §5-2 확인 항목에 "확인_7: Phase 3 Runtime Re-ATI counts 읽기와 discharge_crx0() 순서 강제 메커니즘" 추가. 종합 §7 변경 목록에 기존 tdc_touch_config.h 빌드가드와의 충돌 검사 명시.

### 약점_5 — noTouch 판별에서 "counts 방향" 관례를 종합이 혼용하고 있다 [고위험]

**종합 §3-2 tdc_notouch_gate_check() 코드**:

```c
uint32_t lo = FACTORY_NOTOUCH_COUNTS - MARGIN_STRICT;
uint32_t hi = FACTORY_NOTOUCH_COUNTS + MARGIN_UP;
return (counts >= lo && counts <= hi);
```

주석: "MARGIN_STRICT(하한): Threshold(100)의 40% = 40 제안 [추정]"

**엣지 공격**: self-cap 방식에서 **터치 = 정전용량 증가 = counts 감소**다(`개념정리_터치동작모델.md §2` 명시: "self-cap: 터치 = capacitance 증가 = counts↓"). 따라서 noTouch시 counts가 높고, 터치 시 counts가 낮다.

부분터치 방어를 위한 "하한 엄격화(MARGIN_STRICT)"는 **counts가 터치 방향(낮은 방향)으로 얼마나 벗어날 때 게이트를 거부할지**를 정한다. 즉 `lo = FACTORY_NOTOUCH_COUNTS - MARGIN_STRICT`가 맞다 — 터치는 counts를 낮추므로 lo를 엄격하게(높게) 설정하면 부분터치가 게이트를 통과하지 못한다.

그런데 종합 §3-2 주석: "noTouch 방향(counts 높음)은 여유있게, 터치 방향(counts 낮음)은 엄격하게"

이 설명은 맞지만, 코드에서 `lo = FACTORY_NOTOUCH_COUNTS - MARGIN_STRICT`는 **하한(낮은 쪽 경계)을 높여서 엄격**하게 만든다. 즉 MARGIN_STRICT가 클수록 lo가 높아져 게이트 통과 창이 좁아진다 — 이것이 의도다.

**실제 오류**: 종합 §2-1 Phase 1 `[!]` 기술 "MARGIN_STRICT(하한) < Threshold/2 설정 — 하한을 상한보다 엄격히"는 **MARGIN_STRICT 값(delta 크기)이 Threshold/2보다 작아야 한다**는 의미인데, 이 조건이 "통과 창이 엄격하다"는 방향과 반대다.

- MARGIN_STRICT 값이 작을수록 lo가 FACTORY_NOTOUCH_COUNTS에 가까워져 → 게이트 창이 좁아져 → 더 엄격
- 종합 §2-1 기술 "MARGIN_STRICT < Threshold/2"는 MARGIN_STRICT가 작아야 한다는 의미 → 엄격화 방향 일치

그러나 §3-2에 "40 제안 [추정]"에서 Threshold=100의 40%=40이 MARGIN_STRICT인데, "< Threshold/2 = 50"이므로 40 < 50 — 조건 만족. 이것은 수치상 맞다.

**진짜 엣지 약점**: MARGIN_STRICT=40으로 `lo = 500 - 40 = 460`인데, 부분터치로 counts가 460이라면 게이트 통과. 이때 delta = LTA(480, 예를 들어 이전 RESEED 후 약간 이동된 경우) - 460 = 20 → Threshold(100) 미만이므로 터치 인식 안 함. 즉 **게이트는 통과했지만 실제로 미세 부분터치 상태에서 RESEED 후 LTA=460으로 갱신되면, 이후 정상 터치 시 delta 폭이 좁아진다** — 감도 저하.

**더 핵심 오류**: 종합 §4 달성도 표 "부분 터치 모호성 → △ 확률적 완화만 가능"은 맞지만, 이것이 **감도 저하(false negative, 터치를 못 잡음)**로 이어지는 경로를 "미해결" 표(§6)에 기술하지 않았다. §6에는 "부분 터치 → 물리적 counts 중간값 — SW로 100% 구분 불가"만 있고, MARGIN_STRICT 게이트 통과 후 RESEED가 감도를 낮추는 경로가 별도 "미해결" 항목으로 없다.

**요구 조치**: §6(미해결) 표에 "MARGIN_STRICT 게이트 통과 부분터치 RESEED → 이후 터치 감도 저하(delta 폭 축소)" 항목 추가. 이것은 물리 한계가 아닌 SW 설계 선택의 결과이므로 "원리상 해소 불가"가 아닌 "설계 트레이드오프"로 분류해야 한다.

### 약점_6 — 공장 캘리브레이션 모드 게이트 bypass 빌드가드가 Phase 2 설계와 논리적으로 충돌한다 [중위험]

**종합 §2-1 Phase 2 `[!]`**: "공장캘리 모드에서 노터치 게이트 RESEED bypass 빌드가드 분리 (게이트 대기 최대 5초가 공장 저장 타이밍을 오염하는 결함_8@22 방지)"

**엣지 공격**: 공장 캘리브레이션 빌드(`TDC_TOUCH_FACTORY_CALIB_ENABLE=1`)와 노터치 게이트 빌드(`TDC_TOUCH_NOTOUCH_GATE_ENABLE=1`)가 동시에 활성화되면, bypass 로직이 작동해 공장 캘리브 시 게이트가 우회된다. 이것은 의도된 동작이다.

**그런데**: 공장 캘리브레이션의 전제는 "공장 치구에서 노터치 보장"이다. 이 전제가 맞다면 bypass 없이도 게이트는 항상 통과한다(counts가 이미 noTouch 범위 안). 즉 bypass의 실질 이득은 "게이트 대기 시간 단축"뿐이다.

**역방향 엣지**: 공장에서 치구 조립 불량으로 전극이 눌린 채로 캘리브레이션을 실행하면:
- `FACTORY_CALIB_ENABLE=1` → 게이트 bypass → 즉시 Auto-ATI 실행
- 터치 상태에서 Auto-ATI → 게인 왜곡된 MULT/COMP 저장
- 이 값이 EEPROM에 영구 저장 → 모든 부팅에서 왜곡된 Fixed 게인 사용

종합 §2-1 Phase 2 `[!]` "calib_store() 내부에 저장 전 noTouch Counts 정상 범위 확인 코드 필수"가 이것을 커버한다고 볼 수 있지만, **이 확인은 counts 범위만 보고 Auto-ATI로 산출된 MULT/COMP 자체의 유효성을 검증하지 않는다**.

실제로 터치 상태 Auto-ATI 결과 MULT/COMP는 게인이 터치 정전용량 기준으로 왜곡된 값이다 — 이 값의 noTouch counts는 정상 범위일 수 있다(ATI가 "현재 정전용량=Target"으로 맞췄으므로). 따라서 calib_store() 내 noTouch Counts 범위 확인만으로는 터치 중 ATI 결과를 걸러내지 못한다.

**요구 조치**: 공장 캘리브레이션 시 Auto-ATI 완료 후 **counts가 ATI Target(예: 512) 근방**인지 확인하는 추가 검증 코드 필요. ATI Target은 설정 레지스터로 알 수 있다. 터치 상태면 ATI가 counts를 Target에 맞추더라도 터치 게인 기준이라 이후 노터치 시 counts가 Target보다 높아지므로, noTouch 환경에서 Auto-ATI → counts ≈ Target인지 확인으로 공장 치구 불량 감지 가능.

### 약점_7 — Phase 4 삽입점 main.c:742가 코드 사실과 다르다 [중위험]

실제 `func_cradle_lid_closed_loop()` **호출 위치**를 확인하면: 종합이 말하는 "main.c:742 앞, led_force_fade_off() 직후"는 22_검증_회귀.md §결함_9에서 언급한 "main.c:740~743" 영역이다.

**요구 조치**: Phase 4 착수 전 `main.c` 내 `func_cradle_lid_closed_loop()` 호출 위치를 grep 확정하는 확인_8 추가.

### 약점_8 — "ATI_Error 핸들러 + Re-ATI 쌍" 조건이 충전 중 Re-ATI와 이중 실행될 경우 재귀 위험이 있다 [중위험]

**종합 §2-1 Phase 3**: "ATI_Error 핸들러: (void) ati_error 제거 → pressed==false 시 re_ati_trigger() 발행 / pressed==true 시 s_ati_error_pending=true → 손뗌 후 재트리거"

**엣지 공격**: ATI_Error가 발생하는 두 경로가 있다:
1. 부팅 시 터치 중 Re-ATI → ATI_Error → 핸들러 발동
2. 충전 중 30초 주기 Re-ATI(blocking) 중 터치 시작 → ATI_Error → 핸들러 발동

두 경로가 **동시에 active**일 수 있다: 충전 중 blocking Re-ATI 실행 중 → ATI_Error → wait_re_ati_done() 루프에서 ATI_Error 감지 → 핸들러 발동 → re_ati_trigger() 재발행 → wait_re_ati_done() 다시 호출(재귀).

`wait_re_ati_done()` 내부에서 ATI_Error를 감지하고 재시도(re_ati_trigger())를 하는 구조라면, 이것이 무한 루프를 형성할 수 있다. 종합은 ATI_Error 핸들러를 `tdc_touch_process()` 폴링 루프 레벨에서 처리하는 것으로 설계했는데, `wait_re_ati_done()` 내 ATI_Error 감지와 상위 핸들러의 재시도가 **어느 레이어에서 처리되는지 명시되지 않았다**.

특히 "pressed==true 시 s_ati_error_pending=true → 손뗌 후 재트리거"에서, 충전 중 blocking wait_re_ati_done() 안에서 pressed 상태를 어떻게 확인하는지 기술이 없다 — blocking call 내에서 pressed 상태를 읽으려면 추가 I2C read가 필요하며, 이는 blocking 시간 연장 및 WDT 위험을 다시 유발한다.

**요구 조치**: §5-2 확인 항목에 "확인_9: ATI_Error 핸들러가 wait_re_ati_done() 내부와 상위 폴링 루프 어느 레이어에서 처리되는지, 재귀 호출 경로 차단 구조" 추가.

## 4. 핵심 6줄

1. **충전 중 Re-ATI 1초 blocking race는 "저확률" 주장이 성립하지 않는다** — 부팅 게이트 race(μs)와 달리 충전 중 blocking은 1초이므로 사용자 터치 확률이 무시 불가 수준이며, 종합 §5 블로킹 미지수 목록과 §4 달성도 표에 비블로킹 전환 요구가 누락됐다(약점_1).
2. **Beta POR=0 시 자기치유 다층 방어의 핵심 층위가 동작하지 않는다** — 종합이 "Beta POR [확정 필요]"로만 표기했으나, 미확정 시 RESEED 오염 후 delta 역전 상태에서 복구 불가라는 함의를 명시하지 않아, 블로킹_D를 Phase 3 전이 아닌 Phase 1 착수 전으로 격상해야 한다(약점_2).
3. **REATI_ON_NOTOUCH + !NOTOUCH_GATE 조합의 #error 가드가 빌드가드 세트에 없다** — 이 조합은 게이트 없이 Re-ATI가 실행되는 아키텍처 원리 파괴 경로로, 컴파일 타임에 차단해야 한다(약점_3).
4. **Phase 3 Runtime Re-ATI에서 discharge_crx0()와 counts 읽기 순서 충돌이 종합 §5-2에 없다** — Phase 3 구현 착수 전 확인_7로 추가 필요하며, CRX1_DUMMY 의존성 전체가 종합 파일 변경 목록에서 누락됐다(약점_4).
5. **MARGIN_STRICT 게이트 통과 부분터치 후 RESEED → 감도 저하 경로가 §6 미해결 표에 없다** — "확률적 완화만 가능"으로 처리됐으나 이것은 물리 한계가 아닌 SW 설계 트레이드오프이며, 실측_A 후 MARGIN_STRICT 값이 이 트레이드오프에 직접 영향을 준다(약점_5).
6. **Phase 4 삽입점 main.c:742 라인 번호와 공장 캘리브 치구 불량 ATI Target 검증 누락이 각각 구현 오류·품질 위험이다** — 삽입점은 grep 재확인 필수(약점_7), ATI Target 비교 검증이 없으면 터치 상태 공장캘리 오저장이 EEPROM에 영구 남는다(약점_6).
