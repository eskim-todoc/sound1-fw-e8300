# 58 — 재검증 라운드2 (대안비교 페르소나)

**TL;DR**: 49_종합-재검증1을 대안비교 관점으로 공격한다. 재검증1이 흡수한 6건 치명 결함(ATI_SETUP 분기·EEPROM 로드 경로·사후 검증 역전·충전 Re-ATI 누락·MCLR POR 미검증·#error 쌍 누락)은 아키텍처 원리를 수정하지 않고 구현 세부만 패치했다. 대안비교 관점에서는 이 패치들이 더 나은 대안 없이 채택됐는지, 패치가 내부 모순 없이 정합하는지, 새로운 선택지가 생략됐는지를 공격한다. 신규 약점 7건 발굴.

---

## 0. 공격 방법론

49_종합-재검증1의 각 설계 결정을 **"대안 Y를 선택했으면 어떻게 달랐는가"** 관점에서 공격한다.

- 채택된 패치가 최소 비용·최소 복잡도 해법인가?
- 더 나은 대안이 검토 없이 생략됐는가?
- 재검증1이 수렴 확정으로 분류한 항목 중 재공격이 가능한 것은?
- 재검증1 치명 결함 패치들 사이의 상호 정합성이 파괴된 부분은?

## 1. 공격_1 — ATI_SETUP 분기 패치(§2-1)와 비블로킹 Re-ATI 설계(§2-4)의 내부 모순

### 49_종합-재검증1의 주장

§2-1(회귀_1 반영): `write_ati_compensation()` 내 ATI_SETUP write를 `TDC_TOUCH_ATI_FULL_ENABLE` 빌드가드로 분기한다 — Full 시 ATI Mode Full 레지스터값을 write, 아니면 Disabled(0x08)를 write.

§2-4(R3_CHARGING): 비블로킹 구조 선호. "re_ati_trigger() 발행 후 다음 폴링에서 ATI_Active 확인"을 선호한다고 기술한다.

### 공격

**두 결정이 서로 충돌하는 대안 미검토.**

비블로킹 Re-ATI(re_ati_trigger 후 다음 폴링에서 ATI_Active 확인)를 채택할 경우, ATI 수행 중에도 폴링 루프가 계속 돌면서 `write_ati_compensation()`이 호출될 가능성이 있다. 부팅 시 `tdc_drv_iqs323_apply_settings()`는 1회지만, 충전 중 30초 주기 Re-ATI를 `tdc_touch_process()` 내 타이머로 발행한다면 그 후속 폴링에서 `write_ati_compensation()` 재호출이 발생하는 경로가 있는지 49_종합이 검토하지 않았다.

- **`write_ati_compensation()`이 ATI Full 도중 재호출**되면: ATI_SETUP에 다시 Full을 write하는 것은 무해할 수 있지만 MULT/COMP에 고정값(공장 EEPROM값 또는 컴파일 타임 상수)을 덮어쓰게 된다 → ATI가 중간에 MULT/COMP를 리셋당하는 Race.

- **대안 미비교**: 비블로킹 Re-ATI 중 `write_ati_compensation()` 재진입을 "ATI_Active flag 확인 후 skip"하는 가드가 필요한가, 아니면 비블로킹 자체가 잘못된 선택인가? 블로킹 Re-ATI(wait_re_ati_done)이 이 재진입 문제를 구조적으로 차단하므로, 비블로킹보다 블로킹이 **`write_ati_compensation()` 재진입 race에 더 안전한 대안**이다 [추정]. 49_종합-재검증1은 블로킹 1초 race 창을 이유로 비블로킹을 선호했지만, 비블로킹의 재진입 race를 구조적 위험으로 다루지 않았다.

**판정**: ATI_SETUP 분기 패치와 비블로킹 Re-ATI 설계는 상호 정합성 검토 없이 각각 독립적으로 채택됐다. 두 결정의 교차 시나리오(비블로킹 ATI 중 apply_settings 재호출)를 명시적으로 처리하지 않으면 구현 단계에서 미검출 race가 발생한다. [확정 필요]

## 2. 공격_2 — EEPROM 로드 경로(§2-3)의 "우선 적용" 대 "공장 기준 불변성" 상충 미처리

### 49_종합-재검증1의 주장

§2-3(회귀_6 반영): 부팅 시 `tdc_drv_iqs323_apply_settings()` 내에서 EEPROM 유효 데이터가 있으면 `s_mult_lsb`/`s_comp_lsb`를 EEPROM 로드값으로 교체한 뒤 `write_ati_compensation()`을 실행한다.

§4 Phase 3: Re-ATI가 활성화되면 MULT/COMP가 그 시점 환경으로 갱신된다.

### 공격

**Phase 3 Re-ATI가 MULT/COMP를 갱신하면, Phase 4 크래들 Re-ATI가 그 결과를 EEPROM에 덮어쓰는 경로가 있다 — 이 경우 "공장 절대 기준 MULT/COMP"가 사라진다.**

48_재검증1_대안비교(공격_2)가 이미 "공장값-런타임 ATI 괴리"를 발굴했고, 49_종합-재검증1은 §9 수렴 확정 항목에서 이 문제를 명시적으로 처리했는지 확인이 필요하다.

49_종합-재검증1 §4 Phase 4 항목: "EEPROM write 완료 확인 후 뚜껑 열림 처리." — 이것은 원자성 문제를 다룬 것이고, "크래들 Re-ATI 결과가 공장 캘리브를 덮어쓰는 것이 올바른가" 여부에 대한 명시적 결정이 없다.

**대안 비교**:

| 대안 | EEPROM 저장 내용 | 부팅 적용 | 위험 |
|---|---|---|---|
| 대안_X: 공장값 전용 EEPROM (현 30_종합) | 공장 MULT/COMP 고정 저장 | 매 부팅 공장값 로드 | 런타임 Re-ATI가 환경 적응해도 다음 부팅에서 리셋 |
| 대안_Y: 크래들 Re-ATI 결과를 덮어쓰기 (49 Phase 4) | 최신 Re-ATI 결과 저장 | 매 부팅 최신값 로드 | 공장 절대 기준 소실 → 드리프트 누적 가능 |
| **대안_Z: 공장값 + 마지막 Re-ATI 결과를 별도 슬롯** | 두 값 분리 저장 | 마지막 값 우선, 공장값 fallback | 슬롯 2개 필요(CFX 파서 부담 가중) |

49_종합-재검증1은 이 세 대안을 비교하지 않고 Phase 4에서 암묵적으로 대안_Y를 채택했다(크래들 Re-ATI 결과를 EEPROM에 저장). 그러나 §2-3 EEPROM 로드 경로 설계는 이 값을 부팅 시 그대로 적용하므로, 공장 기준 절대성이 크래들 Re-ATI 이후 파괴된다.

**판정**: 49_종합-재검증1의 "공장 절대 기준 노터치 게이트" 아키텍처 원리가 Phase 4 크래들 Re-ATI+EEPROM 저장에 의해 장기적으로 파괴되는 경로가 미분석이다. 대안_Z(슬롯 분리)를 포함한 명시적 비교가 필요하다. [추정]

## 3. 공격_3 — 블로킹_G(MCLR POR) 해소 방법의 대안 불균형

### 49_종합-재검증1의 주장

§2-5(블로킹_G): "데이터시트 §3.4/§4.1 확인 + 필요시 MCLR 후 THRESHOLD read 실측"으로 해소.

### 공격

**데이터시트 확인이 우선이고 실측이 보조인 이 순서의 가정은, 데이터시트가 모호하거나 실측과 다른 경우를 처리하지 않는다.**

IQS323 데이터시트의 MCLR(핀 토글) 동작과 소프트웨어 RESET 명령의 차이에 대해 §4.1이 명확한 POR 레지스터 초기화 보장을 제공하는지는 현재 미확인이다. 만약 데이터시트가 "MCLR시 모든 레지스터 초기화"를 명시하더라도, **절전 진입 시 write된 threshold=255를 MCLR이 실제로 초기화하는지 실칩에서 다를 수 있다** — 이것이 "필요시 실측"의 의미다.

**대안 비교**:

- **대안_P: 데이터시트 확인으로 충분** — MCLR이 POR임을 DS §3.4가 명확히 보장하면 실측 불필요. 블로킹_G를 가장 빠르게 해소하는 경로.
- **대안_Q: MCLR 후 항상 전 레지스터 재write** — `write_ati_compensation()`가 이미 핵심 레지스터를 write하므로, THRESHOLD도 부팅 설정 write 루틴에 포함하는 방안. 이 경우 MCLR POR 여부와 무관하게 초기 상태가 보장되어 블로킹_G 자체가 소멸한다 [추정].

대안_Q는 49_종합이 전혀 검토하지 않았다. MCLR 후 THRESHOLD를 포함한 전 운용 레지스터를 apply_settings()에서 명시 write하는 방어적 설계가 블로킹_G를 실측 없이 해소하는 가장 견고한 대안이다. 이 대안의 비용은 `write_register()` 1~2회 추가로 아키텍처 변경 없음 [추정].

**판정**: 블로킹_G 해소를 "DS 확인 + 필요시 실측"으로만 접근한 것은, "부팅 시 THRESHOLD 명시 write"라는 단순하고 실측 불필요한 대안을 누락했다. 이 대안이 수용 가능한지 검토 없이 블로킹을 남긴 것이다.

## 4. 공격_4 — 사후 검증 "RTT 경보만 발행, LTA IIR 자기치유 위임"(§2-2)의 Beta POR 의존성 미분리

### 49_종합-재검증1의 주장

§2-2(사후 검증 재시도 제거): RESEED 완료 후 counts 이탈 시 "RTT 경보만 발행, LTA IIR 자기치유에 위임"이 올바른 설계. 재RESEED 없음.

§5 블로킹_D(격상): Beta POR 실측 전까지 자기치유 보장 불가 → Phase 1 착수 전 필수.

### 공격

**사후 검증 설계("LTA IIR 자기치유 위임")와 블로킹_D("Beta POR 확정 전 Phase 1 착수 불가") 사이의 논리적 연결이 처리되지 않았다.**

만약 블로킹_D 해소 결과 Beta POR=0이 확인된다면(자기치유 없음):

- 사후 검증 race 발생 → counts 이탈 → RTT 경보만 발행 → **자기치유 없음 → LTA 오염 지속**
- 이 경우 사후 검증 설계("자기치유 위임")는 무의미해진다
- 올바른 대안은 "Beta POR=0 확인 시 자기치유 위임 경로 폐기 → 대신 counts 이탈 시 노터치 대기 재개" 경로

49_종합-재검증1이 "사후 검증 재시도 제거 → RTT 경보만"을 수렴 확정 항목으로 분류했지만(§9), 이 수렴은 Beta POR ≠ 0(자기치유 동작) 전제 하에서만 유효하다. Beta POR=0 시의 사후 검증 대안 설계가 없다.

**대안 비교**:

| Beta POR 결과 | 현재 사후 검증 설계 | 필요한 대안 |
|---|---|---|
| Beta POR ≠ 0 (자기치유 동작) | RTT 경보 + LTA IIR 수렴 위임 → 유효 | 현재 설계 유지 |
| Beta POR = 0 (자기치유 없음) | RTT 경보 + 위임 → 무의미 | "이탈 시 noTouch 대기 재개" 또는 "RTT 경보 + 폴링 강제 억제(s_boot_touch_ignore 연장)" 대안 필요 |

**판정**: 49_종합이 "Beta POR=0 시 자기치유 없음"을 블로킹_D로 인식했으면서도 사후 검증 설계를 "Beta POR=0 시 어떻게 수정할지"에 대한 조건분기 없이 단일 경로로 확정한 것은 내부 모순이다. 블로킹_D 해소 후 사후 검증 설계를 revisit할 명시적 게이트가 없다 [추정].

## 5. 공격_5 — 충전 중 Re-ATI(R3_CHARGING) 비블로킹 설계(§2-4)와 노터치 게이트 공장 기준의 드리프트 충돌

### 49_종합-재검증1의 주장

§2-4 R3_CHARGING: "30초 주기 도달 시 현재 counts로 게이트 통과 확인 후 트리거", "비블로킹 선호".

Phase 1 노터치 게이트: `FACTORY_NOTOUCH_COUNTS`(공장 캘리브 기준)와 현재 counts를 비교해 노터치 판별.

### 공격

**R3_CHARGING의 노터치 게이트가 부팅 때의 노터치 게이트와 동일한 `FACTORY_NOTOUCH_COUNTS`를 사용해야 하는가?**

부팅 직후에는 공장 캘리브 기준과 현재 counts의 드리프트가 작아 게이트가 유효하다. 그러나 Re-ATI가 여러 번 수행된 이후(운용 수개월 경과)에는 MULT/COMP가 변경돼 counts 절대값 자체가 달라진다. 이 경우:

- `FACTORY_NOTOUCH_COUNTS`는 공장 시점의 counts 절대값
- 현재 Re-ATI 적용 후 noTouch counts는 다른 절대값(ATI Target ≈ 512 또는 공장 Target)

R3_CHARGING 노터치 게이트가 공장 기준을 그대로 사용하면, Re-ATI 이후 정상 noTouch 상태에서도 counts가 공장 기준 윈도우를 이탈해 게이트 통과 실패 → Re-ATI 트리거 불가 → 드리프트 보정 경로 단절.

**대안 미비교**: R3_CHARGING 노터치 게이트 기준을 공장값(정적) 대신 "마지막 Re-ATI 후 측정한 noTouch counts"(동적 업데이트)로 사용하는 대안. 이 대안은 EEPROM에 `last_notouch_counts`를 추가로 저장하는 비용이 있지만, Re-ATI가 반복될수록 게이트 기준이 현실을 추적한다는 이점이 있다 [추정].

49_종합-재검증1은 R3_CHARGING 게이트 기준을 명시하지 않았다. "현재 counts로 게이트 통과 확인"이라는 표현만 있고, 기준값이 무엇인지 기술이 없다.

**판정**: R3_CHARGING의 게이트 기준이 미기술 상태다. Re-ATI 반복 후 공장 기준 게이트가 무의미해지는 장기 드리프트 시나리오가 누락됐다. [확정 필요]

## 6. 공격_6 — stuck-touch(CH_TIMEOUT) 검토 누락의 미해결 유지

### 49_종합-재검증1의 주장

§8 미해결: "stuck-touch(CH_TIMEOUT) 처리 — CH_TIMEOUT 이중 차단 유지 이유 미명시"를 미해결로 분류.

### 공격

**재검증1이 이 항목을 미해결로만 분류하고 Phase 계획 어디에도 처리 경로를 삽입하지 않았다.**

48_재검증1_대안비교(공격_5)가 CH_TIMEOUT 재활성을 Phase 0~1에 추가할 것을 권고했지만, 49_종합-재검증1은 이것을 §8 미해결로만 이관하고 Phase 계획에서 누락시켰다.

이 결정의 대안 비교:

| 대안 | 구현 비용 | 효과 |
|---|---|---|
| 현재: CH_TIMEOUT 이중 차단 유지 | 0 | stuck-touch 자동 해제 없음, 노터치 게이트 실패 시 영구 무반응 가능 |
| CH_TIMEOUT Phase 0에 재활성(단순 타임아웃 설정) | `write_register` 1회 + define 1개 | stuck-touch 자동 해제, 노터치 게이트 race 치명도 감소 |
| CH_TIMEOUT Phase 1에서 노터치 게이트와 조합 | 위와 동일, 게이트 타이밍에 맞춤 | 게이트 실패 시 CH_TIMEOUT이 fallback 복구 역할 |

CH_TIMEOUT 재활성은 SW 복잡도가 가장 낮은 방어 수단 중 하나인데, 이것이 "이중 차단 유지 이유 미명시" 수준의 미해결로만 남아 있는 점은 대안 비교가 불충분함을 보여준다. 특히 Beta POR=0으로 자기치유가 없을 경우 CH_TIMEOUT이 유일한 stuck-touch 복구 경로가 될 수 있다.

**판정**: CH_TIMEOUT은 단순하고 비용이 낮은 stuck-touch 방어 수단으로, Phase 0(항상 ON)에 "분석 필요" 수준이 아닌 "즉시 재활성 검토" 수준으로 포함돼야 한다. Beta POR=0 확인 시 더욱 필수화된다.

## 7. 공격_7 — TDC_TOUCH_RTT_TUNING 분기와 공장 게이트 신뢰도 충돌 — 49_종합의 신규_TDC_RTT_TUNING 미해소

### 49_종합-재검증1의 주장

§9 잔존 미해결: "`TDC_TOUCH_RTT_TUNING` 분기와 공장값 게이트 신뢰도 충돌 — 고위험"으로 분류하고, 2차 재검증 공격 대상으로 명시했다.

### 공격

이 항목이 고위험으로 분류됐지만, 49_종합이 왜 고위험인지, 어떤 충돌이 발생하는지 상세를 기술하지 않았다. 이 점 자체가 "미검증 주장"이다.

**구체 공격**:

`TDC_TOUCH_ATI_CALIB_MODE` 빌드가드 블록에서 RTT 튜닝이 활성화되면 `calib_read_ati()`가 MULT/COMP를 읽어 시리얼로 출력한다. 이 모드는 공장 공정이 아닌 **필드 튜닝·개발 환경**에서 사용된다.

문제 시나리오:
1. 필드에서 RTT 튜닝(`ATI_CALIB_MODE=1`)으로 해당 보드의 MULT/COMP를 측정·기록
2. 이 값을 컴파일 타임 상수로 픽스하거나 EEPROM에 write
3. 이후 일반 사용(`ATI_CALIB_MODE=0`)으로 전환 시 `FACTORY_CALIB_ENABLE=1`로 저장된 공장값과 RTT 튜닝으로 결정된 값이 동기화됐는지 보장 없음

**대안 미비교**: RTT 튜닝 결과를 공장 캘리브레이션 EEPROM 경로에 직접 연결(`ATI_CALIB_MODE=1` 시 RTT로 출력하면서 동시에 FACTORY_CALIB_ENABLE 경로로 EEPROM write)하는 대안. 이 경우 두 경로가 하나로 통합돼 신뢰도 충돌이 소멸한다 [추정]. 이 통합 대안이 검토되지 않은 채 "고위험"으로만 표기됐다.

**판정**: "TDC_TOUCH_RTT_TUNING ↔ 공장값 신뢰도 충돌"의 구체적 충돌 경로와 대안 통합 가능성이 미기술 상태다. 고위험이라면 2차 재검증 공격 대상이 아니라 Phase 계획에 블로킹으로 삽입돼야 한다.

## 9. 3차 재검증에 대한 권고

1. **공격_1·4(높음 2건)**: 비블로킹 Re-ATI 재진입 race 시나리오와 Beta POR=0 시 사후 검증 대안 설계를 Phase 3 계획에 조건분기로 명시. 블로킹_D 해소 후 두 경로 중 하나를 선택하는 게이트 추가.
2. **공격_2(높음)**: 크래들 Re-ATI 결과 EEPROM 저장 전략을 "공장값 덮어쓰기 vs 슬롯 분리" 명시 비교 후 채택. Phase 4 설계에 저장 슬롯 정책 명시 추가.
3. **공격_5(중)**: R3_CHARGING 게이트 기준을 공장값(정적) vs 동적 업데이트(마지막 Re-ATI 후 noTouch counts) 중 명시적 선택 필요. Phase 3 착수 전 이 정책을 확정하지 않으면 Re-ATI 반복 후 드리프트 보정 경로 단절 위험.
4. **공격_6(중)**: CH_TIMEOUT 재활성을 Phase 0 또는 1 진입 전 독립 검토 항목으로 격상. Beta POR=0 확인 시 즉시 필수화.

## 10. 핵심 6줄

1. **비블로킹 Re-ATI ↔ write_ati_compensation() 재진입 Race(공격_1)**: 충전 중 30초 주기 비블로킹 Re-ATI 도중 다음 폴링에서 `write_ati_compensation()`이 MULT/COMP를 덮어쓰는 재진입 race가 미분석이다 — ATI_SETUP 분기 패치(§2-1)와 비블로킹 선호(§2-4)는 서로 정합성 검토가 없다.
2. **크래들 Re-ATI EEPROM 덮어쓰기로 공장 절대 기준 소실(공격_2)**: Phase 4에서 크래들 Re-ATI 결과를 EEPROM에 저장하면 공장 캘리브 기준이 런타임 적응값으로 교체된다 — "공장 절대 기준" 아키텍처 원리가 Phase 4 이후 장기적으로 파괴되는 경로가 미분석이다.
3. **사후 검증 "자기치유 위임"의 Beta POR 의존성(공격_4)**: Beta POR=0(자기치유 없음) 확인 시 "RTT 경보 + LTA IIR 자기치유 위임"이라는 사후 검증 설계가 무의미해진다 — 49_종합이 블로킹_D를 Phase 1 착수 전으로 격상하면서도 사후 검증 대안 경로를 Beta POR=0 시로 준비하지 않은 내부 모순이다.
4. **R3_CHARGING 게이트 기준 미기술(공격_5)**: 충전 중 Re-ATI 게이트가 공장값(정적)을 기준으로 사용하면 Re-ATI 반복 후 noTouch counts 절대값이 달라져 게이트가 영구 실패할 수 있다 — 게이트 기준의 정적·동적 정책 선택이 Phase 3 계획에 없다.
5. **블로킹_G 단순 대안 누락(공격_3)**: MCLR 후 THRESHOLD 잔존 우려를 "DS 확인 + 실측" 블로킹으로만 처리했으나, 부팅 시 THRESHOLD를 apply_settings()에서 명시 write하는 방어적 대안이 실측 없이 블로킹_G를 해소할 수 있다 — 이 대안이 미검토된 채 블로킹이 유지됐다.
6. **CH_TIMEOUT 재활성 미이관(공격_6)**: stuck-touch 방어를 위한 CH_TIMEOUT 재활성은 구현 비용이 `write_register` 1회 수준인 단순 대안이지만, Phase 계획 어디에도 포함되지 않고 "미해결 이관"으로만 처리됐다 — Beta POR=0 시 CH_TIMEOUT이 자기치유 대체 유일 경로가 될 수 있다는 점에서 대안 비교 누락의 심각성이 높다.
