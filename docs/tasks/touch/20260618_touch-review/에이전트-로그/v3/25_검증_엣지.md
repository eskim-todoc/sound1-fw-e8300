# 25 — 검증: 엣지케이스 공격 (v3 1차 계획 8종)

**TL;DR**: 11~18 계획 8종을 엣지케이스(부분터치·절전·충전·크래들 경계) 누락 관점에서 공격한 결과, 총 7개 결함 범주를 발굴했다. 치명 2건(부분터치 게이트 통과·절전 복귀 후 게이트 무의미화), 고위험 3건(충전 중 Re-ATI race·크래들 열림 WDT 직전 방전 누락·Beta POR 가정 오류로 자기치유 붕괴), 중위험 2건(3-샘플 안정성 레이어가 250ms 부분터치에 무력·공장 noTouch Counts 저장 타이밍 결함). 각 결함에 코드 근거 및 수정 방향을 제시한다.

---

## 0. 공격 방법론

본 노드는 **동의가 아닌 결함 발굴** 전용이다. 각 계획 노드가 전제하는 "행복한 경로(happy path)"에서 벗어난 시나리오를 체계적으로 주입해, 설계 논리가 깨지는 지점을 찾는다.

공격 축:
- **부분터치(partial touch)**: counts가 MARGIN 경계 근처에 있는 애매한 접촉
- **절전(sleep)**: WDT 리셋 재부팅이지만 절전 진입 RESEED가 오염을 남기는 경로
- **충전(charging)**: df_Connected 상태에서 절전 없이 터치가 계속되는 상황
- **크래들 경계(cradle boundary)**: 뚜껑 닫힘 직전/직후의 미세 타이밍 경계

## 1. 결함_1 — 부분터치가 레이어_1 윈도우를 통과한다 [치명]

**대상 노드**: 14_계획_노터치게이트코드, 11_계획_부팅시퀀스

### 1-1. 결함 기술

노터치 게이트는 `counts ∈ [FACTORY_NO_TOUCH ± MARGIN]` 조건을 통과 기준으로 쓴다(`14_노터치게이트코드.md §1`). MARGIN=80(임시값)이며, 이것은 터치 Threshold(100, `iqs323.h:132`)의 80%다.

**문제**: self-cap 방향에서 부분터치(손가락이 전극에 살짝 걸린 경우)는 counts를 Threshold 미만으로만 떨어뜨린다 — 즉 터치 판정(delta > 100)은 통과하지 못하면서, counts는 `[FACTORY_NO_TOUCH - 80, FACTORY_NO_TOUCH]` 구간, 예컨대 `FACTORY_NO_TOUCH - 60` 에 놓인다. 이 값은 윈도우 **안에** 있다.

게이트는 이 부분터치를 노터치로 판정해 RESEED를 허용한다. RESEED 후 LTA = 부분터치 counts. 이후 손이 완전히 떨어질 때 counts 상승 폭이 Threshold 미만 → **터치 미인식** 상태가 된다.

```
시나리오:
  FACTORY_NO_TOUCH_COUNTS = 500, MARGIN = 80
  부분터치 시 counts = 460 (윈도우 안: 420~580)
  → 게이트 통과 → RESEED → LTA = 460
  → 손 완전 해제 시 counts = 510 (noTouch)
  → delta = LTA - Counts = 460 - 510 = -50 < 0 → 터치 미인식
```

코드 근거: `14_노터치게이트코드.md §2-2` `is_no_touch_window()` — `counts ∈ [lo, hi]`만 확인, delta 방향을 검증하지 않는다.

### 1-2. 왜 계획이 이를 놓쳤는가

14_계획 §7 미확정 항목에 `FACTORY_NO_TOUCH_MARGIN`만 언급하고, **MARGIN이 Threshold보다 작을 것이라는 암묵 가정**을 전제한다. 그러나 `브레인스토밍_부팅터치모호성.md §1`에서 은수님이 직접 짚은 "살짝 옆으로 밀린 애매한 터치"가 이 시나리오 그 자체다. 설계 문서가 브레인스토밍의 핵심 경고를 흡수하지 않았다.

### 1-3. 수정 방향

레이어_1 윈도우에 **단방향 하한 방어** 추가:

```c
/* 현재: counts ∈ [factory-MARGIN, factory+MARGIN] */
/* 수정: counts ∈ [factory-MARGIN_STRICT, factory+MARGIN] */
/* MARGIN_STRICT = Threshold × 0.5 이하로 설정 */
#define TDC_TOUCH_NO_TOUCH_MARGIN_STRICT   40u  /* Threshold 100의 40% */
```

또는 레이어_2에서 `counts가 감소 추세인가`(n샘플 동안 계속 내려가면 부분터치 의심)를 추가 확인한다.

## 2. 결함_2 — 절전 진입 RESEED가 게이트 우회 경로를 만든다 [치명]

**대상 노드**: 11_계획_부팅시퀀스, 18_계획_통합아키텍처

### 2-1. 결함 기술

`11_부팅시퀀스.md §5`는 "절전 복귀=WDT 리셋 재부팅이므로 위 시퀀스 하나로 두 경우 모두 처리"라고 선언한다. 그러나 이 추론에는 **절전 진입 시 RESEED의 LTA 오염이 부팅 후 게이트에 영향 없다는 암묵 가정**이 있다.

**실제 문제**: 절전 진입 직전에 RESEED가 발행된다(`main.c:952` → `tdc_drv_iqs323_reseed()`, `iqs323.c:955~957`). 만약 롱터치(2400ms, `systemControl.c:162`)로 절전에 진입하면:

1. 사용자가 손을 떼지 않은 채 절전 진입 → `iqs323.c:931~948` 절전 RESEED = LTA ← 터치 counts
2. 이후 WDT 리셋 재부팅 발생
3. 부팅 시 MCLR → Auto-ATI (이 시점 손이 없으면 noTouch counts 생성)
4. **게이트는 현재 counts(noTouch) 기준으로 판별 → 통과**
5. RESEED → LTA = noTouch counts ← **이 경로는 정상이다**

그런데 **다른 절전 종료 경로**가 있다: 절전 중 WDT 정기 리셋 재부팅은 **사용자가 여전히 손을 얹고 있을 때도 발생**할 수 있다. 절전 복귀 = WDT 리셋이라 했는데(`시스템 전제`), WDT 주기 내에 사용자가 다시 터치를 유지하며 부팅되는 경우다.

```
절전 진입(롱터치로 진입 → 손 유지 중) → ULP 모드
WDT 리셋 복귀 → 부팅 시 손 여전히 있음
→ Auto-ATI 오염(터치 상태) → iqs323.c:312~331 TIMEOUT
→ 11번 계획 §2: "TIMEOUT → 고정값 폴백 경로"
→ RESEED 보류 → counts 회복 대기 루프
```

이 부분은 계획이 **커버하고 있다**. 그러나 `iqs323.c:931~948`에서 설정하는 **절전 전용 감도(SLEEP_TOUCH_THRESHOLD, SLEEP_PROX_THRESHOLD)**가 재부팅 후 MCLR로 초기화되는지가 명시되지 않았다.

실제 결함: 절전 파라미터는 레지스터에 write됐는데, MCLR이 실제로 모든 레지스터를 POR로 복구하는지 `[확정 필요]`. 만약 MCLR이 SoftReset(일부 레지스터 보존)이라면, 절전 감도 파라미터가 부팅 후 게이트 counts 해석을 오염시킨다.

코드 근거: `initialize.c:449` `mclr_reset()` 호출. IQS323 데이터시트에서 MCLR이 완전 POR임을 확인하지 않은 채 "이전 LTA 완전 리셋"이라고 단정(`00_오케스트레이터-입력-v3.md §1 전제2`).

### 2-2. 수정 방향

MCLR 후 IQS323 레지스터 상태 완전 초기화를 데이터시트로 확정하는 **실측_MCLR**을 Phase 1 선행 조건으로 추가해야 한다. 확정 전까지는 "절전 파라미터가 부팅 초기에 잔존한다"는 보수 가정 하에 `apply_settings()` 초반에 모든 레지스터를 명시적으로 기본값으로 write하는 방어 코드가 필요하다.

## 3. 결함_3 — 3-샘플 레이어_2가 250ms 부분터치에 완전히 무력하다 [고위험]

**대상 노드**: 14_계획_노터치게이트코드

### 3-1. 결함 기술

레이어_2 안정성 확인은 "연속 N=3샘플이 모두 윈도우 안에 있어야 게이트 통과"로 설계됐다(`14_노터치게이트코드.md §1` `TDC_TOUCH_NO_TOUCH_STABLE_SAMPLES=3`). 폴링 간격 50ms 기준으로 3샘플 = **150ms** 안정 유지 시 통과.

그러나 브레인스토밍에서 정의한 "부분터치(손이 전극에 살짝 걸린 채 부팅)"는 **수백 ms~수 초 지속**되는 준정적 상태다. 부분터치 counts가 윈도우 안에 있으면(결함_1), 3샘플 안정성 확인도 그대로 통과한다. 분산 체크(`레이어_3: 손뗌 급증 없음`)도 정적 부분터치에서는 분산이 작아 통과한다.

레이어_2는 **동적 터치(누르다 놓는 순간)**만 차단하지, 정적 부분터치를 차단하지 못한다.

### 3-2. 수정 방향

결함_1(윈도우 하한 강화)이 이 문제의 근본 해결책이다. 레이어_2를 보완으로만 보고, 단독 방어로 의존하지 말아야 한다. 18_통합아키텍처의 레이어_2 설명에 "동적 변화 감지 목적, 정적 부분터치는 레이어_1(윈도우)로 차단"이라는 명확한 목적 분리가 필요하다.

## 4. 결함_4 — 충전 중 Re-ATI에 노터치 게이트가 적용되지 않는다 [고위험]

**대상 노드**: 18_계획_통합아키텍처

### 4-1. 결함 기술

`18_통합아키텍처.md §2-2 런타임 상태머신`의 `R3_CHARGING` 상태는 "충전 중 주기 Re-ATI, 30초 주기, **노터치 게이트 통과 후만**"이라고 명시한다. 그런데 이 "노터치 게이트 통과"가 어떤 메커니즘으로 보장되는지 구현 레벨에서 정의되지 않았다.

충전 중(`df_Connected`) 절전 진입이 없으므로 터치 폴링은 계속된다(`systemControl.c:162`). 이 상태에서:

1. 사용자가 30초 주기 중 어느 시점에 터치를 하고 있다
2. `R3_CHARGING` 트리거가 발동 — 노터치 게이트 확인
3. 200ms 폴링 루프 내 게이트 확인 시, **직전 폴링에서 noTouch, 게이트 확인 시점에 터치 시작** → counts가 윈도우 이탈 → 게이트 실패 → Re-ATI 안 함

이 부분은 보수적으로 처리되므로 **기능 관점에서는 무해**하다. 그러나 반대 방향의 race가 위험하다:

1. 노터치 게이트 통과(3샘플 150ms 안정)
2. Re-ATI 트리거 발행 (`re_ati_trigger()`)
3. **Re-ATI 수행 중(약 1.5초, `wait_re_ati_done()` 10×100ms)** 터치 시작
4. Re-ATI가 터치 상태에서 수렴 → ATI_Error 또는 게인 왜곡

이것은 `브레인스토밍_부팅터치모호성.md §3 방안C`에서 이미 경고된 "게이트 race" 문제다. 부팅 게이트에서는 race 시간이 수 ms~수십 ms지만, **충전 중 Re-ATI는 1.5초짜리 blocking call** 동안 race가 발생할 수 있다. 확률이 훨씬 높다.

코드 근거: `13_크래들훅.md §3-2` `wait_re_ati_done()`은 10×100ms=1초 상한. 충전 중 사용자가 1.5초 내에 터치를 시작할 확률은 "극히 낮음"이 아니다 — 충전 중 인공와우를 착용 중인 사용자가 언제든 전극에 닿을 수 있다.

### 4-2. 수정 방향

충전 중 주기 Re-ATI는 **비블로킹 방식**으로 전환하거나, Re-ATI 수행 기간(1.5초) 동안 counts를 주기적으로 샘플링해 터치 감지 시 즉시 Re-ATI를 중단하는 인터럽트 가능 구조가 필요하다. 또는 충전 중 Re-ATI를 Phase 4 이후로 미루고 크래들 race-free 경로만 신뢰하는 보수적 접근도 유효하다.

## 5. 결함_5 — 크래들 뚜껑 닫힘 직전 방전 순서가 뒤집혀도 된다는 전제가 잘못됐다 [고위험]

**대상 노드**: 13_계획_크래들훅, 17_계획_방전트랙

### 5-1. 결함 기술

`17_방전트랙.md §5-2`는 크래들 훅 삽입 시 "방전 먼저, 이후 Re-ATI/RESEED" 순서를 권고한다. 그 이유로 "방전이 counts를 정상화한 뒤 Re-ATI를 실행해야 정확한 게인 보정이 가능하다"고 설명한다. 이는 타당하다.

그러나 `13_크래들훅.md §2-2`에서 Phase 1 RESEED 훅의 구현 방안으로 제시한 `tdc_drv_iqs323_reseed_normal()` 코드는 **방전 없이 즉시 RESEED**를 발행한다:

```c
bool tdc_drv_iqs323_reseed_normal(void)
{
    write_register(0xC0, 0x08, 0x00);  /* RESEED 즉시 — 방전 선행 없음 */
    ...
}
```

`main.c:742` 삽입 순서 계획(`17_방전트랙.md §5-2`)에서 방전이 먼저라고 하지만, **`13_크래들훅.md`의 코드와 `17_방전트랙.md`의 삽입 의사코드가 상호 참조하지 않는다**. 구현자가 13번 계획만 보고 작업하면 방전 없이 RESEED부터 삽입한다.

더 중요한 문제: 크래들 뚜껑 닫힘 직전에 ESD 전하가 누적된 상태라면, 방전 없이 RESEED 시 LTA가 ESD로 낮아진 counts(= 부분터치와 구분 불가)로 오염된다. 이 상태에서 뚜껑 열림 → WDT 리셋 재부팅 → 부팅 게이트 판별 시 ESD 오염 LTA가 남아 있지는 않지만(MCLR로 리셋), 크래들 Phase 1 목표인 "뚜껑 닫힘 구간 중 LTA 정상화"가 달성되지 않는다.

### 5-2. 수정 방향

`tdc_drv_iqs323_reseed_normal()` 내부에 또는 `main.c:742` 삽입 코드에 **반드시 방전 선행을 명시적으로 문서화**해야 한다. 구현 체크리스트에 "방전(discharge_crx0) → RESEED 순서 필수" 항목 추가가 필요하다.

## 6. 결함_6 — Beta POR default 0 가정이 틀릴 경우 자기치유 설계 전체가 붕괴된다 [고위험]

**대상 노드**: 15_계획_드리프트LTA, 16_계획_사후검증

### 6-1. 결함 기술

`15_드리프트LTA.md §0`은 "BETA write 0건 → POR default 0x0000 → LTA IIR 갱신 없음"을 분석의 핵심 전제로 사용한다(`분석.md §핵심 발견 #6` 인용). 같은 문서 §0 마지막에 "[확정 필요: 데이터시트 POR table 또는 MCLR 후 0xB0 read 실측]"로 표기했지만, **이 확정이 없으면 자기치유 설계 전체가 다른 방향으로 작동한다**.

IQS323 데이터시트가 Beta POR default를 0이 아닌 **비제로 값**으로 명시하고 있다면:

- 현재 펌웨어에서도 LTA IIR이 이미 동작 중
- Beta 값이 크면(예: 8~12) LTA가 터치값을 학습해 threshold를 소진 중 — 즉 현재 "작동한다"고 알려진 터치가 실제로는 Beta 큰 LTA 학습으로 서서히 감도가 떨어지는 중
- `16_사후검증.md §3 자기치유 추가 구현 불필요` 판정이 틀림 — 이미 자기치유가 반대 방향으로 작동 중

반대로, Beta POR default = 0이라면:
- `16_계획 §3.1` "현재 Beta=0 → LTA freeze 해제 후에도 LTA가 추적하지 않음 → 자기치유 동작 불가"가 사실
- Beta 설정(Phase 2)이 필수

**어느 쪽이든 확정 없이 두 계획 노드가 상이한 베타 가정으로 작성된 것이 문제**다.

### 6-2. 수정 방향

**실측_BETA를 Phase 0 또는 Phase 1 착수 전 선행 필수 조건으로 격상**해야 한다. 현재 Phase 2 이후로 미뤄진(`15_계획 §5 Phase 2`) 것은 부적절하다. Beta 값에 따라 현재 펌웨어의 실제 동작 방향이 달라지므로, 이 확정 없이는 Phase 1 설계 전제도 흔들린다.

## 7. 결함_7 — 공장 noTouch Counts 저장 타이밍에 apply_settings()가 개입해 MULT/COMP를 덮어쓴다 [중위험]

**대상 노드**: 12_계획_공장캘리저장

### 7-1. 결함 기술

`12_공장캘리저장.md §4-3`은 MULT/COMP 읽기 최적 타이밍을 다음과 같이 정의한다:

```
MCLR → Auto-ATI 완료 → [★ 여기서 MULT/COMP 읽기]
  → apply_settings() (고정값으로 덮어씀)
  → RESEED → [★ 50ms 후 noTouch Counts 읽기]
```

문제: `apply_settings()` 실행 후 noTouch Counts를 읽는다. `apply_settings()` 내부에는 `write_ati_compensation()`이 있어 **고정 MULT/COMP를 IC에 write**한다. 이 write로 IC의 counts가 고정 MULT/COMP 기준으로 재계산된다. 즉 **저장되는 noTouch Counts는 Auto-ATI가 산출한 MULT/COMP 기준이 아니라, 고정 MULT/COMP 기준의 counts**다.

Phase 2에서 EEPROM 공장값을 부팅 게이트 기준으로 사용할 때, 이 noTouch Counts와 현재 부팅 시 Auto-ATI 후 counts의 **MULT 기준이 다를 수 있다**:

- 공장 저장 시: 고정 MULT 기준 noTouch Counts = 500
- 부팅 게이트 시: Phase 1에서는 고정 MULT write 후 counts 읽기 → 동일 기준 → 문제 없음
- 부팅 게이트 시: Phase 3 이후 Auto-ATI 채택 경로 → Auto-ATI MULT 기준 counts 읽기 → 공장값과 기준 불일치 → 게이트 판별 오류

`11_부팅시퀀스.md §3-1`의 "채택 경로: ATI_SETUP(Mode=Disabled)만 write하고 MULT/COMP는 Auto-ATI 산출값 그대로 유지"는 Phase 3에서 counts 기준이 공장 저장값과 달라진다는 의미다.

### 7-2. 수정 방향

공장 저장 시 noTouch Counts를 두 벌로 저장할 필요가 있다:
1. 고정 MULT 기준 noTouch Counts (Phase 1~2 게이트용)
2. Auto-ATI MULT/COMP와 함께 저장되는 상대적 ATI Target 기준값 (Phase 3 게이트용)

또는 Phase 3 채택 경로에서는 공장 noTouch Counts와 비교하지 않고 ATI Target(레지스터 설정값)을 기준으로 삼는 별도 게이트 로직을 설계해야 한다. 현재 12번 계획은 이 분기를 인식하지 못했다.

## 9. 핵심 결론 (6줄)

1. **결함_1(치명)**: 부분터치는 MARGIN=80 윈도우를 통과한다 — `FACTORY_NO_TOUCH - 60` 값이 윈도우 안에 있어 RESEED 오염을 일으킨다. `is_no_touch_window()` 하한을 `MARGIN_STRICT ≤ Threshold × 0.4`로 강화해야 한다.
2. **결함_2(치명)**: MCLR이 완전 POR임을 데이터시트로 확정하지 않은 채 "절전 파라미터 완전 리셋"을 전제하고 있다 — 실측_MCLR을 Phase 1 착수 전 선행 필수 조건으로 격상해야 한다.
3. **결함_6(고위험)**: Beta POR default가 0인지 확정되지 않았는데 자기치유 설계 전체가 이 값에 의존한다 — 실측_BETA를 Phase 0으로 당겨야 하며, 비제로 Beta POR 시 현 펌웨어 동작 재분석이 필요하다.
4. **결함_4(고위험)**: 충전 중 주기 Re-ATI는 1.5초 blocking call 동안 터치 시작 race가 부팅 게이트보다 훨씬 높다 — 비블로킹 또는 수행 중 터치 감시 인터럽트 구조가 필요하다.
5. **결함_5(고위험)**: 크래들 훅 13번과 방전 트랙 17번 간 "방전 선행 → RESEED" 순서 일치가 코드 레벨에서 강제되지 않는다 — 단일 함수 `tdc_drv_iqs323_cradle_discharge_and_reseed()` 로 통합 캡슐화가 필요하다.
6. **결함_7(중위험)**: 공장 noTouch Counts는 고정 MULT 기준으로 저장되지만 Phase 3 Auto-ATI 채택 경로는 다른 MULT 기준 counts를 게이트에 사용한다 — Phase 3 게이트는 별도 ATI Target 기준 로직이 필요하다.
