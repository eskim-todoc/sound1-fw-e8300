# 46 — 재검증 라운드1: 할루시 페르소나 공격 (30_종합-1차 대상)

**TL;DR**: 30_종합-1차를 할루시네이션·미검증 주장 관점에서 공격한 결과, 6개 신규 약점을 발굴했다. 가장 치명적인 것은 ① 사후 검증 목적 오정의(race 방향 역전) — 재시도 3회 논리가 실제 race를 방어하지 못하고 I2C 실패와 혼용되는 구조적 오류, ② 충전 중 주기 Re-ATI 트리거 코드 위치 누락 — 종합이 시스템 전제(충전기 연결=터치 계속)를 활용한다고 주장하면서도 구체 삽입 위치를 미기술한 채 "달성도 ✅"로 처리한 환각이다. 이전 검증8이 발굴한 결함들은 종합이 적절히 반영했으나, 위 2개와 4개 추가 약점은 새로 발굴된 것이다.

## 1. 신규 약점 목록

### 약점_1 — 사후 검증 목적 오정의: race 방향이 역전돼 있다 [관점_H, 치명]

**종합 주장**: §3-3에서 "사후 검증의 목적: RESEED 발행 전 노터치 판별~발행 사이 race 검출"이라 정의하고, "RESEED 직후 counts를 재읽어 윈도우 이탈 시 → 재시도 필요(LTA IIR이 다시 오염됐으므로)"라고 설명한다.

**공격**:
이 설명은 race의 방향을 역전시킨 환각이다.

실제 race 시나리오:
1. 노터치 판별 통과 → RESEED write 발행
2. RESEED write 완료 직후 → LTA = 현재 noTouch counts (정상 seed 완료)
3. 이 시점 이후 터치가 시작된다 → Counts가 내려간다 → delta = LTA - Counts > 0 → 터치 인식

이 경우 LTA는 올바른 noTouch counts로 초기화됐고, 터치도 정상 인식된다. **이것은 race가 아니다. 이것은 정상 동작이다.**

진짜 race는 반대 방향이다:
1. 노터치 판별 통과
2. RESEED write 발행 직전(판별 완료 ~ write 사이) 터치가 시작된다
3. write_register(RESEED) 실행 순간 Counts는 이미 낮은 터치값
4. LTA = 터치 counts로 오염

그런데 이 경우 RESEED write가 **완료된 이후** counts를 재읽으면: Counts는 여전히 낮은 터치값이고, LTA도 터치 counts로 seed됐으므로, delta = LTA - Counts ≈ 0 → **윈도우 이탈이 감지되지 않는다.** 터치 중에도 counts가 낮아 윈도우 하한에 걸릴 뿐이고, 이것이 "이탈 감지 = race 검출"이라면 검출하자마자 재RESEED를 하는 것이니 오염된 LTA를 다시 오염시키는 루프다.

**결론**: 사후 검증의 "윈도우 이탈 = race 검출" 논리는 성립하지 않는다. RESEED 완료 후 counts가 윈도우 밖이면 그건 race가 아니라 터치가 **현재 진행 중임을 의미하며**, 이 상태에서 재RESEED를 3회 하는 것은 오염을 3회 반복하는 것이다. 사후 검증 재시도 3회 논리 전체가 환각이다.

올바른 사후 검증 목적은 딱 하나: "RESEED 직후 counts가 윈도우 안이면 LTA seed가 올바른 시점임을 간접 확인." 재시도는 RESEED 재발행이 아니라 게이트 재진입(다시 노터치 판별부터)이어야 한다.

**영향**: §2-1 Phase 1 설계의 "재시도 max 3회" 및 §3-3 전체가 재설계 필요.

### 약점_2 — 충전 중 주기 Re-ATI: 시스템 전제 활용 주장 vs 구현 위치 완전 미기술 [관점_H, 치명]

**종합 주장**: §4 달성도 표에서 "환경 드리프트" 항목을 "Phase 3 Re-ATI + LTA IIR 런타임 추적 → ✅ (Phase 3 + Beta 실측 후)"로 달성도 확정 처리하고, 시스템 전제 "충전기 연결 시 절전 진입 안 함(터치 계속)"을 활용한다고 암묵적으로 함의한다.

**공격**:
종합 전체 어디에도 충전 중 주기 Re-ATI가 어느 함수에서, 어떤 타이머로, 어떤 코드 경로로 트리거되는지 기술되어 있지 않다.

- §2-1 Phase 계획 5단계에 충전 중 Re-ATI가 등장하지 않는다 (Phase 0~4 모두 없음).
- §7 구현 파일 변경 목록에도 없다.
- 검증8(22번 결함_10)이 "충전 중 주기 Re-ATI 구현 위치 미기술"을 이미 결함으로 발굴했고, 종합 §5-2 확인_6에 `s_auto_ati_timeout` 상태 전달 언급이 있지만 충전 Re-ATI 트리거 위치는 반영되지 않았다.

즉 종합이 달성도 ✅로 처리한 "환경 드리프트 해결"의 핵심 메커니즘(충전 중 주기 Re-ATI)이 **아키텍처 어디에도 코드 위치가 없다.** 이것은 달성도 체크가 근거 없는 환각이다.

**영향**: 달성도 표 "환경 드리프트 ✅"는 거짓이다. Phase 3에 충전 중 Re-ATI 구현 위치(tdc_touch_process 내 타이머, 또는 systemControl 이벤트 경로)를 명시하는 설계가 선행되어야 한다.

### 약점_3 — 자기치유 "내장(Beta POR [확정 필요])" 표기와 달성도 ✅ 간 논리 모순 [관점_U, 고위험]

**종합 주장**: §1-1 층위 구조 표에서 층위 3(사후 검증·자기치유)를 "자기치유는 현재 내장(Beta POR [확정 필요])."이라 표기한다. 동시에 §4 달성도에서 "게이트 race → 사후 검증·자기치유 다층 → ✅ 충분히 낮은 확률 [추정]"으로 달성도를 처리한다.

**공격**:
Beta POR default가 확정되지 않은 상태에서 자기치유가 "현재 내장"이라는 주장은 성립하지 않는다. 27번 검증_할루시(결함_5)는 Beta POR default가 코드 grep으로 확정 불가임을 이미 발굴했다. 22번 검증_회귀(결함_7)도 동일 지적을 했다.

그런데 종합은 이를 "[확정 필요]"로 표기하면서도 같은 문장에서 "현재 내장"이라 단정한다. 이 두 표현은 모순이다. 확정 필요한 항목을 "현재 내장"으로 쓰는 것은 미확인 주장이다.

더 나아가 Beta POR=0(LTA 완전 고착)이라면:
- 자기치유는 현재 동작하지 않는다
- race로 LTA가 오염되면 손을 떼도 LTA가 움직이지 않아 delta가 천천히 0으로 수렴하는 자기치유 자체가 없다
- "게이트 race 치명도 낮음"의 전제(자기치유로 일시 오류에 그침)가 붕괴된다

즉 Beta POR default가 0이라면 race는 "일시 오류"가 아니라 "장시간 영향"이 되며, 달성도 "✅ 충분히 낮은 확률"도 근거를 잃는다.

**영향**: 블로킹_D(Beta POR 실측) 완료 전까지 달성도 표의 "게이트 race" 항목을 "△ Beta POR 실측 전 미확정"으로 낮춰야 한다.

### 약점_4 — MARGIN_STRICT "Threshold의 40%" 제안이 단위 오용 환각 [관점_H, 고위험]

**종합 주장**: §3-2에서 "NOTOUCH_MARGIN_STRICT(하한): Threshold(100)의 40% = 40 제안 [추정 — 실측_A 후 조정]"이라고 기술한다.

**공격**:
이 수치 제안은 단위를 혼용한 환각이다.

- `NOTOUCH_MARGIN_STRICT`는 **absolute counts 허용폭** — noTouch counts의 lower bound를 정하는 값이다. (FACTORY_NOTOUCH_COUNTS - MARGIN_STRICT)가 하한이 된다.
- `TOUCH_THRESHOLD(100)`는 **delta 단위** — LTA와 Counts의 차이다.

즉 MARGIN_STRICT와 Threshold는 층위가 다르다. 종합 자체가 §5-3 설계 통일 요구사항에서 "MARGIN = 실측 기반(Threshold 80% 근거 무효 — 결함_2@23). 드리프트 실측 후만 설정 가능"이라고 명시해 놓았는데, 불과 같은 문서 §3-2에서 "Threshold(100)의 40% = 40"으로 MARGIN을 제안하고 있다. 이것은 종합 내부의 자기 모순이다.

Threshold=100(delta 단위)의 40%인 40을 counts 단위 MARGIN으로 쓰는 것은:
- MARGIN_STRICT=40이면 FACTORY_NOTOUCH_COUNTS=400일 때 하한=360
- 그런데 Threshold=100이면 delta=100이 되는 counts = 400-100 = 300
- 즉 counts=360은 MARGIN으로는 "노터치"로 허용하지만 Threshold로는 이미 터치(delta=400-360=40 < 100, 이 경우는 노터치지만)

계산이 맞다 해도 두 값의 근거 단위가 다르므로 제안이 논리적 근거를 갖지 못한다. "40" 숫자는 실측 없이 근거 없이 제안된 것이다.

**영향**: §3-2의 MARGIN_STRICT=40 제안을 삭제하고 "실측_A 완료 전 수치 제안 금지"로 대체해야 한다. 현재 형태로 남으면 구현자가 이 수치를 참고해 실측 없이 설정할 위험이 있다.

### 약점_5 — counts 포화 감지 stub "Phase 0, 항상 ON" + "블로킹_E Max Counts 실측 전 임계 미확정" 간 순서 역전 [관점_U, 중간]

**종합 주장**: §2-1 Phase 0에서 "TDC_TOUCH_SATURATE_DETECT_ENABLE=1 (항상 ON)"이라 규정하고, 빌드가드 기본값을 1로 설정한다. §5-1 블로킹_E에서 "Max Counts 실제값 → Phase 0 포화 감지 임계 확정"을 블로킹으로 명시한다.

**공격**:
포화 감지 stub을 "항상 ON, 기본값 1"로 출하하면서 동시에 임계값(Max Counts)이 미확정이면 이 stub은 **알 수 없는 임계에서 경보를 발생시키는 코드**다. Max Counts 실측 전에 stub이 항상 ON이라면, 임계값은 무엇인가? 종합은 이 초기값을 명시하지 않았다.

Phase 0 빌드가드 섹션에 `TDC_TOUCH_SATURATE_COUNTS` 같은 임계 define이 없다. 포화 감지 stub이 "~5줄 신설"이라고만 기술됐고, 그 임계가 하드코딩 추정값인지, 런타임 계산인지, 0으로 비활성인지 명시가 없다.

MAX_COUNTS가 데이터시트 기재값인지 아니면 실측이 필요한지도 종합은 명확히 하지 않았다 — §5-1에 "데이터시트 + RTT 실측"이라고 돼 있어 데이터시트 기재값만으로는 확정 불가임을 암시하면서도 Phase 0을 즉시 ON으로 처리했다.

**영향**: Phase 0을 "항상 ON"으로 규정하려면 임계값 define과 초기값(데이터시트 기준 추정값 + [확정 필요] 표기)을 빌드가드 섹션에 명시해야 한다. 없으면 stub은 dead code이거나 컴파일 오류 발생.

### 약점_6 — boot_touch_ignore와 노터치 게이트의 역할 중복·충돌 누락 [관점_N, 중간]

**종합 주장**: §7 구현 파일 변경 목록에서 `tdc_touch.c`의 변경 내용으로 "ATI_Error 핸들러(Phase 3), s_boot_5s_warned RESEED 재시도 보강"만 기술하고, `s_boot_touch_ignore`(tdc_touch.c:46)와 Phase 1 노터치 게이트의 관계를 언급하지 않는다.

**공격**:
현재 코드에는 이미 `s_boot_touch_ignore` 방어가 존재한다(분석.md §2 현재 동작 시퀀스). 이것은 "전이 시점 TOUCH면 플래그 set, 해제까지 폴링 억제"하는 사후 방어다.

Phase 1 노터치 게이트가 추가되면 두 방어가 동일 구간에 중복 동작한다:
- 노터치 게이트: 부팅 시 LTA seed를 노터치 확정 후에만 허용 (RESEED 시점 방어)
- boot_touch_ignore: READY 전이 후 터치 이벤트 억제 (폴링 결과 방어)

이 두 방어가 동시에 활성화될 때 "게이트 실패 → 폴백 RESEED 강행 → s_boot_touch_ignore가 폴링 억제"하는 경로에서 어느 방어가 우선하는지, 두 방어가 서로 보완인지 중복인지, 아니면 한쪽을 제거해야 하는지 종합이 다루지 않는다.

더 중요한 놓친 시나리오: 노터치 게이트가 통과해서 RESEED가 올바르게 완료됐는데도 s_boot_touch_ignore가 여전히 활성(직전 READY 전이 시 터치 이벤트가 있었다면)이라면, 올바른 LTA가 seed됐음에도 터치 이벤트가 억제되어 사용자가 터치해도 무반응 구간이 발생한다. 이 시나리오는 종합에서 언급되지 않았다.

**영향**: Phase 1 구현 설계에 `s_boot_touch_ignore`와 노터치 게이트 간 역할 분담 명시가 필요하다. 두 방어의 조합이 오히려 터치 무반응 구간을 만드는 엣지 케이스 시나리오를 다뤄야 한다.

## 4. 핵심 결론 6줄

1. **사후 검증 재시도 3회 논리 역전(약점_1)**: RESEED 완료 후 counts 재읽어 윈도우 이탈 시 재RESEED 3회는 오염된 상태를 반복하는 것이다 — 이탈은 현재 터치 중임을 의미하며 재RESEED는 오염 반복; 재시도가 아닌 게이트 재진입(노터치 대기)이 올바른 처리다.
2. **충전 중 Re-ATI 트리거 위치 미기술로 "환경 드리프트 ✅" 환각(약점_2)**: 시스템 전제 "충전기=절전 진입 안 함"을 활용한다고 전제하면서 어느 함수에서 어떤 타이머로 트리거하는지 종합 어디에도 없다 — 달성도 ✅는 근거 없는 환각.
3. **자기치유 "현재 내장"과 "Beta POR [확정 필요]" 모순 잔존(약점_3)**: Beta POR=0이면 자기치유 자체가 없어 race 치명도 낮음 전제가 붕괴 — 달성도 "게이트 race ✅"는 블로킹_D 실측 전 미확정이어야 한다.
4. **MARGIN_STRICT 단위 오용 자기 모순(약점_4)**: §5-3에서 "Threshold 80% 근거 무효" 결함_2@23을 인용해 놓고 §3-2에서 "Threshold(100)의 40%=40 제안"으로 동일 오류를 반복 — 수치 제안 자체를 삭제해야 한다.
5. **Phase 0 포화 감지 임계값 define 누락(약점_5)**: "항상 ON" + Max Counts 미확정 조합은 임계 없는 stub이므로 빌드가드에 임계 define과 데이터시트 기준 추정 초기값을 명시해야 컴파일 가능.
6. **s_boot_touch_ignore와 노터치 게이트 중복·충돌 시나리오 누락(약점_6)**: 게이트 통과 후 올바른 RESEED가 완료됐더라도 직전 READY 전이 시 터치가 있었다면 boot_touch_ignore로 정상 터치가 억제되는 무반응 구간 시나리오가 종합에서 완전히 다뤄지지 않았다.
