# 23 — adversarial 검증: 실측 없이 단정 결함 발굴

**TL;DR**: 1차 계획 8종(11~18)은 실측 전 추정값을 쓰면서 [확정 필요] 표기가 누락되거나, 단정 표현으로 전환한 지점이 다수 존재한다. 본 페르소나는 "이 값이 틀리면 어떻게 되는가"를 중심으로 7개 치명 결함과 4개 구조적 위험을 식별한다. 동의가 아닌 결함 발굴이 목적이다.

---

## 0. 검증 방법론

각 계획 문서를 다음 세 질문으로 공격한다:

1. **실측 없이 단정했는가?** — 추정값을 확정값처럼 사용하면서 [확정 필요] 없이 설계에 반영.
2. **[확정 필요] 표기가 있으나 그 결과가 '틀렸을 때' 어떤 퇴행이 발생하는지 분석했는가?**
3. **두 개 이상의 추정값이 결합됐을 때 오차가 어떻게 증폭되는가?**

## 1. 치명 결함 — 구현 불가·즉각 퇴행 유발

### 결함_1: FACTORY_NOTOUCH_COUNTS 임시값이 게이트를 무력화한다 (11·14·16·18 공통)

**공격 대상**: `11_계획_부팅시퀀스.md §3-3` → `TDC_TOUCH_FACTORY_NOTOUCH_COUNTS = 512U` [추정].  
`14_계획_노터치게이트코드.md §1` → `TDC_TOUCH_FACTORY_NO_TOUCH_COUNTS = 450u` [확정 필요].  
`18_계획_통합아키텍처.md §4-2` → `TDC_NOTOUCH_FACTORY_COUNTS = 400u` [추정].

**결함**: 세 계획 파일에 같은 개념(noTouch 절대 기준값)에 대해 512, 450, 400이라는 **서로 다른 임시값 3종**이 존재한다. 어느 값을 채택할지 기준이 없다. 더 심각한 것은, 이 값이 잘못됐을 때의 두 극단적 퇴행을 계획이 묵인한다는 점이다:

- `MARGIN=80` 기준, 실제 noTouch counts가 350이면 → 게이트 범위 [370~530 / 370~450 / 320~480] → 세 설정 중 일부는 통과, 일부는 폴백 — **코드 버전마다 다른 동작**.
- 실제 counts가 600이면 → 세 설정 모두 폴백 → **노터치 게이트가 항상 실패** → Phase 1 전체가 무의미한 5초 대기만 추가.

**[확정 필요] 누락 지점**: `11_계획_부팅시퀀스.md §3-3` 코드 블록 안에서 `512U`를 define 값으로 직접 삽입한 것은 [추정] 표기에도 불구하고 "코드에 쓰면 되는 값"처럼 보인다. Phase 1 활성화 조건으로 "RTT 실측 후 값 확정 → 플래그 활성화"를 언급하지만, 세 파일이 다른 추정값을 내면 어느 파일 기준으로 활성화할지 불명확하다.

**요구사항**: 세 파일 임시값을 단일 소스(`tdc_touch_config.h`)의 하나의 define으로 통합하고, 해당 define이 0(=게이트 비활성 safe default)이 되도록 보장해야 한다. `14_계획_노터치게이트코드.md`의 `#ifndef` 가드 구조가 이를 부분적으로 지원하지만, 0으로 설정 시 underflow(base=0, margin=80 → lo=0 [언더플로 방어], hi=80)로 정상 noTouch counts가 항상 게이트 실패가 된다. **0값 safe default 설계 자체가 결함이다** — 게이트 비활성 플래그(`TDC_TOUCH_BOOT_GATE_ENABLE=0`)와 기준값 0을 혼동하지 말아야 한다.

### 결함_2: NOTOUCH_MARGIN이 드리프트 실측 없이 설정돼 게이트 오판 범위를 결정한다 (11·14·15·16 공통)

**공격 대상**: `14_계획_노터치게이트코드.md §1` → `TDC_TOUCH_NO_TOUCH_MARGIN = 80u` [추정].  
`11_계획_부팅시퀀스.md §3-3` → `NOTOUCH_MARGIN = 80U` [추정].  
`16_계획_사후검증.md §1-2` → `FACTORY_NOTOUCH_MARGIN = 0u` [확정 필요].

**결함**: MARGIN을 80으로 설정하는 근거는 "TOUCH_THRESHOLD(100)의 80%"(`11_§3-3`)이다. 이 논리는 성립하지 않는다. TOUCH_THRESHOLD(100)는 LTA−Counts의 delta 판정값이고, NOTOUCH_MARGIN은 absolute counts 윈도우 허용폭이다. **두 값의 단위·층위가 다르다.** TOUCH_THRESHOLD의 80%를 noTouch 환경 드리프트 허용폭으로 사용하는 것은 근거 없는 비유다.

실제 문제: noTouch counts의 환경 드리프트 범위(온도 10°C 변화당 counts 변화)를 실측하지 않으면 MARGIN 80이 너무 좁은지(환경 변화마다 게이트 폴백) 너무 넓은지(약터치도 noTouch로 판정) 알 수 없다. `14_§7` "장기 드리프트 실측(온도·시간·보드 편차 분포)"을 MARGIN 확정 방법으로 언급하면서도 이 실측이 Phase 1 구현 전 선행 필수인지 Phase 1 이후 조정인지 명확하지 않다.

[추정] 표기가 있으나, `14_§5` 구현 변경 파일 요약에서 MARGIN 80을 그대로 반영한 상수를 추가 대상으로 열거한다. 이는 "실측 전 추정값으로 일단 구현하겠다"는 의미인데, MARGIN이 너무 좁으면 게이트가 항상 폴백되어 Phase 1 전체가 무의미해진다.

### 결함_3: LTA IIR Beta POR default가 0이라는 전제가 실측 없이 아키텍처 중심 논거로 사용된다 (15)

**공격 대상**: `15_계획_드리프트LTA.md §1.3` →  
> "POR default=0x0000이면 Beta=0 → alpha=0 → LTA_new = LTA_old (LTA 불변)."  
> "[확정 필요: 데이터시트 POR table 또는 MCLR 후 0xB0 read 실측]"

**결함**: [확정 필요] 표기가 있으나, 이 불확실성이 아키텍처 전체에 미치는 충격이 과소평가돼 있다.

만약 Beta POR default가 0이 아닌 경우(예: IQS323 데이터시트가 특정 비제로 default를 정의할 경우):

- 현재 펌웨어는 Beta를 write하지 않으므로 POR default 그대로 동작한다.
- "현재 LTA가 전혀 추적하지 않는다"는 `분석.md §핵심 발견 #6`의 결론이 번복된다.
- 그러면 `15_§7.3` "Beta 설정이 자기치유의 선행 조건"이라는 결론도 번복되고, 자기치유가 이미 동작 중이거나 다른 속도로 동작 중이라는 새 분석이 필요해진다.

**[확정 필요] 표기 있으나 영향 분석 누락**: 본 계획은 POR default=0을 기정사실로 가정하고 "Beta=0 → 자기치유 불가 → Phase 2 Beta 설정 필수"를 결론으로 내린다. 그러나 이 전제가 틀렸을 때의 재설계 비용이 명시되지 않았다.

**추가 공격**: `15_§2.3` 수렴 시간 계산에서 "폴링 주기 200ms" [추정]을 사용한다. 현재 `tdc_touch_config.h:TDC_TOUCH_POLL_INTERVAL`이 200ms임을 코드 확인하지 않은 것인지, 확인했으면 [추정]이 아니라 [코드 확인]이어야 한다. 이 값이 다르면 수렴 시간 계산 전체가 무효다.

### 결함_4: CFX userSettingValue 파서 크기 제약이 설계 진입 조건임에도 확인 방법이 없다 (12·18)

**공격 대상**: `12_계획_공장캘리저장.md §3-1` →  
> "CFX 파서가 필드 단위 int 배열로 처리할 가능성이 높으므로... [확정 필요: CFX 측 파서 코드 리뷰]"  
> `18_계획_통합아키텍처.md §6` → "CFX_확인: userSettingValue 파서 크기 제약 — Phase 2 전제"

**결함**: Phase 2 전체 아키텍처(공장 캘리브레이션 EEPROM 저장·로드)의 핵심 전제가 "CFX 측 코드 접근 불가"([현재 접근 불가 — 확정 필요]라고 명시)인 상황에서 설계를 확정했다. 이것은 단순 [확정 필요]가 아니라 **블로킹 미지수**다.

구체적 위험:
- CFX 파서가 `userSettingValue` 구조체를 고정 크기(7필드 × 4byte = 28byte) 배열로 처리한다면, 4필드 추가 시 CFX의 기존 7필드 파싱이 오프셋 불일치 없이 동작하더라도 추가 4필드를 CFX가 무시하거나 쓰레기값을 쓸 수 있다.
- 더 심각하게, CFX가 구조체 전체를 직렬화해 flash에 쓰는 경우 CM3 측 확장 구조체와 CFX 측 고정 크기 사이의 불일치가 **CM3 EEPROM 전체를 덮어쓰는 버그**를 낼 수 있다.
- `12_§3-1` 옵션_B, 옵션_C(별도 flash 경로, nvmctrl 독립 저장)가 차선으로 언급되나, 옵션_A(권고) 실패 시 재설계 비용이 명시되지 않았다.

이 불확실성이 Phase 2 전체를 차단할 수 있음에도 불구하고 `12` 계획은 옵션_A를 "권고"로 확정한 뒤 구체적 코드 스니펫까지 작성했다. **미지수가 블로킹임을 인정하면서 블로킹 미지수 위에 설계를 쌓은 것이다.**

### 결함_5: Re-ATI 결과 지속성 한계가 Phase 2~3 아키텍처 가치를 무효화할 수 있다 (13·18)

**공격 대상**: `13_계획_크래들훅.md §3-5` →  
> "Re-ATI가 성공해 MULT/COMP가 갱신되더라도, 뚜껑 열림 WDT 리셋 후 부팅 시 `write_ati_compensation()`이 하드코딩 고정값으로 덮어쓴다."  
> "Re-ATI 갱신값은 뚜껑 닫힘 구간 동안만 유효하다."

**결함**: 이 한계를 `13` 문서 자체가 명확히 인식하고 있다는 점에서 [확정 필요] 누락이 아니라 **설계 모순**이다.

Phase 2 크래들 Re-ATI(~1.5초 블로킹)의 목적은 MULT/COMP 게인+baseline 재보정이다. 그러나 뚜껑 열림 즉시 WDT 리셋 부팅이 발생하고, 부팅 시퀀스의 `write_ati_compensation()`이 이 갱신을 **무효화**한다. 즉 크래들 Phase 2 Re-ATI는 뚜껑 닫힘 기간(터치 폴링이 없는 구간)에서만 유효하다 — 실제 터치 동작이 이루어지는 뚜껑 열림 후에는 효과가 없다.

`13_§7` 핵심 결론 6항에서 이를 명시하지만 "Phase 3 EEPROM 저장과 결합해야 영속"이라고 해결책을 후속 Phase로 미룬다. **Phase 2 Re-ATI 자체가 뚜껑 닫힘 기간에만 유효하다면, Phase 2 구현의 실질 가치는 뚜껑 닫혀 있는 동안의 LTA 드리프트 방지(사용자 터치 없는 구간)뿐이다** — 이것이 얼마나 가치 있는지 정량적 근거가 없다.

### 결함_6: discharge_crx0 데이터시트 A.5 해석이 틀렸을 경우 방전 트랙 전체가 무의미하다 (17)

**공격 대상**: `17_계획_방전트랙.md §1-2` →  
> "`0x30 0x02` write가 실제로 CRX0을 VSS에 연결해 ESD 전하를 방전하는지... RTT 실측(실측1) 전에 단정 불가."

**결함**: [확정 필요] 표기가 정확히 존재한다. 그러나 계획의 Phase 구조는 "실측1 전에는 현재 코드 유지"를 기본 방침으로 한다. 이 판단 자체는 합리적이나, 실측1이 언제 선행되는지 Phase 의존 관계에 명시되지 않았다.

더 심각한 문제: `17_§5-1`에서 "방전이 충분히 작동해야 노터치 게이트의 절대 윈도우가 의미를 가진다"고 명시한다. 즉 **방전 트랙(Phase 미정)이 노터치 게이트(Phase 2)의 전제 조건**이다. 그런데 Phase 2 구현 계획(11·14·18)에서 방전 트랙의 실측1 선행을 게이트 조건으로 명시하지 않았다.

구체적 퇴행 경로: ESD 전하 누적이 심한 환경에서 → counts가 noTouch 윈도우 이하로 떨어짐 → 노터치 게이트 항상 폴백 → Phase 2 전체 무의미 → Phase 2 활성화 후 5초 지연만 추가. 이것이 실측1 없이 Phase 2를 활성화할 때의 실제 위험인데, 계획들이 이를 명시적 의존 관계로 연결하지 않았다.

### 결함_7: apply_settings() 삽입점이 실제 코드 라인 번호와 불일치할 수 있다 (11·14·16)

**공격 대상**:  
`11_계획_부팅시퀀스.md §3-1` → "현재 흐름 (`iqs323.c:1141~1158` 추정, apply_settings 말미)"  
`14_계획_노터치게이트코드.md §0` → `iqs323.c:1147` 무조건 RESEED.  
`16_계획_사후검증.md §1-2` → `tdc_drv_iqs323_apply_settings()` (`:1146~1150`) 변경.

**결함**: `11_§3-1`은 라인 범위를 "추정"으로 표기했지만 `14_§0`, `16_§1-2`는 특정 라인 번호를 확정값으로 사용한다. 현재 git 상태(`git status`에 `tdc_drv_iqs323.c` 수정됨 표기)를 감안하면, 분석.md 기준("정리 커밋 d754e99 이후 현재 코드 기준")과 현재 워킹트리 라인 번호가 불일치할 가능성이 있다.

더 중요하게, `14_§2-3` `tdc_drv_iqs323_reseed_with_gate()` 설계에서 "apply_settings() 내 write_ati_compensation() 직후, CH TIMEOUT 비활성화 write_register(0xC0, 0x00, 0x07) 이전에 호출"이라고 명시하지만, 실제 `apply_settings()` 함수명과 `iqs323.c`에서 이 함수가 어떻게 불리는지 코드 확인 근거가 없다. `tdc_drv_iqs323_apply_settings()`(`16_§1-2`)와 `apply_settings()`(`14_§3`)가 같은 함수인지 다른 함수인지 명시되지 않았다.

**[확정 필요] 표기 누락**: 라인 번호 및 함수명 동일성 확인이 구현 착수 전 필수 확인 항목으로 명시되지 않았다.

## 2. 구조적 위험 — 단정 표현·조합 오차

### 위험_A: 게이트 판별~RESEED 사이 원자성이 SW로 보장되지 않는다

`14_계획_노터치게이트코드.md §2-3` → "원자 블록: RESEED 즉시 실행"이라고 명시하나, 실제 구현은 `read_ch0_filtered_counts()` I2C read 후 `write_register(RESEED)` I2C write 두 번의 연속 호출이다.

ARM Cortex-M3 환경에서 두 I2C 트랜잭션 사이에 인터럽트가 발생하면 실질적 원자성이 깨질 수 있다. 더 중요하게는, 이 두 I2C 트랜잭션은 IQS323 IC 관점에서 하나의 측정 주기 내에 보장되지 않는다 — counts를 읽는 시점과 RESEED가 적용되는 시점 사이에 IQS323이 새 측정 값을 산출할 수 있다.

계획은 이를 "race"로 인식하고 사후 검증으로 완화한다고 하지만, 레이어_2(N샘플 안정성 확인)가 이 race를 줄여주는지 늘려주는지 분석이 없다. 레이어_2가 50ms × 3샘플 = 150ms 대기를 추가하면, 오히려 race 발생 창이 150ms로 넓어진다.

### 위험_B: 자기치유 수렴 시간 "수 초"가 Beta=0 가정 하 성립하지 않는다

`16_계획_사후검증.md §3` →  
> "Fixed ATI Disabled 구조에서 race 오염 시: LTA = 터치 counts → 손뗌 → counts 급상승 → LTA IIR 추적 수렴 → delta ≈ 0 복원. 현재 코드 내장, 추가 구현 없음."

그러나 `15_계획_드리프트LTA.md §7.3`에서 "Beta=0 현재 상태에서 자기치유는 실질적으로 동작하지 않는다"고 명시한다. 두 계획 문서가 **자기치유 동작 여부에 대해 모순된 결론**을 내린다.

`16`은 자기치유를 "현재 코드 내장"으로 기술하면서 추가 구현 불필요로 결론내린다. `15`는 자기치유가 Beta 설정의 선행 조건이므로 Phase 2 전까지 동작하지 않는다고 결론낸다. 이 모순은 [확정 필요] 없이 두 계획이 병렬 존재한다.

### 위험_C: Phase 의존 관계가 여러 문서에 다르게 정의된다

`11_계획_부팅시퀀스.md §2` → Phase 1 즉시 구현, Phase 2 다음 Sprint.  
`14_계획_노터치게이트코드.md §5` → Phase 1/2/3 구분.  
`18_계획_통합아키텍처.md §3` → Phase 0~4, 5단계 빌드가드.

같은 "Phase 1"이 문서마다 다른 내용을 의미한다. `11`의 Phase 1은 고정값 기준 noTouch 게이트이고, `18`의 Phase 1은 ATI_Error 핸들러(ATI Full 전환)다. 통합 아키텍처(`18`)가 마스터 Phase 정의여야 하나, 나머지 문서들이 이를 따르지 않는다. 구현 시 어느 Phase 정의가 우선인지 불명확하여 **구현 순서 오류**가 발생할 수 있다.

### 위험_D: IQS323 RESEED 발행 후 LTA 안정화까지 대기 시간이 없다

`12_계획_공장캘리저장.md §4-3` → "RESEED 완료 후 50ms 안정화 후 noTouch Counts 읽기 [추정: 50ms는 LTA IIR 1스텝 이상 대기]"

Beta=0 POR default 가정(결함_3) 하에서 50ms 안정화는 의미가 없다. LTA IIR이 동작하지 않으면 RESEED 직후 counts = LTA = 안정값이 되어 즉시 읽어도 동일하다. 반대로 Beta가 비제로 default인 경우 50ms는 충분하지 않을 수 있다(Beta=15, 200ms 폴링 기준 1샘플 반영률 5.9% → 50ms는 0.25 샘플).

이 모순 역시 Beta POR default가 확인되지 않은 상태에서 파생된 추정 오류다.

## 5. 핵심 6줄

1. **세 파일에 FACTORY_NOTOUCH_COUNTS 임시값 3종(512·450·400)이 공존** — 단일 소스로 통합하지 않으면 Phase 2 활성화 시 파일마다 다른 게이트 동작이 발생한다. 0값 safe default 설계도 `is_no_touch_window()` 언더플로로 항상 게이트 실패를 유발해 결함이다.
2. **Beta POR default 미확정 상태에서 자기치유·드리프트 추적 전 아키텍처를 구성** — `15_§7.3`과 `16_§3`이 자기치유 동작 여부에 모순된 결론을 내리며, Beta POR default 확정 없이는 어느 결론도 유효하지 않다.
3. **CFX userSettingValue 파서 크기 제약이 "현재 접근 불가"인데 Phase 2 전체가 이 위에 설계됨** — 파서가 고정 크기 구조체를 기대하면 4필드 추가가 CFX EEPROM 전체를 손상시킬 수 있으며, 이 블로킹 미지수가 Phase 2 진입 전 검증 게이트로 명시되지 않았다.
4. **방전 트랙(실측1)이 노터치 게이트(Phase 2)의 전제 조건인데 Phase 의존 관계에 연결되지 않음** — ESD 전하 누적 시 counts가 noTouch 윈도우 이탈 → 게이트 항상 폴백 → Phase 2 전체가 5초 대기 추가에 불과한 퇴행 발생.
5. **Phase 번호 정의가 11·14·18 간 불일치** — 18_통합아키텍처의 Phase 0~4와 11_부팅시퀀스의 Phase 1~4, 14_노터치게이트코드의 Phase 1~2가 다른 내용을 가리키며, 구현 착수 순서 오류로 이어질 수 있다.
6. **크래들 Phase 2 Re-ATI 결과가 WDT 리셋 부팅 즉시 고정값으로 덮어써져 뚜껑 닫힘 기간에만 유효** — 13_§3-5 자체가 이 한계를 인정하지만, Phase 2 Re-ATI의 실질 가치(터치 없는 뚜껑 닫힘 기간의 드리프트 방지)에 대한 정량적 정당화가 없어 구현 비용 대비 효과 불명확하다.
