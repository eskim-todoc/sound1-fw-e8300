## 1. 수렴 확정 항목 재공격

### [회귀_Z1] "RTT_TUNING 관련 #error 2종 추가 — 재검증2 수렴" 선언이 코드 미반영 상태에서 수렴 선언만 됐다 (치명)

**59_종합 §9 수렴 확정**:
> "RTT_TUNING 관련 #error 2종 추가 — 재검증2 수렴"

이 선언은 §3 빌드가드 최종 세트 v2에 아래 두 줄을 추가하는 것으로 처리됐다:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && TDC_TOUCH_RTT_TUNING
#error "NOTOUCH_GATE와 RTT_TUNING 동시 활성 불가 — MULT/COMP 기준 불일치"
#endif
#if TDC_TOUCH_FACTORY_CALIB_ENABLE && TDC_TOUCH_RTT_TUNING
#error "FACTORY_CALIB_ENABLE과 RTT_TUNING 동시 활성 불가 — EEPROM 공장값 무효화"
#endif
```

**코드 ground truth**: 현재 `tdc_touch_config.h`(전체 읽음)에 `TDC_TOUCH_RTT_TUNING`, `TDC_TOUCH_NOTOUCH_GATE_ENABLE`, `TDC_TOUCH_FACTORY_CALIB_ENABLE` 중 **단 하나도 정의되어 있지 않다.** §3 빌드가드 세트는 신규 설계 제안이지 현행 코드 반영이 아니다.

**회귀 경로**:
1. 이 #error들이 존재하지 않는 define에 의존한다 — `TDC_TOUCH_RTT_TUNING`이 `tdc_touch_config.h`·`iqs323.c` 어디에도 없으면 `#if TDC_TOUCH_RTT_TUNING` 블록은 조용히 0으로 평가돼 **#error가 영원히 발화하지 않는다.**
2. `iqs323.c:705~730`의 실제 조건 분기가 `TDC_TOUCH_RTT_TUNING`인지 다른 심볼인지 59_종합은 코드 직접 확인 없이 45_회귀의 인용을 그대로 재사용했다. **실제 분기 심볼명이 다르면 #error 차단 자체가 틀린 심볼 체계를 방어한다.**
3. "수렴"은 코드 변경이 아니라 문서 내 의사코드 추가다 — 구현자가 Phase 1 착수 시 이 #error들을 올바른 심볼로 작성하지 않으면 보호 없음.

**요구 조치**: `iqs323.c:705~730` 실제 분기 심볼명을 grep 확인해 #error 심볼 정합성 확보. `tdc_touch_config.h`에 stub `#define TDC_TOUCH_RTT_TUNING 0` 추가 또는 `#ifndef TDC_TOUCH_RTT_TUNING` 가드 포함 신설 확인.

### [회귀_Z2] "wait_re_ati_done() WDT 갱신 즉시 수정 필요 — 재검증2 수렴" 선언이 Phase −1 이전 즉시라면서 코드 수정이 없는 선언에 그쳤다 (치명)

**59_종합 §9 수렴 확정**:
> "wait_re_ati_done() WDT 갱신 미삽입 즉시 수정 필요 — 재검증2 수렴 (Phase −1 긴급 항목)"

**코드 직접 확인**: `iqs323.c:581~623` `wait_re_ati_done()` 루프 내에 현재 `SYS_WATCHDOG_REFRESH()`가 **없다.** (read 결과 확인: 라인 592, 599, 618에 `Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100)` 있음, WDT 갱신 없음)

**회귀 경로**: 59_종합은 "즉시 수정"이라 선언했으나 git diff 기준 현재 코드가 변경되지 않았다(`git status`에 `tdc_drv_iqs323.c` M 상태이나 이 수정이 포함됐는지 불명). 더 심각한 문제:

59_종합 §2-1이 제안한 수정 위치가:
```c
SYS_WATCHDOG_REFRESH();  /* blocking 최악 ~2.3초 — WDT 갱신 필수 */
Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
```

인데, 코드 구조를 보면 `Sys_Delay` 앞에 `SYS_WATCHDOG_REFRESH()`를 삽입해야 하는 위치가 세 곳이다(라인 592, 599, 618 — read 실패, 0xEEEE 응답, ATI 진행 중 대기). 59_종합은 "루프 본체 내 `Sys_Delay` 직전 삽입"이라 했으나 **어떤 Sys_Delay 앞인지가 불명확**하다. `read_register()` 내 `wait_rdy_window_closed()` 2회 호출(각 최대 20ms) 역시 blocking 경로에 포함되는데, 이 내부에 WDT 갱신이 필요한지도 미분석.

**추가 신규 발굴**: `tdc_drv_iqs323_sleep_measure_dump()`(`iqs323.c:877`)도 `wait_re_ati_done()`을 직접 호출한다(`iqs323.c:893`). 59_종합은 ATI_CALIB_MODE 경로만 언급했으나 SLEEP_MEASURE_MODE 경로도 동일 취약점을 공유한다 — **3개 호출 경로(ATI_CALIB_MODE·SLEEP_MEASURE_MODE·미래 Phase 3 노터치 게이트) 모두 WDT 갱신 없이 blocking**이다.

## 2. 신규 결함 발굴

### [회귀_P1] 59_종합 §4 Phase 1 `gate_check()` 언더플로 가드 — 런타임 이중 방어가 uint32 cast 방향이 틀렸다 (치명)

**59_종합 §4 Phase 1 `gate_check()` 정제 코드**:
```c
if (TDC_TOUCH_FACTORY_NOTOUCH_COUNTS <= TDC_TOUCH_NOTOUCH_MARGIN_STRICT) {
    return false;  /* 비정상 설정 — RTT 경보 */
}
uint32_t lo = (uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS
              - TDC_TOUCH_NOTOUCH_MARGIN_STRICT;
uint32_t hi = (uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS
              + TDC_TOUCH_NOTOUCH_MARGIN_UP;
return ((uint32_t)counts >= lo && (uint32_t)counts <= hi);
```

**회귀 공격**:
1. `hi` 계산 — `(uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS + TDC_TOUCH_NOTOUCH_MARGIN_UP` 에서 두 값 모두 양수라면 uint32 오버플로가 가능하다. IQS323 counts가 12비트라면 FACTORY_NOTOUCH_COUNTS가 4095에 MARGIN_UP이 100이면 `hi = 4195 > Max_Counts(4095)` — 이 경우 `counts <= hi`가 항상 참이 되어 상한 게이트가 무력화된다. **상한 오버플로 방어가 없다.**

2. 컴파일 타임 #error 가드는 `MARGIN_STRICT >= FACTORY_NOTOUCH_COUNTS`를 차단하지만, **`FACTORY_NOTOUCH_COUNTS + MARGIN_UP > Max_Counts`를 차단하는 #error가 없다.** Max_Counts가 블로킹_E(미확정)이므로 이 가드 자체를 작성할 수 없어 런타임 취약점이 잔존한다.

3. `counts` 파라미터 타입이 `uint16_t`인데, `uint32_t`로 cast 후 `lo`·`hi`(uint32_t)와 비교하는 것은 정상이다. 그러나 IQS323 counts가 부호 있는 정수로 반환될 가능성 [확정 필요: `tdc_drv_iqs323_read_status()` 반환 타입] — 음수 counts가 uint32_t로 캐스트되면 매우 큰 양수가 되어 게이트 통과 또는 영구 차단이 발생.

### [회귀_P2] 59_종합 §4 Phase 3 비블로킹 3단계 구조 — "ATI 완료 후 게이트 재확인"이 공장 기준과 동적 Re-ATI 이후 기준 중 어느 것인지 미지정이라 전체 판별 기준이 모순된다 (치명)

**59_종합 §4 Phase 3 R3_CHARGING 비블로킹 구조**:
```
① re_ati_trigger() 발행 → s_ati_in_progress=true
② 폴링 중 NOT_TOUCH 강제
③ ATI_Active=false 확인 후:
   iii-a. 현재 counts로 게이트 재확인 (ATI 중 터치 가능성)
   iii-b. 통과 시 정상 ATI 완료
   iii-c. 이탈 시 RTT 경보
```

**회귀 공격**: 단계 ③-a "현재 counts로 게이트 재확인"에서 게이트 기준이 `FACTORY_NOTOUCH_COUNTS`(공장 절대 기준)인지 `Re-ATI 이후 새 noTouch 기준`인지가 §4에 명시되지 않았다.

- Re-ATI가 완료된 후 IC는 새로운 MULT/COMP로 counts를 생성한다. Re-ATI 전 공장 기준 counts(예: 400)와 Re-ATI 후 새 기준 counts(예: 512 = ATI Target)는 다른 절대값을 가질 수 있다.
- Re-ATI 완료 후 즉시 공장값 `FACTORY_NOTOUCH_COUNTS=400`으로 게이트 재확인하면, IC는 이미 512를 기준으로 MULT/COMP를 재산출했으므로 현재 noTouch counts가 512 근처에 있어도 게이트 윈도우(400 ± MARGIN)에서 이탈해 "ATI 오염"으로 오판한다.

이것은 아키텍처 원리("공장 절대 기준으로 판별")와 "Re-ATI 후 counts 재확인"이 구조적으로 충돌하는 지점이다. 59_종합 §4 Phase 3 설계가 이 분기를 명시하지 않아 구현 시 혼란이 불가피하다.

**확인_14 연결**: 59_종합이 "확인_14 — R3_CHARGING 게이트 기준: 공장값 정적 vs 마지막 Re-ATI 후 noTouch counts 동적 업데이트"로 처리했으나, ③-a 단계의 즉각적 게이트 재확인 기준이 확인_14와 동일 문제임을 59_종합이 연결하지 않았다. **"③-a는 확인_14 결과를 기다려야 결정 가능"임을 Phase 3 설계에 명시해야 하나 없다.**

### [회귀_P3] 59_종합 §8 미해결 — "비블로킹 Re-ATI 중 I2C disabled (DS §8.4)" 항목이 Phase 3 착수 전이라 명시됐으나, Phase −1 긴급 수정 `wait_re_ati_done()` WDT 경로와 충돌한다 (고위험)

**59_종합 §8 미해결**:
> "비블로킹 Re-ATI 중 I2C disabled (DS §8.4) — ATI 진행 중 I²C 응답 보장 여부 미확인. Phase 3 착수 전 DS §8.4 확인."

**회귀 공격**: Phase −1 긴급 수정으로 `wait_re_ati_done()` 내 `read_register()` 10회 루프에 WDT 갱신을 삽입한다. 그런데 이 `read_register()` 자체가 ATI 진행 중에 I2C가 disabled되는지 확인되지 않은 상태에서 동작한다.

현재 `wait_re_ati_done()`은 **블로킹** 방식이다 — 즉 ATI 완료를 기다리는 동안 `read_register()`로 상태를 폴링한다. DS §8.4가 "ATI 진행 중 I2C disabled"를 확인하면:

1. `wait_re_ati_done()` 내 `read_register()` 10회 시도가 **모두 실패**한다.
2. 각 실패 시 `Sys_Delay(100ms)` → 총 1초 blocking.
3. WDT 갱신을 삽입해도 "ATI 완료를 감지하는 방법 자체가 없는" 상황이 된다.
4. 결국 10회 loop timeout으로 `false` 반환 → ATI_CALIB_MODE 경로에서 캘리브레이션 실패 오판.

Phase −1 긴급 수정의 전제가 **DS §8.4 미확인 상태에서의 설계**라는 점에서, 긴급 수정 후 DS §8.4 확인 결과에 따라 `wait_re_ati_done()` 전체 설계를 바꿔야 할 수 있다. "긴급"이라 칭하며 즉시 반영하도록 지시했으나 전제 검증이 필요한 설계다.

### [회귀_P4] 59_종합 §9 수렴 확정 — "절전 RESEED→ULP 즉시 재부팅 루프를 §8 미해결에 명시" 처리가 실제 루프 종료 조건을 간과한다 (고위험)

**59_종합 §8 미해결**:
> "절전 RESEED 오염→ULP 즉시 재부팅 루프. GATE_ENABLE=0 환경 현재 코드에서 재현 가능. 블로킹_G 해소 후 절전 RESEED 게이트화 여부 결정."

**회귀 공격**: 이 루프가 실제로 종료되는 조건이 §8에 없다.

현재 절전 진입/복귀 경로:
1. 절전 진입: `func_sleep()` → `apply_sleep_settings()` → `tdc_drv_iqs323_reseed()` → `ci_power_sleep()` → WDT 타임아웃 대기 → WDT 리셋
2. WDT 리셋 재부팅 → MCLR → Auto-ATI → RESEED(부팅, 터치 중) → `s_boot_touch_ignore` 방어

"터치 중 재부팅 → RESEED 오염 → LTA = 터치 counts → 부팅 후 노터치로 즉시 false detection → 롱터치 없이 절전 진입 가능?"이라는 가설이 있다. 그런데:

- 실제 절전 진입 조건이 롱터치(2400ms)이므로 **재부팅 직후 곧바로 절전 재진입하려면 2400ms 롱터치가 다시 있어야** 한다. LTA 오염만으로는 즉시 재부팅 루프가 성립하지 않는다.
- 반면 절전 중 ULP 루프 내에서 터치로 WDT가 리셋되는 경로가 있다면 — `func_sleep()` 내 ULP 터치 감지 경로(`main.c:869~` 확인 필요) — ULP 롱터치로 WDT 리셋 → 재부팅 → 절전 진입 시 또 터치 중 → ULP 루프 재진입 루프가 성립할 수 있다.

59_종합은 이 루프의 **실제 성립 조건을 검증하지 않은 채 "재현 가능"이라 선언**했다. GATE_ENABLE=0 환경에서 이 루프가 재현되려면 ULP 터치 감지 경로에서 WDT 리셋이 어떻게 발생하는지 코드 확인이 선행돼야 한다. 현재 선언은 [추정] 수준이다.

### [회귀_P5] 59_종합 §4 Phase 1 확인_15 — `s_boot_touch_ignore` 해제 조건 코드(touch.c:323/352) 확인이 잔존 미해결로 남아있는데, Phase 1 계획에 이 해제 조건과 timeout 폴백 RESEED 동시 활성 시나리오가 여전히 미기술이다 (고위험)

**59_종합 §6 확인_15**:
> "`s_boot_touch_ignore` 해제 조건 코드(touch.c:323/352) + timeout 폴백 RESEED 동시 활성 시 LTA IIR 복구 경로 — Phase 1 구현 전"

**55_재검증2_회귀 회귀_F**에서 이미 지적한 사항이며, 59_종합은 이를 "확인_15"로 등록하는 데 그쳤다.

**회귀 공격**: 확인_15가 단순 등록에 그친 것은 55_재검증2의 회귀_F와 동일한 구조적 공백이다. 구체적 시나리오:

1. 부팅 → 노터치 게이트 timeout → 저신뢰 폴백 RESEED(현재 counts로 LTA seed, 오염 가능)
2. 동시에 `s_boot_touch_ignore` 활성
3. 폴링 억제 → LTA IIR 갱신 불가 → LTA가 오염된 상태로 동결
4. `s_boot_touch_ignore` 해제 = pressed==false → 터치 해제 이벤트 발생 → 억제 해제
5. 그러나 LTA IIR 갱신이 억제 구간 동안 멈췄으므로 LTA = 오염 값 유지
6. 억제 해제 직후 delta = LTA(오염) - counts(정상) = 양수 가능 → **false touch 발행**

이 시나리오가 발생할 물리적 조건이 명확함에도 59_종합은 "확인_15"로 등록만 하고 해결 설계를 Phase 1 이전 어딘가로 위임했다. **Phase 1 계획에 이 시나리오의 해결 방법이 없으면 구현 착수 불가임에도 블로킹 목록(§5)에 등록되지 않았다.** 확인_15는 단순 확인 항목이 아니라 블로킹 수준 항목이다.

## 3. 아키텍처 원리 메타 회귀

### [회귀_META] "새 약점 발굴 수가 감소하지 않아 블로킹 해소 실측을 우선" 권고 자체가 회귀 위험을 외재화한다

**59_종합 §10 핵심 10번**:
> "새로운 약점 발굴 수가 감소하지 않아 3차 재검증보다는 블로킹 해소 실측을 우선한 후 구현 착수가 권고된다."

**회귀 공격**: 이 권고는 "실측 → 블로킹 해소 → 구현"이라는 순서를 제안한다. 그러나 현재 블로킹 목록(§5)의 11건 가운데 **실측 없이 코드 확인만으로 해소 가능한 항목이 최소 3건 있다:**

1. **블로킹_K** — `MAX_WAIT_MS_FOR_WINDOW_CLOSE` 상수는 `tdc_drv_iqs323.h` grep 1회로 즉시 확인 가능. 실측 불필요.
2. **블로킹_J** — `ATI_SETUP_FULL_LSB`는 데이터시트 §5.9 직독으로 확인. 실측 불필요.
3. **블로킹_H** — `tdc_drv_iqs323_is_ati_active()` API는 코드 추가로 즉시 구현 가능. 실측 불필요.

이 3건을 "블로킹 해소 실측"과 같은 레벨로 묶어 "실측 우선 후 구현"이라 권고하는 것은 즉시 해소 가능한 블로킹을 필요 이상으로 지연시킨다. 특히 블로킹_H(`ATI_Active API`)는 Phase 3 설계 논의가 계속되는 동안 코드 작성이 없어 논의 자체가 공회전 중이다.

더 심각하게: Phase −1 긴급 수정(WDT 갱신)이 "즉시"로 분류됐으나 회귀_Z2에서 지적한 대로 코드 수정이 미완이다. "블로킹 해소 실측 우선"이 Phase −1 긴급 항목의 즉각 이행을 흐리게 한다.

**이것은 수렴도 평가 방법의 회귀다** — "부분 수렴 유지"라는 판정이 3라운드 연속으로 동일하게 유지되면서, 각 라운드가 새 결함을 발굴하고 블로킹 수를 증가시키고(7→11건) 있다. 아키텍처 원리가 기각되지 않는다는 것과 구현 가능성 사이의 간극이 매 라운드 벌어지고 있다.

## 5. 핵심 6줄

1. **[회귀_Z1 치명] RTT_TUNING #error "수렴"이 코드 미반영 상태**: `TDC_TOUCH_RTT_TUNING`이 `tdc_touch_config.h`·`iqs323.c`에 존재하지 않으면 `#if TDC_TOUCH_RTT_TUNING` 블록은 조용히 0으로 평가돼 #error가 영원히 발화하지 않으며, `iqs323.c:705~730` 실제 분기 심볼명 grep 확인 없이 수렴 선언한 것은 환각이다.

2. **[회귀_Z2 치명] wait_re_ati_done() WDT "즉시 수정" 선언 후 코드 미수정 + SLEEP_MEASURE_MODE 경로 누락**: `iqs323.c:893`에서 `tdc_drv_iqs323_sleep_measure_dump()`도 동일 함수를 호출하므로 ATI_CALIB_MODE와 SLEEP_MEASURE_MODE 두 경로가 모두 WDT 갱신 없는 blocking이며, 수정 위치(3개 `Sys_Delay` 중 어느 앞)가 미명확하다.

3. **[회귀_P1 치명] gate_check() 상한 오버플로 가드 부재**: `hi = FACTORY_NOTOUCH_COUNTS + MARGIN_UP`이 12비트 Max_Counts(블로킹_E 미확정)를 초과하면 `counts <= hi`가 항상 참이 되어 상한 게이트가 무력화되며, counts 파라미터가 부호 있는 타입이면 uint32_t 캐스트 시 음수 wrap-around로 게이트 전체가 역전될 수 있다.

4. **[회귀_P2 치명] Phase 3 ③-a Re-ATI 완료 후 게이트 재확인 기준이 공장 기준과 Re-ATI 이후 기준 중 미지정**: Re-ATI 후 IC noTouch counts가 ATI Target(512 근처)으로 이동하므로 공장 기준 FACTORY_NOTOUCH_COUNTS(400)로 재확인하면 정상 ATI 완료를 오염으로 오판하며, 이는 확인_14와 동일 문제이나 Phase 3 설계에 확인_14 의존성이 명시되지 않았다.

5. **[회귀_P3·P5 고위험] Phase −1 긴급 수정 전제(DS §8.4 I2C disabled 미확인) + 확인_15 블로킹 강등**: wait_re_ati_done()이 blocking 폴링하는 구조 자체가 DS §8.4 확인 결과에 따라 전면 재설계 대상이 될 수 있으며, s_boot_touch_ignore timeout 폴백 동시 활성 시 LTA 동결→억제 해제 후 false touch 시나리오는 확인 항목이 아닌 블로킹_L로 격상해야 한다.

6. **[회귀_META 중간] 블로킹 11건 중 3건(블로킹_H·J·K)은 실측 불필요 즉시 해소 가능**: "실측 우선 후 구현" 권고가 이 3건을 실측 블로킹과 묶어 지연시키고, 매 라운드 블로킹 수가 증가(7→11→잠재 14건)하는 패턴은 "수렴" 보다 "발산" 경향이며, 즉시 해소 가능 항목을 분리·처리하는 triage가 필요하다.
