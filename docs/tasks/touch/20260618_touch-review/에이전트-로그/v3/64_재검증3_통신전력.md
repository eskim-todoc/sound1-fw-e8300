# 64 — 재검증3: adversarial (통신전력 관점)

**TL;DR**: 59_종합-재검증2를 통신·전력 예산 관점에서 3차 공격. 코드 직접 확인으로 신규 발굴 4건: ① re_ati_trigger()가 SYSTEM_CONTROL MSB=0x00을 무조건 write해 CH_TIMEOUT 비활성화(0x07)를 덮어쓰는 확정된 구조적 버그(확인_13 미해소 내용을 코드로 확정), ② wait_re_ati_done() 내 SYS_WATCHDOG_REFRESH() 미삽입은 Phase−1 긴급 처리되나 wait_rdy_window_closed() busy-loop 자체에도 WDT 리프레시 공백이 존재하는 2차 취약점, ③ MAX_WAIT_MS_FOR_WINDOW_CLOSE=20ms 상수 확정으로 재검증2의 "~2.3초" 산술이 수렴됨(블로킹_K 해소), ④ write_rdy_window_closed 타임아웃 시 soft-timeout으로 반환(코드 `:132`)되어 ATI 상태 불확실성이 증가하는 미분석 경로 신규 발굴. 이전 라운드의 "FPGA 전력 미정량화(확인_11)"와 "비블로킹 Re-ATI I2C disabled(DS §8.4)"는 여전히 해소되지 않았다. 아키텍처 원리 기각 없음 — 부분 수렴 유지.

## 0. 검토 범위 및 방법

- **코드 직접 확인**: `tdc_drv_iqs323.c`, `tdc_drv_iqs323.h` — 함수 본체 및 레지스터 비트 필드 구조체
- **관점**: 통신 타이밍 정확성, 전력 예산, WDT 안전성, 레지스터 write 부작용

## 1. 신규 발굴 1 — re_ati_trigger()가 CH_TIMEOUT 비활성화를 덮어쓰는 것은 확정된 코드 버그 [치명도: 높음]

### 1-1. 59_종합의 처리

> "확인_13: `re_ati_trigger()` MSB=0x00 write로 CH_TIMEOUT 비활성화(0x07) 덮어쓰기 여부" (`§6 확인_13`) — 아직 "확인 필요" 상태로 유지.

### 1-2. 코드 직접 확인 (`tdc_drv_iqs323.c:569~579`, `tdc_drv_iqs323.h:277~304`)

```c
/* iqs323.c:569~579 */
static bool re_ati_trigger(void)
{
    tdc_drv_iqs323_reg_system_control_t reg;

    reg.bytes[0]            = TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL;
    reg.bytes[1]            = 0x00;  /* LSB 전체 초기화 */
    reg.bytes[2]            = 0x00;  /* MSB 전체 초기화 ← CH_TIMEOUT 비활성화 비트(0x07) 소멸 */
    reg.elements.lsb.re_ati = TDC_DRV_IQS323_TRIGGER_RE_ATI;

    return write_register(reg.bytes[0], reg.bytes[1], reg.bytes[2]);
}
```

SYSTEM_CONTROL(0xC0)의 MSB는 다음과 같다 (`tdc_drv_iqs323.h:277~281`):

```c
typedef struct
{
    uint8_t ch0_timeout_disable  : 1;  // [8]
    uint8_t ch1_timeout_disable  : 1;  // [9]
    uint8_t ch2_timeout_disable  : 1;  // [10]
    uint8_t reserved_bit11_to_15 : 5;  // [11:15]
} tdc_drv_iqs323_msb_system_control_t;
```

`apply_settings()` 말미(`iqs323.c:1155`)에서:
```c
write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x00, 0x07)
/* MSB=0x07 = ch0/ch1/ch2_timeout_disable 모두 1 = CH_TIMEOUT 이중 비활성화 */
```

그런데 **`re_ati_trigger()`가 MSB=0x00으로 write**하므로 `ch0/ch1/ch2_timeout_disable`이 0으로 리셋된다. 즉 **Re-ATI 발행 시마다 CH_TIMEOUT이 재활성화**된다.

### 1-3. 확정 결론

59_종합은 확인_13을 "확인 필요"로 유지했으나, 코드에서 즉시 확인 가능하며 **이미 확정된 구조적 버그**다:
- Re-ATI trigger 1회 = CH_TIMEOUT 비활성화 상태 소멸
- Phase 3 R3_CHARGING에서 Re-ATI를 발행하면 그 시점부터 CH_TIMEOUT이 되살아남
- CH_TIMEOUT이 되살아난 상태에서 stuck-touch 발생 시 auto-reATI 경로가 열릴 수 있음 — ATI Mode=Disabled 이중 방어 중 절반(CH_TIMEOUT 비활성)이 무효화

**수정 (Phase 3 착수 전 필수)**:
```c
/* re_ati_trigger() 수정 — CH_TIMEOUT 비활성화 유지 */
static bool re_ati_trigger(void)
{
    tdc_drv_iqs323_reg_system_control_t reg;

    reg.bytes[0]                        = TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL;
    reg.bytes[1]                        = 0x00;
    reg.bytes[2]                        = 0x07;  /* CH_TIMEOUT 비활성화 유지 */
    reg.elements.lsb.re_ati             = TDC_DRV_IQS323_TRIGGER_RE_ATI;

    return write_register(reg.bytes[0], reg.bytes[1], reg.bytes[2]);
}
```

> [!IMPORTANT]
> 확인_13("re_ati_trigger MSB=0x00 write 부작용 분석 필요")은 코드 확인으로 즉시 해소 가능하며, 그 결과는 "CH_TIMEOUT 비활성화 덮어쓰기 확정"이다. Phase 3 설계 시 re_ati_trigger()를 수정하거나, CH_TIMEOUT 비활성화를 Re-ATI 완료 후 재write해야 한다. 블로킹_K와 달리 이것은 [추정]이 아닌 코드 확정 사실이다.

## 2. 신규 발굴 2 — wait_rdy_window_closed() busy-loop 내 WDT 리프레시 공백 [치명도: 중간]

### 2-1. 59_종합의 처리

> "[긴급] wait_re_ati_done() 내 SYS_WATCHDOG_REFRESH() 삽입 즉시 필요" — `§2-1` 및 `§9 수렴 확정`.

Phase−1 긴급 처리 대상으로 올바르게 격상됐다. 그러나 **2차 WDT 공백**이 미분석됐다.

### 2-2. 코드 직접 확인

```c
/* iqs323.c:120~141 wait_rdy_window_closed() */
static bool wait_rdy_window_closed(int max_ms)
{
    int tick_old = ci_timer_get_tick();

    while (1)
    {
        if (max_ms <= (ci_timer_get_tick() - tick_old))
        {
            ci_printv("[TOUCH] WAIT WINDOW CLOSE: soft timeout (%d ms) \r\n", max_ms);
            return false;
        }

        if (Sys_GPIO_Read(TDC_DRV_IQS323_RDY_PIN) == TDC_DRV_IQS323_RDY_WINDOW_CLOSED)
        {
            return true;
        }
        /* SYS_WATCHDOG_REFRESH() 없음 */
    }
}
```

`wait_rdy_window_closed()`는 GPIO 폴링 pure busy-loop이며 **SYS_WATCHDOG_REFRESH() 호출이 없다.** `MAX_WAIT_MS_FOR_WINDOW_CLOSE=20ms`이므로 단독으로는 WDT 위협이 낮다.

그런데 `wait_re_ati_done()` 루프 1회에서 다음 순서가 발생한다:

```
force_window_open()           최악 45ms — GPIO busy-loop, WDT 없음
  └─ wait_rdy_window_closed() 최악 20ms — GPIO busy-loop, WDT 없음
force_window_open()           최악 45ms — GPIO busy-loop, WDT 없음
  └─ wait_rdy_window_closed() 최악 20ms — GPIO busy-loop, WDT 없음
Sys_Delay(100ms)              ← Phase−1 WDT 삽입 지점
```

**Phase−1에서 Sys_Delay 직전에 SYS_WATCHDOG_REFRESH()를 삽입해도,** Sys_Delay 직전까지의 연속 busy-wait 구간은 최악 45+20+45+20 = **130ms**이다. WDT timeout이 이 값보다 짧으면 Phase−1 수정 후에도 WDT 리셋이 발생한다.

[추정] 현 WDT timeout 설정값이 문서화되어 있지 않다. 만약 WDT=128ms(@32kHz, 전형적 CM3 설정)라면 130ms 연속 busy-wait 구간에서 WDT가 발동한다.

**수정 방향 (Phase−1 수정 보완)**:
```c
/* wait_re_ati_done() 루프 내 SYS_WATCHDOG_REFRESH 위치는 Sys_Delay 전만으로 불충분 */
/* force_window_open() 또는 wait_rdy_window_closed() 내부에 WDT 삽입 필요 여부 확인 */

/* 또는: wait_re_ati_done() 내 read_register 직전에 추가 삽입 */
SYS_WATCHDOG_REFRESH();  /* read_register 전 — 130ms 연속 busy-wait 진입 전 */
if (!read_register(...)) { ... }
SYS_WATCHDOG_REFRESH();  /* Sys_Delay 전 (기존 Phase−1 위치) */
Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
```

> [!NOTE]
> 이 공격의 전제는 WDT timeout < 130ms인 경우다. WDT timeout이 130ms를 초과하면 Phase−1 단순 삽입으로 충분하다. WDT timeout 실제값 확인이 필요하다 [확정 필요: SYS_WATCHDOG_TIMEOUT 또는 동치 설정값].

## 3. 신규 발굴 3 — 블로킹_K(MAX_WAIT_MS_FOR_WINDOW_CLOSE) 이미 헤더에 확정됨 — 수렴

### 3-1. 59_종합의 처리

> "블로킹_K: MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수 실제값 — `tdc_drv_iqs323.h` grep 확인 필요" (`§5 블로킹_K`)

### 3-2. 코드 직접 확인

```c
/* tdc_drv_iqs323.h:31~32 */
#define TDC_DRV_IQS323_MAX_WAIT_MS_FOR_WINDOW_OPEN  45
#define TDC_DRV_IQS323_MAX_WAIT_MS_FOR_WINDOW_CLOSE 20
```

**MAX_WAIT_MS_FOR_WINDOW_CLOSE=20이 코드에 확정 정의**돼 있다. 54_재검증2가 "최악 20ms [확정 필요]"로 처리했으나, 이미 헤더에 존재했다. 블로킹_K는 즉시 해소 가능하다.

이에 따라 59_종합 §2-7의 최악 시간 재산출이 확정된다:

```
read_register 1회 최악:
  force_window_open × 2 = 45+45 = 90ms
  wait_rdy_window_closed × 2 = 20+20 = 40ms  ← 블로킹_K 확정값
  i2c overhead ≈ 0.5ms
  합계 = 130.5ms

wait_re_ati_done() 10회 최악:
  (130.5ms + 100ms) × 10 = 2305ms ≈ 2.3초  ← 확정
```

> [!NOTE]
> 블로킹_K는 헤더 grep으로 즉시 해소된다. 블로킹 목록에서 제거하고 "~2.3초 확정"으로 §2-7을 갱신해야 한다.

## 4. 신규 발굴 4 — wait_rdy_window_closed() soft-timeout 반환이 ATI 상태 불확실성을 야기함 [치명도: 중간]

### 4-1. 코드 확인 (`iqs323.c:120~141`)

```c
if (max_ms <= (ci_timer_get_tick() - tick_old))
{
    ci_printv("[TOUCH] WAIT WINDOW CLOSE: soft timeout (%d ms) \r\n", max_ms);
    return false;  /* 소프트 타임아웃: 에러가 아니라 상태 관찰 실패 */
}
```

주석에 "에러가 아니라 단순 상태 관찰 실패이므로 verbose 레벨로 유지"라고 명시돼 있다. 즉 `wait_rdy_window_closed()` 타임아웃은 **무시**된다. `write_register()`·`read_register()`의 호출자는 이 soft-timeout 발생 여부를 알 수 없다.

### 4-2. Re-ATI 완료 판별에서의 위험

`wait_re_ati_done()` 내 `read_register()` → `wait_rdy_window_closed()` soft-timeout 발생 시나리오:

1. `force_window_open()` 성공 → I2C read 성공 → `wait_rdy_window_closed()` **20ms timeout**
2. IC가 아직 I2C window를 닫지 않은 상태에서 20ms 초과 → soft-timeout → `read_register()` 반환은 **true(성공)**
3. 다음 `read_register()` 호출 시 IC가 이전 트랜잭션을 처리 중 → `force_window_open()` 실패 가능 → `read_register()` 반환 **false**
4. `wait_re_ati_done()`이 false 반환 → Re-ATI 완료 판정 불가 → ATI_CALIB_MODE 경로에서 오류

더 심각한 경우: soft-timeout 후에도 읽힌 status 레지스터 값이 유효하지 않을 수 있다. `ati_event` 비트를 "성공"으로 잘못 판독하면 ATI가 실제로 완료되지 않은 상태에서 Re-ATI 완료 처리가 되는 **허위 완료** 시나리오가 생긴다.

**59_종합이 이 soft-timeout 경로를 어디서도 분석하지 않았다.** `wait_re_ati_done()` 10회 루프의 실패 분기는 read_register() 반환값 false만 처리하고, soft-timeout 발생 후 true 반환 + 잘못된 데이터 조합은 처리하지 않는다.

[추정] 정상 동작 시 window close는 수 ms 내이므로 20ms soft-timeout 발생 빈도는 낮다 [확정 필요: 실제 window close 지연 측정]. 그러나 ATI 진행 중 I2C 동작(DS §8.4 "I²C disabled during ATI" — §8 미해결 항목)과 soft-timeout이 겹칠 경우 허위 완료 가능성이 높아진다.

## 5. 기존 미해소 항목 — 재검증3에서도 해소 불가 확인

### 5-1. 확인_11 (FPGA 전력 미정량화) — 미해소 유지

59_종합 §6 확인_11: "Phase 4 크래들 Re-ATI 중 FPGA 활성 전력 × ~2.3초 정량화"

이 항목은 2차 공격(54_재검증2_통신전력 §4) 후 확인_11로 추가됐으나 정량화가 이루어지지 않았다. 3차 공격에서도 코드만으로는 FPGA 활성 전력을 확인할 수 없다 [확정 필요: HW 스펙]. **Phase 4 착수 전 해소 필요 유지.**

### 5-2. 비블로킹 Re-ATI 중 DS §8.4 I2C disabled — 미해소 유지

59_종합 §8 미해결: "비블로킹 Re-ATI 중 I2C disabled (DS §8.4)"

코드에서 확인 불가능한 데이터시트 제약 사항이다. 3차 공격에서도 해소 불가. **Phase 3 착수 전 DS §8.4 + 실측 확인 필요 유지.** 단, 신규 발굴 4(soft-timeout 경로)와 결합 시 ATI 진행 중 I2C 응답 불능 → force_window_open timeout → 연속 read_register 실패 → wait_re_ati_done() 10회 소진 → ATI 완료 판정 불가 시나리오가 구체화된다.

| **미해소** | DS §8.4 | 비블로킹 Re-ATI 중 I2C disabled 상세 | — | 데이터시트 + 실측으로 Phase 3 착수 전 확인 |

## 8. 핵심 6줄

1. **[코드 확정] re_ati_trigger()가 CH_TIMEOUT 비활성화를 매번 덮어쓴다** — `reg.bytes[2]=0x00`으로 MSB 전체 초기화 후 write하므로 `ch0/ch1/ch2_timeout_disable(0x07)`이 소멸된다. Re-ATI 발행 시마다 이중 방어 절반이 무효화되는 구조적 버그이며, 확인_13은 "확인 필요"가 아니라 코드 즉시 확정 사항이다. `re_ati_trigger()` 내 `reg.bytes[2]=0x07`로 수정 또는 Re-ATI 완료 후 재write가 필수다.

2. **[Phase−1 수정 보완] wait_rdy_window_closed() busy-loop 자체도 WDT 공백이다** — Phase−1에서 `Sys_Delay` 직전에만 `SYS_WATCHDOG_REFRESH()`를 삽입하면, read_register 1회당 최악 130ms(force_window_open×2 + wait_rdy_window_closed×2) 연속 WDT 미갱신 구간이 잔존한다. WDT timeout < 130ms인 경우 Phase−1 단순 삽입 후에도 WDT 리셋이 발생하므로, `read_register()` 직전에 추가 삽입이 필요하다 [확정 필요: WDT timeout 설정값].

3. **[블로킹_K 즉시 해소] MAX_WAIT_MS_FOR_WINDOW_CLOSE=20ms가 헤더에 이미 정의돼 있다** — `tdc_drv_iqs323.h:32` 코드 확인으로 블로킹_K는 즉시 제거 가능하며, 재검증2의 "~2.3초" 최악 시간 산출이 확정 수렴된다. 블로킹 목록 갱신 필요.

4. **[신규 미분석] wait_rdy_window_closed() soft-timeout 경로에서 허위 ATI 완료 판정 가능** — 타임아웃 시 `return false`이지만 verbose 로그만 남기고 상위 호출자가 이를 무시한다(코드 설계 의도). ATI 진행 중 I2C disabled(DS §8.4) + soft-timeout이 겹치면 잘못된 status 데이터로 `ati_event` 비트를 "성공"으로 판독하는 허위 완료 시나리오가 생기며, 59_종합 어디서도 이 경로를 분석하지 않았다.

5. **[미해소 유지] 확인_11(FPGA 전력)·DS §8.4(ATI 중 I2C disabled)는 3차 공격에서도 코드 확인 불가** — 두 항목 모두 HW 실측 또는 데이터시트 직독으로만 해소 가능하다. 특히 DS §8.4와 신규 발굴 4(soft-timeout 허위 완료)의 결합 시나리오가 Phase 3 착수 전 반드시 확인해야 할 리스크다.

6. **[수렴도] 통신전력 관점 부분 수렴 — 신규 결함 수 감소 추세 확인** — 3차 공격에서 발굴된 치명/높음 항목은 1건(신규_1 CH_TIMEOUT 덮어쓰기), 중간 항목 2건(신규_2 WDT 2차 공백, 신규_3 soft-timeout 허위 완료)으로, 2차 공격(치명 9건 + 고위험 7건)에 비해 감소했다. 아키텍처 원리는 3차 공격에서도 기각되지 않았다. 단, 신규_1은 코드 즉시 확정 사항으로 Phase 3 설계 전 반드시 반영해야 한다.
