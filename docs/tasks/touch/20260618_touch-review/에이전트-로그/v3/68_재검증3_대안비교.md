# 68 — 재검증 라운드3 (대안비교 페르소나) — 59_종합-재검증2 adversarial 공격

**TL;DR**: 59_종합-재검증2를 대안비교 관점으로 공격한다. 재검증2가 흡수한 9건 치명 결함(WDT·언더플로·ATI_SETUP_FULL·RTT_TUNING·EEPROM전달·ATI_Active·~2.3초·CH_TIMEOUT·SATURATE)은 구현 세부를 패치했으나 결정의 상호 정합성·대안 선택의 정당성·59가 새로 도입한 내부 모순을 검토하지 않았다. 신규 약점 7건 발굴. 아키텍처 원리 자체는 기각 근거 없음.

## 0. 공격 방법론

59_종합-재검증2가 "수렴 확정"으로 선언한 항목 및 신규 반영한 결정을 **"대안 Y를 선택했으면 어떻게 달랐는가"** 관점으로 공격한다.

- 59가 재검증2에서 새로 도입한 결정이 기존 설계와 정합하는가?
- 더 단순·더 확실한 대안이 검토 없이 배제됐는가?
- 재검증2가 "수렴"으로 선언한 항목 중 재공격 가능한 것은?
- 여러 패치가 동시에 적용될 때 새로운 교차 모순이 발생하는가?

**이전 대안비교 라운드 누적 제외 항목 (재공격 금지)**:
- 58_대안비교(공격_1): 비블로킹 Re-ATI 중 write_ati_compensation() 재진입 race → 59 §3 재진입 가드 코드로 수렴
- 58_대안비교(공격_2): 크래들 EEPROM 덮어쓰기로 공장 기준 소실 → 59 §4 Phase 4 슬롯 정책(대안_Z) 수렴
- 58_대안비교(공격_4): Beta POR=0 시 사후 검증 조건분기 → 59 §4 Phase 3 Beta POR 조건분기 수렴
- 58_대안비교(공격_5): R3_CHARGING 게이트 기준 미기술 → 59 §6 확인_14 신규 등록 수렴

## 1. 공격_1 — `write_ati_compensation()` 시그니처 선택지_1(인자 추가)이 Phase 3 재진입 가드와 구조적 충돌 [치명]

### 59_종합-재검증2의 주장

§2-5: "선택지_1 우선 권고 — `write_ati_compensation(uint8_t mult_lsb, uint8_t mult_msb, uint8_t comp_lsb, uint8_t comp_msb)` (더 명시적, 의존성 추적 용이)"

§3 Phase 3: "비블로킹 Re-ATI 중 `write_ati_compensation()` 재진입 가드 — `if (s_ati_in_progress) { return; }`"

### 공격

**두 결정이 교차할 때 시그니처 변경(선택지_1)이 재진입 가드 구조를 복잡화한다.**

선택지_1(인자 추가)을 채택하면 `write_ati_compensation()` 호출처가 모두 4인자 전달로 변경돼야 한다. 현재 호출처는 두 곳이다:

1. `tdc_drv_iqs323_apply_settings()` — 부팅 시 1회
2. 추후 Phase 3에서 Re-ATI 완료 후 MULT/COMP 재적용이 필요하면 추가 호출처 생성 가능

재진입 가드(`if (s_ati_in_progress) { return; }`)는 인자 없는 버전 전제로 설계됐다. 선택지_1 채택 시:
- 4인자 버전은 `s_ati_in_progress` 가드에서 return 시 **인자를 소비하지 않고 조용히 무시**한다 — 호출자가 "가드에 의해 skip됐음"을 감지하는 반환값이 없으면(현재 `static bool` 구조) 호출자 로직이 "write 완료"로 오인할 수 있다.
- 선택지_2(정적 변수 신설)는 이 문제가 없다 — 재진입 가드 내 `return;`이 "이미 설정된 정적 변수를 다시 쓰지 않는" 구조이므로 인자 전달 손실 없음.

**대안 비교**:

| 선택 | 재진입 가드 정합성 | EEPROM 로드 경로 명확성 | 기존 코드 변경 범위 |
|---|---|---|---|
| 선택지_1(인자 추가) | 재진입 시 인자 소멸 문제 [추정] | 명시적 | 모든 호출처 시그니처 변경 필수 |
| 선택지_2(정적 변수 신설) | 재진입 시 기존 정적 변수 유지 — 안전 | RTT_TUNING 패턴과 동일 구조 | 변수 추가 + 함수 내부 분기 추가만 |

59 §2-5는 선택지_1을 "더 명시적"이라고 권고했으나, 재진입 가드(§3 Phase 3)와의 교차 동작을 검토하지 않았다. 선택지_2가 재진입 가드와 더 정합하는 대안이다.

**판정**: 선택지_1 우선 권고가 §3 재진입 가드와의 교차 시나리오를 무시한 채 이루어졌다. 선택지_2가 59 §3의 기존 `s_ati_in_progress` 가드 구조에 더 자연스럽게 통합된다. [추정]

## 2. 공격_2 — SATURATE_DETECT_ENABLE 기본값 0으로 수정(§2-9)이 Phase 0 존재 이유를 소멸시킨다 [고위험]

### 59_종합-재검증2의 주장

§2-9: "선택지_A 권고 — `SATURATE_DETECT_ENABLE=0u` (실측_E 완료 후 1u로)."
§4 Phase 0: "SATURATE_DETECT_ENABLE=0u 기본 유지, 블로킹_E 해소 후 활성."
§4 Phase -1: "Phase 0 이전 즉시 실행 — SATURATE_DETECT_ENABLE 기본값 0u로 수정."

### 공격

**Phase 0가 "counts 포화 감지 stub"을 목적으로 하는데, SATURATE_DETECT_ENABLE=0u(기본 비활성)이면 Phase 0가 코드 변경 없는 빈 단계가 된다.**

59 §4 Phase 0의 내용: "SATURATE_DETECT_ENABLE=0u 기본 유지, 블로킹_E 해소 후 활성. CH_TIMEOUT 재활성 여부 이중 차단 이유 확인 후 결정(확인_12 해소 후)."

이것이 Phase 0의 전부라면:
- SATURATE_DETECT_ENABLE=0u → 포화 감지 코드가 실제로 돌지 않음
- CH_TIMEOUT 결정 → 확인_12 해소 전까지 결정 보류

즉 Phase 0는 "실측_E 완료 전까지 아무것도 활성화하지 않는다"는 단계다.

**대안 비교**:

| 대안 | Phase 0 내용 | 실측 의존성 |
|---|---|---|
| 현재(59 선택): ENABLE=0u 기본 | Phase 0 = 빈 단계(stub 선언만) | 블로킹_E(Max Counts) 해소 후에만 의미 있음 |
| 대안_S: ENABLE=1u + MAX_COUNTS=4095u [추정] | DS 12비트 ADC 추정값으로 즉시 활성 | 실측_E로 정밀화 — 과잉 경보 위험 있으나 포화 감지 즉시 동작 |
| 대안_T: Phase 0 제거, 블로킹_E 해소 후 Phase 1과 함께 활성 | Phase 구조 단순화 | 동일 |

59가 "Phase 0 즉시 실행"으로 Phase -1을 설정했으면서 Phase 0를 사실상 빈 단계로 남긴 것은 Phase 구조 설계의 비효율이다. **대안_T(Phase 0 제거, 블로킹_E 해소 시 Phase 1 착수 시 함께 활성화)가 동일한 안전성을 유지하면서 불필요한 단계를 제거하는 더 단순한 대안이다.** 이 대안이 59에서 검토되지 않았다.

**판정**: SATURATE_DETECT_ENABLE=0u 수정(Phase -1)과 Phase 0(빈 단계) 병립은 Phase 구조의 낭비다. Phase 0를 제거하거나 CH_TIMEOUT 결정을 Phase -1에 통합하는 구조 단순화 대안이 미검토됐다. [추정]

## 3. 공격_3 — wait_re_ati_done() ~2.3초 재산출(§2-7)이 "블로킹 K"를 신설했으나 즉시 해소 가능한 대안을 생략했다 [중위험]

### 59_종합-재검증2의 주장

§2-7: "최악 ~2.3초 재산출. `MAX_WAIT_MS_FOR_WINDOW_CLOSE` 상수 미확인 → 블로킹_K 신설. Phase 3 WDT·FPGA 지연 계산 재수행 필요."

§5: "블로킹_K: MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수 실제값 — `tdc_drv_iqs323.h` grep 확인."

### 공격

**블로킹_K는 `tdc_drv_iqs323.h`의 상수 1개를 grep하면 즉시 해소 가능한 작업인데, "블로킹"이라는 이름으로 구현 전 해소 필수 항목에 포함시킨 것은 과잉 차단이다.**

블로킹 항목은 실측·데이터시트 확인·설계 결정 등 외부 의존성이 있는 항목에 쓰이는 것이 타당하다. `MAX_WAIT_MS_FOR_WINDOW_CLOSE`가 `tdc_drv_iqs323.h`에 존재하면 grep 1회로 확인되고, 존재하지 않으면 코드에서 직접 `wait_rdy_window_closed()` 구현을 읽으면 된다. 이것은 블로킹이 아니라 **Phase 3 착수 전 5분 내 해소 가능한 확인 항목**이다.

**대안 비교**:

| 처리 방식 | 공수 | Phase 3 착수 영향 |
|---|---|---|
| 블로킹_K(현재): Phase 3 착수 전 해소 필수 | grep 1회 (~5분) | 해소 전 Phase 3 착수 불가 선언 — 과잉 |
| 확인 항목으로 재분류 | grep 1회 (~5분) | 확인 시 바로 해소, Phase 3 계획 내 병행 처리 가능 |

더 나아가 ~2.3초 최악 계산 자체가 `MAX_WAIT_MS_FOR_WINDOW_CLOSE` 미확인 상태의 추정이다(59 §2-7 "[확정 필요: MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수]"). 즉 Phase 3 WDT·FPGA 지연 계산 재수행이 실제로 필요한지조차 이 상수 확인 전에는 불명이다. **블로킹_K를 즉시 해소해 ~2.3초가 실제로 달라지는지 확인 후 Phase 3 계획 재수행 여부를 결정하는 것이 더 효율적인 순서**다.

**판정**: 블로킹_K는 5분 내 해소 가능한 확인 항목을 블로킹으로 상향 처리한 과잉 차단이다. 확인 항목으로 재분류해 Phase 3 설계 병행 처리가 가능하도록 하는 것이 더 단순한 대안이다.

## 4. 공격_4 — 빌드가드 세트 v2(§3)의 `NOTOUCH_GATE_ENABLE && RTT_TUNING #error`가 올바른 방향인지 대안 미검토 [고위험]

### 59_종합-재검증2의 주장

§3 빌드가드 세트 v2:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && TDC_TOUCH_RTT_TUNING
#error "NOTOUCH_GATE와 RTT_TUNING 동시 활성 불가 — MULT/COMP 기준 불일치"
#endif
#if TDC_TOUCH_FACTORY_CALIB_ENABLE && TDC_TOUCH_RTT_TUNING
#error "FACTORY_CALIB_ENABLE과 RTT_TUNING 동시 활성 불가 — EEPROM 공장값 무효화"
#endif
```

### 공격

**이 `#error` 가드는 RTT_TUNING을 "적과 공장 캘리브의 배타적 경쟁자"로 규정하는데, 58_재검증2_대안비교 공격_7이 지적한 "두 경로를 통합하는 대안"이 59에서 채택 검토 없이 배제됐다.**

58_대안비교(공격_7)는 "RTT 튜닝 결과를 공장 캘리브레이션 EEPROM 경로에 직접 연결(`ATI_CALIB_MODE=1` 시 RTT로 출력하면서 동시에 FACTORY_CALIB_ENABLE 경로로 EEPROM write)하는 대안"을 제시했다.

59 §3 빌드가드는 이 통합 대안을 검토한 흔적 없이 `#error`로 차단했다. 그 결과:

- RTT_TUNING 빌드로 개발 중인 환경에서는 **NOTOUCH_GATE 기능을 전혀 테스트할 수 없다** — 빌드 자체가 실패하므로.
- 공장 공정이 RTT_TUNING을 통해 캘리브레이션 값을 결정하는 경우(즉 ATI_CALIB_MODE와 RTT_TUNING이 모두 켜진 공장 빌드 시나리오), NOTOUCH_GATE도 함께 검증할 수 없다.

**대안 비교**:

| 대안 | RTT_TUNING + GATE 관계 | 개발 환경 테스트 가능성 |
|---|---|---|
| 현재(59 #error): 동시 활성 불가 | 배타적 — 개발과 운용 빌드 완전 분리 | GATE가 RTT 빌드에서 미검증 상태로 운용 빌드에 투입됨 |
| 대안_U: #warning으로 격하 + RTT_TUNING 시 게이트 기준 MULT/COMP 소스를 RTT 값으로 자동 전환 | 통합 — RTT 값이 게이트 기준이 됨 | RTT 빌드에서 GATE 동작 검증 가능 |
| 대안_V: #error 유지 + ATI_CALIB_MODE만 예외(RTT 출력 동시에 EEPROM write) | 공장 빌드 한정 통합, 일반 RTT_TUNING은 차단 | 제한적 통합 |

59 §3이 `#error`를 선택한 이유는 "MULT/COMP 기준 불일치"이나, 이 불일치는 "RTT 값을 게이트 기준으로도 쓰면 통합 가능"함을 무시한 판단이다. **게이트 기준 소스를 RTT 값으로 동기화하는 대안(대안_U)이 더 유연하고 테스트 가능한 설계다.**

**판정**: `#error`에 의한 동시 활성 금지는 개발 중 NOTOUCH_GATE 테스트 경로를 막는 부작용이 있으며, RTT_TUNING과 GATE를 통합하는 대안이 검토 없이 배제됐다.

## 5. 공격_5 — 59 §4 Phase 1 `tdc_notouch_gate_check()` 런타임 언더플로 가드가 컴파일 타임 가드와 중복되는 이중 방어의 비용 미분석 [중위험]

### 59_종합-재검증2의 주장

§4 Phase 1 `gate_check()` 정제:
```c
static bool tdc_notouch_gate_check(uint16_t counts)
{
    /* 언더플로 가드: 컴파일 타임에 #error로 선차단, 런타임 이중방어 */
    if (TDC_TOUCH_FACTORY_NOTOUCH_COUNTS <= TDC_TOUCH_NOTOUCH_MARGIN_STRICT) {
        return false;  /* 비정상 설정 — RTT 경보 */
    }
    ...
}
```

§3 빌드가드:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && \
    (TDC_TOUCH_NOTOUCH_MARGIN_STRICT >= TDC_TOUCH_FACTORY_NOTOUCH_COUNTS)
#error "NOTOUCH_MARGIN_STRICT must be < FACTORY_NOTOUCH_COUNTS (underflow risk)"
#endif
```

### 공격

**컴파일 타임 `#error`가 MARGIN_STRICT ≥ FACTORY_COUNTS 조합을 이미 차단하므로, 런타임 `if (COUNTS <= MARGIN_STRICT) { return false; }` 가드는 `#error`가 통과한 유효 빌드에서는 절대 실행되지 않는 죽은 코드(dead code)다.**

`#error`가 컴파일 타임에 이 조합을 차단하면, 실제 빌드에서는 `TDC_TOUCH_FACTORY_NOTOUCH_COUNTS > TDC_TOUCH_NOTOUCH_MARGIN_STRICT`가 항상 참이다. 따라서 런타임 분기 `if (COUNTS <= MARGIN_STRICT) { return false; }`는:
- 조건이 항상 거짓 → **컴파일러 최적화 시 제거될 수 있으나 명시적으로 dead code임을 표기하지 않음**
- 코드 리뷰자가 "왜 컴파일 타임 가드가 있는데 런타임 가드도 있는가?"라는 혼란을 겪을 수 있음

**대안 비교**:

| 대안 | 안전성 | 코드 복잡도 |
|---|---|---|
| 현재(이중 가드): #error + 런타임 if | 최고 | 높음 — dead code로 인한 혼란 |
| 대안_W: #error만(런타임 가드 제거) | 컴파일 타임 안전 보장 충분 | 낮음 — 코드 명확 |
| 대안_X: #error 제거 + 런타임 가드만 | 낮음 — 런타임 조건 분기로 처리 | 중간 |

59 §4가 "컴파일 타임에 #error로 선차단, 런타임 이중방어"라고 의도를 명시했으나, 이 이중방어는 컴파일 타임 차단이 완전한 이상 런타임 비용·dead code·코드 혼란을 유발할 뿐 안전성 향상이 없다.

**판정**: 런타임 언더플로 가드는 컴파일 타임 #error와 중복되는 dead code다. 대안_W(#error만)가 더 단순하고 명확하다. [추정]

## 6. 공격_6 — 59 §4 Phase 1 사후 검증 "counts < lo = 정상 터치 중"(56_할루시 §3-1 반영) 정정이 불완전하다 [고위험]

### 59_종합-재검증2의 주장

§4 Phase 1 사후 검증:
```
RESEED 발행 → counts 1회 재읽기
  → counts < lo (터치 중 = counts 감소 방향): 정상 터치 진행 중, RTT 경보 불필요
  → counts > hi (상한 이탈): 이상 상태, RTT 경보 발행 ("race 추정, LTA IIR 자기치유 위임")
  → 재RESEED 없음.
```

### 공격

**"counts < lo = 정상 터치"라는 판정이 사후 검증 로직을 비어 있는 상태로 만든다.**

사후 검증의 목적은 "게이트 통과 → RESEED 발행 사이에 race가 발생했는지 확인"이다. race가 발생하면:
- 게이트 통과 시점: counts ≈ FACTORY_NOTOUCH_COUNTS (윈도우 내, 노터치 판정)
- RESEED 발행 직후 counts 재읽기: counts가 낮아졌으면 → 게이트 통과 후 터치 시작

이 경우 "정상 터치 진행 중, RTT 경보 불필요"라는 판정은 "race가 있었음에도 아무 조치 없이 통과"하는 것이다. RESEED는 이미 발행됐고 LTA가 게이트 통과 시점의 counts(≈ FACTORY_NOTOUCH_COUNTS)로 seed됐다. 이후 터치 중이므로 delta는 LTA - Counts = FACTORY_COUNTS - (낮아진 값) > 0 → 터치 인식은 정상 동작한다.

그러나 **LTA가 FACTORY_COUNTS 근처로 올바르게 seed됐으므로 race 자체는 무해**하다 — 게이트 통과 직후 터치가 시작됐어도 LTA는 노터치 기준으로 올바르게 세팅됐다. 즉:

1. `counts < lo` (RESEED 후 터치 시작): race 있었으나 RESEED는 정상 노터치 기준으로 됐음 → 무해
2. `counts > hi` (RESEED 후 counts 급상승): 이것은 **실제로 발생하기 어려운 상황**이다 — RESEED 후 수십ms 내에 counts가 FACTORY_COUNTS + MARGIN_UP을 초과하려면 정전용량이 MCLR 이후 추가로 감소해야 하는데 이는 비현실적 [추정]

따라서 59의 사후 검증은:
- `counts < lo` 케이스: 무해하게 통과 (올바름)
- `counts > hi` 케이스: RTT 경보 발행하지만 이 케이스가 현실에서 발생할 수 있는가? [확정 필요]

**놓친 케이스**: `counts ∈ [lo, hi]` (윈도우 내 유지): 정상 noTouch 유지 — 이 케이스 처리가 사후 검증 코드에 명시 없음. 59 §4의 의사 코드는 `< lo`와 `> hi` 두 분기만 기술하고 **정상 케이스(윈도우 내 유지)에서 어떻게 처리하는지 빠져 있다.**

**판정**: 59 §4 사후 검증 의사 코드의 `counts ∈ [lo, hi]` (정상) 케이스 처리가 누락됐다. 또한 `counts > hi` 케이스가 현실에서 발생 가능한지 근거가 없다. 사후 검증 설계가 실제로 구현 가능한 완전한 3분기 구조로 명시돼야 한다. [확정 필요]

## 7. 공격_7 — 59 §9 "수렴 확정" 목록에서 EEPROM 로드 방향이 수렴 확정됐으나 선택지 미확정이라는 모순 [중위험]

### 59_종합-재검증2의 주장

§9 수렴 확정 항목:
> "EEPROM 로드 경로 필요성 + 설계 방향(인자 전달 구조 선택) — 방향 수렴, 구체 선택 미확정"

§5 블로킹 목록:
> "신규_EEPROM전달: `write_ati_compensation()` 인자 전달 방법 확정 — Phase 2 착수 전"

### 공격

**"방향 수렴, 구체 선택 미확정"은 수렴이 아니다. §9 수렴 확정 목록에 넣어서는 안 될 항목이다.**

수렴의 정의는 "더 이상 공격으로 기각할 수 없고 결정이 확정됐음"이어야 한다. "구체 선택 미확정"은 결정이 열려 있다는 뜻이므로 수렴이 아닌 "블로킹으로 대기 중"이 올바른 상태다.

더 나아가 §5 블로킹에 "신규_EEPROM전달"로 이미 등록됐으므로, §9 수렴 확정 목록에 동일 항목이 "방향 수렴"으로도 들어가는 것은 **블로킹과 수렴 확정의 이중 분류**다. 이는 이 항목의 상태가 실제로 무엇인지 모호하게 만든다.

**대안 비교**:

| 현재 분류 | 문제 | 올바른 분류 |
|---|---|---|
| §9 수렴 확정 + §5 블로킹 동시 | 상태 모호 — 수렴인가 블로킹인가? | §5 블로킹만(신규_EEPROM전달) |
| §9에서 제거, §5 블로킹만 유지 | Phase 2 착수 전 선택지 결정 게이트 명확 | 권장 |

이 문제는 작은 것 같지만, 재검증4(최종 종합)에서 "수렴 확정 항목 목록"이 아키텍처 원리 확립의 증거로 사용될 때 **실제로는 미결인 항목이 수렴된 것처럼 오인될 수 있다**.

**판정**: "방향 수렴, 구체 선택 미확정"은 수렴 확정이 아닌 블로킹이다. §9에서 제거하고 §5 블로킹 항목(신규_EEPROM전달)으로만 표기해야 상태가 명확하다.

## 9. 수렴도 평가 (재검증3)

**부분 수렴 유지** — 판정 근거:

- 아키텍처 원리(공장 절대 기준 → 노터치 게이트 → Re-ATI)는 3회 대안비교 라운드(48·58·68) 모두에서 기각 근거가 발굴되지 않았다 → **아키텍처 원리 수렴 강화**.
- 신규 약점 발굴 수: 라운드1(8건) → 라운드2(7건) → **라운드3(7건)** — 감소 없음. 단, 라운드3 발굴 약점의 심각도가 "구현 세부 정합성 및 단순화" 수준으로 이동했으며 치명_1건(선택지_1 재진입 race)·고위험_3건·중위험_3건 구성.
- **치명 블로킹은 추가되지 않았다**: 공격_1은 선택지_1 vs 선택지_2 중 선택지_2 권고이며, 기존 블로킹 구조를 변경하는 것은 아님.
- **결론**: 추가 대안비교 라운드보다 블로킹_A·B·D·G·H·I·J + 신규_EEPROM전달 해소 실측·코드 확인을 우선하는 것이 권고된다.

## 10. 핵심 6줄

1. **[치명] 선택지_1(인자 추가) 우선 권고가 §3 재진입 가드와 충돌한다**: `write_ati_compensation(mult, comp)` 4인자 버전을 `s_ati_in_progress` 가드에서 `return`하면 인자가 소멸하며 호출자가 skip 여부를 알 수 없다 — 선택지_2(정적 변수 신설)가 RTT_TUNING 기존 구조와 일치하고 재진입 가드와 자연스럽게 통합된다.

2. **[고위험] Phase 0이 SATURATE=0u 기본 + CH_TIMEOUT 결정 보류로만 구성돼 실질 동작 없는 빈 단계가 됐다**: Phase -1(즉시 수정)이 이미 독립 단계로 설정됐으므로 Phase 0를 제거하고 블로킹_E 해소 후 Phase 1에서 SATURATE 활성화를 처리하는 구조 단순화 대안이 미검토됐다.

3. **[고위험] #error RTT_TUNING 차단이 개발 빌드에서 NOTOUCH_GATE 테스트 경로를 막는다**: RTT 빌드에서 GATE를 동시 활성화하면 컴파일 실패 → RTT 환경에서 GATE 기능을 검증할 방법이 없다 — 게이트 기준 MULT/COMP를 RTT 값으로 동기화하는 통합 대안(대안_U)이 배제된 채 배타적 #error만 채택됐다.

4. **[고위험] 사후 검증 의사 코드의 정상 케이스(counts ∈ [lo, hi]) 처리가 누락됐다**: RESEED 후 counts 재읽기에서 `< lo`(터치 진행 중 — 무해)와 `> hi`(이상 상태 — RTT 경보) 두 분기만 기술하고 윈도우 내 유지(정상 noTouch) 케이스 처리가 없어 완전한 3분기 구조가 아니다.

5. **[중위험] 블로킹_K(MAX_WAIT_MS_FOR_WINDOW_CLOSE)는 grep 1회로 해소 가능한 확인 항목을 블로킹으로 과잉 처리했다**: Phase 3 WDT·FPGA 지연 재계산이 이 상수에 의존하므로 즉시 grep 후 확인해 블로킹 목록에서 제거하는 것이 Phase 3 착수 지연을 줄이는 더 효율적인 처리다.

6. **[수렴도] 라운드3 대안비교 결과 아키텍처 원리 수렴 강화 — 구현 전 블로킹 해소 우선 권고**: 48·58·68 세 라운드 대안비교 누적 공격에서 아키텍처 원리(공장 절대 기준 → 노터치 게이트 → Re-ATI)는 단 한 번도 기각되지 않았다. 라운드3 신규 약점은 모두 구현 세부 정합성 수준으로 이동했으며, 추가 재검증보다 블로킹 해소 실측(블로킹_A·D·G·H 우선)이 차기 단계로 권고된다.
