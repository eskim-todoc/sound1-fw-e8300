## 1. 치명 — TDC_TOUCH_RTT_TUNING 분기, 게이트 신뢰도 파괴 경로 해소 전무

### 1-1. 49 종합의 처리

§9 신규 약점 반영 후 잔존 미해결 표에 `신규_TDC_RTT_TUNING` 항목이 "고위험"으로 등록됐다:
> "TDC_TOUCH_RTT_TUNING 분기와 공장값 게이트 신뢰도 충돌 — 고위험"

### 1-2. 공격

이 항목이 등록됐을 뿐 **해소 방향이 한 줄도 제시되지 않았다.** §1·§2·§3·§4·§5 어디에도 RTT_TUNING 분기와 공장값 게이트의 충돌 해소를 위한 설계 결정이 없다.

구체 문제는 45_회귀 §회귀_2에서 발굴됐다:

- `write_ati_compensation()` 내부에 `#if TDC_TOUCH_RTT_TUNING` 분기가 존재(`iqs323.c:705~730`). RTT_TUNING=1 + `s_tdc_normal_tuning.ati_valid=true`이면 MULT/COMP가 런타임 튜닝값으로 대체된다.
- Phase 1 노터치 게이트는 `FACTORY_NOTOUCH_COUNTS`와 현재 counts를 비교한다. 그런데 공장 캘리브레이션 시점의 MULT/COMP와 런타임 RTT_TUNING 활성 시의 MULT/COMP가 다르면, **동일한 물리 정전용량이라도 counts 절대값이 달라진다** — 공장 저장 기준값이 무의미해진다.
- 이 충돌을 해소하려면 최소한 다음 중 하나를 결정해야 한다: ① 공장 캘리브레이션은 RTT_TUNING=0 빌드에서만 수행(릴리즈 빌드 전용), ② RTT_TUNING과 FACTORY_CALIB 동시 활성 차단 #error, ③ 게이트 비교 시 현재 활성 MULT/COMP를 기준으로 FACTORY_NOTOUCH_COUNTS를 재환산.

49 종합에는 이 세 가지 중 **어느 것도 선택되지 않았다.** 신규_TDC_RTT_TUNING을 "고위험"으로 분류만 하고 블로킹 테이블이나 확인 항목에 넣지 않아, Phase 1 또는 Phase 2 착수 전 해소 의무가 명시되지 않은 채 떠있다.

**추가 함의**: 49 종합 §3 정제된 빌드가드 최종 세트에 `RTT_TUNING` 관련 #error가 없다. `TDC_TOUCH_NOTOUCH_GATE_ENABLE=1` + `TDC_TOUCH_RTT_TUNING=1` 조합이 컴파일 타임에 차단되지 않아, 게이트가 활성화된 채 RTT_TUNING이 MULT/COMP를 바꾸는 상황이 실제 배포에서 발생할 수 있다.

**판정**: [치명] — Phase 1·2 설계의 핵심 전제(단일 MULT/COMP 게인 기준)를 파괴하는 경로가 해소 방법 없이 §9 표에만 등록됐다. 블로킹 테이블(§5)에 추가하고 Phase 1 착수 전 #error 가드 설계를 명시해야 한다.

## 2. 치명 — stuck-touch(CH_TIMEOUT) 검토 계획 "추가 필요"로 끝난 채 실질 해소 없음

### 2-1. 49 종합의 처리

§8 미해결 표 마지막 행:
> "stuck-touch(CH_TIMEOUT) 처리 — CH_TIMEOUT 이중 차단 유지 이유 미명시 — Phase 0 또는 1에서 재활성 여부 검토 추가 필요"

### 2-2. 공격

48_대안비교 §공격_5에서 지적한 핵심이 **그대로 §8에 이전됐을 뿐**이다. 구체적으로 해소된 내용이 없다.

무한 터치 시나리오(개념정리_터치동작모델.md §5 의문_5)는 다음 조건에서 발생한다:

- 부팅 시 터치 중 RESEED → LTA 오염 → 손 뗌 후에도 delta≈0 → 터치 인식 없음(의문 5와 반대 방향인 "미인식 고착")
- 또는 RESEED 오염으로 LTA가 터치값 고착 → delta 음수 → 영구 노터치 혼동

CH_TIMEOUT이 이중 차단(`write_register(0xC0, 0x00, 0x07)` — `CH_TIMEOUT_DISABLE`)된 이유가 어느 에이전트 로그에도, 49 종합에도 기술되지 않았다. 이중 차단 이유를 모르는 상태에서 재활성 검토를 "추가 필요"로만 남기면 구현자가 CH_TIMEOUT 재활성 조건을 독자 판단해야 하는 위험이 있다.

**더 심각한 완전성 공백**: CH_TIMEOUT 재활성이 Phase 0~4 어느 Phase에서 수행되는지 49 종합 §4 Phase 계획에 일절 없다. §8에서 "Phase 0 또는 1에서 재활성 여부 검토 추가 필요"라고 했으나, Phase 0·1 계획 본문(§4 Phase 0, Phase 1 섹션)에 이 검토가 포함되지 않았다. 따라서 Phase 0·1 구현이 완료돼도 CH_TIMEOUT 재활성 검토는 자동으로 누락된다.

**관련 미완 연결**: 49 종합 §3 빌드가드 세트에도 `TDC_TOUCH_CH_TIMEOUT_ENABLE` 같은 define이 없어, CH_TIMEOUT 재활성을 빌드가드로 관리하는 경로도 없다.

**판정**: [치명] — 무한 터치 방어의 핵심 하드웨어 타이머(CH_TIMEOUT)가 Phase 계획 본문과 빌드가드 세트에서 완전히 누락됐다. 이중 차단 이유 미명시 상태에서의 재활성 검토는 회귀 위험을 내포한다.

## 3. 치명 — ESD 환경에서 Phase 1 폴백이 현재 무조건 RESEED와 동일 결과임을 미분석

### 3-1. 49 종합의 처리

§8 미해결 표:
> "게이트 race 원천 제거 — 원자 블록 불가능 — RTT 경보 + Beta POR 실측 후 자기치유 확인"

§1-1 층위 별 현재 상태 표: 층위 1(노터치 게이트) — "미구현"

### 3-2. 공격

48_대안비교 §공격_8이 발굴한 "ESD 환경 Phase 1 폴백 = 현재와 동일 오작동" 시나리오가 49 종합 어디에도 분석되지 않았다.

문제 재현:

ESD 전하 누적 상태에서 부팅:
- 현재(GATE_ENABLE=0): RESEED 무조건 발행 → LTA가 ESD-낮은 counts로 seed → 손 뗌 후에도 오작동
- Phase 1 활성(GATE_ENABLE=1) + ESD로 counts가 FACTORY_NOTOUCH_COUNTS보다 낮음: 게이트 "터치 의심" 판정 → RESEED 보류 → `TDC_TOUCH_BOOT_WAIT_MS` timeout 대기 → 폴백 RESEED 실행 → LTA가 ESD-낮은 counts로 seed → **손 뗌 후에도 동일 오작동**

즉 ESD 환경에서 Phase 1을 활성화해도 최종 결과가 현재와 동일하다. 그런데 Phase 1 활성 시 사용자는 부팅 직후 `BOOT_WAIT_MS`(미확정 값) 동안 추가 지연을 경험한다 — 현재보다 UX가 나빠지는 케이스다.

49 종합은 "ESD = 독립 트랙(별도 HW 블리더 or 주기 방전)"으로 분리했지만, **ESD 독립 트랙이 해소되기 전에 Phase 1이 배포되면 ESD 환경 사용자는 Phase 1 이전보다 나쁜 UX를 경험한다는 사실이 어디에도 기술되지 않았다.**

Phase 1 활성화 조건(블로킹_A·B·G 완료 후)에 "ESD 독립 트랙(방전 확인 또는 HW 블리더) 선행" 조건이 명시되지 않으면, ESD 상태 보드에서 Phase 1을 일찍 배포했을 때의 위험이 없다.

**추가 누락**: `TDC_TOUCH_BOOT_WAIT_MS` define이 49 종합 §3 빌드가드 세트에 없다. timeout 값이 없으면 폴백 경로 코드 자체를 작성할 수 없다. 미확정 상태임을 표기하더라도 define 이름이라도 예약해야 Phase 1 구현 시 참조할 수 있다.

**판정**: [치명] — ESD 환경에서 Phase 1 조기 배포 시 UX 악화 위험이 블로킹 조건과 §8 미해결 표 어디에도 없다. 실측_B(방전 효과 확인)를 Phase 1 활성화 전 블로킹으로 이미 등록했음에도 이 상황이 왜 발생하는지 논거가 없어 구현자가 블로킹_B의 중요성을 과소평가할 수 있다.

## 4. 고위험 — 공장 캘리브 전제로 인한 All-or-Nothing 구조, 런타임 추정 기준값 대안 명시적 기각 없음

### 4-1. 49 종합의 처리

§1-1 층위 1(노터치 게이트): "Phase 2(EEPROM) 선행 필수"
§5 블로킹 전체 목록: 블로킹_A·B·C·D·E·F·G — 모두 해소 전 Phase 1 착수 불가 또는 Phase 2 착수 불가

### 4-2. 공격

48_대안비교 §공격_4가 제기한 "런타임 추정 기준값" 대안이 49 종합에서 명시적으로 기각되지 않았다. 49 종합은 이 공격을 언급 자체를 하지 않아 흡수·기각 모두 없다.

대안의 요지: 공장 캘리브레이션 없이 `FACTORY_NOTOUCH_COUNTS=0` 기본값 상태에서도, 부팅 후 일정 시간(예: 10초) counts 분포 관찰로 추정 기준값을 사용한 임시 게이트를 운용 → 공장 공정 확립 전에도 Phase 1이 부분 동작해 "무조건 RESEED"보다 낫다.

49 종합이 이 대안을 채택하지 않는 이유는 전혀 기술되지 않았다. 결과적으로:

- 현재 펌웨어에서 Phase 1을 활성화하려면 블로킹_A~G를 모두 해소해야 한다.
- 블로킹_C(CFX 파서 크기 확인)는 외부 코드 접근에 달려 있다.
- 이 중 하나라도 지연되면 Phase 1 전체가 동결된다.

"런타임 추정 기준값" 대안을 "공장값이 없으면 Cold-Start Ambiguity 근본 해소 불가"이유로 기각하는 것은 타당하지만, **"근본 해소가 아닌 현재 대비 확률적 개선"이라는 목표라면 유효하다**. 이 구분이 49 종합에 없다. 구현 우선순위를 정할 때 이 대안이 고려 대상임을 명시하지 않으면 "공장 공정 완료 전까지 아무것도 개선하지 않는" 전략적 선택으로 귀결된다.

**판정**: [고위험] — 49 종합은 All-or-Nothing 구조를 의도적으로 선택했는지, 대안을 검토하지 않아 우연히 그렇게 됐는지 불분명하다. 이 선택의 트레이드오프를 §8 미해결 또는 §7 달성도 표에 명시해야 한다.

## 5. 고위험 — Re-ATI 도입 비용·공장값-런타임 괴리 해소 방법 미기술

### 5-1. 49 종합의 처리

§4 Phase 3 계획:
> "R3_CHARGING: df_Connected=true 상태에서 30초 주기 Re-ATI"

§2-3 EEPROM 로드 경로(치명 결함 반영):
> "Phase 2 EEPROM 로드 경로를 명시 추가"

### 5-2. 공격

48_대안비교 §공격_2가 발굴한 핵심 문제가 49 종합에서 해소되지 않았다:

**문제**: Phase 3에서 Re-ATI를 활성화하면 MULT/COMP가 갱신된다. 이때 공장 캘리브레이션 시점의 EEPROM 저장 MULT/COMP와 런타임 Re-ATI 결과가 달라진다. 다음 부팅에서 49 종합 §2-3이 설계한 EEPROM 로드 경로가 실행되면, 가장 최근 Re-ATI 결과(환경 적응값)가 아닌 공장 캘리브레이션 값이 로드된다.

즉 Re-ATI가 환경 적응을 위해 MULT/COMP를 갱신했어도, **재부팅하면 공장값으로 되돌아간다**. 이것이 반복되면:
- 켜진 직후: 공장 MULT/COMP(구형) 적용
- 30초 후: Re-ATI → 현재 환경 MULT/COMP로 갱신
- 재부팅 시: 다시 공장 MULT/COMP로 리셋
- 30초 후: Re-ATI 반복

사용자 경험: 부팅 직후 30초 동안 환경 드리프트가 누적된 공장값 기반으로 동작 → 감도 편차. Re-ATI의 환경 적응 효과가 재부팅 시마다 소멸한다.

49 종합 §2-3이 "EEPROM 로드 경로"를 추가했으나, 로드하는 값이 공장값인지 최근 Re-ATI 결과인지 설계가 없다. Phase 4(크래들 Re-ATI + EEPROM 저장)가 이 문제를 해소하는 구조인데, Phase 4가 미구현 상태에서 Phase 3만 활성화하면 위 문제가 발생한다.

**추가 누락**: EEPROM에 저장하는 데이터 구조체에 "공장값"과 "최근 Re-ATI 값"을 어떻게 구분할지 49 종합에 없다. 단일 구조체(`tdc_touch_calib_t`)로 관리하면 공장값이 Re-ATI 결과로 덮어씌워지고, 다음 부팅 시 "공장값"이라 믿고 로드한 것이 사실 환경-특화 값이 된다.

**판정**: [고위험] — Phase 3·4 상호 의존 관계와 EEPROM 데이터 구조 설계가 49 종합 어디에도 없다. EEPROM 로드 경로만 추가하고 저장 데이터의 의미 분리(공장값 vs 런타임 ATI 결과)를 정의하지 않으면 Phase 2·3·4가 일관성 없이 동작한다.

## 6. 고위험 — Phase 0 포화 감지 임계 define 초기값 여전히 미기술

### 6-1. 49 종합의 처리

§3 빌드가드 최종 세트:
```c
#define TDC_TOUCH_SATURATE_DETECT_ENABLE     1u
#define TDC_TOUCH_SATURATE_MAX_COUNTS        0u  /* [확정 필요] 데이터시트+실측_E 후 교체 */
```

### 6-2. 공격

46_할루시 §약점_5가 발굴한 문제가 49 종합에서 **형식은 반영됐으나 실질이 해소되지 않았다**.

`SATURATE_MAX_COUNTS=0u`인 상태에서 `SATURATE_DETECT_ENABLE=1u`이면:
- 포화 감지 로직: `if (counts >= SATURATE_MAX_COUNTS)` → `if (counts >= 0u)` → **항상 참** → 모든 counts에서 포화 경보 발행
- 또는 `if (counts >= SATURATE_MAX_COUNTS)`에서 MAX_COUNTS=0이면 포화 조건이 의미를 잃어 dead code 또는 무한 경보

49 종합이 `0u`를 "데이터시트+실측_E 후 교체"라고 주석을 달았으나, Phase 0 "항상 ON"이 즉시 적용되는 상태에서 `MAX_COUNTS=0u`로 출하하면 코드가 의미 없이 동작하거나 오경보를 발생시킨다.

올바른 처리는 다음 중 하나:
- Option A: `SATURATE_DETECT_ENABLE=0u` (기본 비활성) + 실측_E 완료 후 1u로 + MAX_COUNTS 설정
- Option B: `SATURATE_DETECT_ENABLE=1u` + `SATURATE_MAX_COUNTS`를 데이터시트 기재 최대값(예: 4095 for 12비트, [확정 필요])으로 초기화 + [확정 필요] 표기

49 종합은 두 옵션을 선택하지 않고 `ENABLE=1u + MAX_COUNTS=0u` 조합을 그대로 최종 세트로 확정했다. 이 조합은 실제 컴파일 시 포화 감지 코드가 `0u`를 임계로 사용하게 된다.

**추가 함의**: Phase 0 "항상 ON"을 49 종합 §4 Phase 0 설명에서 다시 확인했으나, 이 §4 설명에도 임계값 초기화 방법이 없다. Phase 0 구현자가 `MAX_COUNTS=0u`를 그대로 두면 코드 오동작 가능성이 잔존한다.

**판정**: [고위험] — 빌드가드 세트의 ENABLE=1u + MAX_COUNTS=0u 조합이 실제 코드에서 오동작을 일으킬 수 있다. Phase 0 구현 게이트에 "MAX_COUNTS 초기값 결정 선행" 또는 "ENABLE 기본값을 0u로 변경"을 명시해야 한다.

## 8. 미검증 주장 추가 발굴

### 8-1. Phase 1 BOOT_WAIT_MS define 존재 전제 [할루시 가능성]

49 종합 §4 Phase 1에서 "timeout 시 저신뢰 폴백 RESEED + RTT 경보"를 기술했으나, `TDC_TOUCH_BOOT_WAIT_MS`(또는 동등 define)가 49 종합 §3 빌드가드 세트에 없다. 이 define 없이 timeout 로직을 구현할 수 없는데, 종합이 이 define을 전제한 채 timeout 경로를 설계했다면 미완성 설계다.

### 8-2. EEPROM 데이터 구조체 크기 · 파서 호환성 전제 [실측 의존 미표기]

49 종합 §2-3 EEPROM 로드 경로 코드 예시에서 `tdc_touch_calib_load_eeprom(&calib)` 함수를 전제했으나, EEPROM 구조체 크기와 CFX 파서 크기 호환성은 블로킹_C(CFX 파서 크기 확인)로 여전히 미해소다. 코드 예시가 마치 구현 가능한 것처럼 기술됐으나 블로킹_C 해소 전에는 구조체 필드 수 자체가 확정 불가다. [확정 필요] 표기가 코드 예시 내에 없다.

### 8-3. Re-ATI 비블로킹 "다음 폴링에서 ATI_Active 확인" 방법의 force_window_open 비용 미계상

49 종합 §2-4 R3_CHARGING 최소 명세에서 "비블로킹 선호 — re_ati_trigger() 발행 후 다음 폴링에서 ATI_Active 확인"이라고 했다. 그런데 ATI_Active 확인을 위한 status read는 force_window_open을 수반한다(명제_G 확정, 최악 130ms). 비블로킹 선호라 했지만 폴링마다 130ms 비용이 발생하는 구조는 Event Mode 전환 없이는 해소되지 않는다. "비블로킹"이 I/O 비용을 해소하는 것처럼 암시돼 있으나 실제 통신 비용은 유지된다. [추정] 표기 필요.

## 10. 핵심 6줄

1. **RTT_TUNING 분기 + 공장값 게이트 신뢰도 충돌이 "고위험 등록"으로 끝났다** — 49 종합 §9에 등록만 됐고 해소 방향(#error 차단·빌드가드 추가·기준값 재환산 중 선택)이 전혀 없다. Phase 1 또는 Phase 2 착수 전 블로킹으로 격상하고 #error `RTT_TUNING && NOTOUCH_GATE` 가드를 §3 빌드가드 세트에 추가해야 한다.
2. **CH_TIMEOUT(stuck-touch 가드) 재활성 검토가 §8 미해결 표에 1줄로만 있고 Phase 계획 본문과 빌드가드 세트에 없다** — 무한 터치 방어의 핵심 메커니즘이 구현 계획에서 누락됐으며, 이중 차단 이유 미명시 상태에서 재활성하면 회귀 위험이 있다.
3. **ESD 환경에서 Phase 1 게이트 폴백이 현재 무조건 RESEED와 동일한 최종 오작동을 낳는다** — Phase 1 조기 배포 시 ESD 환경 사용자는 기존보다 UX가 나빠지는 케이스가 §8 미해결 표나 블로킹 테이블에 없다. 방전 실측(블로킹_B) 중요성 논거가 부재한 채 등록만 됐다.
4. **공장 캘리브레이션 All-or-Nothing 구조의 대안(런타임 추정 기준값)이 명시적으로 기각되지 않았다** — 블로킹_C(CFX 확인) 지연 시 Phase 1 전체가 동결되는 리스크를 피할 중간 경로가 채택도 기각도 되지 않은 채 49 종합을 통과했다.
5. **Phase 3 Re-ATI가 MULT/COMP를 갱신하나 다음 부팅 시 공장값으로 리셋되는 구조적 순환이 미설계다** — EEPROM에 공장값과 런타임 Re-ATI 결과를 어떻게 구분·저장·로드할지 데이터 구조가 없어, Phase 2·3·4가 서로 일관성 없이 동작할 수 있다.
6. **Phase 0 SATURATE_DETECT_ENABLE=1u + SATURATE_MAX_COUNTS=0u 조합이 실제 코드에서 "항상 포화" 오경보를 일으킬 수 있다** — 46_할루시 약점_5가 발굴한 이 문제가 49 종합에서 형식 반영됐으나(0u로 표기), ENABLE=1u 기본값이 유지돼 잠재적 오동작 조합이 최종 빌드가드 세트에 남아 있다.
