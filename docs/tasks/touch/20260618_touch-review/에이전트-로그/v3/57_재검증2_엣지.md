# 57 — 재검증 라운드2 (엣지 관점) — 49_종합-재검증1 adversarial 공격

**TL;DR**: 49_종합-재검증1을 엣지 관점에서 재공격. 신규 약점 5건 발굴 — 치명 2건(wait_re_ati_done() 내 WDT SYS_WATCHDOG_REFRESH 실제 미삽입 + `TDC_TOUCH_RTT_TUNING` 분기가 EEPROM 로드 경로 설계와 구조적으로 충돌), 고위험 2건(Phase 4 삽입점 main.c:742 주변 코드 구조가 종합 기술과 다름 + `s_boot_touch_ignore` 해제 타이밍 충돌 시나리오 미해소), 중위험 1건(ATI_FULL_ENABLE=1 시 re_ati_trigger() SYSTEM_CONTROL write가 기존 CH_TIMEOUT 비활성화 write와 레지스터 충돌). 수렴 판정: **부분 수렴 유지** — 아키텍처 원리 기각 없음, 구현 전 해소 필수 신규 2건 추가.

## 2. 신규 약점 발굴 — 49가 놓친 엣지

### 신규_A — `wait_re_ati_done()` 내 `SYS_WATCHDOG_REFRESH()` 실제 미삽입 [치명]

**49 §4 Phase 3 주장**: "wait_re_ati_done() 내 SYS_WATCHDOG_REFRESH() 추가 — '명시 필요' 수준이 아닌 **함수 수정 필수 선행 사항**으로 격상."

**코드 ground truth 확인** (`iqs323.c:581~623`):

```c
static bool wait_re_ati_done(void)
{
    for (int i = 0; i < 10; i++)
    {
        if (!read_register(...))
        {
            Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
            continue;
        }
        /* ... ATI_ERROR 체크 ... */
        /* ... ATI_EVENT 체크 → return true ... */
        Sys_Delay(TDC_DRV_IQS323_DEFAULT_DELAY_MS * 100);
    }
    return false;
}
```

현재 코드에 `SYS_WATCHDOG_REFRESH()` 호출이 **단 한 줄도 없다**. 10회 × 100ms 딜레이 = 최대 1초. 게다가 49 §4 Phase 3는 "최악 ~1.9초(Sys_Delay 1초 + force_window_open 포함)"로 기술했다. 즉 blocking 구간이 최악 ~1.9초이며 WDT 갱신이 없다.

**엣지 공격**: 49는 "함수 수정 필수 선행 사항으로 격상"이라고 했으나, 이것은 **구현 계획 수준의 선언**이지 코드에 반영된 사실이 아니다. 이 함수는 현재 `ATI_CALIB_MODE` 경로(`iqs323.c:860`)에서 이미 호출 중이다. `ATI_CALIB_MODE` 운용 중 WDT 리셋이 발생했다면 이미 현장 버그가 잠재한다. 49가 "필수 선행"으로 격상했다는 선언이 Phase 1~4 어느 단계에서 실제로 코드 수정이 이뤄지는지 Phase 계획에 명시되지 않았다.

더 나아가 49 §3 빌드가드 세트에 `TDC_TOUCH_ATI_CALIB_MODE` 관련 정의가 없다 — 기존 `ATI_CALIB_MODE=1` 빌드에서 이미 돌아가고 있는 `wait_re_ati_done()` 경로의 WDT 위험이 Phase 0 이전부터 존재한다.

**요구 조치**: Phase 0 즉시 실행 항목으로 "wait_re_ati_done() 내 SYS_WATCHDOG_REFRESH() 삽입(루프 본체 내, Sys_Delay 직전)" 추가. `ATI_CALIB_MODE` 경로 포함 즉시 수정 필요.

### 신규_B — `TDC_TOUCH_RTT_TUNING` 분기가 EEPROM 로드 경로 설계와 구조적으로 충돌한다 [치명]

**49 §2-3 EEPROM 로드 경로 코드 스니펫**:

```c
/* tdc_drv_iqs323_apply_settings() 내 수정 흐름 */
#if TDC_TOUCH_FACTORY_CALIB_ENABLE == 0
  if (tdc_touch_calib_load_eeprom(&calib)) {
    s_mult_lsb = calib.mult_lsb;
    s_comp_lsb = calib.comp_lsb;
  }
#endif
write_ati_compensation();  /* 항상 실행 */
```

**코드 ground truth 확인** (`iqs323.c:705~730`):

`write_ati_compensation()` 내부에는 `#if TDC_TOUCH_RTT_TUNING` 분기가 이미 존재한다. `RTT_TUNING=1`일 때 MULT/COMP 소스는 `s_tdc_normal_tuning.ati_valid ? s_tdc_normal_tuning.mult_lsb : TDC_DRV_IQS323_ATI_MULT_LSB`다 — 즉 **RTT 런타임 튜닝 구조체** 우선이다.

**엣지 공격**: 49의 EEPROM 로드 경로는 `s_mult_lsb = calib.mult_lsb`로 정적 변수를 설정하고 `write_ati_compensation()`이 이를 사용한다고 가정한다. 그런데 현재 `write_ati_compensation()` 내부에는 `s_mult_lsb` 같은 변수를 참조하는 구조가 없다 — RTT_TUNING 빌드에서는 `s_tdc_normal_tuning` 구조체를, 비-RTT 빌드에서는 컴파일 타임 상수를 직접 write한다.

49의 EEPROM 로드 설계가 실제 동작하려면:

1. **비RTT 빌드**: `write_ati_compensation()` 내부 상수를 런타임 변수로 교체 → 함수 시그니처 또는 전역 변수 구조 변경 필요 (현재 함수는 `static bool write_ati_compensation(void)` — 인자 없음)
2. **RTT_TUNING 빌드**: `s_tdc_normal_tuning` 구조체에 EEPROM 로드값을 주입하는 경로가 필요 — 현재 `s_tdc_normal_tuning`은 RTT 세션에서만 populate된다.

어느 경로도 49의 코드 스니펫(`s_mult_lsb = calib.mult_lsb`→`write_ati_compensation()`이 이 값 사용)으로 달성되지 않는다. 49의 스니펫은 존재하지 않는 변수(`s_mult_lsb`)를 참조하는 [추정] 수준의 의사 코드이며, 실제 `write_ati_compensation()` 내부 구조와 맞지 않는다.

**45_회귀의 회귀_2와 연결**: RTT_TUNING=1 환경에서 EEPROM 공장값이 `s_tdc_normal_tuning` 구조체와 무관하게 write되면, RTT_TUNING 활성 시 게이트 기준과 실제 IC MULT/COMP가 불일치한다. 49는 회귀_2(RTT_TUNING 분기 누락)를 "신규_TDC_RTT_TUNING — 고위험, 2차 재검증에서 추가 공격 대상"(§9 신규 약점 표)으로만 분류했고, 실질 설계 결함으로 반영하지 않았다.

**요구 조치**:
1. `write_ati_compensation()`을 실제로 EEPROM 로드값을 수용할 수 있도록 함수 시그니처 또는 내부 변수 구조 변경 설계 명시(Phase 2 착수 전).
2. RTT_TUNING 빌드에서 EEPROM 로드값이 `s_tdc_normal_tuning` 구조체와 동일 경로를 타도록 설계하거나, RTT_TUNING + FACTORY_CALIB 동시 활성 시 #error 차단.

### 신규_C — 49 §2-3 EEPROM 로드 스니펫의 `s_mult_lsb`·`s_comp_lsb` 변수가 현재 코드에 존재하지 않는 할루시네이션이다 [고위험]

**49 §2-3 코드**:
```c
s_mult_lsb = calib.mult_lsb;
s_comp_lsb = calib.comp_lsb;
/* write_ati_compensation()이 이 값을 사용하도록 전달 */
```

**코드 ground truth**: `iqs323.c` 전체에 `s_mult_lsb`, `s_comp_lsb`라는 정적 변수가 **존재하지 않는다**. RTT_TUNING 경로에는 `s_tdc_normal_tuning.mult_lsb`가 있지만, 비RTT 경로에는 컴파일 타임 상수만 있고 런타임 변수가 없다.

49의 스니펫은 "이 변수들을 새로 추가해야 한다"는 의미였을 수 있으나, `write_ati_compensation()이 이 값을 사용하도록 전달`이라는 주석은 이미 이 변수를 참조하는 코드가 있음을 암시한다. 신규 변수 추가 + 함수 내부 수정이 필요하다는 설계 의무를 과소 기술한 것이다.

이것은 구현 시 착수하면 바로 드러나는 결함이지만, 설계 문서 수준에서 "로드 경로 있음"으로 수렴 처리되면 Phase 2 구현 시 불필요한 재설계가 발생한다.

**요구 조치**: §2-3 보완 — EEPROM 로드 설계에 "(1) s_ati_override 신규 구조체 추가, (2) write_ati_compensation() 내 RTT_TUNING 분기 병렬로 FACTORY_CALIB 분기 추가, (3) RTT_TUNING과 FACTORY_CALIB 동시 활성 빌드가드 처리" 3단계 명시.

### 신규_D — Phase 4 삽입점 `main.c:742` 코드 확인 결과, 종합의 기술이 실제 코드와 부분 불일치한다 [고위험]

**49 §4 Phase 4**: "삽입점 라인 번호 확인: 'main.c:742' 환각 가능성 — 착수 전 `func_cradle_lid_closed_loop()` 호출 위치 grep 재확인(확인_8 신규)."

**코드 ground truth 직접 확인** (`main.c:742`):

```
742:            led_force_fade_off(); /* fade-out ISR 완료 후 LED 완전 소등 */
743:            func_cradle_lid_closed_loop();
```

즉 main.c:742가 `led_force_fade_off()` 호출이고, main.c:743이 `func_cradle_lid_closed_loop()` 호출이다. "742 앞, led_force_fade_off() 직후"라는 기술은 삽입점으로 743 직전(742와 743 사이)을 의미하므로 라인 번호 자체는 실제 코드와 **1줄 오차**로 근사적으로 맞다. 따라서 "742 환각 가능성"으로 블로킹 처리한 것은 과도한 경보였다.

그러나 진짜 문제는 다른 곳에 있다:

**엣지 공격**: `func_cradle_lid_closed_loop()` 진입 직전(main.c:742~743 사이)에 Phase 4 Re-ATI를 삽입하는 설계는 다음을 전제로 한다:
- 이 시점에 충전기 연결(`df_Connected`) 상태
- 터치 IC IQS323이 정상 폴링 중(터치 폴링 loop 내에서 뚜껑 닫힘을 감지해 이 위치에 도달)
- 이 위치는 폴링 루프 **안**인가 **밖**인가?

`main.c:742~743` 주변 맥락 없이는 이 호출이 폴링 루프 내부인지, 폴링 루프를 탈출한 후 메인 루프에서 호출되는지 알 수 없다 [확정 필요]. 만약 폴링 루프 **외부**에서 호출된다면, 이 시점에 IQS323은 이미 폴링이 멈춘 상태일 수 있고, Re-ATI 삽입 전 force_window_open 비용이 발생한다.

49 §4 Phase 4는 "진입 시점 노터치 게이트 재확인"만 명시했고, 이 호출 위치가 폴링 루프 내/외 여부에 따른 I2C 윈도우 상태를 별도 확인 항목으로 넣지 않았다.

**요구 조치**: 확인_8에 "func_cradle_lid_closed_loop() 호출 위치가 tdc_touch_process() 폴링 루프 내부인지 외부인지 + 이 시점 IQS323 통신 윈도우 상태" 항목 추가.

### 신규_E — `s_boot_touch_ignore`와 노터치 게이트 해제 타이밍 충돌 시나리오가 확인_10으로 명시됐으나 실제 코드 구조와 조화되는 설계가 없다 [고위험]

**49 §4 Phase 1·§6 확인_10**: "`s_boot_touch_ignore`와 노터치 게이트 해제 조건 정합성 — 올바른 RESEED 후 억제 구간 발생 방지(45_회귀_3·46_약점_6)."

이 항목을 "확인_10"으로 등록하고 수렴 처리했으나, 실제 해소 설계가 없다.

**엣지 공격**: 두 가드의 동시 활성 시나리오를 49가 구체적으로 기술하지 않았다. 실제 코드 흐름:

1. 부팅 → `apply_settings()` → `write_ati_compensation()` → 노터치 게이트 검사(Phase 1 활성화 후) → 통과 → `RESEED` 발행
2. 같은 `apply_settings()` 완료 후 `tdc_touch.c`의 READY 전이 시점에 `s_boot_touch_ignore` 평가
3. RESEED 직후 Race — 게이트 통과 직후 터치 발생 → `s_boot_touch_ignore` 아직 활성 상태

이 상태에서:
- 노터치 게이트: 통과(RESEED 발행 완료)
- `s_boot_touch_ignore`: READY 전이 후 TOUCH 감지 → 폴링 억제

두 가드가 모두 정상 동작하더라도, `s_boot_touch_ignore` 해제 조건이 "TOUCH가 해제될 때"인지 "일정 시간 후"인지 코드 확인 없이 알 수 없다. 만약 "TOUCH 해제 후"라면, race로 LTA가 약간 오염된 상태에서 `s_boot_touch_ignore`가 해제되고 → TOUCH가 해제되면 counts 상승 → delta 감소 → 정상 복귀. 이 경로에서 두 가드는 **상보적으로 동작**한다.

그러나 노터치 게이트 timeout 폴백(5초 대기 후 저신뢰 RESEED)이 발동한 경우:
- 폴백 RESEED 발행 → LTA 오염(터치 counts로 seed)
- `s_boot_touch_ignore`: 동시에 TOUCH 감지 → 폴링 억제
- 폴링이 억제된 상태에서 LTA IIR이 복귀 방향으로 동작하는가? → 폴링이 없으면 counts 갱신도 없고 IIR도 돌지 않는다 [추정] → LTA 오염이 복구되지 않은 채 `s_boot_touch_ignore` 해제 시 false touch 발생 가능

이 시나리오는 49 어디에도 기술되지 않았다. 확인_10은 "해제 조건 정합성 확인"이라고만 했고, 폴백 RESEED 발동 시 두 가드의 상호작용 결과를 분석하지 않았다.

**요구 조치**: 확인_10에 "timeout 폴백 RESEED + s_boot_touch_ignore 동시 활성 시 LTA IIR 복구 경로 분석" 항목 추가. `s_boot_touch_ignore` 해제 조건(touch.c:323/352 코드 read) 확인 후 두 가드 해제 타이밍 명시.

### 신규_F — `re_ati_trigger()` SYSTEM_CONTROL write가 CH_TIMEOUT 비활성화 write와 같은 레지스터를 공유한다 [중위험]

**49 §4 Phase 1**: "CH_TIMEOUT 재활성 여부 검토 추가 필요 (§8 미해결)" — 미해결로만 기록.

**코드 ground truth**:

```c
/* re_ati_trigger() — iqs323.c:569~579 */
reg.bytes[0]            = TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL;
reg.bytes[1]            = 0x00;
reg.bytes[2]            = 0x00;
reg.elements.lsb.re_ati = TDC_DRV_IQS323_TRIGGER_RE_ATI;
return write_register(reg.bytes[0], reg.bytes[1], reg.bytes[2]);

/* CH_TIMEOUT 비활성화 — iqs323.c:1155 */
write_register(TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL, 0x00, 0x07);
```

두 write 모두 `TDC_DRV_IQS323_REG_ADDR_SYSTEM_CONTROL`(0xD0 추정)에 write한다.

**엣지 공격**: `re_ati_trigger()`는 `lsb.re_ati` bit만 세트하고 MSB는 0x00으로 write한다. CH_TIMEOUT 비활성화는 MSB=0x07(ch0/ch1/ch2_timeout_disable 3비트)이다.

Phase 3에서 `re_ati_trigger()` 호출 시 SYSTEM_CONTROL MSB를 0x00으로 write하면 **기존에 설정된 CH_TIMEOUT 비활성화(0x07)가 초기화**된다 — 즉 Re-ATI 트리거 후 CH_TIMEOUT이 다시 활성화되어 stuck-touch 시 IC가 auto-Re-ATI를 발동한다. 현 펌웨어는 "ATI Mode=Disabled + CH_TIMEOUT 이중 차단"을 명시(iqs323.c:1152 주석)했는데, Re-ATI 활성화 경로(Phase 3)에서 이 이중 차단이 부분 해제된다.

49 §8 미해결 표에 "stuck-touch(CH_TIMEOUT) 처리 — CH_TIMEOUT 이중 차단 유지 이유 미명시"가 있지만, **Re-ATI 트리거가 CH_TIMEOUT 비활성화를 덮어쓰는 race 경로**는 기술하지 않았다.

Phase 3 설계에서:
- ATI_FULL_ENABLE=1 → ATI_SETUP을 Full로 write → CH_TIMEOUT은 ATI Mode=Full 환경에서 어떻게 동작해야 하는가? 데이터시트 §5.10 CH_TIMEOUT with ATI Full 모드 상호작용을 확인해야 한다 [확정 필요].
- `re_ati_trigger()` 내부 MSB=0x00 write 후 CH_TIMEOUT 비활성화(0x07)를 재write해야 하는가?

**요구 조치**: Phase 3 구현 시 `re_ati_trigger()` 함수가 SYSTEM_CONTROL MSB를 0x00으로 덮어쓰는 부작용 확인 후, Re-ATI 트리거와 CH_TIMEOUT 비활성화의 순서·공존 설계 명시(확인_11 신규).

## 6. 핵심 6줄

1. **wait_re_ati_done() 내 SYS_WATCHDOG_REFRESH() 가 현재 코드에 전혀 없다** — `iqs323.c:581~623` 직접 확인. 최대 1초(~1.9초) blocking 중 WDT 갱신 0회이며, 현재 `ATI_CALIB_MODE` 경로(`iqs323.c:860`)에서 이미 호출 중이므로 잠재 현장 버그. **Phase 0 즉시 삽입 필수**(신규_A).
2. **49 §2-3 EEPROM 로드 스니펫의 `s_mult_lsb`·`s_comp_lsb`는 현재 코드에 존재하지 않는 할루시네이션이다** — `write_ati_compensation()`은 인자 없는 `void` 함수이며 내부에 해당 변수가 없음. RTT_TUNING 분기(`iqs323.c:705~730`)와 공존 설계 없이 EEPROM 로드 경로를 구현하면 RTT_TUNING 빌드에서 즉시 경로 충돌 발생(신규_B·C).
3. **`re_ati_trigger()`가 SYSTEM_CONTROL 레지스터를 MSB=0x00으로 write해 기존 CH_TIMEOUT 비활성화(0x07)를 덮어쓴다** — Phase 3 Re-ATI 활성화 후 매 Re-ATI 트리거마다 CH_TIMEOUT이 재활성화돼 stuck-touch 시 IC 자동 Re-ATI가 발동될 수 있다. 현 "이중 차단" 설계가 Phase 3 도입 시 부분 해제된다(신규_F).
4. **Phase 4 삽입점 main.c:742 라인 번호는 근사 정확(743에 호출 확인)이나, 이 호출이 tdc_touch_process() 폴링 루프 내부인지 외부인지 미확인** — 폴링 루프 외부라면 Re-ATI 삽입 전 force_window_open 비용 + I2C 윈도우 상태 재개방이 필요하며, 49는 이를 확인_8에 포함하지 않았다(신규_D).
5. **timeout 폴백 RESEED + s_boot_touch_ignore 동시 활성 시 폴링이 억제된 채 LTA 오염 상태 지속 가능** — 폴링이 없으면 counts 갱신도 없고 LTA IIR도 돌지 않아 자기치유 경로가 차단됨. 49의 확인_10은 "해제 조건 정합성"만 명시하고 이 경로를 분석하지 않았다(신규_E).
6. **수렴도 판정: 부분 수렴 유지** — 아키텍처 원리는 2차 재검증에서도 기각되지 않았으나, Phase 0 즉시 실행(WDT 삽입) 1건과 Phase 2 착수 전 설계 확정(EEPROM 로드·RTT_TUNING 충돌) 필수 항목이 신규 추가되어 구현 전 해소 총 9건으로 증가.
