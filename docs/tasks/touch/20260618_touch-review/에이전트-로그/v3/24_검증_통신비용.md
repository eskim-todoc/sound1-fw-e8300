# 24_검증_통신비용 — adversarial: force_window_open 비용·통신 타이밍 공격

**TL;DR**: 계획 11~18이 RESEED 게이트·Re-ATI·사후검증·크래들 훅 설계에서 I2C 통신 비용(force_window_open 당 0.1~45ms)을 일관되게 과소평가했다. 핵심 결함 6개: ① 게이트 루프의 실제 블로킹 시간이 명세 5초를 최대 9배 초과할 수 있음, ② 노터치 게이트 사후 검증 1회에 force_window_open×2=최대 90ms 소요, ③ 크래들 Re-ATI 전 discharge_crx0 삽입 시 순서 역전이 비용 중복 유발, ④ BETA write 신설 시 apply_settings 내 추가 force_window_open 연쇄가 분석 없이 계획됨, ⑤ 공장 캘리브레이션 저장 함수의 50ms 안정화 대기가 EEPROM write timeout(TDC_TOUCH_INIT_TIMEOUT_MS)과의 중첩 위험을 무시함, ⑥ 부팅 게이트 poll_ms=50ms로 설정했으나 IQS323 측정 사이클(T_주기 최대 16ms)보다 커서 샘플이 IIR 수렴 전 counts를 반복 관찰할 수 있음.

---

## 0. 검증 기준

v2 명제_G 확정값: `force_window_open` 비용 = **0.1~45ms** (데이터시트 §8.13). `read_register`는 주소-write STOP 후 re-open → data-read 패턴이므로 **호출 1회 = force_window_open 2회** 발생 가능 (`10_rdy-window-timing.md §3.3`). 최악 시나리오 = 1회 read_register에 **최대 90ms**. 이 수치를 기준으로 각 계획 파일의 루프·함수를 역산해 실제 블로킹 시간을 재계산한다.

---

## 1. 결함_1: 게이트 루프 블로킹 시간 — 명세 5초가 최대 9배 초과

**공격 대상**: `14_계획_노터치게이트코드.md §2-3` — `tdc_drv_iqs323_reseed_with_gate()`

### 1-1. 계획의 주장

```c
const uint32_t poll_ms = 50u;   /* 게이트 폴링 간격 */
```

`elapsed_ms += poll_ms`로 타임아웃 `TDC_TOUCH_NO_TOUCH_TIMEOUT_MS = 5000ms`를 측정하며, 5000 / 50 = 100회 반복 후 폴백.

### 1-2. 실제 비용 역산

루프 1회 실제 비용:
```
read_ch0_filtered_counts() 1회
  = read_register() 1회
  = force_window_open() (0.1~45ms) × 2   [주소-write STOP + data-read re-open]
  + I2C 트랜잭션 (~1ms)
  최악 = 45 + 45 + 1 ≈ 91ms
```

`poll_ms` 대기는 그 위에 **추가**된다:
```
루프 1회 실제 소요 = 최악 91ms + poll_ms 50ms = 141ms
```

100회 루프 최악 총 소요:
```
141ms × 100 = 14,100ms ≈ 14.1초
```

**명세 타임아웃 5초가 최악 14.1초로 약 2.8배 초과된다.** [확정 필요: T_주기 실측]

그런데 `elapsed_ms` 측정이 `elapsed_ms += poll_ms`(고정 증가)이지, 실제 경과 시간을 `ci_timer_get_tick()`으로 측정하는 것이 아니다. force_window_open 대기 시간은 `elapsed_ms`에 **포함되지 않는다.** 타임아웃 카운터가 실제 시간과 최대 2.8배 괴리되어, 실제 14.1초를 돌고 있는데 코드는 5초 경과로 판단하지 못한다.

> [!IMPORTANT]
> **`elapsed_ms += poll_ms` 방식은 force_window_open 대기를 누락한다.** 실제 경과를 `ci_timer_get_tick()` 기반으로 측정해야 한다. `11_계획_부팅시퀀스.md`의 손뗌 대기 루프도 동일 패턴(`reseed_with_wait_recovery`)이므로 동일 결함이 전파된다.

### 1-3. 시스템 영향

부팅 초기화 지연이 최악 14초 이상 → `SYS_WATCHDOG_REFRESH()` 호출은 루프 안에 있으나, WDT timeout 설정값이 force_window_open 블로킹 중 리프레시 간격을 보장하는지 [확정 필요]. `SYS_WATCHDOG_REFRESH()`가 poll_ms 대기 루프 안에서만 호출된다면, force_window_open busy-wait 45ms 중 WDT가 리프레시되지 않는다.

## 2. 결함_2: 사후 검증 함수의 숨겨진 통신 비용

**공격 대상**: `11_계획_부팅시퀀스.md §3-1` `tdc_drv_iqs323_reseed_with_verify()`, `16_계획_사후검증.md §1-2` `reseed_with_post_verify()`

### 2-1. 계획의 주장

RESEED 발행 직후 `read_ch0_filtered_counts()`로 counts를 재확인해 race를 감지하고, 최대 3회 재시도.

### 2-2. 재시도 1회 실제 비용

```
RESEED write_register():
  = force_window_open (0.1~45ms) + 3-byte write (~0.6ms)
  최악 ≈ 45.6ms

counts 재확인 read_register():
  = force_window_open×2 (최악 90ms) + I2C (~1ms)
  최악 ≈ 91ms

Sys_Delay(RETRY_DELAY_MS=10ms)

재시도 1회 최악 = 45.6 + 91 + 10 = 146.6ms
```

최대 3회 재시도 최악 = 146.6 × 3 = **440ms**

**계획은 "사후 검증 즉시 재확인"이라 설명하지만 최악 0.44초가 소요된다.** 이 지연 동안 사용자가 손을 뗀 뒤 다시 얹는 시나리오(race 확률 증가)가 고려되지 않았다. 재시도가 race를 "치유"하는 것이 아니라 오히려 race 발생 윈도우를 늘릴 수 있다.

### 2-3. `16_계획_사후검증.md`의 추가 오류

`RESEED_RETRY_DELAY_MS = 10ms` 근거로 "LTA IIR 최소 수렴 대기"를 들었다. 그러나:

- Beta=0(현재) → LTA IIR 갱신 없음(`15_계획_드리프트LTA.md §1.3`)
- 10ms 딜레이는 RESEED 후 IC 내부 LTA 갱신이 아니라 단순 대기일 뿐
- IQS323은 RESEED 직후 다음 측정 사이클(최대 16ms, DS §3.4) 이후 LTA를 실제로 갱신 → **10ms 딜레이는 1 측정 사이클도 보장하지 않는다** [확정 필요: T_주기 실측]

## 3. 결함_3: 크래들 훅 방전→Re-ATI 순서의 통신 비용 중복

**공격 대상**: `13_계획_크래들훅.md §3-4` Phase 2 및 `17_계획_방전트랙.md §5-2`

### 3-1. 계획의 주장

`main.c:742` 앞에:
```c
tdc_drv_iqs323_discharge_crx0();   /* 방전 먼저 */
tdc_drv_iqs323_cradle_re_ati();    /* 이후 Re-ATI */
```

방전 → Re-ATI 순서로 묶어 "구현 효율 확보"가 가능하다고 서술.

### 3-2. 실제 통신 비용 분석

`discharge_crx0()`:
```
write_register(0x30, 0x02, 0x00):  force_window_open (최악 45ms) + write (~0.6ms)
write_register(0x30, 0x01, 0x01):  force_window_open (최악 45ms) + write (~0.6ms)
최악 = 91.2ms
```

`cradle_re_ati()` = `re_ati_trigger()` + `wait_re_ati_done()`:
```
re_ati_trigger(): write_register 1회 → 최악 45.6ms
wait_re_ati_done(): 10회 폴링 × read_register 1회
  = 10 × (force_window_open×2 최악 90ms + I2C 1ms)
  = 10 × 91ms = 910ms  [추정]
ATI Mode=Disabled 복원: write_register 1회 → 최악 45.6ms
최악 = 45.6 + 910 + 45.6 = 1001ms
```

**방전 + Re-ATI 합산 최악 = 91.2 + 1001 = 1092ms**

그런데 방전 직후 `discharge_crx0` 복원 write(`0x30, 0x01, 0x01`)가 윈도우를 닫고, 즉시 Re-ATI trigger write가 윈도우를 다시 열어야 한다. **force_window_open이 연쇄로 2회 발생한다.** `17_계획_방전트랙.md`는 이 중첩 비용을 계산하지 않았다.

더 근본적으로: Re-ATI가 SENSOR0_SETUP 레지스터(0x30)를 내부적으로 갱신할 가능성이 있는데, 방전을 위해 `write_register(0x30, ...)` 직후 Re-ATI를 발행하면 방전 복원 설정이 Re-ATI에 의해 덮어써질 수 있다 [확정 필요: Re-ATI 시 0x30 레지스터 갱신 여부].

## 4. 결함_4: Beta write 신설 시 apply_settings 내 추가 force_window_open 연쇄 미분석

**공격 대상**: `15_계획_드리프트LTA.md §2-4` `write_filter_betas()`

### 4-1. 계획의 주장

`apply_settings()` 내 CH_TIMEOUT 비활성 직후에 `write_filter_betas()` 호출. NP LTA Beta·Fast Beta를 `write_register()` 1회로 설정.

### 4-2. apply_settings 내 누적 통신 비용

현재 `apply_settings()` 내 write_register 호출 체인 (`iqs323.c:1141~1155` 기준):
```
write_ati_compensation()   → write_register 여러 회 (MULT/COMP/ATI_SETUP 등)
RESEED write_register       → force_window_open 1회 이상
CH_TIMEOUT write_register  → force_window_open 1회 이상
[신규] write_filter_betas() → write_register 1~2회 추가 → force_window_open 2~4회 추가
```

**신규 Beta write는 각 write마다 force_window_open(최악 45ms)을 유발한다.** `15_계획_드리프트LTA.md`는 Beta write 1회의 I2C 트랜잭션 비용만 언급하고, write 사이 force_window_open 대기를 전혀 계산하지 않았다.

실제로 `write_filter_betas()`를 NP LTA Beta(0xB2)·Fast Beta(0xB4) 두 레지스터에 write한다면:

```
write_register(0xB2, ...): force_window_open (최악 45ms) + write (~0.6ms)
write_register(0xB4, ...): force_window_open (최악 45ms) + write (~0.6ms)
추가 최악 비용 = 91.2ms
```

`apply_settings()` 전체 최악 비용이 이미 수백 ms 수준인데 `write_filter_betas()`가 추가된다. 이 누적 비용이 **부팅 초기화 순서 상위 타임아웃**(`TDC_TOUCH_INIT_TIMEOUT_MS`, `12_계획_공장캘리저장.md §4-2`에서 동일 상수를 EEPROM write 타임아웃으로 사용)과 충돌 가능성이 있다.

## 5. 결함_5: 공장 캘리브레이션 저장 함수의 50ms 안정화 대기 + EEPROM write timeout 중첩

**공격 대상**: `12_계획_공장캘리저장.md §4-2` `tdc_drv_iqs323_calib_store()`

### 5-1. 계획의 주장

```c
/* 4. 안정화 대기 (~50ms) */
while ((ci_timer_get_tick() - t0) < 50) { SYS_WATCHDOG_REFRESH(); }

/* 5. noTouch Counts 읽기 */
if (!read_register(TDC_DRV_IQS323_REG_ADDR_CH0_FILTERED_COUNTS, &lsb, &msb))

/* 6. setReadWriteMapDataFlashCommand() */
while (!isReadWriteMapDataFlashCommandDone()) {
    SYS_WATCHDOG_REFRESH();
    if ((ci_timer_get_tick() - t0) > TDC_TOUCH_INIT_TIMEOUT_MS) { ... }
}
```

`t0`가 **안정화 대기 시작** 시점으로 초기화된 후, EEPROM write 타임아웃도 `t0` 기준으로 측정한다.

### 5-2. 결함: t0 재사용 버그

코드 §4-2를 상세히 보면:

```c
int t0 = ci_timer_get_tick();   /* 안정화 대기용 */
while ((ci_timer_get_tick() - t0) < 50) { SYS_WATCHDOG_REFRESH(); }

/* ... read_register 비용: force_window_open×2 최악 90ms ... */

/* t0를 재선언하지 않고 아래 EEPROM 루프에서 동일 t0를 사용 */
int t0 = ci_timer_get_tick();   /* EEPROM write 타임아웃용 — 코드에서 재선언 */
```

계획 코드를 보면 §4-2의 두 번째 `int t0`가 EEPROM write 루프에서 재선언됐다. 이건 별도 변수이므로 겹치지 않는다. 그런데 **다른 결함이 있다:**

`noTouch Counts 읽기` 단계(5단계)에서 `read_register` 호출은 force_window_open×2 = 최악 90ms를 소비한다. 이 90ms는 **50ms 안정화 대기 이후에 추가로 발생**한다. 따라서 실제 noTouch Counts 샘플링 시점은 RESEED 후 최소:

```
50ms (안정화 대기) + 90ms (force_window_open×2) = 140ms 이후
```

설계 근거로 쓴 "50ms는 LTA IIR 1스텝 이상 대기 [추정]"는 이 force_window_open 지연을 무시했다. Beta=0(현재) 시 LTA IIR 갱신이 없으므로 50ms 자체가 의미 없지만, Phase 2 이후 Beta 설정 시 실제 안정화 대기가 50ms인지 140ms인지 불명확해진다.

### 5-3. 공장 캘리브레이션 흐름의 구조 문제

```
apply_settings() 실행 → 고정값 덮어쓰기 → RESEED → [50ms 대기] → [force_window_open×2 90ms] → Counts 읽기
```

`apply_settings()` 내부 자체가 이미 수백 ms의 I2C 비용을 포함한다. 이후 50ms 대기, 이후 read_register 90ms — **총 안정화 시점까지 최악 수백 ms 이상**이 소요된다. 그 동안 SYS_WATCHDOG_REFRESH()는 안정화 대기 루프에서만 호출된다. `apply_settings()` 내부 write_register 체인 중 WDT 리프레시 호출이 없다면 WDT 리셋 위험이 존재한다 [확정 필요: apply_settings 내 WDT 처리].

## 6. 결함_6: 게이트 루프 poll_ms=50ms와 IQS323 측정 사이클(T_주기)의 관계 미검토

**공격 대상**: `14_계획_노터치게이트코드.md §2-3` `const uint32_t poll_ms = 50u`

### 6-1. 계획의 주장

"게이트 폴링 간격 50ms [추정]"으로 N=3 stable_samples = 3 × 50ms = 150ms 대기.

### 6-2. T_주기와의 관계

IQS323 측정 사이클 T_주기:
- 데이터시트 §3.4 NP self-cap 3ch 예시: 최대 **16ms** [참고값, `10_rdy-window-timing.md §3.2`]
- Report Rate=0(기본값): 측정 완료 즉시 RDY 토글

**T_주기 ≈ 16ms라면 poll_ms 50ms 간격으로 샘플링할 때 1회 read_register 사이에 IQS323은 3~4회 측정을 마친다.** 각 측정 후 LTA IIR이 갱신(Beta≠0 시)되므로, 50ms 간격 샘플은 중간 갱신 이력 없이 결과만 읽는다.

그런데 Beta=0 현재 상황에서는 LTA가 변하지 않으므로 counts는 **IIR 수렴 여부와 무관하게 환경 noise만 반영**한다. stable_count N=3이 "counts 안정성 확인"이라고 설계했지만, 사실 50ms × 3 = 150ms 동안 연속 noTouch 환경이라는 것을 확인하는 것뿐이다. **이는 race 방어가 아니라 단순 시간 지연에 가깝다.**

더 심각한 문제: 터치 부팅 시 손가락이 50ms 이상 올려져 있으면 stable_count가 증가하지 않아 timeout 5초까지 게이트가 대기한다. 그런데 **force_window_open 최악 91ms × 100회 = 최대 9100ms(9.1초) 실제 블로킹** (결함_1과 동일 경로). 5초 timeout 의도와 최대 9.1초 실제 대기 간의 괴리를 어디서도 명시하지 않았다.

## 7. 추가 결함: BETA 레지스터 주소 0xB0~0xB4가 계획 간 불일치

**공격 대상**: `15_계획_드리프트LTA.md §2.1` vs 코드 베이스

계획은 NP LTA Filter Beta = `0xB2`, Fast Beta = `0xB4`로 정의했다. 그런데:
- 현재 코드에 `0xB0~0xB4` 범위의 어떤 define도 없음 (`14_계획_노터치게이트코드.md §0`의 "현재 값" 표에도 없음)
- `분석.md §핵심 발견 #6` 확정: BETA write 0건

0xB2, 0xB4는 데이터시트 §5.6 추정값이며 [확정 필요] 표기가 있다. 그러나 계획 코드 스니펫(`write_register(TDC_DRV_IQS323_REG_ADDR_NP_LTA_FILTER_BETA, ...)`)에서는 마치 주소가 확정된 것처럼 define을 사용한다. 이 define을 **실제 코드에 추가하면 데이터시트와 다른 레지스터를 건드릴 수 있다.** 실측 전 코드 구현 자체를 Phase 2 게이트 뒤로 미루어야 하며, Phase 1 코드 스켈레톤에 아직 확정되지 않은 define이 포함되면 빌드는 통과하되 잘못된 레지스터를 write할 수 있다.

## 9. 핵심 결론 (6줄)

1. **게이트 루프 타임아웃 측정 방식 결함**: `elapsed_ms += poll_ms`는 force_window_open(최악 45ms/회) 비용을 누락 — 명세 5초가 실제 최대 14초로 늘어남. `ci_timer_get_tick()` 기반 실제 경과 시간 측정으로 교체 필수.
2. **사후 검증 재시도가 race 윈도우를 확대**: 1회 최악 147ms × 최대 3회 = 440ms 블로킹 — 재시도 딜레이 10ms는 IQS323 측정 1사이클(최대 16ms)도 보장 안 함. T_주기 실측 선행 후 딜레이 재결정.
3. **크래들 방전→Re-ATI 순서의 force_window_open 연쇄 미계산**: 방전 복원 write 직후 Re-ATI trigger write 사이에 force_window_open이 추가로 발생, Re-ATI가 SENSOR0_SETUP(0x30)을 갱신할 경우 방전 복원값 덮어쓰기 위험 [확정 필요].
4. **Beta write 신설 = apply_settings 블로킹 최악 91ms 추가**: Beta 레지스터 주소 자체가 [확정 필요] 상태에서 코드 define 구현 시 잘못된 레지스터 write 위험 — 주소 확정 전까지 코드 신설 자체를 Phase 2 게이트 뒤로 이동 필요.
5. **공장 캘리브레이션 50ms 안정화 대기 이후 90ms 추가**: 실제 Counts 샘플링 시점이 RESEED 후 최소 140ms — "LTA IIR 1스텝 대기"는 Beta=0 현재 무의미, Beta 설정 후 실측 기반 재결정 필요.
6. **poll_ms=50ms는 T_주기(최대 16ms) 대비 과대하지 않으나 stable_count의 의미가 noise 필터가 아닌 단순 시간 보장**: stable_count N=3이 실질적으로 150ms 노터치 연속이라는 시간 조건임을 명시해야 하며, T_주기 실측으로 샘플 독립성 확인 필요.
