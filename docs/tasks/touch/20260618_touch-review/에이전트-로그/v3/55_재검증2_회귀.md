# 55 — 재검증 라운드2 (회귀 관점) — 49_종합-재검증1 공격

**TL;DR**: 49_종합-재검증1을 회귀 관점에서 공격. 수렴 확정 항목은 명시 수렴 처리하고, 신규 발굴 약점 6건을 보고한다. 핵심 결함: ① `TDC_TOUCH_RTT_TUNING` 분기가 2차 종합에서도 완전 누락돼 게이트 신뢰도 설계에 모순이 생겼고, ② EEPROM 로드 경로 의사코드가 `write_ati_compensation()` 인자 전달 메커니즘을 미확정 상태로 남겨 사문 위험이 잔존하며, ③ 비블로킹 Re-ATI 설계가 ATI_Error 재귀 위험과 동일 폴링 루프에서 새 race를 만든다. 부분 수렴 판정 유지 — 아키텍처 원리는 확립됐으나 회귀_2(RTT_TUNING)·회귀_6(EEPROM 로드 실제 경로)가 Phase 1·2 착수 전 해소 필수 항목으로 승격된다.

## 2. 신규 결함 발굴

### [회귀_A] `TDC_TOUCH_RTT_TUNING` 분기 — 45_회귀 회귀_2가 재검증1에서도 여전히 미해소다 (치명)

**49_종합 §9 수렴 확정 표**: 45_회귀에서 발굴된 6건 가운데 "회귀_1(write_ati_compensation ATI_SETUP 덮어쓰기)"·"회귀_6(EEPROM 로드 경로)"만 수렴 반영 항목으로 등장한다. **45_회귀 회귀_2(`TDC_TOUCH_RTT_TUNING` 분기)**는 수렴 확정 표에 없고 §2-1~§5 어디에도 반영 흔적이 없다.

**코드 ground truth**: `iqs323.c:705~730`:
```c
#if TDC_TOUCH_RTT_TUNING
    uint8_t m_l = s_tdc_normal_tuning.ati_valid
                  ? s_tdc_normal_tuning.mult_lsb
                  : TDC_DRV_IQS323_ATI_MULT_LSB;
    ...
#else
    write_register(... TDC_DRV_IQS323_ATI_MULT_LSB ...);
#endif
```

`TDC_TOUCH_RTT_TUNING=1` + `s_tdc_normal_tuning.ati_valid=true` 빌드 환경에서는 MULT/COMP가 런타임 튜닝값(`s_tdc_normal_tuning`)으로 대체된다. 이 MULT/COMP 기준으로 생성된 counts와 **공장 캘리브레이션 환경(RTT_TUNING 빌드 여부·ati_valid 여부)이 같다는 보장이 없으면** `FACTORY_NOTOUCH_COUNTS`와 비교하는 게이트 윈도우는 다른 게인 기준 값들 사이의 비교가 된다.

**49_종합의 누락**: §3 빌드가드 최종 세트에 `TDC_TOUCH_RTT_TUNING`과 노터치 게이트 간 충돌을 차단하는 #error 또는 설계 주석이 없다. §5 블로킹 목록에도 없다.

**회귀 경로**: Phase 1 `NOTOUCH_GATE_ENABLE=1` 활성화 후 개발 빌드(`RTT_TUNING=1`)에서 개발자가 ati_valid를 set하면, 공장 캘리브레이션과 다른 MULT/COMP 기준 counts로 게이트가 판별한다 → 게이트 윈도우 완전 무의미.

**요구 조치**: 블로킹 목록에 신규 추가 — "`TDC_TOUCH_RTT_TUNING=1` 빌드에서 공장 캘리브레이션 수행·저장 금지 및 NOTOUCH_GATE 비활성화" 컴파일 타임 강제 또는 설계 주석 명시. #error 후보:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && TDC_TOUCH_RTT_TUNING
#error "NOTOUCH_GATE와 RTT_TUNING은 동시 활성화 불가 — 게이트 기준값(FACTORY_NOTOUCH_COUNTS) MULT/COMP 기준 불일치"
#endif
```

### [회귀_B] EEPROM 로드 경로 의사코드의 인자 전달 메커니즘이 미확정 상태로 사문 위험이 잔존한다 (치명)

**49_종합 §2-3 수정 내용**:
```c
/* tdc_drv_iqs323_apply_settings() 내 수정 흐름 */
if (tdc_touch_calib_load_eeprom(&calib)) {
    s_mult_lsb = calib.mult_lsb;
    s_comp_lsb = calib.comp_lsb;
    /* write_ati_compensation()이 이 값을 사용하도록 전달 */
}
write_ati_compensation();  /* 항상 실행, 위 분기로 인자 결정 */
```

**회귀 공격**: 의사코드에 `s_mult_lsb`, `s_comp_lsb`라는 정적 변수를 삽입하고 "write_ati_compensation()이 이 값을 사용하도록 전달"이라는 주석만 남겼다. 그런데 현재 `write_ati_compensation()` 함수 시그니처(`iqs323.c:696`)는 `static bool write_ati_compensation(void)`로 인자가 없다. 내부에서 `TDC_DRV_IQS323_ATI_MULT_LSB`(컴파일 타임 상수)를 직접 참조한다.

이 의사코드가 실제로 동작하려면 두 가지 중 하나가 필요하다:
1. `write_ati_compensation()`에 MULT/COMP 인자를 추가하거나
2. 정적 파일 스코프 변수(`s_mult_lsb`, `s_comp_lsb`)를 신설하고 함수 내부가 이를 참조하도록 변경

49_종합은 이 중 어느 방법을 선택하는지 명시하지 않았다. "전달"이라는 한 단어로 핵심 구현 결정을 유보했다. 이 결정 없이 의사코드는 사문이다.

**추가 위험**: 방법 ②(정적 변수)를 선택하면, RTT_TUNING 분기(`iqs323.c:705~730`)가 `s_tdc_normal_tuning` 정적 구조체를 참조하는 패턴과 동일하다. 두 정적 변수 쌍(`s_mult_lsb`/`s_comp_lsb` vs `s_tdc_normal_tuning.mult_lsb`/`comp_lsb`)이 공존하면 어느 값이 실제 write에 사용되는지 빌드 환경(RTT_TUNING 여부·ati_valid 여부)에 따라 달라져 디버깅이 복잡해진다.

**요구 조치**: 49_종합 §2-3의 "write_ati_compensation()이 이 값을 사용하도록 전달"을 구체 구현 방법(함수 시그니처 변경 vs 정적 변수)으로 확정. RTT_TUNING 분기와 EEPROM 로드값 분기의 우선순위 정책 명시.

### [회귀_C] 비블로킹 Re-ATI 설계(R3_CHARGING)가 ATI_Error 재귀 위험(확인_9)과 동일 폴링 루프에서 새 race를 만든다 (고위험)

**49_종합 §2-4 R3_CHARGING 설계**:
```
구조: 비블로킹 선호 — re_ati_trigger() 발행 후 다음 폴링에서 ATI_Active 확인
노터치 게이트: 30초 주기 도달 시 현재 counts로 게이트 통과 확인 후 트리거
충전 중 터치 race: Re-ATI 도중 터치 → ATI_Error 핸들러 발동
```

**§6 확인_9**: "ATI_Error 핸들러 레이어 처리 위치 + 재귀 호출 차단 구조"

**회귀 공격**: 비블로킹 R3_CHARGING 구조에서 re_ati_trigger() 발행 후 **다음 폴링에서 ATI_Active 확인**하는 구조는, 그 사이(발행~다음 폴링 200ms) 터치가 발생하면 ATI_Error가 발생한다. ATI_Error 핸들러가 **동일 폴링 루프**에서 처리된다면:

```
폴링 N: 노터치 게이트 통과 → re_ati_trigger() 발행
폴링 N+1: ATI_Active=1(진행 중), 터치 발생
폴링 N+2: ATI_Error=1 → 핸들러 발동
  → pressed=true 시 s_ati_error_pending=true
폴링 N+k: 손 뗌 감지 → re_ati_trigger() 재발행 (충전 중이면 다시 R3_CHARGING 트리거 대상)
폴링 N+k+1: 30초 타이머 리셋 없으면 동시에 R3_CHARGING 주기도 도달 → 이중 트리거
```

49_종합은 `s_ati_error_pending` 플래그 처리와 R3_CHARGING 30초 타이머 리셋 간의 상호작용을 명시하지 않았다. ATI_Error 후 `re_ati_trigger()` 재발행이 R3_CHARGING 타이머를 리셋하는지 여부에 따라 폴링 N+k에서 이중 트리거가 발생할 수 있다.

**추가**: 비블로킹 구조에서 ATI_Active 폴링을 "다음 폴링에서 확인"한다면, ATI가 완료되기 전 또 다른 R3_CHARGING 주기가 도달했을 때(ATI 완료 시간 > 30초 타이머 잔여 시간인 극단 경우 [추정])의 처리도 미기술이다.

**요구 조치**: R3_CHARGING 설계에 "Re-ATI 진행 중(`ATI_Active=true`)이면 새 트리거 발행 금지 플래그" 및 "ATI_Error 재발행 시 R3_CHARGING 타이머 리셋 여부" 명시. 확인_9 항목에 "비블로킹 R3_CHARGING과 ATI_Error 재트리거 타이머 충돌" 추가.

### [회귀_D] 49_종합 §4 Phase 1 게이트 삽입점 설계에서 절전 진입 RESEED(`iqs323.c:931~948`)가 누락됐다 (고위험)

**49_종합 §4 Phase 1 설계**:
```
삽입점: write_ati_compensation() 항상 실행 유지, 이후 RESEED만 게이트화
현재 iqs323.c:1141~1158 (tdc_drv_iqs323_apply_settings 말미)
```

**분석.md §2 및 §3**에 확정된 RESEED 발행 위치는 **두 곳**이다:
1. `iqs323.c:1146` — `tdc_drv_iqs323_apply_settings()` 내 부팅 RESEED (Phase 1 게이트 대상으로 명시)
2. `iqs323.c:955` — `tdc_drv_iqs323_reseed()` 내 절전 진입 RESEED (`main.c:952`에서 호출)

49_종합-재검증1 §4 Phase 1 계획은 삽입점을 "`tdc_drv_iqs323_apply_settings()` 말미"로만 기술한다. 절전 진입 RESEED(`iqs323.c:955`)는 `§1-2` "절전/부팅 통합 조건부 확정"에서 "MCLR이 IC LTA 레지스터를 포함한 전 레지스터를 POR 초기화하는지 미확인 → 블로킹_G"로 처리했을 뿐, **절전 RESEED 자체를 게이트화할지 여부**가 미결이다.

**회귀 경로**: 절전 진입 시 `pressed==false` 대기 후 수백 ms 동안 절전 파라미터 설정 → `tdc_drv_iqs323_reseed()` — 이 구간에 터치 재개 race가 존재함은 42_race 공격_3에서 이미 지적됐다. 49_종합은 이 race를 "블로킹_G 해소 후 판단"으로 연기했으나, **절전 RESEED를 Phase 1 게이트 범위에 포함할지 여부를 명시하지 않았다**. 블로킹_G가 해소돼 MCLR이 완전 POR임이 확인되면 절전 RESEED 오염은 재부팅 후 소멸한다는 논리는 성립하지만, MCLR이 일부 보존이면 절전 RESEED 게이트화도 필요하다.

49_종합 §4 Phase 1 계획에 "절전 진입 RESEED는 블로킹_G 해소 결과에 따라 게이트화 범위 결정"이라는 조건 분기가 없다 — 개발자가 Phase 1을 구현할 때 절전 RESEED를 게이트화해야 할지 판단 근거가 없는 상태다.

**요구 조치**: Phase 1 계획에 "절전 RESEED 게이트화 여부 = 블로킹_G 결과 의존" 명시. 블로킹_G 해소 시 체크리스트에 "절전 RESEED 게이트화 필요 여부 재결정" 추가.

### [회귀_E] 49_종합 §3 빌드가드 최종 세트의 `TDC_TOUCH_SATURATE_MAX_COUNTS` 초기값 0이 포화 감지 stub을 즉시 무력화한다 (중간)

**49_종합 §3 빌드가드**:
```c
#define TDC_TOUCH_SATURATE_DETECT_ENABLE     1u
#define TDC_TOUCH_SATURATE_MAX_COUNTS        0u  /* [확정 필요] 데이터시트+실측_E 후 교체 */
```

**회귀 공격**: `SATURATE_DETECT_ENABLE=1`이고 `SATURATE_MAX_COUNTS=0`이면, 포화 감지 코드에서 `counts >= SATURATE_MAX_COUNTS`는 `counts >= 0`으로 **항상 참**이 된다. 이는 매 폴링마다 포화 경보를 발생시키거나(= 경보 범람), 아니면 포화 로직이 `counts < 0` (부호 없는 타입에서 불가)으로 처리되어 **경보가 완전 발생하지 않는 침묵**으로 동작한다. 어느 방향이든 stub은 의도대로 동작하지 않는다.

30_종합-1차 §2-2에서 동일한 0 기본값이 있었는데, 46_할루시 약점_5가 이를 "임계 없는 stub"으로 지목했다. 49_종합-재검증1은 `SATURATE_MAX_COUNTS` 초기값을 0으로 유지한 채 "[확정 필요]" 주석만 추가했다.

**추가 문제**: 30_종합의 Phase 0 설계는 "SATURATE_DETECT_ENABLE=1 (항상 ON)"이고 49_종합도 동일하게 유지했다. 그러나 MAX_COUNTS가 0이면 실측_E 완료 전까지 이 stub은 "항상 ON"이 아닌 "항상 오작동"이 된다. 구현 시 이 define으로 코드를 작성하면 의도치 않은 동작이 발생한다.

**요구 조치**: 두 방법 중 하나 선택:
1. `SATURATE_DETECT_ENABLE` 기본값도 0으로 변경 (실측_E 완료 전 OFF 유지)
2. `SATURATE_MAX_COUNTS`에 데이터시트 §5.5(Max Counts 항목) 값을 추정치로 삽입하되 [확정 필요] 표기

### [회귀_F] 49_종합이 수렴 처리한 "s_boot_touch_ignore와 노터치 게이트 해제 조건 정합성(확인_10)"이 실질적으로 미해소다 (중간)

**49_종합 §6 확인_10**: "`s_boot_touch_ignore`와 노터치 게이트 해제 조건 정합성 — 올바른 RESEED 후 억제 구간 발생 방지(45_회귀 회귀_3·46_약점_6)"

이것은 "확인 항목"으로만 추가됐다. **해소 방법이 없다** — 45_회귀 회귀_3·46_할루시 약점_6이 제기한 "두 가드 동시 활성 시 독립 해제 조건 충돌로 터치 무반응 구간 발생 시나리오"에 대한 설계 답이 49_종합 어디에도 없다.

**회귀 공격**:
- `s_boot_touch_ignore`는 READY 전이 시 TOUCH 상태면 set, **터치 해제 이벤트까지 억제**하는 사후 방어다(`touch.c:352`에서 pressed==false 시 clear).
- 노터치 게이트는 **RESEED 시점 사전** 방어다.

두 가드가 동시 활성 시 시나리오:
1. 부팅 → 노터치 게이트 통과 → 올바른 RESEED 완료
2. 그런데 READY 전이 직후 순간 TOUCH 이벤트가 있었다면 → `s_boot_touch_ignore` set
3. 이후 count read → pressed=false → `s_boot_touch_ignore` clear 가 올바른 해제 경로이나, RESEED 이후 첫 폴링에서 pressed 상태를 읽는 타이밍에 따라 게이트 통과 시점 대비 이벤트 순서가 뒤집힐 수 있다
4. 결과: 올바른 LTA가 seed됐음에도 수백 ms 동안 터치 이벤트 무반응

"확인_10"이라는 이름만 붙여 등록한 것은 이 시나리오를 해소하지 않고 구현자에게 위임한 것이다. **구현 착수 전 두 가드의 해제 타이밍 정합성 설계가 Phase 1 계획에 명시돼야 하며, "확인_10 해소 방법 미기술"이 계획 공백으로 잔존한다.**

**요구 조치**: Phase 1 설계에 "s_boot_touch_ignore와 노터치 게이트의 역할 분리 및 해제 타이밍 통합 방법" 구체 기술. 예: 올바른 RESEED 완료 시 `s_boot_touch_ignore`를 강제 clear하고 이후 첫 폴링부터 터치 이벤트를 정상 처리하도록 또는 두 가드 중 하나를 폐기·통합.

## 4. 핵심 6줄

1. **[회귀_A 치명] `TDC_TOUCH_RTT_TUNING` 분기는 45_회귀 회귀_2로 이미 지목됐으나 49_종합-재검증1 수렴 표에 누락됐다** — RTT_TUNING=1 빌드에서 MULT/COMP가 런타임 값으로 대체되면 공장 캘리브 기준 `FACTORY_NOTOUCH_COUNTS`와 비교 자체가 무의미해지므로, `NOTOUCH_GATE + RTT_TUNING` 동시 활성화 #error 가드가 빌드가드 세트에 즉시 추가돼야 한다.
2. **[회귀_B 치명] §2-3 EEPROM 로드 의사코드에서 "write_ati_compensation()이 이 값을 사용하도록 전달"이라는 주석은 인자 전달 방법(함수 시그니처 변경 vs 정적 변수)을 결정하지 않아 사문이다** — RTT_TUNING 분기의 `s_tdc_normal_tuning`과 동일 레이어에서 충돌할 수 있으며, 구체 구현 방법 확정 없이 Phase 2 착수는 불가.
3. **[회귀_C 고위험] 비블로킹 R3_CHARGING 설계에서 ATI_Error 재트리거(`s_ati_error_pending` → re_ati_trigger())가 30초 타이머를 리셋하는지 여부가 미기술** — 미리셋 시 ATI_Error 후 짧은 간격으로 이중 트리거가 발생하며, ATI_Active 진행 중 새 트리거 발행 금지 플래그가 R3_CHARGING 설계에 명시돼야 한다.
4. **[회귀_D 고위험] 절전 진입 RESEED(`iqs323.c:955`)의 게이트화 여부가 블로킹_G 결과에 따라 달라지는데, 49_종합 Phase 1 계획에 이 조건 분기가 없다** — MCLR이 완전 POR이면 절전 RESEED 오염은 재부팅 후 소멸하므로 게이트 불필요이나, 일부 보존이면 게이트 범위를 절전 RESEED까지 확장해야 한다.
5. **[회귀_E 중간] `TDC_TOUCH_SATURATE_MAX_COUNTS=0` 기본값은 포화 감지 stub을 "항상 ON"이 아닌 "항상 오작동" 상태로 만든다** — counts >= 0은 부호 없는 타입에서 항상 참이어서 경보 범람 또는 역방향 무발동이 발생하며, ENABLE 기본값을 0으로 내리거나 데이터시트 추정값을 [확정 필요] 표기와 함께 삽입해야 한다.
6. **[회귀_F 중간] 확인_10(s_boot_touch_ignore 해제 정합성)은 이름만 등록됐을 뿐 해제 타이밍 설계 답이 없어 구현자에게 미해소 상태로 위임됐다** — 올바른 RESEED 완료 후 s_boot_touch_ignore 강제 clear 여부·두 가드 통합 방법을 Phase 1 계획에 명시해야 구현 시 터치 무반응 구간 생성을 막을 수 있다.
