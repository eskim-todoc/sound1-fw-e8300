# 22_검증_회귀 — 기존 동작 회귀·부작용 adversarial 검증

**TL;DR**: 8개 계획(11~18)에 대해 회귀·부작용 관점에서 17개 결함을 발굴했다. 가장 치명적인 것은 ① `apply_settings()` 내 삽입점 충돌(11+14가 동일 지점에 서로 다른 교체를 제안), ② CFX `userSettingValue` 구조체 확장이 야기하는 기존 EEPROM 데이터 무효화 회귀, ③ Beta=4 설정 후 자기치유 가정이 깨지는 조건(노터치 방향 LTA freeze 미고려), ④ 크래들 Phase 1 RESEED가 절전 진입 직전과 동일 `0x08` 커맨드를 사용해 절전 THRESHOLD 파라미터 누락으로 ULP 모드 불능 위험이다.

## 결함 목록 (심각도 순)

### [결함_1] 11_부팅시퀀스 ↔ 14_노터치게이트코드 삽입점 충돌 (치명)

**근거**: `11_계획_부팅시퀀스.md §3-1`은 `apply_settings()` 내 `write_ati_compensation()` **이전에** 노터치 판별 후 MULT/COMP를 조건부 write하는 구조를 제안한다. `14_계획_노터치게이트코드.md §3`은 동일한 `apply_settings()` 내 `write_ati_compensation()` **이후** RESEED 무조건 write(`:1147`) 1줄을 `tdc_drv_iqs323_reseed_with_gate()`로 교체하는 구조를 제안한다. 두 계획이 동일 함수의 서로 다른 위치에 서로 다른 논리를 삽입하며, 채택/폴백 분기가 **이중**으로 중첩된다.

코드 ground truth(`iqs323.c:1141~1158`):
```
write_ati_compensation()  ← 현재 고정값 MULT/COMP 덮어씀
write_register(RESEED)    ← 무조건 RESEED
write_register(CH_TIMEOUT_OFF)
```

- 11번은 `write_ati_compensation()` **전 삽입** (ATI 채택 vs 고정값 선택)
- 14번은 `write_ati_compensation()` **후 삽입** (RESEED 게이트)
- 둘을 동시에 구현하면 MULT/COMP 결정 경로와 RESEED 게이트 경로가 각각 별도 분기를 가져 상호 전제가 불일치한다 — 예: 11번이 Auto-ATI MULT/COMP를 채택했는데 14번 RESEED 게이트가 다시 `write_ati_compensation()`(고정값)을 폴백 경로로 재호출하는 경우.

**회귀 경로**: Phase 1에서 두 파일을 통합 없이 각각 구현하면 `apply_settings()` 내에 서로 다른 전제를 가진 두 빌드가드 블록이 공존하여 결정론적 순서가 깨진다. 18번 통합아키텍처도 이 충돌을 단일 코드 설계로 해소하지 않았다.

**요구 조치**: 두 계획을 단일 `apply_settings()` 수정 계획으로 통합, 분기 트리를 하나로 확정.

### [결함_2] cfx_cm3_sharedMemory.h 구조체 확장 → 기존 EEPROM 데이터 오프셋 붕괴 (치명)

**근거**: `12_계획_공장캘리저장.md §3-1 옵션_A`는 `ST__CFX_CM3_SharedMemory_userSettingValue`에 `int` 4필드(touch_calib_magic, touch_mult, touch_comp, touch_noTouch_counts)를 추가하도록 권고한다.

**회귀 경로**: 이 구조체는 EEPROM에 직렬화되어 영속된다. 구조체에 필드를 추가하면 이미 필드에 데이터가 저장된 기존 보드는 부팅 시 로드할 때 **기존 7개 필드 외 나머지가 이전 다른 데이터의 오프셋 위치를 읽게 된다**. CFX 파서가 파일 크기 고정이면 `touch_calib_magic` 위치는 이전 EEPROM에서 의미없는 바이트를 읽어 0xCA1B가 아닌 값을 반환하므로 로드 실패(폴백) — 이것은 의도된 동작이지만, 문제는 `mapNum` 등 기존 7개 필드 자체가 오염되는지 여부다. CFX 파서가 고정 오프셋 배열로 파싱한다면 기존 필드 오프셋이 변하지 않으므로 안전하나, 구조체 크기를 sizeof로 read/write한다면 기존 데이터가 잘못된 크기 블록으로 덮여 **mapNum·stimulVolume 등 기존 설정 전체 소실**이 발생한다.

12번 §7 자체에서 "CFX 파서 크기 제약 [확정 필요]"로 명시하나, **확정 전에도 구조체 확장을 코드에 반영하면 CFX 파서 확인 없이 배포될 수 있다**. 이 확인이 선행 게이트로 강제되지 않은 채 Phase 2 구현을 진행하면 현장 보드의 청각설정(mapNum, stimulVolume 등)이 리셋되는 치명적 회귀가 발생한다.

**요구 조치**: cfx_cm3_sharedMemory.h 수정은 CFX 파서 구조 확인이 완료되기 전까지 코드에 merge 금지. 확인 완료 여부를 빌드가드가 아닌 **코드 미수정 상태**로 강제.

### [결함_3] 13_크래들훅 Phase 1 RESEED → 절전 ULP 파라미터 누락으로 약 절전 이후 터치 감도 불일치 (심각)

**근거**: `13_계획_크래들훅.md §2-2`는 `tdc_drv_iqs323_reseed()` 사용 불가 이유로 절전 THRESHOLD·HYSTERESIS·PROX 파라미터를 적용한다는 점을 정확히 지적하고, `tdc_drv_iqs323_reseed_normal()`을 신규 추가하는 방안을 권장한다. 그런데 이 분석 안에 **반대 회귀 방향**이 숨겨져 있다:

`func_cradle_lid_closed_loop()` 진입 전 `reseed_normal()`을 삽입하면 LTA가 뚜껑 닫힘 직전 noTouch counts로 갱신된다. 그런데 뚜껑 열림 후 WDT 리셋 → 재부팅 → `apply_settings()` → `write_ati_compensation()` → 무조건 RESEED 순서가 다시 실행된다. 즉 크래들 훅 RESEED는 뚜껑 열림 재부팅의 RESEED에 **덮어써지므로 직접 이득이 없다**.

13번 §3-5에서 이를 "뚜껑 닫힘 기간 동안만 유효"라고 인정하나, **뚜껑 닫힘 기간에는 터치 폴링 자체가 중단(`main.c:807`)되므로** 이 기간 RESEED의 실질 효과는 '없음'에 가깝다. 즉 Phase 1 크래들 RESEED의 유일한 이득은 "뚜껑 닫힘 루프 진입 중 혹시 I2C 통신을 시도하는 코드가 있다면 LTA 기준이 noTouch임"인데, 그 구간은 IQS323이 idle이다.

**회귀 경로**: 코드 추가(3파일 ~12줄)에 비해 효과가 없는 dead code가 main.c에 삽입된다. 더 중요하게는 향후 개발자가 이 RESEED를 "cradddle 기준 보정 완료" 신호로 오해하고 Phase 2 Re-ATI 구현을 생략하거나 지연하는 판단 오류로 이어질 수 있다.

**요구 조치**: Phase 1 크래들 훅의 실질 이득이 없음을 계획에 명시하거나, Phase 2 Re-ATI + EEPROM 저장과 묶어 진행.

### [결함_4] 15_드리프트LTA Beta 설정 후 약터치 방향 LTA 가속학습 위험 (심각)

**근거**: `15_계획_드리프트LTA.md §2.2`는 Beta=4(alpha≈1.6%) 설정을 권고하며, Fast Beta=12(alpha≈4.7%)를 노터치 복귀에 적용한다고 설명한다. 그런데 데이터시트 §5.6 Fast Filter Band 비대칭 구조는 다음과 같다:

> Counts가 LTA 대비 **노터치 방향**(Counts > LTA, 즉 delta 음수 방향)으로 Fast Filter Band 이상 벗어날 때 Fast Beta 적용.

**자기치유에 필요한 방향은 반대다**: race 오염 후 LTA=터치 counts, 손을 떼면 Counts가 LTA보다 **높아지는 방향**(노터치 방향)으로 이동 → Fast Beta 적용 → LTA 빠른 수렴. 이것은 정확하다.

**그러나**: 환경 드리프트(온도 상승)로 noTouch counts 자체가 서서히 **상승**하는 경우에도 동일하게 Counts > LTA 상황이 발생하며, Fast Beta가 적용된다. 즉 환경 드리프트로 counts가 상승할 때 LTA가 빠르게 따라가는 것은 의도된 동작이나, **약터치로 counts가 약간 감소했다가 손을 떼면 다시 상승**하는 경우에도 Fast Beta 조건에 부합하여 LTA가 터치 중간값까지 빠르게 수렴할 수 있다.

15번은 "약터치 방향 LTA 억제"를 설계 원칙으로 제시하나, Fast Beta가 **적용되는 방향**(Counts > LTA)은 약터치가 아니라 노터치 복귀 방향이므로 이 억제는 오히려 약터치 방향(Counts < LTA)에는 Beta(normal)=4가 적용되는 것을 의미한다. 이는 현재 Beta=0(LTA 완전 고착)보다는 낫지만, 실제 약터치 시 LTA가 낮은 counts 방향으로 천천히 내려가는 문제는 여전히 존재한다.

**회귀 경로**: Beta=4 설정으로 현재 동작(Beta=0, LTA 고착)에서 LTA가 움직이는 동작으로 전환되는 순간, 기존에 RESEED로 noTouch counts에 정확히 고착된 LTA가 환경 변화를 추적하기 시작한다. 이것이 의도된 개선이지만, 현재 `TDC_TOUCH_NOTOUCH_GATE_ENABLE`이 OFF(기존 동작)인 상태에서 Beta만 ON하면, 터치 부팅 시 LTA가 터치 counts에서 출발한 뒤 Beta=4로 **서서히 noTouch 방향으로 이동**하는 중간 상태가 수 분간 지속된다. 이 구간에 delta가 부정확해 오인식이 발생한다. 즉 노터치 게이트 구현 전에 Beta를 활성화하면 기존 동작보다 나쁜 중간 상태가 발생한다.

**요구 조치**: Beta 설정(Phase 2) 활성화는 노터치 게이트(Phase 2 동일) 구현 완료 후 동시 활성화여야 함을 계획에 강제 순서로 명시.

### [결함_5] 11_부팅시퀀스 §3-1의 `write_ati_setup_only()` 분리 — 기존 함수 내부 구조 가정 오류 (심각)

**근거**: 11번은 Auto-ATI 채택 경로에서 "ATI_SETUP(Mode=Disabled)만 write하고 MULT/COMP는 유지"하기 위해 `write_ati_setup_only()` 신규 함수 분리를 제안한다. 그런데 현재 `write_ati_compensation()`(`iqs323.c:696~`)의 내부 구조를 확인하면:

코드 ground truth(`iqs323.c:1141~1144`):
```c
if (!write_ati_compensation())
{
    ci_printe("[TOUCH] FAIL: WRITE ATI COMPENSATION \r\n");
}
```

`write_ati_compensation()` 내부에서 MULT·COMP·ATI_SETUP 레지스터를 **모두** write한다. 11번이 제안하는 "채택 경로에서 ATI_SETUP만 write"는 `write_ati_compensation()`을 일부만 실행하는 것이 아니라, 기존 함수를 아예 **스킵**하고 ATI_SETUP 레지스터 write만 별도로 수행하는 것이다.

문제는 현재 `write_ati_compensation()` 내부에 MULT/COMP 이외에 다른 레지스터 write(ATI_BASE, ATI_TARGET, Channel_Setup 등)가 포함되어 있을 수 있다는 점이다. [확정 필요: 696줄부터 함수 전체 내용 확인] 이 함수를 스킵하면 해당 레지스터들이 Auto-ATI 완료 후 IC 내부의 POR/Auto-ATI 결과 상태로 남아, 운용에 필요한 채널 설정이 누락될 수 있다.

**회귀 경로**: ATI 채택 경로에서 `write_ati_compensation()` 전체를 스킵하고 ATI_SETUP 레지스터만 write하면, MULT/COMP 이외의 다른 운용 설정이 IC에 적용되지 않아 터치 감도·필터 설정이 Auto-ATI 완료 직후 IC 내부 임시 상태로 고착된다.

**요구 조치**: `write_ati_compensation()` 내 레지스터 write 목록을 완전 확인(L696~ 전체 독해) 후, 스킵 가능 레지스터와 반드시 write해야 하는 레지스터를 분리한 명세 작성.

### [결함_6] 16_사후검증 `reseed_with_post_verify()` — FACTORY_NOTOUCH_COUNTS=0 기본값 시 RESEED 3회 반복 발행 (심각)

**근거**: `16_계획_사후검증.md §1-2`의 코드:

```c
for (uint8_t retry = 0u; retry < TDC_DRV_IQS323_RESEED_MAX_RETRY; retry++)
{
    if (!write_register(...RESEED...)) { continue; }
#if (TDC_DRV_IQS323_FACTORY_NOTOUCH_COUNTS > 0u)
    /* 사후 검증 로직 */
#else
    return true;  /* 공장값 미확정: 사후검증 없이 성공 반환 */
#endif
}
```

`FACTORY_NOTOUCH_COUNTS=0`일 때 `#else return true`가 실행되므로 **루프 첫 번째 iteration에서 즉시 return**되는 것이 의도다. 그런데 위 코드는 `write_register(RESEED)` **성공 후** `#else return true`에 도달한다. 즉 RESEED 1회 발행 후 성공 반환 → 기존 동작과 동일. 얼핏 안전해 보인다.

**그러나**: `write_register(RESEED)`가 실패(`!write_register`)할 경우 `continue` → 다음 iteration → 다시 `write_register(RESEED)` 시도. FACTORY_NOTOUCH_COUNTS=0이라도 I2C 실패 시 **최대 3회 RESEED를 연속 발행**한다. 현재 코드(1147줄)는 실패 시 ci_printe 후 진행(1회만)인데, 제안 코드는 3회 retry한다.

**회귀 경로**: 현재 코드 대비 I2C 일시 오류 시 RESEED 발행 횟수가 최대 3배가 된다. 연속 RESEED는 LTA가 세 번 연속 현재 counts로 재초기화되는 것을 의미하며, RESEED와 RESEED 사이에 counts가 변할 경우 최종 LTA가 예측 불가능한 값이 된다.

**요구 조치**: FACTORY_NOTOUCH_COUNTS=0 시는 현재 동작(1회 발행, 실패 시 ci_printe 후 진행)과 동일하게 루프 1회만 실행하도록 수정, 또는 `retry`를 `FACTORY_NOTOUCH_COUNTS > 0` 조건에서만 활성화.

### [결함_7] 15_드리프트LTA Beta POR default 미확인 — Beta=0 전제가 틀릴 경우 현재 동작 이해 자체 붕괴 (중요)

**근거**: `15_계획_드리프트LTA.md §1.3`은 "POR default=0x0000 → Beta=0 → LTA 불변"이라고 분석하고, 이를 기반으로 "현재 LTA가 RESEED 이후 전혀 변하지 않는다"는 핵심 전제를 세운다. 그러나 바로 아래에 "[확정 필요: 데이터시트 POR table 또는 MCLR 후 0xB0 read 실측]"이라고 스스로 표기하고 있다.

만약 IQS323 데이터시트의 Beta POR default가 0이 아닌 값(예: 4 또는 8)이라면:
- 현재 펌웨어에서 RESEED 후 LTA는 이미 IIR로 움직이고 있다
- "Beta=0 → LTA 고착"이 전제인 결함 #4의 논리가 바뀐다
- Beta write 신규 추가 계획 전체가 "이미 동작 중인 것을 다시 설정"하는 불필요한 변경이 된다
- 더 심각하게는 POR default Beta가 큰 값이라면 현재 약터치 시 LTA 학습 문제가 이미 발생 중이며, 이것이 현장 먹통의 원인일 수 있다

### [결함_8] 12_공장캘리저장 §4-2 — `apply_settings()` 실행 후 noTouch Counts 읽기 타이밍 오염 (중요)

**근거**: 12번 §4-3에서 제안하는 공장캘리 저장 시퀀스:
```
Auto-ATI 완료 → MULT/COMP 읽기 → apply_settings() 실행 → 50ms 안정화 → noTouch Counts 읽기
```

`apply_settings()`는 고정값 MULT/COMP write + RESEED를 실행한다. RESEED 실행 시 LTA←현재 counts로 재초기화되는 것은 의도된 동작이나, **공장환경에서 노터치 보장 상태라면 RESEED 직후 counts는 노터치 값이 맞다**.

**회귀 경로**: 11번·14번 계획의 부팅 시퀀스 변경이 공장 캘리브레이션 모드(`TDC_TOUCH_ATI_CALIB_MODE=1`)에서도 적용되면, 공장캘리 저장 함수가 가정하는 "50ms 후 안정화 완료" 타이밍이 게이트 대기(최대 5000ms) 동안 지연된다.

**요구 조치**: 공장 캘리브레이션 모드에서는 노터치 게이트 RESEED를 bypass하고 즉시 RESEED하도록 빌드가드 분리.

**요구 조치**: Flowchart를 교체 코드 구조와 일치하도록 수정 — ch_timeout write는 `apply_settings()` 내부 게이트 함수 호출 후에 위치함을 명시.

### [결함_14] 12_공장캘리저장 §2-1 — `touch_calib_magic` 필드를 `int`로 저장 시 0x0000CA1B와 엔디안 불일치 위험 (보통)

**근거**: 12번은 `int touch_calib_magic = 0x0000CA1B`로 저장하고 로드 시 `if (magic != (int)TDC_TOUCH_CALIB_MAGIC)` 비교한다. CM3는 little-endian이므로 `int 0x0000CA1B`는 메모리에 `1B CA 00 00` 순으로 저장된다.

**문제**: CFX 측이 EEPROM 데이터를 big-endian으로 처리하거나, 16비트 단위로 파싱한다면 `0xCA1B`(하위 16비트)가 `0x1BCA`로 읽힐 수 있다. 매직넘버가 `0xCA1B`로 선택된 것이 ASCII 'CAL' + 'IB' 약어 기반이라면, CFX에서 같은 약어를 big-endian으로 쓴다면 충돌한다.

실제로 `cfx_cm3_sharedMemory.h`의 기존 7개 필드가 모두 `int`이고 CM3-CFX 통신이 동일 엔디안으로 처리된다면 무관하다. [확정 필요: CFX-CM3 통신 엔디안 및 파서 방식]

**요구 조치**: 매직넘버를 `0xCA1B0000`(MSB 배치)로 바꾸거나, 엔디안 무관하게 양쪽에서 동일하게 처리됨을 CFX 코드에서 확인.

### [결함_17] 15_드리프트LTA Beta 레지스터 주소 추정 — 0xB2·0xB4가 틀릴 경우 기존 레지스터 덮어씀 (보통)

**근거**: `15_계획_드리프트LTA.md §2.1`에서 Beta 레지스터 주소를 "[추정] 0xB0~0xB4"로 기재하고, `write_filter_betas()`에서 `0xB2`·`0xB4`를 직접 write하는 코드를 제안한다.

현재 `tdc_drv_iqs323.c`에는 `0xB0~0xB4` 범위 레지스터 write가 없으므로, 이 주소가 데이터시트와 다를 경우 **기존 동작 중인 다른 레지스터(터치 설정, 채널 설정 등)를 덮어쓰는 사고**가 발생한다. `write_register(0xB2, 4, 12)`가 실제로는 다른 기능의 레지스터를 변경하면 터치가 완전히 동작 불능이 될 수 있다.

**회귀 경로**: Beta 레지스터 주소가 추정값인 상태에서 Phase 2 구현 시 잘못된 주소에 write → 기존 정상 동작하던 터치가 즉시 불능화.

**요구 조치**: Beta 레지스터 주소는 IQS323 데이터시트 register map 원문 확인 완료 후에만 코드에 기재. `[추정]` 상태로 코드에 포함 금지.

## 핵심 요약 (6줄)

1. **삽입점 이중 충돌(결함_1)**: 11번과 14번이 `apply_settings()` 내 서로 다른 위치에 서로 다른 분기를 제안하여, 두 계획을 동시에 구현하면 결정론적 MULT/COMP 선택 경로가 붕괴된다 — 단일 통합 설계가 없으면 Phase 1 구현 불가.
2. **EEPROM 구조체 확장(결함_2)**: CFX 파서 크기 확인 전 `userSettingValue` 구조체 확장 코드가 merge되면 기존 보드의 청각설정(mapNum·stimulVolume 등) 전체가 부팅마다 소실된다 — CFX 파서 확인 완료 전 코드 수정 절대 금지.
3. **크래들 Phase 1 dead code(결함_3)**: 뚜껑 닫힘 구간에서 터치 폴링 자체가 중단되므로 Phase 1 RESEED 삽입의 실질 이득이 없다 — Phase 2 Re-ATI+EEPROM 저장과 묶지 않으면 12줄 dead code 추가에 불과하다.
4. **Beta-게이트 순서 강제 누락(결함_4)**: Beta 설정을 노터치 게이트 전에 활성화하면 터치 부팅 시 LTA가 터치 counts에서 출발해 수 분간 중간값으로 이동하여 오인식이 악화된다 — 두 Phase는 동시 활성화만 허용.
5. **WDT 미갱신 재부팅 위험(결함_9)**: 크래들 Re-ATI 1.5초 블로킹 동안 `SYS_WATCHDOG_REFRESH()` 호출이 계획 코드에 없어 WDT 만료 재부팅이 발생하면 뚜껑 닫힘 진입이 영구 불능화된다.
6. **Beta POR default 미확인(결함_7)**: IQS323 Beta 레지스터 POR default가 0인지 실측 없이 Phase 2 전체를 잘못된 전제 위에 구축할 수 있으며, 0이 아닌 경우 현재 동작 이해 자체가 뒤바뀐다.
