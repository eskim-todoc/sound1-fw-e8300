# 67 — 재검증 라운드3 (엣지 관점) — 59_종합-재검증2 adversarial 공격

**TL;DR**: 59_종합-재검증2를 엣지 관점에서 3차 공격. 신규 약점 5건 발굴 — 치명 1건(gate_check() MARGIN_UP 방향 언더플로 대칭 결함, 상한 hi 또한 동일 수식 오버플로 가능), 고위험 2건(R3_CHARGING 30초 타이머 기준 기술 없음·ATI_Error 후 재시도 상한 N회 소진 뒤 Fixed 기저 복귀 경로에서 MULT/COMP가 공장값인지 ATI 오염값인지 미확정), 중위험 2건(비블로킹 Re-ATI 중 NOT_TOUCH 강제 구간에서 롱터치 2400ms 카운터가 오동작 가능·블로킹_K의 MAX_WAIT_MS_FOR_WINDOW_CLOSE가 코드에 이미 존재하는지 grep 미실시). 기존 수렴 확정 항목 기각 없음 — **수렴 판정: 부분 수렴 유지**. 신규 4건 추가로 구현 전 해소 항목 총 15건.

## 2. 신규 약점 발굴 — 59가 놓친 엣지

### 신규_1 — gate_check() 상한 `hi` 오버플로 가드 누락 [치명]

**59 §4 Phase 1 gate_check() 코드**:
```c
uint32_t lo = (uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS
              - TDC_TOUCH_NOTOUCH_MARGIN_STRICT;
uint32_t hi = (uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS
              + TDC_TOUCH_NOTOUCH_MARGIN_UP;
```

**엣지 공격**: 59는 MARGIN_STRICT ≥ COUNTS 시 `lo`의 uint32 언더플로(wrap-around) 가드를 §2-2에서 치명으로 발굴해 빌드가드 `#error`를 §3에 추가했다. 그러나 **상한 `hi`의 오버플로는 완전히 누락**됐다.

`hi = (uint32_t)FACTORY_NOTOUCH_COUNTS + MARGIN_UP`에서:
- FACTORY_NOTOUCH_COUNTS가 uint16_t(최대 0xFFFF = 65535)이고
- MARGIN_UP이 uint16_t이며 두 값의 합이 0xFFFFFFFF(uint32 최대)를 초과하면 wrap-around → `hi ≈ 0` → 상한 조건 `counts <= hi`가 사실상 항상 거짓 → 게이트 영구 거부

실제 IQS323 counts가 12비트 또는 16비트이므로 정상 범위에서 이 오버플로가 발생하기는 어렵다 [추정]. 그러나 **MARGIN_UP을 잘못된 큰 값으로 설정하면 발생 가능**하고, 현재 `MARGIN_UP=0u` 기본값은 안전하지만 실측_A 이후 실측 기반으로 값을 설정할 때 이 위험이 잠재한다.

59 §3 빌드가드 세트에 MARGIN_STRICT에 대한 `#error`는 있으나 MARGIN_UP에 대한 가드가 없다:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && \
    (TDC_TOUCH_NOTOUCH_MARGIN_STRICT >= TDC_TOUCH_FACTORY_NOTOUCH_COUNTS)
#error "NOTOUCH_MARGIN_STRICT must be < FACTORY_NOTOUCH_COUNTS (underflow risk)"
#endif
/* [누락] hi 오버플로 가드 없음 */
```

더불어 59 §4 Phase 1의 gate_check() 런타임 코드에도 상한 오버플로 방어가 없다:
```c
if (TDC_TOUCH_FACTORY_NOTOUCH_COUNTS <= TDC_TOUCH_NOTOUCH_MARGIN_STRICT) {
    return false;  /* lo 방향만 체크 */
}
```

**요구 조치**:
1. §3 빌드가드 세트에 추가:
```c
#if TDC_TOUCH_NOTOUCH_GATE_ENABLE && \
    ((uint32_t)TDC_TOUCH_FACTORY_NOTOUCH_COUNTS + TDC_TOUCH_NOTOUCH_MARGIN_UP > 0xFFFFu)
#error "FACTORY_NOTOUCH_COUNTS + NOTOUCH_MARGIN_UP overflows uint16 range (hi overflow risk)"
#endif
```
2. §4 Phase 1 gate_check() 런타임 이중방어에 hi 방향 추가.

### 신규_2 — R3_CHARGING 30초 타이머 기준 및 리셋 시점이 59 전체에서 단 한 번도 확정·코드 근거로 제시되지 않았다 [고위험]

**59 §4 Phase 3** 기술: "R3_CHARGING: 충전 중 30초 주기 Re-ATI" 및 확인_13(ATI_Error 후 R3_CHARGING 타이머 리셋 정책). 확인_14(R3_CHARGING 게이트 기준 정책).

**엣지 공격**: "30초"라는 주기 값의 출처가 v1~v3 전 로그를 통해 **단 한 번도 데이터시트 또는 코드 근거로 제시되지 않았다** [추정]. 이 숫자는 브레인스토밍 발산 단계에서 계획 페르소나(12_계획_공장캘리저장 또는 18_계획_통합아키텍처)가 임의 제안한 값이 그대로 종합에 흡수됐을 가능성이 높다.

더 심각한 것은 **타이머 기준이 무엇인지 코드 어디에도 없다**는 것이다:
- 현재 `tdc_touch_process()`의 폴링 주기 200ms(`TDC_TOUCH_POLL_INTERVAL`)에서 30초 = 150폴링 카운트다.
- 이 카운터를 정적 변수로 관리해야 하는데, 59가 제시한 코드 어디에도 이 카운터 변수가 등장하지 않는다.
- `df_Connected` 상태 변화(충전 시작/중단) 시 타이머를 리셋해야 하는지, 현재 충전 상태면 계속 누적하는지 정책이 없다.
- 배터리 방전(<40%) → POWER_OFF → 절전 → WDT 재부팅 시 타이머 카운터는 MCLR로 소멸한다. 이는 타이머를 EEPROM에 저장할 필요가 없음을 의미하지만, 동시에 절전 직전에 Re-ATI 기회를 강제로 잃는다.

**확인_14가 "R3_CHARGING 게이트 기준: 공장값 정적 vs 마지막 Re-ATI 후 counts 동적 업데이트 정책"을 미해결로 두었는데**, 이 정책이 결정되지 않으면 "30초 주기"라는 숫자 자체의 설계 의미도 불완전하다.

**요구 조치**:
1. "30초" 출처를 데이터시트 권장 또는 실측 기반으로 명시하거나, [임의추정] 표기 후 실측_F(Re-ATI 주기 최적값 실측) 블로킹으로 등록.
2. R3_CHARGING 타이머 구현 위치(tdc_touch_process() 내 정적 카운터), 리셋 조건(충전 시작·ATI_Error·절전 진입), 타이머 기준 정책(§4 Phase 3 설계에)을 명시.

### 신규_3 — ATI_Error 소진 후 "Fixed 기저 유지"가 공장값 MULT/COMP인지 ATI 오염값인지 미확정 [고위험]

**59 §4 Phase 3**: "ATI_Error 후 재시도 상한 N회(제안 3회, [확정 필요]) + 소진 시 Fixed 기저 유지 + RTT 경보."

**엣지 공격**: "Fixed 기저 유지"라는 표현이 무엇을 의미하는지 불명확하다. 가능한 상태가 두 가지이기 때문이다:

**상태_A**: ATI_Error가 발생했다는 것은 Re-ATI 시도 중 실패했다는 의미다. `re_ati_trigger()` 후 ATI_Error가 set되면, IQS323 내부 MULT/COMP는 어떤 상태인가?
- 데이터시트 §5.11(ATI Error): "ATI_Error set → ATI 결과 불신뢰" — 이 시점 IC의 MULT/COMP가 이전 성공한 값(공장값 또는 직전 성공 Re-ATI 값)을 유지하는지, 아니면 중간 수렴 실패값으로 변경됐는지 데이터시트에 명시가 없다 [확정 필요].

**상태_B**: N회 소진 후 "Fixed 기저 유지" = `write_ati_compensation()`으로 공장 MULT/COMP를 IC에 재write한다는 의미인가, 아니면 IC가 이미 보유한(오염 가능한) MULT/COMP를 그대로 쓰는 "아무것도 안 함"인가?

59 §4 Phase 3 기술 어디에도 "N회 소진 시 공장 MULT/COMP를 IC에 재write해 알려진 안전값으로 복원한다"는 명시가 없다. 만약 "아무것도 안 함"이 의도라면, ATI_Error 중 IC가 MULT/COMP를 부분 변경했을 경우 Fixed 기저가 오염값이 된다.

이것은 층위 0(Fixed 기저 = 공장 MULT/COMP 항상 보장)의 전제를 파괴할 수 있다.

**요구 조치**: Phase 3 ATI_Error N회 소진 처리를 "소진 시 `write_ati_compensation(공장값)`을 IC에 명시 재write해 MULT/COMP를 알려진 안전값으로 복원 후 RTT 경보" 로 구체화. 데이터시트 §5.11에서 ATI_Error 시 IC 내부 MULT/COMP 상태 확인 필수(확인_16 신규).

### 신규_4 — 비블로킹 Re-ATI 중 NOT_TOUCH 강제 구간에서 롱터치 카운터 오동작 [중위험]

**59 §4 Phase 3 비블로킹 3단계 구조**:
```
② 폴링 중 s_ati_in_progress=true이면 터치 판정 결과 NOT_TOUCH 강제
```

**엣지 공격**: `tdc_touch_process()` 내부의 롱터치 감지 로직(`TDC_TOUCH_LONG_TOUCH_MS = 2400ms`)은 연속 TOUCH 상태 누적 카운터 기반이다. `s_ati_in_progress=true` 구간에서 NOT_TOUCH를 강제하면 롱터치 카운터가 초기화된다.

시나리오:
1. 사용자가 2200ms 롱터치 중 (카운터 2200ms 누적)
2. R3_CHARGING 주기 도달 → `re_ati_trigger()` → `s_ati_in_progress=true`
3. 폴링 2회(400ms, 최악 2.3초) 동안 NOT_TOUCH 강제 → **롱터치 카운터 리셋**
4. Re-ATI 완료 후 사용자가 계속 누르고 있어도 카운터 처음부터 다시 시작

이 경우 2400ms 롱터치(절전 진입)를 유발하려면 Re-ATI 완료 후 추가 2400ms를 기다려야 한다 → 롱터치 응답 지연 최악 2400 + 2300 = 4700ms [추정].

반대로:
1. 사용자가 2350ms 롱터치 중 → 롱터치 인식 임박
2. 마침 Re-ATI 발행 → NOT_TOUCH 강제 → 롱터치 카운터 리셋
3. 사용자가 계속 누르지 않으면 절전 미진입 → 오동작

59 전체 로그(v1~v3)에서 "Re-ATI 중 롱터치 카운터 관리" 관련 언급이 단 한 줄도 없다 [확정 필요: tdc_touch_process() 롱터치 카운터 관리 위치].

**요구 조치**: Phase 3 비블로킹 3단계 구조에 "s_ati_in_progress=true 구간 동안 롱터치 카운터를 freeze(증가 중단, 리셋 금지)하거나, Re-ATI 완료 후 카운터를 이전 누적값으로 복원하는 설계" 명시. Phase 3 착수 전 확인_17(신규) 등록.

### 신규_5 — 블로킹_K(MAX_WAIT_MS_FOR_WINDOW_CLOSE)가 코드에 이미 존재할 수 있는데 grep 미실시 [중위험]

**59 §5 블로킹_K**: "MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수 실제값 — `tdc_drv_iqs323.h` grep 확인"

**엣지 공격**: 59는 블로킹_K를 신규 미지수로 등록하면서 해소 방법으로 "tdc_drv_iqs323.h grep 확인"이라고 했다. 그런데 이것은 **현 세션 내 즉시 가능한 단순 grep 작업**이며, v3 전 로그(57_엣지 포함)를 통해 이 상수가 코드에 존재하는지 여부를 단 한 번도 직접 확인하지 않았다.

만약 이 상수가 `tdc_drv_iqs323.c` 또는 `.h` 내에 이미 정의돼 있다면, 블로킹_K는 즉시 해소 가능한 사이비 블로킹이다. 반대로 존재하지 않는다면 wait_rdy_window_closed() 함수 내부에서 하드코딩된 값이나 루프 카운터 등 다른 형태로 구현됐을 가능성을 탐색해야 한다.

더 나아가 §2-7의 "최악 ~2.3초" 계산은 `wait_rdy_window_closed()` 최악 대기 시간을 "[확정 필요: MAX_WAIT_MS_FOR_WINDOW_CLOSE]"로 남겨 두었는데, 이 상수를 확인하지 않고 "~2.3초"를 확정값처럼 Phase 3 WDT 설계 근거로 사용하는 것은 계산 오류의 위험이 있다.

WDT 갱신 삽입(Phase −1 긴급)이 이미 진행됐다면 이 계산 오류는 WDT 주기 설정에 영향을 줄 수 있다.

**요구 조치**: 블로킹_K를 "즉시 grep 해소 가능" 우선순위로 격상. wait_rdy_window_closed() 함수 내부 타임아웃 구조를 코드 직접 확인(grep `wait_rdy` + `WINDOW_CLOSE` + `MAX_WAIT`) 후 블로킹_K 해소 또는 하드코딩값 확정. Phase −1 WDT 갱신 삽입의 최악 시간 근거도 이 결과로 재정정.

## 4. 아키텍처 원리 재확인

**"공장 절대 기준으로 노터치를 판별하고, 노터치가 확인된 순간에만 Re-ATI를 허용한다."**

3차 재검증(신규_1~5)에서도 이 원리 자체는 기각되지 않았다. 발굴된 결함은 모두 구현 세부(빌드가드 대칭성·타이머 미설계·ATI_Error 복구 경로·롱터치 카운터 상호작용·상수 미확인)다.

## 5. 3차 재검증 후 수렴도 판정

**부분 수렴 유지** — 2차 재검증과 동일 판정.

## 6. 핵심 6줄

1. **[치명] gate_check() 상한 `hi` 오버플로 가드가 59 §3 빌드가드 세트에서 누락**됐다 — `(uint32_t)FACTORY_NOTOUCH_COUNTS + MARGIN_UP`이 uint16 범위를 초과하면 wrap-around로 게이트 영구 거부가 발생하며, 59는 lo 방향 언더플로 #error만 추가하고 hi 방향은 대칭적으로 처리하지 않았다(신규_1).
2. **[고위험] R3_CHARGING "30초"는 v1~v3 전 로그에서 데이터시트·코드 근거 없이 등장한 임의 추정값**이다 — 타이머 카운터 구현 위치·리셋 조건·확인_14(게이트 기준 정책)가 모두 미결인 상태에서 "30초 주기"가 Phase 3 설계의 기정 수치로 반복 인용되고 있어 구현 착수 시 바로 공백이 드러난다(신규_2).
3. **[고위험] ATI_Error N회 소진 후 "Fixed 기저 유지"가 공장 MULT/COMP를 IC에 명시 재write하는 것인지 IC 내부 오염값을 방치하는 것인지 59 전체에서 기술 없다** — ATI_Error 중 IC MULT/COMP가 중간 실패값으로 변경됐을 경우 층위 0(Fixed 기저 공장값 보장)이 파괴되며, 데이터시트 §5.11에서 ATI_Error 시 IC 내부 상태 확인이 확인_16으로 신규 필요하다(신규_3).
4. **[중위험] 비블로킹 Re-ATI 중 NOT_TOUCH 강제(s_ati_in_progress=true)가 롱터치 카운터를 리셋시켜 절전 진입 지연 최악 4700ms 또는 롱터치 오인식을 유발한다** — v1~v3 전 로그에서 롱터치 카운터와 Re-ATI 상호작용이 단 한 줄도 기술되지 않았으며, Phase 3 구현 전 확인_17(롱터치 카운터 freeze 설계)이 필요하다(신규_4).
5. **[중위험] 블로킹_K(MAX_WAIT_MS_FOR_WINDOW_CLOSE)는 tdc_drv_iqs323.h grep으로 즉시 해소 가능한 사이비 블로킹일 수 있는데 3라운드까지 직접 확인하지 않았다** — 이 상수가 이미 코드에 있다면 블로킹_K는 즉시 해소되고 §2-7의 "~2.3초" 계산도 재확정되며, Phase −1 WDT 갱신 삽입 주기 근거도 정정된다(신규_5).
6. **[수렴도] 신규 약점 발굴 수가 2차 9건→3차 5건으로 감소해 수렴 방향이나 치명·고위험 항목 잔존으로 수렴 확정 불가** — 4차 재검증보다는 신규_5(블로킹_K 즉시 grep) + Phase −1(WDT·SATURATE) 실행 → 블로킹 해소 실측 순서로 진행이 권고된다.
