## 2. 신규 약점 발굴

### 약점_1 — TDC_BOARD_VARIANT별 MULT/COMP 다중화와 EEPROM 공장 캘리브레이션 경로의 충돌 미해결 [관점_H, 치명]

**59 종합의 주장 (§4 Phase 2, §5 블로킹_F)**:

> "write_ati_compensation() 시그니처 변경(인자 추가) 또는 정적 변수 신설 방법 중 선택"
> "블로킹_F: write_ati_compensation() 내 레지스터 write 전체 목록(L696~) + 시그니처 변경 방법 결정"

**코드 ground truth 확인** (`tdc_drv_iqs323.c:650~690`):

현재 `write_ati_compensation()`은 **`TDC_BOARD_VARIANT`(0=MINI/1=DEVELOP/2=PACKAGE)에 따라 컴파일 타임에 다른 MULT/COMP 상수를 선택**하는 `#if` 분기 구조다. 코드 직접 확인:

```c
#if (TDC_BOARD_VARIANT == TDC_BOARD_VARIANT_MINI)
#define TDC_DRV_IQS323_ATI_MULT_MSB  0x5A
#define TDC_DRV_IQS323_ATI_COMP_LSB  0x00
...
#elif (TDC_BOARD_VARIANT == TDC_BOARD_VARIANT_PACKAGE)
#define TDC_DRV_IQS323_ATI_MULT_MSB  0x5C
#define TDC_DRV_IQS323_ATI_COMP_LSB  0xEF
```

**공격**:

59 종합의 "선택지_1: 인자 추가" 또는 "선택지_2: 정적 변수 신설"은 단일 보드 기준만 고려한 설계다. 실제 코드는 `TDC_BOARD_VARIANT`로 **3개 보드 변형의 MULT/COMP를 컴파일 타임에 다르게 선택**한다. EEPROM 공장 캘리브레이션을 도입하면:

1. **MINI 보드**: 공장 캘리브 MULT/COMP = EEPROM에서 런타임에 로드
2. **PACKAGE 보드**: 동일 구조, 그러나 현재 `0x5C/0xEF`와 다른 개별 보드 측정값이 EEPROM에 저장됨
3. **단일 펌웨어 바이너리 + BOARD_VARIANT 컴파일**: 어느 변형 빌드이냐에 따라 컴파일 타임 상수가 다르고, EEPROM 로드값은 런타임에 결정 → 두 경로가 동시에 존재

문제: **Phase 2 구현 후 `write_ati_compensation()`이 EEPROM 로드값(런타임)과 BOARD_VARIANT 상수(컴파일타임) 중 어느 쪽을 우선하는가?** 59 종합의 어디에도 이 우선순위가 명시되지 않았다.

더 심각한 문제: "공장 캘리브레이션 1회 수행 → EEPROM 저장"이라는 설계에서 BOARD_VARIANT마다 별도 캘리브를 수행하는지, 아니면 모든 보드가 동일 EEPROM 슬롯을 공유하는지가 미결이다. 만약 PACKAGE 보드에서 캘리브한 값이 MINI 보드에 EEPROM으로 로드되면 부정확한 게인이 적용된다.

**결론**: 59 종합의 Phase 2 EEPROM 로드 설계는 BOARD_VARIANT 다중 보드 환경을 가정하지 않은 단일 보드 환경 환각이다. BOARD_VARIANT별 캘리브 슬롯 분리 또는 "캘리브 결과는 BOARD_VARIANT 불문 해당 보드 전용" 정책 명시가 Phase 2 착수 전 필수다.

### 약점_2 — SLEEP ATI 보상값(`TDC_DRV_IQS323_SLEEP_ATI_*`) 경로가 Phase 설계 전체에서 완전 누락 [관점_N, 치명]

**코드 ground truth 확인** (`tdc_drv_iqs323.c:657~690`):

```c
/* 절전 환경 ATI 고정 보상값 — 보드 변종별 normal ATI와 동일값 (절전 전용 실측 미적용). */
#define TDC_DRV_IQS323_SLEEP_ATI_SETUP_LSB 0x08
#define TDC_DRV_IQS323_SLEEP_ATI_MULT_LSB  0x82
#define TDC_DRV_IQS323_SLEEP_ATI_MULT_MSB  0x5A   /* MINI 기준 */
#define TDC_DRV_IQS323_SLEEP_ATI_COMP_LSB  0x00
#define TDC_DRV_IQS323_SLEEP_ATI_COMP_MSB  0x58
```

즉 현재 코드에는 **normal 환경과 절전(SLEEP) 환경에 각각 독립된 MULT/COMP 상수 세트**가 존재한다(`_SLEEP_ATI_*` 접두어). 이는 `tdc_drv_iqs323_apply_sleep_settings()`에서 다른 경로로 사용된다.

**공격**:

59 종합의 Phase 2(EEPROM 공장 캘리브레이션 저장·로드)·Phase −1·Phase 0~4 전체 어디에도 `SLEEP_ATI_*` 상수 세트에 대한 설계가 없다. 구체적으로:

1. **공장 캘리브 수행 시**: noTouch 상태에서 auto-ATI → MULT/COMP 산출 → EEPROM 저장. 이 저장값은 normal 환경 기준이다.
2. **절전 진입 시**: `tdc_drv_iqs323_apply_sleep_settings()`에서 `SLEEP_ATI_*` 상수를 write한다. 현재 이 값은 normal ATI와 동일값(주석 "절전 전용 실측 미적용")이지만, 공장 캘리브레이션 후에는 어떤 값을 쓸 것인가?
3. **Phase 2 도입 후 절전 경로**: EEPROM에서 normal MULT/COMP는 로드하지만, `apply_sleep_settings()`는 여전히 컴파일 타임 `SLEEP_ATI_*` 상수를 write한다 → **절전 환경에서 공장 캘리브 결과가 적용되지 않는 설계 공백**.

4. **절전 RESEED 게이트화**(§1-2): 블로킹_G 해소 후 절전 RESEED 게이트화를 결정하겠다고 했으나, 게이트 기준(FACTORY_NOTOUCH_COUNTS)이 절전 환경에서도 동일하게 유효한지 여부가 미분석이다. 절전 시 감도 파라미터(`THRESHOLD=255`)가 노말과 다르므로, 동일 noTouch counts 기준으로 게이트하면 절전 환경에서 오판 가능성이 있다.

**결론**: Phase 2 공장 캘리브레이션 설계가 normal 경로만 다루고 SLEEP 경로를 완전히 누락한 환각 공백이다. 절전 진입 경로(`apply_sleep_settings`)의 MULT/COMP 처리 방식을 Phase 2 설계에 포함해야 한다 [확정 필요].

### 약점_3 — `func_cradle_lid_closed_loop()` 호출 위치가 폴링 루프 **외부**라는 코드 근거를 59 종합이 제시하지 않은 채 Phase 4 설계를 진행 [관점_U, 고위험]

**57_엣지 신규_D 반영 주장 (59 종합 §4 Phase 4)**:

> "삽입점: main.c:743 `func_cradle_lid_closed_loop()` 직전 (57_엣지 신규_D: 742+1줄 오차 확인)"
> "호출 위치가 `tdc_touch_process()` 폴링 루프 내/외 여부 + I2C 윈도우 상태 확인 (확인_8 확장)"

**코드 ground truth 확인** (`main.c:739~745`):

```c
/* 크래들 뚜껑 닫힘 첫 감지 → 약 절전 루프 (ISD 연결 중이면 차단) */
if (systemState.cradleLidClosed && !isd_state.conneded_ISD)
{
    led_force_fade_off(); /* fade-out ISR 완료 후 LED 완전 소등 */
    func_cradle_lid_closed_loop();
    /* 도달 불가 — 루프 내 SYS_WATCHDOG_RESET()으로 재부팅 */
}
```

**공격**:

코드를 직접 확인하면 `func_cradle_lid_closed_loop()` 호출은 **메인 루프(while 루프) 내부**이며, `tdc_touch_process()` 폴링 호출과 동일 루프 안에 있다. 57_엣지가 "확인_8에 폴링 루프 내/외 여부 추가"를 요구했고, 59 종합이 "확인_8 확장"으로 반영했다고 선언했으나, 실제 코드에서 이 호출이 메인 루프 안인지 밖인지를 명시하지 않았다.

더 중요한 것은: `func_cradle_lid_closed_loop()` 직전 삽입점에서 Phase 4 Re-ATI를 수행하려면, 그 시점에 **마지막 `tdc_touch_process()` 폴링이 이미 완료된 후**이며 IQS323은 폴링 간격(200ms) 중 임의 시점에 있다. 이 시점에 `re_ati_trigger()` → `wait_re_ati_done()`을 호출하면:

- 마지막 폴링 직후이면 RDY 윈도우가 닫혀 있어 `force_window_open()` 필요 → 최악 130ms+
- `func_cradle_lid_closed_loop()` 진입 후에는 IQS323 폴링이 완전 중단됨 → Re-ATI **전에** 삽입해야 하는데 통신 윈도우 열림 보장이 없음

59 종합은 "확인_8 확장"이라는 확인 항목으로만 처리하고, 이 시점의 I2C 윈도우 상태와 force_window_open 비용을 Phase 4 설계에 명시하지 않았다. `func_cradle_lid_closed_loop()` 직전이 Re-ATI 수행에 적절한 위치인지 코드 구조상 검증이 필요하다 [확정 필요: 확인_8].

### 약점_4 — R3_CHARGING 30초 타이머 기준 시점과 타이머 리셋 정책의 환각 [관점_H, 고위험]

**59 종합의 주장 (§4 Phase 3)**:

> "ATI_Error 후 re_ati_trigger() 재발행 시 30초 타이머 리셋 여부 명시 (확인_13 신규: R3_CHARGING 타이머 리셋 정책)"

**공격**:

R3_CHARGING의 "30초 타이머"는 v3 에이전트 로그 전체를 통해 발원지가 불명확하다. 구체적으로:

1. **30초 기준 코드 근거 없음**: `tdc_touch.c`·`main.c`·`tdc_touch_config.h` 어디에도 "30초 타이머" 관련 코드·상수가 없다. v3 Phase 계획에서 R3_CHARGING을 "충전 중 30초마다 Re-ATI 시도"로 기술했으나, 이 30초는 설계 제안이지 기존 코드 근거가 아니다.

2. **타이머 구현 방법 미기술**: 30초 주기 타이머를 어떤 메커니즘으로 구현하는가? `main.c`의 메인 루프는 `SYS_WAIT_FOR_INTERRUPT` 기반으로 인터럽트 도달마다 실행된다. 고정 주기 타이머가 없으므로 폴링 횟수 카운터(`200ms × N회 = 30초`)를 직접 구현해야 한다. 59 종합은 "30초 타이머"를 마치 기존 인프라가 있는 것처럼 기술했으나, 이 타이머 구현 자체가 신규 코드다 [확정 필요].

3. **충전기 연결(`df_Connected`) 감지 경로와 R3_CHARGING 활성화 조건**: `systemControl.c:162`에서 충전기 연결 시 절전 진입 안 함이 확인됐으나, R3_CHARGING이 ① "충전 중 진입" 시 즉시 시작인지 ② 일정 안정화 후 시작인지 정책이 없다. 충전기 연결 순간 counts가 불안정할 수 있다 [추정].

4. **확인_13 "타이머 리셋 정책"**: ATI_Error 후 타이머를 리셋하면 에러 빈발 환경에서 Re-ATI가 영구 지연될 수 있다. 리셋 안 하면 에러 직후 즉시 재시도가 반복될 수 있다. 59 종합은 이를 확인_13으로만 등록하고 Policy 방향을 제시하지 않았다.

**결론**: "30초 타이머"는 기존 코드 기반이 없는 신규 설계 요소인데, 59 종합이 마치 구현 예정 사항처럼 기술한 환각이다. 타이머 구현 방법, 기준 시점, ATI_Error 시 리셋 정책을 Phase 3 착수 전 설계 문서에 명시해야 한다.

### 약점_5 — 선택지_1(인자 추가) 채택 시 SLEEP 경로 `apply_sleep_settings()` → 절전 MULT/COMP write 분기 미설계 [관점_N, 고위험]

**59 종합의 주장 (§2-5)**:

> "선택지_1: write_ati_compensation()에 MULT/COMP 인자를 추가"
> "→ static bool write_ati_compensation(uint8_t mult_lsb, uint8_t mult_msb, uint8_t comp_lsb, uint8_t comp_msb)"

**공격**:

`write_ati_compensation()` 시그니처를 인자 추가로 변경하면, 이 함수를 호출하는 **모든 호출 경로**의 인자를 일관되게 수정해야 한다. 현재 `write_ati_compensation()`은 `tdc_drv_iqs323_apply_settings()`에서만 호출되는 것처럼 보이지만, 절전 환경에서는 **`tdc_drv_iqs323_apply_sleep_settings()`도 MULT/COMP를 write**한다(`SLEEP_ATI_*` 상수 사용).

절전 경로:
- `apply_sleep_settings()`는 `write_ati_compensation()`을 호출하는가, 아니면 `SLEEP_ATI_*` 상수를 직접 레지스터에 write하는가?

코드 확인 결과: `SLEEP_ATI_*` 상수가 별도로 존재한다는 것은 `apply_sleep_settings()`가 `write_ati_compensation()`과 **분리된 경로**를 가진다는 뜻이다. 즉 선택지_1 인자 추가가 `apply_settings()` 경로만 수정하면, 절전 경로는 여전히 컴파일 타임 `SLEEP_ATI_*` 상수를 사용한다.

59 종합 §4 Phase 2의 EEPROM 로드 설계는 `apply_settings()` 경로만 언급하고, 절전 경로에서 공장 캘리브 SLEEP MULT/COMP를 어떻게 적용할지 완전 누락됐다. 이는 약점_2와 연동되는 같은 공백의 다른 측면이다.

**추가 발견**: `write_ati_compensation()` 인자 추가 시 절전 경로에서는 다른 MULT/COMP 값(SLEEP 환경 보정)을 전달해야 할 수 있다 — 공장 캘리브 시 SLEEP 환경 별도 측정이 필요한지도 미결이다.

---

### 약점_6 — 59 종합 §2-7의 ~2.3초 계산에서 `read_register()` 1회당 `force_window_open()` 2회 호출이라는 전제의 근거가 코드와 불일치 가능 [관점_H, 중간]

**59 종합의 주장 (§2-7)**:

> "read_register() 1회당 wait_rdy_window_closed() 2회 호출(코드 :244, :261)이 49_종합의 '~1.9초' 계산에서 누락됐다."
> "재산출: (130.5ms + 100ms) × 10 ≈ 2.3초"

**공격**:

56_할루시(약점_2)와 54_통신전력이 ~1.9초 계산의 근거 부재를 지적했고, 59 종합은 "~2.3초"로 정정했다. 그러나 이 정정도 같은 종류의 약점을 가진다:

1. **`force_window_open()` vs `wait_rdy_window_closed()` 구분**: 59 종합은 "wait_rdy_window_closed() 2회 호출"을 추가 비용으로 산정했다. 그러나 `wait_rdy_window_closed()`의 최악 시간(`MAX_WAIT_MS_FOR_WINDOW_CLOSE` — 블로킹_K)이 여전히 [확정 필요] 상태다.

2. **블로킹_K 미해소**: 59 종합 §5 블로킹 목록 맨 아래에 "블로킹_K: MAX_WAIT_MS_FOR_WINDOW_CLOSE 상수 실제값 — `tdc_drv_iqs323.h` grep 확인"이 신규 추가됐다. 즉 2.3초 계산의 핵심 파라미터가 아직 [확정 필요]다.

3. **~2.3초 계산 근거 재구성**: 블로킹_K가 해소되지 않은 상태에서 "~2.3초"를 확정으로 표기한 것은, 56_할루시가 비판한 "검증 없는 새 수치 도입"과 동일한 오류 패턴이다. 계산식은 제시됐지만 핵심 변수(MAX_WAIT_MS)가 [확정 필요]이므로 ~2.3초도 [추정] 또는 [확정 필요]로 표기했어야 한다.

4. **WDT 리셋 위험 평가 연동**: ~2.3초가 실제 맞는 값이라면 WDT 타임아웃(일반적으로 2초대)과 비교해 Phase −1 긴급 수정의 필요성이 달라진다. MAX_WAIT_MS 실측값 없이 위험도를 "잠재 현장 버그"로 단정한 것은 과소·과대 평가 중 하나다 [확정 필요: 블로킹_K 해소 후 재평가].

## 6. 핵심 6줄

1. **[치명] BOARD_VARIANT별 MULT/COMP 다중화 미설계(약점_1)**: 현재 코드는 `TDC_BOARD_VARIANT`(0/1/2)마다 다른 컴파일타임 ATI 상수를 선택한다. 59 종합의 EEPROM 공장 캘리브 설계는 단일 보드 가정이며, 다른 변형 보드에 같은 EEPROM 슬롯값이 로드될 경우 게인 불일치가 발생하는 다중화 경로를 전혀 다루지 않았다 — Phase 2 착수 전 BOARD_VARIANT별 캘리브 슬롯 분리 정책 필수.

2. **[치명] SLEEP ATI 경로 완전 누락(약점_2)**: 코드에는 `TDC_DRV_IQS323_SLEEP_ATI_*` 상수 세트가 별도로 존재하며, 절전 환경 MULT/COMP는 `apply_sleep_settings()` 경로를 통해 적용된다. Phase 2 공장 캘리브 설계는 노말(`apply_settings()`) 경로만 다루고 SLEEP 경로를 완전히 누락했다 — 절전 환경에서 공장 캘리브 결과가 적용되지 않는 구조 공백이다.

3. **[고위험] func_cradle_lid_closed_loop 삽입점 I2C 상태 미확인(약점_3)**: 코드 확인 결과 이 호출은 메인 폴링 루프 내부 조건 분기로 호출되나, 그 시점의 IQS323 RDY 윈도우 상태가 미분석이다. `wait_re_ati_done()` (~2.3초)을 이 직전에 삽입하면 force_window_open 비용이 추가되고, 삽입점 자체가 폴링 중간 임의 시점이라 통신 상태 보장이 없다 — 확인_8이 "확인 항목"으로만 등록됐을 뿐 Phase 4 설계에 반영되지 않았다.

4. **[고위험] R3_CHARGING 30초 타이머 구현 방법 환각(약점_4)**: "30초 타이머"는 기존 코드에 존재하지 않는 신규 설계 요소로, 메인 루프 인터럽트 기반 구조에서 별도 폴링 카운터 구현이 필요하다. 59 종합은 타이머를 기존 인프라처럼 기술하고 구현 방법을 명시하지 않았으며, ATI_Error 시 리셋 정책(확인_13)도 방향 없이 등록만 했다.

5. **[고위험] 선택지_1 인자 추가 시 SLEEP 경로 분기 미설계(약점_5)**: `write_ati_compensation()` 시그니처를 인자 추가로 변경하면 절전 경로(`apply_sleep_settings()`)의 SLEEP MULT/COMP write 분기도 동시에 설계해야 한다. 59 종합의 선택지_1 권고는 노말 경로만 다루고 SLEEP 경로 처리 방법을 명시하지 않았다 — 약점_2(SLEEP ATI 경로 누락)의 구현 레이어 연장선이다.

6. **[중간] ~2.3초 수치의 블로킹_K 미해소 상태 단정(약점_6)**: 56_할루시의 ~1.9초 비판을 정정해 ~2.3초로 재산출했으나, 핵심 파라미터(`MAX_WAIT_MS_FOR_WINDOW_CLOSE`, 블로킹_K)가 아직 [확정 필요]다. 블로킹_K 해소 전 ~2.3초도 [추정]으로 표기했어야 하며, WDT 위험도 평가도 이 값에 의존하므로 재평가 조건이 Phase 계획에 명시되어야 한다.
