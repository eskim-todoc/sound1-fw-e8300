# 45 — 재검증 라운드1 (회귀 관점)

**TL;DR**: 30_종합-1차를 회귀 관점에서 재공격. `write_ati_compensation()`이 ATI_SETUP까지 덮어쓰는 사실을 종합이 누락해 "항상 실행 유지" 결론이 Phase 3 Re-ATI와 구조적 충돌을 일으킨다. `s_boot_touch_ignore` 기존 게이트가 종합 계획과 어떻게 공존·충돌하는지 전혀 분석되지 않았다. `TDC_TOUCH_RTT_TUNING` 분기가 있는 `write_ati_compensation()`의 내부 구조가 "단순 MULT/COMP write"로 단정됐으나, 이 define 분기 유무가 Phase 1 게이트 설계의 전제를 바꾼다.

## 0. 공격 범위 및 방법

- **타깃**: `30_종합-1차.md` §2~§8 전체
- **관점**: 회귀 — 기존 동작을 파괴하거나, 종합이 "해소됐다"고 선언한 결함이 실제 코드에서 아직 열려 있는 경로 발굴
- **근거 기준**: 코드 라인 직접 확인 우선, 추정에는 [추정] 표기

## 결함 목록

### [회귀_1] `write_ati_compensation()`이 ATI_SETUP(0x36 — Mode=Disabled)을 **함께 write**한다 — "항상 실행 유지" 결론이 Phase 3 Re-ATI를 무력화한다 (치명)

**종합의 주장**: §2-3 설계에서 "write_ati_compensation()은 항상 실행 유지(Fixed 기저)" — Phase 3에서 Re-ATI를 활성화한 뒤에도 이 함수를 매 부팅마다 무조건 실행한다고 명시(§2-1 층위 0, §8 결론 3번).

**코드 근거**:
```c
/* iqs323.c:696~732, write_ati_compensation() 내부 */
write_register(TDC_DRV_IQS323_REG_ADDR_SENSOR0_ATI_SETUP,
               TDC_DRV_IQS323_ATI_SETUP_LSB,   /* 0x08: ATI Mode=Disabled */
               TDC_DRV_IQS323_ATI_SETUP_MSB);
write_register(TDC_DRV_IQS323_REG_ADDR_SENSOR0_ATI_MULT, ...);
write_register(TDC_DRV_IQS323_REG_ADDR_SENSOR0_ATI_COMP, ...);
```

ATI_SETUP_LSB=0x08은 bits[2:0]=000 = **ATI Mode=Disabled**다(`iqs323.c:651`). 즉 `write_ati_compensation()`는 MULT/COMP뿐 아니라 **ATI Mode를 Disabled로 고정**하는 레지스터까지 write한다.

**회귀 경로**: Phase 3에서 `TDC_TOUCH_ATI_FULL_ENABLE=1`을 활성화해 Re-ATI를 허용하도록 ATI_SETUP을 변경해도, 다음 재부팅 시 `tdc_drv_iqs323_apply_settings()`가 호출되면 `write_ati_compensation()`이 ATI_SETUP을 다시 Disabled(0x08)로 덮어쓴다. Phase 3 재부팅 생존성이 완전히 깨진다.

Phase 4 크래들 Re-ATI 후 EEPROM 저장을 권고(§2-1 층위 4)한 것도 이 덮어쓰기가 있으면 의미가 없다 — Re-ATI 결과를 EEPROM에 저장해도, 재부팅 시 `write_ati_compensation()`이 ATI_SETUP을 Disabled로 고정해 저장된 ATI 결과가 IC에 적용되지 않는다.

**종합의 누락**: `write_ati_compensation()` 내부에 ATI_SETUP write가 포함됐다는 사실을 30_종합이 §2-3에서 명시하지 않았다. "MULT/COMP 고정값 write 함수"로 단순화해 기술하나, 실제 함수는 ATI_SETUP write를 선두로 실행한다(`iqs323.c:700`이 `iqs323.c:721·726`보다 먼저).

**요구 조치**: Phase 3 활성화 시 `write_ati_compensation()` 내부 ATI_SETUP write를 조건부(ATI_FULL_ENABLE=0일 때만 Disabled 고정, ATI_FULL_ENABLE=1일 때는 ATI Mode=Full 또는 스킵)로 분기해야 한다. 이 분기 없이 "항상 실행 유지"는 Phase 3 자체를 무의미하게 만든다.

### [회귀_2] `TDC_TOUCH_RTT_TUNING` 분기 — 종합의 "FACTORY_NOTOUCH_COUNTS 단일 소스" 설계가 RTT 튜닝 경로와 충돌한다 (심각)

**코드 근거**:
```c
/* iqs323.c:705~730, write_ati_compensation() 내부 */
#if TDC_TOUCH_RTT_TUNING
    uint8_t m_l = s_tdc_normal_tuning.ati_valid
                  ? s_tdc_normal_tuning.mult_lsb
                  : TDC_DRV_IQS323_ATI_MULT_LSB;
    /* ... */
#else
    write_register(TDC_DRV_IQS323_REG_ADDR_SENSOR0_ATI_MULT,
                   TDC_DRV_IQS323_ATI_MULT_LSB, ...);
#endif
```

**회귀 경로**: `TDC_TOUCH_RTT_TUNING=1` 빌드 환경에서 `s_tdc_normal_tuning.ati_valid=true`이면 MULT/COMP가 RTT 런타임 튜닝값으로 대체된다. Phase 1 노터치 게이트에서 `FACTORY_NOTOUCH_COUNTS`와 비교하는 counts는 **어느 MULT/COMP 기준**으로 생성된 것인가? RTT 튜닝값이 공장 캘리브레이션 MULT/COMP와 다르면, 저장된 `FACTORY_NOTOUCH_COUNTS`와 현재 counts가 다른 게인 기준으로 생성돼 게이트 윈도우가 무의미해진다.

**종합의 누락**: §2-3 및 §2-2 빌드가드 설계 어디에도 `TDC_TOUCH_RTT_TUNING` 분기를 언급하지 않는다. "FACTORY_NOTOUCH_COUNTS = 단일 소스, tdc_touch_config.h"라고 선언하지만, MULT/COMP가 런타임 조건에 따라 달라지는 분기가 이미 코드에 존재한다.

**요구 조치**: Phase 1 공장 캘리브레이션 저장 시와 부팅 게이트 비교 시 동일 MULT/COMP 경로가 적용됨을 보장하는 조건 명시. RTT 튜닝 활성 환경에서의 게이트 신뢰도 별도 분석 필요.

### [회귀_3] 기존 `s_boot_touch_ignore` 가드(touch.c:46/323/352)와 신설 노터치 게이트의 역할 중복·충돌이 종합에서 완전 누락됐다 (심각)

**코드 근거**: `분석.md §4` 코드 ground truth: "boot_touch_ignore: touch.c:46/:323/:352 — 전이 시 TOUCH면 set, 해제까지 폴링 억제". 이 기존 메커니즘은 RESEED 완료 후 **이미 터치 중임을 감지해 폴링을 억제**한다.

**회귀 경로**:
1. 기존 `s_boot_touch_ignore`: RESEED가 이미 발행된 후, TOUCH 상태면 폴링을 억제하는 **사후 방어**다. LTA는 이미 터치 counts로 오염된 상태이나, 폴링 억제로 false positive 터치 이벤트 발행을 막는다.
2. 신설 노터치 게이트(Phase 1): RESEED 발행을 **사전**에 막는다.

두 메커니즘이 동시에 활성화되면 다음 시나리오가 발생할 수 있다:
- 노터치 게이트가 터치를 감지해 RESEED 보류 → timeout → 저신뢰 폴백 RESEED 실행
- `s_boot_touch_ignore`가 TOUCH 상태를 감지해 폴링 억제
- 두 가드가 모두 "비정상"으로 판단했으므로 사용자가 손을 뗀 후에도 두 가드가 독립적으로 해제 조건을 검사해 **해제 타이밍 불일치**가 발생할 수 있다

더 심각하게는, `s_boot_touch_ignore` 가드를 Phase 1 노터치 게이트로 **승격**한다고 `분석.md §4` 표 3번에 명시됐으나, 30_종합 §2~§7 어디에도 이 승격 설계의 구체 방법이 없다. 기존 코드를 어떻게 변경해 두 가드의 중복을 제거하는지 계획 공백이다.

**요구 조치**: Phase 1 구현 전 `s_boot_touch_ignore` 가드 코드(touch.c:46/323/352)와 신설 노터치 게이트의 역할 분리·통합 방법을 명시. 동시 활성 상태에서의 상호작용 시나리오 분석.

### [회귀_4] 종합 §3-3 사후 검증 목적 정의의 논리 모순 — 21_검증_race의 결함_11_B가 완전히 반영되지 않았다 (심각)

**종합 주장**: §3-3 "사후 검증의 목적: RESEED 발행 전 노터치 판별~발행 사이 race 검출" → RESEED 직후 counts를 재읽어 윈도우 이탈 시 재시도.

**21_검증_race 결함_11_B의 논리**:
- RESEED 발행 **이후** 터치가 시작된 경우: LTA는 noTouch counts로 정확히 seed됨 → 이후 정상 동작(LTA IIR이 추적) → **재시도 불필요**
- race가 문제가 되는 것은 RESEED **이전**에 터치가 시작된 경우 → 이미 RESEED가 오염된 LTA로 발행된 후에는 사후에 감지 불가

종합 §3-3은 이를 수용해 "RESEED 직후 counts 재확인"으로 설계했으나, 논리 모순이 남는다:
- RESEED 이전 race → LTA가 터치 counts로 seed됨 → 사후 counts 읽기 시 counts가 다시 상승해 있으면 "윈도우 이탈" 감지 → 재시도
- 그런데 재시도 시에도 동일한 RESEED 게이트를 통과해야 하므로, 이미 LTA가 오염된 상태에서 counts를 읽어 비교하는 것이다. LTA가 오염됐을 때 counts와 LTA의 관계는 `delta ≈ 0`(터치 중이 아니라면) → counts가 새로 상승해 있으면 윈도우 안에 들어올 수 있다.

**실제 문제**: 재시도 3회 로직(`§3-3: 재시도 3회, 10ms 딜레이`)이 "LTA 오염 후 정상 회복"과 "일시 터치 후 손뗌"을 구분하지 못한다. 10ms 딜레이 후 counts가 윈도우 안에 있으면 오염된 LTA로 재RESEED한다. 이것은 최초 RESEED보다 더 최신 counts로 seed하지만, 오염이 "수정"됐다는 보장이 없다.

**종합의 누락**: §3-3이 21_검증_race 결함_11_B를 "채택: 사후 검증은 RESEED 직후"로 단순 처리했으나, 재시도 조건 분기 논리에 모순이 잔존한다. 재시도가 실제로 race를 검출·복구하는지 아니면 단순히 더 많은 RESEED를 발행하는지가 명확하지 않다.

### [회귀_5] 종합이 선언한 "25_검증_엣지 결함_2 절전 RESEED 우회 경로" 처리가 불완전하다 (심각)

**25_검증_엣지 결함_2의 핵심**: 롱터치(2400ms)로 절전 진입 시:
1. 사용자가 손을 떼지 않은 채 절전 진입 → `iqs323.c:931~948` → RESEED = LTA ← 터치 counts
2. WDT 리셋 재부팅 → `apply_settings()` → RESEED 게이트 실행
3. 그런데 이 시점에 사용자가 여전히 터치 중일 수 있음 → 게이트 실패 → timeout → 폴백 RESEED

**종합 §1-3의 처리**: "절전 진입 RESEED(`iqs323.c:931~948`)는 ULP 루프 전용 — 복귀 후 baseline에 무관." 이 선언이 결함_2를 해소한다고 암묵 처리했다.

**회귀 경로**: 절전 진입 RESEED(`iqs323.c:931~948`)는 WDT 리셋 후에도 IC에 물리적으로 적용된 LTA를 즉시 바꾸는가? IQS323이 WDT 리셋(CM3 MCU 리셋)을 수신했을 때 **IC 자체는 MCLR을 받기 전까지 이전 LTA를 유지**하고 있다. 즉 절전 진입 시 터치 counts로 오염된 LTA가 IC 내부에 그대로 남아 있다가, 재부팅 후 MCLR이 실행되는 `initialize.c:449` 시점에야 POR 리셋된다.

`initialize.c:449` MCLR 이후 auto-ATI가 실행되므로, 이 시점에 IC LTA가 초기화된다. 따라서 절전 진입 RESEED 오염은 MCLR+auto-ATI 후 실질 소멸한다 — 종합의 "ULP 루프 전용, 복귀 후 무관" 선언은 이 맥락에서 맞다.

그러나 종합이 이 논리를 명시하지 않고 단순히 "무관"이라고만 선언했다. 코드 근거 없는 단정으로 오해 가능성 있다 [추정: MCLR이 IC LTA를 포함한 전체 레지스터를 POR 초기화하는지 데이터시트 §4.1 확인 필요]. MCLR이 IC의 LTA 레지스터까지 리셋하는지 [확정 필요] 상태다.

### [회귀_6] 종합 §4 달성도 테이블 — "보드 편차" ✅ 달성 주장이 과신이다 (중요)

**종합 주장**: §4 테이블 "보드 편차(감도 불균일)" → 달성도 ✅ (Phase 2·3 완료 후).

**회귀 공격**: Phase 2(공장 캘리브레이션 EEPROM)가 완료돼 개별 보드의 MULT/COMP가 저장된다고 해도, `회귀_1`에서 지적한 대로 `write_ati_compensation()` 내 ATI_SETUP write가 항상 Phase 3 Re-ATI를 덮어쓴다. Phase 3 없이 Phase 2 MULT/COMP 저장만으로 보드 편차가 해결되는가?

Phase 2 공장 캘리브레이션은 "그 보드의 공장 MULT/COMP를 저장"하지만, 매 부팅 시 고정값 MULT/COMP(`TDC_DRV_IQS323_ATI_MULT_LSB/MSB`)로 덮어씌워지는 현재 구조(`write_ati_compensation()`)가 Phase 2 구현 후에도 변경되지 않으면, 저장한 공장 MULT/COMP를 **부팅 시 로드해서 적용하는 코드가 없다**. EEPROM에 저장만 하고 부팅 시 로드·적용하는 경로가 Phase 2 계획에 있는가?

**종합의 누락**: §2-1 층위 0 "공장 캘리브 MULT/COMP를 항상 적용" — 현재 코드가 이미 고정 MULT/COMP를 적용하고 있으나 이것은 보드별 개별 공장값이 아니라 **컴파일 타임 상수**다. Phase 2 EEPROM 저장은 개별 보드값을 저장하지만, 이 값을 부팅 시 읽어 `write_ati_compensation()` 내 상수를 대체하는 코드가 설계에 없다. 결론 10번에서 "보드 편차" ✅는 아직 미구현 경로에 의존한 과신 [추정: Phase 2 EEPROM 로드 경로 구체 설계 미발견].

### [회귀_7] 종합 §5-3 "자기치유 동작 여부 — Beta POR 실측 후 재정립" 처리가 여전히 단정 위험을 남긴다 (중요)

**종합 주장**: §5-3 설계 통일 요구사항 "자기치유 동작 여부 — 16(내장) vs 15(Beta=0이면 불가) 모순 → 블로킹_D(Beta POR 실측) 후 재정립."

**회귀 공격**: 블로킹_D가 해소되지 않은 상태에서 §4 달성도 테이블이 "게이트 race → ✅ 충분히 낮은 확률 [추정]"로 마무리했다. 이 평가는 자기치유(Beta IIR 추적)가 동작함을 암묵 전제한다. Beta POR=0이면 자기치유 층이 완전히 비활성이며, race 치명도 평가가 "낮음"에서 "중간~높음"으로 재산정되어야 한다.

즉 §4 달성도의 race ✅ 평가는 **블로킹_D(Beta POR) 확정 전에는 유효하지 않다**. [추정] 표기로 단서를 달았으나, 달성도 표에서 ✅로 표시된 것은 계획 신뢰도를 과대 선언한다.

### [회귀_8] 종합 §2-1 층위 4 크래들 구현 — "뚜껑 닫힘 기간 노터치 보장"이 현재 코드에서 실제로 어디에 쓰이는지 연결 경로가 없다 (보통)

**종합 주장**: §2-1 층위 4 "크래들 race 소멸 — 뚜껑 닫힘 = race-free 기회, 노터치 절대 보장. 미구현. 공장 캘리브+EEPROM 저장 선행."

**회귀 공격**: `func_cradle_lid_closed_loop()`(`main.c:807`) 진입 시 터치 폴링이 완전 중단된다. 뚜껑 열림 시 WDT 리셋 재부팅이 발생한다. 즉 크래들 노터치 구간에서 Re-ATI를 실행해도, 결과는 재부팅 시 `write_ati_compensation()`이 덮어쓴다(`회귀_1`과 동일 경로). 따라서 크래들 Re-ATI + EEPROM 저장을 "쌍으로 구현"(`§2-1 Phase 4`)한다고 해도, 재부팅 후 EEPROM에서 읽어 `write_ati_compensation()` 경로를 우회하지 않으면 효과가 없다.

이 연결 경로(EEPROM 로드 → `write_ati_compensation()` 내 상수 대체)는 `회귀_6`에서 지적한 것과 동일하게 Phase 계획 어디에도 명시되지 않았다.

## 핵심 6줄

1. **[회귀_1 치명]** `write_ati_compensation()`은 MULT/COMP뿐 아니라 ATI_SETUP(0x36 = Mode Disabled)도 선두에 write(`iqs323.c:700`)한다 — "항상 실행 유지" 선언은 Phase 3 Re-ATI를 매 재부팅마다 덮어쓰는 회귀를 만들며, Phase 4 크래들 Re-ATI 결과도 동일하게 소실된다.
2. **[회귀_2 심각]** `TDC_TOUCH_RTT_TUNING` 분기(`iqs323.c:705~730`)로 MULT/COMP가 런타임 튜닝값으로 대체될 수 있다 — 공장 캘리브레이션 MULT/COMP 기준으로 저장된 `FACTORY_NOTOUCH_COUNTS`가 다른 게인 환경에서 비교되면 게이트 윈도우 자체가 무의미해지며, 종합은 이 분기를 완전 누락했다.
3. **[회귀_3 심각]** 기존 `s_boot_touch_ignore` 가드(touch.c:46/323/352)와 신설 노터치 게이트의 역할 중복·해제 타이밍 불일치를 종합이 다루지 않았다 — 두 가드가 동시 활성 시 독립 해제 조건 충돌로 부팅 후 터치 미인식 구간이 연장될 수 있다.
4. **[회귀_4 심각]** 사후 검증 재시도 3회 로직이 "RESEED 전 race 복구"가 아니라 "추가 RESEED 3회 발행"에 가깝다 — 21_검증_race 결함_11_B에서 지적한 race 방향 모순이 종합 §3-3에서 완전히 해소되지 않았다.
5. **[회귀_6 중요]** Phase 2 EEPROM에 개별 보드 MULT/COMP를 저장해도, 부팅 시 이를 읽어 `write_ati_compensation()` 내 컴파일 타임 상수를 대체하는 코드 경로가 종합 설계 어디에도 없다 — §4 "보드 편차" ✅ 달성 주장은 이 누락으로 과신이다.
6. **[회귀_5 추정 유보]** 절전 RESEED 우회 문제는 MCLR이 IC LTA까지 POR 초기화하는지 데이터시트 §4.1 확인 후에야 "무관" 선언이 유효하다 — 현재는 [확정 필요] 상태이며 코드 근거만으로 단정 불가.
