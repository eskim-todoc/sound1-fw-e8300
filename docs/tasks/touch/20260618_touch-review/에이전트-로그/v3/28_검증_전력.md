# 28_검증_전력 — 전력·절전 예산 adversarial 공격

**TL;DR**: 계획 11~18은 기능 정확성에 집중했으나, 부팅 지연 증가·busy-wait I2C 폴링·크래들 약 절전 방해·절전 직전 추가 I2C·WDT 리셋 타이밍 윈도우 등 전력·절전 예산에 직접 영향을 주는 결함 6건을 발굴한다. 특히 5초 gate-wait busy-loop는 부팅 중 CPU를 100% 점유하며, 이 구간에 WDT refresh가 누락되면 의도치 않은 WDT 리셋 연쇄가 발생할 수 있다.

---

## 0. 검증 기준

전력·절전 예산 관점의 공격 기준:

1. **I2C 트랜잭션 비용**: `force_window_open()` 최대 45ms + `wait_rdy_window_closed()` 최대 20ms = 트랜잭션 1회당 최대 **65ms CPU busy-wait**(`tdc_drv_iqs323.h:31~32`). 이 비용은 모두 busy-loop이며 WFI/저전력 상태가 아니다.
2. **부팅 지연 예산**: 현재 부팅 시퀀스에 이미 MCLR(1ms) + boot_wait(50ms) + Auto-ATI 폴링(≤1500ms) + apply_settings 다수 write가 포함돼 있다. 추가 구현은 이 예산을 넘지 않아야 한다.
3. **절전 전환 지연**: 절전 진입(`func_sleep`)은 롱터치 2400ms 뒤 사용자 기다리는 구간이다. 이 경로에 블로킹 추가 시 사용자 체감 지연이 직접 증가한다.
4. **크래들 약 절전 방해**: `func_cradle_lid_closed_loop()` 진입 전 훅은 그 시간만큼 FPGA/QCC가 sleep 진입을 늦춘다(`main.c:827` FPGA sleep 핀 설정 직전이 삽입 지점과 인접).
5. **WDT 리셋 위험**: 부팅 중 `SYS_WATCHDOG_REFRESH()` 없이 5000ms 루프를 돌면 WDT timeout 설정에 따라 의도치 않은 리셋이 발생할 수 있다.

## 1. 결함 1 — 게이트 5000ms busy-loop의 I2C 전력 비용 미계산 [치명도: 높음]

**공격 대상**: 11_계획_부팅시퀀스 §2 흐름도 `reseed_hold → recover` 대기 경로, 14_계획_노터치게이트코드 §2-3 `tdc_drv_iqs323_reseed_with_gate()`.

**결함**:
계획 14의 게이트 대기 루프(`while (elapsed_ms < timeout_ms)`)는 `TDC_TOUCH_NO_TOUCH_TIMEOUT_MS = 5000ms` 동안 최대 100회(50ms × 100) `read_ch0_filtered_counts()`를 호출한다. 각 호출은 `read_register()` → `force_window_open()` → I2C write(주소 전송) → I2C read → `wait_rdy_window_closed()`로 구성되어 I2C 트랜잭션 **2회(주소write + 데이터read)**를 소모한다. 매 read_register는 최대 65ms × 2 = 130ms CPU busy-wait을 유발할 수 있으나, 이 비용이 계획 어디에도 명시되어 있지 않다.

**수치 산출** [추정: MAX_WAIT 상한값 기준]:
- 노터치 게이트 정상 통과(3샘플, 150ms): read 3회 × 130ms = **390ms 추가**
- timeout 경로(5000ms): read 100회 × 130ms = **13000ms = 13초** — 이는 현재 부팅 시퀀스 전체(≤1500ms)를 9배 초과하는 시간이다

계획은 이 비용을 언급하지 않는다. "부팅 지연 허용 범위"를 정의하지 않은 채 5초 timeout을 설정한 것은 **전력 예산 분석 누락**이다.

**추가 위험**: `force_window_open()`은 IQS323 RDY 핀이 열릴 때까지 CPU가 바쁘게 GPIO를 폴링하는 busy-wait이다(`tdc_drv_iqs323.c:157~171`). 이 구간에 `SYS_WATCHDOG_REFRESH()`가 없으면 WDT timeout이 발생할 수 있다. 계획 14의 루프 내에는 `SYS_WATCHDOG_REFRESH()`가 있으나(`iqs323.c:1139` 수준에서 외부 `apply_settings()`에서 이미 1회 호출), read_register 내부 busy-wait 구간에는 WDT refresh가 없다 [확정 필요: WDT timeout 주기 vs MAX_WAIT_MS_FOR_WINDOW_OPEN=45ms 비교].

## 2. 결함 2 — 크래들 Re-ATI 1.5초 블로킹의 FPGA 절전 진입 지연 [치명도: 중간]

**공격 대상**: 13_계획_크래들훅 §3-2 `tdc_drv_iqs323_cradle_re_ati()`, 18_계획_통합아키텍처 §2-3 크래들 상태머신.

**결함**:
계획 13은 Re-ATI 블로킹 시간을 "~1.5초(wait_re_ati_done 10×100ms)"로 명시하나, 이것이 FPGA 및 시스템 절전 진입에 미치는 영향을 분석하지 않는다. `main.c:827`에서 `Sys_GPIO_Set_Low(DIO_PIN_INDEX_for_FPGA_SLEEP)`을 통해 FPGA sleep 핀을 내리는 것은 `func_cradle_lid_closed_loop()` 진입 직후이다. 즉, Re-ATI 1.5초 + 실패 시 RESEED 폴백까지 더하면 최대 2초가량 FPGA가 sleep 진입을 대기한다.

이 구간 FPGA가 활성 상태를 유지하면:
- FPGA 및 ISD의 절전 전력(수 mW → 수십 mW)이 그만큼 더 소모된다
- 배터리 잔량이 적을 때(방전 직전) 크래들에 놓이는 케이스에서 이 지연이 최후 수 mA를 낭비할 수 있다

계획 13은 "~1.5초 블로킹 허용(약 절전 루프 진입 전)"이라고만 쓰고 FPGA 전력 예산 영향을 정량화하지 않는다. [확정 필요: FPGA 활성 상태 전력 소모량 및 뚜껑 닫힘 진입 시점의 FPGA 상태]

## 3. 결함 3 — 절전 진입 직전 추가 I2C 트랜잭션 비용 누락 [치명도: 중간]

**공격 대상**: 17_계획_방전트랙 §3-3 절전 진입 전 방전 추가 옵션, 13_계획_크래들훅 §2-2.

**결함**:
계획 17 §3-3은 절전 진입 직전(`main.c:943` 앞)에 `tdc_drv_iqs323_discharge_crx0()` 1회를 추가하는 안을 제안한다. `discharge_crx0()`는 `write_register_discharge()` 2회 호출로 I2C 트랜잭션 **2 × 2 = 4번**(force_window_open + write + wait_close = 각 1회)을 소모한다. 이미 `tdc_drv_iqs323_reseed()` 내부에도 `touch_settings_impl`(write 1회) + `prox_settings`(write 1회) + RESEED(write 1회) = 최소 3회 write가 있다. 절전 전 합산 I2C 트랜잭션은 현재 3회 → 제안 시 최대 7회로 증가한다.

절전 진입 경로(`func_sleep → apply_sleep_settings → ci_power_sleep`)는 사용자가 롱터치 후 기다리는 구간이다. 이 경로에 블로킹 I2C가 추가될 때의 사용자 체감 지연을 계획이 다루지 않는다. [추정: 7회 × 65ms = 455ms 최대 추가 지연, 실제 window 상황에서는 훨씬 짧을 수 있음]

## 4. 결함 4 — EEPROM write 경로의 ISD 인덱스·Flash 내구성 예산 미분석 [치명도: 낮음~중간]

**공격 대상**: 12_계획_공장캘리저장 §3 EEPROM 저장 경로, 18_계획_통합아키텍처 §4-6 크래들 Re-ATI.

**결함 A — ISD 인덱스 미확정**:
계획 12 §4-2 코드에서 `isd_index = 0, map_index = 0`으로 하드코딩하고 "[확정 필요]"로 표기했으나, 잘못된 인덱스를 사용하면 다른 ISD의 사용자 설정값(`mapNum`, `stimulVolume` 등)을 덮어쓸 수 있다. 전력 관련이 아닌 데이터 무결성 위험이지만, **공장 캘리브레이션 실패 시 재부팅-재캘리브레이션 반복 루프**로 이어져 배터리 소모가 증가할 수 있다.

**결함 B — Flash write 내구성**:
크래들 뚜껑 닫힘마다 Re-ATI 결과를 EEPROM에 저장하는 계획(18 §4-6 크래들 Re-ATI)은 Flash write 횟수를 증가시킨다. 일반적인 NVM/Flash는 10만~100만 회 write 내구성이다. 하루 10회 크래들 사용 × 365일 = 3650회/년으로 이 자체는 안전하나, 계획 어디에도 Flash 내구성 예산이 명시되어 있지 않다. [확정 필요: 해당 NVM/Data Flash의 write 내구성 스펙]

## 5. 결함 5 — Auto-ATI 채택 경로의 전력 비용 이중 계상 [치명도: 중간]

**공격 대상**: 11_계획_부팅시퀀스 §3-1 채택 경로 코드.

**결함**:
계획 11의 채택 경로는 다음과 같이 동작한다:

```
(1) 기존: Auto-ATI 1회 (IC 자율) → apply_settings() 전 counts 읽기 (read 1회)
(2) 추가: tdc_drv_iqs323_reseed_with_verify() — RESEED 1회 + 즉시 counts 재확인(read 1회) + 재시도 최대 3회
```

그런데 계획 11과 계획 14가 **동일한 삽입 지점(`apply_settings()` 내 iqs323.c:1147)을 각각 독립적으로 설계**하고 있다. 두 계획을 동시에 활성화하면:

- 계획 11: counts 읽기(gate 판별) → `write_ati_compensation()` 생략 또는 실행
- 계획 14: `tdc_drv_iqs323_reseed_with_gate()` (내부에서 또 counts 읽기 루프)

삽입 지점이 중복되므로 어느 쪽이 실행될지 모호하며, 최악의 경우 **게이트 중복 판별 + counts 이중 읽기**로 부팅 지연이 배가될 수 있다. 계획 18의 통합 아키텍처가 이 두 계획을 어떻게 결합하는지 명확히 정의하지 않는다. [추정: Phase 1에서 한쪽만 활성화하도록 빌드가드로 분리해야 하지만 현재 구체화 없음]

## 6. 결함 6 — 게이트 대기 중 `Sys_Delay` vs `ci_timer_get_tick` 혼용 전력 특성 차이 무시 [치명도: 낮음]

**공격 대상**: 14_계획_노터치게이트코드 §2-3 `tdc_drv_iqs323_reseed_with_gate()` poll_ms 대기 구현.

**결함**:
계획 14 코드에서 게이트 폴링 50ms 대기를 다음과 같이 구현한다:

```c
int32_t tick_start = ci_timer_get_tick();
while ((ci_timer_get_tick() - tick_start) < (int32_t)poll_ms)
{
    SYS_WATCHDOG_REFRESH();
}
elapsed_ms += poll_ms;
```

이것은 `ci_timer_get_tick()` 기반 busy-loop이다. 반면 기존 `apply_settings()` 내 50ms 안정화 대기(`iqs323.c:852~855`)도 동일 패턴을 사용한다. 두 방식 모두 CPU를 100% 점유하는 순수 busy-wait이다.

부팅 중이라 저전력 슬립 전환이 어렵지만, 50ms × 3샘플 = 150ms의 순수 busy-wait은 현재 Auto-ATI 완료 폴링(비블로킹 폴링과 혼합)보다 전력 효율이 낮다. 이 차이를 계획이 인식하지 못하며 "부팅 중 CPU 점유율 100%"라는 전제가 적절한지 평가하지 않는다.

더 중요한 점은, **timeout 경로에서 `elapsed_ms += poll_ms`가 실제 경과 시간을 반영하지 못한다는 것**이다. `read_ch0_filtered_counts()` 내부에서 소요된 I2C 트랜잭션 시간(최대 130ms/회)은 `elapsed_ms`에 포함되지 않는다. 따라서 실제 timeout은 `TDC_TOUCH_NO_TOUCH_TIMEOUT_MS`보다 훨씬 길어질 수 있다. [추정: 100회 순환 시 실제 elapsed = 50ms × 100 + 130ms × 100 = 18초, 명시 timeout 5초의 3.6배]

## 7. 결함 7 — Beta write 이후 LTA IIR 동작이 절전 진입 RESEED를 무의미하게 만들 가능성 [치명도: 낮음]

**공격 대상**: 15_계획_드리프트LTA §2.4 write_filter_betas() 호출 시점.

**결함**:
계획 15는 `write_filter_betas()` 호출 시점을 "RESEED 완료 후, ATI Disabled 설정 직후"로 명시한다. 그러나 현재 절전 진입 경로(`tdc_drv_iqs323_reseed()`, `iqs323.c:931~948`)는 `touch_settings_impl` + `prox_settings` + RESEED를 실행하며, 이 함수는 Beta 레지스터를 리셋하지 않는다. 따라서 절전 진입 직전 RESEED 이후에도 Beta는 설정된 값으로 유지되어 **ULP 모드에서 LTA가 IIR 추적을 계속**할 수 있다.

IQS323의 LP 및 ULP 모드에는 별도의 LP Filter Betas 레지스터(0xB1·0xB3 [추정])가 있다. 계획 15는 NP 모드 Beta만 설정하고 LP/ULP Beta를 명시하지 않는다. 절전 중 LP/ULP Beta가 NP와 다른 POR 기본값으로 동작한다면 절전 중 LTA 추적 속도가 의도와 다르게 동작할 수 있다. [확정 필요: IQS323 LP·ULP 모드 Beta 레지스터 POR default + 절전 중 LTA IIR 동작 여부]

## 9. 권고 (계획 수정 방향)

1. **게이트 timeout을 전력 예산 기반으로 재설정**: 부팅 허용 최대 지연을 먼저 정의(예: 현재 Auto-ATI 포함 ≤2초)하고, 게이트 timeout을 그 잔여 예산 내로 제한. 5000ms는 설계 근거 없는 임의값임.
2. **I2C 시간을 elapsed_ms에 포함**: `read_ch0_filtered_counts()` 호출 전후 `ci_timer_get_tick()` 차이를 `elapsed_ms`에 가산해 실제 경과 시간 추적.
3. **크래들 Re-ATI 블로킹 시간 정당화**: FPGA 절전 지연 비용을 Re-ATI 이득과 비교 정량화 필요. Phase 1 RESEED(~수 ms)와 Phase 2 Re-ATI(~1500ms)의 전력 비용 차이를 명시.
4. **삽입 지점 중복 명확화**: 계획 11과 14 중 어느 것이 Phase 1에서 `iqs323.c:1147`을 점유하는지 18_통합아키텍처에서 단일 진실로 명시.
5. **LP/ULP Beta 명시**: 계획 15에 LP·ULP 모드 Beta 레지스터(0xB1·0xB3) 처리 방침을 추가.

## 10. 핵심 결론 (6줄)

1. **게이트 timeout 5초는 실제 최대 ~18초 부팅 지연을 야기할 수 있다** — I2C 트랜잭션 overhead(최대 130ms/read)를 elapsed_ms에 포함하지 않아 실제 경과 시간이 명시 timeout의 3.6배가 될 수 있으며, 이 전체 구간이 CPU 100% busy-wait이다.
2. **크래들 Re-ATI 1.5초 블로킹은 FPGA 절전 진입을 지연시키며 전력 비용이 미정량화됐다** — main.c:827 FPGA sleep 핀 설정 직전 삽입이므로 FPGA 활성 전력이 1.5초 추가 소모된다.
3. **절전 직전 방전 추가는 사용자 체감 롱터치 응답 지연을 악화시킨다** — 이미 RESEED 경로에 3회 I2C write가 있으며, 방전 2회 추가 시 최대 455ms 지연이 발생한다.
4. **계획 11과 14가 동일 삽입 지점(iqs323.c:1147)을 중복 점유하며 통합 계획(18)에서 해소되지 않아 게이트 이중 실행 위험이 있다** — 두 계획의 우선순위와 빌드가드 관계가 명확히 정의되지 않았다.
5. **elapsed_ms 계산 오류로 실제 timeout 시간이 예측 불가능하다** — I2C 트랜잭션 시간이 poll 대기 시간에서 제외되어 timeout 조건이 의도보다 훨씬 늦게 발동된다.
6. **LP/ULP Beta 미설정은 절전 중 LTA IIR이 의도치 않게 동작할 수 있는 경로를 열며**, NP Beta 설정의 절전 구간 부작용이 계획 15에 분석돼 있지 않다.
