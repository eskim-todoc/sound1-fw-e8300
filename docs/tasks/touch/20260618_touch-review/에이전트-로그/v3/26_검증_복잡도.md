# 26_검증_복잡도 — 1차 계획 adversarial 공격 (복잡도·EEPROM/공정 비용·유지보수)

**TL;DR**: 계획 8종(11~18)을 구현 복잡도·EEPROM/공정 비용·유지보수 관점으로 공격한다. 핵심 결함 6개: ① FACTORY_NOTOUCH_COUNTS 실측 없이 Phase 1 구현이 의미 없는 데드코드 위험, ② CFX userSettingValue 구조체 확장이 CFX 파서를 건드려 전체 공정 플래시 재기록 필요 가능성, ③ Phase 단계 수(0~4)×빌드가드 수가 테스트 매트릭스를 5차 폭발 생성, ④ 크래들 Re-ATI 결과 재부팅 시 소멸(Phase 2/3 연결 누락), ⑤ Beta 레지스터 주소·POR 미확인으로 LTA IIR 계획 전체가 [추정] 위에 선 공중누각, ⑥ 공장 공정 전용 빌드가드(FACTORY_CALIB_ENABLE)가 런타임 코드에 컴파일 포함되어 출하 펌웨어 공격 표면 확장.

---

## 0. 공격 관점 정의

본 페르소나는 **구현 복잡도·EEPROM/공정 비용·유지보수** 세 축으로 설계안을 공격한다.
- **구현 복잡도**: 신규 코드량·의존 관계·조건 분기 수·블로킹 타이밍 오류 가능성
- **EEPROM/공정 비용**: 공장 공정 변경 필요성·플래시 수명·CFX 파서 변경 파급
- **유지보수**: 빌드가드 조합 폭발·실측 게이트 누락 시 데드코드 퇴화·디버깅 가시성 부족

## 1. 결함_1 — FACTORY_NOTOUCH_COUNTS 미확정 = Phase 1 전체가 데드코드 위험

### 1-1. 공격 근거

11_계획_부팅시퀀스 §3-3, 14_계획_노터치게이트코드 §1:
```c
#define TDC_TOUCH_FACTORY_NO_TOUCH_COUNTS  450u   /* [확정 필요] */
```
16_계획_사후검증 §1-2:
```c
#define TDC_DRV_IQS323_FACTORY_NOTOUCH_COUNTS 0u  /* [확정 필요] — 0이면 사후검증 건너뜀 */
```

**문제**: 두 계획 파일이 동일한 개념(공장 noTouch counts 절대 기준값)에 **서로 다른 상수명·서로 다른 파일·서로 다른 임시값**(450 vs 0)을 정의한다. Phase 1 구현 시 어느 값을 기준으로 게이트를 구현할지 단일 소스가 없다.

### 1-2. 복잡도 함의

- `tdc_touch_config.h`(11·14 계획)와 `tdc_drv_iqs323.c`(16 계획) 두 곳에 분산된 상수가 실측 후 갱신될 때 어느 파일을 수정해야 하는지 코드 리뷰어가 알기 어렵다.
- 14_계획 §8-4: "이 값이 잘못되면 게이트가 항상 폴백하거나 항상 통과" — Phase 1을 `TDC_TOUCH_BOOT_GATE_ENABLE=0`(기존 동작)으로 시작하라고 권고하면서, 실측 게이트를 통과하기 전까지 게이트 관련 신규 함수 3개(`read_ch0_filtered_counts`, `is_no_touch_window`, `tdc_drv_iqs323_reseed_with_gate`)가 **데드코드**로 존재한다. 데드코드는 빌드 경고 없이 정적 분석을 통과하면서 다음 개발자를 혼란에 빠뜨린다.
- [추정] RTT 실측 일정을 계획에서 정의하지 않으므로 "실측 후 교체"가 무기한 미뤄질 가능성이 크다.

### 1-3. 권고 공격

11 계획 §10 체크리스트에 "RTT 실측으로 `FACTORY_NOTOUCH_COUNTS`·`NOTOUCH_MARGIN` 확정 후 `TDC_TOUCH_BOOT_GATE_ENABLE=1` 활성화"가 마지막 항목이다 — 이 순서가 역전되면 임시값으로 활성화될 위험이 있다. **계획이 빌드가드를 안전장치로 두지만, 빌드가드가 항상 0인 상태로 코드를 커밋하면 게이트 함수는 컴파일 되지 않아 ODR(One Definition Rule) 위반 또는 컴파일러 dead-code 경고가 발생한다.** `#if 0` 감싸기도, `__attribute__((unused))` 도 명시돼 있지 않다.

## 2. 결함_2 — CFX userSettingValue 구조체 확장의 공정 파급 미평가

### 2-1. 공격 근거

12_계획_공장캘리저장 §3-1 옵션_A(권고):
```c
/* cfx_cm3_sharedMemory.h:89~98 — int 7필드에 int 4필드 추가 */
int touch_calib_magic;
int touch_mult;
int touch_comp;
int touch_noTouch_counts;
```

§7 미해결 항목: "CFX 측 userSettingValue 파서 크기 제약 — CFX 코드 리뷰 [현재 접근 불가]"

### 2-2. EEPROM/공정 비용 공격

- CFX 측 파서가 `sizeof(ST__CFX_CM3_SharedMemory_userSettingValue)` 또는 **필드 개수를 하드코딩**하고 있을 경우, 구조체 확장만으로 기존 EEPROM 레이아웃이 깨진다. 이는 **이미 출하된 기기의 펌웨어 OTA 업데이트 시 EEPROM 데이터 불일치 → 공장값 읽기 실패 → 기존 동작 폴백**으로 이어진다.
- 더 심각하게: CFX 측이 필드 수로 배열을 순회하면, 4필드 증가분이 다른 설정값(mapNum·volume·LED·BLE 등)의 오프셋을 밀어서 **기존 설정값 전체 오염**이 발생할 수 있다. [추정]
- 12 계획이 "기존 CFX EEPROM 경로 재사용"이라 권고한 이유가 바로 "write 1회로 전체 저장"인데, 이것이 동시에 기존 설정값과 터치 캘리브값을 **단일 EEPROM write 원자 트랜잭션**으로 묶는다. 공장 공정 실패(예: EEPROM write timeout)가 기존 설정값까지 손상시키는 새 위험 경로를 만든다.

### 2-3. 공장 공정 비용 공격

- `remoteControl.c`에 공장초기화 패킷 수신 경로가 존재한다고 전제하지만, 공장 캘리브레이션을 위한 **노터치 환경 보장 절차(치구 또는 크래들 닫힘 상태 진입)**가 공정 문서에 추가돼야 한다.
- 12 계획 §4-1: "공장 치구 또는 크래들 닫힘 환경에서 노터치 보장 상태에서만 실행"이라고 쓰여 있으나, 이 조건을 SW가 검증할 방법이 없다. 공정 작업자가 실수로 기기를 들고 캘리브레이션 명령을 보내면 잘못된 noTouch Counts가 EEPROM에 기록되고 이후 게이트 판별이 영구 왜곡된다.
- **캘리브레이션 자체 유효성 검증 로직이 없다**. `tdc_drv_iqs323_calib_store()`에서 저장 전 `no_touch_counts`가 정상 범위인지 확인하는 코드가 없다.

## 3. 결함_3 — Phase 0~4 × 빌드가드 5개 = 테스트 매트릭스 폭발

### 3-1. 공격 근거

18_계획_통합아키텍처 §3, tdc_touch_config.h 빌드가드:
```
TDC_TOUCH_SATURATE_DETECT_ENABLE   (Phase 0)
TDC_TOUCH_ATI_FULL_ENABLE          (Phase 1/3)
TDC_TOUCH_NOTOUCH_GATE_ENABLE      (Phase 2)
TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE  (Phase 3)
TDC_TOUCH_CRADLE_REATI_ENABLE      (Phase 4)
TDC_TOUCH_FACTORY_CALIB_ENABLE     (공장 공정)
```

### 3-2. 유지보수 공격

- 6개 빌드가드는 이론적으로 2^6 = 64가지 조합을 만든다. 18 계획 §3 "의존 관계" 제약을 적용해도 유효 조합은 **12~20가지 이상**이다.
- 각 유효 조합에서 코드가 올바르게 컴파일되고 올바르게 동작하는지 검증하는 자동화 테스트가 없다. 임베디드 특성상 RTT 실측 기반 수동 검증이 유일한 방법인데, Phase당 실측 시간이 수 시간 이상 소요된다.
- `TDC_TOUCH_ATI_FULL_ENABLE=0`이면 `tdc_touch.c`의 ATI_Error 핸들러 전체가 `#else` 분기로 처리되어 빌드 누락 시에도 컴파일 오류가 없다. 실수로 `TDC_TOUCH_ATI_FULL_ENABLE=1`과 `TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE=1`을 따로 활성화하면 `re_ati_trigger()` extern 노출 없이 링커 오류가 발생한다 — 16 계획 §2-4 주석에 "TODO" 수준으로만 언급됨.
- 빌드가드 의존 관계 위반을 **컴파일 타임에 강제하는 `#error` 검증 코드**가 없다:
  ```c
  /* 없는 코드: */
  #if TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE && !TDC_TOUCH_NOTOUCH_GATE_ENABLE
  #  error "REATI_ON_NOTOUCH requires NOTOUCH_GATE_ENABLE"
  #endif
  ```
  이 누락 때문에 의존 관계 위반이 링크 오류나 런타임 오작동으로만 드러난다.

## 4. 결함_4 — 크래들 Phase 2 Re-ATI 결과가 재부팅 시 소멸 — 설계 목적 달성 불가

### 4-1. 공격 근거

13_계획_크래들훅 §3-5:
> Re-ATI가 성공해 MULT/COMP가 갱신되더라도, 뚜껑 열림 WDT 리셋 후 부팅 시 `iqs323.c:1141` `write_ati_compensation()`이 **하드코딩 고정값으로 덮어쓴다**. 따라서 Re-ATI 갱신값은 뚜껑 닫힘 구간 동안만 유효하다.

### 4-2. 복잡도 공격

- Phase 2 크래들 Re-ATI(`tdc_drv_iqs323_cradle_re_ati()`)는 ~1.5초 블로킹 실행 비용을 지불하면서 **뚜껑 닫힘 기간 중에만** 효과를 낸다. 뚜껑 열림 WDT 리셋 후 모든 보정값이 초기화되므로, 이 함수는 **크래들 닫힘 → 열림 → 재부팅 주기**에서 얻는 실질 이익이 없다.
- 13 계획 §7-6에 이 한계가 명시되어 있고 "Phase 3 EEPROM 저장과 결합해야 영속"이라 쓰여 있다. 즉 Phase 2 크래들 Re-ATI 단독으로는 설계 목표(환경 적응 보정 유지)를 달성하지 못한다.
- **Phase 2와 Phase 3이 별도 단계로 분리된 설계가 잘못**이다 — 크래들 Re-ATI가 유효하려면 EEPROM 저장이 원자적으로 함께 실행돼야 한다. 분리 설계는 중간 단계(Phase 2만 활성)에서 "비용만 지불하고 이득 없음"인 상태를 합법적으로 만든다.
- 18_계획 §4-6의 Phase 4 크래들 Re-ATI 코드:
  ```c
  tdc_drv_iqs323_factory_calib_store(&calib_update);
  tdc_touch_calib_save_to_eeprom(&calib_update);
  ```
  `tdc_touch_calib_save_to_eeprom()`는 12 계획에 정의된 함수가 아니다. 18 계획에서 새 API 이름이 등장했지만 12 계획의 `tdc_drv_iqs323_calib_store()`와의 관계가 불명확하다. **API 명명 불일치**가 통합 구현 시 혼선을 유발한다.

## 5. 결함_5 — LTA IIR(Beta) 계획 전체가 미확인 전제 위의 공중누각

### 5-1. 공격 근거

15_계획_드리프트LTA §1.3:
> **[확정 필요]**: 0xB0~0xB4 레지스터 정확한 주소·비트 레이아웃은 IQS323 데이터시트 §5.6 레지스터 맵에서 확인 후 기재. 현재 코드에 이 레지스터 define이 없으므로 신규 추가 필요.

동 §1.3:
> POR default 확인 필요 — IQS323 데이터시트가 Beta POR default를 0이라 명시하는지 실측으로 교차 확인 필요. [확정 필요]

### 5-2. 구현 복잡도 공격

- Beta 레지스터 주소(0xB0~0xB4)가 추정값이다. 잘못된 주소에 write하면 **엉뚱한 레지스터를 덮어쓰게 된다** — 이 경우 silent 오동작으로 디버깅이 매우 어렵다.
- Beta 비트 레이아웃(LSB=normal, MSB=fast라는 가정)이 확인되지 않았다. 반대로 배치돼 있으면 "느린 Beta"와 "빠른 Beta"가 교환돼 비대칭 설계 의도와 반대 동작을 낸다.
- 수렴 시간 계산(Beta=4 → 40초, Beta=12 → 13초)은 "폴링 주기 200ms" 가정 위에 있다. 실제 폴링 주기가 다르거나(ISR 지연, WDT 갱신 등) IQS323 내부 샘플링 주기와 연동되지 않으면 계산값이 틀린다.
- **현재 Beta write가 0건이라는 사실**(분석.md §4-6)이 의미하는 것은, LTA IIR이 실제로 동작하는지 검증된 적이 없다는 뜻이다. LTA IIR을 처음 활성화할 때 예상치 못한 부작용(약터치 흡수, 환경 급변 시 민감도 급락)이 발생할 수 있다.

### 5-3. Phase 2 선행 조건 연쇄 공격

15 계획은 Beta 설정을 "Phase 2"로 분류하면서, Phase 2의 선행 조건으로 "노터치 게이트 + RESEED 구현"을 요구한다. 그런데 17_계획_사후검증 §7-6에서:
> "Beta 설정이 자기치유의 선행 조건 — 현재 Beta=0이라면 자기치유는 실질적으로 동작하지 않는다."

즉 **자기치유(사후검증의 핵심 완화책)가 Beta 설정 없이는 동작하지 않는데, Beta 설정은 Phase 2 이후**다. Phase 1 구현이 "자기치유로 복구"에 의존하는 모든 설계 가정이 Phase 1 단계에서는 거짓이 된다.

## 6. 결함_6 — 공장 공정 전용 코드가 출하 펌웨어에 컴파일 포함

### 6-1. 공격 근거

12_계획_공장캘리저장 §4-1:
> BLE 공장초기화 패킷 수신 (수술위치=3, `remoteControl.c:171` 분기)으로 공장 캘리브레이션 실행.

18_계획 §3 빌드가드:
```c
#define TDC_TOUCH_FACTORY_CALIB_ENABLE     0u  /* 공장 캘리브레이션 공정에서만 1로 */
```

### 6-2. 유지보수·보안 공격

- 빌드가드가 0이더라도 `tdc_drv_iqs323_calib_store()`와 `remoteControl.c`의 분기 코드가 출하 펌웨어 바이너리에 **포함될 수 있다** — `#if` 조건이 `CALIB_ENABLE`에만 걸려 있고, BLE 공장초기화 패킷 수신 경로(`수술위치=3`)는 런타임에 항상 존재하는 코드다.
- 즉 **출하 후 사용자 기기에 "수술위치=3 BLE 패킷을 보내면 터치 캘리브레이션이 실행되는" 경로**가 남아있을 가능성이 있다. [확정 필요: remoteControl.c:171 분기가 FACTORY_CALIB_ENABLE 빌드가드 안에 있는지 확인]
- 설령 빌드가드로 완전히 막혀 있더라도, 공장 공정 전용 코드를 제품 소스에 #if로 관리하는 것은 장기 유지보수 관점에서 **별도 공장용 브랜치 또는 별도 플래시 파티션 구조**보다 변경 추적이 어렵다. 공장 공정 코드 수정 시 제품 소스를 함께 수정해야 해서 회귀 위험이 증가한다.

### 6-3. EEPROM write 수명 공격

- EEPROM 플래시 write 수명이 공장 공정에서 몇 회 소비되는지 분석이 없다. 재작업(re-work) 시 캘리브레이션을 재실행하면 write 횟수가 증가한다.
- 12 계획이 `setReadWriteMapDataFlashCommand`를 사용하는데, 이 함수가 전체 `userSettingValue` 구조체를 한 번에 write한다면, 향후 설정값 변경(볼륨·LED 등)이 발생할 때마다 터치 캘리브값도 함께 재기록된다 — 런타임 write 횟수 증가 가능성. [확정 필요]

## 9. 핵심 결론 (6줄)

1. **FACTORY_NOTOUCH_COUNTS 이중 정의·임시값**이 Phase 1 핵심 함수 3종을 데드코드로 만들 수 있으며, 두 파일에 서로 다른 이름과 임시값이 분산된 현황은 통합 전 단일 소스 정리가 선행돼야 한다.
2. **CFX userSettingValue 구조체 확장**이 CFX 파서 코드 리뷰 없이 진행되면 기존 설정값(볼륨·LED·BLE) 오프셋 오염 + 단일 EEPROM write 원자성이 공장 캘리브레이션 실패를 기존 설정 손상으로 연결하는 새 위험 경로를 만든다.
3. **빌드가드 6개 × 의존 관계**가 컴파일 타임 `#error` 강제 없이 관리되어, 의존 관계 위반이 링크 오류나 런타임 오작동으로만 드러난다 — `TDC_TOUCH_REATI_ON_NOTOUCH_ENABLE=1 + NOTOUCH_GATE_ENABLE=0` 조합이 현재 빌드 오류 없이 통과한다.
4. **크래들 Phase 2 Re-ATI(~1.5초 블로킹)가 뚜껑 닫힘 기간 동안만 유효**하고 WDT 리셋 재부팅 시 소멸하므로, Phase 2 단독 구현은 비용 대비 효과가 없으며 Phase 3 EEPROM 저장과 원자적으로 묶어야 의미가 있다.
5. **Beta 레지스터 주소·POR default·비트 레이아웃이 모두 추정**인 상태에서 LTA IIR 설계 전체가 성립하며, Beta 미확인 상태에서는 Phase 1 "자기치유로 복구"라는 완화책이 실제 동작하지 않아 race 오염 시 복구 수단이 없다.
6. **공장 공정 전용 BLE 캘리브레이션 트리거가 출하 펌웨어에 잔존**할 가능성이 있으며, 캘리브레이션 함수 자체에 noTouch 환경 검증 로직이 없어 잘못된 조건에서 실행 시 영구 오염된 공장값이 EEPROM에 기록된다.
