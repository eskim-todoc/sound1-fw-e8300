# 16 · 그라운드_7 — 폴링 의존 타이밍 로직 전수 확인

**TL;DR**: IQS323 터치 타이밍 로직 11종을 전수 확인했다. 깨어있음 FSM의 롱터치·Re-ATI쿨다운·stuck승격은 free-running ms타임스탬프 기반이라 폴링 빈도와 무관히 안전하지만, 절전 ULP의 ATI에러재부팅(7연속)·롱터치재부팅(24사이클)·RESEED 2종과 FSM 내부 read실패hold·부팅해제디바운스까지 6종은 순수 호출횟수 누적이라 인터럽트 재설계 시 타이머 비교로 전환이 필요하다.

---

## 0. 조사 범위·방법

- 지시 파일 3개(`tdc_touch.c`, `main.c`, `tdc_touch_time.h`) 전수 통독 + `grep`. 단, 2026-06-20 "3레이어 탈피 간결 재작성"으로 실제 FSM 판정 로직 대부분이 `tdc_touch_logic.c`/`tdc_touch_logic.h`로 이동했음을 확인해 이 두 파일도 전수 포함했다(`tdc_touch.c`는 현재 init 상태머신 + 얇은 연결층일 뿐, 롱터치·stuck·Re-ATI 판정 자체는 없음).
- `ci_timer_get_tick()`/`tdc_timer_get_t3_tick()`가 "진짜 free-running 하드웨어 타이머인지, 폴링 호출에 종속된 소프트웨어 카운터인지"를 판정하기 위해 `Gen1_5/common/ci_timer.c/.h`, `Cortex-M3-src/systemControl/driver_timmer.c`, `initialize.c`의 TIMER3 초기화 지점까지 추가로 확인했다(직접 `Read`).
- **스코프 밖 명시**: `force_window_open()`/`wait_window_closed()`의 45ms/20ms I2C 버스 프로토콜 타임아웃(`tdc_touch_iqs323.c:128~175`)은 100ms 폴링 도메인과 다른 레이어(I2C 통신 창 타이밍)이며 이미 G2·C4 문서가 전담 분석했다 — 본 문서는 언급하지 않는다.
- 전 항목 파일·라인·리터럴 값은 본 노드가 직접 `Read`/`grep`한 것만 기재했다. 코드가 명시하지 않는 것은 전부 **[미확인]**으로 표시했다.

## 2. 판정 근거 — free-running 타이머 확인

`ci_timer_get_tick()`(`Gen1_5/common/ci_timer.c:143~146`)이 반환하는 `g_ci_timer_main_tick`은 `ci_timer_increase_tick()`(`ci_timer.c:130~141`)이 증가시키며, 이 함수는 `driver_timmer.c:10~16`의 `CFX_0_IRQHandler()`(및 이를 그대로 호출하는 `FIFO_5_IRQHandler()`)가 매 호출마다 부른다 — 즉 **CFX(오디오 DSP) FIFO 인터럽트가 구동하는, 터치 폴링과 완전히 독립적인 카운터**다. 헤더 자체 주석(`ci_timer.h:52~53`)도 "시스템 시간 전담 카운터"라고 명시한다.

`tdc_timer_get_t3_tick()`(`ci_timer.c:148~151`)이 반환하는 `g_tdc_timer_t3_tick`은 `TIMER_3_IRQHandler()`(`ci_timer.c:19~29`)가 증가시키는 **별도의 TIMER3 하드웨어 인터럽트 구동 카운터**다.

**중요한 추가 확인**: TIMER3의 "1틱"이 의미하는 실제 ms 값은 모드에 따라 다르다.
- 정상 부팅 시: `initialize.c:280` `ci_timer_init(OTE_1_5_GEN_TIMER_TICK_1MS_PM_NORMAL)` — 매크로 이름 그대로 **1ms/틱**으로 설정.
- 절전 ULP 진입 시: `main.c:868`(`fake_func_sleep`)·`main.c:1224`(`func_sleep`)에서 `ci_timer_init_prescaled(TDC_TOUCH_ULP_TIMER_PRESCALE, TDC_TOUCH_ULP_TIMER_TIMEOUT_VALUE)`로 **동일 TIMER3를 100ms/틱으로 재구성**한다(`tdc_touch_time.h:51~56` 공식: `PRESCALE_1 × (3999+1) / 40kHz = 100.0ms 정확`).

즉 절전 진입과 동시에 TIMER3 자체가 "100ms마다 정확히 1번" 울리도록 재설정되고, ULP 루프는 이 인터럽트로 깨어나는 `SYS_WAIT_FOR_INTERRUPT`(`main.c:891`,`:1230`) 구조다. 이 결합(웨이크업 1회 = TIMER3 100ms 재구성 1주기) 때문에 그룹_2의 "호출 횟수"가 지금까지는 "100ms 배수"와 정확히 일치해왔다 — 이 등가 관계가 §8의 핵심 논점이다.

## 3. 그룹_1 — 실제 경과시간(타이머) 기반, 폴링 빈도 무관 안전 (5종)

### 항목_1 — 롱터치(2400ms) → 절전 진입 트리거

`tdc_touch_logic.c:172~186`:
```c
if (curr_state == TDC_TOUCH_STATE_TOUCH)
{
    if (st->prev_state != TDC_TOUCH_STATE_TOUCH)
    {
        st->first_touch_ms = in->now_ms;   /* 진입 엣지 -> 기록 */
        st->long_latched   = false;
    }
    else if (!st->long_latched
             && TDC_TOUCH_LONG_TOUCH_MS <= (in->now_ms - st->first_touch_ms))
    {
        st->long_latched = true;
        out->long_touch  = true;
    }
}
```
`first_touch_ms`는 터치 진입 시각(`now_ms`, ci_timer 기반)을 1회만 기록하고, 이후 매 호출마다 `now_ms - first_touch_ms`(실제 경과 ms)를 2400과 직접 비교한다. **카운터 변수가 아예 없다.** 호출이 몇 번 있었는지는 이 판정에 전혀 영향을 주지 않는다.

### 항목_2 — Re-ATI 쿨다운(드리프트 게이트)

`tdc_touch_logic.c:154~161`:
```c
if (curr_state == TDC_TOUCH_STATE_NOT_TOUCH
    && !in->ati_active && in->ati_error
    && in->now_ms >= st->re_ati_cooldown_until_ms)
{
    out->action                  = TDC_TOUCH_ACT_RE_ATI;
    st->re_ati_cooldown_until_ms = in->now_ms + TDC_TOUCH_RE_ATI_COOLDOWN_MS;
}
```
"미래 절대시각"(`now_ms + 2000`)을 저장해두고 그 시각에 도달했는지만 비교한다 — 순수 타이머 기반. `TDC_TOUCH_RE_ATI_COOLDOWN_CNT` 매크로가 `tdc_touch_time.h`에 정의돼 있지만 **이 코드 어디에서도 쓰이지 않는다**(§7.1, grep 재확인).

### 항목_3 — stuck 3단계 승격 (RESEED → Re-ATI → MCLR)

`tdc_touch_logic.c:17~60`(`stuck_eval`), 핵심 조건 `:33`:
```c
if (TDC_TOUCH_STUCK_TIMEOUT_MS <= (now_ms - st->stuck_anchor_ms))
{
    st->stuck_anchor_ms = now_ms;
    switch (st->stuck_stage)
    {
        case 0: st->stuck_stage = 1; return TDC_TOUCH_ACT_RESEED;   /* 여기서 RESEED 발행 */
        case 1: st->stuck_stage = 2; return TDC_TOUCH_ACT_RE_ATI;
        default: return TDC_TOUCH_ACT_MCLR;
    }
}
```
30000ms(30초) 간격으로 `now_ms - stuck_anchor_ms`를 비교하는 순수 타이머 기반이다. **이것이 "reseed 관련" 폴링 카운터의 첫 번째 후보였으나, 실제로는 카운터가 아니라 타이머다** — §6에서 나머지 두 RESEED 트리거(카운트 기반)와 대조한다.

### 항목_4 — 부팅 5초 경고

`tdc_touch_logic.c:137~143`: `TDC_TOUCH_BOOT_WARN_MS <= (in->now_ms - st->boot_ready_ms)` — 타이머 기반.

### 항목_5 — auto-ATI 부팅 타임아웃

`tdc_touch.c:151~157`: `TDC_TOUCH_INIT_TIMEOUT_MS >= (tdc_timer_get_t3_tick() - s_mclr_done_tick)` — `ci_timer_get_tick()`이 아니라 T3 tick을 쓰지만 동일하게 타이머 기반(부팅 시점엔 T3가 1ms/틱이므로 값 자체도 정확히 ms 단위).

> [!NOTE]
> 항목_1~4가 참조하는 `now_ms`는 `tdc_touch.c:295~306`의 `int now = ci_timer_get_tick(); ... in.now_ms = (uint32_t) now;`에서 주입된다. 이 gate(`:296`) 자체도 "몇 번 호출됐는가"가 아니라 "이전 실행 이후 100ms가 실제로 지났는가"를 재는 타이머 게이트다 — `tdc_touch_process()`가 아무리 자주(또는 불규칙하게) 호출되어도 내부 FSM step은 실제 100ms 간격으로만 실행된다. **바깥 호출 빈도와 안쪽 판정 정확도가 이미 분리돼 있다**는 뜻이며, 그룹_1 전체가 이 분리 위에 성립한다.

## 4. 그룹_2 — 순수 호출횟수 누적(카운트) 기반, 현재는 100ms 고정주기에 결합 (6종)

### 항목_6 — read 연속실패 hold (깨어있음 FSM 내부)

`tdc_touch_logic.c:96~113`:
```c
if (!in->read_ok)
{
    st->read_fail_cnt++;
    if (st->read_fail_cnt <= TDC_TOUCH_READ_FAIL_HOLD_CNT)   /* =20 */
    {
        out->action = TDC_TOUCH_ACT_HOLD;
        out->curr_state = st->prev_state;
        return;   /* 상태머신 진입 자체를 동결 */
    }
    curr_state = TDC_TOUCH_STATE_NOT_TOUCH;
}
```
`now_ms`를 전혀 참조하지 않는다 — 오직 "연속으로 몇 번 호출됐을 때 read가 실패였는가"만 센다. **더 중요한 구조적 사실**: `read_fail_cnt <= 20`인 동안(21번째 연속 실패 전까지) 함수가 `return`하므로, 항목_1~4·7의 로직은 이 구간 동안 아예 평가되지 않는다 — 그룹_1이 안전한 것은 "호출될 때"의 이야기이고, 이 게이트가 호출 자체를 막아버리는 것은 별개 문제다(§9에서 INV-CTRL과 연결).

### 항목_7 — 부팅해제 디바운스 (깨어있음 FSM 내부)

`tdc_touch_logic.c:118~136`, 핵심 `:126~127`:
```c
st->boot_release_cnt++;
if (st->boot_release_cnt >= TDC_TOUCH_BOOT_RELEASE_DEBOUNCE_CNT)   /* =3 */
```
"연속 not-pressed 폴링 카운트"(헤더 주석, `tdc_touch_logic.h:70`)라는 표현 자체가 이미 카운트 방식임을 명시한다. `now_ms` 미참조.

### 항목_8 — ATI 에러 재부팅(7연속) ★ 과제 지정 대상

`main.c:1060~1092`(canonical helper) / `:947~965`(fake_func_sleep 인라인 중복):
```c
static void tdc_touch_sleep_handle_ati_error(bool ok, const tdc_touch_iqs323_status_t *st, int *ati_error_reboot_cnt)
{
    if (ok && st->ati_error && !st->ati_active)
    {
        if (5 < *ati_error_reboot_cnt)          /* :1066 */
        {
            ...
            SYS_WATCHDOG_RESET();               /* 실제 리부팅 */
        }
        else
        {
            tdc_touch_iqs323_re_ati();
            (*ati_error_reboot_cnt)++;           /* :1085 */
        }
    }
    else if (ok && !st->ati_error && !st->ati_active)
    {
        *ati_error_reboot_cnt = 0;               /* :1090 */

}
```
직접 트레이스(초기값 0):

| 호출 순번 | 진입 시 cnt | `5 < cnt`? | 동작 | 종료 후 cnt |
|---|---|---|---|---|
| 1 | 0 | false | re_ati, cnt++ | 1 |
| 2 | 1 | false | re_ati, cnt++ | 2 |
| 3 | 2 | false | re_ati, cnt++ | 3 |
| 4 | 3 | false | re_ati, cnt++ | 4 |
| 5 | 4 | false | re_ati, cnt++ | 5 |
| 6 | 5 | false | re_ati, cnt++ | 6 |
| **7** | 6 | **true** | **`SYS_WATCHDOG_RESET()`** | (리부팅) |

**정확히 7번째 연속 발생에서 재부팅**한다(6회 복구 시도 후) — 과제가 지정한 "ATI에러 카운터(7연속)"와 정확히 일치한다. `5`는 `tdc_touch_time.h`에 매크로화돼 있지 않은 리터럴이다(§7.3). `read` 실패 시(`ok`==false)는 두 분기 모두 조건을 만족하지 못해 **카운터가 동결**된다(증가도 리셋도 없음) — `now_ms` 미참조, 순수 호출횟수 누적.

### 항목_9 — 롱터치 재부팅(2400ms=24사이클) ★ 과제 지정 대상

`main.c:1124~1153`(helper) / `:1002~1019`(fake 인라인):

## 5. 교차 발견 — 같은 "2400ms 롱터치"의 이중 구현

| 구분 | 매크로 | 파일:라인 | 목적 | 방식 |
|---|---|---|---|---|
| 항목_1 | `TDC_TOUCH_LONG_TOUCH_MS`=2400 | `tdc_touch_logic.c:180~181` | **깨어있음 → 절전 진입** 트리거 (`tdc_touch_process()`가 `true` 반환) | 타이머(`now_ms` 차분) |
| 항목_9 | `TDC_TOUCH_ULP_REBOOT_TOUCH_MS`=2400 → `_CNT`=24 | `main.c:1129~1130` | **절전 중 재부팅 → 노말 복귀** 트리거 | 카운트(`touch_cnt++`) |

이름(롱터치)과 값(2400ms)은 같지만 서로 다른 매크로·다른 상태(하나는 깨어있음, 하나는 절전)·다른 후속 동작(절전 진입 vs CM3 재부팅)이며, 무엇보다 **구현 기법이 완전히 다르다**. 인터럽트 재설계 논의에서 "롱터치 로직"을 한 덩어리로 취급하면 이 이중성을 놓치기 쉽다 — 재설계는 반드시 두 지점을 별도로 검토해야 한다.

## 6. 교차 발견 — "RESEED"라는 이름 아래 숨은 3가지 트리거

| 트리거 | 소속 | 방식 | 파일:라인 |
|---|---|---|---|
| stuck stage0 승격 | 깨어있음 FSM (항목_3) | **타이머**(30000ms) | `tdc_touch_logic.c:38~42` |
| 노터치 확정 (항목_10) | 절전 ULP | **카운트**(3회) | `main.c:1101~1104` |
| 10초 무확정 강제 (항목_11) | 절전 ULP | **카운트**(100회) | `main.c:1114~1121` |

`tdc_touch_iqs323_reseed()`(`tdc_touch_iqs323.c:468`) 자체는 0xC0 bit3 단발 write일 뿐 내부에 시간·카운트 로직이 없다 — 모든 타이밍 판단은 호출부(위 3곳)에 있다. 과제가 예시로 든 "reseed 관련" 카운터는 **하나가 아니라 셋이며, 그중 하나(stuck)는 타이머, 나머지 둘(절전 ULP)은 카운트**라는 것이 정확한 답이다.

## 7. 부가 발견 (문서 위생·데드코드)

### 7.1 `TDC_TOUCH_RE_ATI_COOLDOWN_CNT` — 죽은 코드

`tdc_touch_time.h:29~30`에 정의되지만, `grep -rn "COOLDOWN_CNT"` 결과 이 정의 라인 외 사용처가 저장소 전체에 **0건**이다. 실제 Re-ATI 쿨다운(항목_2)은 `_MS` 값을 `now_ms`와 직접 연산해 `_CNT` 변형을 아예 쓰지 않는다.

### 7.2 주석 불일치 — "@200=" 잔재

`tdc_touch_time.h`의 `_CNT` 매크로들에 달린 인라인 주석이 전부 옛 `POLL_INTERVAL_MS=200`(현재는 100) 시절 값을 반영한 채 갱신되지 않았다:

| 매크로 | 주석 표기 | 현재 컴파일 값(직접 재계산) |
|---|---|---|
| `READ_FAIL_HOLD_CNT` | `@200 = 10` | **20** |
| `BOOT_RELEASE_DEBOUNCE_CNT` | `@200 = 2` | **3** |
| `ULP_NOTOUCH_DEBOUNCE_CNT` | `@200 = 2` | **3** |
| `ULP_FORCE_RESEED_CNT` | `@200 = 50` | **100** |
| `ULP_REBOOT_TOUCH_CNT` | `@200 = 2` | **24**(주석은 200 가정에서도 2400/200=12가 맞아야 하므로 단순 오기로 보인다) |

매크로 자체는 `TDC_TIME_TO_CNT()`로 자동 파생되므로 **동작에는 영향이 없다**. 다만 이 주석들은 "카운트를 손으로 ms로 환산해 두는" 관행 자체가 유지보수 중 얼마나 쉽게 어긋나는지를 실증한다 — 그룹_2를 그룹_1처럼 순수 ms 비교로 바꾸면 이런 "환산 주석"이 애초에 필요 없어진다는 점에서 §8 권고와 직결된다.

### 7.3 매직넘버 `5` — ATI 재부팅 임계값 미중앙화

항목_8의 `5`(`main.c:1066`,`:949`)는 `tdc_touch_time.h`("터치 시간 상수 한 곳"이 헌장인 파일)에 전혀 등재되지 않은 리터럴이다. 파일 헤더 철학("ms 수치만 바꾸면 자동 파생")과 어긋나는 유일한 예외다.

### 7.4 read 실패 시 처리 정책 — 3갈래로 갈린다

| 카운터 | read 실패 시 동작 | 근거 |
|---|---|---|
| 항목_6 `read_fail_cnt` | 실패 자체를 세고, 20회까지는 **HOLD**(전체 FSM 동결) | `tdc_touch_logic.c:96~106` |
| 항목_8 `ati_error_reboot_cnt` | 증가도 리셋도 없이 **동결** | `main.c:1064~1091`, 두 조건 모두 `ok` 필요 |
| 항목_9 `touch_cnt` | **즉시 0 리셋** | `main.c:1149~1152` |
| 항목_10 `notouch_cnt` | **즉시 0 리셋** | `main.c:1109~1112` |
| 항목_11 `ignore_elapsed` | 실패 무관 **무조건 증가**(리셋 없음) | `main.c:1097` 주석 명시 |

구조적으로 유사한 카운터 5개가 read 실패에 대해 4가지 서로 다른 정책(hold·동결·즉시리셋·무조건증가)을 갖는다. 이는 인터럽트 재설계와 별개로 이미 존재하는 비일관성이며, 그룹_2를 재작성할 기회가 있다면 정책 통일도 함께 검토할 가치가 있다(단, 이는 내 역할 범위를 넘는 설계 제안이라 언급만 한다).

## 8. 인터럽트 재설계 함의 — 조건부 결론

과제 질문("폴링횟수 카운터를 그대로 못 쓰고 타이머로 바꿔야 하는지")에 대한 답은 **그룹_2(6종) 전부에 대해 "예, 원칙적으로 전환이 필요하다"**이나, 필요성의 강도는 채택되는 재설계 방식에 따라 갈린다.

- **후보_6(15번 문서, `19_C6_...md`) 방식**: "터치진입/ATI에러 이벤트 수신 시 활성 폴링(100ms) 재개"라는 설계라면, 그 활성 구간 동안은 지금과 동일하게 TIMER3 100ms 고정 주기가 유지되므로 그룹_2 카운터는 **수정 없이도 현재와 동일하게 동작**할 수 있다. 이 경우 "호출 1회 = 100ms"라는 현재의 암묵적 전제가 재설계 이후에도 그대로 보존되기 때문이다.
- **더 급진적인 설계**(활성 구간에서도 RDY 엣지 자체가 웨이크업원이 되어 호출 간격이 이벤트 도착 패턴에 좌우되는 경우, 또는 §8.12(공통 배경 인용)의 "이벤트 플래그가 set된 동안 계속 ready window 제공" 특성상 짧은 시간에 여러 번 깨어날 수 있는 경우)에서는 "N회 호출"이 "N×100ms"와 더 이상 같지 않으므로, 그룹_2를 그대로 쓰면 **7연속·24사이클·3회·100회라는 문턱이 실제로는 훨씬 짧거나 긴 실제 시간에 도달**하게 되어 설계 의도(700ms/2400ms/300ms/10s)가 조용히 깨진다.

**권고**: 어느 방식이 채택되든, 그룹_2 6종을 `tdc_touch_time.h`가 이미 그룹_1에서 증명한 패턴(정수 카운터 대신 `now_ms`/`now_ms`류 절대시각 저장 + 차분 비교)으로 통일 전환하는 편이 안전하다. 근거: (a) 이미 5종에서 검증된 안전한 패턴이라 신규 리스크가 낮다, (b) 어느 폴링 설계를 택하든 정답이 되어 재설계 방식 선택과 독립적으로 안전하다, (c) §7.2가 보여준 "카운트↔ms 환산 주석 노후화" 문제 자체가 사라진다, (d) 변경 비용이 낮다(변수형을 `int cnt`→`uint32_t xxx_start_ms`로, 비교를 `cnt++;cnt>=N`→`now_ms - xxx_start_ms >= N_MS`로 바꾸는 정도). 다만 이는 **구현 설계 제안이며 내 역할(그라운드_7=현황 확인) 범위를 넘는 부분이라 후보 페르소나 판단에 맡긴다.**

> [!NOTE]
> 그룹_2 전환을 위해서는 절전 ULP 경로에서도 그룹_1과 동일한 free-running 시각 소스가 필요하다. §2에서 확인했듯 절전 중에는 CFX FIFO(`ci_timer_get_tick()`의 원천)가 꺼져 있을 가능성이 높고(FPGA·PMIC OFF), 대신 TIMER3(`tdc_timer_get_t3_tick()`)가 100ms 주기로 재구성되어 살아있다 — 그러나 이 재구성된 T3 tick도 "1틱=100ms"라는 고정 전제를 매핑에 쓰고 있어(§2), 이벤트 기반으로 T3 재구성 자체가 바뀌면(예: 더 이상 고정주기가 아니게 되면) 이 시각 소스 자체를 다시 검토해야 한다는 점은 [미확인] 리스크로 남긴다.

## 9. 불변식(INV-CTRL) 연결

- **INV-CTRL-1(Full ATI)**: 그룹_2 어느 항목도 Full ATI 실행 경로 자체를 게이팅하지 않는다 — 직접 연관 없음.
- **INV-CTRL-2(ATI에러 → Re-ATI)**: 항목_2(깨어있음, 타이머)와 항목_8(절전, 카운트)이 이 불변식의 두 구현이다. 이 둘은 **서로 다른 그룹**에 속한다 — 깨어있음 쪽은 인터럽트 재설계 영향이 낮고, 절전 쪽(7연속 재부팅)은 §8의 전환 검토 대상이다.
- **INV-CTRL-3(첫 터치 해제 감지)**: 항목_7(깨어있음 부팅해제 디바운스, 카운트)과 항목_10(절전 노터치확정, 카운트) 둘 다 그룹_2다 — 이 불변식의 구현은 **양쪽 다 카운트 기반**이라는 뜻이며, 인터럽트 재설계 시 우선적으로 검토가 필요한 지점이다. 선행 문서(G3, `03_G3_...md:134`)가 이미 "절전측 디바운스가 노말측보다 통신 신뢰도에 더 취약"하다고 지적한 바 있는데, 본 노드가 확인한 사실(항목_7·10 둘 다 `read` 실패 시 즉시 0 리셋)이 그 지적과 정합한다.

## 핵심 결론 (요약)

1. 100ms 폴링 의존 타이밍 로직은 총 **11종**이며, **5종(그룹_1)은 `now_ms`/T3 tick 실제 경과시간 차분**(free-running, CFX FIFO·TIMER3 하드웨어 인터럽트 구동, 폴링 호출 빈도와 무관), **6종(그룹_2)은 `int` 변수 `++`만 하는 순수 호출횟수 누적**(`now_ms` 미참조)이다.
2. 과제가 지정한 두 카운터 — **ATI에러(main.c:1062~1092, 7연속 재부팅)와 롱터치(main.c:1125~1153, `TDC_TOUCH_ULP_REBOOT_TOUCH_CNT`=24, 2400ms=24사이클)** — 는 모두 **그룹_2(순수 카운트)**로 확정 판정한다. 정확히 7번째 연속 발생, 정확히 24번째 연속 발생에서 트리거되는 것을 직접 코드 트레이스로 검증했다.
3. 다만 이름이 같은 "2400ms 롱터치"가 깨어있음 경로(항목_1, 타이머)와 절전 경로(항목_9, 카운트)에 **완전히 다른 메커니즘으로 이중 구현**되어 있다는 점, "reseed"도 3가지 서로 다른 트리거(타이머 1 + 카운트 2)로 나뉜다는 점은 재설계 논의에서 반드시 구분해야 한다.
4. 현재 그룹_2가 정확한 것은 ULP 루프의 웨이크업이 TIMER3 100ms 고정 재구성에 100% 결합돼 있기 때문일 뿐이다 — 인터럽트/이벤트 기반으로 호출 간격이 불규칙해지는 재설계를 채택하면 이 등가가 깨지므로, 안전을 위해서는 그룹_2 6종 전부를 그룹_1과 같은 절대시각 비교 방식으로 전환하는 것을 권고한다(단, 이는 구현 설계 제안이라 후보 페르소나 판단 영역).
