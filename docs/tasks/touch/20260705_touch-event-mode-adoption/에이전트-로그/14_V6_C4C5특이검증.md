# 14 · 검증_6 — C4·C5 특이 검증 (이벤트 모드 채택 딥다이브)

**TL;DR**: C4의 DIO 인터럽트 인프라·2슬롯 제약·mclr 핀 공유 주장은 코드 직접 대조로 전부 정확했으나, 같은 문서의 WFI 리스크 근거("노말 루프에 WFI 없음")는 반증됨(같은 루프 738행에 WFI 실재). C5의 핵심 주장인 "에라타 노출 오늘과 변화 없음"은 C5 자신이 인용한 G2 히트율 모델을 C5 자신의 제안값(83ms)에 적용하면 히트율이 17%로 급락해 모순됨을 발견했다. 데이터시트 "펌웨어 권장" 인용 한 건은 원문에 없고 요약 md 해설로 확인됐다.

## 1. (a) C4 — DIO 인터럽트 인프라·2슬롯 제약·mclr 핀 공유

### 반증시도_1 — ci_dio.c의 인터럽트 인프라가 실재하는가

C4는 `ci_dio_configure_sleep()`(`:102~151`) 내부 `#if 0`(`:104~125`) 블록에 `Sys_DIO_IntConfig(0, DIO_INT_SRC_DIO_34|...|FALLING_EDGE, ...)`(가속도, 하강엣지)·`Sys_DIO_IntConfig(1, DIO_INT_SRC_DIO_28|...|RISING_EDGE, ...)`(케이스덮개, 상승엣지)가 있고, `#if 0` **밖**(`:144~148`)에 `NVIC_ClearPendingIRQ`/`NVIC_EnableIRQ(DIO_0_IRQn/DIO_1_IRQn)`가 있으며, `DIO_0_IRQHandler`/`DIO_1_IRQHandler`(`:156~167`)가 각각 `ci_dio_set_int_flag_acc_sensor()`/`ci_dio_set_int_flag_case_lid_open()`를 호출한다고 주장했다.

`ci_dio.c` 전문을 직접 Read한 결과, **라인 번호까지 완전히 일치**한다.

```c
// :121, :124 (#if 0 블록 내부, :104~125)
Sys_DIO_IntConfig(0, (DIO_INT_SRC_DIO_34 | DIO_INT_DEBOUNCE_DISABLE | DIO_INT_EVENT_FALLING_EDGE), DIO_DEBOUNCE_SLOWCLK_DIV32, 0);
Sys_DIO_IntConfig(1, (DIO_INT_SRC_DIO_28 | DIO_INT_DEBOUNCE_DISABLE | DIO_INT_EVENT_RISING_EDGE), DIO_DEBOUNCE_SLOWCLK_DIV32, 0);

// :144~148 (#if 0 블록 밖, 현재도 실행됨)
NVIC_ClearPendingIRQ(DIO_0_IRQn);
NVIC_ClearPendingIRQ(DIO_1_IRQn);
NVIC_EnableIRQ(DIO_0_IRQn);
NVIC_EnableIRQ(DIO_1_IRQn);

// :156~167
void DIO_0_IRQHandler(void) { ci_dio_set_int_flag_acc_sensor(); }
void DIO_1_IRQHandler(void) { ci_dio_set_int_flag_case_lid_open(); }
```

또한 `Sys_DIO_IntConfig` 리터럴을 `src/2__cm3` 전체에서 grep한 결과 **정확히 이 2곳뿐**이며(반증 시도: 다른 곳에서 슬롯 0/1을 재구성하거나 충돌시키는 코드가 있는지 찾았으나 0건), `ci_dio_configure_sleep()`은 `initialize.c:206`에서 실제 호출됨을 확인했다(반증 시도: 죽은 함수인지 확인했으나 살아있는 호출부 존재).

**반증 실패 — 근거**: 코드 원문이 C4의 인용과 완전히 일치하고, 독립적으로 수행한 "다른 곳에서 슬롯을 이미 쓰고 있는가" 반증 시도도 실패했다(0건). **C4의 이 주장은 CONFIRMED.**

### 반증시도_2 — "2슬롯 제약"은 실제 하드웨어 제약인가, 아니면 리포지토리 사용 현황일 뿐인가

C4는 "`DIO_2_IRQn` 등 3번째 이상 슬롯은 저장소 전체에서 0건... 그 이상이 실리콘 차원에서 존재하는지는 벤더 레퍼런스 매뉴얼이 저장소에 없어 [미확인]"이라고 명시적으로 헤지했다. 이 헤지 자체를 반증(즉, "사실은 정말 2개뿐이다" 또는 "사실은 이미 이 안에 답이 있었는데 놓쳤다"는 방향으로) 시도했다.

리포지토리 안에서는 C4의 주장대로 `DIO_0_IRQn`·`DIO_1_IRQn` 2개만 발견되며(`.d` 의존성 파일이 가리키는 `hw.h` 자체가 저장소 밖에 있다는 C4의 진단도 `find`로 재확인 완료 — 저장소 안에는 `hw.h`가 없다), 저장소 내부만으로는 이 이상 답을 낼 수 없다는 C4의 판단은 정확하다.

다만 본 검증은 **리포지토리 밖까지 추적**해 이 [미확인]을 실제로 풀어보았다. `.d` 의존성 파일(`Debug/Cortex-M3-src/main.d`)이 `sdk\include\cm3\sk5_hw_cid101.h`를 가리키고 있어(이 프로젝트 빌드가 실제로 참조하는 정확한 파일 경로), 로컬에 설치된 `ON Semiconductor/Ezairo 8300 SDK`에서 바로 이 파일을 확인했다.

- `sk5_hw_cid101.h:13219`에 `#define DIO_INT_SRC_DIO_16 ((uint32_t)(0x10U << DIO_INT_CFG_SRC_Pos))`가 **실재한다** — C4가 "명명 패턴상 개연성만 있다"고 낮춰 잡은 [미확인] 항목이 실제로는 존재가 확인된다.
- `sk5_vectors.h:61~65`에 `DIO_0_IRQn=16, DIO_1_IRQn=17, DIO_2_IRQn=18, DIO_3_IRQn=19, DIO_4_IRQn=20`가 정의되어 있다 — **실리콘/CMSIS 레벨에서는 최소 5개의 DIO 인터럽트 슬롯이 존재**한다.

> [!IMPORTANT]
> **반증 시도 결과 — 부분 성공(단, C4의 결론은 무효화하지 않음)**: "2슬롯 제약"은 **리포지토리가 현재 사용하는 슬롯 수에 대한 사실**로는 정확하지만(C4도 정확히 이렇게 표현했다 — "코드로 확인 가능한... 정확히 2개"), **실리콘 차원의 진짜 제약이 아니다**. 실제로는 최소 5개 슬롯이 있고 그중 2개만 쓰인다. C4의 "3번째 필요 시 벤더 확인 필요"라는 조건부 우려는 이번에 확인한 벤더 근거로 완전히 해소된다(3번째는커녕 4번째·5번째까지 여유가 있다). 이것이 C4의 최종 판정("SW-only 실현 가능")을 뒤집지는 못한다 — 오히려 C4 본인의 구체적 설계안(§1.4, 슬롯 0을 DIO16 재사용)은 애초에 신규 슬롯이 필요 없는 안이었으므로 영향이 없다. 다만 C4의 리스크 서술이 실제보다 다소 보수적이었다는 점은 지적할 가치가 있다.
>
> **단, 이 벤더 SDK 파일은 Sound1 git 리포지토리 밖(로컬 환경의 Eclipse/Ezairo SDK 설치본)에 있다** — 원 지시사항이 못박은 "실제 코드(`src/2__cm3/Cortex-M3-src/`)" 범위를 벗어난 보조 근거이므로, 본 항목의 확신도는 **PLAUSIBLE**(리포지토리의 `.d` 파일이 정확히 이 파일·이 변주(cid101)를 가리킴을 확인했으므로 근거는 강하나, 완전히 동일한 빌드환경 재현까지는 확인 못함)로 표기한다.

### 반증시도_3 — DIO16-MCLR 핀 공유 리스크가 실재하는가

C4는 `tdc_touch_iqs323_mclr()`(`:474~481`)가 평상시 입력인 RDY(DIO16) 핀을 리셋 시 잠깐 출력·LOW 구동으로 전환한다며, 이것이 인터럽트 상시 활성화 시 자기유발 인터럽트를 일으킬 수 있다고 주장했고, 유일한 호출부가 `tdc_touch.c:185`(`tdc_touch_init_begin()`) 1곳뿐이라 부팅 시퀀스만 지키면 회피 가능하다고 결론지었다.

직접 확인한 코드:
```c
// tdc_touch_iqs323.c:474~481
void tdc_touch_iqs323_mclr(void)
{
    Sys_DIO_Config(TDC_TOUCH_IQS323_RDY_PIN, TDC_TOUCH_IQS323_RDY_PIN_CFG_OUTPUT);
    Sys_GPIO_Set_Low(TDC_TOUCH_IQS323_RDY_PIN);
    Sys_Delay(TDC_TOUCH_IQS323_DEFAULT_DELAY_MS * TDC_TOUCH_IQS323_MCLR_HOLD_MS);
    Sys_DIO_Config(TDC_TOUCH_IQS323_RDY_PIN, TDC_TOUCH_IQS323_RDY_PIN_CFG_INPUT);
    Sys_Delay(TDC_TOUCH_IQS323_DEFAULT_DELAY_MS * TDC_TOUCH_IQS323_BOOT_WAIT_MS);
}
```
`grep -rn "tdc_touch_iqs323_mclr"` 결과 정의(`iqs323.c:474`)·선언(`iqs323.h:85`)·**호출 1곳**(`tdc_touch.c:185`)뿐이다(반증 시도: 다른 호출부가 있는지 전수 검색했으나 없음). `Board_OTE_ver1_5.h:46`도 `#define DIO_PIN_INDEX_for_Accelerometer DIO16 // v0.35, NET: INTERRUPT_n (터치센서 rdyy)`로 DIO16이 원래 "INTERRUPT_n" 네트였다가 터치 RDY로 전용됐음을 정확히 뒷받침한다.

**반증 실패 — 근거**: 호출부 단일성·핀 토글 시퀀스·주석 근거 모두 코드와 문자 그대로 일치한다. **C4의 이 주장도 CONFIRMED.**

### 발견_1(범위 확장) — C4 §1.4의 WFI 리스크 근거 자체는 반증됨

과제 지시 범위(2슬롯·mclr 공유)를 검증하는 과정에서 C4의 같은 절(§1.4)에 있는 인접 주장을 추가로 점검했다. C4는 다음과 같이 서술했다.

> "**노말 모드(`tdc_touch_process`, `main.c:452`)가 속한 메인 루프는 WFI 호출이 전혀 없다**(그 루프 부근 738·801·891·1230행 WFI는 전부 다른 루프 소속임을 grep으로 확인) — 즉 노말 경로에 WFI를 도입하는 것은 지금까지 한 번도 검증되지 않은 새로운 거동..."

`main.c`를 직접 Read해 루프 경계를 추적한 결과:

```c
// main.c:437
    while (1)
    {
        ...
        powerButtonPushed = tdc_touch_process();   // :452, 같은 루프 안
        ...
        if (systemState.systemOff == true) { ... break; ... }   // :701~728
        ...
        SYS_WATCHDOG_REFRESH();      // :737
        SYS_WAIT_FOR_INTERRUPT;      // :738  ← 같은 루프의 마지막 문장
    }  // 끝, while                  // :739  ← 원본 주석 그대로
```

**452행(`tdc_touch_process()`)과 738행(`SYS_WAIT_FOR_INTERRUPT`)은 437행에서 시작해 739행에서 닫히는 동일한 `while(1)` 루프 안에 있다** — 이 while문의 닫는 중괄호에는 원본 코드 자신이 "`// 끝, while`"이라는 주석을 달아 놓아 루프 경계가 모호할 여지도 없다. `systemState.systemOff`로 인한 조기 `break`(:726) 경우를 제외하면, `tdc_touch_process()`가 호출되는 **매 이터레이션마다 루프 끝에서 WFI를 거친다.**

> [!WARNING]
> **반증 성공(CONFIRMED)**: C4의 "노말 모드가 속한 메인 루프는 WFI 호출이 전혀 없다"는 서술은 코드 사실과 어긋난다. 738행은 452행과 **다른 루프가 아니라 같은 루프**다. 아마도 grep 결과에서 함수 경계(중괄호 균형)를 따라가지 않고 라인 번호만으로 "부근 루프가 다르다"고 판단한 데서 온 오류로 추정된다.
>
> 이 오류가 C4의 최종 판정("RDY 엣지 인터럽트 전환 SW-only 실현 가능")을 무효화하지는 않는다. 다만 C4가 이 사실을 근거로 세운 위험 프레이밍("노말 경로에 WFI 도입은 완전히 새로운, 한번도 검증되지 않은 거동")은 반대 방향으로 재평가되어야 한다 — 노말 모드 루프는 **이미** 자기 자신의 주기로 WFI를 정상적으로 쓰고 있다(그 웨이크업원이 정확히 무엇인지, `iterationFlag`를 세팅하는 인터럽트와 어떤 관계인지는 본 검증 범위에서 끝까지 추적하지 못해 **[미확인]**으로 남긴다). 즉 실제 리스크는 "WFI를 처음 들여오는 것"이 아니라 "이미 있는 루프-레벨 WFI 지점보다 더 앞선 시점에, `force_window_open()` 내부에서 중첩된(nested) 더 짧은 WFI 대기를 추가하는 것"이라는, C4가 서술한 것과는 성격이 다른 문제다. 이는 C4의 컨텍스트별 차등 적용 권고(노말 모드는 WFI 미사용) 자체를 반박하지는 않지만, 그 권고의 **근거**는 다시 써야 한다.

## 2. (b) C5 — "Streaming+ReportRate가 공정한 비교 대상인가"

### 반증시도_4 — 레지스터 구조·전류표 인용이 정확한가

C5가 인용한 사실관계를 원문·코드로 전부 재대조했다.

**반증 실패** — 위 8개 항목 전부 원문·코드와 정확히 일치한다. C5의 그라운드 재확인 부분은 매우 견고하다.

한 가지 짚을 점: §8.11.1 원문("streaming mode data is constantly reported **at the relevant power mode report rate**... registers")은 C5가 §3에서 실제로 사용한 것(비트필드 독립성 + 전류표 정황)보다 **더 직접적인 근거**다 — Streaming 모드 자체의 정의문이 Report Rate 레지스터를 명시적으로 지목하기 때문이다. C5는 이 문장을 §2.2에 인용은 해두고도 §3의 핵심 논거로는 격상하지 않았다 — 자신에게 유리한 가장 강한 증거를 스스로 과소 활용한 셈이다(사소하지만, 주장이 과장되었다는 방향과는 반대다).

### 반증시도_5(핵심) — "히트율 프로필은 오늘과 근본적으로 같은 성격을 유지한다"는 주장

C5의 §5.3은 "후보_5는 단독으로 완결적이다... `force_window_open()`의 기존 조기반환 구조·히트율 프로필은 오늘과 근본적으로 같은 성격을 유지한다(**§6.1에서 상술**)"라고 주장하고, §6.2 리스크 비교표는 "I2C Lock-Up 에라타 노출: 후보_5 = **오늘 대비 변화 없음**(§6.1 상술 — 여전히 자가토글 기반 조기반환이 대부분 히트)"이라고 못박는다.

**교차 확인**: C5 문서의 §6.1을 직접 다시 읽었으나, §6.1은 "이득 비교" 표(표적 메커니즘·근거 수준·아키텍처 적합성·데이터시트 정합성)일 뿐, 히트율이 왜 "오늘과 근본적으로 같은 성격"인지에 대한 **정량적 서술이 어디에도 없다**. 즉 "§6.1에서 상술"이라는 스스로의 약속이 실제로는 이행되지 않은 참조다.

**독립 재계산**: C5가 §2.3에서 그대로 계승한다고 밝힌 그라운드_2(G2) 문서의 히트율 모델(§2.4, "히트율(단순 모델) ≈ (P − T_주기) / P", P=100ms 폴링 주기)을 C5 자신이 §5.2에서 제안한 구체적 예시값(**0xC1=83ms**, `0x53,0x00`)에 그대로 적용해 보았다.

| T_주기(자연 재개방 주기) | 히트율 (P−T)/P | 출처 |
|---|---|---|
| 0.4ms | 99.6% | G2 §2.3 자체유도(현재, 0xC1=0 가정) |
| 1ms | 99% | G2 §2.4 |
| 5ms | 95% | G2 §2.4 |
| 16ms | 84% | G2 §2.4(단, G2 자신이 "무관한 참고치"로 격하) |
| 50ms | 50% | G2 §2.4(극단 보수 가정) |
| **83ms (C5 §5.2 자신의 제안값)** | **17%** | **본 검증 산출** |

> [!IMPORTANT]
> **반증 시도 성공(PLAUSIBLE)**: G2가 검토한 어떤 T_주기 가정(0.4ms~50ms, 즉 오늘의 현황에 대한 가장 보수적인 추정치까지 포함)을 쓰더라도, C5가 실제로 제안한 83ms를 대입하면 히트율은 그 전 범위보다 훨씬 낮은 **17%**로 떨어진다 — 즉 강제개방(0xFF) 빈도가 오늘 대비 대폭 증가한다는 뜻이다. 이는 C5의 "히트율 프로필 유지"·"에라타 노출 변화 없음" 주장과 **정면으로 모순**된다.
>
> 물론 이벤트 모드(유휴구간 히트율 ≈0%, G2 §3.2)만큼 완전히 무너지지는 않는다 — 17%는 0%보다는 낫다. 그러나 "오늘(50~99.6%) → 후보_5(17%)"의 하락폭이 이미 "후보_5(17%) → 이벤트 모드(0%)"의 남은 하락폭보다 훨씬 크다는 점이 중요하다. 다시 말해 **강제개방 빈도가 늘어나는 손실의 대부분은 이미 "Report Rate를 명시적으로 어떤 값이든 설정하는 행위" 자체에서 발생**하며, 거기서 이벤트 모드까지 마저 가는 추가 비용은 상대적으로 작다. 이것이 사실이라면 C5가 강조하는 "이벤트 모드 대비 압도적으로 안전"이라는 상대적 우위는 **정도의 차이이지 종류의 차이가 아니게 되어, C5가 주장하는 만큼 벌어지지 않는다.**
>
> **반증이 성공한 근거**: (1) C5가 §2.3에서 명시적으로 계승한다고 밝힌 G2의 모델과 수식을 그대로 사용했다(임의 모델을 새로 만들지 않음). (2) 대입값(83ms)도 C5 자신이 §5.2에서 제안한 구체적 수치를 그대로 썼다(가상의 숫자가 아님). (3) 계산 결과가 G2의 전체 민감도 범위(0.4~50ms)를 완전히 벗어나 있어, 우연한 경계효과가 아니라 방향성이 뚜렷하다.
>
> **다만 확신도를 CONFIRMED가 아닌 PLAUSIBLE로 제한하는 이유**: 이 계산이 기대는 "재개방 후 서비스되거나 타임아웃 전까지는 계속 열려있다"는 창 모델 자체가, G2 스스로도 §7 리스크표에서 "[가설, 원문 미명시]"로 표기한 **미확정 가설**이다. 또한 83ms는 C5 자신도 "[실측 게이트]"로 명시한 예시값일 뿐 확정 제안치가 아니다 — 더 작은 값(예: 10ms대)을 골랐다면 히트율 하락은 훨씬 완만했을 것이다. 즉 이 반증은 "C5의 특정 예시 숫자가 무조건 틀렸다"가 아니라, **"Report Rate를 얼마나 늦출지(자기애그레서 저감 효과)와 히트율을 얼마나 지킬지(에라타 노출 억제) 사이에 실재하는 트레이드오프를, C5가 전혀 검토하지 않은 채 '변화 없음'이라고 단정했다"**는 데 있다. 이 트레이드오프 자체의 존재는 C5가 인용한 모델만으로도 이미 도출 가능했던 것이라, "확인 안 했다"는 것 자체가 이번 검증의 핵심 소득이다.

### 반증시도_6 — "데이터시트 권장은 Event mode 기본" 인용의 출처 감사

C5는 §6.1 비교표의 "데이터시트 권장과의 정합성" 행에서 이벤트 모드 쪽에 "정합(§8.11.2 '펌웨어 권장은 Event mode 기본')"을, 후보_5 쪽에 "어긋남(Streaming은 '개발단계 임시용', §8.11.2)"를 적어 후보_5 스스로에게 불리한 항목으로 인정했다. 이 인용의 원문 실재 여부를 추적했다.

- 오케스트레이터 공통 입력(`00_...md`)은 이 표현을 "데이터시트 확정 사실(선행 작업에서 원문 대조 완료)"이라고 명시하며 "§8.11.2 NOTE: '펌웨어 권장은 Event mode 기본, Streaming은 개발단계 임시용'"이라 인용했다.
- 본 검증에서 `pdftotext -layout` 원문 §8.11.2 전체를 재추출한 결과, 실제 문장은 **"In event mode the RDY line will only go low when one or more of the enabled events are triggered or if the device resets. This is usually enabled since the master does not want to be interrupted unnecessarily during every cycle if no activity occurred."**뿐이다. "recommend"·"temporary"·"development"·"debug" 계열 단어를 §8 전 구간에서 grep했으나 이런 취지의 문장은 **찾지 못했다.**
- 출처를 추적한 결과, `docs/참고/touch/데이터시트/05_i2c인터페이스.md`(:349~350, :360)의 `[!NOTE]` 해설 블록에 "펌웨어 권장: **event mode를 기본**으로 사용하고, streaming은 개발·디버깅 단계에서 임시 활용한다"라는 문장이 있다 — 이 요약 md 자체가 §8.11.2 원문 옆에 **작성자 자신의 해설**로 덧붙인 것으로 보이며(같은 노트 안에 ASCII 다이어그램·CPU 부하 비교표 등 명백한 부가 해설이 함께 있음), 데이터시트 원문의 직접 인용이 아니다. §8.15 Program Flow Diagram(Figure 8.3)도 "이벤트 모드 통신의" 흐름도라고 명시(원문 "The program flow **for event mode communication** is shown in Figure 8.3")할 뿐, "이것이 권장 기본값"이라는 일반적 선언은 아니다.

> [!WARNING]
> **[미확인 확정] 이 인용은 데이터시트 원문에 없다.** "펌웨어 권장은 Event mode 기본, Streaming은 개발단계 임시용"이라는 표현은 프로젝트 자체 요약 문서의 해설(추정)이 마치 원문 대조 완료된 사실인 것처럼 오케스트레이터 공통 입력에 실려, 이후 C5(및 다른 페르소나들)에게 "이미 검증된 사실"로 전파된 것으로 보인다. 이는 이번 워크플로우 자체의 인용 사슬 문제이며, V5(할루시네이션 감사) 소관과 겹치므로 이쪽에도 동일 내용을 전달할 가치가 있다.
>
> **C5의 "공정성" 평가에 대한 함의**: 이 항목은 C5가 **자기 자신에게 불리하게** 인정한 항목이다(후보_5가 "정합성에서 어긋난다"고 스스로 적음). 따라서 이 인용이 근거 박약으로 밝혀졌다고 해서 C5의 주장이 "과장되었다"는 방향으로 작용하지 않는다 — 오히려 반대로, C5가 자기 불리한 사실을 성실히 반영하려다 상위 문서의 부정확한 전제를 그대로 물려받은 사례다. 참고로만 남긴다.

### 반증시도_7 — 회귀 표면(신규 write 사이트 5곳 대 1곳) 비교가 공정한가

C5는 "이벤트 모드 전환은 bit7이 5개 write 사이트(318·447·453·465·471)에 흩어져 있어 전부 동시 수정해야 하고... 후보_5는 신규 write 사이트가 1곳(0xC1)뿐"이라고 주장한다.

코드를 직접 대조한 결과 각 0xC0 write 사이트는 **레지스터 전체 16비트 값을 완전한 리터럴로 재작성**한다(`0x50,0x07`·`0x54,0x07`·`0x58,0x07`처럼 bit7을 공유 상수로 빼놓지 않고 사이트마다 하드코딩) — 즉 이벤트 모드로 가려면 이 5곳의 리터럴을 개별적으로 찾아 각각 bit7을 세워야 하고, 하나라도 놓치면 "조용한 Streaming 회귀"가 발생한다는 P3·S3의 우려(공통 입력에도 인용)가 코드 구조상 실제로 타당하다. 반면 후보_5는 기존 5곳을 전혀 건드리지 않고 신규 레지스터(0xC1) 1곳만 추가한다.

**반증 실패** — 이 비교는 "오늘 코드가 실제로 어떻게 짜여 있는가"라는 사실에 근거하고 있어 견고하다. 다만 이 비교가 암묵적으로 전제하는 것("5곳을 일일이 손으로 고친다"는 구현 방식)은 유일한 구현법이 아니다 — 예컨대 공유 상수/헬�I 함수로 리팩터링해 5곳을 1개 지점으로 좁히는 것도 이론상 가능하다. 그러나 **오늘 시점의 실제 코드** 기준으로는 C5의 "5곳 대 1곳" 서술이 정확하며, 리팩터링 여부는 어느 후보안이든 별도로 선택 가능한 구현 디테일이라 이 비교의 공정성 자체를 깨뜨리지 않는다.

**(a) 답변**: C4의 "2슬롯 제약"·"mclr() 핀 공유" 두 핵심 주장은 코드로 독립 재확인한 결과 **정확하다**. 다만 "2슬롯 제약"은 리포지토리 밖 벤더 SDK까지 추적한 결과 실리콘 차원의 진짜 병목이 아니라 현재 코드가 2개만 쓰고 있다는 사실일 뿐임이 드러났다(C4 자신도 이를 [미확인]으로 적절히 헤지했었다). 검증 과정에서 별도로, C4가 같은 절에서 편 WFI 리스크 근거("노말 루프에 WFI가 전혀 없다")는 코드와 직접 모순되어 **반증되었다** — C4의 최종 실현가능 판정 자체는 유지되지만, 그 판정을 뒷받침하는 위험 서술 하나는 정정이 필요하다.

**(b) 답변**: C5가 자체 완결적이라 자신하는 "히트율 프로필 유지"·"에라타 노출 변화 없음" 주장은 **C5 자신이 인용한 G2 모델을 C5 자신의 제안값에 적용하는 것만으로 반증된다** — 실제로는 강제개방 빈도가 상당히 늘어날 것으로 추정되며, 그 증가분의 상당수는 이벤트 모드까지 가지 않고 "Report Rate를 명시적으로 설정하는 행위" 자체에서 이미 발생한다. 이는 C5가 주장하는 "이벤트 모드 대비 상대적 우위"가 **정도의 차이일 뿐 종류의 차이가 아니게 만들어, 과장되어 있다고 판단한다.** 반면 회귀표면(5곳 대 1곳) 비교는 오늘 코드의 실제 구조에 근거해 견고하며 과장이 아니다. "데이터시트 권장" 인용 오류 1건은 발견했으나 C5에 불리한 방향이라 공정성 판단에 추가 손상을 주지 않는다.
