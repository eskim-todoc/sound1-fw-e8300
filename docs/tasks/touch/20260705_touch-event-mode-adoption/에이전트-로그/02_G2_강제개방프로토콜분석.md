# G2 · force_window_open 프로토콜 정밀분석 — 조기반환 히트율과 총 I2C 트래픽 변화

**TL;DR**: 현재 Streaming(0xC1 Report Rate 미기록·POR 0ms)에서 IC 자가 재개방 주기(추정 0.4~16ms)가 SW 폴링(100ms)보다 훨씬 빨라 force_window_open의 조기반환이 대부분(추정 84~99.6%) 히트한다. Events 전환 시 무이벤트 유휴구간엔 §8.11.2/8.12 원문대로 RDY가 완전히 침묵해 조기반환이 사실상 소멸, 매 폴링 4회 호출 전부가 0xFF 강제개방으로 바뀐다. read_debug 포함 총 I2C 트랜잭션 수는 유휴구간 기준 어떤 가정을 대입해도 항상 증가하며(약 1.3~2.0배, 실측 불필요한 강건한 결론), 0xFF만 보면 6배~250배까지 벌어질 수 있다. "RDY 자가토글 감소 = 이득"이라는 전제는 IC 측 관점에서만 참이고, SW가 유발하는 통신량 관점에서는 반대 방향임을 확인했다.

## 1. 대상 코드 정밀분석 (라인 정확 확인)

파일: `src/2__cm3/Cortex-M3-src/systemControl/tdc_touch_iqs323.c`

| 함수 | 정확한 라인 범위 | 핵심 동작 |
|---|---|---|
| `wait_window_closed(int max_ms)` | 128~143행 | RDY 핀이 `WIN_CLOSED`(=1) 될 때까지 busy-wait, `max_ms` 초과 시 false(소프트 타임아웃) |
| `force_window_open(void)` | 145~175행 | **149~152행**: RDY==`WIN_OPEN`(=0)이면 **즉시 true 반환(조기반환)**. 아니면 154~159행에서 `0xFF` 1바이트 write(강제통신) 후 161~174행에서 최대 `TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS`(=45ms, `tdc_touch_iqs323.h:32`)까지 RDY OPEN 폴링 |
| `write_register(addr, lsb, msb)` | 180~197행 | `force_window_open()` 1회 → 3바이트 write → `wait_window_closed(20ms)`(`MAX_WAIT_CLOSE_MS`, `iqs323.h:33`) |
| `read_register(addr, *lsb, *msb)` | 199~230행 | `force_window_open()` 1회(주소 write용) → 1바이트 write → `wait_window_closed` → `force_window_open()` 1회(데이터 read용) → 2바이트 read → `wait_window_closed` — **총 force_window_open 2회/호출** |

`force_window_open()`의 `#if 1` 블록(154~159행)은 컴파일 시 항상 활성 — 조기반환에 실패하면 **반드시** 0xFF write가 실행된다. 이 구조 자체는 프로토콜의 핵심 전제이며, 본 분석 전체가 이 위에 서 있다.

> [!NOTE]
> RDY 핀 매크로: `TDC_TOUCH_IQS323_WIN_OPEN=0`, `WIN_CLOSED=1`(`iqs323.h:30~31`), 핀은 `DIO16`(`iqs323.h:29`) — active-low open-drain(§8.6 원문 확인)과 정합.

### 1.1 read_debug()의 동일 구조 (main.c 지시사항 반영)

`tdc_touch_iqs323_read_debug()`(iqs323.c **369~398행**)는 `read_register()`와 동일한 2단계(주소write창+데이터read창) 패턴이나 static 헬퍼를 재사용하지 않고 자체 구현한다: **380행**·**387행**에서 각각 `force_window_open()`을 호출(총 2회), 0x13(CH0 Counts)+0x14(CH0 LTA) 4바이트 연속 read.

### 1.2 폴링 사이클당 호출 구성 — 3개 경로 전부 동일 확인

| 호출 경로 | 파일:라인 | 주기 | read_status | read_debug (게이트) |
|---|---|---|---|---|
| 깨어있음(FSM) | `tdc_touch.c` 273~349행 | `TDC_TOUCH_POLL_INTERVAL_MS`=100ms(`tdc_touch_time.h:18`), 게이트 296행 | 305행 | 311~338행, `TDC_TOUCH_DEBUG_PRINT_ENABLE`(기본 1, `tdc_touch_config.h:22`) 게이트, `in.read_ok`일 때만(313행) |

## 2. Streaming 모드에서 조기반환 히트율 추정

### 2.1 Report Rate(0xC1) 현황 — 코드·데이터시트 직접 확인

`tdc_touch_iqs323.c`의 레지스터 주소 정의(17~34행)에 `0xC1`이 **존재하지 않으며**, 파일 전체에 `write_register(... 0xC1 ...)` 또는 `0xC1` 리터럴이 **0건**이다(직접 grep 재확인, ATI Base 0x37·Mult 0x38·Comp 0x39도 동일하게 0건 — 이 세 레지스터 모두 POR 기본값 그대로 유지).

데이터시트 §9 메모리맵(PDF 원문, `/tmp/iqs323_full.txt:2150`):
```
0xC1   Normal Power Mode Report Rate   0x0000   16-bit value (ms), Range: 0 - 3000
```
→ **0xC1 = POR 기본값 0x0000(=0ms), 코드 미기록 확정.**

### 2.2 §8.11.1 원문과 "0"의 의미 — [미확인] 명시

PDF 원문(`/tmp/iqs323_full.txt:1836~1839`, 직접 추출):
> "In I2 C streaming mode data is constantly reported at the relevant power mode report rate specified in milliseconds by the Normal Power Report Rate, Low Power Report Rate and Ultra Low Power Report Rate registers."

이 문장과 §5(전력모드)·부록 A 전체를 검색했으나 **"Report Rate = 0일 때의 동작"을 명문으로 정의하는 문장은 찾지 못했다**(선행 문서 `05_S3_...md`§4, `RDY 윈도우 타이밍 분석/2_검증_핵심수치.md` 미해결_1과 동일 결론 — 본 노드도 독립적으로 재확인, 그레인지 못함을 재확인). 유일하게 확보 가능한 텍스트 근거는:

- 메모리맵 표가 0xC1의 유효 범위를 **"Range: 0 - 3000"**으로 명시 — 0은 배제된 값이 아니라 정의역 안의 값.
- Azoteq 공식 예제코드(`docs/참고/touch/iqs323-example-code/src/IQS323/IQS323_3PROJ_BUTTONS_EV_KIT.h:168~169`)는 `NP_REPORT_RATE_0=0x10`(=16decimal)을 **항상 명시적으로 write**한다 — 0을 그대로 두는 참조 설계 사례는 찾지 못함(정황증거일 뿐, "0의 의미"에 대한 직접 증거는 아님).

**[미확인]**: "0"이 "지연 없이 최대속도로 연속 보고"를 뜻하는지, 다른 의미(예약값 등)인지는 데이터시트 원문이 명문화하지 않는다. 이하 분석은 "0=측정 완료 즉시 보고(지연 없음)"라는 선행 작업과 동일한 가장 합리적인 해석을 **가설로 채택**하되, 가설임을 계속 명시한다.

### 2.3 IC 자가토글 주기(T_주기) 추정 — 참고치 재검토 + 자체 물리적 유도

**선행 문서의 "16ms 참고 상한"에 대한 재평가(본 노드 추가 발견)**: `RDY 윈도우 타이밍 분석/3_종합결론.md` 등이 "§3.4 self-cap 3ch NP=16ms"를 T_주기의 느슨한 상한 참고치로 사용해왔다. 그러나 PDF 원문(`/tmp/iqs323_full.txt:655~666`)을 다시 보면 이 표는 **"Current Consumption" 측정 조건표**이며, "Report rate [ms]" 열은 그 전류 측정을 위해 **의도적으로 설정한 값**이지 "0일 때 최대속도"의 실측치가 아니다(측정 조건: ATI Target=512·Fxfer=500kHz·**3채널**·Event mode — Sound1과 조건이 전혀 다름). 즉 이 16ms는 T_주기의 상한 근거로서 **타당성이 선행 문서가 취급한 것보다도 약하다** — 사실상 무관한 값이다. 이는 본 노드가 원문을 재대조해 얻은 정정 사항이다.

**자체 물리적 유도(제 자신의 추정, 데이터시트 미보증 — 신뢰도 중간)**:
- §5.4 원문 설명: Counts = "Cs가 임계값 도달까지 필요한 charge-transfer 반복 횟수".
- Sound1 확정값: `REG_CONV_FREQ`(0x31) write = `0x7F,0x05` → `0x057F` → 부록 A.6 Table A.1에서 Period=5 → **f_xfer = 1.00 MHz**(코드 316행, 데이터시트 직접 대조 완료).
- Sound1 ATI Target: `REG_SENSOR0_ATI_SETUP`(0x36) write = `0x0C,0x04` → `0x040C`(코드 437행, POR 기본값과 동일값을 명시 재기록) → 부록 A.12로 ATI Resolution Factor=64, Mode=Full → **ATI Target = ATI Base(0x37, 미기록, POR 0x0064=100) × (64/16) = 400 counts**.
- CH1·CH2는 `sensor_setup()`(266~282행)에서 명시 disable — 단일채널만 변환한다고 가정.
- **가정**: 1 count ≈ 1회 charge-transfer 사이클 ≈ 1/f_xfer 시간 (§5.4의 서술을 직접적인 시간 공식으로 확장한 것 — 데이터시트가 명문화한 공식이 아니라 본 노드의 논리적 확장이다. 필터·비교·ATI 밴드 판정 등 부가 연산 시간은 미포함).
- **유도 결과**: T_주기 ≈ 400 counts × (1/1,000,000) s/count ≈ **400µs ≈ 0.4ms**.

이 두 값(원문의 16ms는 무관한 참고치, 자체유도 0.4ms는 근거는 있으나 미보증 추정치)의 간극이 크므로, 아래 §2.4는 **민감도 표**로 처리한다.

### 2.4 조기반환 히트율 — 민감도 표

전제: SW 폴링 주기 P=100ms, 폴링 사이는 "이전 서비스 종료 후 T_주기 지나 자연 재개방 → 다음 폴링이 올 때까지 열린 채 유지"라는 모델(선행 문서 `RDY 윈도우 타이밍 분석/1_분석_스트리밍동작.md` §4.2가 "원문 미명시 — 논리적 추론"으로 이미 제시한 것과 동일 모델, 본 노드도 이를 채택하되 계속 추론임을 명시). I2C Transaction Timeout(0xD1, POR 0x00C8=200ms, 코드 미기록 — 직접 grep 재확인)이 100ms 폴링 간격보다 커서(200ms>100ms) 자연개방된 창이 다음 폴링 전에 스스로 닫히는 일은 없다고 가정한다.

히트율(단순 모델) ≈ (P − T_주기) / P :

| 가정 | 근거 | 조기반환 히트율 | Streaming 예상 0xFF/사이클(4×(1−히트율)) |
|---|---|---|---|
| T_주기=0.4ms | 본 노드 자체유도(§2.3, 단일채널 1MHz 400counts) | 99.6% | 0.016 |
| T_주기=1ms | 자체유도 + 부가연산 여유 | 99% | 0.04 |
| T_주기=5ms | 임의 중간값(여유 대폭 반영) | 95% | 0.2 |
| T_주기=16ms | 데이터시트 §3.4 참고치(§2.3에서 **무관한 값으로 판명** — 비교용으로만 유지) | 84% | 0.64 |
| T_주기=50ms | 극단적 보수 가정(지지 근거 없음, 방향성 검증용) | 50% | 2.0 |

> [!IMPORTANT]
> 어느 가정을 쓰든 히트율은 **50% 이상**이다 — 즉 Streaming에서 조기반환은 최소한 "가끔"이 아니라 "우세하게" 일어난다는 결론은 T_주기 불확실성 범위 전체에서 강건하다. 정확한 값은 실측(RTT 타임스탬프 또는 오실로스코프로 RDY 핀 직접 관측)이 필요하며, 이는 선행 문서의 미해결_1과 동일한 게이트다.

## 3. Events 모드 전환 시 — 조기반환 소멸 논증

### 3.1 원문 근거 (직접 재확인)

§8.11.2(`/tmp/iqs323_full.txt:1849~1852`):
> "In event mode the RDY line will only go low when one or more of the enabled events are triggered or if the device resets."

§8.12(`/tmp/iqs323_full.txt:1858~1862`):
> "Enabled events are reported in the System Status register when triggered... The global event flags are cleared when the master reads them via I2C. When they are set, the IQS323 will continuously provide ready windows."

Table 8.1 Touch 행: "Any channel has **entered or exited** a touch state" — 진입/이탈 **전이(edge)** 에만 이벤트가 발생하고, 유지 상태(steady touch)에는 재발생하지 않는다. 현재 `0xD3`(Events Enable) = `0x52`(ati_error·ati_event·touch_event, 코드 300~304행 `events_enable()` 확인 완료).

**결론**: 이벤트가 활성화되어 있지 않은 구간(터치 없음 + ATI 정상 + ATI 진행중 아님)에서는 §8.11.2/8.12 원문에 따라 **RDY가 전혀 스스로 움직이지 않는다** — Streaming에서와 달리 "자연 재개방을 기다리면 언젠가 열린다"는 메커니즘 자체가 없다.

### 3.2 유휴구간 vs 터치유지구간 — 둘 다 "조기반환 거의 0%"로 수렴

- **완전 유휴(터치 없음, ATI 정상)**: 이벤트 자체가 없으므로 RDY는 계속 HIGH(닫힘) — 조기반환 히트율 ≈ **0%**.
- **터치 유지 중(눌린 채 정지)**: 최초 진입 전이(1회)만 이벤트로 잡히고, 그 전이가 다음 폴링에서 `read_status`로 읽혀 flag가 clear되면(§8.12) 이후 유지 구간은 새 전이가 없어 다시 이벤트 없음 상태로 수렴 — 첫 1~2 사이클을 제외하면 완전 유휴와 동일하게 조기반환 ≈ 0%.
- **롱터치 2400ms 구간**(`TDC_TOUCH_LONG_TOUCH_MS`, `tdc_touch_time.h:19`) 기준으로 보면 100ms 폴링 24회 중 "전이가 있어 조기반환이 우연히 성립할 수 있는" 사이클은 최대 1~2회뿐 — 나머지 22~23회는 완전 유휴와 동일하다.

**시간 평균 조기반환 히트율(Events, 이벤트 무발생 유휴 지배 구간) ≈ 0%에 매우 근접**한다고 결론 내린다. 이 결론은 원문 §8.11.2/§8.12 문장에 직접 근거하며, §2의 Streaming 추정치보다 **불확실성이 훨씬 낮다**(Streaming 쪽은 T_주기라는 미실측 변수에 의존하지만, Events 쪽은 "이벤트가 없으면 RDY는 안 움직인다"는 원문이 이미 확정적이기 때문).

## 4. 총 0xFF 강제개방·총 I2C 트랜잭션 수 비교

### 4.1 사이클당 트랜잭션 구성 (모드 무관 불변부 + 모드 의존 가변부)

`read_status()`+`read_debug()`가 발생시키는 **"실제" I2C 버스 동작**(레지스터 주소선택 write 1회 + 데이터 read 1회, ×2쌍)은 **4회로 고정**이며 Streaming/Events 어느 쪽이든 변하지 않는다 — Interface Selection(bit7)은 RDY 트리거 조건만 바꿀 뿐 폴링 로직(`tdc_touch.c` 296행 게이트, `read_status`+`read_debug` 호출)은 전혀 건드리지 않기 때문이다. 변하는 것은 그 4회의 `force_window_open()` 호출이 조기반환(0xFF 생략)으로 끝나는지, 강제개방(0xFF 1회 write)으로 끝나는지뿐이다.

### 4.2 Streaming vs Events 비교표 (100ms 폴링 사이클 1회 기준, TDC_TOUCH_DEBUG_PRINT_ENABLE=1 기본값)

| 구분 | 실제 I2C 오퍼레이션(고정) | 보조 0xFF 강제개방(가변) | 총 트랜잭션 |
|---|---|---|---|
| Streaming, T_주기=0.4ms(자체유도) | 4 | 0.016 | 4.016 |
| Streaming, T_주기=1ms | 4 | 0.04 | 4.04 |
| Streaming, T_주기=5ms | 4 | 0.2 | 4.2 |
| Streaming, T_주기=16ms(무관참고치) | 4 | 0.64 | 4.64 |
| Streaming, T_주기=50ms(극단보수) | 4 | 2.0 | 6.0 |
| **Events, 유휴(이벤트 무발생)** | 4 | **≈4** | **≈8** |

**증가율**:

| 지표 | 최소 증가(T_주기=50ms 극단가정) | 중심 추정(T_주기=1~5ms) | 최대 증가(T_주기=0.4ms) |
|---|---|---|---|
| 0xFF 강제개방 횟수 | 2.0배 | 20~100배 | 250배 |
| 총 I2C 트랜잭션 수 | 1.33배 | 1.9~1.98배 | 1.99배 |

> [!IMPORTANT]
> **방향성은 T_주기 값과 무관하게 강건하다.** §2.4에서 검토한 가정 범위(0.4ms~50ms) 전 구간에서 Events 전환은 총 I2C 트랜잭션 수를 **늘리면 늘렸지 줄이는 경우는 단 하나도 없다**. "총 트랜잭션 수" 지표는 특히 강건해서 어떤 가정에서도 대략 **1.3~2.0배(중심값은 거의 정확히 2배)** 로 수렴한다 — 이는 실측 없이도 신뢰할 수 있는 결론이다. 반면 "0xFF 단독" 지표는 T_주기에 극도로 민감(2배~250배)해 정확한 배수는 실측 게이트로 남는다.

### 4.3 부가 리스크(참고, G1 소관) — Force Comm t_wait 마진

§8.13 원문(`/tmp/iqs323_full.txt:1898~1899`, 직접 확인): "The typical values of twait are 0.1ms ≤ twait ≤ 45ms" (각주: "Contact Azoteq for an application specific value of twait"). 현재 코드의 `TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS=45`(`iqs323.h:32`)는 이 상한과 **정확히 일치** — 마진이 0에 가깝다. Events 전환으로 0xFF 강제개방 빈도가 늘어나면 이 근접-경계 타임아웃에 노출되는 횟수도 비례해 늘어난다(V3가 이미 지적한 것과 동일 방향, 본 노드는 "노출 횟수가 몇 배 느는지"의 정량 근거를 §4.2로 제공). I²C Lock-Up 에라타(부록C, G1 담당)와의 연결고리이므로 언급만 하고 상세 판정은 G1에 위임한다.

## 5. 은수님 전제에 대한 정직한 평가

> "이벤트 모드로 RDY가 매번 토글되지 않아 이득이다."

이 전제를 두 갈래로 분해하면 결과가 **정반대**로 갈린다.

**참인 부분 — IC 자체가 스스로 일으키는 RDY 어서션 빈도**: §8.11.2/8.12 원문이 확정하듯, 이벤트 무발생 구간에서 Events 모드는 RDY를 전혀 움직이지 않는다(§3.1~3.2). Streaming은 (T_주기가 얼마든) 지속적으로 자가토글한다. 이 좁은 의미에서는 전제가 **명백히 참**이다.

**전제가 놓친 부분 — 그 결과로 늘어나는 SW측 트래픽**: 현재 `force_window_open()`의 "이미 열려있으면 생략" 구조(149~152행) 때문에, Streaming의 잦은 IC측 자가토글은 오히려 SW가 0xFF를 거의 안 써도 되게 만드는 **부수적 이득**으로 작동해왔다(§2). Events로 전환하면 이 부수적 이득이 사라지고, 유휴구간마다 매 폴링 4회 호출 전부가 0xFF 강제개방 경로를 타게 된다(§3). 순계산 결과 총 I2C 트랜잭션 수는 **거의 항상 증가**한다(§4.2) — "RDY가 안 움직여서 이득"이 아니라 "RDY가 안 움직이는 대신 마스터가 그만큼 더 자주 SDA를 흔들어 깨워야 하는" 구조다.

**추가로 짚어야 할 지점(본 노드 자체 발견)**: Interface Selection(bit7)은 §8.11 원문상 "I²C interface type" 선택 비트이며, Power Mode(bits[6:4], 별개 필드)와 달리 CH0의 실제 charge-transfer 변환 활동(§5.4의 물리적 스위칭) 자체를 제어한다는 근거는 어디에도 없다 — 이벤트 감지 자체가 내부적으로는 계속 변환·비교를 수행해야 성립하는 기능이기 때문이다. 즉 "하이젠베르크" 자기간섭 가설의 물리적 원인이 CTx0 자체 스위칭이라면 Events 전환은 그 원인에 **영향을 주지 못할 가능성이 높다**(RDY 핀·I2C 버스라는 별개 배선의 활동만 바꾼다). 원인이 RDY(DIO16) 핀 자체의 토글이라면 Events가 유리하고, 원인이 I2C 버스(SDA/SCL) 스위칭이라면 §4의 계산대로 Events가 오히려 불리하다 — **어느 물리 메커니즘을 겨냥하는지에 따라 답이 달라진다**는 것이 본 노드가 제공할 수 있는 가장 정직한 결론이다.

> [!NOTE]
> 이 결론은 **`force_window_open()`의 현재 프로토콜(조기반환+강제경로 이분법)을 그대로 유지한다는 전제** 위에서만 성립한다. 프로토콜 자체를 재설계(예: RDY 인터럽트 전환, 조기반환 로직 변경)하면 결론이 달라질 수 있으며, 이는 후보_4(C4)·검증_6(V6)의 스코프다.
