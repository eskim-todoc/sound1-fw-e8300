# 검증_10 · 할루시네이션 감사 — 16~20번 문서 전수 대조

**TL;DR**: 16~20번 문서(그라운드_7~9·후보_6·7)의 코드·데이터시트 인용 84건을 직접 대조와 pdftotext 재추출로 전수 검증했다. 최우선 대상인 후보_7의 "main.c:452·738이 동일 while(1) 루프" 정정 주장을 독립 브레이스 추적으로 확정 참으로 확인했으며, 이는 07_C4·후보_6이 반복한 "WFI 없음" 주장이 실제 오류였음을 뜻한다. 그 외 인용은 전부 원문과 일치했고 사소한 라인 오프셋 1건 외 할루시네이션은 없었다.

- 배경 문서(`15_보충입력_결합시나리오.md`)와 대상 문서 5개(`16_G7_...`·`17_G8_...`·`18_G9_...`·`19_C6_...`·`20_C7_...`)를 전부 직접 `Read`했다. 대조를 위해 선행 라운드 문서(`07_C4_프로토콜재설계.md`)도 추가로 `Read`했다(후보_7이 이 문서의 주장을 정정한다고 명시했기 때문).

## 1. 최우선 검증 — main.c while(1) 루프 구조 독립 재추적

### 1.1 쟁점

- **07_C4(`07_C4_프로토콜재설계.md`) §1.4 원 주장**: "노말 모드(`tdc_touch_process`, `main.c:452`)가 속한 메인 루프는 WFI 호출이 전혀 없다(그 루프 부근 738·801·891·1230행 WFI는 전부 다른 루프 소속임을 grep으로 확인)."
- **후보_6(`19_C6_...md`) §2.3**: 07_C4의 위 주장을 그대로 인용하면서, 자체적으로 "main.c:437~460행 직접 재확인해 grep으로 해당 구간에 `SYS_WAIT_FOR_INTERRUPT` 0건임을 확인"했다고 추가 — 결론적으로 "노말 모드에서는 CPU를 재우지 않는다"고 서술.
- **후보_7(`20_C7_...md`) §5의 정정 주장**: "main.c:452(`tdc_touch_process()` 호출)와 main.c:738(`SYS_WAIT_FOR_INTERRUPT`)은 동일한 `while(1)` 루프 본문(437~739행, 닫는 중괄호 739행) 안에 있다"며 07_C4의 주장이 "현재 코드와 불일치한다"고 반박.

세 문서가 서로 정면으로 모순되므로, 오케스트레이터가 지정한 대로 main.c를 직접 열어 437행부터 739행까지 중괄호 깊이를 독립적으로 재추적했다.

### 1.2 검증 방법

`main.c`를 `Read`로 전체 통독한 뒤, 별도 Python 스크립트로 `//` 라인 주석·`/* */` 블록 주석·문자열 리터럴·문자 리터럴을 공백으로 치환(단 개행은 보존)한 "정제 텍스트"를 만들고, 1행부터 437행 직전까지 순차적으로 중괄호 개수 차(`{` 수 − `}` 수)를 누적해 437행 진입 직전의 깊이를 구한 뒤, 437행부터 742행까지 한 줄씩 깊이 변화를 추적했다. 전처리기 지시문(`#if`/`#ifdef`/`#else`/`#endif`)은 그 자체에 중괄호가 없어 이 추적에 영향을 주지 않음을 별도로 확인했다(§1.4).

### 1.3 결과

```
line  437: depth_before=1 -> depth_after=1   while (1)
line  438: depth_before=1 -> depth_after=2   {                                  ← while(1) 본문 시작
line  439: depth_before=2 -> depth_after=2   if ((iterationFlag == true))
line  440: depth_before=2 -> depth_after=3   {                                  ← if 본문 시작
line  452: depth_before=3 -> depth_after=3   powerButtonPushed = tdc_touch_process();   ← 여기
...
line  669: depth_before=3 -> depth_after=2   }  // 끝, iteration            ← if 본문 종료
...
line  737: depth_before=2 -> depth_after=2   SYS_WATCHDOG_REFRESH();
line  738: depth_before=2 -> depth_after=2   SYS_WAIT_FOR_INTERRUPT;             ← 여기
line  739: depth_before=2 -> depth_after=1   }  // 끝, while                  ← while(1) 본문 종료
line  740: depth_before=1 -> depth_after=1
line  741: depth_before=1 -> depth_after=1   return 0;
line  742: depth_before=1 -> depth_after=0   }                                  ← func_normal() 종료
```

- 437행 진입 직전 깊이는 1(`func_normal()` 함수 본문 안, 다른 중첩 블록 밖) — 373~436행의 `Initialize()`·CFX 초기화·ISD 정보 출력 블록(387행 여는 중괄호 → 435행 닫는 중괄호)이 이미 자체적으로 닫혀 있어 정확히 1로 복귀함을 확인했다.
- 438행의 `{`가 `while(1)` 루프 본문을 열고, 452행(`tdc_touch_process()` 호출)은 깊이 3(440행에서 연 `if` 블록 내부, 즉 while 본문 한 단계 아래)에 위치한다.
- 669행의 `}`가 그 `if` 블록을 닫아 깊이 2로 복귀하고, 671행부터 736행까지(main_counter 증가·LED/절전 판정 등)는 while 본문에 직접 속한다(깊이 2 유지).
- **737~738행(`SYS_WATCHDOG_REFRESH()`, `SYS_WAIT_FOR_INTERRUPT`)은 깊이 2 — 452행과 같은 `while(1)` 본문(단, if 블록 밖) 안에 있다.**
- **739행의 `}`가 정확히 이 `while(1)`(438행에서 연 것)을 닫아 깊이 1로 복귀한다.**

### 1.4 전처리기 분기에 대한 안전성 확인

437~742행 구간에는 `#if 1`(456행, 사실상 상시 참)·`#ifdef ENABLE_UI_CMD`(548·575·581·586·622·633행)가 존재하나, 직접 대조한 결과 `ENABLE_UI_CMD` 분기 내부의 조건부 코드는 전부 중괄호가 없는 단문(예: `bool ovr_batt_active = ...;`)이거나, 중괄호가 있는 블록(590·636행)은 `#ifdef`가 이미 `#endif`로 닫힌 **뒤**(즉 매크로 상태와 무관하게 항상 컴파일되는 지점)에 위치함을 확인했다. `#if 1`(456~485행) 블록도 상시 참이라 무조건 포함된다. 따라서 `ENABLE_UI_CMD` 정의 여부와 무관하게 위 깊이 추적 결과는 변하지 않는다.

### 1.5 판정

> [!IMPORTANT]
> **후보_7(20번 문서) §5의 주장은 확정 참이다** — 독립 재현으로 확인했다. `main.c:452`(`tdc_touch_process()` 호출)와 `main.c:738`(`SYS_WAIT_FOR_INTERRUPT`)은 정확히 동일한 `while(1)` 루프(437~739행, 닫는 중괄호 739행) 안에 있다.
>
> **07_C4(07번 문서) §1.4의 원 주장은 확정 오류다** — "노말 모드가 속한 메인 루프는 WFI 호출이 전혀 없다"는 서술은 main.c와 불일치한다. 노말 모드 루프는 매 iteration 끝에 이미 `SYS_WAIT_FOR_INTERRUPT`를 호출한다.
>
> **후보_6(19번 문서) §2.3은 이 오류를 그대로 계승했다** — 후보_6이 직접 재확인한 "437~460행에 WFI 0건"이라는 **좁은 범위의 사실 자체는 참**이다(`grep -n "SYS_WAIT_FOR_INTERRUPT" main.c` 결과 실제로 738·801·891·1230행 4곳뿐이며 437~460 사이엔 없음). 그러나 이 좁은 사실을 07_C4의 (틀린) "메인 루프 전체에 WFI 없음"이라는 넓은 프레이밍에 그대로 결합해, "노말 모드에서는 CPU를 재우지 않는다"는 **틀린 결론**에 도달했다. 즉 후보_6은 조회 자체를 조작(fabrication)하지 않았지만, 조회 범위가 실제 루프 경계(437~739행)보다 훨씬 좁아(437~460행) 루프 뒷부분(737~738행)의 WFI를 놓쳤다.

나머지 세 WFI 라인(801·891·1230행)에 대한 07_C4의 주장은 grep으로 재확인한 결과 **정확하다**: 801행은 `func_cradle_lid_closed_loop()`(748행부터 시작하는 별개 함수) 내부, 891행은 `fake_func_sleep()`(810행부터) 내부, 1230행은 `func_sleep()`(1164행부터) 내부로 각각 `func_normal()`의 while(1)(437~739행)과는 다른 함수·다른 루프에 속한다. **07_C4의 오류는 4개 WFI 지점 중 738행 단 하나에 대한 소속 판정에 국한된다.**

### 1.6 그라운드_9(18번)와의 교차 확인

이번 라운드의 그라운드_9(`18_G9_FSM폴링구조확인.md`) §4.1도 독립적으로 "`main.c`의 `func_normal()` 안 **437~739행** `while(1)` 루프는 `iterationFlag`(439행)가 true일 때만 몸체를 실행한다"고 서술한다 — 이는 후보_7의 브레이스 추적과 **동일한 루프 경계(437~739)**를 별도 경로(코드 통독)로 확인한 것이며, 본 노드의 독립 재추적과도 정확히 일치한다. 세 개의 독립적 접근(후보_7의 브레이스 매칭, 그라운드_9의 코드 통독, 본 노드의 프로그램적 재추적)이 모두 동일한 결론에 도달했다.

## 4. 후보_6·7 자체 그라운딩 vs 실제 그라운드_7~9 교차검증

과제 배경대로, 후보_6·7은 작업 착수 시점에 16~18번(그라운드_7~9) 파일이 존재하지 않아 스스로 독자 그라운딩을 수행했다고 명시했다(각 §0/§0 참조). 이제 실제 16~18번이 존재하므로 아래와 같이 대조했다.

### 4.1 후보_6 §3("그라운드_7 관점") vs 실제 그라운드_7(16번)

- 후보_6의 결론: "노말 모드 롱터치(`tdc_touch_logic.c`)는 타임스탬프 기반이라 자동으로 안전. 절전모드 카운터(`main.c` `func_sleep`)는 횟수 기반이라... 설계 규율에 전적으로 의존."
- 실제 그라운드_7의 결론: 11개 메커니즘을 그룹_1(타이머 기반, 5종)·그룹_2(카운트 기반, 6종)로 분류 — 동일한 근본 이분법.
- **판정: 합치.** 후보_6의 자체 그라운딩은 그라운드_7이 이후 더 정밀하게(11항목 전수) 확인한 것과 같은 결론에 먼저 도달했다 — 범위는 더 좁지만(롱터치·ATI에러 카운터 2종에 집중, read실패hold·부팅해제디바운스·RESEED 3트리거·데드코드 등은 미언급) 방향이 틀리지 않았다.
- 다만 그라운드_7 §10의 리스크 항목("§8.12 재제공 상태에서 ULP 웨이크업이 100ms보다 잦아질 수 있는지 [미확인]")은 후보_6의 핵심 안전 전제("웨이크 이벤트 시점부터... 반드시 실제 100ms 카덴스로 진행")를 잠재적으로 흔들 수 있는 지점이다. 다만 후보_6 §2.6의 `rdy_irq_disarm()`(ACTIVE 전이 시 인터럽트 자체를 disarm)을 다시 대조하면, ACTIVE 구간에서는 DIO16 인터럽트가 꺼져 있어 100ms HW 타이머만 웨이크 소스로 남으므로 이 리스크는 후보_6 자신의 설계 안에서 이미 구조적으로 해소된다 — **모순이 아니라, 그라운드_7이 일반적으로 남긴 리스크를 후보_6의 구체적 설계가 우연히 회피하고 있는 관계**로 판단한다.

### 4.2 후보_6 §3.3("그라운드_8 관점") vs 실제 그라운드_8(17번)

- 후보_6은 "재시도 루프에서 `re_ati()` 호출마다 IC 내부에서 새 ATI 프로세스가 완료되고, 그 완료 시점마다 ati_error 비트가 재평가된다"는 것을 §5.11 원문으로 뒷받침했다(재시도=NOT_TOUCH 상태의 idle/재시도 국면).
- 실제 그라운드_8 §3.2는 "터치 유지 중"(TOUCH 상태, LTA 동결)에는 ATI Error 트리거 조건 자체가 억제된다고 결론짓는다.
- **판정: 모순 아님, 서로 다른 상태를 다룸.** 후보_6은 NOT_TOUCH 상태에서의 재시도 루프를, 그라운드_8은 TOUCH 상태 유지 구간을 다뤄 서로 겹치지 않는 보완적 결론이다.

### 4.3 후보_7 §2.5 vs 실제 그라운드_7(16번)

- 후보_7은 `func_sleep()`의 카운터 4종(`notouch_cnt`·`ignore_elapsed`·`touch_cnt`·`ati_error_reboot_cnt`)이 전부 "폴링횟수 카운트"(ms 미참조)라고 자체 확인했다.
- 실제 그라운드_7의 항목_8·10·11이 정확히 이 4개 카운터(ATI에러재부팅·노터치확정RESEED·강제RESEED)를 그룹_2(카운트 기반)로 동일하게 분류한다.
- **판정: 완전 합치.** 후보_7의 자체 확인은 그라운드_7의 전수조사와 세부(매크로명·판정)까지 정확히 일치한다.

### 4.4 후보_7 §2.7의 `[미확인]` vs 실제 그라운드_9(18번)의 발견

- 후보_7: "본 노드가 `tdc_get_fake_op_mode` 호출부를 재확인한 결과 `main.c` 밖 참조 0건 — 다른 노드에서도 이 변수를 세팅하는 곳을 찾지 못했다. 정확한 활성화 트리거는 **[미확인]**."
- 실제 그라운드_9 §2.3: "이 플래그는 BLE 원격 디버그 커맨드(`tdc_remote_general_debug.c:169`)로만 set된다"— 본 노드가 직접 grep으로 재확인한 결과도 **동일하게 169행에서 `tdc_set_fake_op_mode(1)` 확인**.
- **판정: 후보_7의 할루시네이션은 아니다**(거짓 주장을 하지 않고 정직하게 "못 찾았다"고 기술) — 그러나 실제로는 존재하는 정보(같은 라운드의 그라운드_9가 찾아낸 세터)를 후보_7이 놓쳤다는 점에서, "병렬 실행으로 인한 정보 격차"의 구체적 사례다. 이는 오케스트레이터가 요청한 교차검증의 핵심 발견 중 하나로 남긴다.

### 4.5 후보_7 §5(WFI 정정) vs 실제 그라운드_9(18번)

- §1.6에서 이미 다뤘듯, 그라운드_9가 독립적으로 확인한 루프 경계(437~739행)가 후보_7의 브레이스 매칭 결과와 정확히 일치한다 — 상호 보강되는 관계다.

## 6. 종합 판정

1. **최우선 검증 대상은 확정 참으로 판정한다.** 후보_7(20번 문서) §5의 "main.c:452와 738이 동일 while(1) 루프(437~739행) 안에 있다"는 주장은 본 노드의 독립적·프로그램적 브레이스 깊이 추적(주석·문자열 제거 후 문자 단위 스캔)으로 확정 확인됐다. 이는 선행 07_C4(07번 문서) §1.4가 주장한 "노말 모드가 속한 메인 루프는 WFI 호출이 전혀 없다"가 **실제로는 오류**였음을 뜻하며, 후보_6(19번 문서) §2.3이 이 오류를 좁은 범위의 재확인(437~460행)으로 인해 그대로 계승했음도 확인했다.
2. **코드 인용 67건·데이터시트 인용 17건, 총 84건을 전수 대조한 결과 §1의 구조적 오류(1건, 07_C4→후보_6 전파, 후보_7이 자체 발견·정정)를 제외하면 할루시네이션은 발견되지 않았다.** 매크로 값(2400·2000·30000·5000·2500·300·10000·24·20·3·100 등), 코드 라인 번호, 함수 시그니처, 코드 스니펫 전문, 데이터시트 절 번호·표·비트맵·직접 인용문이 전부 원문과 정확히 일치했다.
3. **후보_6·7의 자체 그라운딩은 실제 그라운드_7~9와 대체로 합치한다.** 두 건의 구체적 지점(§4.1 그라운드_7 §10 리스크, §4.4 fake_op_mode 세터)에서 정보 격차가 있었으나, 둘 다 거짓 주장이 아니라 "찾지 못해 정직하게 미확인 처리" 또는 "그라운드_7이 일반적으로 남긴 리스크를 후보_6의 구체 설계가 이미 회피"하는 관계로, 병렬 실행 구조의 자연스러운 한계이지 할루시네이션은 아니다.
4. **실무적 함의**: 후보_6의 §2.3(노말모드 WFI 없음 근거로 한 CPU 논증)은 사실관계 정정이 필요하다 — 노말 모드 루프도 이미 매 iteration 끝에 WFI를 호출하고 있으므로, 후보_6의 IDLE 분기 삽입이 "이 루프에 처음 WFI를 들여오는 변경"이 아니라는 점은 오히려 **후보_6의 결론(안전하다)을 강화**하는 방향이다 — 다만 근거 문장 자체(§2.3의 "CPU를 재우지 않는다")는 수정이 필요하다. 이는 후보_7 §5도 동일하게 지적한 바("이 정정은 후보_6·후보_7 본안 모두에게 유리한 방향")와 일치한다.
