# 후보_1 — 순수 Events 전환 재검토

**TL;DR**: 후보_1(순수 Events 전환) 재검토 결과, P3 스펙의 코드 라인·값은 현재 코드와 100% 일치해 수정이 불필요하다. 다만 I2C Lock-Up 에라타는 강제개방 사용 시 발생 가능성이 높아지고, 데이터시트 버전표상 00x·A0x 두 계열 모두 현재 버전이 에라타 상한에 위치하며, 기존 글리치 검사는 워크어라운드를 대체 못 한다. 순수 단독 채택에는 반대하며, 워크어라운드 동반과 IC 버전 실측 병행을 권고한다.

---

## 0. 결론 먼저 — 판정

> **단독채택반대** (조건부채택으로 전환 가능하나, 조건이 이중이고 그중 하나는 현재 증거상 통과 낙관 불가)

- P3 스펙의 **기계적 내용(파일:라인, 레지스터값)은 재검증 결과 100% 유효** — 재작업 불필요.
- 그러나 "부속 레버 → 주역 방식" 승격 상태에서, **에라타 워크어라운드도 Report Rate 결합도 없는 순수 형태**를 그대로 단독 채택하는 것은 반대한다.
- IC 버전 확인(그라운드_1 스펙)은 **반드시 필요하지만 그 자체만으로 충분조건이 아니다** — 이유는 §3, §5에서 근거와 함께 제시한다.

## 1. 재검증 — P3 스펙과 현재 코드(2026-07-05 기준) 일치 여부

### 1.1 `tdc_touch_iqs323.c` — 0xC0 write 6곳 재확인

직접 재실행한 확인 명령과 결과:

```
grep -n "write_register(REG_SYSTEM_CONTROL" tdc_touch_iqs323.c
→ 237, 318, 447, 453, 465, 471 (6곳, 유일)

grep -rn "0xC0|SYSTEM_CONTROL" src/2__cm3/Cortex-M3-src/ (제외: iqs323.c)
→ main.c:64 g_cm3_manu_reserved[0xC0](배열 크기, 무관) / ble_communication.c:348·ci_ble_control_ota.h:110
  (OTA 커맨드 상수 0xC0, 무관) / systemControl.h:1-2(헤더가드명, 무관) / iqs323.h:78,81(주석, write 아님)

wc -l tdc_touch_iqs323.c → 499 (P3 스펙 프런트매터 "전체 499줄"과 일치)
```

**결론**: P3가 명시한 "IQS323 0xC0 write는 전 소스트리에서 `tdc_touch_iqs323.c` 6곳뿐"이라는 전제는 오늘 재실행 기준으로도 그대로 성립한다.

라인별 before 값 재대조 (P3 스펙 표 대 현재 코드 직접 Read 결과):

| # | 라인 | 함수 | P3가 기록한 before | 현재 코드 실제 값(직접 확인) | 일치 |
|---|---|---|---|---|---|
| 1 | 237 | `ack_reset()` | `0x01,0x00` | `write_register(REG_SYSTEM_CONTROL, 0x01, 0x00);` | 일치 |
| 2 | 318 | `beta_power_settings()` | `0x50,0x07` | `ok &= write_register(REG_SYSTEM_CONTROL, 0x50, 0x07);` | 일치 |
| 3 | 447 | `apply_settings()` 부팅 Re-ATI | `0x54,0x07` | `if (!write_register(REG_SYSTEM_CONTROL, 0x54, 0x07))` | 일치 |
| 4 | 453 | `apply_settings()` 부팅 RESEED | `0x58,0x07` | `if (!write_register(REG_SYSTEM_CONTROL, 0x58, 0x07))` | 일치 |
| 5 | 465 | `tdc_touch_iqs323_re_ati()` | `0x54,0x07` | `return write_register(REG_SYSTEM_CONTROL, 0x54, 0x07);` | 일치 |
| 6 | 471 | `tdc_touch_iqs323_reseed()` | `0x58,0x07` | `return write_register(REG_SYSTEM_CONTROL, 0x58, 0x07);` | 일치 |

6곳 전부 **파일:라인·함수·값이 한 글자도 어긋나지 않고 일치**한다. 즉 2026-07-03(P3 작성) 이후 오늘(2026-07-05)까지 `tdc_touch_iqs323.c`의 이 부분은 전혀 수정되지 않았다 — P3는 "구현-레디 스펙"으로 작성됐을 뿐 실제 구현(④단계)은 아직 착수되지 않은 상태로 확인된다.

부가 확인:
- `events_enable()`(:300-304)의 `write_register(REG_EVENTS_ENABLE, 0x52, 0x00)`(:303) — 현재도 그대로. `apply_settings()` 내 호출 순서도 `events_enable()`(:427) → `beta_power_settings()`(:431)로, P3가 주장한 "Events Enable 선행" 순서 그대로 유지.
- `confirm_reset()`(:240-263)의 reset_event bit clear 확인(`(lsb & (1u << 7)) == 0`, :256) — 여전히 `ack_reset()`→`confirm_reset()`→…→`beta_power_settings()`(site#2, bit7 write) 순서이므로 §8.12 순서 제약("Reset Event bit이 set이 아니어야 event mode 진입 가능")은 여전히 만족.
- 값 계산 재검산: `0x50(0b0101_0000) | 0x80 = 0xD0(0b1101_0000)`, `0x54(0b0101_0100) | 0x80 = 0xD4`, `0x58(0b0101_1000) | 0x80 = 0xD8` — bit7 단독 OR, Power Mode(bit6-4)·CH Timeout Disable(MSB 0x07)은 불변. 데이터시트 A.30(0xC0, p.61)의 비트 배치(Bit 7 = Interface Selection, MSB 바이트 bit10-8 = CH2/1/0 Timeout Disable)와 대조해도 LSB/MSB 귀속이 정확하다 — bit7은 LSB 바이트 소속이므로 P3의 OR 연산 대상(lsb 파라미터)이 옳다.

### 1.2 `main.c` — 롱터치 재부팅 카운터 read-fail 상호작용 재확인

P3 §4.3의 핵심 발견을 라인 단위로 재확인했다(main.c 직접 Read, 2026-07-05 기준):

| 대상 | P3가 인용한 라인 | 현재 코드 실제 라인·내용 | 일치 |
|---|---|---|---|
| `tdc_touch_sleep_handle_ati_error()` | main.c:1062-1092 | 1062~1092, 두 분기 모두 `ok &&` 게이트 → read 실패 시 카운터 **동결**(증감 없음) | 일치 |
| `tdc_touch_sleep_handle_touch_reboot()` | main.c:1125-1153 | 1125~1153, `if (ok && state==TOUCH){cnt++} else {cnt=0;}` → read 실패는 else로 떨어져 **즉시 0 리셋** | 일치 |
| `fake_func_sleep()`의 동일 패턴 | :1017 `touch_cnt=0` | 1017행 `touch_cnt = 0;` (else 분기) | 일치 |

추가로 본 재검토에서 `tdc_touch_time.h`를 직접 대조해 P3가 인용한 "24연속 폴링" 수치를 독립적으로 재계산했다:

```
TDC_TOUCH_ULP_REBOOT_TOUCH_MS = 2400  (:42)
TDC_TOUCH_ULP_WAKE_MS         = 100   (:37)
TDC_TOUCH_ULP_REBOOT_TOUCH_CNT = TDC_TIME_TO_CNT(2400,100) = ceil(2400/100) = 24  (:48-49)
```

P3가 §4.3에서 언급한 "24연속 폴링 중 단 1회 실패로도 무한정 재시작" 수치와 정확히 일치 — 파생 매크로를 직접 계산해 재확인했으므로 인용 의존이 아닌 독립 재검증이다.

### 1.3 참고 — 일반(노말) 경로의 hold 방식과 대조

`tdc_touch_logic.c:96-113`을 확인한 결과, **노말 폴링 경로(FSM `tdc_touch_logic_step`)는 read 실패 시 즉시 리셋이 아니라 hold 방식**을 쓴다(`TDC_TOUCH_READ_FAIL_HOLD_CNT`=10회/2000ms 허용 후에야 NOT_TOUCH 강제, tdc_touch_time.h:26,31-32). 즉 P3 §4.3이 지적한 "즉시 리셋" 취약점은 **ULP(절전) 경로의 롱터치 재부팅 카운터에 한정된 문제**이고, 일반 FSM 자체는 이미 더 견고한 패턴을 쓰고 있다는 것이 재확인된다 — P3의 스코핑이 정확했음을 뒷받침하는 교차 확인이다.

**1절 소결**: P3 스펙은 코드 측면에서 **재작업이 전혀 필요 없다**. 문제는 스펙 자체가 아니라, 이를 "순수(워크어라운드 없이) 단독" 채택해도 되는가라는 §5의 질문이다.

## 2. 데이터시트 원문 재대조 (`iqs323_datasheet.pdf`, Revision v1.11, 2025년 8월, pdftotext -layout 직접 대조)

### 2.1 Streaming vs Events, Force Comm (§8.11~8.13, p.32-33)

- §8.11.1 (p.32): "In I2C streaming mode data is constantly reported at the relevant power mode report rate..." — Streaming은 이벤트 유무 무관 매 Report Rate마다 보고.
- §8.11.2 (p.32): "In event mode the RDY line will only go low when one or more of the enabled events are triggered or if the device resets." — Events는 활성 이벤트 발생 또는 리셋 시에만 RDY assert. **이 문장 자체는 원문 그대로이며 P3의 인용과 정확히 일치**.
- §8.12 (p.32): "To enter event mode, the Reset Event bit in the System Status register must not be set." — P3가 인용한 순서 제약과 일치.
- §8.13 (p.33): "The typical values of twait are 0.1ms ≤ twait ≤ 45ms." — P3가 인용한 `TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS`=45(iqs323.h:32)와의 "여유 거의 0" 지적 근거가 원문 그대로 확인된다.

### 2.2 부록C(Known Issues, p.67) — I2C Lock Up 에라타

원문:
```
I2 C Lock Up
Versions Affected:
IQS323-00x v1.3 and below.
IQS323-A0x v1.4 and below.

Issue Description:
In certain cases the IQS323 can enter a state in which all bytes read over I2 C
return a constant value. There is a higher likelihood of this occuring when using
the force communications method described in Section 8.13.

Recommended Workaround
At the end of every I2 C communication, read one byte from a register that does
not exist. If the returned value is not 0xEE, hard reset the IQS323 by following
the guidelines in Section 6.6.
```

P3(그리고 오케스트레이터 입력)의 인용과 **버전 범위·워크어라운드 문구 모두 정확히 일치**한다. 아울러 같은 "C Known Issues" 절에 **별개의 에라타**("I2C Settings Register", IQS323-00x v1.3 and below만 해당, 비트 클리어 불가 문제)가 함께 있음을 확인 — 두 에라타는 버전 범위가 다르므로(Lock Up은 00x·A0x 모두, Settings Register는 00x만) 혼동하지 않도록 구분해 기록한다.

### 2.3 레지스터 근거 (A.1/A.30/A.32-A.33/A.37)

- A.30 System Control(0xC0, p.61): "Bit 7: Interface Selection — 0: I2C Streaming / 1: I2C Events" — P3의 bit7 해석과 일치.
- A.32/A.33 Events Enable(0xD3, p.61-62): Release UI 주문코드(A.32)·Movement UI 주문코드(A.33) 모두 동일 비트 배치 — bit6=ATI Error, bit4=ATI Event, bit1=Touch Event. `0x40+0x10+0x02=0x52` — 코드 주석·P3 인용과 정확히 일치. **두 주문코드 계열 어느 쪽이든 0x52 값 자체는 동일하게 유효** (아래 §3.2의 계열 모호성과는 별개 사안).
- A.37 Hardware ID(0xE1, p.64): "0xF003: IQS3dd / 0xF004: IQS3ed" — 그라운드_1(G1) 스펙이 다룰 레지스터의 값이 정확히 일치함을 확인.
- A.1 Version Information(0x00–0x09, p.49): 아래 §3.3에서 상세.

## 3. 발견 사항 (본 재검토에서 추가로 확인)

### 발견_1 — 인용 사슬 정정: "펌웨어 권장" 문구는 데이터시트 원문이 아니다

오케스트레이터 입력과 본 작업 `요구사항.md`(:17)는 "데이터시트 §8.11.2 NOTE가 '펌웨어 권장: Event mode를 기본, Streaming은 개발·디버깅 단계 임시용'이라 명시"라고 "확인"으로 적어 두었고, 이는 선행 작업 `20260703_touch-heisenberg-sw-mitigation`의 V3(`13_V3_S3검증.md:51`)에서 "데이터시트는 '...'라고 명시한다(§8.11.2 NOTE)"로 최초 기록된 것이 그대로 계승된 것이다.

**직접 대조 결과**: `iqs323_datasheet.pdf` §8.11.2 원문(위 2.1 인용)에는 이 "펌웨어 권장" 문구가 **존재하지 않는다**. 데이터시트가 실제로 말하는 것은 "event mode는 마스터가 활동 없을 때 매 사이클 불필요하게 방해받고 싶지 않아서 보통(usually) 활성화된다"는 서술적 설명뿐이다(원문: "This is usually enabled since the master does not want to be interrupted unnecessarily during every cycle if no activity occurred.").

"펌웨어 권장: event mode를 기본으로..." 문구는 실제로는 `docs/참고/touch/데이터시트/05_i2c인터페이스.md`(:350, :360)의 **`[!NOTE]` 콜아웃** — 즉 Sound1 팀이 데이터시트 직역 문단 사이에 추가한 자체 해설/주석 — 에서 나온 것이다. 이 파일은 직역 문단과 `[!NOTE]` 해설을 GFM Alert 문법으로 구분해 담고 있는데(문서 작성 규칙상 정상적인 스타일), V3가 파일 전체를 "데이터시트"로 뭉뚱그려 인용하면서 해설 주석을 원문 인용처럼 표기하는 인용 사슬 오류가 발생했고, 이것이 오늘 `요구사항.md`까지 그대로 전파되었다.

**정정**: "제조사가 event mode를 기본으로 쓰라고 명시한다"는 주장은 근거가 없다 — [미확인]으로 하향한다. 다만 "Events 모드가 유휴 구간 RDY 토글을 없앤다"는 핵심 사실 자체는 §8.11.1-8.11.2 원문에서 직접, 명확히 확인된다. 이번 승격 판단에서 "제조사 권장과 반대로 설정돼 있었다"는 식의 도덕적/규범적 근거는 빼고, 순수하게 트래픽·CPU 이득이라는 사실 기반 근거로만 판단해야 한다.

### 발견_2 — I2C 주소 0x44의 계열 모호성: 그라운드_1 게이트가 왜 "있으면 좋은 것"이 아니라 "필수"인가

Table 10.1(Order Code Description, p.38) 원문 확인 결과:

| 주문코드 | I2C 주소 | UI 종류 |
|---|---|---|
| 001 | 0x44 | Release UI |
| 002 | 0x58 | Release UI |
| A01 | 0x44 | Movement UI |

Sound1 코드의 `TDC_TOUCH_IQS323_SLAVE_ADDR`(iqs323.h:28)는 `0x44`다. 그런데 **0x44는 001(00x 계열)과 A01(A0x 계열) 양쪽에 공유되는 주소**다 — I2C 주소만으로는 Sound1 보드의 실장 IC가 00x 계열인지 A0x 계열인지 **구분할 수 없다**. 회로 참고 문서(`레퍼런스/IQS323-회로-구성.md:103`, `개선/회로 구성·분석.md:158`)도 주소(0x44)만 기록할 뿐 계열을 특정하지 않는다.

이 때문에 그라운드_1(IC 버전 실측)이 다루는 `0x00`(Product Number, 00x=1106/A0x=1462) 또는 `0xE1`(Hardware ID, 0xF003/0xF004) 레지스터 read는 "여유가 있으면 하는 부가 확인"이 아니라, **어느 에라타 버전 상한(v1.3 vs v1.4)을 적용해야 하는지 자체를 결정하는 선행 필수 단계**다. 이는 SW-only(`read_register()` 재사용, HW 무수정)로 가능하다는 점도 코드 구조상 확인된다 — `read_register()`(iqs323.c:199-230)는 임의 주소를 인자로 받으므로 `0x00`/`0x01`/`0x02`/`0xE1` 어느 것이든 함수 변경 없이 호출부만 추가하면 된다.

### 발견_3 — 버전표 상한 일치: 그라운드_1 게이트의 "통과"(비적용 확정) 낙관은 근거가 약하다

A.1 Version Information(0x00–0x09, p.49) 원문 표:

| 주소 | 항목 | 00x 값 | A0x 값 |
|---|---|---|---|
| 0x00 | Product Number | 1106 | 1462 |
| 0x01 | Major Version | 1 | 1 |
| 0x02 | Minor Version(LSB, MSB는 Reserved) | 3 | 4 |

부록C의 에라타 적용 범위는 "IQS323-00x **v1.3 이하**"·"IQS323-A0x **v1.4 이하**"다. Major.Minor를 "v1.3"="Major 1·Minor 3", "v1.4"="Major 1·Minor 4"로 대응시키면(이 대응 자체는 데이터시트가 한 문장으로 명시하진 않으므로 **[가설-강, 본 재검토의 추론]**), **같은 데이터시트 개정판(v1.11, 2025년 8월)이 현재 문서화하는 두 계열의 버전 값이 정확히 에라타의 "이하" 상한과 일치**한다 — 즉 이 데이터시트 기준으로는 00x·A0x 어느 계열이든 **에라타를 벗어난(더 높은 버전의) 실리콘이 별도로 문서화돼 있지 않다**.

이는 "IC 버전을 실측하면 에라타 미적용이 확인될 가능성이 있다"는 낙관적 전제에 대한 반대 증거다. 실측 자체는 (발견_2대로) 여전히 필요하고 유의미하지만 — **결과가 "미적용"으로 나올 것을 기대하고 게이트를 설계해서는 안 된다.** 다만 이는 어디까지나 데이터시트 표와 에라타 절이라는 두 개의 별개 섹션을 본 재검토가 연결한 추론이며, Sound1 실장 IC의 실제 실리콘 로트가 이 표보다 신규(에라타 이후) 스테핑일 가능성 자체를 배제하지는 못한다 — 그래서 실측(그라운드_1)은 여전히 "필수"이지 "생략 가능"이 아니다.

### 발견_4 — 기존 0xEE/0xEE 글리치 검사는 에라타 워크어라운드를 대체하지 못한다

`read_status()`(iqs323.c:357-360)·`confirm_reset()`(:251-255)·`wait_ati_done_blocking()`(:334)은 모두 **읽으려는 대상 레지스터(0x10 System Status) 자체**의 값이 `lsb==0xEE && msb==0xEE`인지를 검사해 글리치로 처리한다. 이는 §8.10(Invalid Communications Return)이 규정하는 "존재하지 않는 레지스터 read" 또는 "윈도우 밖 read" 상황에 대한 방어다.

반면 부록C의 Lock-Up 워크어라운드는 "**존재하지 않는 별도 레지스터**를 매 통신 끝에 read해 0xEE인지 확인"하라는 것이다 — 이는 0x10을 읽어 0xEE0xEE인지 보는 것과 **다른 검사**다. Lock-Up 상태에서 "모든 read byte가 반환하는 상수 값"이 우연히 0xEE0xEE가 아닌 한(에라타 원문은 이 상수 값이 무엇인지 특정하지 않는다 — [미확인]), 0x10을 읽었을 때 **그럴듯해 보이는 임의의 상태 워드가 정상 데이터인 것처럼 통과**될 수 있다. 즉 현재 코드의 기존 글리치 검사는 부록C 워크어라운드의 **우연한 대체물이 아니며**, 순수 채택(C1)은 이 보호를 자동으로 얻지 못한다.

> [!NOTE]
> 발견_2~4는 그라운드_1(G1) 고유 미션(IC 버전·에라타 적용범위 실측 가능성 스펙)을 대신하려는 것이 아니라, 본 후보(C1)의 "단독채택 여부" 판정에 필요한 만큼만 확인한 지지 근거다. G1의 정식 스펙(실측 프로토콜 상세)은 별도 산출물을 참조해야 한다.

## 4. "부속 레버 → 주역 방식" 승격이 리스크 계산을 바꾸는 지점

P3(2026-07-03)는 Events 전환을 S1~S8 여러 완화 레버 중 하나로, "시도해보고 아니면 다른 레버로 대체 가능"한 실험적 옵션으로 다뤘다. 오늘(2026-07-05)의 지시는 이를 **터치 드라이버의 상시 통신 방식(주역)으로 승격**하는 것이다. 이 전환은 다음 두 가지를 바꾼다:

1. **노출 시간 축의 변화**: 실험적 레버였다면 문제 발생 시 되돌리거나 다른 레버로 교체하는 재량이 있었다. 주역 방식이 되면 **양산되는 모든 개체가, 기기 수명 전체 동안, 상시로** 이 통신 모드에 의존한다 — I2C Lock-Up이라는 낮은 확률의 사건이라도 노출 시간(개체 수 × 가동 시간)이 커지면 누적 발생 기대값이 커진다.
2. **대안 상실**: 실험 단계에서는 "Events가 문제면 Streaming으로 되돌린다"가 항상 열려 있는 폴백이었다. 주역으로 승격한다는 것은 이 폴백을 포기하고 Events에 아키텍처를 고정한다는 의미다 — 따라서 채택 이전에 리스크를 확정적으로 낮춰야 하는 부담이 실험 단계보다 훨씬 크다.

프로젝트 메모리 기준으로 Sound1은 인공와우(인공와우 외부기) 사운드 프로세서의 터치 UI를 담당한다 — 오조작·먹통은 사용자가 청각 보조를 잃는 것과 직결될 수 있는 기능이다. 이 맥락에서 "가능성 있는 리스크를 방치한 채 주역으로 승격"하는 결정은 실험적 레버 채택보다 훨씬 보수적으로 접근해야 한다고 판단한다.

## 5. 권고

### 5.1 판정: 단독채택반대

"에라타 워크어라운드도 Report Rate 결합도 없는 순수 형태"(P3 스펙 그대로, C1의 원래 스코프)를 **그대로 단독 채택하는 것에는 반대**한다. 근거를 요약하면:

1. Events 전환은 `force_window_open()`의 "이미 열림" 조기반환(iqs323.c:149-152)을 유휴 구간에서 사실상 소멸시켜, §8.13 force communications 의존도를 상시화한다(P3 §4.1-4.2, 본 재검토 §1.2에서 재확인).
2. 부록C(p.67)는 "force communications 사용 시 Lock-Up 발생 가능성이 높아진다"고 **직접, 명시적으로** 경고한다 — 1번과 정확히 맞물리는 트리거 조건이다.
3. IC 버전 실측(그라운드_1)은 필수 선행 단계이지만, A.1 버전표(발견_3)를 근거로 "미적용 확정"으로 귀결될 가능성을 낙관할 근거는 약하다.
4. 기존 코드의 0xEE0xEE 글리치 검사는 부록C 워크어라운드를 대체하지 못한다(발견_4) — 즉 순수 채택은 우연한 보호막도 없다.
5. P3 §4.3(본 재검토 §1.2에서 재확인)의 롱터치 재부팅 카운터(24연속 폴링 즉시 리셋) 취약점은 **에라타 발생 여부와 무관하게**, 강제개방 실패율 자체가 늘어나는 것만으로도 성립하는 별개의 위험이다 — 설령 그라운드_1이 "에라타 비적용"을 확인해도 이 위험은 그대로 남는다.
6. §4에서 논한 대로, 이번 승격은 실험적 레버가 아니라 상시 아키텍처로의 고정을 의미하므로 위 리스크들을 방치한 채 넘어갈 여지가 실험 단계보다 작다.

"채택"(무조건 그대로 진행)은 2·3·5번 근거로 기각한다. 단순 "조건부채택"(그라운드_1 통과만을 유일 게이트로 설정)도 5번 근거(에라타와 독립적인 잔존 위험)로 인해 **불충분**하다고 판단해 기각한다.

### 5.2 조건부채택으로 전환되는 조건

본 판정은 "영원히 반대"가 아니다. 다음이 모두 충족되면 순수 형태(C1) 단독 채택으로 격상할 수 있다:

- **조건_1**: 그라운드_1의 IC 버전 실측이, Sound1 실장 IC가 부록C 적용 범위(00x v1.3 이하 / A0x v1.4 이하)를 **명확히 벗어난** 버전임을 실측으로 확인.
- **조건_2**: P3 §4.3의 롱터치 재부팅 카운터가 hold 방식(또는 동등한 완화)으로 재설계되어, 강제개방 실패율 증가가 정상 기상 제스처를 약화시키지 않음을 확인(C4/그라운드_3·후속 S6 계열 영역).

### 5.3 실무 권고

1. P3의 5개 write 사이트 변경(§1.1 표) 자체는 **그대로 유지** — 재작업 불필요, 향후 구현 시 그대로 반영 가능.
2. 다만 최초 구현·배포 시점의 기본값은 **후보_2(에라타 워크어라운드 결합)를 동반한 번들**로 잡을 것을 권고한다 — "일단 순수로 배포하고 문제 생기면 워크어라운드 추가"가 아니라, 처음부터 방어적으로 시작하는 순서를 권고한다.
3. 그라운드_1의 IC 버전 read(0x00/0x01/0x02 또는 0xE1)는 **런타임 게이트가 아니라 최소한 부팅 시 1회 로그 계측으로라도 반드시 도입** — 조건_1이 실측으로 확인되면, 그 시점에 워크어라운드를 제거해 순수 형태로 단순화하는 재작업 근거로 삼는다.
4. 조건_2(재부팅 카운터 완화)는 에라타 논의와 별개로 진행 — 에라타가 최종적으로 비적용 판정을 받더라도 이 위험은 남으므로, 채택 여부와 무관하게 처리가 필요하다.

4. 최종 권고는 **단독채택반대** — 순수 형태(워크어라운드·Report Rate 결합 없음)를 그대로 주역 방식에 고정하는 것에는 반대하며, 에라타 워크어라운드 동반과 IC 버전 실측 병행, 그리고 롱터치 재부팅 카운터의 별도 완화를 조건으로 조건부채택으로 격상할 것을 권고한다.
