# 99 · 종합 평결 — 이벤트 모드 채택 딥다이브

**TL;DR**: 은수님의 원래 전제("이벤트 모드로 RDY가 매번 토글되지 않아 이득")를 14페르소나(그라운드3·후보5·검증6)로 분해 검증한 결과, **좁은 의미(IC 자체 RDY assert 빈도 감소)는 참이나, 은수님이 의도했을 실질적 이득(불필요한 인터럽트 회피)은 이 아키텍처에 성립하지 않는다** — 현재 RDY 핀은 애초에 인터럽트가 아니라 busy-wait 폴링 전용(EXTI 등록 0건, 코드 직접 확인)이기 때문이다. 대신 순수 트래픽 관점의 대안적 이득은 존재하되 방향만 유효하고 크기는 과대추정(1.3~2.0배→보정 시 1.07~1.39배)됐다. 반면 은수님이 이번에 직접 추가한 "폴링→인터럽트 전환"(후보_4)은 기존 `ci_dio.c` 인터럽트 인프라 재사용으로 **SW-only 실현 가능**하며 Events 모드 채택과 무관하게 독립적으로 유효하다. 검증 과정에서 이벤트 모드 도입과 무관하게 항상 존재하는 신규 위험(IQS323 내장 255ms 통신 워치독을 런타임이 전혀 점검하지 않는 구조적 공백)도 발견했다. 할루시네이션은 확정 오류 2건·경미 오류 2건뿐(약 150건 인용 중), 최종 결론에 영향 없음.

> [!IMPORTANT]
> **2차 라운드 갱신(§6~7)**: 은수님이 "결론은 지금과 별 차이 없는 것 아니냐"고 재차 확인, 이벤트모드+인터럽트 **결합** 시나리오(유휴 시 폴링 자체 정지)를 9페르소나로 추가 검증했다. 결론: 결합하면 실제로 큰 차이(유휴 트래픽 최대 98%+ 감소)가 나지만, **인터럽트·이벤트모드 없이 유휴 폴링 주기만 늘리는 훨씬 단순한 방식(후보_7 변형_1)도 대등한 효과**를 내며, 이것이 리스크 대비 최선의 선택으로 격상됐다.

## 1. 은수님 원래 전제의 3중 분해 (검증_2 §6 최종판정)

| 층위 | 판정 | 근거 |
|---|---|---|
| ① 좁은 의미: IC 자체 RDY assert 빈도 | **참** | §8.11.2/8.12 원문 확정, 반증 실패 |
| ② 실질 의도: 불필요한 인터럽트 회피 | **불성립** | Sound1은 RDY를 인터럽트로 쓴 적이 없음(EXTI 0건, `Sys_DIO_IntConfig` 미대상) — 검증_2·검증_6 독립 재확인 |
| ③ 대안적 이득: 순수 I2C 트래픽 감소 | **방향은 유지, 크기는 과대추정** | "1.3~2.0배 증가"는 반증 실패해 방향은 살아남으나, 사이클당 4회 호출의 비균질성을 반영한 독립 재계산 결과 1.07~1.39배로 절반 수준 |

**결론**: 은수님이 원했던 "RDY 안 토글돼서 이득"의 진짜 실현 경로는 **이벤트 모드 자체가 아니라 폴링을 인터럽트로 바꾸는 것**(후보_4)이다 — 은수님이 검증 진행 중 직접 추가한 지시("폴링을 인터럷트 방식으로 변경하는 것까지 고려")가 정확히 이 발견과 맞아떨어진다.

## 3. 검증 과정의 신규 발견 (그라운드·후보가 다루지 못한 것)

- **[최중요, 검증_4 발견]** IQS323 내장 **255ms 통신 워치독**(§7.6)이 있고, 이것이 트리거되면 IC는 POR 기본값으로 완전 초기화되며 System Status의 Reset Event 비트(bit7)가 set된다. **런타임 코드(`read_status()`) 어디에도 이 비트를 담는 필드가 없어, 부팅 이후 어떤 원인으로든 IC가 스스로 리셋되면 FSM은 눈치채지 못한 채 깨진 설정(3채널 활성·Threshold=0)으로 계속 동작한다.** 기존 안전장치 3종(`re_ati()` 복구·후보_2의 `lockup_probe()`·기존 0xEE 글리치 검사) 전부 이 시나리오를 탐지하지 못함을 코드로 확인했다. 이는 **이벤트 모드 채택 여부와 무관하게 항상 존재하는 위험**이며, Events 전환 시 강제개방 빈도 증가로 노출 빈도만 늘어난다.
- **[검증_4 발견]** azd004(별도 앱노트)에만 있는 "강제개방-자연이벤트 경합 레이스" — force_window_open()이 RDY 확인 직후 0xFF를 보내는 순간 실제 이벤트가 끼어들면 방금 연 창을 도로 닫아 0xEE를 유발할 수 있다. 부록C 에라타(버전 한정)와 달리 **버전 무관, 모든 IQS323에서 발생 가능**한 별개 원인.
- **[검증_3 발견]** 후보_2(에라타 워크어라운드)의 `lockup_probe()`+`mclr()` 재사용에 신규 위협 2건: 위협_A(락업 발생 시 특정 고착값 조합에서 게이트가 영구 정체할 가능성), 위협_B(`mclr()` 런타임 재사용이 §6.6.3의 150µs 스위치오버 여유를 위반해 재초기화가 침묵적으로 무력화되는 라이브락).

## 4. 할루시네이션 감사 결과 (검증_5, 은수님 최우선 지시 대응)

01~08 문서 약 150건 이상의 인용(레지스터·비트·라인·페이지) 전수 대조 결과 **95% 이상 정확**. 확정 오류 2건:
1. 그라운드_1이 데이터시트 Table 10.1의 오더코드 I2C 주소를 **반전 인용**(001=0x58/002=0x44라 썼으나 실제는 001=0x44/002=0x58) — 단 후보_1은 같은 표를 독자적으로 정확히 재대조해 하류 영향 없음.
2. 후보_5가 "§8.11.2 펌웨어 권장은 Event mode 기본"을 데이터시트 원문 근거처럼 3곳에서 인용했으나, 실제로는 **참고 md 파일의 사내 해설**(원문에 "recommend"/"firmware" 문구 없음) — 후보_1은 동일 문제를 스스로 찾아 정정했으나 후보_5는 반영하지 못함. 후보_5의 핵심 논거 자체는 이와 무관하게 성립하므로 최종 권고는 안 바뀜.

경미 오류 2건(페이지·라인 근소 이탈)은 내용 자체가 정확해 영향 없음. **하드 할루시네이션(존재하지 않는 사실 창작) 0건.**

## 5. 1차 라운드 종합 결론

1. 은수님의 원래 방향(이벤트 모드=이득)은 이 특정 아키텍처(RDY=busy-wait 폴링)에서는 **의도한 형태로 성립하지 않는다** — 검증이 정직하게 반박 방향으로 수렴했다.
2. 대신 은수님이 검증 도중 직접 확장한 스코프(폴링→인터럽트 전환, 후보_4)가 **진짜 이득을 주는 경로**임이 확인됐고, SW-only·기존 인프라 재사용으로 실현 가능하다.
3. 이벤트 모드 자체(후보_1·2)는 순 이득이 작고 에라타·워크어라운드 부작용을 동반해 **단독 채택 비권고**, 다만 IC 버전 실측(SW-only 가능)과 워크어라운드 개선을 전제로 조건부 검토는 가능하다.
4. 검증 과정에서 이벤트 모드 논의와 별개로 **항상 존재했던 위험**(255ms 워치독 미점검 공백)을 발견한 것이 이번 딥다이브의 부수적이지만 중요한 성과다.

## 6. 2차 라운드 — 결합 시나리오(Events+인터럽트) 정량 검증

은수님 지적("지금이랑 별 차이가 없을 것 같다") — 정확했다. 1차 라운드의 후보_4(단순 인터럽트 전환)·이벤트모드 단독 모두 **폴링 주기(100ms 고정) 자체는 그대로 유지**한다는 전제였기 때문이다. 이 사각지대를 9페르소나(그라운드3·후보2·검증4)로 정량 검증했다.

- **그라운드_7**: 100ms 폴링 의존 타이밍 로직 11종 확인 — 5종(롱터치·Re-ATI쿨다운·stuck승격 등)은 실제 경과시간(타임스탬프) 기반이라 인터럽트 재설계와 무관히 안전, 6종(ATI에러재부팅·롱터치재부팅 등 절전 ULP 카운터)은 순수 호출횟수 누적이라 유휴 게이트 설계 시 반드시 고려 필요.
- **그라운드_8**: 터치 이벤트는 **진입/이탈 전이(edge)에만 발생**, 유지 중(steady touch) 재발생 없음을 원문(§8.11~8.12)으로 확정 — 순수 이벤트만으론 "아직 눌려있는가"라는 레벨 상태를 알 수 없다.
- **그라운드_9**: 3개 폴링 경로 전부 경과시간 게이트 통과 후 read 무조건 호출 — I2C 자체를 게이팅할 삽입 지점 존재(단, 정확한 위치는 검증_7·9가 후보_6과 이견 발견, 아래 참조).
- **후보_6(하이브리드)**: 유휴 시 폴링 완전정지+RDY 인터럽트 대기, 이벤트 시 활성폴링(100ms) 재개. 3불변식 무손상 확인. **duty(터치 활성 비율) 1% 가정 시 유휴 트래픽 약 98.6~98.9% 감소, 0.05%면 99.9%+.**
- **후보_7(대안, 유휴 폴링주기 연장)**: 유휴 시 100ms→500~1000ms로 늘리고 이벤트 시 인터럽트로 즉시 복귀. 후보_6 대비 회귀위험은 더 낮음(정지→재개 실패라는 단일장애점이 없음). **핵심 발견**: 인터럽트·이벤트모드 전부 빼고 유휴 폴링주기만 늘리는 **변형_1**(Streaming 유지, 레지스터·인터럽트 배선 전혀 불요)도 트래픽 절감이 본안과 대등 — 과제가 요구한 "훨씬 단순한 대안" 취지에 가장 부합.
- **검증_7·9 신규 발견**: `tdc_touch_process()`의 RDY 게이팅 삽입 위치가 그라운드_9(경과시간 게이트 통과 후, 301행)와 후보_6(경과시간 게이트 이전, 294행 앞)이 **서로 다르다** — 그라운드_9 방식대로 구현하면 후보_6이 약속한 "즉시 감지" 이점이 사라지고 기존과 동일한 최대 100ms 지연이 재현된다. **구현 시 후보_6 방식(294행 앞)을 명시적으로 채택해야 함.**
- **검증_9·10 신규 발견**: 후보_7이 제기한 "노말모드에 이미 WFI가 있다"(main.c:452·738 동일 while(1) 루프)는 정정이 **사실로 확정**됐다 — 1차 라운드 후보_4·후보_6이 인용한 "노말모드 WFI 부재" 주장이 오류였다. 다만 실익은 "인터럽트 도입 리스크 완화" 수준이며, CPU 절전 심도 자체는 별개(iterationFlag가 이미 ms급으로 자주 깨움).
- **검증_8 최중요 발견**: 후보_6·7의 duty 가정(1%·0.05%, "의도적 조작" 프레이밍)이 **이 프로젝트 자체의 선행 UX 분석(2026-06-15, maturity:stable)이 이미 문서화한 "간접 접촉 빈도 높음"(안경다리 마찰·헤어·베개 압착, 수초 지속)** 채널을 반영하지 않았다 — 이를 반영하면 duty가 5~10%대일 근거가 있고, 이 경우 **후보_6의 절대적 우위(93%+ 감소)는 유지되나, 후보_6 대 후보_7의 상대적 격차(10.9~20.8배)는 1.9~2.8배 수준까지 좁혀진다.** 즉 구현 복잡도·회귀위험이 더 큰 후보_6을 선택할 실익이 duty 실측 없이는 확정되지 않는다.

## 7. 최종 권고 (2차 라운드 반영)

1. **결합 시나리오는 실제로 의미 있는 차이를 만든다** — 은수님의 "지금과 별 차이 없다" 우려는 1차 라운드(폴링 주기 유지 전제)에서는 맞았으나, 유휴 시 폴링 자체를 줄이는 결합안에서는 반박된다.
2. **그러나 가장 리스크가 낮으면서 효과가 대등한 것은 후보_7의 변형_1**(유휴 시 폴링주기만 연장, Events 모드·인터럽트 배선 전부 불요)이다 — duty 실측 전까지는 이것이 권고 1순위다.
3. 후보_6(완전정지+인터럽트)은 duty가 낮을수록(실사용 근접일수록) 상대적 이점이 커지므로, **실사용 duty(간접 접촉 포함) 실측 후** 후보_6으로 격상할지 결정하는 것이 합리적이다.
4. 구현 착수 시 두 가지 정정을 필수 반영: (a) `tdc_touch_process()` 게이팅은 경과시간 게이트 **이전**(294행 앞) 배치, (b) "노말모드 WFI 부재"라는 1차 라운드 서술은 오류이므로 폐기.
5. 1차 라운드의 다른 결론(이벤트 모드 자체 비권고, 255ms 워치독 공백 등)은 그대로 유효하다.
