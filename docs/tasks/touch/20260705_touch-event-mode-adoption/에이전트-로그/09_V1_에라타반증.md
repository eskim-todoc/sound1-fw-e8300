# 검증_1 · 에라타 반증

**TL;DR**: G1·C1·C2의 에라타 핵심 주장 네 건을 코드·데이터시트 원문으로 반증 시도했다. read_register() 실측가능성·0xF0 비존재·mclr() 기존함수 존재는 반증 실패로 원 주장이 유지된다. G1의 두 미확인 매핑은 부록·주문정보 섹션을 추가로 뒤졌으나 닫지 못해 미확인 유지가 타당함을 확인했고, 부가로 G1의 Table 10.1 주소 오독(001·002 뒤바뀜)을 발견했다.

> [!NOTE]
> 본 문서의 모든 데이터시트 인용은 `docs/참고/touch/iqs323_datasheet.pdf`를 오늘 세션에서 `pdftotext -layout`(및 표 셀 경계 재확인용 `pdftotext -bbox`)로 직접 재추출해 대조했다. 코드 인용은 `src/2__cm3/Cortex-M3-src/systemControl/tdc_touch_iqs323.c`(499줄 전체)·`tdc_touch_iqs323.h`·`tdc_touch.c`를 직접 Read해 확인했다. 확인하지 못한 부분은 전부 **[미확인]**으로 명시했다. 4개 반증시도 전부 "반증 실패 시 근거를 상세히 제시"하라는 지시에 따라 판정마다 재현 가능한 근거(페이지·행 번호·명령)를 남겼다.

## 반증시도_1 — G1 "0x00~0x02/0xE1은 read_register()로 추가 HW 없이 실측 가능" 재검증

### 원 주장 (G1 확인_3, 결론)

> "`addr` 파라미터에 레지스터 주소별 분기·화이트리스트·범위 검사가 전혀 없다 — 함수는 완전히 주소-불가지론적(register-address-agnostic)이다 ... 0x00·0x01·0x02·0xE1을 인자로 넘기는 것만으로 추가 HW·프로토콜 변경 없이 즉시 동작한다." / "결론: 실측 가능성 — 가능(확정)."

### 반증 경로 1 — 코드 재대조로 "숨은 분기"를 찾는다

`tdc_touch_iqs323.c`를 오늘 세션에서 처음부터 다시 Read했다. `read_register()`는 정확히 199~230행이며, G1이 인용한 라인 범위·본문과 한 글자도 다르지 않다.

```c
199  static bool read_register(uint8_t addr, uint8_t *p_lsb, uint8_t *p_msb)
200  {
201      uint8_t reg = addr;
202      uint8_t buf[2];
203
204      if (!force_window_open())
...
209      if (!i2c_write(&reg, 1))
...
214      wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
216      if (!force_window_open())
...
221      if (!i2c_read(buf, 2))
...
226      *p_lsb = buf[0];
227      *p_msb = buf[1];
228      wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
229      return true;
230  }
```

`addr`에 대한 `switch`·`if`·화이트리스트·범위 검사는 **0건**이다. 반증 시도로 하위 계층까지 내려가 봤다 — `i2c_write()`(57~87행)·`i2c_read()`(89~123행)도 각각 버퍼 바이트 개수(`len`)만 검사하고 그 바이트의 **내용**(레지스터 주소인지 여부)에는 전혀 관심이 없다. `force_window_open()`(145~175행)·`wait_window_closed()`(128~143행)도 RDY 핀 상태만 볼 뿐 어떤 레지스터를 대상으로 하는지 알지 못한다. 즉 addr=0x10이든 0x00이든 0xE1이든 물리적으로 완전히 동일한 코드 경로를 탄다 — **반증 실패**.

### 반증 경로 2 — 기존 REG_* 매크로와 주소가 충돌하지 않는가

```
grep -n "REG_" tdc_touch_iqs323.c
```
정의된 18개 매크로(`REG_SYSTEM_STATUS 0x10` ~ `REG_EVENTS_ENABLE 0xD3`, 17~34행) 중 `0x00`·`0x01`·`0x02`·`0xE1`과 겹치는 것은 **0건**이다. 신규 read 삽입이 기존 로직과 주소를 다투거나 부작용을 일으킬 여지가 코드 구조상 없다 — **반증 실패**.

### 반증 경로 3 — 데이터시트가 이 레지스터들에 별도 접근 규칙을 요구하지 않는가 (가장 강한 반증 시도)

§8절(I2C Interface, PDF p.29~33) 전체를 재독해 addr-종속적 접근 제약이 있는지 찾았다.

- §8.2 I2C Address(PDF p.30, 원문 1727~1734행): "The 7 bit I2C address is determined by the order code ... the debug address is the primary address with the least significant bit inverted." — 이것은 슬레이브 주소 자체에 대한 규칙이고 메모리맵 **레지스터** 접근과는 무관하다.
- §8.4 Communication During ATI(PDF p.30, 원문 1738~1741행): "Provided the Reset Event bit in the System Status register is not set, I2C communications are disabled for the duration of the ATI process." — 이것은 **addr와 무관한 전역 제약**이다. 그런데 G1이 제안한 삽입 시점(`wait_ati_done_blocking()` 반환 직후, 453행 RESEED 트리거 이전)은 `ati_active==0`이 334행에서 이미 실측 확정된 지점이라, 이 제약을 정확히 피한다 — 반증하려던 지점이 오히려 G1의 설계를 뒷받침한다.
- §8.5 Memory Map Addressing(PDF p.30, 원문 1742~1747행): "The memory map implements 8-bit addressing. Data is formatted as 16-bit words ... The 16-bit data is sent in little endian byte order." — 0x00~0x09·0xE1을 포함한 전체 주소 공간에 예외 없이 적용되는 서술이며, 특정 주소 구간만 다른 규칙을 쓴다는 언급은 §8.1~8.15 어디에도 없다.
- A.1(PDF p.49, 원문 2698~2708행)·A.37(PDF p.64, 원문 3794~3809행) 원문에는 "Read Only" 상수 값이라는 서술만 있을 뿐, 언락·인증·read-to-clear 등 부작용을 암시하는 문구가 전혀 없다.

이 세 방향(전용 접근 규칙, 전역 제약과의 충돌, read 부작용) 모두에서 반증에 실패했다.

### 판정 — refuted=false

**반증 실패. G1의 원 주장은 유지된다.** 근거: (1) 오늘 코드를 처음부터 다시 읽어 `read_register()`와 그 하위 3계층(`i2c_write`/`i2c_read`/`force_window_open`/`wait_window_closed`) 전부가 addr 값에 무관심함을 직접 재확인했고, (2) 기존 18개 `REG_*` 매크로와 주소 충돌이 없음을 grep으로 재확인했고, (3) 데이터시트 §8.1~8.15 전체를 다시 훑어 addr-종속적 접근 제약을 찾지 못했으며 유일하게 존재하는 전역 제약(§8.4 ATI 중 I2C 비활성)은 G1이 제안한 삽입 시점이 이미 회피하고 있음을 확인했다.

## 반증시도_2 — G1의 두 [미확인] 매핑, 부록A.7/A.8·§10·Table 10.x로 추가로 닫기 시도

### 매핑_1 — 부록C "IQS323-00x v1.3 / IQS323-A0x v1.4" ↔ 레지스터 Major/Minor Version 값 등치

**시도한 곳**: A.7·A.8(Prox Control, PDF p.51~53), §10 전체(Ordering Information, PDF p.38~40), Table 10.1, Appendix B(Revision History, PDF p.65).

- A.7(PDF p.51~52, 원문 2959~3010행)·A.8(PDF p.52~53, 원문 3012~3046행)은 0x32/0x42/0x52(Prox Control) 레지스터의 "Cs Size" 비트 폭이 IQS3dd/IQS3ed 사이에서 다르다는 내용만 다룬다. "v1.3"·"v1.4"·"Major Version"·"Minor Version" 등 버전 관련 단어는 **이 두 절 어디에도 등장하지 않는다**(직접 재독, 0건).
- §10(PDF p.38~40)은 주문코드(zzz)·패키지(pp)·벌크포장(b)만 다루며 실리콘 버전 개념 자체가 없다.
- Appendix B "Revision History"(PDF p.65, bbox 좌표 재확인)를 다시 열었다: `v1.3`(y=309.3)은 "October 2023"(y=309.3, 같은 행)과, `v1.4`(y=427.1)는 "November 2023"(y=427.1, 같은 행)과 정확히 같은 y좌표에 위치한다 — 이는 **데이터시트 문서 자체의 개정 이력**이지 실리콘 버전이 아님을 bbox로 재확인했다(G1의 발견_2와 동일 결론에 독립 도달).
- **정황(반증 재료)**: A.37 Hardware ID에는 각주 `iii`("Take note of Cs Size selection in Appendix A.7 and Appendix A.8")가 붙어 A.7/A.8과 명시적으로 교차 인용되는데, A.1 Version Information 표에는 이런 각주가 **전혀 없다**(원문 재확인, 2698~2708행에 각주 마커 0건). 데이터시트가 실제로 관련 있는 개념끼리는 각주로 교차 인용하는 습관을 보이면서도(A.37→A.7/A.8, Appendix C 각주 i→A.8), A.1과 Appendix C 사이에는 그런 각주가 없다는 점은 "둘 사이 명시적 연결이 진짜로 없다"는 소극적 증거를 보강한다.

**결론**: 추가 탐색으로도 닫지 못했다. G1의 [미확인] 표기가 게으른 것이 아니라 정직한 것임을 재확인했다.

### 매핑_2 — 00x/A0x 오더코드 ↔ IQS3dd/IQS3ed 명칭 등치

**시도한 곳**: 위와 동일한 절 + §10.2(Top Marking, PDF p.38~40).

- "IQS3dd"·"IQS3ed" 문자열은 전체 68페이지 중 정확히 6곳에서만 등장한다(`grep -n "IQS3dd\|IQS3ed"` 전수 확인): Figure 10.3/10.4 캡션("IQS3dd-DFN12 Package Top Marking"/"IQS3ed-DFN12 Package Top Marking", §10.2.2 DFN12 패키지 마킹, PDF p.39), A.7·A.8 표제, A.8 각주 `i`("Header files generated using the product GUI with IQS3ed should not be used with IQS3dd"), A.37 본문(0xF003/0xF004 정의). **이 6곳 중 어느 하나도 "00x" 또는 "A0x"라는 문자열과 같은 문장·같은 표에 등장하지 않는다** — 직접 grep 및 문맥 재독으로 확인.
- §10.2.1(WLCSP11)·§10.2.3(QFN20) 패키지의 Top Marking(Figure 10.1·10.5)은 주문코드(001/002/A01)와 무관하게 전부 "IQS323" 표기 하나뿐이고, "IQS3dd"/"IQS3ed" 마킹은 **DFN12 패키지에서만** 등장한다(§10.2.2, Figure 10.2~10.4가 "IQS323"/"IQS3dd"/"IQS3ed" 세 옵션을 나열). 이는 IQS3dd/IQS3ed가 패키지 종류(DFN12)에 결부된 별도 마킹 관행임을 보여줄 뿐, zzz(001/002/A01) 주문코드와의 등치를 성립시키지 않는다.
- §10.1의 "IQS323-00x refers to all versions with the Release UI, all package types and all bulk packaging options"(PDF p.38, 원문 2211~2214행)는 "00x"가 **Release UI 계열 주문코드 전체**(001·002)를 가리키는 축약 표기라는 것만 명시한다 — 이것 자체는 명확하지만, "00x = IQS3dd"라는 실리콘 명칭 등치와는 **다른 층위의 정의**다.

**결론**: 이 역시 추가 탐색으로 닫지 못했다. G1이 인용한 정황(A.7 "for IQS3dd"/A.8 "for IQS3ed"가 §10.2 패키지 마킹의 IQS3dd/IQS3ed와 이름이 일치)은 여전히 가장 강한 근거지만, 등치를 명시하는 단일 문장은 문서 전체에서 찾지 못했다.

### 판정 — 닫지 못함, G1의 [미확인] 유지가 타당함

두 매핑 모두 A.7/A.8·§10·Table 10.x·Appendix B를 추가로 뒤졌지만 닫는 데 실패했다. 이것은 탐색이 불충분해서가 아니라, 데이터시트가 실제로 이 두 명명 체계(주문코드 zzz ↔ 실리콘 명 IQS3dd/ed, 문서리비전 vX.Y ↔ 레지스터 Major/Minor)를 어느 한 문장에서도 등치시키지 않기 때문이라고 판단한다 — 각주 인용 패턴의 "의도적으로 보이는 부재"(매핑_1)와 두 이름 체계가 근본적으로 다른 두 개념(회로 마스크 리비전 vs. 논리적 오더코드)일 가능성(매핑_2)이 이 판단을 뒷받침한다.

## 반증시도_3 — C2 "비존재 레지스터 0xF0" 재검증 (§9 전체 주소표 대조)

### 원 주장 (C2 §2.1)

> "정의된 마지막 주소는 0xE1(Hardware ID, A.37)이며, 그 이후 0xE2~0xFF는 표에 어떤 행도 존재하지 않는다 ... 0xE2~0xFE(0xFF 제외) 중 0xF0을 선정한다."

### 반증 시도 — §9 Memory Map Register Descriptions 전문 재추출

`pdftotext -layout`로 §9(PDF p.34~37, 원문 2007~2176행) 전체를 다시 뽑아 표 전 항목을 처음부터 끝까지 순서대로 대조했다: `0x00-0x09`(Version)→`0x10~0x18`(System Info)→`0x20~0x25`(Release/Movement UI)→`0x30~0x39`/`0x40~0x49`/`0x50~0x59`(Sensor 0/1/2)→`0x60~0x64`/`0x70~0x74`/`0x80~0x84`(Channel 0/1/2)→`0x90~0x99`(Slider)→`0xA0~0xA6`(Gesture)→`0xB0~0xB4`(Filter Betas)→`0xC0~0xC5`(System Control)→`0xD0~0xD4`(General)→`0xE0~0xE1`(I2C Settings, Hardware ID) — 표는 **정확히 0xE1에서 끝나고** 바로 다음 줄에 "10 Ordering Information" 절이 시작된다(원문 2176~2182행). 표에 0xE2 이후 행은 **1건도 없다**.

더 강하게 반증해보려고, "표에 없을 뿐 다른 절에 흩어진 언급이 있지 않을까"를 가정하고 `0xE2`~`0xFF` **32개 값 전부**를 전체 68페이지 텍스트에서 개별 grep했다:

```
for hex in E2 E3 ... FE FF; do grep -n "0x$hex\b" iqs323_layout.txt; done
```

결과: 0xEE(§8.10 "invalid communication response", Appendix C 원문)와 0xFF(§8.9/§8.13의 종료·강제통신 커맨드) **단 두 개만** 문서 전체에 등장하며, **0xF0 자체는 68페이지 전체에서 단 한 번도 등장하지 않는다**(0건). 추가로 Azoteq 공식 예제 드라이버(`docs/참고/touch/iqs323-example-code/src/IQS323/inc/IQS323_addresses.h`)를 열어 매크로 정의를 끝까지 확인했다 — 마지막 정의가 `#define IQS323_MM_HARDWARE_ID 0xE1`(148행)이며 그 뒤에 0xE2 이후 매크로가 **전혀 없다**(코드 자체를 재확인, C2의 인용과 정확히 일치).

### 판정 — refuted=false

**반증 실패. C2의 원 주장은 유지된다.** §9 표 전체 재대조, 0xE2~0xFF 32개 값 전수 grep, 독립적인 Azoteq 공식 드라이버 헤더 재확인까지 세 가지 경로 전부에서 0xF0이 미매핑임이 재확인됐다. 단 C2 스스로도 §7 리스크 게이트 항목 4("0xE2~0xFE 구간이 정말 항상 0xEE를 반환하는지 [가설-강]")에서 밝혔듯, "문서화되지 않음"이 "미문서 부작용이 절대 없음"을 보장하지는 않는다 — 이 잔여 불확실성은 C2가 이미 투명하게 인정한 것이라 본 반증시도에서 새로 발견한 결함은 아니다.

## 반증시도_4 — C2 "tdc_touch_iqs323_mclr()는 이미 hard reset 가능 함수로 존재" 재검증

### 원 주장 (C2 §2.4)

> "기존 함수는 있다. `tdc_touch_iqs323_mclr()`(iqs323.c:474-481, 헤더 선언 iqs323.h:85)이 §6.6.3 Hardware Reset을 구현한다 ... 오늘 이 함수의 유일한 호출부는 `tdc_touch_init_begin()`(tdc_touch.c:184-188, 콜드 부팅 1회)뿐이다."

### 반증 시도 1 — 함수가 실제로 존재하고 코드가 일치하는가

`tdc_touch_iqs323.c` 474~481행을 직접 재확인했다.

```c
474  void tdc_touch_iqs323_mclr(void)
475  {
476      Sys_DIO_Config(TDC_TOUCH_IQS323_RDY_PIN, TDC_TOUCH_IQS323_RDY_PIN_CFG_OUTPUT);
477      Sys_GPIO_Set_Low(TDC_TOUCH_IQS323_RDY_PIN);
478      Sys_Delay(TDC_TOUCH_IQS323_DEFAULT_DELAY_MS * TDC_TOUCH_IQS323_MCLR_HOLD_MS);
479      Sys_DIO_Config(TDC_TOUCH_IQS323_RDY_PIN, TDC_TOUCH_IQS323_RDY_PIN_CFG_INPUT);
480      Sys_Delay(TDC_TOUCH_IQS323_DEFAULT_DELAY_MS * TDC_TOUCH_IQS323_BOOT_WAIT_MS);
481  }
```
헤더 선언은 `tdc_touch_iqs323.h` 85행에 정확히 존재하며, 84행 주석 "MCLR 하드리셋 (DIO16 OUTPUT->LOW->INPUT, 약 51ms 블로킹)"과 코드가 일치한다. C2가 인용한 라인 번호·내용이 100% 일치 — **반증 실패**.

### 반증 시도 2 — 이 함수가 정말 데이터시트의 "hard reset"인가, 아니면 이름만 그럴듯한 별개 동작인가

§6.6.3 Hardware Reset(PDF p.22, 원문 1329~1346행)을 재확인했다: "Pulling the Ready/Master Clear (RDY/MCLR) pin low will hard reset the device." 코드의 동작(DIO16을 OUTPUT으로 바꾸고 LOW로 구동 → 홀드 → INPUT 복귀)은 이 절이 요구하는 정확한 메커니즘과 일치한다 — 이름만 붙인 게 아니라 실제로 데이터시트가 정의하는 hard reset 절차를 구현한다. **반증 실패**.

### 반증 시도 3 — 호출부가 정말 유일한가 (C2의 "boot 전용" 서술 자체를 반증)

```
grep -rn "tdc_touch_iqs323_mclr" src/
```
전체 소스트리에서 호출부는 정확히 **1곳**뿐이다: `tdc_touch.c:185`. 그 문맥을 직접 확인했다.

```c
180  void tdc_touch_init_begin(void)
181  {
182      ci_printi("[TOUCH] INIT BEGIN \r\n");
183
184      SYS_WATCHDOG_REFRESH();
185      tdc_touch_iqs323_mclr();
186
187      s_mclr_done_tick = tdc_timer_get_t3_tick();
188      s_init_state     = TDC_TOUCH_INIT_MCLR_DONE;
189  }
```
`tdc_touch.h` 11행 주석 "POWER_ON 진입 시 1회 (MCLR 트리거)"와 정확히 일치하며, `tdc_touch_init_begin()` 자체의 호출부도 `initialize.c:448` 단 1곳(부팅 시퀀스)뿐임을 재확인했다. `s_init_state`가 `TDC_TOUCH_INIT_MCLR_DONE`으로 대입되는 곳도 코드 전체에서 188행 **1곳뿐**이다 — C2가 제안한 런타임 재사용 스니펫(§2.4)이 재현하려는 바로 그 상태다. C2의 "부팅 전용" 서술은 **반증 실패**(정확했다).

### 부수 확인 — C2가 스스로 인정한 잔여 위험(150µs 스위치오버)도 재확인

§6.6.3 후반(원문 1343~1346행): "The typical time for the switchover to be completed is 150 µs." — C2가 §2.4에서 인용한 수치와 정확히 일치한다. 또한 `mclr()` 코드에는 RDY가 이미 high(윈도우 닫힘)인지 확인하는 로직이 **없다**(무조건 OUTPUT 전환 후 LOW 구동) — C2가 §2.4에서 스스로 지적한 한계("`mclr()` 자체는 RDY-high 사전 확인이나 명시적 150µs 대기를 코드로 강제하지 않는다")도 코드 재확인으로 사실임을 검증했다. 이는 (d) 주장 자체("함수가 존재한다")를 반증하지 못하며, C2가 이미 투명하게 공개한 런타임 재사용 시 리스크임을 재확인한 것이다.

### 판정 — refuted=false

**반증 실패. C2의 원 주장은 유지된다.** 함수 존재·라인 번호·내용, §6.6.3과의 정합성, 유일 호출부라는 서술까지 세 갈래 모두 코드 재확인으로 뒷받침됐다.

## 부가발견_1 — G1의 Table 10.1 전사 오류 (주문코드 001/002 주소 뒤바뀜, A01 주소 "미확인" 오표기)

반증시도_2에서 §10/Table 10.x를 다시 파는 과정에 예정에 없던 오류를 하나 발견해 정직하게 보고한다. 이는 지시된 네 개 반증 대상 자체는 아니지만, 같은 자료(Table 10.1)를 다루는 G1·C1 두 문서의 신뢰도에 직접 영향을 준다.

G1 발견_4는 다음과 같이 서술한다:

> "데이터시트 Table 10.1 Ordering Code(PDF 38페이지, `pdftotext -layout` 2189~2198행)에 따르면 오더코드 "001"은 I2C 주소 0x58, "002"는 0x44(둘 다 Release UI, "00x" 계열), "A01"(Movement UI, "A0x" 계열)은 이 발췌 범위에서 주소가 확인되지 않았다[미확인]."

이를 재확인하기 위해 **G1이 인용한 바로 그 줄 범위**(2189~2198행)를 다시 열었다:

```
                                                                        I2 C address = 0x44.
                                                               001      3 button self capacitance with
                                                                        Release UI, configurable via I2 C.
                                                                        I2 C address = 0x58.
    DEFAULT CONFIGURATION                     zzz        =     002      3 button self capacitance with
                                                                        Release UI, configurable via I2 C.
                                                                        I2 C address = 0x44.
                                                               A01      3 button self capacitance with
                                                                        Movement UI, configurable via I2 C.
```

`pdftotext -bbox`로 각 단어의 y좌표를 대조한 결과, "I2C address = 0x44."(y≈201~212)는 바로 아래 "001"(y≈215~226) 행의 설명 앞부분이고, "I2C address = 0x58."(y≈244~255)은 "002"(y≈258~268) 행 앞부분이며, 두 번째 "I2C address = 0x44."(y≈287~297)는 "A01"(y≈300~311) 행 앞부분이다 — 즉 **001=0x44, 002=0x58, A01=0x44**이다. 이는 §8.2(PDF p.30)의 독립적인 예시 문장 "the primary address for IQS323-001 is 0x44 and its debug address is 0x45"로도 **표 대조 없이 그 자체로 재확인**된다.

G1은 001/002의 주소를 서로 뒤바꿔 적었고("001은 0x58", "002는 0x44" — 실제는 반대), A01의 주소가 "이 발췌 범위에서 확인되지 않았다"고 했으나 **바로 그 발췌 범위(2189~2198행) 안에 A01=0x44가 명시돼 있다** — 발췌 범위가 부족했던 게 아니라 같은 범위를 보고도 놓친 전사 실수다.

반면 C1(04_C1) §3.2 발견_2는 같은 표를 "001→0x44, 002→0x58, A01→0x44"로 정확히 옮겼다 — 오늘 재확인 결과 C1의 전사가 맞고 G1의 전사가 틀렸다.

**이 오류가 결론에 미치는 영향**: G1은 이 정황을 근거로 "현재 코드 주소 0x44는 정황상 00x 계열일 가능성이 높다"고 썼지만, 올바른 표에 따르면 0x44는 00x(001)와 A0x(A01) **양쪽에 똑같이 존재**하는 주소라 00x 쪽으로 기울 근거가 전혀 없다(1:1 완전 모호). 즉 정정 후에는 "실측이 필수"라는 G1·C1 공통의 최종 결론(그리고 반증시도_1에서 반증에 실패한 "SW-only 실측 가능" 주장의 실무적 필요성)은 오히려 더 강해지지, 약해지지 않는다 — G1의 최종 권고 자체를 뒤집는 오류는 아니고, 그 권고를 뒷받침하는 곁가지 서술 한 곳의 전사 실수다.

## 검증_1이 후속 단계에 남기는 권고

1. 반증시도_1·3·4는 모두 반증에 실패했으므로, G1·C2의 해당 스펙(진단 read 4종, `REG_ERRATA_PROBE 0xF0`, `mclr()` 재사용 플러밍)은 사실관계 층위에서 안정적인 토대로 취급해도 좋다고 판단한다.
2. 반증시도_2의 두 매핑은 데이터시트만으로는 원천적으로 닫을 수 없어 보인다 — 최종 확정은 문서 재독이 아니라 G1이 제안한 부팅 1회 실측(0x00/0x01/0x02/0xE1 read)으로만 가능하다는 점을 재확인했다. 후속 fan-in 합성 시 "추가 문헌 조사로 닫힐 여지가 있다"는 식으로 낙관하지 않도록 유의할 것을 권고한다.
3. 부가발견_1(Table 10.1 오독)은 G1 원문서의 발견_4 한 문단만 정정하면 되는 사안이며, G1·C1·C2 공통 결론("실측 필수")에는 영향이 없다 — 다만 fan-in 합성 문서가 G1의 발견_4를 그대로 인용한다면 정정된 주소(001=0x44, 002=0x58, A01=0x44)로 바로잡을 것을 권고한다.
