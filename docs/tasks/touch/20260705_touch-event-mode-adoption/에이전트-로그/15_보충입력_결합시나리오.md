# 15 · 보충 입력 — 결합 시나리오(Events+인터럽트) 정량 검증

**TL;DR**: 은수님이 "이벤트 모드 단독 도입도, 인터럽트 전환 단독도 지금과 별 차이 없어 보인다"는 정확한 지적을 하셨고, 이에 오케스트레이터가 "그럼 이벤트 모드로 유휴 시 RDY를 침묵시키고, 인터럽트로 유휴 시 폴링 자체를 끊는 결합 시나리오"를 별도로 정량 검증하기로 합의했다(은수님 확인: "응"). 본 라운드는 1차 딥다이브(01~14)에 이어 15번부터 번호를 이어간다.

## 배경 — 이 라운드가 필요한 이유

1차 딥다이브 결론(에이전트-로그 99_종합.md): 이벤트 모드 단독(방향 유지하나 크기 작음, 1.07~1.39배) 또는 인터럽트 전환 단독(Streaming 유지 시 IC가 여전히 자주 토글해 이득 미미)은 각각 "지금과 별 차이 없음". 그러나 **그라운드_2(02번 문서)의 트래픽 계산 모델 자체가 "SW는 100ms 고정 주기로 항상 폴링한다"는 전제를 그대로 유지**한 채 Streaming/Events의 조기반환 히트율만 비교했다 — 즉 "유휴 시 폴링 자체를 아예 안 한다"는 결합 시나리오는 이번 라운드 전까지 **정량화되지 않은 사각지대**였다.

## 핵심 질문 (이번 라운드가 판정할 것)

- **질문_1(치명적 우려)**: IQS323 Events(§8.12, 이미 1차에서 확인됨)는 터치 **진입/이탈 전이(edge)에만** 이벤트를 발생시키고, "유지 상태(steady touch)"에는 재발생하지 않는다. 그런데 Sound1의 롱터치(2400ms) 판정은 **"터치가 계속 유지되고 있는가"라는 레벨(level) 상태를 100ms마다 확인**하는 방식이다 — Events 기반 순수 인터럽트 구동으로 전환하면, 터치 유지 중 인터럽트가 더 이상 오지 않으므로 이 레벨 모니터링이 원리적으로 불가능해질 수 있다. 이게 진짜 문제인지, 아니면 회피 설계(터치 진입 이벤트 수신 시에만 활성 폴링으로 전환)가 가능한지 확정해야 한다.
- **질문_2**: 유휴(터치없음·ATI정상) 구간에서 폴링을 완전히 끊는 하이브리드 설계가 3거동(INV-CTRL-1~3)을 훼손하지 않는지.
- **질문_3**: 실사용 patterns(터치 활성 비율)을 가정했을 때 총 I2C 트래픽·강제개방 횟수가 실제로 얼마나 줄어드는지 정량 추정.
- **질문_4**: ATI 에러 감지가 인터럽트 기반으로 더 빨라지는지(현재는 최대 100ms 지연 후 감지, 이벤트 기반이면 즉시) — 이게 오히려 개선점인지.

## 코드 기준점 (1차 라운드에서 이미 확인된 것, 재확인 없이 사용 가능)

- `force_window_open()`/`wait_window_closed()`/`read_register()`/`write_register()` — `tdc_touch_iqs323.c:128~230`
