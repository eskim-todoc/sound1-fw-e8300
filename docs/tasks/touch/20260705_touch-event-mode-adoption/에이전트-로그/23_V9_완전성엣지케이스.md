# 검증_9 · 완전성·엣지케이스

**TL;DR**: 최우선 과제인 후보_7의 "노말모드 WFI 존재" 브레이스매칭 정정은 `main.c` 직접 재확인으로 사실로 확정한다(후보_6·후보_4의 "WFI 부재" 주장이 틀림). 더 중요하게, 그라운드_9와 후보_6이 제시한 RDY 게이트 삽입 위치가 서로 달라(경과시간 게이트 이전 vs 이후) 실제 구현 시 지연시간이 달라지는 신규 불일치를 발견했다 — 그라운드_9 방식을 그대로 따르면 후보_6이 주장하는 "즉시 감지" 이점이 사라진다. ATI active 중 유휴전환·부팅/절전 무시 구간·mclr() 타이밍은 코드·데이터시트 직접대조로 안전함을 확인했고, `fake_func_sleep()`은 ATI에러 카운터만 생존해 있어 후보_6의 "카운터 전부 죽음" 서술을 정정한다.

## 1. 최우선 사항 — 후보_7의 "노말모드 WFI 존재" 정정 검증

### 1.1 브레이스 매칭 직접 재현 — 정정이 사실임을 확정

`main.c`를 직접 읽고 중괄호 깊이를 라인별로 추적했다.

| 라인 | 내용 | 중괄호 깊이(들여쓰기로 교차확인) |
|---|---|---|
| 437 | `while (1)` | — |
| 438 | `{` | while 본문 시작(4칸 들여쓰기) |
| 439 | `if ((iterationFlag == true))` | 8칸 |
| 440 | `{` | if 본문 시작 |
| 452 | `powerButtonPushed = tdc_touch_process();` | 12칸, if 본문 내부 |
| 669 | `}  // 끝, iteration` | 8칸 — if 본문(440) 닫음 |
| 671~736 | `main_counter++;` 등 | 8칸 — **while 본문(438)에 속하되 if 본문 밖** |
| 737 | `SYS_WATCHDOG_REFRESH();` | 8칸 |
| 738 | `SYS_WAIT_FOR_INTERRUPT;` | 8칸 |
| 739 | `}  // 끝, while` | 4칸 — while(437/438) 닫음 |

들여쓰기(4칸=while 본문, 8칸=if 밖 while 본문, 12칸=if 안)가 정확히 일관되게 대응한다. **결론: `main.c:452`(`tdc_touch_process()` 호출)와 `main.c:738`(`SYS_WAIT_FOR_INTERRUPT`)은 문자 그대로 같은 `while(1)` 루프(437~739행) 안에 있다.** 후보_7 §5의 정정은 **사실로 확정**한다.

### 1.2 계보 추적 — 오류가 어떻게 전파됐는가

- **최초 출처(07_C4 §1.4)**: "그 루프 부근 738·801·891·1230행 WFI는 전부 다른 루프 소속임을 grep으로 확인" — **738행에 대해서는 이 주장이 틀렸다.** 801·891·1230행은 각각 `func_cradle_lid_closed_loop()`(748~808행, 자체 WFI 784~807행 별도 루프)·`fake_func_sleep()`(810~1031행, WFI 891행 별도 루프)·`func_sleep()`(1164~1252행, WFI 1230행 별도 루프)에 속해 **정말로 다른 함수의 다른 루프**가 맞다(본 노드 직접 재확인). 그러나 738행만은 452행과 **동일 함수(`func_normal()`) 동일 루프**다 — C4가 4개 라인번호를 뭉뚱그려 "전부 다른 루프"라 일반화하면서, 유일하게 같은 루프에 속하는 738행까지 함께 오분류했다.
- **전파(19_C6 §2.3)**: 후보_6은 이 주장을 재인용하면서 "본 노드가 main.c:437~460행 직접 재확인해 grep으로 해당 구간에 `SYS_WAIT_FOR_INTERRUPT` 0건임을 확인"이라고 **독자 재검증**을 시도했다. 그러나 재검증 범위를 437~460행으로 좁혀 놓았다 — 이 범위는 애초에 738행을 포함할 수 없는 구간이므로, "0건 확인"은 **사실이지만 원래 주장("메인 루프 전체에 WFI가 없다")을 반증하지 못하는 반쪽짜리 재확인**이었다. 후보_6은 이 결과를 "메인 루프에 WFI가 없다"는 원래(C4의) 결론으로 그대로 일반화했다(§2.3: "이는 오디오/DSP 실시간 처리에 영향을 주지 않는 가장 안전한 형태다"의 근거로 사용).
- **정정(20_C7 §5)**: 후보_7은 `main.c` 전체를 직접 읽고 브레이스 매칭으로 452행과 738행이 같은 루프임을 발견해 정정했다 — **본 노드가 독립적으로 전체 재현해 이 정정이 옳음을 확인했다.**

### 1.3 정정의 실질적 의미 — 후보_7의 표현보다는 약하게 봐야 한다

후보_7은 "이 정정은 후보_6·후보_7 본안 모두에게 유리한 방향이다"라고 결론지었으나, 본 노드는 이 이득을 **더 정밀하게 한정**해야 한다고 판단한다.

- `main.c:439`의 `iterationFlag`는 CFX(오디오 DSP) 구동 인터럽트가 매 사이클 set하는 플래그다(그라운드_9 §4.1, `driver_timmer.c` 주석 "CFX에서 일정주기의 인터럽트를 수신하여 타이머처럼 동작"). 이 tick은 100ms 폴링과 무관하게 훨씬 빠르다(그라운드_9 추정 ~1ms, [미확인]).
- 즉 `func_normal()`의 while(1) 루프는 **터치 이벤트 유무와 무관하게 이미 CFX/오디오 인터럽트에 의해 매우 빈번히(ms급) 깨어난다.** 738행의 WFI는 "이 빈번한 깨어남들 사이의 짧은 낮잠"일 뿐이며, DIO16을 이 WFI의 웨이크소스로 추가해도 **CPU가 깨어나는 빈도 자체는 이미 DIO16과 무관하게 ms급으로 정해져 있어 거의 달라지지 않는다.**
- 후보_6·7의 노말모드 설계는 애초에 이 WFI를 건드리지 않는다 — 설계가 손대는 것은 `tdc_touch_process()` 내부의 `if(activity_mode==IDLE)` 조기반환뿐이며, 이 조기반환은 WFI 유무와 무관하게 항상 동일하게 동작한다.

**정정된 결론**: 이 브레이스매칭 정정은 (1) "이 루프에 WFI를 처음 도입하는 것"이라는, C4가 우려했던 **좁은 의미의 리스크(실시간 처리와의 미검증 상호작용)를 제거**한다는 점에서는 유효하고 가치 있다. 그러나 (2) 노말모드 하이브리드 설계 자체의 CPU 수면 심도나 응답성에 실질적 이득을 더하지는 않는다 — 노말모드에서 이 설계의 가치는 전적으로 "I2C 트래픽을 스킵한다"는 데 있으며 이는 WFI 존재 여부와 무관하다. 후보_7의 "유리한 방향" 서술은 방향은 맞으나 실질 효과를 과장할 소지가 있다.

## 2. 신규 발견 — RDY 게이트 삽입 위치, 그라운드_9와 후보_6이 서로 다르다 (지연시간에 실질 영향)

이것은 과제가 명시한 (a)~(e) 항목 밖에서 본 노드가 그라운드_9·후보_6을 직접 대조하다 발견한 것이나, "설계가 놓친 엣지케이스"의 정중앙에 있는 문제라 최우선사항 바로 다음에 배치한다.

### 2.1 두 문서의 실제 서술 대조

**후보_6 §2.3** (원문 그대로): "삽입 지점은 `tdc_touch_process()`의 init-switch(276~292행) 이후, **폴링 게이팅(294~300행) 이전** 한 곳뿐이다"

```
(READY 상태, 294행 진입 직전)
if (activity_mode == IDLE) {
    if (!rdy_irq_check_and_clear()) { return false; }
    rdy_irq_disarm();
    activity_mode = ACTIVE;
    s_poll_tick_old = now - TDC_TOUCH_POLL_INTERVAL_MS;
}
/* --- 이하 294행부터 기존 코드 100% 불변 --- */
```

**그라운드_9 §3** (원문 그대로): "위치_1 | `tdc_touch.c` : `tdc_touch_process()` : **300행과 302행 사이**(301행, 현재 공백) | **기존 경과시간 게이트(296~300행) 통과 직후**, `read_status` 호출(305행) 직전... 기존 게이트(경과시간)와 신규 게이트(RDY)가 **AND로 결합되는 2단 게이트**가 된다."

이는 단순한 표현 차이가 아니라 **게이트 순서 자체가 반대**다 — 후보_6은 "RDY 체크 → (통과 시) 경과시간 체크", 그라운드_9는 "경과시간 체크 → (통과 시) RDY 체크"다.

### 2.2 실제 코드 트레이스로 차이의 결과를 검증

`tdc_touch_process()`는 `main.c:452`에서 `iterationFlag==true`일 때마다 호출된다(§1.3에서 확인한 대로 ~1ms급으로 추정). 두 배치를 각각 시뮬레이션한다.

```mermaid
sequenceDiagram
    participant Loop as iterationFlag tick(~1ms)
    participant A as 후보_6 배치(RDY 먼저)
    participant B as 그라운드_9 배치(경과시간 먼저)

    Note over A,B: 유휴 진입, RDY 이벤트가 +10ms 시점에 도착
    Loop->>A: 매 tick 호출
    Note over A: activity_mode==IDLE ? RDY 플래그를 매 tick(~1ms) 확인
    Loop->>B: 매 tick 호출
    Note over B: 296행 경과시간 게이트가 매 tick "100ms 안 지남" → 즉시 return false<br/>RDY 체크 코드(신규 301행)에 아예 도달 못함
    Note over A: +10ms 시점 다음 tick(~11ms)에 RDY 감지 → 즉시 ACTIVE 전환, 이번 tick에 read 강행(now 강제 보정)
    Note over B: s_poll_tick_old 는 이전 poll 이후 계속 갱신 안 됨(활성 전환 전까지) → 경과시간 게이트가 100ms 찰 때까지(~90ms 후) RDY 체크 자체가 실행되지 않음
    Note over A,B: 결과: 후보_6 배치 = 약 1~2ms 지연, 그라운드_9 배치 = 최대 ~100ms 지연(기존과 동일한 폴링 주기 재현)
```

**핵심 원인**: 그라운드_9의 배치는 296~300행(기존 경과시간 게이트)을 **활동모드와 무관하게 매번 그대로 통과시킨 뒤**, 300행에서 `s_poll_tick_old = now;`를 실행하고 나서야 신규 RDY 체크(301행)에 도달한다. 이 때문에 RDY 체크 자체가 "100ms에 한 번"이라는 **기존과 동일한 주기로 rate-limit**된다 — 인터럽트 인프라를 도입해 놓고도 그 확인 주기는 폴링 시절과 똑같아진다. 반면 후보_6의 배치는 활동모드가 IDLE이면 296~300행에 도달하기 전에 RDY를 먼저 확인하므로, 매 호출(빠른 iterationFlag tick)마다 즉시 확인된다.

### 2.3 이 불일치가 왜 결정에 영향을 주는가

후보_6 §4.2와 후보_7 §7(질문_4 답변)은 모두 "ATI 에러 감지가 **즉시**(사실상 인터럽트 지연 수준)로 개선된다"는 것을 이 설계의 핵심 이점 중 하나로 제시한다. **이 주장은 후보_6이 실제로 서술한 배치(RDY 먼저)에서만 성립하고, 그라운드_9가 제시한 "자연스러운 삽입 슬롯"(경과시간 먼저)을 그대로 따르면 성립하지 않는다** — 그 경우 유휴 중 이벤트 감지는 여전히 최대 100ms 지연될 수 있어, 사실상 §4.2/Q4가 명시적으로 부인한 "변형_1급 지연"과 다를 바 없어진다. 더 나쁜 것은, 그라운드_9 배치를 택하면 DIO16 인터럽트 인프라(2슬롯 제약·mclr 핀공유 시퀀싱·arm/disarm 레이스, 후보_6 §2.6이 인정한 리스크들)를 **그대로 짊어지면서도** 그 인프라가 주는 응답성 이득은 얻지 못하는, 순수하게 손해뿐인 조합이 된다는 점이다.

### 2.4 부가 — 후보_6 의사코드 자체의 사소한 스코프 결함

후보_6의 배치("294행 진입 직전")를 문자 그대로 구현하면, 그 블록 안의 `s_poll_tick_old = now - TDC_TOUCH_POLL_INTERVAL_MS;`가 참조하는 `now`는 **아직 선언되지 않은 변수**다(`int now = ci_timer_get_tick();`는 원래 295행, 즉 이 블록 "다음"에 위치). 이는 컴파일 에러 수준의 사소한 의사코드 결함이며(수정은 한 줄 — `ci_timer_get_tick()`을 그 블록 안에서 한 번 더 호출하거나 선언을 끌어올리면 됨), 설계의 정합성 자체를 해치지는 않는다. 다만 §2.3의 발견과 합쳐보면 "정확한 삽입 지점과 순서"는 어느 문서도 실제 diff 수준까지 완결하지 못했다는 뜻이며, 구현 단계에서 반드시 명시적으로 재확정해야 한다.

**판정**: 그라운드_9와 후보_6 어느 쪽도 "틀렸다"고 할 수는 없다 — 둘은 서로 다른 질문에 답했다(그라운드_9는 "기존 코드 구조상 삽입 가능한 지점이 어디냐", 후보_6은 "내 설계의 응답성 목표를 만족하는 지점이 어디냐"). 그러나 **이 둘을 대조 없이 그대로 구현에 옮기면 그라운드_9 쪽이 "더 깔끔해 보인다"는 이유로 채택될 위험이 있고, 그 경우 후보_6/7이 약속한 핵심 이점(즉시 감지)이 조용히 사라진다** — 이것이 본 노드가 발견한, 설계가 놓친 완전성 공백이다.

## 3. (a) ATI 진행 중(ati_active=1) 유휴 진입 / 유휴 중 ATI 시작

### 3.1 코드 확인 — 게이트가 이미 ati_active를 배제한다

`tdc_touch_logic.c:155~161`(Re-ATI 게이트)와 후보_6 §2.2(유휴 진입 게이트) 둘 다 `!ati_active`를 조건에 명시한다. `tdc_touch_logic.c` 전체를 재확인한 결과 `in->ati_active`는 155행(Re-ATI 게이트) **단 한 곳**에서만 참조되며, `stuck_eval()`(TOUCH 상태 전용)·롱터치 추적(TOUCH 상태 전용)에는 등장하지 않는다 — ATI 활성 여부가 다른 로직과 얽힐 여지가 코드 구조상 없다. **ATI 진행 중에는 유휴 진입 자체가 게이트에 의해 원천 차단된다** — 후보_6·7의 설계 그대로 안전하다.

### 3.2 데이터시트 원문 재확인 — "ATI Active"는 이벤트가 아니라 레벨 비트다 (본 노드 신규 발견)

A.2 System Status 비트별 원문(`/tmp/iqs323_v9.txt:2742~2749`)을 직접 대조했다.

| 비트 | 원문 서술 | 문법 유형 |
|---|---|---|
| 6 ATI Error | "0: No ATI Error occurred / 1: ATI Error occurred" | 발생(occurred) — edge |
| **5 ATI Active** | **"0: ATI not active / 1: ATI active"** | **상태(active) — level** |
| 4 ATI Event | "0: No ATI Event occurred / 1: ATI Event occurred" | 발생(occurred) — edge |

"System Flags" 바이트(bit7~0) 안에서 **bit5만 유일하게 "occurred" 문법이 아니라 "active" 문법**을 쓴다 — 그라운드_8이 이 바이트 전체를 "clear-on-read 이벤트 그룹"으로 일괄 서술한 것(§1.2)은 6개 비트에는 맞지만 **bit5에는 그대로 적용되지 않을 가능성**을 시사하는 단서다.

이를 뒷받침하는 독립 증거를 추가로 확인했다 — **Events Enable 레지스터(0xD3)에는 "ATI Active"에 대응하는 enable 비트가 아예 없다.** A.32(Release UI)·A.33(Movement UI) 양쪽 원문(`/tmp/iqs323_v9.txt:3664~3719`)을 대조한 결과, bit5는 두 order code 변형 모두에서 **"Reserved"**다(bit6 ATI Error·bit4 ATI Event·bit1 Touch Event만 실제 enable 비트 존재). 즉 **"ATI Active"는 RDY를 스스로 어서션할 수 있는 이벤트 후보 자체가 아니다** — §8.11.2의 "one or more of the enabled events" OR 조건에 참여할 자격이 원천적으로 없다.

추가로, 코드 자체가 이 레벨-비트 해석에 이미 의존하고 있다: `wait_ati_done_blocking()`(`tdc_touch_iqs323.c:328~342`)은 25회까지 50ms 간격으로 `read_register`를 반복 호출해 `ati_active==0`이 될 때까지 폴링한다 — 만약 이 비트가 read 시 clear되는 latch라면 ATI가 실제로 진행 중이어도 두 번째 read부터 항상 0으로 읽혀 "완료"를 오판했을 것이다. 이 코드가 (추정컨대 정상 동작해온) 것은 bit5가 **매 read마다 IC 내부 실시간 상태를 그대로 반영하는 레벨 비트**라는 방증이다.

**정확한 정밀도 표기**: 이 결론은 (i) 비트별 문법 차이, (ii) Events Enable에 대응 비트 부재, (iii) 기존 코드의 폴링 패턴 3가지 정황증거의 수렴이며, 데이터시트에 "bit5는 read해도 clear되지 않는다"는 **명시적 단일 문장은 없다** — 따라서 결론 자체는 고신뢰이나 **[일부 추론, 명문 확인 아님]**으로 표기한다.

### 3.3 유휴 중 ATI 자동 시작 — 놓치는 경로가 있는가

§5.10 원문("when a re-ati occurs the ATI Event bit... will be set")은 자동 Re-ATI가 **완료될 때마다** 무조건 ATI Event를 세팅한다고 읽힌다(§5.11도 "after the ATI has completed" 동일 시점). ATI Event(bit4)는 이미 enable(0x52)돼 있으므로, 유휴 중 자동 ATI가 시작되어 완료되면 반드시 RDY가 어서션되어 MCU를 깨운다 — **"시작"의 순간은 MCU가 보지 못해도(§3.2에서 확인했듯 그 순간엔 이벤트 신호가 없다), "완료"의 순간은 반드시 신호가 온다.** 이는 baseline(100ms 폴링)도 애초에 ATI 진행 중 하위 단계를 실시간으로 못 보는 것과 동일한 수준이라 **회귀가 아니다.**

레이스 하나가 남는다: 후보_6 §2.6의 arm-vs-check 패턴은 "GPIO 레벨 재확인(`Sys_GPIO_Read`) → 없으면 `Sys_DIO_IntConfig` 설정 → NVIC 활성화" 순서인데, **GPIO 재확인과 `Sys_DIO_IntConfig` 설정 사이에도 이론적으로 좁은 틈이 있다** — 그 틈에 걸쳐 발생하는 엣지가 벤더 DIO 주변장치에서 "설정 완료 전에는 pending으로 latch되지 않는" 방식이라면 놓칠 수 있다. 이는 §8.12의 "미해결 이벤트가 있으면 계속 재개방" 재시도 메커니즘(그라운드_8 §2.2, 간접추론)이 자연 치유해줄 개연성이 높으나, 재개방 정확한 주기가 [미확인]이고 이 재시도 자체가 그라운드_8의 간접 종합이라 **완전히 닫힌 문제는 아니다.** 벤더 SDK(`hw.h`, 저장소 밖) 확인 전까지 [미확인, 실측 게이트]로 남긴다.

**판정**: (a)는 상태전이가 꼬이는 시나리오를 찾지 못했다 — 게이트 설계가 이미 정확하고, "ATI Active"의 레벨-비트 성격이 오히려 이 안전성을 데이터시트 차원에서 뒷받침한다. 유일한 잔여 리스크는 §2.6 자체의 일반적 arm-vs-check 좁은 레이스이며 ATI 특유의 문제는 아니다.

## 4. (b) 부팅(boot_ignore)·절전(sleep_ignore) 무시 구간과 유휴 게이트 중첩

### 4.1 코드 확인 — 무시 구간은 구조적으로 항상 ACTIVE

`tdc_touch_logic.c:119~152`를 직접 재확인했다: `boot_ignore==true`인 동안 `tdc_touch_logic_step()`은 119행에서 즉시 분기해 Re-ATI 게이트(154행)·stuck 평가(163행)·롱터치 추적(172행)에 **도달하지 못하고 151행에서 return**한다. 후보_6의 유휴 진입 게이트가 `boot_ignore==false`를 명시 조건으로 요구하므로, `boot_ignore==true`인 한 유휴 전이 자체가 불가능하다 — **"무시 구간과 유휴 구간이 겹치는" 시나리오가 게이트 설계상 원천적으로 발생할 수 없다**(중첩이 아니라 상호배타).

`func_sleep()`의 `sleep_ignore`도 동일 패턴을 확인했다: `main.c:1172` `bool sleep_ignore = true;`가 **`func_sleep()` 호출 1회당 1회만 초기화**되고(주석 1171행 "매 iteration 재초기화 금지"), `tdc_touch_sleep_handle_notouch_gate()`(1095~1122행)가 `sleep_ignore==true`인 동안만 호출되어(1239~1246행 분기) 노터치 확정 전까지 게이트를 유지한다. 후보_6·7 모두 유휴 진입 게이트에 `sleep_ignore==false`를 요구하므로 동일하게 상호배타가 성립한다.

### 4.2 "정확히 그 폴링에서 즉시 유휴 전환" 이 안전한가 — 추가 디바운스 필요성 검토

boot_ignore/sleep_ignore가 해제되는 바로 그 폴링(3회 연속 not-pressed 확정 순간)에서 곧바로 유휴로 전환해도 되는지 검토했다. 결론: **문제없다.** 디바운스(3회 연속)는 "웨이크 제스처의 잔여 접촉을 노이즈로 오인하지 않기 위한 것"이며, 이미 3회 연속 확인이 완료된 시점이면 그 이후의 "터치 없음" 판정과 동등한 신뢰도를 갖는다 — 추가로 유휴 전환 전에 별도 안정화 기간을 더 요구할 근거가 없다. 또한 터치 재진입은 IC의 edge 기반 Touch Event가 자율 감지하므로(§8.11.2), 유휴 전환이 "한 폴링 이르다"고 해도 실제 터치를 놓치는 것은 아니다(그라운드_8 §5 확정 사실).

### 4.3 boot_ignore/sleep_ignore 재무장(re-arm) 가능성 확인

`tdc_touch_logic_set_boot_ignore()`의 호출부는 저장소 전체에서 `tdc_touch.c:175`(`try_finish_init()` 내부, READY 전이 시 1회) **단 한 곳**임을 grep으로 재확인했다 — boot_ignore는 부팅당 정확히 0회 또는 1회만 세팅되고 이후 재진입 경로가 없다. 반면 `sleep_ignore`는 `func_sleep()`의 지역변수라 **매 절전 사이클(func_normal→func_sleep 재호출마다) 자동으로 재무장**된다(1172행) — 이는 의도된 설계이며 후보_6·7의 게이트 서술과 일치한다.

**판정**: (b)는 설계가 이미 정확히 처리했다. 추가로 검토해볼 법한 "해제 즉시 유휴 전환이 너무 이르지 않은가"라는 질문도 근거 없음으로 기각한다.

## 5. (c) mclr()(하드리셋) 호출과 유휴 상태 전환의 타이밍 상호작용

### 5.1 호출 지점 유일성 재확인

```
grep -rn "tdc_touch_iqs323_mclr\|tdc_touch_init_begin" Cortex-M3-src/
```
결과: `tdc_touch_iqs323_mclr()`의 실행부 정의는 `tdc_touch_iqs323.c:474`, **호출부는 `tdc_touch.c:185`(`tdc_touch_init_begin()`) 단 1곳**. `tdc_touch_init_begin()`의 호출부는 **`initialize.c:448` 단 1곳**. 본 노드가 저장소 전체 대상으로 독립 재확인했다 — 런타임 중 재호출 경로 0건.

### 5.2 호출 순서 재확인

`initialize.c`를 grep한 결과, `Initialize()`(244행) 안에서 `ci_dio_configure_sleep()`(206행)·`ci_dio_configure_normal()`(265행)·`tdc_touch_init_begin()`(448행)이 이 순서로 등장한다(라인 순서 확인, 전체 제어흐름의 분기·루프까지 완독하지는 않아 **[직접 확인: 호출 라인 순서 / 미확인: 전체 제어흐름상 예외 분기 없음을 완전 배제]**). `tdc_touch_init_begin()`은 `mclr()`을 동기(블로킹, `Sys_Delay` 포함)로 호출하고 즉시 리턴한다(`tdc_touch.c:180~189`) — DIO 인터럽트 관련 두 설정 함수는 이보다 먼저 끝난다.

### 5.3 활동모드(activity_mode) 최초 도달 시점과 mclr() 사이의 거리

`tdc_touch_process()`는 `s_init_state`가 `TDC_TOUCH_INIT_READY`(276~292행 init switch)에 도달하기 전까지는 매번 즉시 return한다(`tdc_touch.c:277~292`). `TDC_TOUCH_INIT_READY`는 `try_finish_init()`(149~178행)이 (i) auto-ATI 완료 확인(또는 2500ms 타임아웃), (ii) `tdc_touch_iqs323_apply_settings()`(500행 아우르는 시퀀스, 내부에 `wait_ati_done_blocking()` 블로킹 대기 포함) 완료 후에만 세팅한다. 후보_6이 제안하는 `activity_mode`/`rdy_irq_arm()` 관련 신규 코드는 전부 이 READY 이후 구간(294행 이하)에 위치하므로, **mclr()(부팅 최초, 블로킹 완료)과 이 신규 코드의 최초 실행 사이에는 auto-ATI 완료 대기(최대 2500ms)+`apply_settings()` 전체 시퀀스라는 상당한 시간적 여유가 항상 확보된다.** 후보_6 §2.6의 주장("mclr() 실행보다 항상 논리적으로 한참 뒤")은 이 순서 확인으로 뒷받침된다.

### 5.4 더 근본적인 안전장치 — 리부트 경계가 상태를 통째로 지운다 (본 노드 추가 논거)

`TDC_TOUCH_ACT_MCLR` FSM 액션(`tdc_touch.c:400~406`, stuck stage2 초과 시)은 이름과 달리 `tdc_touch_iqs323_mclr()`을 직접 호출하지 않는다 — `SYS_WATCHDOG_RESET()`(CM3 전체 리부트)를 호출할 뿐이다. `main.c`의 다른 모든 재부팅 경로(ATI에러 7연속·롱터치 24사이클 등)도 전부 동일하게 `SYS_WATCHDOG_RESET()` 경유다. 즉 **실제 IQS323 `mclr()`가 실행되는 유일한 순간은 항상 "방금 전에 CM3 자체가 완전히 리부트된 직후"뿐이다.** CM3 리부트는 RAM을 재초기화하므로 `s_init_state`·`s_logic`·(신규) `activity_mode`·NVIC 인터럽트 설정(DIO_0_IRQn enable 여부 포함, ARM Cortex-M 계열 일반 리셋 동작 — [Sound1 특정 확인 아님, 일반 아키텍처 지식])이 전부 공장 초기값으로 되돌아간다. **따라서 "이전 세션의 유휴/활성 상태가 mclr() 실행과 겹친다"는 시나리오는 세션 경계(리부트) 자체가 상태를 지우기 때문에 구조적으로 존재할 수 없다** — 후보_6이 명시한 "부팅 시퀀스 내 순서"보다 한 단계 더 근본적인 이유다.

**판정**: (c)는 리스크가 없다. mclr()은 부팅 1회성·동기 호출이며, 신규 유휴/활성 로직이 실행되는 시점은 항상 그보다 한참 뒤이고, 설령 순서를 헷갈리게 짤 여지가 있더라도 리부트 경계가 모든 관련 상태를 초기화하므로 크로스세션 간섭이 원천 차단된다.

## 6. (d) BLE 프로파일링 경로(fake_func_sleep)에서 실제 동작

### 6.1 활성화 트리거 — 후보_7의 [미확인]을 해소

후보_7 §2.7·§9는 "`fake_func_sleep()`의 실제 활성화 트리거... [미확인] — 본 노드가 grep한 범위에서 세터 호출부를 찾지 못함"이라 명시했다. 본 노드가 `grep -rn "tdc_set_fake_op_mode"`를 직접 재실행한 결과:

```c
// tdc_remote_general_debug.c:160~183, gd_handle_op_mode_setting()
if (op_mode == 1)  // 절전 모드
    tdc_set_fake_op_mode(1);   // :169
else
    tdc_set_fake_op_mode(0);   // :174
```

**트리거는 BLE 원격 디버그 패킷(`packet->data[1]==1`)이다 — 이미 그라운드_9(§2.3)가 정확한 라인번호(`tdc_remote_general_debug.c:169`)까지 명시했던 사실과 정확히 일치한다.** 후보_7은 `tdc_get_fake_op_mode`(게터) 호출부만 grep했고 `tdc_set_fake_op_mode`(세터)는 검색하지 않아 이 사실을 놓쳤다 — 이는 15번 문서가 명시한 "그라운드_7~9 부재로 자체 그라운딩했다"는 방법론적 한계가 실제로 드러난 구체적 사례다. 지금 그라운드_9가 존재하는 시점에서 이 [미확인]은 **해소됐다.**

### 6.2 "fake"의 실제 의미 — 전력 측정이 아니라 BLE로 제어 가능한 로직 검증 하네스

`ci_fake_power_sleep()`(`ci_power.c:163~174`)과 `ci_power_sleep()`(176행~)을 직접 대조했다: 전자는 `SYS_FREQ_30M72`(정상 노말모드와 동일 풀클럭)를 유지하고, 후자는 `SYS_FREQ_2M56`으로 실제로 클럭을 낮춘다. **`fake_func_sleep()`은 전력을 낮추지 않는다** — CPU가 풀클럭으로 계속 돌기 때문에 RTT·BLE 통신이 절전 중에도 끊기지 않는다. 즉 이 경로의 목적은 "전력 프로파일링"이 아니라 **"실제 저전력 하드웨어 절전(및 그에 수반하는 리부트 탈출)을 거치지 않고, BLE로 원격 제어하며 절전 로직(터치 카운터·게이트)만 검증하는 하네스"**다.

### 6.3 카운터 생존 여부 — 후보_6의 "전부 죽음" 서술을 정정

`fake_func_sleep()`(810~1031행)을 재확인한 결과, 두 재부팅 카운터의 상태가 다르다.

| 카운터 | 코드 위치 | `SYS_WATCHDOG_RESET()` 상태 |
|---|---|---|
| `touch_cnt`(웨이크 제스처, 24사이클) | 1004~1019행 | **주석 처리됨**(`// SYS_WATCHDOG_RESET();`, 1011행) — 도달해도 무동작 |
| `ati_error_reboot_cnt`(ATI에러, 7연속) | 947~965행 | **활성**(953행 `SYS_WATCHDOG_RESET();`, 주석 없음) — 실제로 리부트 발생 |
| `tdc_get_fake_op_mode()==0` 감지(901~906행) | — | **활성**(905행) — BLE로 "노말모드로" 명령이 오면 즉시 리부트 |

후보_6 §2.7은 "적용하더라도 무해하지만(카운터가 죽어있어 로직 영향 없음)"이라고 서술했으나, 이는 **`touch_cnt`에 한해서만 맞고 `ati_error_reboot_cnt`에는 틀린 일반화다.** 이 카운터는 `tdc_touch_iqs323_re_ati()`를 실제로 호출하는(960행) INV-CTRL-2의 살아있는 3번째 사이트다 — 요구사항.md(:35)가 명시한 "노말/절전/fake 3사이트" 정의와 정확히 일치한다.

### 6.4 하이브리드 설계를 적용하지 않고 두면 — 기능은 안전하나 검증 사각지대가 생긴다

후보_6·7 모두 이 경로를 설계 적용 대상에서 제외했다. 본 노드가 검토한 결과:

- **기능적으로는 안전하다** — `force_window_open()`(`tdc_touch_iqs323.c:145~175`)은 RDY 레벨을 직접 읽어 열려있으면 생략, 아니면 강제개방하는 방식으로 Streaming/Events 어느 모드든 그대로 동작한다. Events 모드를 전역으로 채택해도 `fake_func_sleep()`을 건드리지 않으면 이 경로는 그저 "이득 없이 계속 폴링"할 뿐 오동작하지 않는다.
- **그러나 검증 사각지대가 생긴다** — `fake_func_sleep()`은 BLE로 원격 트리거해 절전 로직을 관찰하는 유일한 경로다. 이 경로를 하이브리드 설계에 맞춰 갱신하지 않으면, 향후 은수님이 이 BLE 커맨드로 새 유휴/활성 전환 거동을 확인하려 할 때 **여전히 구모드(100ms 상시 폴링)만 보이게 되어, 실제 배포될 `func_sleep()`의 거동과 이 하네스가 보여주는 거동이 서로 달라지는 조용한 괴리**가 발생한다. 후보_7 §2.7이 "향후 유지보수 부담"이라 표현한 것을 본 노드는 한 단계 더 구체화한다 — 이는 단순 유지보수 문제가 아니라, **이 설계 자체를 검증하는 데 쓰일 유일한 원격 하네스가 그 설계를 반영하지 못하는 상황**이다.

**판정**: (d)는 기능 안전은 확인되나, "카운터 전부 죽음"이라는 후보_6의 근거는 부정확했고(하나는 생존), 설계를 이 경로에 적용하지 않기로 한 결정은 향후 원격 검증 시 실제 배포 거동과 괴리를 낳을 수 있다는 점을 명시적 리스크로 남겨야 한다.

## 핵심 결론

1. **최우선 사항**: 후보_7의 "노말모드 WFI 존재" 브레이스매칭 정정은 `main.c` 직접 재현으로 **사실 확정**한다(452행·738행 동일 루프). C4의 원 주장과 후보_6의 재확인 모두 이 지점에서 틀렸다 — 후보_6은 재확인 범위(437~460행)가 애초에 738행을 포함할 수 없어 반쪽 검증이었다. 다만 이 정정의 실익은 "실시간 처리 미검증 리스크 제거"에 그치고, 노말모드 CPU 수면 심도 개선과는 무관하다(iterationFlag가 이미 ms급으로 CPU를 자주 깨움).
2. **신규 발견(최중요)**: 그라운드_9가 제시한 RDY 게이트 삽입 위치(경과시간 게이트 이후, 300~302행)와 후보_6이 실제로 설계한 위치(경과시간 게이트 이전, 294행 앞)는 게이트 순서가 반대이며, 코드 트레이스 시뮬레이션 결과 그라운드_9 방식을 그대로 구현하면 후보_6·7이 약속한 "즉시 감지" 이점이 사라지고 기존과 동일한 최대 100ms 지연이 재현된다. 구현 단계에서 반드시 후보_6의 배치(RDY 우선 확인)를 명시적으로 채택해야 하며, 그 의사코드의 `now` 변수 스코프 오류도 함께 수정해야 한다.
3. (a)~(c)는 코드·데이터시트 직접 대조 결과 상태전이 꼬임·타이밍 충돌이 발견되지 않았다 — 특히 "ATI Active" 비트가 Events Enable 레지스터에 대응 enable 비트가 없는 순수 레벨 비트라는 것은 두 order code 변형(A.32/A.33) 모두에서 확인한 신규 사실이며, 이것이 (a)의 안전성을 데이터시트 차원에서 뒷받침한다.
4. (d) `fake_func_sleep()`은 기능적으로는 안전하게 방치 가능하나, 후보_6의 "카운터가 죽어있다"는 일반화는 부정확하다 — `ati_error_reboot_cnt`(7연속 재부팅) 경로는 살아있는 INV-CTRL-2의 3번째 사이트다. 또한 후보_7이 [미확인]으로 남긴 활성화 트리거(BLE `packet->data[1]==1`→`tdc_touch_remote_general_debug.c:169`)는 그라운드_9가 이미 정확히 해소했던 사실이며, 본 노드가 grep으로 재확인했다 — 후보_7의 자체 그라운딩과 실제 그라운드_9 사이의 구체적 불일치 사례다.
5. 하이브리드 설계를 이 경로에 적용하지 않기로 한 결정은, 향후 이 설계를 BLE로 원격 검증하려 할 때 실제 배포 거동과 다른 결과를 보여줄 수 있다는 검증 사각지대를 남긴다 — 은수님 확인이 필요한 트레이드오프로 남긴다.
