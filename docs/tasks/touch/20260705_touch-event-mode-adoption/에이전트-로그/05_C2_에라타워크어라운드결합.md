# 후보_2 · Events 모드 + I2C Lock-Up 에라타 워크어라운드 결합 스펙

**TL;DR**: Events 모드에 부록C I2C Lock-Up 워크어라운드(비존재 레지스터 0xF0 read 후 0xEE 확인)를 결합한다. `write_register`/`read_register` 꼬리에 삽입하고, 기존 `mclr()` 하드리셋을 재사용하되 런타임 재진입용 latch를 신규로 더한다. 단 이 워크어라운드 자체가 force-comm 빈도를 100ms당 4→6회로 늘려 새로운 자기애그레서가 된다.

---

## 0. 결론 먼저

| 질문 | 답 |
|---|---|
| 비존재 레지스터 주소는? | **0xF0** (안전 구간 0xE2~0xFE 내에서 선정, §2.1) |
| 어느 함수에 삽입? | `write_register()` 꼬리 + `read_register()` 꼬리 (신규 공유 static 헬퍼 `lockup_probe()`). `read_debug()`는 의도적 제외 (§2.2·§4) |
| 기존 hard reset 함수 있는가? | 있다 — `tdc_touch_iqs323_mclr()`(iqs323.c:474-481). 단 지금은 **부팅 전용** 호출 경로뿐이라 런타임 재사용에는 신규 플러밍 필요 (§2.4) |
| 워크어라운드 자체가 자기애그레서 되는가? | 그렇다, 정량적으로 확인됨 — force-comm 횟수 100ms당 4→6회(+50%), read 경로 최악 지연 130ms→260ms(§4) |

## 1. Part A — Events 모드 전환분 (P3 계승, 재도출 없음)

본 후보는 Events 모드(0xC0 bit7) 전환 자체를 P3(`docs/tasks/touch/20260703_touch-heisenberg-sw-impl/에이전트-로그/04_P3_0xC0_bit7_RDY토글제거.md`)의 이미 검증된 스펙 그대로 채택한다. 재도출하지 않고 인용하는 이유: 동일 파일(`tdc_touch_iqs323.c`, 499줄)을 본 세션에서 직접 재독해 P3가 인용한 6개 라인(237·318·447·453·465·471) 전부가 **현재도 정확히 일치**함을 재확인했다(라인 드리프트 없음).

- 변경 5곳(237 ack_reset 제외): 318(`0x50→0xD0`) · 447(`0x54→0xD4`) · 453(`0x58→0xD8`) · 465(`0x54→0xD4`) · 471(`0x58→0xD8`). bit7(0x80)만 OR, Power Mode·CH timeout 비트는 불변.
- 순서 제약(§8.12 Reset Event bit clear 후 Events 진입, Events Enable 0xD3 선행)은 현재 시퀀스가 이미 만족 — 재배치 불요.

본 후보의 신규 기여는 **Part B**(에라타 워크어라운드)이며, Part A는 그 전제 조건으로만 인용한다.

## 2. Part B — 에라타 워크어라운드 스펙 (핵심 기여)

### 2.1 비존재 레지스터 주소 선정 (원문 직접 대조)

`iqs323_datasheet.pdf`를 `pdftotext -layout`으로 직접 추출해 §9 Memory Map 전체를 재확인했다(원문 p.35~37, 추출본 1행~181행 구간). 정의된 마지막 주소는 **0xE1**(Hardware ID, A.37)이며, 그 이후 **0xE2~0xFF는 표에 어떤 행도 존재하지 않는다** — Azoteq 공식 예제 드라이버(`IQS323_addresses.h`)의 주소 정의도 `IQS323_MM_HARDWARE_ID 0xE1`에서 끝나 동일하게 확인된다.

주의할 함정 두 가지(원문 대조로 확인):

1. **"Reserved" ≠ "존재하지 않음".** 0x00~0x09(Version details) 블록은 표에 명시적으로 존재하는 주소 범위이며, 그 안의 0x03~0x09는 부록 A.1에서 "Reserved"로만 표기된다(추출본 156행 부근) — 즉 **주소 자체는 존재**하고 내용만 예약값이다. §8.10(추출본 1815~1820행) "invalid communication response(0xEE)" 조건은 "host가 **존재하지 않는** memory map register를 read"이지, "reserved 필드를 read"가 아니다. 따라서 0x03·0x99(Slider Reserved) 같은 "예약이지만 매핑된" 주소를 고르면 0xEE가 보장되지 않아 워크어라운드가 무력화될 위험이 있다 — 0xE2 이후의 **표 자체에 행이 없는** 구간만 안전하다.
2. **0xFF는 제외해야 한다.** §8.9 Terminate Communication(Figure 8.1, 추출본 1792~1811행)과 §8.13 Force Communication(Figure 8.2, 추출본 1893~1924행)이 **동일한 와이어 패턴**("Setup to write / 0x44 + ACK / 0xFF + ACK")을 사용한다 — 즉 I2C 주소-단계 바이트로 0xFF를 쓰는 것은 "레지스터 0xFF를 읽어라"가 아니라 IQS323이 "통신 종료" 또는 "강제 통신 요청" 커맨드로 특별 해석하는 예약된 프로토콜 토큰이다(창이 열려있는지 닫혀있는지에 따라 IC가 둘 중 하나로 판단). 이 값을 프로브 주소로 쓰면 §8.10의 "존재하지 않는 레지스터" 경로를 타지 않고 프로토콜 커맨드로 소비되어, 워크어라운드 자체가 의도치 않게 창을 열거나 닫는 부작용을 낼 수 있다.

**결정**: 0xE2~0xFE(0xFF 제외, 총 29개 주소) 중 **0xF0**을 선정한다. 마지막 실재 레지스터(0xE1)로부터 15칸, 특수 커맨드(0xFF)로부터 15칸 떨어져 여유가 대칭적이고, 로그·코드 리뷰 시 0xEE(반환 기대값)와 시각적으로 혼동되지 않는다. 0xF0 자체가 유일한 정답은 아니며, 0xE2~0xFE 구간 내 다른 값으로 대체해도 안전성은 동일하다 — 구현 단계(④)에서 확정하면 된다.

```c
/* 부록 C Known Issues "I2C Lock Up" 워크어라운드용 비존재 레지스터.
 * §9 Memory Map 전체 주소표(0x00~0xE1)에 행이 없는 gap 중 하나(원문 p.35-37 직접 대조).
 * 0xFF는 제외 — §8.9/§8.13(Figure 8.1·8.2)이 공용으로 "0xFF write"를
 * end-communications / force-comm 커맨드로 쓰므로 register address로 쓰면 충돌한다. */
#define REG_ERRATA_PROBE 0xF0
```

### 2.2 삽입 위치 — 선택지 비교와 결정

파일 헤더 주석(`tdc_touch_iqs323.c:6-8`)이 명시한 계층 원칙("레이어 호출은 위에서 아래로만")을 기준으로 4개 배치안을 비교했다.

| 배치안 | 위치 | 판정 |
|---|---|---|
| 배치안_1 | `i2c_write()`/`i2c_read()` 내부(L0, 최하단) | **기각** — 이 두 함수가 프로브의 유일한 실행 수단이기도 해 무한재귀 방지용 우회 로직이 필요해지고, `read_register()` 안에서 개별 i2c_write/i2c_read 호출마다(주소단계·데이터단계 각각) 중복 발동해 배치안_3보다 트래픽이 더 나빠진다 |
| 배치안_2 | `force_window_open()`/`wait_window_closed()` 내부(L1) | **기각** — `force_window_open()`은 각 호출의 **맨 앞**에서 창을 여는 역할이라 "통신 끝"이라는 에라타 문구의 시점과 맞지 않고, 마찬가지로 무한재귀 문제가 생긴다 |
| 배치안_3 | `write_register()`/`read_register()` 꼬리(L2, 성공 경로만) | **채택** — 파일 헤더 주석이 "전부 이 함수 경유"라 명시한 유일한 초크포인트. 신규 L3/L4 호출부가 추가돼도 별도 계측 없이 자동 상속(§2.3 하단 상속 목록 참고) |
| 배치안_4 | `apply_settings()`/`read_status()` 등 상위 L3·L4 시퀀스 래퍼 1곳 | **기각(부분)** — 배치안_3보다 트래픽은 적지만(§4), 신규 함수가 추가될 때마다 각 작성자가 "여기도 프로브 호출을 잊지 말아야" 하는 암묵 규약에 의존해 유지보수 안전성이 낮다. 단, `read_debug()`(아래) 한 곳에 한해 예외적으로 배치안_4의 논리(제외)를 적용 |

**결정: 배치안_3.** `write_register()`/`read_register()` 성공 경로(각 함수의 마지막 `wait_window_closed()` 직후, `return true;` 직전)에 공유 static 헬퍼 `lockup_probe()`를 호출한다. 실패 경로(조기 `return false`)에는 삽입하지 않는다 — 근거: 부록C의 증상("모든 read byte가 상수 반환")은 **통신이 기계적으로는 성공**한 채 데이터만 오염되는 현상이라, `write_register()`/`read_register()`가 이미 `false`를 반환한 경우는 프로브가 검증하려는 상태와 다른 실패(윈도우 오픈 실패·I2C 자체 실패)이며 기존 read-fail 처리 경로(호출자의 재시도·카운터)가 이미 담당한다.

**`read_debug()` 명시적 제외**: 이 함수(iqs323.c:369-398)는 `read_register()`를 경유하지 않고 `force_window_open()`+`i2c_write`/`i2c_read`를 직접 호출하는 별도 4바이트 버스트 read라, 배치안_3을 그대로 적용하면 커버리지 공백이 생긴다. 그러나 의도적으로 제외를 권고한다 — 이유는 §4(자기애그레서 평가)에서 정량적으로 다룬다: `TDC_TOUCH_DEBUG_PRINT_ENABLE` 기본값 1(`tdc_touch_config.h:22`, 본 세션에서 직접 재확인)이라 `read_debug()`가 매 폴링 실행되는데, 여기에도 프로브를 걸면 100ms당 force-comm 횟수가 6회에서 8회로 한 번 더 늘어난다. `read_debug()`의 결과값(`counts`/`lta`)은 FSM 입력이 아닌 디버그 전용(`tdc_touch_iqs323.h:90-91` "FSM 입력 아님")이고, 같은 폴링 사이클에서 `read_status()`(→`read_register()`, 프로브 포함)가 항상 먼저 실행되므로(`tdc_touch.c:302-337` 순서), lock-up 발생 시 최악의 경우에도 다음 폴링 주기(≤100ms) 이내에 `read_status()` 쪽 프로브가 잡아낸다. 안전-critical 경로 없이 트래픽만 배로 느는 대가이므로 제외가 낫다고 판단했다 — 이 판단은 [가설-강]이며, §7 실측 게이트에 등재한다.

### 2.3 구체 코드 스펙

**신규 섹션 위치**: `force_window_open()` 종료(현재 175행) 직후, `write_register()` 시작(현재 180행) 이전 — 즉 "RDY 윈도우" 섹션과 "레지스터 helper" 섹션 사이에 신규 "에라타 워크어라운드" 섹션을 삽입한다. 이 위치를 고른 이유는 `lockup_probe()`가 L0(`i2c_write`/`i2c_read`)·L1(`force_window_open`/`wait_window_closed`)만 호출하고 그보다 위 계층은 일절 호출하지 않아, 헤더 주석의 "위에서 아래로만" 원칙을 그대로 지키기 때문이다.

```c
/* **********************************************************************
 * 에라타 워크어라운드 (데이터시트 부록 C "I2C Lock Up")
 * 매 통신 끝에 비존재 레지스터 1byte read, 0xEE 아니면 lock-up latch 세팅.
 * hard reset(mclr)은 여기서 직접 호출하지 않는다 — L2가 L4 공개 함수를
 * 호출하면 계층 역행이고, tdc_touch.c의 init 상태머신과 동기화되지 않은 채
 * IC만 리셋되면 설정이 초기화(POR 기본값)된 상태로 방치된다(§2.4). 대신
 * latch만 세팅해 상위(tdc_touch.c)가 재초기화 시퀀스를 정식으로 재진입하게 한다.
 */
static bool g_iqs323_lockup_latched = false;

static void lockup_probe(void)
{
    uint8_t reg = REG_ERRATA_PROBE;
    uint8_t val;

    if (!force_window_open())
    {
        return; /* 프로브 자체 실패 → 미확정 처리, 기존 read-fail 카운터가 별도 담당 */
    }
    if (!i2c_write(&reg, 1))
    {
        return;
    }
    wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);

    if (!force_window_open())
    {
        return;
    }
    if (!i2c_read(&val, 1))
    {
        return;
    }
    wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);

    if (val != 0xEE)
    {
        g_iqs323_lockup_latched = true;
        ci_printe("[TOUCH] I2C LOCK-UP SUSPECTED (probe=0x%02X, expect 0xEE) \r\n", val);
    }
}

bool tdc_touch_iqs323_is_lockup_detected(void)
{
    return g_iqs323_lockup_latched;
}

void tdc_touch_iqs323_clear_lockup(void)
{
    g_iqs323_lockup_latched = false;
}
```

**주의(구현 시 반드시 지킬 것)**: `lockup_probe()` 내부에서 절대로 `write_register()`/`read_register()`를 호출하면 안 된다(무한재귀 — 그 두 함수의 꼬리가 바로 `lockup_probe()`를 호출하므로). 반드시 `i2c_write`/`i2c_read`/`force_window_open`/`wait_window_closed`만 직접 호출한다.

**호출부 삽입 — `write_register()`** (현재 194~197행):
```c
    ci_printv("[TOUCH] WRITE 0x%02X: LSB=0x%02X MSB=0x%02X \r\n", addr, lsb, msb);
    wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
    lockup_probe(); /* ← 신규: 부록C 워크어라운드 */
    return true;
```

**호출부 삽입 — `read_register()`** (현재 226~229행):
```c
    *p_lsb = buf[0];
    *p_msb = buf[1];
    wait_window_closed(TDC_TOUCH_IQS323_MAX_WAIT_CLOSE_MS);
    lockup_probe(); /* ← 신규: 부록C 워크어라운드 */
    return true;
```

**자동 상속 확인**: 이 두 곳만 편집하면 `ack_reset()`(237, write_register 경유) · `sensor_setup()`(268·272·277) · `touch_settings()`/`public_touch_settings()`(289·297) · `events_enable()`(303) · `beta_power_settings()`(312~320, 8곳) · `apply_settings()` 직접 호출(423·437·447·453) · `tdc_touch_iqs323_re_ati()`(465) · `tdc_touch_iqs323_reseed()`(471) · `confirm_reset()`(246, 최대 10회 루프) · `wait_ati_done_blocking()`(334, 최대 25회 루프) · `tdc_touch_iqs323_read_status()`(353) 까지 총 20곳 이상이 코드 수정 없이 자동으로 커버리지를 얻는다 — 단일 초크포인트 배치의 핵심 이점이다.

**헤더 추가** (`tdc_touch_iqs323.h`, 기존 `tdc_touch_iqs323_set_ulp`/`clear_ulp`/`is_ulp` 선언부 인근):
```c
bool tdc_touch_iqs323_is_lockup_detected(void);
void tdc_touch_iqs323_clear_lockup(void);
```

**선택적 킬스위치** (`tdc_touch_config.h`, 기존 `TDC_TOUCH_DEBUG_PRINT_ENABLE`과 동일 패턴 — 이 파일 자체 취지가 "터치 빌드 토글"이라 자연스러운 위치):
```c
#ifndef TDC_TOUCH_IQS323_LOCKUP_ERRATA_ENABLE
#  define TDC_TOUCH_IQS323_LOCKUP_ERRATA_ENABLE 1
#endif
```
필수는 아니나, §7의 실측 게이트 항목들을 A/B로 검증하려면 컴파일 타임에 끄고 켤 수 있는 스위치가 있는 편이 유리하다.

### 2.4 Hard Reset 기존 함수 확인과 신규 플러밍

**기존 함수는 있다.** `tdc_touch_iqs323_mclr()`(iqs323.c:474-481, 헤더 선언 iqs323.h:85)이 §6.6.3 Hardware Reset을 구현한다 — RDY/MCLR 겸용 핀(DIO16)을 OUTPUT 전환→LOW 구동→홀드→INPUT 복귀 후 부팅 대기. 오늘 이 함수의 유일한 호출부는 `tdc_touch_init_begin()`(tdc_touch.c:184-188, 콜드 부팅 1회)뿐이다.

**그러나 "런타임에서 안전하게 재사용 가능한" 형태로는 없다.** 두 가지 이유:

1. **재초기화 미동기화**: `mclr()`을 `lockup_probe()`(L2 내부)에서 직접 호출하면 IC는 POR로 되돌아가 모든 애플리케이션 설정이 시작값으로 복귀한다(§6.6.1, 추출본 1310~1315행 "chip's settings revert to their start-up values"). 특히 Sensor0/1/2 Setup(0x30/0x40/0x50) POR 기본값이 **0x0101**(A.5 — CTx0+Enable Channel 모두 1)이라, CH1/CH2를 의도적으로 0x0000(disable)으로 꺼둔 현재 설정이 무효화되며 잠시나마 3채널 모두 활성 상태로 되돌아간다. Touch Threshold(0x62)도 POR 기본값 0x0000이라, 재초기화가 완료되기 전까지는 극도로 낮은 임계값 상태가 된다. 이 복구는 `tdc_touch.c`의 init 상태머신(`try_finish_init()` → `apply_settings()`)이 다시 돌아야 완결되는데, `lockup_probe()`가 IC만 리셋하고 `s_init_state`를 그대로 두면 상위 FSM은 계속 "READY" 상태로 착각한 채 미설정 IC를 읽게 된다. 따라서 **latch만 세우고 hard reset 실행 자체는 tdc_touch.c로 위임**하는 것이 맞다(§2.3에 이미 반영).
2. **§6.6.3 스위치오버 가정이 호출 시점에 따라 달라짐**: 원문(추출본 1341~1343행) "typical switchover time... 150 µs" — MCLR 기능이 복귀하려면 RDY 윈도우가 닫힌 후 150µs를 기다려야 하며, 그 전에 시도된 reset request는 무시된다(추출본 1332~1345행). 기존 유일한 호출부(`tdc_touch_init_begin()`)는 콜드 부팅 시점 — 아직 IC와 아무 통신도 없었으니 RDY가 안정적으로 idle(high)임을 안전하게 가정할 수 있다. 반면 본 스펙이 신규로 추가하는 런타임 호출(방금 lock-up을 검출한 **직후**)은 바로 직전에 프로브 자체의 `wait_window_closed()`가 실행된 시점이라 원칙적으로 150µs 여유가 필요하다. `tdc_touch_process()`가 다음에 호출되기까지는(메인 루프 스케줄링 지연, main.c:452) 최소 수 ms~수십 ms가 걸릴 것으로 보여 150µs 조건은 사실상 충족될 것으로 보이나, 이는 **실측하지 않은 추정([가설])**이며 `tdc_touch_iqs323_mclr()` 자체는 RDY-high 사전 확인이나 명시적 150µs 대기를 코드로 강제하지 않는다(원문 §6.6.3 권고 절차 3단계 중 ①·② 확인 없이 곧장 LOW를 구동). 배포 전 확인 또는 방어적으로 `mclr()`에 RDY-high 폴링을 추가하는 편을 권고하되, 이는 본 스펙의 필수 전제는 아니고 §7 실측 게이트에 등재한다.

**최소 신규 플러밍(`tdc_touch.c`)**: `tdc_touch_process()` 최상단(276행 `switch` 이전)에 삽입.

```c
bool tdc_touch_process(void)
{
    if (tdc_touch_iqs323_is_lockup_detected())
    {
        tdc_touch_iqs323_clear_lockup();
        ci_printe("[TOUCH] I2C LOCK-UP -> MCLR RE-INIT \r\n");
        tdc_touch_iqs323_mclr();
        s_mclr_done_tick = tdc_timer_get_t3_tick();
        s_init_state     = TDC_TOUCH_INIT_MCLR_DONE;
        return false;
    }

    /* --- init 상태머신 (READY 전) --- */
    switch (s_init_state)
    ...
```

이 4줄(`mclr()` + `s_mclr_done_tick` + `s_init_state` 대입)은 `tdc_touch_init_begin()`(180-189행)이 이미 쓰는 것과 **완전히 동일한 패턴**을 재사용한다 — 새 로직을 발명하지 않고 검증된 부팅 경로를 재진입시키는 방식이다. 이 재사용 덕분에 `try_finish_init()`의 기존 "누른 채 부팅 방어" 로직(tdc_touch.c:171-177, 첫 read에서 눌려있으면 해제까지 무시)도 **자동으로 재적용**된다 — 방금 원인 불명의 lock-up에서 회복한 직후 IC가 보고하는 눌림 상태를 곧바로 신뢰하지 않고 해제 엣지를 기다리는 것은 오히려 안전한 방향이라, INV-CTRL-3(첫 터치 해제 감지)이 약화되지 않고 그대로 재확인된다(§5).

**커버리지 밖(명시)**: `main.c`의 `func_sleep()`/`fake_func_sleep()`(908-996행 부근)은 `tdc_touch_process()`를 거치지 않고 `tdc_touch_iqs323_read_status()`/`_re_ati()`/`_reseed()`를 **직접** 호출한다(main.c:452는 이 함수들과 별도 호출 지점 — `tdc_touch_process()`는 main.c:452 한 곳에서만 호출됨을 grep으로 확인). 즉 절전 중 lock-up이 발생하면 `g_iqs323_lockup_latched`는 세팅되지만, 절전 루프가 그 latch를 확인하지 않으므로 **절전 모드가 끝나고 `tdc_touch_process()`가 다시 호출될 때까지 회복이 지연**된다. 이 경로를 마저 커버하려면 `func_sleep()`에도 동일 getter 확인을 추가해야 하나, 이는 main.c 절전 시퀀스 자체를 건드리는 별도 범위(다른 페르소나·후속 작업 영역)라 본 스펙에서는 **의도적으로 미포함**하고 공백으로 명시한다.

## 3. 결합 시 상호작용 — 왜 이 조합이 필요한가

V3(`13_V3_S3검증.md`)가 이미 직접 지적한 사실을 그대로 인용한다: Events 모드 단독 전환은 `force_window_open()`의 "RDY 이미 열림" 조기반환 분기가 이벤트-무발생 유휴 폴링에서 사실상 소멸해 **매 폴링 강제-오픈(0xFF)이 상시화**되며, 이것이 부록C "I2C Lock Up" 에라타가 스스로 지목한 위험 조건("§8.13 force communications 방법 사용 시 발생 가능성↑")과 **정확히 일치**한다(V3 §"신규 중대 위험" 인용). V3는 이 위험이 확인되기 전까지 Events 모드를 "저위험" 분류할 근거가 없다고 결론지었다.

본 후보(C2)는 이 V3의 발견에 대한 직접 응답이다 — Events 모드가 유발하는 force-comm 증가를 되돌리지 않은 채로(되돌리면 P3의 원래 목표, 즉 RDY 상시 토글 제거 자체가 무산된다), 그 증가된 위험을 정면으로 완화하는 **감지·복구 계층**을 얹는 조합이다. 즉:

- Events 모드가 없으면 → 에라타 워크어라운드의 필요성이 낮다(현재 Streaming 상태에서는 IC 자가토글 덕에 force-comm 빈도가 낮을 것으로 추정 — [가설-강, 미실측]).
- 에라타 워크어라운드가 없으면 → Events 모드 전환이 V3가 지적한 미검토 위험을 그대로 안은 채 배포된다.
- 두 개를 결합하면 → Events 모드의 이득(RDY 상시 토글 제거)을 유지하면서, 그로 인해 커진 lock-up 가능성을 최소한 **감지 가능**하게 만든다(사전 차단은 아니다 — 워크어라운드는 예방책이 아니라 발생 후 자동 복구 메커니즘이다).

단, 이 결합이 "공짜"는 아니다 — §4에서 정량화하듯, 에라타 워크어라운드 자체도 force-comm을 추가로 소모하므로, Events 모드가 이미 올려놓은 force-comm 빈도를 **또 한 번** 올린다. 이 이중 상승효과가 본 결합안의 핵심 트레이드오프다.

## 4. 자기애그레서 가능성 평가 (트래픽·지연 정량화)

### 4.1 force-comm(0xFF 강제개방) 호출 횟수 — 100ms 유휴 폴링 1회당

| 시나리오 | force_window_open 호출 수(최악값) | 근거 |
|---|---|---|
| 현재(Streaming, 워크어라운드 없음) | [가설-강, 미실측] IC 자가토글로 "이미 열림" 히트가 잦아 낮을 것으로 추정 | S3 §해당 서술, 실측 안 됨 |
| Events 단독(C1/P3) | **4회** | V3 직접 인용(`read_status` 2 + `read_debug` 2, `TDC_TOUCH_DEBUG_PRINT_ENABLE` 기본 1 — 본 세션에서 `tdc_touch_config.h:22` 직접 재확인) |
| **Events + 에라타(본 후보, read_debug 제외)** | **6회** | 4(기존) + 2(`read_status`→`read_register` 꼬리의 `lockup_probe` 자체가 2단계) |
| Events + 에라타(read_debug까지 포함 — 기각안) | 8회 | 4 + 2(read_status 프로브) + 2(read_debug 프로브) |

**+50%** — 본 후보가 채택한 배치(read_debug 제외)만으로도 V3가 이미 "미검토 중대 위험"으로 지목한 4회 기준에서 6회로 늘어난다. `read_debug`까지 포함했다면 +100%였을 것이므로, §2.2의 제외 결정은 이 수치를 정확히 절반으로 억제하는 효과가 있다.

### 4.2 최악 지연 (파일 자체 상수 기반 산출, 실측 아님)

`TDC_TOUCH_IQS323_MAX_WAIT_OPEN_MS=45`·`MAX_WAIT_CLOSE_MS=20`(iqs323.h:32-33, 본 세션 직접 확인)으로부터 1개 "단계"(force_window_open+전송+wait_window_closed)의 최악 소요시간은 **65ms**(45+20, i2c_write/i2c_read 자체 전송시간은 별도 미보증분 — [미확인]).

| 함수 | 기존 단계 수 | 기존 최악(ms) | 워크어라운드 추가 후 단계 수 | 추가 후 최악(ms) |
|---|---|---|---|---|
| `write_register()` | 1 | ≤65 | 1+2=3 | ≤195 |
| `read_register()` | 2 | ≤130 | 2+2=4 | ≤260 |

100ms 폴링 주기(`TDC_TOUCH_POLL_INTERVAL_MS`, tdc_touch_time.h:18) 자체보다 최악값이 이미 초과한다는 점은 워크어라운드 유무와 무관하게 **기존에도 성립하던 사실**(130ms>100ms)이나, 워크어라운드 추가로 그 초과폭이 커진다(260ms, 주기의 2.6배)는 점은 본 결합안이 새로 만드는 조건이다. 다만 이는 **이론적 상한**이며 실제 관측치(전형적 케이스)는 [미확인] — force-comm 응답이 t_wait 범위(0.1~45ms, §8.13) 하단에 가깝다면 체감 영향은 훨씬 작을 수 있다.

### 4.3 물리적 자기애그레서 관점

`docs/참고/touch/터치 계측 관측 교란/터치 계측 관측 교란.md`가 정리한 3대 메커니즘(결합 임피던스·샘플링 윈도우 일치·에일리어싱) 관점에서, force-comm은 RDY/MCLR 핀(DIO16)과 I2C SDA/SCL 라인의 스위칭 활동이다. §4.1의 힌트대로 force-comm 횟수가 늘면 이 라인들의 토글 빈도가 늘어나고, 그만큼 "샘플링 윈도우 안에 애그레서 엣지가 떨어질" 기회(메커니즘_2)도 늘어난다. DIO16-CRX0 간 실제 PCB 결합도는 이 세션에서도 **[미확인]**(S3·V3와 동일하게 미해결 이월)이라 정량적 영향(카운트 오염량)까지는 산출할 수 없으나, 정성적으로는 "에라타를 잡으려고 늘린 통신이 정확히 그 에라타를 유발한다고 알려진 바로 그 행위(force-comm)를 늘린다"는 순환적 긴장이 성립한다.

이 긴장은 본 결합안을 무효화하지는 않는다 — 데이터시트 자체가 이 워크어라운드를 공식 권고하므로(제조사도 이 트레이드오프를 알면서 권고), 건강한 IC에서 프로브가 실패할 확률은 매우 낮고(§2.1에서 논증한 대로 0xE2~0xFE는 §8.10에 의해 결정론적으로 0xEE를 반환) 실제 발생 비용은 "가끔 있는 추가 65~130ms 지연"에 그친다. 그러나 **"자기애그레서가 되는가?"라는 질문에는 "그렇다, 정량적으로"가 정직한 답**이며, 배포 전 다음 실측으로 크기를 확정해야 한다(§7).

## 5. 불변식(INV-CTRL) 회귀 체크

| 불변식 | 판정 | 근거 |
|---|---|---|
| INV-CTRL-1 (Full ATI 유지) | 무손상 | `lockup_probe()`는 0x36(ATI Setup)에 관여하지 않음. lock-up 오탐으로 재초기화가 트리거돼도 `apply_settings()`가 매번 0x36=0x040C(Full)를 재적용하므로 오히려 자기치유적 |
| INV-CTRL-2 (ATI 에러→Re-ATI) | 무손상 | 본 스펙은 `tdc_touch_logic`의 ATI 에러 판정 로직에 전혀 접촉하지 않음 |
| INV-CTRL-3 (첫 터치 해제 감지) | 무손상~강화 | §2.4에서 논증 — 재진입 경로가 `try_finish_init()`의 기존 "부팅 터치 무시" 게이트를 자동 재사용해, lock-up 복구 직후에도 해제 엣지 확인 전까지 눌림 상태를 신뢰하지 않음 |
| (참고) P3 기존 위험 §4.3 롱터치 재부팅 카운터 | **주의, 본 결합으로 완화 방향** | P3가 지적한 "read 실패 시 카운터 즉시 0 리셋"은 `ok=false` 경로에서만 발동하는데, lock-up은 `ok=true`(기계적 성공, 데이터만 오염)로 나타나므로 이 카운터 자체는 lock-up에 영향받지 않는다 — 다만 lock-up 중 오염된 `pressed` 비트가 우연히 계속 1을 유지하면 카운터가 오히려 "정상 롱터치"로 잘못 누적될 가능성은 남는다([가설], §7 등재) |

## 6. 커버리지 한계·미해결 항목 (정직하게 명시)

1. `read_debug()` 미계측(§2.2) — 의도적 제외, 잔여 리스크는 같은 폴링 주기 내 `read_status()` 프로브가 대개 커버.
2. `func_sleep()`/`fake_func_sleep()`(main.c) 경로 미계측(§2.4) — `tdc_touch_process()`를 거치지 않는 절전 전용 직접 호출 경로라 latch를 확인하지 않음. 본 스펙 범위 밖으로 명시.
3. `tdc_touch_iqs323_mclr()`의 §6.6.3 스위치오버(150µs) 사전 확인 부재 — 런타임 재사용 시 새로 노출되는 조건이나 자체 검증은 미실시([가설]).
4. 프로브 실패(윈도우 오픈 실패 등) 시 미확정 처리 — lock-up도 아니고 정상도 아닌 상태를 "정상"과 동일하게 취급(latch 미세팅). 보수적으로는 반대(프로브 실패=lock-up 의심)로 처리하는 대안도 있으나, 기존 read-fail 경로와의 중복 트리거를 피하기 위해 본 스펙은 전자를 택했다 — 이 판단 자체가 [가설], 재검토 여지 있음.

## 7. 리스크 · 실측 게이트 (우선순위순)

| 순위 | 항목 | 상태 | 게이트 |
|---|---|---|---|
| 1 | §4 force-comm 횟수 100ms당 4→6회(+50%) 증가가 실제 lock-up 유발 확률에 미치는 영향 | [가설-강] | 배포 전 보드 실측 IC 버전(0x00~0x02, 0xE1) 확인 후(G1 영역), 장시간 스트레스 테스트로 lock-up 발생 빈도 전·후 비교 |
| 2 | `read_register()`/`write_register()` 최악 지연 130→260ms·65→195ms이 실사용 폴링에 미치는 체감 영향 | [미확인] | RTT 타임스탬프로 실제 소요시간 분포 측정(이론 상한이 아닌 전형값) |
| 3 | `tdc_touch_iqs323_mclr()` 런타임 재호출 시 150µs 스위치오버 조건 실제 충족 여부 | [가설] | 오실로스코프로 RDY/MCLR 핀 전압 시퀀스 확인, 필요 시 `mclr()`에 RDY-high 폴링 추가 |
| 4 | lock-up 오탐(false positive) 발생 빈도 — 0xE2~0xFE 구간이 정말 항상 0xEE를 반환하는지 | [가설-강, 데이터시트 §8.10 근거 강함] | 정상 동작 중 프로브 값 장시간 로깅, 0xEE 이외 값 발생 빈도 확인 |
| 5 | §6 항목 2(func_sleep 경로 미계측) 잔여 위험의 실제 크기 | [미확인] | 절전 중 lock-up 재현 시나리오 실측(난이도 높음 — 우선순위 낮게 유지) |
| 6 | 현재 실장 IC가 에라타 적용 버전(00x v1.3 이하 / A0x v1.4 이하)에 해당하는지 | [미확인, G1 영역과 중복] | Hardware ID(0xE1)·Major/Minor Version(0x01/0x02) 실측 — 본 워크어라운드는 미해당 버전에서도 안전(§4.3 결정론적 0xEE)하므로 필수 전제조건은 아니나, 비용 대비 편익 판단에는 필요 |

## 핵심 결론

1. 비존재 레지스터로 **0xF0**을 선정한다 — §9 주소표 전 구간(0x00~0xE1) 원문 대조로 미매핑 확인, 0xFF는 §8.9/§8.13 공용 프로토콜 커맨드라 별도 제외.
2. 삽입 위치는 `write_register()`/`read_register()` 성공 경로 꼬리(신규 공유 static `lockup_probe()`) — 파일의 유일한 초크포인트라 20곳 이상의 기존 호출부가 자동 상속받는다. `read_debug()`는 트래픽 절감을 위해 의도적으로 제외한다.
3. IQS323 hard reset 함수는 이미 존재한다(`tdc_touch_iqs323_mclr()`). 다만 지금은 부팅 전용이라, 런타임 lock-up 검출 후 안전히 재사용하려면 latch(`g_iqs323_lockup_latched`)+getter/clear 공개 함수+`tdc_touch_process()` 최상단의 재진입 로직(기존 `tdc_touch_init_begin()` 패턴 재사용) 4줄 추가가 필요하다.
4. 이 워크어라운드는 스스로도 자기애그레서가 된다 — 100ms 유휴 폴링당 force-comm 횟수가 V3 기존 발견(4회) 대비 6회(+50%)로 늘고, read 경로 최악 지연이 130ms에서 260ms로 늘어난다. 데이터시트가 공식 권고하는 조치이고 정상 IC에서는 결정론적으로 무해(§8.10)하지만, "잡으려는 에라타를 유발한다고 알려진 바로 그 행위(force-comm)를 늘린다"는 순환적 긴장은 정직하게 인정하고 §7의 실측 게이트로 관리해야 한다.
