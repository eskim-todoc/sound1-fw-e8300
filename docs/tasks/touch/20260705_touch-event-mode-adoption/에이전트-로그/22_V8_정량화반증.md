# 검증_8 · 후보_6·후보_7 트래픽 절감 정량화 반증

**TL;DR**: 후보_6·후보_7의 핵심 수치(98.6~98.9%/99.9%+ 감소, duty 1%에서 10.9~20.8배·50%에서 1.1~1.2배 잔존)를 파이썬으로 전부 재계산한 결과 산술 오류는 0건이며 그라운드_2·검증_2 모델과도 정합한다. 다만 (a) 후보_6의 자체 그라운딩 일부가 실제 그라운드_9와 삽입위치가 다르고 "CPU를 재우지 않는다"는 부수주장은 코드 직접 재확인 결과 틀렸다(트래픽 수치엔 무영향), (b) 이 프로젝트 자체의 선행 UX 분석(2026-06-15, maturity:stable)이 "간접 접촉 빈도 높음(안경·헤어·베개, 안경다리 마찰 수초 지속)"을 이미 문서화했음에도 두 후보 모두 이 채널을 duty 가정에 반영하지 않아, 실사용 duty가 "보수적 1%"보다 높을 가능성을 배제하기 어렵다 — 이 경우 후보_6의 절대우위는 유지되나 후보_7 대비 상대우위(10.9~20.8배)는 후보_7 자신의 표에 따라 2~3배 수준까지 좁혀질 수 있다.

**핵심 발견(방향성 확인)**: "8"이라는 값은 검증_2가 보정 작업(§1.3)을 거친 뒤에도 **변경하지 않고 그대로 승인**한 값이다 — 그 이유는 Events 유휴(무이벤트) 상태는 RDY 자연토글이 원리적으로 0건(§8.11.2 원문)이라 T_주기 불확실성이 개입할 여지 자체가 없기 때문이다. 즉 후보_6·7의 ACTIVE 비용(8) 가정은 baseline 비용(5.77~7.49, T_주기 불확실성에 노출)보다 **오히려 더 확실한 수치**다 — 반증 시도 결과 이 점에서는 두 후보의 모델링이 그라운드_2·검증_2보다 약해지는 지점이 아니라 강해지는 지점임을 확인했다.

또한 후보_6이 웨이크 직후 첫 폴링의 조기반환 가능성(§5.2 NOTE)을 알고도 "8"을 낮추지 않고 보수적으로 유지한 점, T_주기 전 구간(5%도 포함)을 사용한 점 모두 **결과를 유리하게 왜곡하지 않는 방향의 선택**이었음을 확인했다 — 반증 시도가 오히려 후보_6·7의 방법론적 정직성을 재확인해 준 셈이다.

## 5. 자체 그라운딩 대 실제 그라운드_7~9 교차검증

15번 문서는 그라운드_7~9(16~18번)를 반영하라 지시했으나 병렬 실행 구조상 후보_6·7 작업 착수 시점엔 해당 파일이 없어 두 후보 모두 자체 그라운딩을 수행했다(후보_6 §0 명시, 후보_7 §0 명시). 이제 실제 16~18번 문서가 존재하므로 대조한 결과는 다음과 같다.

### 발견_1 — RDY 게이트 삽입 위치 불일치 (후보_6 vs 실제 그라운드_9)

후보_6 §2.3은 "삽입 지점은... 폴링 게이팅(294~300행) **이전** 한 곳뿐이다 — 그라운드_9 질문에 대한 직접 답이다: 있다, 정확히 한 곳"이라 명시하고, 실제 pseudo-code도 294행 진입 **직전**에 IDLE 체크를 둔다.

그러나 실제 그라운드_9(`18_G9_...md` §3)는 "위치_1: `tdc_touch.c:tdc_touch_process()`: **300행과 302행 사이**(301행)... **기존 경과시간 게이트(296~300행) 통과 직후**, read_status 호출(305행) 직전"이라고 명시한다 — 즉 실제 그라운드_9는 시간 게이트 **이후**를 지목했는데, 후보_6은 시간 게이트 **이전**을 택했다.

**영향 평가**: I2C 트래픽 수치(본 검증의 핵심 대상)에는 영향이 없다 — 어느 위치든 IDLE 상태에서 `read_status` 호출 자체가 스킵되므로 트랜잭션 카운트는 동일하다. 다만 CPU 사이클 비용 차원에서는 차이가 있다: 후보_6의 배치는 그라운드_9가 확인한 더 빠른 외곽 tick(iterationFlag, ~1ms 추정)마다 IDLE 플래그를 체크하지만, 그라운드_9의 배치는 100ms 경과시간 게이트에 편승해 체크 빈도를 10배 이상 낮춘다. 따라서 "그라운드_9 질문에 대한 직접 답이다"라는 후보_6의 자체 평가는 **부정확하다** — 실제로는 그라운드_9가 제시한 것과 다른 위치를 택했다. (트래픽 정량 결론에는 영향 없음, 검증_7·검증_9 소관 사항일 수 있어 병기.)

### 발견_2 — ATI 에러 재평가 메커니즘(후보_6 §3.3)은 그라운드_8이 직접 다루지 않음

후보_6 §3.3은 "재시도마다 새 ATI 완료가 일어나 ati_error가 재평가되어 RDY를 다시 assert한다"(§5.11 인용)를 자체 그라운딩으로 제시했다. 실제 그라운드_8(`17_G8_...md`)은 §3.2에서 **다른** 메커니즘(§5.10 자동 Re-ATI의 LTA 동결 억제)을 다루었을 뿐, §5.11(완료 시마다 재평가되는 ATI Error) 자체나 "수동 `re_ati()` 호출도 매번 새 완료로 재평가되는지"는 다루지 않았다 — 이 하위주장은 **그라운드_7·8·9 어디에서도 교차검증되지 않은 채로 남아있다**.

**영향 평가**: 다행히 이 주장은 트래픽 모델에 실질적으로 하중을 지지 않는다 — ACTIVE 상태의 폴링(및 그에 따른 8/사이클 비용)은 §2.4~2.5에 따라 100ms HW 타이머가 무조건 구동하므로, ati_error 재평가가 RDY를 실제로 재assert하는지 여부와 무관하게 재시도 루프는 계속 폴링된다. 따라서 이 [미확인] 항목은 존재하나 저위험이다.

### 발견_3 — 후보_6·후보_7 상호 간 "노말모드 WFI 존재 여부" 모순 (코드 직접 재확인으로 해소)

후보_6 §2.3: "본 노드가 main.c:437~460행 직접 재확인해... `SYS_WAIT_FOR_INTERRUPT` 0건임을 확인" → "노말 모드에서는 CPU를 재우지 않는다"
후보_7 §5: "main.c:452와 main.c:738이 **동일한 while(1) 루프**(437~739행) 안에 있다... 이미 WFI를 호출한다" → 07_C4·후보_6 계열의 "WFI 없음" 주장을 정정

본 노드가 `main.c`를 직접 Read해 재확인한 결과(437행 `while(1)` 시작 ~ 739행 `}` 종료까지 중괄호 깊이 추적, 738행 `SYS_WAIT_FOR_INTERRUPT;` 직접 확인):

> [!IMPORTANT]
> **후보_7의 주장이 코드와 정확히 일치한다.** main.c:452(`tdc_touch_process()`)와 main.c:738(`SYS_WAIT_FOR_INTERRUPT`)은 동일한 `while(1)` 루프 안에 있다. 후보_6의 "437~460행에 WFI 0건"이라는 **좁은 범위 확인 자체는 사실**이나(그 구간엔 실제로 없음), 이로부터 "노말 모드에서는 CPU를 재우지 않는다"고 일반화한 것은 **틀렸다** — 같은 루프 뒷부분(738행)에서 매 iteration 끝에 WFI가 호출된다(단, `systemState.systemOff==true`로 조기 `break`하는 경로는 예외).

**영향 평가**: 이 오류는 I2C 트래픽 수치에는 영향을 주지 않는다 — 후보_6의 IDLE 플래그체크는 WFI 유무와 무관하게 순수 조건분기이기 때문이다. 다만 "이것이 가장 안전한 형태다(오디오/DSP 실시간 처리에 영향 없음)"라는 후보_6의 안전성 논거의 근거 하나가 부정확하다는 점은 밝혀둔다(이미 baseline에 존재하던 WFI이므로 실질적 회귀 리스크로 이어질 가능성은 낮다). 검증_10(할루시네이션 감사) 소관으로 인계할 사안이나, 본 노드가 직접 코드로 재확인했으므로 본 문서에도 기록한다.

## 6. 실사용 duty 반증 시도 — 두 후보 우위의 역전 가능성

### 6.1 코드 확인 — 현재 터치의 유일한 기능적 소비처

`main.c:452` `powerButtonPushed = tdc_touch_process();` → `tdc_touch.c:415~419` `if (out.long_touch) { ...; return true; /* 절전 트리거 */ }` → `systemControl.c:263` `if (veryLowBattery || powerButtonPushed) { ...전원 끄기 시작... }`.

**확인**: 현재 코드에서 터치 FSM의 유일한 출력(`long_touch`)은 "전원 버튼"으로 소비되며, 롱터치(2400ms) 시 전원 끄기 시퀀스를 개시한다. 짧은 탭에 대응하는 볼륨·프로그램 변경 등 별도 기능 출력은 **현재 코드에 없다**(`tdc_touch_logic.h:56` 주석 자체가 `long_touch`를 "롱터치 발동 1회(절전 트리거)"로 명시). 이는 후보_6 §5.3의 "파워 온/오프·절전 트리거로 기능"이라는 서술과 일치한다.

또한 `systemControl.c:230` 주석 "매핑이 연결되어있으면 전원 버튼은 무시한다"를 확인했다 — 매핑(피팅) 세션 중에는 의도적으로 터치를 무시하도록 설계되어 있다는 점도 확인된다.

### 6.2 핵심 발견 — 이 프로젝트 자체의 선행 UX 분석이 이미 문서화한 "간접 접촉" 채널

`docs/tasks/touch/20260615_eunsu-consensus-review/에이전트-로그/06_분석_A06_UX담당자.md`(maturity: **stable**, 즉 검증된 지침 수준 문서)를 직접 Read한 결과, 다음 서술을 확인했다(원문 그대로 인용):

> §1-1 표: "**간접 접촉 빈도 높음** | 안경 착용·헤어 터치·머리 베개 압착 시 패드에 의도치 않은 접촉 | **우발 터치 비율 높음** → Beta 빠르면 우발 터치가 LTA 흡수 위험"
>
> §1-1 표: "**조작 빈도 낮음** | 볼륨·프로그램 변경 등 **하루 수~수십 회 수준**"
>
> §3-2 표: "**안경 다리 마찰** | 중간(흡수 위험) | **수초 지속 접촉** → LTA 완전 흡수 가능"

**의미**: 이 문서는 인공와우 외부기의 실사용 맥락에서 터치패드 접촉이 **두 갈래**로 나뉜다는 것을 이미 확립해 두었다 —
1. **의도적 조작**: 하루 수~수십 회(후보_6의 "낙관적 하루 20~30회" 가정과 대체로 부합)
2. **간접(우발) 접촉**: 안경·헤어·베개로 인한 접촉이며, "빈도 높음"으로 명시. 안경다리 마찰은 개별 에피소드당 "수초 지속"으로 별도 명시.

두 후보(후보_6·7)의 duty 가정(§5.3, "하루 20~30회 조작", "매우 빈번한 조작·오탐 포함")은 모두 **의도적 조작 빈도** 프레이밍에 머물러 있고, 이 프로젝트가 이미 별도로 확립해 둔 "간접 접촉"이라는 **독립된 duty 기여 채널을 명시적으로 인용하지 않았다** — 두 후보 모두 duty를 "은수님만 아실 수 있는 부분"(실측 없음)으로 취급했으나, 실제로는 같은 프로젝트 안에 이미 이 질문에 부분적으로 답하는 자료가 있었다.

### 6.3 정량적 함의 — 두 후보 자신의 표를 이용한 재해석

안경을 상시 착용하는 사용자(고령 인공와우 착용자 비율이 높다는 §4-3 서술과 결합하면 드물지 않은 인구)의 경우, 안경다리가 터치패드에 지속 접촉하는 시간이 하루 중 상당 부분(안경 착용 시간대 전체)에 걸쳐 있을 수 있다. 이것이 정확히 얼마나 되는지는 [미확인]이나, 후보_6·7이 이미 계산해 둔 duty 시나리오 중 **"보수적 1%"보다 위쪽(5%, 나아가 10%)이 "매우 빈번한 조작"보다는 "장시간 안경 접촉"으로 더 쉽게 설명될 수 있는 영역**이라는 점이 이번 조사의 핵심 발견이다.

두 후보가 이미 계산해 둔 표를 이용해 이 시나리오를 재해석하면:

| duty 시나리오 | 근거(추정) | 후보_6 절대 감소율(§2.1 재계산) | 후보_6 대비 후보_7 잔존배율(§3.3 재계산) |
|---|---|---|---|
| 1%("보수적", 두 후보 공통 가정) | 의도적 조작만 반영 | 98.6~98.9% | **10.9~20.8배** |
| 5%("매우 보수적", 후보_6 참고치) | 오탐+ATI재시도까지 반영(간접접촉 미반영) | 93.1~94.7% | (후보_7 표에 없음, 10%행이 근사치) |
| 10%(후보_7 자체 산출 행) | 간접 접촉이 의도적 조작을 상회하는 시나리오를 근사 | (후보_6 모델 적용 시 90%+ 유지, §2.1 로직 연장) | **1.9~2.8배** |

**해석**: duty가 "간접 접촉"을 반영해 1%에서 5~10%대로 올라간다고 해도, 후보_6이 baseline 대비 갖는 **절대적 우위**(93%+ 감소)는 크게 훼손되지 않는다 — 손익분기(72.1~93.6%)까지는 여전히 거리가 멀기 때문이다. 그러나 후보_6이 후보_7 대비 갖는 **상대적 우위**(트래픽 잔존 배율)는 duty 1%에서 가정한 10.9~20.8배가 아니라, duty 5~10%대에서는 후보_7 자신의 표가 보여주는 1.9~2.8배 수준으로 **좁혀질 근거가 있다.** 이는 후보_6 §6.3의 "은수님이 우려하신 '지금과 별 차이 없다'는... 실사용 범위에서 벗어나지 않는 한... duty-cycle 가정의 구체적 숫자와 무관하게 강건한 결론"이라는 서술 중 "duty 가정의 구체적 숫자와 무관하게"라는 부분을 부분적으로 반증한다 — **절대적 개선폭은 duty에 강건**하지만, **후보_6과 후보_7 사이의 상대적 우위(구현 복잡도·회귀위험이라는 대가와 맞바꾸는 그 폭)는 duty에 결코 강건하지 않으며**, 이 프로젝트 자신의 UX 근거가 이미 그 duty를 "낙관적" 시나리오보다 높은 쪽으로 밀어올릴 힌트를 제공한다.

> [!NOTE]
> 이는 후보_6·7의 결론을 "틀렸다"고 반증하는 것이 아니라, "정상 사용 범위 내에서는 손익분기에 도달할 방법이 사실상 없다"(후보_6 §5.5)는 명제 — 이는 여전히 참으로 보인다 — 와 "duty 가정과 무관하게 강건하다"는 조금 더 강한 명제를 구분해야 한다는 뜻이다. 후자는 특히 **후보_6 vs 후보_7의 선택 문제**에서는 duty 민감도가 매우 크므로(§6.1의 회귀위험 축 논거와 결합 시), 실측 duty(간접 접촉 포함) 없이 후보_6을 확정 채택하는 것은 후보_7이 강조한 안전마진(§6.2, 정지→재개 단일장애점 부재)의 가치를 과소평가할 위험이 있다.

### 6.4 이 발견이 [미확인]으로 남는 이유

- 안경 착용 인공와우 사용자 비율, 안경다리가 실제로 터치패드 위치에 물리적으로 접촉하는 기하학적 개연성, 접촉이 "터치 임계값"을 실제로 넘는지(단순 근접이 아니라)는 모두 **[미확인]**이다 — 06_분석_A06 문서 자체도 "간접 접촉 빈도 높음"을 정성적으로만 서술하고 정량화하지 않았다.
- 야간 미착용(충전) 시간이 있다면 24시간 정규화(864,000틱/일) 자체가 과대평가일 수 있으나, 이는 분자·분모에 동일 비율로 작용해 **절감률(%)에는 영향을 주지 않는다** — 절대 건수에만 영향.
- 검증_4(12번 문서)가 이미 이월한 "ATI 자동 재조정 빈도(분·시간 단위로 드묾)"는 그대로 유효하다고 가정했다 — 재검증하지 않았다(내 역할 범위 밖).

## 7. 최종 판정

1. **산술**: 후보_6·후보_7의 모든 정량 수치(§5.4~5.6, 표1~3)를 독립 재계산한 결과 오차 0 — 반증 시도는 완전히 실패했다. 두 문서의 계산은 신뢰할 수 있다.
2. **모델 정합성**: 두 후보가 인용한 baseline(5.77~7.49)·강제개방(1.77~3.49)·Events idle(8) 수치는 그라운드_2·검증_2 원 모델과 정확히 일치하며, 오히려 "8"은 T_주기 불확실성에서 자유로운 더 견고한 상수임을 확인했다 — 반증 시도가 두 후보의 방법론적 보수성을 재확인해 주었다.
3. **자체 그라운딩 교차검증**: 3건의 불일치/오류를 발견했으나(그라운드_9 삽입위치, ATI 재평가 미검증, WFI 유무 상호모순) 셋 다 **I2C 트래픽 정량 결론 자체에는 영향을 주지 않는다** — 부수적 설계·CPU비용 서술의 정확도 문제로 국한된다.
4. **실사용 duty**: 정성적 순위(후보_6의 트래픽 절감 절대 우위, 후보_7의 회귀위험 절대 우위)를 뒤집지는 못했으나, 이 프로젝트 자체의 선행 UX 문서(2026-06-15, stable)가 이미 밝혀 둔 "간접 접촉 빈도 높음(안경·헤어·베개)"이라는 duty 기여 채널을 두 후보 모두 놓쳤다는 것을 발견했다 — 이를 반영하면 후보_6·후보_7 간 **상대적** 트래픽 격차(10.9~20.8배)는 후보_7 자신의 표가 보여주는 더 높은 duty 구간(1.9~2.8배)까지 좁혀질 근거가 있다. **완전한 역전(50%대 duty)은 여전히 비현실적**이라는 후보_6의 판단은 유효하다.

**총평**: 이 라운드의 정량 계산 자체는 견고하다. 다음 단계(검증_7·9·10 또는 오케스트레이터 종합)에서는 (a) 그라운드_9 삽입위치·WFI 서술을 후보_6 설계에 반영해 정정하고, (b) 실측이 불가능하다면 최소한 06_분석_A06의 "간접 접촉" 채널을 duty 민감도표에 명시적 시나리오로 추가해, 후보_6(고효율·고리스크)과 후보_7(중효율·저리스크) 사이의 선택이 "차이가 크다"는 전제 위에서만 정당화되지 않도록 하는 것을 권고한다.
