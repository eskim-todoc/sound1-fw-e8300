# 분석 — 이벤트 모드(0xC0 bit7) 채택 딥다이브

**TL;DR**: 은수님의 전제("이벤트 모드로 RDY가 매번 토글되지 않아 이득")를 그라운드3·후보5·검증6 총 14페르소나로 딥다이브했다. 결론은 3층 분해로 요약된다 — ① IC 자체 RDY assert 빈도 감소는 **참**, ② 은수님이 의도했을 실질 이득(불필요한 인터럽트 회피)은 현재 아키텍처(RDY=busy-wait 폴링, 인터럽트 미사용)에서 **성립하지 않음**, ③ 순수 I2C 트래픽 감소라는 대안적 이득은 방향은 유지되나 크기는 과대추정(1.3~2.0배→검증 후 1.07~1.39배)됐다. **2차 라운드(§8)**: 은수님이 "지금과 별 차이 없다"고 재확인해 "폴링 주기 자체는 유지"라는 1차 라운드의 숨은 전제를 깨는 결합 시나리오를 추가 검증한 결과, 유휴 시 폴링을 줄이면 실제로 큰 차이(트래픽 최대 98%+ 감소)가 나며, 그 효과는 이벤트 모드·인터럽트 없이 **유휴 폴링주기 연장만으로도 대등**하다는 것이 최종 발견이다. 할루시네이션은 확정오류 2건(1차)뿐, 최종 결론에 영향 없음. 상세: [`에이전트-로그/99_종합.md`](에이전트-로그/99_종합.md).

> [!NOTE]
> 워크플로우 14에이전트(그라운드3·후보5·검증6, 전부 model:sonnet effort:max). 은수님 지시 "할루시네이션 절대 절대 없게 검증 빡세게"에 따라 검증 6개 전체를 적대적 검증(반증 시도)으로 구성 — **하드 할루시네이션 0건**(참고문서·인용 오류 2건 확정 발견, 하류 영향 없음).

## 1. 스코프 계승

INV-CTRL-1(Full ATI)·INV-CTRL-2(ATI에러→Re-ATI)·INV-CTRL-3(첫터치해제) 3거동만 불변, 그 외 자유(레지스터·채널·측정·**force_window_open 프로토콜 자체**). 은수님이 검증 진행 중 "폴링을 인터럽트 방식으로 변경하는 것까지 고려"를 명시적으로 추가 — 이는 요구사항.md §3에서 이미 자유변수로 열어둔 범위이며, 후보_4가 정확히 이 방향을 다룬다.

## 2. 그라운드 사실 (G1·G2·G3, 검증_1·2·3 대조 완료)

- **G1 IC버전·에라타범위**: 0x00~0x02(Major/Minor Version)·0xE1(Hardware ID)은 기존 `read_register()`로 **추가 HW 없이 실측 가능**(검증_1 반증 실패로 확정). 단 "부록C의 v1.3/v1.4 ↔ 레지스터값 등치"·"00x/A0x ↔ IQS3dd/IQS3ed 명칭 등치" 두 매핑은 데이터시트 전체를 재탐색해도 명문 근거를 찾지 못해 **[미확인] 유지가 타당함**을 검증_1이 재확인 — 최종 확정은 실측(부팅 1회 read)으로만 가능.
- **G2 강제개방 프로토콜 정량분석**: Streaming에서 `force_window_open()` 조기반환은 우세하게 히트(추정 T_주기 0.4~16ms 기준 84~99.6%)하지만, Events 전환 시 유휴구간엔 §8.11.2/8.12 원문대로 RDY가 완전히 침묵해 조기반환이 사실상 소멸 — 총 I2C 트랜잭션이 증가한다는 **방향**은 검증_2가 반증에 실패해 유지된다. 단 사이클당 4회 호출을 동일 취급한 모델링 결함을 검증_2가 발견해 **크기는 1.3~2.0배가 아니라 1.07~1.39배**(128kHz I2C 클럭 기반 독립 재계산)로 정정된다.
- **G3 3불변식 코드훅**: INV-CTRL-1~3의 정확한 파일:라인 재확인 완료(검증_3이 5개 후보 전체 대상 재검증, C1·C3·C4·C5 전부 무손상 확정).

## 3. 후보 5종 최종 판정

| 후보 | 판정 | 핵심 근거 |
|---|---|---|
| **후보_1** 순수 Events 전환 | 단독채택반대(조건부 검토 가능) | P3 스펙 코드 일치 재확인. 순 이득 작음(§4)+에라타 노출 증가로 워크어라운드·IC버전실측 동반 필요 |
| **후보_2** Events+에라타 워크어라운드 | 개선 필요(현행 스펙 배포 부적합) | 핵심 스펙(0xF0 비존재·`mclr()` 기존함수)은 검증_1 반증 실패로 유지되나, 검증_3이 신규 위협 2건 발견(게이트 영구정체 가능성·150µs 위반 라이브락) |
| **후보_3** Events+Report Rate | 유효하나 효과 제한적 | Report Rate가 Events에도 유효한 독립 축임을 확인(0xC1=70ms 제안). 단 저지연 이점은 후보_4 완료 전까지 실현 안 됨 |
| **후보_4** 폴링→인터럽트 프로토콜 재설계 | **최우선 채택 권고** | `ci_dio.c` 기존 2슬롯 인터럽트 인프라 재사용으로 SW-only 실현 가능. 검증_6이 핵심 주장 재확인(WFI 근거 서술 1건만 반증). Events 채택과 독립적으로 유효 |
| **후보_5** Streaming+ReportRate 대안 | 상대적 우위 과장 확인 | "에라타 노출 무변화" 핵심 주장이 **자기모순**(자기 제안값 83ms 대입 시 히트율 17%로 급락, 검증_2·6 공동 발견) — 트래픽이 실제로는 크게 증가 |

## 4. 은수님 원래 전제의 3중 분해 (결정적)

| 층위 | 판정 |
|---|---|
| ① IC 자체 RDY assert 빈도 감소 | **참**(§8.11.2/8.12 원문 확정) |
| ② 실질 의도(불필요한 인터럽트 회피) | **불성립** — RDY는 처음부터 인터럽트가 아니라 busy-wait 폴링 전용(EXTI 등록 0건, 검증_2·6 독립 재확인) |
| ③ 대안적 이득(순수 트래픽 감소) | 방향 유지, 크기 과대추정(1.3~2.0배→1.07~1.39배) |

**결론**: "RDY 안 토글돼서 이득"의 진짜 실현 경로는 이벤트 모드 자체가 아니라 **폴링→인터럽트 전환(후보_4)**이다.

## 5. 검증이 발견한 신규 위험 (이벤트 모드 논의와 별개로 항상 존재)

- **[최중요]** IQS323 내장 **255ms 통신 워치독**(§7.6) 트리거 시 IC가 POR로 초기화되고 Reset Event 비트(bit7)가 set되나, **런타임 코드(`read_status()`)가 이 비트를 구조적으로 점검하지 않는다** — 기존 안전장치 3종(`re_ati()` 복구·후보_2 프로브·기존 0xEE 글리치 검사) 전부 이 시나리오를 놓친다(검증_4, 코드로 직접 확인).
- azd004 고유의 "강제개방-자연이벤트 경합 레이스" — 버전 무관, 모든 IQS323에서 이론상 발생 가능(검증_4).
- 후보_2의 `lockup_probe()`+`mclr()` 재사용 경로에 위협_A(게이트 영구정체 가능성)·위협_B(150µs 스위치오버 위반 라이브락) 신규 발견(검증_3).

## 6. 할루시네이션 감사 (검증_5)

150여 건 인용 전수 대조, 하드 할루시네이션 0건. 확정 오류 2건: ① 그라운드_1의 Table 10.1 오더코드 I2C 주소 반전 인용(하류 영향 없음, 후보_1은 정확), ② 후보_5의 "§8.11.2 펌웨어 권장" 인용이 실제로는 참고 md의 사내 해설(원문 아님) — 후보_5 핵심 논거와는 무관해 최종 권고 불변.

## 8. 2차 라운드 — 결합 시나리오(Events+인터럽트) 정량 검증

은수님의 재확인("결론은 지금이랑 별 차이가 없을 것 같다 이거야?")이 정확한 지적이었다 — 후보_4(단순 인터럽트 전환)와 이벤트모드 단독 모두 **100ms 고정 폴링 주기는 그대로 유지**한다는 전제였다. 이 사각지대를 그라운드3·후보2·검증4(9페르소나)로 추가 검증했다.

### 8.1 그라운드 사실

- **그라운드_7**: 100ms 폴링 의존 타이밍 로직 11종 중 5종(롱터치·Re-ATI쿨다운·stuck승격 등, 깨어있음 FSM)은 실제 경과시간(타임스탬프) 기반이라 인터럽트 재설계와 무관히 안전. 6종(ATI에러재부팅·롱터치재부팅 등 절전 ULP 카운터)은 순수 호출횟수 누적이라 유휴 게이트 설계 시 반드시 고려해야 한다.
- **그라운드_8**: 터치 이벤트는 **진입/이탈 전이(edge)에만 발생**하고 유지 중(steady touch) 재발생하지 않음을 §8.11~8.12 원문으로 확정 — 순수 이벤트 기반으로는 "아직 눌려있는가"라는 레벨 상태를 알 방법이 없다.
- **그라운드_9**: 3개 폴링 경로(노말 FSM·func_sleep·fake_func_sleep) 전부 경과시간 게이트 통과 후 read가 무조건 호출되는 구조 — I2C 자체를 게이팅할 삽입 지점이 존재한다(단 정확한 위치는 검증_7·9가 후보_6과 이견 발견, §8.3).

### 8.2 후보 2종

- **후보_6(하이브리드)**: 유휴(터치없음·ATI정상) 시 폴링 완전정지+RDY 인터럽트 대기, 터치진입·ATI에러 이벤트 시 활성폴링(100ms) 재개. 3불변식 무손상 확인(검증_7). duty(터치 활성 비율) 1% 가정 시 유휴 트래픽 약 **98.6~98.9% 감소**, 0.05%면 99.9%+.
- **후보_7(대안)**: 유휴 시 폴링주기만 100ms→500~1000ms로 늘리고 이벤트 시 인터럽트로 즉시 복귀(본안). 후보_6 대비 회귀위험이 명확히 더 낮다(정지→재개 실패라는 단일장애점 없음). **핵심 발견 — 변형_1**: 인터럽트·이벤트모드를 전부 뺀 순수 저속폴링(Streaming 유지, 레지스터·배선 변경 전혀 불요)도 트래픽 절감이 본안·후보_6과 대등하다 — "훨씬 단순한 대안"이라는 과제 취지에 가장 부합한다.

### 8.3 검증이 발견한 신규 사항

- **[구현 필수 정정 1]** `tdc_touch_process()`의 RDY 게이팅 삽입 위치가 그라운드_9(경과시간 게이트 통과 후, `tdc_touch.c:301`)와 후보_6(경과시간 게이트 **이전**, 294행 앞)이 서로 다르다(검증_7·9 공동 발견). 그라운드_9 방식대로 구현하면 후보_6이 약속한 "즉시 감지" 이점이 사라지고 기존과 동일한 최대 100ms 지연이 재현된다 — **구현 시 반드시 후보_6 배치(294행 앞)를 채택**해야 한다.
- **[구현 필수 정정 2]** "노말모드에 WFI가 없다"(1차 라운드 후보_4·후보_6 서술)는 **오류로 확정**됐다(검증_9·10 독립 재확인) — `main.c:452`(터치 처리 호출)와 `:738`(WFI)이 동일한 `while(1)` 루프 안에 있다. DIO16 인터럽트는 기존 WFI에 웨이크소스를 하나 추가하는 국소 변경이지, WFI를 신규 도입하는 구조 변경이 아니다 — 인터럽트 전환 리스크가 1차 라운드가 서술한 것보다 낮다.
- **[최중요, duty 재평가]** 후보_6·7의 duty 가정(1%·0.05%, "의도적 조작 빈도" 프레이밍)이 이 프로젝트 자체의 선행 UX 분석(`2026-06-15`, maturity:stable)이 이미 문서화한 **"간접 접촉 빈도 높음"(안경다리 마찰·헤어·베개 압착, 수초 지속)** 채널을 반영하지 않았다(검증_8 발견). 이를 반영하면 duty가 5~10%대일 근거가 있으며, 이 경우 후보_6의 **절대적** 우위(93%+ 감소)는 유지되나 후보_6 대 후보_7의 **상대적** 격차(10.9~20.8배)는 1.9~2.8배 수준까지 좁혀진다.

### 8.4 2차 라운드 결론

은수님의 지적대로, 1차 라운드 권고(후보_4)만으로는 "지금과 별 차이 없다"가 정확했다. 그러나 폴링 자체를 줄이는 결합안까지 가면 실제로 큰 차이가 나며, 그중 **가장 단순하고 낮은 리스크로 그 차이를 얻는 방법은 이벤트 모드도 인터럽트도 필요 없는 "유휴 시 폴링주기 연장"(후보_7 변형_1)** 이다. 상세 로드맵은 [`계획.md`](계획.md) §2 참조.
