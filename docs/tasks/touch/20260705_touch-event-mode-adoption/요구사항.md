# 요구사항 — 이벤트 모드(0xC0 bit7) 채택 딥다이브

**TL;DR**: 은수님이 새 관측 방식으로 **이벤트 모드(Interface Selection: Streaming→Events)** 도입을 지시했다. 근거는 "RDY가 매번 토글되지 않는다"는 자가토글 제거 효과. 이 후보는 이미 선행 작업(`20260703_touch-heisenberg-sw-mitigation` S3/V3 후보_3, `20260703_touch-heisenberg-sw-impl` P3)에서 **부속 레버로 스펙까지 갔으나, I²C Lock-Up 에라타(부록C)와 force_window_open() 강제개방 상시화라는 미해결 중대 리스크로 "조건부 구현-레디(보류)"** 상태였다. 본 작업은 이를 **주역 방식으로 승격**해 미해결 리스크를 끝까지 판정하고, 3거동 불변식을 지킨 채 채택 여부를 결정한다. 브랜치는 `claude_feature_touch-mutual-cap-review` 유지, 신규 작업 폴더에서 진행. 페르소나 다수(그라운드·후보·검증 3단), 할루시네이션 검증 최우선.

## 1. 배경 — 선행 작업 계보

1. `20260703_touch-mutual-cap-review` — 상호용량(mutual) 센싱 HW 전환 조건부 No-Go.
2. `20260703_touch-heisenberg-sw-mitigation` — SW-only 완화 포트폴리오 1차 조사. S3(에이전트-로그/05)가 **후보_3: Interface Selection→Events 모드**를 발굴, V3(13)가 적대적 검증에서 두 가지를 발견:
   - 확인: 데이터시트 §8.11.2 NOTE가 "펌웨어 권장: Event mode를 기본, Streaming은 개발·디버깅 단계 임시용"이라 명시 — 현재 제품 코드(Streaming)가 **제조사 권장과 반대**.
   - 신규 중대 위험: `force_window_open()`의 "RDY 이미 열림 시 0xFF 생략" 조기반환이 Events 전환 시 사실상 소멸 → **매 폴링 강제개방(0xFF)이 상시화**되며, 이것이 데이터시트 부록C **"I²C Lock Up" 에라타**(IQS323-00x v1.3 이하·A0x v1.4 이하, force communications 사용 시 발생 가능성↑, 모든 read byte가 상수 반환)의 트리거 조건과 정확히 일치. 현재 보드 실장 IC 버전이 에라타 적용 범위인지 **미확인**(코드에 버전 read 없음).
3. `20260703_touch-heisenberg-sw-impl` — 완화 포트폴리오 구현계획. P3(에이전트-로그/04)가 이벤트 모드 전환을 write 사이트 5곳(318·447·453·465·471, `tdc_touch_iqs323.c`) 단위로 구현-레디 스펙까지 작성했으나, **§4.3 신규 발견**(func_sleep() 롱터치 재부팅 카운터가 read 실패 시 즉시 0 리셋 — 강제개방 실패 빈도 증가 시 정상 기상 제스처가 약화될 위험)까지 겹쳐 "**조건부 구현-레디**"로 보류.
4. `20260703_touch-heisenberg-config-reexplore` — 센서 config/channel/measurement 레벨로는 코히런트 AC 노이즈 **상쇄 불가**가 fact-verified로 확정(reference tracking·SW차동 전부 데이터시트로 기각). 은수님이 "센서 자체로는 방법이 없다"고 확인. → 남는 길은 **애그레서 제거·결합 저감·재부팅 완충** 뿐이라는 결론.

## 2. 은수님의 새 지시 (본 작업 트리거)

> "새 방식을 도입해보게. 이벤트 모드를 사용하는 방식이야. Rdy가 매번 토글되지도 않고. 브랜치는 유지하고 새 작업 폴더에 분석 계획을 해봐 검증이랑. 빡세게 많은 페르소나로"

- 이벤트 모드를 **④단계 구현 후보 중 하나(P3)에서 → 이번 작업의 주역 방식**으로 승격.
- 브랜치 유지: `claude_feature_touch-mutual-cap-review`.
- 신규 작업 폴더에서 ①요구사항(본 파일)→②분석→③계획, 검증(다수 페르소나·adversarial-verify) 수행. 코드 변경(④)은 미착수.

## 3. 불변식 (계승, 변경 없음)

`20260703_touch-heisenberg-config-reexplore/요구사항.md`에서 확정된 INV-CTRL-1~3을 그대로 승계한다 — 이벤트 모드 전환이 아래 3거동을 훼손하면 채택 불가:

- **INV-CTRL-1 Full ATI**: 0x36 ATI Mode 설정·부팅 시 Full ATI 실행 경로 불변.
- **INV-CTRL-2 ATI 에러 처리(Re-ATI)**: `ati_error`→`tdc_touch_iqs323_re_ati()` 호출 경로(노말/절전/fake 3사이트) 불변.
- **INV-CTRL-3 첫 터치 해제 감지**: `boot_ignore`/`sleep_ignore` 게이트 로직 불변.

**자유변수**: 센서 레지스터 설정·채널 구성·측정 방식은 물론, **force_window_open()/wait_window_closed() 프로토콜 자체의 재설계까지 포함**(SW 범위 내라면 자유) — 이벤트 모드 채택이 이 프로토콜 변경을 요구하기 때문에 이번 작업은 앞선 재탐색보다 자유변수 범위가 더 넓다.

## 4. 스코프 — 판정해야 할 핵심 질문 (make-or-break)

| 질문 | 내용 | 판정 기준 |
|---|---|---|
| 질문_1 | **IC 버전 실측 가능성**: `0x01`(Major Version)·`0x02`(Minor Version, A.1) 또는 `0xE1`(Hardware ID, A.37) read로 에라타 적용 범위(00x v1.3 이하·A0x v1.4 이하) 여부를 **SW-only로**(추가 HW 없이, 기존 `read_register()` 재사용) 확정할 수 있는가 | 가능하면 "미확인" 블로커 자체가 실측 프로토콜로 해소됨 |
| 질문_2 | **자기애그레서 트레이드오프**: Events 전환으로 IC 자가 RDY 토글(Report Rate마다 무조건)은 사라지나, `force_window_open()` 조기반환 소멸로 **매 폴링 0xFF 강제개방(SDA 토글)이 상시화** — 이게 기존 "IC 자가토글"보다 더 심한/약한 애그레서인지 | 순 이득이 있는지 정성·가능하면 정량 판정 |
| 질문_3 | **에라타 워크어라운드 타당성**: 매 I²C 통신 끝 비존재 레지스터 1byte read + `0xEE` 검사(부록C 권고) 도입 시 부가 트래픽이 또 다른 애그레서를 만드는지, 코드 변경 범위는 어느 정도인지 | 도입 비용 대비 리스크 저감 효과 |
| 질문_4 | **Report Rate(0xC1)/ATI 버스트 타이밍 간섭** (V3 §2 신규위험) 재검증 — Events 단독 도입 시엔 무관한지, 병행 시에만 발생하는지 | Events 단독안의 위험 범위 확정 |
| 질문_5 | **fake_func_sleep 프로파일링 경로 영향**: `read_debug()` 호출 빈도·강제개방 성공률이 이 전환으로 어떻게 바뀌는지, 기존 H2(read_debug 자체애그레서) 가설과의 상호작용 | 원 목적(절전 프로파일링 안정화)에 실제 기여하는지 |
| 질문_6 | **P3(sw-impl) §4.3 롱터치 카운터 read-fail 즉시리셋** 위험이 여전히 유효한지, 완화책(hold 방식 등) 필요 여부 | INV-CTRL-3(첫 터치 해제) 인접 회귀 위험 재확인 |

## 5. 제약

- **SW-only, HW 무수정** — 보드·회로 변경 없음.
- **브랜치 유지**: `claude_feature_touch-mutual-cap-review`에서 계속 작업.
- **코드 변경은 사용자 승인 후**(④단계) — 본 작업은 ①~③(+검증)까지, 제품 소스 변경 0건 유지.
- 검증 최우선 — 은수님 지시("할루시네이션 절대 절대 없게 검증 빡세게")를 계승. 모든 핵심 주장은 데이터시트 원문(PDF)·현재 코드 직접 대조.

## 6. 페르소나 구성 (빡세게, 다수)

3단 구성 — 그라운드(사실 확정) → 후보(방안 설계) → 검증(적대적):

- **그라운드**: G1 IC버전·에라타 적용범위 실측 가능성, G2 force_window_open 프로토콜 정밀분석(자기애그레서 정량화 시도), G3 3불변식 코드훅 재확인.
- **후보**: C1 순수 Events 전환(P3 스펙 재검토), C2 Events+에라타 워크어라운드 결합, C3 Events+Report Rate 결합, C4 force_window_open 프로토콜 자체 재설계, C5 대안 비교군(Events 도입 없이 Streaming 유지+RDY 토글 최소화).
- **검증**: V1 에라타 반증, V2 자기애그레서 트레이드오프 반증, V3 3불변식 회귀 전수 재확인, V4 완전성 비평(데이터시트·에라타 문서 재검토), V5 할루시네이션 감사, V6 C4/C5 특이 검증.
