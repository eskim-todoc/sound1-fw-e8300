# 소규모 설정값 파일 영속화 선례 조사

> [!NOTE]
> 본 문서는 Explore 서브에이전트(read-only)가 조사한 결과를 오케스트레이터(세션)가 그대로 옮겨 적은 것이다. 해당 노드에는 파일 쓰기 권한이 없어 직접 Write 하지 못했다. 사실 검증은 `분석-검증.md`에서 별도로 수행한다.

**TL;DR**: `ci_stim_mute`는 IDENT(매직넘버)+범위검증+실패시 기본값 재기록 패턴의 유효한 소규모 설정 영속화 템플릿이나, 초기화 실패를 assert하지 않고 `FA_OPEN_APPEND` 오용 등 사소한 결함이 있다. FS 계층은 `snd_fatfs_remount(0|1)` 드라이브 전환과 `ci_filesystem_read/write[_with_crc_and_aes128]` 래퍼로 통일되어 있으며, 원자적 쓰기(임시파일/이중버퍼)나 플래시 수명 관련 보호장치는 코드베이스 전체에서 발견되지 않았다.

## 1. `ci_stim_mute` 패턴 분석

### 1.1 파일명·구조체

- 파일명: `"STIM_MUTE.TXT"` (선행 `/` 없음) — `src/2__cm3/Gen1_5/FS/ci_stim_mute.h:21`
- 구조체 `CI_STIM_MUTE_T` (16바이트, uint32_t 4개): `file_ident_begin`, `is_enabled_mute_stimulation_under_t_level`, `mute_stimulation_t_level_offset`, `file_ident_end` — `ci_stim_mute.h:35-41`
- 매직넘버: `CI_STIM_MUTE_FILE_IDNET_BEGIN = 0x12345678`(원문 오타 "IDNET"), `CI_STIM_MUTE_FILE_IDENT_END = 0x87654321` — `ci_stim_mute.h:23-24`
- 값 도메인: enable은 `1`(ENABLE)/`2`(DISABLE) 화이트리스트, offset은 `0~255`(기본값 `2`) — `ci_stim_mute.h:26-31`

### 1.2 초기화(`ci_stim_mute_init`, `ci_stim_mute.c:4-131`)

1. `f_open(FA_OPEN_ALWAYS|FA_READ|FA_WRITE)` — 없으면 생성 — `ci_stim_mute.c:18`
2. 4KB 클러스터 강제 확보용 `f_lseek(4096)→f_lseek(0)` 트릭 — `ci_stim_mute.c:30-32` (동일 트릭이 `ci_filesystem.c:622-624`, `ci_filesystem.c:877-879`, `ci_event_log.c:64-66`에도 반복됨)
3. `f_read`로 구조체 읽기, 읽기 실패/크기 불일치/IDENT 불일치/enable 화이트리스트 불일치/offset 범위초과 시 `is_validated_file=false` — `ci_stim_mute.c:35-78`
4. 무효 시 하드코딩 기본값(`DISABLE`, offset=2)으로 재구성 후 `f_lseek(0)`+`f_write` — `ci_stim_mute.c:83-105`. 쓰기마저 실패하면 `return -1` (단, 이 실패는 아래 §5에서 보듯 `Initialize()`에서 검사되지 않음)
5. `f_sync` 플러시, `f_stat` 디버그 출력, `f_close` — `ci_stim_mute.c:108-122`
6. 검증/재구성 결과를 무조건 공유메모리(`cfx_cm3_sharedMemoryAll`)에 반영 — `ci_stim_mute.c:127-128`

### 1.3 갱신(`ci_stim_mute_update`, `ci_stim_mute.c:133-201`)

- 파라미터 화이트리스트/범위 재검증 후에만 진행 — `ci_stim_mute.c:142-160`
- `f_open(FA_OPEN_APPEND|FA_READ|FA_WRITE)`로 열지만 직후 `f_lseek(fp, 0)`으로 위치를 되돌려 실제로는 append 모드가 무의미해짐 — `ci_stim_mute.c:166`, `181` (동작상 오류는 아니나 코드 일관성 결함으로 판단, **추정**: 원래 `FA_OPEN_ALWAYS`를 의도했을 가능성)
- 매번 구조체 전체를 덮어쓰기(`f_write`), 성공 시에만 공유메모리 갱신 — `ci_stim_mute.c:176-198`
- 호출처: `remoteControl.c:1420,1454`(BLE 리모트 명령), `tdc_ui_command.c:761,769`(UI 명령) — 사용자 조작 시점에만 쓰기 발생(주기적 아님)

### 1.4 템플릿 평가

**적합한 부분**: 매직넘버+범위검증에 의한 자기수복(self-healing) 구조, 실패 시 안전한 기본값 재기록, `f_sync`로 즉시 플러시.

**한계(신규 설계 시 유의)**:
- 초기화 실패(open/write fail)가 `-1`을 반환하지만 `Initialize()`에서 검사하지 않음 → 실패해도 부팅이 계속되고 공유메모리는 불확실한 값을 가질 수 있음 (`initialize.c:334`, 아래 §5 참조)
- `FA_OPEN_APPEND` 사용이 실질적으로 무의미(코드 스멜)
- 파일명에 선행 `/`가 없어 `ci_map`/`ci_fft`/`ci_boot` 계열(모두 `/`로 시작)과 명명 관례가 불일치 — `ci_map.h:61-79`, `ci_fft.h:22-37`, `Gen1_5/dfu/sdk_ci_boot.h:15` 대비 `ci_stim_mute.h:21`, `ci_event_log.h:18`은 `/` 없음

결론적으로 **참고 템플릿으로 사용 가능**하나, 위 한계는 그대로 답습하지 말고 개선(실패 시 assert 여부 명시적 결정, 파일명 컨벤션 통일)이 필요.

## 2. 파일시스템 API 계층

### 2.1 드라이브 구분

- `SND_FATFS_LDRV_NUM_BOOT = 0`, `SND_FATFS_LDRV_NUM_USER_DATA = 1` — `ci_filesystem.h:36-37`
- 레거시 상수 `CI_FILESYSTEM_LOGICAL_DRIVE_NUM = "1:"`(사용자), `..._FOR_BOOT_STATUS = "0:"`(부트) — `ci_filesystem.h:33-34`. 이를 사용하는 `ci_filesystem_mount()/ci_filesystem_remount()`(`ci_filesystem.c:150-193`)는 실제 코드베이스에서 **호출되는 곳이 없음**(자기참조 1건만 존재, `ci_filesystem.c:162`) — 사실상 미사용 레거시 경로로 판단. 현재 실사용 관례는 `snd_fatfs_remount(int ldrv)`(§2.2)이다.

### 2.2 마운트/언마운트 함수 (`ci_filesystem.c:40-148`)

- `snd_fatfs_init_mem_map()`: FFT/맵 공유메모리 포인터만 세팅, FS 마운트와 무관 — `ci_filesystem.c:40-46`
- `snd_fatfs_mount(int ldrv)`: `ldrv==0→"0:"`, else `"1:"` — `ci_filesystem.c:79-86`; `f_mount(force=1)` → `f_chdrive` → `f_opendir/f_closedir`로 정상 동작 검증 — `ci_filesystem.c:89-111`
- `snd_fatfs_unmount()`: `g_ci_filesystem_mount.fs_type==0`이면 이미 언마운트 상태로 간주해 즉시 성공 반환, 아니면 `g_ci_filesystem_mount.ldrv`로 경로 판단 후 `f_unmount` — `ci_filesystem.c:116-148`
- `snd_fatfs_remount(int ldrv)` = unmount 후 mount — `ci_filesystem.c:63-71`. **이것이 실제 사용되는 드라이브 전환 관용구**이며, `Initialize()`(`initialize.c:261,313,316`)와 `ci_boot.c`(`248,254,271,277`), `ci_ble_control_ota.c`(`98,124,139,214,218,306,342,357`) 전역에서 이 패턴으로 드라이브를 전환한다.
- `snd_fatfs_remount_twice(int ldrv)`: 주석에 "두 번 수행해야 이상동작하지 않음. 이유는 모름"이라 적혀 있으나(`ci_filesystem.c:50`), 코드베이스 전체에서 **호출처가 전무**함(선언·정의만 존재, `ci_filesystem.h:127`, `ci_filesystem.c:48`) — 원인 불명 quirk를 우회하려던 흔적으로 보이나 현재 사용되지 않음 (**확인 실패**: 왜 두 번 필요한지 근거 없음)

### 2.3 파일 열기/읽기/쓰기/닫기 시그니처와 관례

FatFs 저수준: `FIL *ci_fatfs_get_fp(void)`가 전역 핸들 `g_ci_filesystem_ohdl`의 포인터를 반환 — `ci_filesystem.c:15-18`, `ci_filesystem.h:116,122`. 전역 마운트 구조체 `FATFS g_ci_filesystem_mount` — `ci_filesystem.c:12`, `ci_filesystem.h:115`.

고수준 래퍼(`ci_filesystem.h:153-154`, 정의는 `ci_filesystem.c:822-917`):
```c
int ci_filesystem_read(char *p_name, uint8_t *p_buf, int size);
int ci_filesystem_write(char *p_name, uint8_t *p_buf, int size);
```
- `read`: `FA_OPEN_EXISTING|FA_READ|FA_WRITE`로 열고 `f_lseek(0)` 후 `f_read`, 크기 불일치 시 실패 — `ci_filesystem.c:822-860`
- `write`: `FA_OPEN_ALWAYS|FA_READ|FA_WRITE`로 열고 4KB 클러스터 확보 트릭(`f_lseek(4096)→0`) 후 `f_write`, `f_sync`, `f_stat` 디버그 출력, `f_close` — `ci_filesystem.c:862-917`

CRC+AES128 겸용 래퍼(`ci_filesystem.h:135-151`, 정의는 `ci_filesystem.c:195-820`):
```c
int ci_filesystem_read_with_crc_and_aes128(char *p_name, uint8_t *p_data, int data_size,
    uint32_t *p_uint32_crc, uint32_t *p_uint32_aes128_padding, int aes128_padding_size,
    bool enable_crc, bool enable_aes);
int ci_filesystem_write_with_crc_and_aes128(char *p_name, uint8_t *p_data, int data_size,
    uint32_t *p_uint32_crc, uint32_t *p_uint32_aes128_padding, int aes128_padding_size,
    bool enable_crc, bool enable_aes);
```
- 평문 뒤에 CRC16-CCITT(4바이트, 하위16비트만 유효) + 선택적 AES128 패딩을 이어붙여 기록. 마지막 16바이트 블록만 AES-ECB로 암/복호화(`remain+4+padding==16` 불변식 검증) — `ci_filesystem.c:342-401`(복호화), `ci_filesystem.c:628-734`(암호화)
- CRC 계산: `ci_crc_ccitt_calc()` 사용, 쓰기 시 계산(`ci_filesystem.c:526-538`), 읽기 시 검증(`ci_filesystem.c:404-482`)

### 2.4 `snd_fatfs_remount()` 사용법 요지

호출 규약: 부트 상태 파일 접근 시 `snd_fatfs_remount(SND_FATFS_LDRV_NUM_BOOT)`→작업→`snd_fatfs_remount(SND_FATFS_LDRV_NUM_USER_DATA)`로 반드시 사용자 드라이브로 복귀시키는 페어 호출 패턴이 전역적으로 관찰됨 — `ci_boot.c:248-254`, `271-277`; `ci_ble_control_ota.c:98-124`(주석 "디렉토리 생성 실패시 드라이브1로 되돌린다") 등.

### 2.5 파일 경로 문자열 규칙

- 대부분 모듈이 선행 `/`을 붙임: `/ISD*_INFO`, `/ISD*_USER_SETTING`, `/ISD*STAMP`, `/ISD*_MAP*` — `ci_map.h:61-79`(`*`는 ISD/맵 번호로 런타임 치환, 인덱스 상수 `ci_map.h:86-87`); `/PASS_BIN**`, `/WND_COEFF` — `ci_fft.h:22-37`(두 자리 채널번호로 치환, `ci_fft.c:18-27`); `/BOOT_STATUS.TXT` — `Gen1_5/dfu/sdk_ci_boot.h:15`
- 예외적으로 `ci_stim_mute`(`STIM_MUTE.TXT`, `ci_stim_mute.h:21`)와 `ci_event_log`(`EVENTLOG.TXT`, `ci_event_log.h:18`)는 선행 `/` 없음 — 명명 관례 불일치
- 파일명 8.3 규칙에 준하는 짧은 대문자+언더스코어 `.TXT` 확장자 패턴이 전체 공통

## 4. 쓰기 안전성

**원자적 쓰기 보호(임시파일+rename, 이중버퍼) — 발견되지 않음**: `f_rename`/`.bak`/임시파일 패턴을 FS 폴더 전체(`ci_stim_mute.c`, `ci_event_log.c`, `ci_map.c`, `ci_fft.c`, `ci_filesystem.c`, `ci_boot.c`)에서 검색했으나 관련 코드가 전무함(검색 결과 0건). 모든 쓰기는 기존 파일을 직접 열어 처음부터 덮어쓰는 in-place overwrite 방식이다(예: `ci_stim_mute.c:94-95`, `ci_filesystem.c:613-751`, `ci_event_log.c:127-135`).

**존재하는 무결성 장치**:
- 매직넘버/IDENT 필드 검증: `ci_stim_mute`(`ci_stim_mute.h:23-24`, `ci_stim_mute.c:52-56`), `ci_event_log`(`ci_event_log.h:18`, `ci_event_log.c:83-91,209-217,358-368`) — **파일별 개별 구현이며 공통 유틸리티는 없음**
- CRC16-CCITT: `ci_map`의 4개 파일 유형에만 적용(`ci_filesystem_write_with_crc_and_aes128`/`read_with_crc_and_aes128`, `ci_filesystem.c:404-482,526-538`) — `ci_fft`, `ci_boot`에는 미적용
- AES128-ECB 암호화: ISD 정보에만 적용(`ci_map.c:14`), 나머지 맵 필드는 `enable_aes=false`
- `f_sync()` 호출로 쓰기 직후 플러시: `ci_stim_mute.c:108`, `ci_filesystem.c:737,884`, `ci_event_log.c:141`, `ci_boot.c:110`(단 `f_sync`는 매체 반영을 보장할 뿐 쓰기 도중 정전에 대한 원자성은 보장하지 않음)
- 4KB 클러스터 사전 확보 트릭(`f_lseek(4096)→f_lseek(0)`): FatFs가 파일에 고정 크기 클러스터를 미리 할당하게 하려는 의도로 주석에 명시(`ci_stim_mute.c:30-32` 등) — 이 트릭이 마모 균등화(wear-leveling)나 정전 안전성과 직접 연관된다는 근거는 코드/주석에 없음(**확인 실패**, 목적은 "고정 크기 파일 생성" 정도로만 명시됨)

**전원 차단/워치독 리셋 시 결과**: 쓰기 도중 전원이 끊기면 파일 크기 또는 IDENT/CRC가 불일치하게 되고, 다음 부팅 시 해당 모듈의 `*_init()`이 이를 감지해 **하드코딩된 기본값으로 자동 재기록**한다(예: `ci_stim_mute.c:83-105`, `ci_event_log.c:111-138`). 즉 "쓰기 도중 손상을 방지"하는 것이 아니라 "손상을 사후 감지해 공장 초기화"하는 사후 복구(reset-on-detect) 전략이며, `ci_fft` PASS BIN/WINDOW 파일처럼 콘텐츠 검증이 없는 경우 손상이 감지되지 않고 그대로 사용될 위험이 있다(§3 표 참조).

**플래시 수명(쓰기 횟수) 관련 주석/고려 — 발견되지 않음**: `wear`, `endurance`, `erase cycle`, "수명", "마모", "쓰기 횟수" 등을 FS 및 관련 폴더 전체에서 검색했으나 매치 0건. 반면 §3에서 확인했듯 사용자 설정 파일(`ISD*_USER_SETTING`)은 볼륨/LED/텔레코일 등을 바꿀 때마다 즉시 쓰기가 발생하는 구조로(`cfx_cm3_sharedMemory.c:451` 등), 빈번한 조작 시 마모 누적 가능성이 있으나 코드베이스에 이를 완화하는 로직(배치 지연, 디바운스, wear-leveling)은 없다(**추정**: 사용 패턴상 문제될 가능성은 있으나 실측 근거 없음).

## 5. 초기화 순서

`Initialize()`(`src/2__cm3/Cortex-M3-src/systemControl/initialize.c:245-522`) 내 파일시스템 관련 순서:

1. `ci_filesystem_nvm_init()` — NVM 드라이버 초기화(FS 마운트 아님) — `initialize.c:259`, `ci_filesystem.c:20-38`
2. `snd_fatfs_init_mem_map()` — 공유메모리 포인터만 세팅(FS 마운트 아님) — `initialize.c:260`, `ci_filesystem.c:40-46`
3. `ci_util_assert(snd_fatfs_remount(1))` — **최초 FatFs 마운트**(사용자 드라이브) — `initialize.c:261`. 실패 시 `ci_util_assert`가 `ci_util_indicate_critical_error()`를 호출해 **적색 LED 무한 토글 루프에 영구 진입**(워치독은 루프 내에서 `SYS_WATCHDOG_REFRESH()`로 계속 리프레시되어 리셋되지 않음 — 즉 자동 복구 없이 영구 정지) — `ci_util.c:8-47`
4. `ci_power_normal()`, LED/타이머/터치 초기화 등(FS 무관) — `initialize.c:262-330` 사이
5. `snd_fatfs_remount(0)` → `ci_boot_init_fp()` → `ci_boot_handle_fsm()` → `snd_fatfs_remount(1)`: 부트 드라이브로 전환해 `/BOOT_STATUS.TXT` 처리 후 사용자 드라이브로 복귀 — `initialize.c:313-316`. `ci_boot_handle_fsm()` 내부에서 FS 오류가 나면 `_INFINITE_LOOP()`로 **영구 정지**(assert보다 더 엄격, LED 표시조차 없음) — `ci_boot.c:8-12,27-33`
6. `ci_map_init_map_data_all(false)` — `initialize.c:321` (반환값 미검사)
7. `ci_fft_init_pass_bin_all()` — `initialize.c:326` (반환값 미검사)
8. `ci_fft_init_window_coeff()` — `initialize.c:330` (반환값 미검사)
9. `ci_stim_mute_init()` — `initialize.c:334` (반환값 미검사)
10. `ci_event_log_init()` — `initialize.c:337` (반환값 미검사)
11. `ci_filesystem_copy_isd_info_from_filesystem_to_shared_memory()` + `CFX_EEPROM_data_is_Loaded=1` — `initialize.c:344-345`
12. `tdc_remote_gain_control_init()` — 주석: "인덱스 0이 뮤트이므로 CFX가 참조하기 전에 반드시 유효값을 넣어야 한다"며 `enable_CFX_trigger_for_iteration()`(`initialize.c:458`)보다 반드시 앞서야 함을 명시 — `initialize.c:347-350`

**"FS 사용 가능 이전 접근" 시 동작**: 6~10단계는 모두 3단계(최초 마운트)와 5단계(드라이브 0/1 전환) **이후**에 실행되므로 정상 흐름에서는 문제되지 않는다. 다만 3단계와 5단계는 `ci_util_assert`/`_INFINITE_LOOP()`로 **실패 시 즉시 영구 정지**(fail-fast)하는 반면, 6~10단계(`ci_map`/`ci_fft`/`ci_stim_mute`/`ci_event_log`의 `*_init()`)는 **반환값이 전혀 검사되지 않아 실패해도 부팅이 계속됨**(fail-soft) — `initialize.c:321,326,330,334,337`에 `ci_util_assert` 래핑 없음. 이는 "마운트 자체는 반드시 성공해야 하지만, 개별 설정 파일의 유효성 검증 실패는 각 모듈이 내부적으로 기본값 재기록으로 흡수한다"는 설계 의도로 해석되며, 신규 게인 변환 테이블 영속화 모듈 설계 시 이 비대칭(마운트=fail-fast, 파일별 초기화=fail-soft)을 그대로 따를지 명시적으로 결정할 필요가 있다.
