# [단계3·검증 34] QCC의 DMIC2 공유는 E8300 상시 빔포밍을 제약한다

**판정**: `CONFIRMED`

## 근거
제약은 실재하며 세 층위로 성립한다.

첫째, 감지 불가 구조: E8300이 가진 유일한 QCC 상태 신호는 I2S_FLAG(DIO29)인데, 이것만으로는 QCC가 DMIC2를 실제로 사용하는 "전화 통화" 상황과 단순 미디어 스트리밍을 구별할 수 없다(현재 상태 정리 및 복기.md). 따라서 E8300은 DMIC2 충돌 여부를 자율 판단할 수 없다.

둘째, SPI 협조 지연: 충돌 회피를 위해서는 QCC가 DMIC2 사용 시작/종료를 SPI 프로토콜로 E8300에 통보해야 하고, 이 처리에 최대 10ms 대기가 발생한다(현재 상태 정리 및 복기.md). 이 구간 동안 빔포밍은 DMIC2 입력이 유효하지 않거나 충돌 상태에 놓인다.

셋째, 클럭 경합 가능성: E8300 코드는 DMIC2(DIO17, FE)를 CLK1/DIO22 하나로만 구동할 수 있다("CLK 설정은 하나만 가능", lib_audio_in.c 주석; 조사_데이터시트-그라운딩.md §1). QCC는 CLK2(DIO10)로 DMIC2를 구동한다. 전화 통화 중 두 클럭이 동시에 DMIC2에 인가될 경우의 HW 동작(충돌·오버드라이브)이 데이터시트에서 명시 허용되지 않는다.

이 세 가지 복합으로 "상시(always-on)" 빔포밍은 전화 통화 전환 시 보장되지 않으며, 운용 모드 분리 또는 SPI 협조 프로토콜 구현이 없으면 제약은 해소되지 않는다.
