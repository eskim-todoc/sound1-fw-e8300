# service 모드 RTT 디버그 콘솔 — 요구사항

**TL;DR**: 부트로더 UART 디버그 모드와 동일한 펌웨어 파일 hex 덤프 기능을 service 모드(`service_main`)에서 RTT 입력으로 동작시킨다. 호스트 측은 auto-rtt-viewer. **출력 형식은 [`sound1-fw-extractor` 명세](../../../../../sound1-fw-extractor/docs/사용방법/Sound1%20측%20fw.txt%20출력%20명세.md) 준수 → Python 도구로 4 바이너리 자동 추출 가능**. UART 디버그 모드는 어차피 미사용이므로 폐기 (부트로더 사이즈 감소). storage init 코드는 헬퍼로 추출해 부트로더·service 공유. LED는 디버그 명령 처리 중 백그라운드 tick (정밀할 필요 없음).

## 1. 배경

### 1.1 현재 부트로더 디버그 모드 (참조 모델)

호출 경로:

```
main() → bootloader_main() → bootloader_boot() → tdc_boot_debug_mode()
                                                 → tdc_boot_handle_debug_mode()
```

[`ci_boot.c:143`](../../../../src/0__bootloader/source/bootmgr/ci_boot.c) `tdc_boot_handle_debug_mode()` 동작:

| 항목 | 내용 |
|---|---|
| 입력 | `tdc_uart_getch()` (UART RX 1바이트 폴링) |
| 명령 | `--quit`, `--print=mf`, `--print=a0`, `--print=a1`, `--print=a2` |
| 처리 | [`_print_fw_file()`](../../../../src/0__bootloader/source/bootmgr/ci_boot.c) — 64바이트 단위로 파일 hex 덤프, `rtt_printf`로 출력 + `tdc_uart_printf` 상태 메시지 |
| 진입 | 카운트다운 (`CI_BOOT_COUNT_DOWN_SEC=0`) 후 `\n` 입력 시 |

### 1.2 service 모드 현황

[`service.c:5`](../../../../src/0__bootloader/source/service/service.c) `service_main()`:

- `DIO_NUM_DMIC_CLK1_CAL` 핀 활성 시 진입 ([`main.c:74`](../../../../src/0__bootloader/main.c))
- LED RGB 8가지 색을 380 ms 주기로 순회하는 무한 루프
- 종료 조건 없음, 디버그 명령 처리 없음
- NVM/FATFS 마운트, `snd_boot_set_fp(&ohdl)` 등 storage init 미수행

### 1.3 사용자 요구

부트로더 디버그 모드와 동일한 hex 덤프 기능을 **service 모드에서** 사용. 단, **입력은 UART 가 아닌 RTT down channel**. 호스트 측은 auto-rtt-viewer(`E:\Claude\projects\auto-rtt-viewer`)로 모니터링 + stdin으로 명령 송신.

## 2. 확정 결정 사항 (사용자 승인)

| ID | 내용 |
|---|---|
| 결정_1 | 부트로더 UART 디버그 모드 코드 폐기. service에서만 RTT 디버그 콘솔 운영 |
| 결정_2 | 코드 사이즈 우선 — `bootloader_boot()`의 storage init 부분을 헬퍼로 추출, 부트로더·service 양쪽이 호출 |
| 결정_3 | service의 LED 색 8개 순회 루프 폐기. 디버그 명령 처리 루프 안에서 백그라운드로 LED tick (정밀할 필요 없음) |
| 결정_4 (Rev.4) | 헬퍼 함수 책임 = NVM/FATFS init 만. `snd_boot_set_fp` / `snd_boot_handle_file` / `tdc_boot_print_boot_file` 은 OTA DFU 이미지 슬롯 선택 영역이라 **부트로더만 호출** (`bootloader_load_app_file()` 직전, `&ohdl` 직접 사용). **service 는 슬롯 처리 자체 불필요라 3 함수 모두 호출 안 함**. 신규 `tdc_boot_get_ohdl()` getter 는 service 의 `_print_fw_file` 이 부트로더 정적 변수 `ohdl` 을 재사용용 (별도 fp 변수 폐기) |
| 결정_5 (Rev.5) | 출력 형식을 [`sound1-fw-extractor` 명세](../../../../../sound1-fw-extractor/docs/사용방법/Sound1%20측%20fw.txt%20출력%20명세.md) 준수로 변경. 5 개별 명령 (`manifest`/`app0~2`) → 단일 `dump` 명령으로 4 파일 일괄 hex 출력. 마커 = 데이터 영역 (`========== FW DUMP BEGIN/END ==========`) + 파일 (`:::FILE:<NAME>:BEGIN/END:::`). 데이터 라인 = `%02X ` × 16 B + `\n`. 데이터 영역 안 줄바꿈 LF only (외부 파싱 호환). 외부 프로그램 (sound1-fw-extractor Python 도구) 자동 파싱 → 4 바이너리 추출 |
| 결정_6 (Rev.5) | service 모드 한정 RTT up 채널 모드를 `SEGGER_RTT_MODE_BLOCK_IF_FIFO_FULL` 로 전환. 기본 NO_BLOCK_SKIP 의 buffer 가득 시 chunk 통째 drop 방지 (큰 파일 dump 데이터 누락 0 보장). BLOCK 모드는 buffer 빌 때까지 CPU stall — 인터랙티브 콘솔이라 허용. 부트로더 본체는 service_main 진입 안 하므로 영향 없음. 사용자 검증 통과 (2026-05-08) |

## 3. 목표

`service_main()`에서 다음 기능을 제공한다:

1. NVM/FATFS 초기화 (`tdc_boot_storage_init()`) — OTA 슬롯 처리는 service 미해당 (Rev.4)
2. RTT down channel 0 입력으로 명령어를 받고 펌웨어 파일 hex 덤프 (RTT up channel 0 출력)
3. 명령 처리 루프 동안 LED 색을 백그라운드 갱신 (전원 인가 표시)

부트로더 측은:

- UART 디버그 모드 코드 4개 함수 + 호출 1줄 삭제
- storage init 부분은 헬퍼로 호출

## 5. 범위

### 5.1 In-scope

- **삭제**: [`ci_boot.c`](../../../../src/0__bootloader/source/bootmgr/ci_boot.c)의 `tdc_boot_debug_mode()`, `tdc_boot_handle_debug_mode()` (정적), `_print_fw_file()` (정적), `tdc_boot_debug_mode_count_down()` (정적)
- **삭제**: [`bootloader.c`](../../../../src/0__bootloader/source/bootloader.c)의 `tdc_boot_debug_mode();` 호출 1줄
- **수정**: [`ci_boot.h`](../../../../src/0__bootloader/include/bootmgr/ci_boot.h) — `tdc_boot_debug_mode` 선언 제거, `tdc_boot_storage_init` 추가
- **추출**: [`bootloader.c`](../../../../src/0__bootloader/source/bootloader.c) `bootloader_boot()`의 NVMInit ~ `NVMSync()` 구간을 신규 함수 `tdc_boot_storage_init()`로 분리. `snd_boot_*` / `tdc_boot_print_boot_file` 은 OTA DFU 영역이라 헬퍼 외부 — **부트로더만 호출** (`bootloader_load_app_file()` 직전, `&ohdl` 직접 사용)
- **추가 (Rev.4)**: [`bootloader.c`](../../../../src/0__bootloader/source/bootloader.c) 에 `tdc_boot_get_ohdl()` getter 함수 — service.c 의 `_print_fw_file` 이 부트로더 정적 변수 `ohdl` 재사용용
- **수정**: [`service.c`](../../../../src/0__bootloader/source/service/service.c) — LED 루프 폐기, `tdc_boot_storage_init(NULL)` 호출 + RTT 디버그 콘솔 + LED tick. `_print_fw_file` 은 `tdc_boot_get_ohdl()` 로 부트로더 fp 재사용 (별도 fp 변수 폐기). OTA 슬롯 처리는 미해당 (Rev.4)
- **수정**: [`service.h`](../../../../src/0__bootloader/include/service/service.h) — 필요 시 추가 선언 (변경 없을 수도)

### 5.2 Out-of-scope

- 부트로더 부팅 시퀀스의 실제 boot 행위 (`bootloader_load_app_file`, `bootloader_boot_cm3` 등) 변경 없음
- auto-rtt-viewer 측 코드 변경 (이미 stdin → RTT down 0 송신 지원)
- 명령어 셋 확장 (Rev.5: 2 명령 = `dump` / `reboot` 으로 충분)
- LED 색 알고리즘 정교화 (단순 순회로 충분)
- SEGGER_RTT 모듈 자체 변경 (모드 전환만 service 진입 시 1회)
- sound1-fw-extractor Python 도구 측 변경 (Sound1 측 형식 준수만 책임)

## 7. 비기능 요구사항

- **코드 사이즈**: 부트로더 binary 순 증가 ≤ 100 B (수용_6). UART 디버그 코드 제거(-)와 service RTT 디버그 추가(+) 거의 상쇄, storage init 1벌만 존재. Rev.5 출력 형식 변경은 명령어 5→2 축소(-) + 마커 문자열 길어짐(+) + dump 함수 추가(+) 로 ~+50~90 B 추정
- **명령어 셋** (Rev.5): 2개 — `dump` (4 파일 일괄), `reboot` (워치독 리셋)
- **출력**: RTT up channel 0 (`rtt_printf`). UART 출력은 service 모드에서는 불필요하므로 제거 또는 최소화
- **입력**: RTT down channel 0 (`rtt_getch`), non-blocking 폴링
- **LED tick**: 단순 카운터 기반 색 순회. 정밀 주기 무관 (~380 iteration 마다 색 변환)
- **네이밍**: 루트 [`지침/코딩/네이밍 컨벤션.md`](../../../../../../docs/지침/코딩/네이밍%20컨벤션.md) `tdc_` prefix 적용
