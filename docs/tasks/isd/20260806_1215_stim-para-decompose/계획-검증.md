# 계획 검증

**TL;DR**: 3축 통과. 이번 계획의 강점은 **예측치를 숫자로 못 박은 것**이다(`for` -12 · `return` +16). 약점은 **기계 추출이 «의미» 를 검증하지 못한다**는 점이고, 그것은 실기로만 메워진다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 단계마다 검증 | 통과 |
| 불변량에 **예측치** | **통과** - 방향이 아니라 숫자다 |
| 실기 항목 | 통과 - 모드별 + 맵 전환 |
| 포맷·인코딩 | 생성 코드에 적용 |

## 축_2 - 논리 정합성

### 정합_1 - `for` -12 계산이 맞는가

맞다.

| 병합 | 원본 루프 | 병합 후 |
|---|---|---|
| `send_reference_range` | 2 블록 × (전극 루프 1 + NOP 채움 1) = **4** | 1 × 2 = **2** |
| `read_reference_burst` | 6 블록 × (읽기 루프 1 + NOP 채움 1) = **12** | 1 × 2 = **2** |
| 합 | 16 | 4 |

**-12.** ✓

### 정합_2 - `return` +16 이 맞는가

추출 함수 16개가 각각 `return` 하나씩. 원본 함수 3개의 `return` 4개(mono 1 · bi 1 · 디스패처 1 · `is_stim_para_setting_done` 1)는 그대로다. **+16.** ✓

### 정합_3 - 기계 추출이 검증하지 못하는 것

> [!CAUTION]
> **스크립트는 «코드가 옮겨졌는가» 만 보장한다.** «옮긴 코드가 여전히 옳은가» 는 보장하지 않는다.
>
> 특히 **어느 case 를 어느 함수 이름에 붙였는지**는 사람이 정한 표다. 표가 틀리면 스크립트는 그대로 틀리게 만든다. 지표도 통과한다.

**완화**: 이름 표를 각 case 앞 주석에서 뽑았다. 그리고 **디스패처가 원본 case 라벨을 그대로 유지**하므로, `case 5` 가 `flow05_` 를 부르는지 눈으로 확인 가능하다.

**남는 위험은 실기가 메운다.**

### 정합_4 - 「text 감소」 예측이 이번엔 확실한가

**중복 8블록 제거 vs 호출 16개 추가**가 겨룬다. 병합분이 훨씬 크므로 감소가 맞지만, 단계_3 처럼 순수 추출만 있었다면 증가했을 것이다. **방향만 보고 크기는 예측하지 않는다.**
