# 분석 검증

**TL;DR**: 3축 통과. §2.2 의 «`HoldOn` 을 나누지 않는다» 판단이 이 분석의 핵심이다 — **죽은 코드를 함수로 승격시키지 않는다.**

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 근거에 줄 번호 | 통과 |
| 과분해 금지 | 통과 - `case 6`·`12` 는 한 줄이지만 **상태 표의 일관성**을 위해 함수로 뺀다. 예외를 두면 «어떤 상태는 함수, 어떤 상태는 인라인» 이 되어 읽기 어렵다 |
| 추측 배제 | 통과 - 전처리기 문제를 실측으로 확인 |

## 축_2 - 논리 정합성

### 정합_1 - 한 줄짜리 case 를 함수로 빼는 것이 과분해인가

**아니다.** 과분해의 기준은 «4줄 위임을 함수로 빼면 한 줄을 감싼 한 줄 함수» 였다. 여기는 다르다 — **상태 기계의 모든 상태를 같은 형태로 두는 것**이 목적이고, 한 상태만 인라인으로 남기면 디스패처가 균일하지 않게 된다.

### 정합_2 - `HoldOn` 을 남기는 판단이 맞는가

맞다. 근거가 둘이다.

| 근거 | 내용 |
|---|---|
| 죽은 코드 승격 방지 | 285줄 중 상당수가 `#else` 안이다. 지금 나누면 **죽은 코드에 이름을 붙이게** 된다 |
| 순서 | 죽은 코드 제거(단계_1)가 먼저다. 그 뒤에 나누면 살아 있는 것만 나뉜다 |

**«남긴다» 가 «못 한다» 는 아니다.** 단계_1 이 끝나면 다시 본다.

### 정합_3 - 스크립트를 파일마다 다시 쓰는 것이 낭비인가

낭비가 아니다. **§2.1 의 차이 넷이 전부 스크립트 구조에 영향**을 준다. 하나의 범용 스크립트로 만들면 조건 분기가 늘어 스크립트 자체가 검증 대상이 된다.
