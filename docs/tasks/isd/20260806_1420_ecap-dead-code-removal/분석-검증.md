# 분석 검증

**TL;DR**: 3축 통과. §3.2 가 «다른 바이트가 몇 개이고 각각 무엇인지» 를 요구한 것이 핵심이다. 보완 1건 — **어느 `__LINE__` 이 밀리고 어느 것이 안 밀리는지** 미리 갈라 둬야 사후 확인이 검증이 된다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 근거에 줄 번호 | 통과 - §1 전수 |
| 자산 적용 | 통과 - 자산_1(`cmp -l`) · 자산_Q(타임스탬프) |
| 추측 배제 | 통과 - 조건부 `#if` 유무를 실측 |

## 축_2 - 논리 정합성

### 정합_1 - 지표를 안 쓴다는 판단이 도구 불신인가

아니다. **용도가 다르다**는 판단이다. §2 가 그 근거를 코드로 댔다(`^[[:space:]]*if` 가 `#if 0` 안도 센다).

지표는 여전히 유효하다 — 다만 **이 작업의 불변량이 «분기 보존» 이 아니라 «살아 있는 코드 보존»** 이므로 다른 자를 쓴다.

### 정합_2 - 두 겹 검증이 중복인가

중복이 아니다. **서로 다른 것을 본다.**

| 검증 | 보는 것 | 못 보는 것 |
|---|---|---|
| 살아 있는 줄 대조 | **소스**가 같은가 | 컴파일 결과 |
| `.text` 바이트 | **바이너리**가 같은가 | 왜 다른지 |

첫째만 하면 «컴파일러가 다르게 냈을 가능성» 이 남고, 둘째만 하면 **차이의 원인을 못 짚는다.**

### 누락 - 어느 `__LINE__` 이 밀리는지 미리 갈라야 한다

> [!WARNING]
> §3.2 는 «`__LINE__` 6건» 이라고만 했다. **6개가 다 밀린다면 6바이트 차이를 예상해야 하고, 일부만 밀린다면 그보다 적다.** 미리 가르지 않으면 사후에 «몇 개든 `__LINE__` 이겠지» 가 되어 검증이 아니게 된다.

**보완 - 첫 제거 지점(395줄)을 기준으로 가른다.**

| `__LINE__` 위치 | 판정 |
|---|---|
| 395줄 **앞** | **안 밀린다** |
| 395줄 **뒤** | 밀린다. 다만 **하위바이트가 우연히 같으면 차이가 안 보인다** |

따라서 예상 차이 바이트 수는 **«395 뒤에 있는 살아 있는 `__LINE__` 개수 이하»** 다. 정확한 수는 각 값의 하위바이트를 계산해야 나온다.

### 정합_3 - `TDC_PRINTF` 0건이 정말 다행인가

다행이다. 자산_1 이 기록한 함정은 **`util/tdc_printf.h:36` 이 매크로 안에 `__LINE__` 을 숨겨 `grep __LINE__` 으로 안 보인다**는 것이었다. ecap 은 그 매크로를 안 써서 소스에 보이는 6개가 전부다.

**다른 파일에 같은 작업을 한다면 이 전제가 깨진다.** `map_live` 등은 `TDC_PRINTF` 를 쓴다.

## 축_3 - 근거 검증

| 주장 | 확인 |
|---|---|
| 죽은 구역 10곳 235줄 | **실측** |
| 조건부 `#if` 없음 | **실측** - 지시자 전수 |
| `TDC_PRINTF` 0건 | **grep** |
| 살아 있는 `__LINE__` 6건 | **전처리기 마스크 적용 후 grep** |

## 판정

**통과.** 보완 1건(`__LINE__` 사전 분류)을 반영한다.
