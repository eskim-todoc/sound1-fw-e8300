# 이력 및 결과 - ecap 죽은 코드 제거

**TL;DR**: `tdc_isd_map_ecap.c` 에서 **컴파일되지 않던 267줄**을 걷어냈다(1,455 → 1,188). **`.text` 186,516바이트 중 다른 바이트가 딱 2개**이고 둘 다 `__LINE__` 즉치의 하위바이트로 정확히 설명된다. **실기가 필요 없다.**

## 배경

[분해 분석](../20260806_0834_isd-대형함수-분해-분석/분석.md) §6.1 의 **단계_1**. 분석은 이 단계를 1순위로 두면서도 **«`#if 0` 안에 되살릴 참고 코드가 있는지는 은수님만 판단할 수 있다»** 며 보류했다.

2026-08-06 은수님 — *"ecap 죽은 코드 제거해."*

## 검증 - 두 겹

### 1. 살아 있는 줄이 한 글자도 안 바뀌었다 (정적)

제거 전후에서 **컴파일되는 줄만** 뽑아 대조했다. **1,188개가 완전 일치.**

죽은 가지를 지우면서 산 가지를 건드렸다면 여기서 걸린다. 이것이 «컴파일 결과가 같다» 에 가장 가까운 정적 증거다.

### 2. `.text` 바이트 전수 비교 (자산_1 준수)

> [!IMPORTANT]
> **자산_1 이 «바이트 동일 주장은 `cmp -l` 전수 비교로» 라고 못 박았다.** 크기가 같다고 내용이 같은 것은 아니다.

원본을 되돌려 빌드하고(자산_Q - `LastWriteTime` 갱신 필수) `.text` 를 뽑아 비교했다.

```
before 186,516 바이트 / after 186,516 바이트
다른 바이트: 2개
  오프셋 48963  220 -> 65
  오프셋 49045  236 -> 81
```

**두 바이트가 정확히 설명된다.** ecap 은 `TDC_PRINTF` 가 0건이고 명시 `__LINE__` 이 살아 있는 것만 6개인데, 그중 **제거 지점보다 뒤에 있는 둘**만 밀렸다.

| 원본 줄 | 제거본 | 16진 | 하위바이트 |
|---|---|---|---|
| 68 · 218 · 361 · 373 | 그대로 | - | **동일** (제거 지점보다 앞) |
| **1244** | **1089** | `0x4DC` → `0x441` | **220 → 65** |
| **1260** | **1105** | `0x4EC` → `0x451` | **236 → 81** |

상위바이트(`0x04`)는 둘 다 같아 즉치당 1바이트씩만 달라졌다. `cmp -l` 이 낸 두 값과 완전히 일치한다.

**나머지 186,514바이트는 동일하다.**

### 3. 실기가 필요 없다

바뀐 것은 **앱에 보내는 오류 보고의 줄 번호 2개**뿐이고, 그것도 새 줄 번호를 정확히 가리킨다. 동작에 영향이 없다.

> [!IMPORTANT]
> **실기 대기가 늘지 않는다.** 코드를 지우는 변경인데도 그렇다. 바이트 수준으로 등가를 증명했기 때문이다.

## 자산

### 자산_W - 죽은 코드 제거는 «살아 있는 줄 대조» 로 검증한다

지표 대조는 이 작업에 **쓸 수 없다.** `tests/metrics.sh` 는 원시 줄을 세므로 **죽은 구역의 `if`·`for` 도 세고 있었다.** 실제로 제거 후 `if` 46→35 · `else` 19→14 · `for` 15→12 · `while` 4→3 으로 줄었다.

**이건 도구의 결함이 아니라 용도의 문제다.** 지표는 «함수 추출로 분기가 보존됐는가» 를 보는 도구이고, 죽은 코드 제거는 애초에 분기 수를 줄이는 작업이다.

**죽은 코드 제거의 불변량은 «살아 있는 줄이 같은가» 이고, 그것을 직접 대조해야 한다.**

### 자산_X - `.text` 2바이트 차이까지 설명할 수 있다

자산_1 은 «소량 바이트 어긋남은 `__DATE__` 를 먼저 의심하라» 고 했다. 이번엔 `__LINE__` 이었고, **어느 줄이 어디로 밀려 어떤 바이트가 됐는지까지** 짚었다.

**«2바이트뿐이니 괜찮겠지» 로 넘기지 않는 것이 요령이다.** 짚어 보니 4개는 제거 지점보다 앞이라 안 밀렸다는 사실까지 드러났고, 그것이 오히려 제거 범위가 의도대로였다는 방증이 된다.
