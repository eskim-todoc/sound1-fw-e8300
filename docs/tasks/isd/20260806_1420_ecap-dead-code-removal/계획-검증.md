# 계획 검증

**TL;DR**: 3축 통과. 이 계획의 강점은 **검증을 스크립트 안에 넣은 것**과 **실기 불필요 주장의 근거 사슬을 3단으로 명시한 것**이다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 단계마다 검증 | 통과 |
| 불변량이 구체적 | 통과 - «1바이트라도 다르면 실패» |
| 실기 판단 근거 | 통과 - §4 사슬 |

## 축_2 - 논리 정합성

### 정합_1 - 자기 검증을 스크립트에 넣는 것이 과한가

과하지 않다. **이 세션에서 검증을 잊거나 잘못 돌린 사례가 이미 둘 있다.**

- 지표 대조를 «의도한 변화» 로 넘길 뻔했다 (단계_3)
- 원본 재빌드가 실제로 안 됐는데 결론을 낼 뻔했다 (단계_4, `Copy-Item`)

**사람이 기억해야 하는 검증은 언젠가 빠진다.** 파일을 쓰기 전에 스크립트가 막는 편이 확실하다.

### 정합_2 - 「실기 불필요」 주장이 안전한가

안전하다. **다만 조건부다.** §4 의 3단 사슬이 전부 성립해야 하고, 어느 하나라도 어긋나면 주장이 무너진다.

특히 2단(바이트 비교)이 없으면 «소스가 같으니 바이너리도 같겠지» 라는 추론에 기대게 된다. 그 추론은 대개 맞지만 **확인 비용이 낮은데 추론에 기댈 이유가 없다.**

### 정합_3 - 구조 지표가 줄어드는 것을 «통과» 로 두는 것이 위험하지 않은가

위험하지 않다. **다만 기록은 남겨야 한다.** 지표가 줄어든 것을 보고 다음 사람이 «분기가 사라졌다» 고 오해할 수 있다.

**보완**: 구현-검증에 지표 변화량과 그 이유(죽은 구역의 분기가 세어지고 있었다)를 적는다.
