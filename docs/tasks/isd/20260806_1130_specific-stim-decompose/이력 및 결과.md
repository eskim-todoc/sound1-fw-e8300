# 이력 및 결과 - specific_stim 분해 (단계_3)

**TL;DR**: `tdc_isd_map_specific_stim_step()` **576줄 단일 함수**를 flowCounter 상태별 **12함수**로 나눴다. 함수-지역 `static` 15개를 파일 범위로 승격했고(단일 인스턴스 성질은 그대로), `case 5`·`case 7` 이 경계값만 다른 같은 코드여서 **인자 하나로 합쳤다**. **`tests/metrics.sh` 가 그 병합을 잡아내 도구 자체의 결함도 함께 드러났다.**

## 배경

[isd 대형 함수 분해 분석](../20260806_0834_isd-대형함수-분해-분석/분석.md) §6.3 의 **단계_3**. 2026-08-06 은수님 지시 — *"분해할거 다 분해하고 작성할거 다 작성하고 실기는 마지막에 몰아서 하자"*.

이 파일이 `stim_para_setting` 보다 먼저인 이유는 분석 §6.3 이 정했다 — 줄/함수가 더 나쁘고(576/1), 0x65 로 실기가 되며, **폭발 반경이 피팅 기능에 한정**된다.

## 자산

### 자산_J - metrics.sh 가 제 역할을 했고, 동시에 자기 결함을 드러냈다

`for` 지표가 **12 → 11** 로 변했다고 경고했다. 원인을 파고드니 둘이 나왔다.

**하나 - 진짜 변화**: `case 5`(전극 0~23)와 `case 7`(24~31)이 **경계값만 다른 같은 코드**였다. 인자 둘을 받는 함수 하나로 합쳐 루프 4개가 2개가 됐다. 의도한 병합이고 동작은 동일하다.

**둘 - 도구 결함**: 실제 감소는 **-2** 인데 도구는 **-1** 로 보고했다. 원본 `:587` 이 `for(;pcm_index...` 로 **`for` 뒤에 공백이 없어** 패턴 `^[[:space:]]*for \(` 에 안 걸렸다. 새로 쓴 코드는 공백이 있어 세어졌고, 그 차이가 감소분 하나를 상쇄했다.

**`tests/metrics.sh` 의 `if`·`for`·`while`·`switch` 패턴을 `[[:space:]]*\(` 로 고쳤다.** 고친 뒤 재측정하니 13 → 11 로 정확히 나온다.

> [!CAUTION]
> **자산_6 의 새 사례다.** «검증 도구의 실패 모드는 틀린 값이 아니라 매번 다른 방식» — 이번엔 **소스의 포맷 불일치가 도구를 새게 했다.** 도구가 «변했다» 고 말한 것 자체는 옳았고, 그 크기가 틀렸다.
>
> 지표가 변했을 때 «의도한 것» 이라며 넘기지 말고 **왜 그 크기만큼인지** 따져야 한다. 따지지 않았으면 도구 결함을 못 찾았다.

### 자산_K - 상태 사이로 값을 넘기는 static 은 승격이 정답이다

15개를 파일 범위로 올렸다. 함수-지역 `static` 은 **한 함수 안에서만 보이는 전역**이라, 함수를 나누는 순간 반드시 걸린다.

승격이 안전한 이유는 **단일 인스턴스라는 성질이 같기 때문**이다. 초기화 시점(프로그램 시작), 저장 위치(`.bss`), 수명(영구)이 전부 같다. `bss` 크기 불변이 그것을 뒷받침한다.

**접근자는 만들지 않았다.** 파일을 나누지 않았기 때문이다(자산_4).

### 자산_L - `pcm_index` 는 넘기고 나머지는 각자 선언한다

`pcm_index` 는 부모가 0으로 두고 `switch` 와 그 뒤 블록이 이어 쓴다. 분해할 때 갈렸다.

| 대상 | 처리 | 근거 |
|---|---|---|
| 각 flow 함수 | **각자 `= 0` 선언** | 부모가 `switch` 앞에서 0으로 두고 **한 호출에 한 case 만** 실행되므로, 모든 case 는 0에서 시작한다. 증명 가능 |
| `_output_finish` · `_output_fill` | **인자로 받음** | `switch` 가 남긴 값을 이어받는다. 실질적으로 늘 0이지만 **추론에 기대지 않는다** |
