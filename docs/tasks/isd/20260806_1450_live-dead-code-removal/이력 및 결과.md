# 이력 및 결과 - map_live 죽은 코드 제거

**TL;DR**: `tdc_isd_map_live.c` 에서 **155줄**을 걷어냈다(911 → 756). `.text` 차이는 **8바이트**이고 전부 밀린 `__LINE__` 즉치임을 **디스어셈블로 확인**했다. 부수로 **`HoldOn` 이 285 → 143줄**이 되어 추가 분해가 불필요해졌고, **자산_1 의 부정확한 기술을 바로잡았다.**

## 배경

2026-08-06 은수님 — *"map_live 죽은 코드도 제거해"*. [ecap 제거](../20260806_1420_ecap-dead-code-removal/) 에 이은 단계_1 의 두 번째다.

## 검증

### 1. 살아 있는 줄 대조 - 756개 완전 일치

> [!IMPORTANT]
> **디스어셈블까지 간 이유** — 처음 예측이 12바이트였는데 실제가 8이었다. «8이면 12보다 적으니 괜찮겠지» 로 넘기면 **왜 적은지** 를 모른 채 지나간다. 짚어 보니 예측이 틀린 것이었고, 그 과정에서 자산_1 의 오류가 드러났다.

### 3. 실기 불필요

바뀐 것은 오류 보고의 줄 번호 8개뿐이다. **실기 대기 11건 그대로다.**

## 자산_1 정정 - `TDC_PRINTF_E` 만 `__LINE__` 을 품는다

> [!CAUTION]
> **기존 자산_1 의 기술이 과장돼 있었다.**
>
> «**모든** `TDC_PRINTF_*` 호출이 `__LINE__` 을 품는다» → **틀렸다.**

`util/tdc_printf.h` 를 확인했다.

| 매크로 | `__LINE__` |
|---|---|
| **`TDC_PRINTF_E`** (`:35~37`) | **품는다** - `tdc_printf_file_func_line(__SHORT_FILE__, __func__, __LINE__);` |
| `TDC_PRINTF_W` (`:43`) | 없다 |
| `TDC_PRINTF_I` (`:49`) | 없다 |
| `TDC_PRINTF_D` (`:55`) | 없다 |
| `TDC_PRINTF_V` (`:61`) | 없다 |

`W`·`I`·`D`·`V` 는 평범한 `SEGGER_RTT_printf` 다.

**이번에 그 차이가 실제로 드러났다.** 밀린 운반체 11개 중 3개(`TDC_PRINTF_I` 2건 · `TDC_PRINTF_V` 1건)가 바이트를 안 바꿨고, 진짜 운반체만 세니 **8개 → 8바이트로 정확히 맞았다.**

**정정의 실익**: 예측이 훨씬 좁아진다. `.text` 변화를 셀 때 `grep -c "TDC_PRINTF_"` 가 아니라 **`grep -c "TDC_PRINTF_E"` + 명시 `__LINE__`** 을 세야 한다.

## 부수 성과 - `HoldOn` 이 절반으로

[impedance·live 분해](../20260806_1330_impedance-live-decompose/분석.md) §2.2 에서 `HoldOn` 285줄을 **«상당수가 죽은 `#else` 안이라 지금 나누면 죽은 코드에 이름을 붙이는 꼴»** 이라며 남겼다.

죽은 106줄을 지우니 **285 → 143줄**이 됐다. 다른 함수들과 비슷한 크기라 **추가 분해가 불필요하다.**

> [!NOTE]
> **«나중에 하겠다» 가 «안 해도 되게» 됐다.** 순서를 지킨 덕이다 - 먼저 나눴다면 죽은 코드를 담은 함수 두 개가 생겼고, 그 뒤 죽은 코드를 지우면 껍데기만 남은 함수를 다시 합쳐야 했다.
