# 분석

**TL;DR**: 죽은 구역은 **2곳 145줄**이고 그중 **106줄이 `#if 1` 의 `#else` 가지**다. 첫 지시자가 153줄이라 **그 뒤 `__LINE__` 이 전부 밀린다** — ecap(4개는 안 밀림)과 다르다.

## 1. 전처리기 구조

```
153 #if 1  ... 162 #endif                     (살아 있음, else 없음)
485 #if 1
      540 #if 0 ... 580 #else ... 646 #endif  (앞 39줄 죽음)
      620 #if 1 ... 629 #endif                (살아 있음)
662 #else  ... 769 #endif                     (뒷 106줄 죽음)
```

| 죽은 구역 | 줄 |
|---|---|
| `#if 0` 앞 가지 | 541~579 = **39** |
| `#else` 뒷 가지 | 663~768 = **106** |
| **소계** | **145** |

**조건부 `#if` 가 없다.** 전부 `#if 0`/`#if 1` 이라 판정이 확정적이다.

## 2. `__LINE__` 운반체 - 여기가 ecap 과 다르다

`map_live` 는 `TDC_PRINTF` 를 쓴다. **자산_1 은 «모든 `TDC_PRINTF_*` 가 `__LINE__` 을 품는다» 고 적었다.**

그 전제로 세면 살아 있는 운반체가 **16개**(명시 9 + `TDC_PRINTF` 7)이고, 첫 지시자(153줄) 뒤가 **11개**다.

| 구분 | 개수 |
|---|---|
| 153 앞 (안 밀림) | 5 |
| 153 뒤 (밀림) | **11** |

각 줄 번호의 상·하위 바이트를 계산하면 **예상 차이 12바이트**(하위 11 + 상위 1)다.

> [!NOTE]
> **ecap 은 4개가 안 밀렸다.** 첫 제거 지점이 395줄이라 그 앞의 `__LINE__` 이 온전했기 때문이다. 여기는 첫 지시자가 153줄로 앞쪽이라 대부분이 밀린다.

## 3. 검증 설계

ecap 과 같은 두 겹이되 **셋째를 더한다.**

| # | 검증 | 왜 |
|---|---|---|
| 1 | 살아 있는 줄 대조 | 소스가 같은가 |
| 2 | `.text` `cmp -l` | 바이너리가 같은가 |
| **3** | **차이 주소 디스어셈블** | **그 바이트가 정말 `__LINE__` 인가** |

차이가 2바이트였던 ecap 은 값 일치만으로 충분했다. **8~12바이트가 되면 «우연히 값이 맞는» 경우를 배제할 수 없다.** 명령어를 봐야 한다.

## 4. `HoldOn` 은 얼마나 줄어드는가

`HoldOn` 은 476~752(285줄)이고, 죽은 `#else` 106줄이 그 안에 있다.

**제거하면 약 179줄이 된다.** 다른 함수(`read_equalizer` 87 · `start` 86)와 비교해 여전히 크지만, 285줄일 때만큼 두드러지지는 않는다.

**분해 여부는 제거 후 실측하고 판단한다.** 지금 정하지 않는다.
