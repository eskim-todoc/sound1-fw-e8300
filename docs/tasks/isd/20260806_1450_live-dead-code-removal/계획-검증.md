# 계획 검증

**TL;DR**: 3축 통과. §3 이 «빗나가면 자산부터 의심하고, 틀렸으면 자산을 고친다» 까지 적은 것이 이번 계획의 값어치다 — 검증이 **자기 근거를 되짚는 데까지** 간다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 단계마다 검증 | 통과 |
| 예측치가 숫자 | 통과 - 12바이트 |
| 빗나감 대응 | 통과 - §3 |

## 축_2 - 논리 정합성

### 정합_1 - 「자산을 고친다」까지 계획에 넣는 것이 맞는가

맞다. **자산은 다음 사람이 근거로 쓰는 것**이라 틀린 채 두면 같은 오예측이 반복된다.

이번 예측(12바이트)이 자산_1 에 의존하므로, **빗나감은 곧 자산의 반증**이 된다. 그걸 기록하지 않으면 이 작업에서만 알고 끝난다.

### 정합_2 - `HoldOn` 기준(150/200)이 자의적이지 않은가

자의적이지만 **명시된 것이 낫다.** 근거는 «다른 함수와 비슷한가» 이고, 현재 live 의 다른 함수가 87·86·47… 이므로 150 이하면 최대치 근처, 200 이상이면 두드러진다.

**숫자를 미리 적어 두면 나중에 «크니까 나누자» 로 흘러가지 않는다.**

### 정합_3 - 디스어셈블 단계가 절차에 들어간 것이 실효가 있는가

있다. ecap 에서는 값 대조로 충분했지만 **그때도 «명령어가 무엇인지» 는 몰랐다.** 값이 맞는 것과 그 바이트가 `__LINE__` 인 것은 다른 주장이다.

## 축_3 - 근거 검증

| 주장 | 확인 |
|---|---|
| 예측 12바이트 | **계산** - 각 줄 번호의 상·하위 바이트 |
| live 의 다른 함수 크기 | **실측** |
| ecap 3단 사슬 | 해당 작업 계획 §4 |
