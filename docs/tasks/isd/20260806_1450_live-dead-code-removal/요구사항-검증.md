# 요구사항 검증

**TL;DR**: 3축 통과. 요구사항_4(«적게 나와도 원인을 찾는다»)가 이번 요구사항의 핵심이다 — 검증이 느슨해지는 지점이 바로 «예상보다 좋게 나왔을 때» 다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| **코드 전 승인** | **확보** - 2026-08-06 은수님 *"map_live 죽은 코드도 제거해"* |

| 자산 계승 | 통과 - ecap 작업이 남긴 경고를 요구사항_3 으로 받았다 |

## 축_2 - 논리 정합성

### 정합_1 - 「적게 나와도 원인을 찾는다」가 과한가

과하지 않다. **차이가 예측보다 적으면 안심하게 되는 것이 문제다.**

가능한 원인이 둘이고 성격이 정반대다.

| 원인 | 뜻 |
|---|---|
| 예측이 과했다 | **모델이 틀렸다** - 다음에도 틀린다 |
| 실제로 안 바뀐 곳이 있다 | 다행 |

**둘을 구분하지 않으면 틀린 모델을 계속 쓴다.**

### 정합_2 - 디스어셈블까지 요구하는 것이 과한가

과하지 않다. ecap 은 2바이트라 값(220→65, 236→81)이 `__LINE__` 계산과 정확히 맞아떨어져 그것으로 충분했다. **차이가 많아지면 «우연히 값이 맞는» 경우를 배제할 수 없다.**

명령어를 보면 `movs r3, #179` 처럼 **무엇을 싣는 명령인지**가 드러난다. 값 일치보다 강한 증거다.

### 정합_3 - `HoldOn` 재분해를 이 작업에 포함해야 하는가

**아니다.** 지시는 죽은 코드 제거다. 제거 후 `HoldOn` 이 얼마나 줄어드는지 보고, **분해가 여전히 필요한지는 그때 판단**한다.

죽은 코드를 지우면 285줄 중 상당수가 사라지므로 **애초에 분해가 불필요해질 수 있다.**
