# 분석 검증

**TL;DR**: 3축 통과. **다만 §2 가 자산_1 을 검증 없이 인용했다** — «모든 `TDC_PRINTF_*` 가 `__LINE__` 을 품는다» 를 사실로 받아 예측치를 세웠다. 기록된 자산이라도 근거를 확인해야 한다.

## 축_2 - 논리 정합성

### 정합_1 - 검증을 셋으로 늘린 판단이 맞는가

맞다. ecap 에서 «값이 맞으면 충분» 했던 것은 **차이가 2개뿐이라 우연의 확률이 낮았기** 때문이다. 8~12개가 되면 다르다.

디스어셈블은 **«이 바이트가 무슨 명령의 일부인가»** 를 보여주므로 값 일치보다 강하다.

### 정합_2 - `HoldOn` 판단을 미루는 것이 맞는가

맞다. **제거 후 크기를 모르는 상태에서 «분해한다/안 한다» 를 정할 근거가 없다.** 실측하고 판단한다.

이것은 회피가 아니라 순서다 - 죽은 코드를 먼저 지워야 살아 있는 것만 놓고 판단할 수 있다.

### 누락 - 자산_1 을 검증 없이 인용했다

> [!WARNING]
> §2 는 «자산_1 은 모든 `TDC_PRINTF_*` 가 `__LINE__` 을 품는다고 적었다» 를 **그대로 받아** 운반체 16개를 셌다.
>
> **기록된 자산이라도 이번 예측의 근거로 쓸 때는 확인해야 한다.** 자산은 그때의 관찰이고, 이번 파일에 그대로 적용된다는 보장이 없다.

**보완 - 예측이 빗나가면 자산부터 의심한다.** 요구사항_4 가 «적게 나와도 원인을 찾는다» 를 요구하므로, 빗나가면 `tdc_printf.h` 를 직접 확인하는 것이 첫 수순이다.

> [!NOTE]
> 이것은 [자산_3](../20260806_0834_isd-대형함수-분해-분석/분석.md) «이월 항목의 전제는 착수 시점에 자주 뒤집힌다» 의 변형이다. **자산 자체도 전제이므로 뒤집힐 수 있다.**

## 축_3 - 근거 검증

| 주장 | 확인 |
