# 계획 검증

**TL;DR**: 3축 통과. 보완 1건 — §5 가 «호스트가 6개 모드를 덮는다» 고 적었지만 **호스트가 덮지 못하는 것이 무엇인지**를 함께 적어야 실기 항목의 필요성이 선다. 명시했다.

| 항목 | 판정 |
|---|---|
| 단계마다 검증 방법 | 통과 - §2 |
| 불변량 명시 | 통과 - §4. **`text` 는 «감소» 라는 방향까지 못 박았다**(위험_4 조치의 계획-검증에서 «증가하면 통과는 검증이 아니다» 를 배웠다) |

## 축_2 - 논리 정합성

### 정합_1 - 「text 감소」가 검증 기준으로 성립하는가

성립한다. 같은 `switch` 5벌이 1벌이 되므로 **방향이 정해져 있다.** 늘어나면 통합이 안 됐거나 호출 오버헤드가 절감분을 넘은 것이고, 둘 다 조사할 이유가 된다.

다만 **크기까지 예측하지는 않는다.** 분기 5벌의 코드량과 호출 10곳의 오버헤드를 정확히 계산할 근거가 없다. 방향만 본다.

### 정합_2 - §3 의 세 가지 대비가 서로 다른 실패를 막는가

막는다. 이 작업에서 실제로 셋 다 필요했다.

| 대비 | 막는 실패 |
|---|---|
| 건수 못 박기 | 패턴 불일치로 **0건 처리** |
| 눈 확인 | 건수는 맞는데 **결과가 틀림** |
| 일괄 쓰기 | 중간 실패 시 **부분 적용** |

### 정합_3 - §5 실기 항목이 충분한가

> [!WARNING]
> **불충분했다.** «호스트 테스트가 6개 모드를 전부 덮는다» 고 적어 두면, 읽는 사람이 «그럼 실기는 왜?» 라고 묻게 된다.

**보완 - 호스트가 못 보는 것을 명시한다.**

| 층 | 보는 것 | 못 보는 것 |
|---|---|---|
| 호스트 테스트 | 모드 → 비트 값이 맞는가 | 그 비트가 **레지스터의 맞는 자리**에 들어갔는가 |
| 실기 | 내부기가 실제로 그 모드로 자극하는가 | 개별 분기의 경계값 |

**치환이 시프트를 건드리지 않았다는 것은 호스트가 증명하지 못한다.** 호출부의 `<< 2` 를 실수로 지웠어도 신규 스위트는 통과한다. 그래서 실기가 필요하다.

### 정합_4 - 실기 대기 7건을 감수할 가치가 있는가

있다. 다만 위험_4(결함 조치)와 달리 이것은 **리팩터링**이라 근거가 다르다.

| 근거 | 내용 |
|---|---|
| 선행 조건 | 단계_3·4 분해가 이 통합 없이는 복제를 늘린다 |
| 검증 자산 | **`isd/` 로직에 처음으로 호스트 테스트가 생긴다.** 이후 작업이 이 안전망 위에서 진행된다 |
| 실기 부담 | 특정자극·라이브 자극 각 1회. 이미 대기 중인 항목과 **겹친다**(`dc0442c` 의 자극 확인) |
