# 분석

**TL;DR**: **5쌍 10블록이 전부 로직상 동일함을 전수로 확인했다** — 차이는 주석·공백과 «뒤따르는 코드» 뿐이다. `tdc_shm.h` 가 SDK `hw.h` 를 끌어옴에도 **호스트 컴파일이 통과**해 열거형을 그대로 쓸 수 있다. 함수는 **2비트 값만 돌려주고** 시프트·OR 는 호출부에 남긴다.

## 1. 5쌍 전수 대조 (요구사항-검증 정합_1)

| # | 파일 | 기준전극 | 출력모드 | 스위치 대상 |
|---|---|---|---|---|
| 1 | `map_ecap.c` | `:858` | `:879` | `mappingPacket->eCapMeasurement.stimulationMode` |
| 2 | `map_ecap.c` | `:1081` | `:1103` | 동 |
| 3 | `map_specific_stim.c` | `:368` | `:386` | `mappingPacket->tdc_isd_map_specific_stim_step.stimulationMode` |
| 4 | `stim_para_setting.c` | `:189` | `:211` | `p_mapdata->stimulationMode` |
| 5 | `stim_para_setting.c` | `:907` | `:928` | 동 |

### 1.1 같은 것

| 항목 | 5쌍 공통 |
|---|---|
| 기준전극 분기 | `body`→1 · `rod`→2 · `BothRodBody`→3 · **`default`→`en__referenceNA`(0)** |
| 출력모드 분기 | 모노폴라 3종→0 · `bipolar`→1 · `commonground`→2 · `semi_simultaneously`→3 |
| 출력모드 `default` | **5쌍 전부 없음** |
| 시프트 | `w_isd_registerValue = w_isd_registerValue << 2;` 가 **각 스위치 바로 위, 스위치 밖** |

### 1.2 다른 것 - 전부 함수 밖에 남길 것들

| 차이 | 어디 |
|---|---|
| 스위치 대상 표현식 | 3종 (위 표) |
| 주석 위치·문구 | 쌍마다 다름. `specific_stim` 은 **`)` 뒤에** 설명 주석 |
| 빈 줄 | `ecap` 은 `case` 라벨 다음에 빈 줄이 있음 |
| **뒤따르는 코드** | `stim_para` 2쌍만 `sent_stimulConfig = w_isd_registerValue & 0xFF;` |

> [!IMPORTANT]
> **`sent_stimulConfig` 를 함수 안으로 끌어들이면 안 된다.** 5쌍 중 2쌍에만 있고, 나중에 «내가 쓴 값이 맞나» 비교하는 데 쓰이는 **호출부 사정**이다. 호출부에 남긴다.

## 2. 헤더 의존 실측 (요구사항-검증 정합_3)

`EN___STIMULATION_MODE` 는 `cfx_link/tdc_shm.h:67~76` 에 있고, 그 헤더는 SDK `hw.h` 를 포함한다. 호스트에서 컴파일되는지 직접 시험했다.

```c
#include <tdc_shm.h>
int probe(EN___STIMULATION_MODE m) { return (int) m; }
```

`run.sh` 와 같은 include 경로로 `gcc -std=gnu11 -Wall -Wextra` 컴파일 → **통과**.

> [!NOTE]
> **추측했다면 인자를 `int` 로 낮췄을 것이다.** 그러면 `switch` 에서 열거형 완전성 검사를 못 받고, 호출부에서 실수로 다른 정수를 넘겨도 잡히지 않는다. 실측 한 번으로 타입 안전성을 지켰다.

## 3. 함수 설계

```c
int tdc_isd_stim_mode_reference_bits(EN___STIMULATION_MODE mode);  // 비트 [3:2]
int tdc_isd_stim_mode_output_bits(EN___STIMULATION_MODE mode);     // 비트 [1:0]
```

호출부는 이렇게 된다.

```c
w_isd_registerValue = w_isd_registerValue << 2;
w_isd_registerValue = w_isd_registerValue | tdc_isd_stim_mode_reference_bits(mode);
```

### 3.1 왜 두 함수인가

한 함수로 4비트를 한꺼번에 돌려주면 **호출부의 시프트 두 번이 사라져** 레지스터 조립 흐름이 끊긴다. 이 레지스터는 상위 비트부터 한 필드씩 쌓아 올리는 구조라(`STIM_REF_HW_CTRL_DISABLE` → `SLOPE_OFFSET_RESOLUTION` → `SLOPE_SELECT` → `MP_CONFIG` → `STIM_MODE`), 두 필드만 뭉치면 오히려 읽기 어려워진다.

### 3.2 왜 테이블이 아닌가

모드가 6개뿐이고 값이 불규칙(기준전극은 열거형 값 그대로, 출력모드는 별도 매핑)하다. 배열로 만들면 **인덱스와 의미의 대응을 눈으로 못 쫓는다.** 불가침 «테이블 주도 재도입 금지» 의 기준이 «사람이 눈으로 보고 관리하기 쉬운가» 다.

### 3.3 `default` 를 어떻게 둘 것인가

| 함수 | 원본 | 통합본 |
|---|---|---|
| 기준전극 | `default` **있음** → `en__referenceNA`(0) | 그대로 |
| 출력모드 | `default` **없음** → 아무것도 OR 안 됨 = 하위 2비트 0 | **`default` → 0** |

**결과가 같다.** 원본에서 `default` 가 없어 0이 남던 것을 명시적으로 0으로 쓴다. 컴파일러 경고(`-Wswitch`)도 함께 없어진다.

> [!CAUTION]
> **여기서 «더 안전한 값» 을 고르고 싶은 유혹이 있다.** 예컨대 범위 밖이면 에러를 올린다든지. 하지만 그건 동작 변경이고, 이 작업의 불변량(요구사항_2)을 깬다. `en__referenceNA`(0)의 도달 가능성 조사는 별건으로 남긴다.

## 4. 배치

```
src/2__cm3/source/isd/tdc_isd_stim_mode_encode.c / .h
```

`isd/` 안에 두되 **순수 함수만** 갖게 한다. [위험_4 조치](../../ble/20260806_0942_map-write-range-guard/이력%20및%20결과.md) 자산_D 가 실증한 방법이다 — `isd/` 를 통째로 호스트에 올리는 대신 **검증하고 싶은 로직만 순수 함수로 떼어낸다.**

`run.sh` 에는 **자체 테스트 대상**으로 넣는다(`COMMON_SRC` 아님). 이 함수를 쓰는 것은 `isd/` 파일뿐이고 그것들은 어차피 호스트가 컴파일하지 않는다.
