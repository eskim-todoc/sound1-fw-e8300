## 3. `.text` - 예측 17개 명령어, 실제 17개

```
before 186,516 / after 186,516
cmp -l : 41바이트
```

바이트가 예측(18)과 어긋나 **두 바이너리를 각각 디스어셈블해 명령어 단위로 diff** 했다.

**바뀐 명령어 17개.** 전부 `movs`/`mov.w`/`movw rN, #<줄번호>` 이고 값 변화가 파일별 삭제량과 일치한다(−13·−24·−27·−28·−29·−34·−39·−57).

| 전 | 후 | 비고 |
|---|---|---|
| `mov.w r2, #448` | `mov.w r2, #420` | −28 |
| `movw r2, #627` | `movw r2, #593` | −34 |
| `mov.w r2, #636` | **`movw r2, #602`** | −34, **형식 전환** |
| `movw r3, #789` | **`mov.w r3, #776`** | −13, **형식 전환** |
| `movs r2, #189` | `movs r2, #165` | −24 |
| … 나머지 12개 | | |

### 3.1 왜 41바이트인가 - Thumb-2 인코딩 형식

| 형식 | 쓰임 |
|---|---|
| `MOV.W Rd, #imm` | 「modified immediate」 패턴에 맞는 값 |
| `MOVW Rd, #imm16` | 임의의 16비트 값 |

줄 번호가 밀리며 **한 형식에서 다른 형식으로 넘어가면 4바이트가 통째로** 바뀐다. 실제로 형식이 뒤바뀐 것이 **8건**이다.

> [!IMPORTANT]
> **예측은 바이트가 아니라 명령어 수로 해야 한다.**
>
> ecap(2바이트)·live(8바이트)에서 «운반체 1개 = 1바이트» 가 통했던 것은 **형식이 안 바뀐 우연**이다. 그 모델을 믿고 «41 ≠ 18 이니 뭔가 잘못됐다» 고 결론냈다면 틀렸을 것이고, 반대로 «많이 다르네» 로 넘겼어도 틀렸을 것이다.
>
> **명령어 수는 운반체 수와 1:1이라 안정적이다.**
