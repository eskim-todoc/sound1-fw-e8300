# 분석

**TL;DR**: 「컴파일 안 되는 191줄」은 **결정적 116 + 조건부 85**였다. `tdc_isd_fpga.c` 는 파일 전체가 `#ifdef` 로 I2C 경로 두 벌을 유지하는 구조라 **한 줄도 지우면 안 된다.**

## 1. 결정적 vs 조건부

| | 형태 | 판정 근거 | 지워도 되나 |
|---|---|---|---|
| **결정적** | `#if 0` · `#if 1` | **소스에 답이 박혀 있다** | **된다** |
| **조건부** | `#ifdef X` · `#ifndef X` · `#if defined(X)` · `#if !defined(X)` | **빌드 설정이 정한다** | **안 된다** |

앞선 계량(`deadcount.py`)은 «비-`#if 0` 은 첫 가지가 활성» 이라는 편의 가정으로 세어 **둘을 섞었다.**

### 2.1 `tdc_isd_fpga.c` 는 통째로 조건부다

`#ifdef CM3_I2C_controls_FPAG` 가 **16블록**이고 전부 같은 모양이다.

```c
#ifdef CM3_I2C_controls_FPAG
    if (tdc_hal_i2c_isd_read(...))     // CM3 가 직접 I2C
#else
    if (tdc_hal_i2c_cfx_read(...))     // CFX 를 거쳐 I2C
#endif
```

**FPGA 를 어느 쪽이 제어하느냐에 따라 갈리는 두 벌**이다. 한쪽을 지우면 그 설정 빌드가 통째로 깨진다.

### 2.2 `#ifndef DisalbedBackTel`

`tdc_isd_init.c`(60줄) · `tdc_isd_stim_para_setting.c`(10줄)가 이것이다. 백텔 수신을 끄는 설정에서 살아나는 코드다.

## 3. 검증 설계 - 독립성이 핵심

### 3.1 기존 검증이 왜 약한가

ecap·live 에서 쓴 «살아 있는 줄 대조» 는 이렇게 동작한다.

1. 전처리기 마스크로 «살아 있는 줄» 을 뽑는다
2. 제거 전후를 비교한다

**마스크가 «조건부의 첫 가지가 활성» 을 가정한다. 제거 스크립트도 같은 가정을 쓴다.**

따라서 `#else` 가지는 양쪽 계산에서 똑같이 «살아 있지 않은 것» 으로 빠진다. 지워지든 남든 대조 결과가 같다. **그 실수를 볼 수 없는 구조다.**

> [!CAUTION]
> ecap·live 에서 이 검증이 통했던 것은 **두 파일에 조건부 `#if` 가 하나도 없었기** 때문이다. 검증이 강해서가 아니다.

### 3.2 독립 검증기

**활성/비활성 판단을 하지 않는다. 구조만 본다.**

1. 원본과 결과를 diff 해 **지워진 줄**을 뽑는다
2. 각 줄이 원본에서 **어떤 전처리기 블록 안에 있었는지** 되짚는다
3. 감싼 것 중 하나라도 **조건부의 비활성 가지**면 잘못된 삭제다

«이 줄이 컴파일되는가» 를 묻지 않고 «이 줄이 조건부 안에 있었는가» 만 묻는다. **제거 도구와 겹치는 가정이 없다.**

### 3.3 검증기를 먼저 시험한다

**일부러 틀린 결과를 만들어 잡히는지 본다.** 1차 스크립트로 `tdc_isd_fpga.c` 를 처리한 결과(버그본)를 검증기에 넣는다.

잡지 못하면 검증기가 무딘 것이고, 그 상태로 본 작업에 쓰면 통과가 아무 뜻이 없다.
