# 이력 및 결과 - isd 죽은 코드 일괄 제거

**TL;DR**: 나머지 7파일에서 **149줄**을 걷어냈다. **그 과정에서 제 도구가 조건부 컴파일(`#ifdef`)의 `#else` 가지를 지우는 버그를 냈고, 검증도 같은 가정을 써서 통과시켰다.** 독립 검증기를 만들어 잡았다. 커밋 전에 발견했다.

## 배경

2026-08-06 은수님 *"전부 지워"*. [ecap](../20260806_1420_ecap-dead-code-removal/) · [live](../20260806_1450_live-dead-code-removal/) 에 이은 단계_1 의 마무리다.

## 착수 전 정정 - «191줄» 은 틀렸다

직전 보고에서 «남은 죽은 코드 191줄» 이라고 했는데, 그 계량이 **조건부 컴파일의 비활성 가지까지 죽은 것으로 세고 있었다.**

| 구분 | 줄 | 성격 |
|---|---|---|
| **진짜 죽음** | **116** | `#if 0` · `#if 1` 의 `#else`. 어떤 빌드 설정에서도 안 살아난다 |
| **조건부 비활성** | **85** | `#ifdef CM3_I2C_controls_FPAG` · `#ifndef DisalbedBackTel` 의 비활성 가지. **설정을 바꾸면 살아난다** |

`tdc_isd_fpga.c` 는 15줄 전부가, `tdc_isd_stim_para_setting.c` 는 10줄 전부가 조건부였다.

## 도구가 낸 버그 - 조건부 `#else` 를 지웠다

1차 스크립트(`strip_dead.py`)를 7파일에 돌린 결과다.

```
tdc_isd_fpga.c   삭제 15줄   <- 진짜 죽음이 0인데?
```

`diff` 로 보니 지워진 것이 이것이었다.

```c
#ifdef CM3_I2C_controls_FPAG
    if (tdc_hal_i2c_isd_read(i2cAddr_FPGA_version, p_readValue, 1))
#else
    if (tdc_hal_i2c_cfx_read(i2cAddr_FPGA_version, p_readValue, 1))   <- 이게 지워졌다
#endif
```

**`CM3_I2C_controls_FPAG` 를 정의하지 않는 빌드에서 살아나는 코드**다. 지우면 그 설정이 통째로 깨진다.

### 더 나쁜 것 - 검증이 못 잡았다

1차 스크립트의 검증은 «살아 있는 줄이 전후 완전 일치» 였고 **통과했다.**

**검증이 도구와 같은 가정을 쓰고 있었기 때문이다.** 둘 다 «조건부 `#if` 의 첫 가지가 활성» 이라고 보므로, `#else` 가지는 양쪽 계산에서 똑같이 «살아 있지 않은 것» 으로 빠졌다. 지워지든 남든 결과가 같다.

> [!CAUTION]
> **검증이 도구와 전제를 공유하면 그 전제가 틀린 경우를 영원히 못 본다.**
>
> ecap·live 에서 이 검증이 통했던 것은 **두 파일에 조건부 `#if` 가 하나도 없었기** 때문이다. 운이 좋았던 것이지 검증이 강했던 것이 아니다.

## 독립 검증기

가정을 공유하지 않는 검사기를 따로 만들었다.

**방식**: 원본과 결과를 diff 해 지워진 줄을 뽑고, **각 줄이 원본에서 어떤 전처리기 블록 안에 있었는지 되짚는다.** 감싼 것 중 하나라도 조건부의 비활성 가지면 잘못된 삭제다.

**먼저 버그본으로 시험했다.**

```
fpga_buggy.c
  지워진 줄: 15
  !! 조건부 비활성 가지에서 지워진 줄: 15
     45줄  [if (tdc_hal_i2c_cfx_read(...)]  <- #ifdef CM3_I2C_controls_FPAG 안
```

**15줄 전부를 정확히 지목했다.** 검증기가 작동함을 확인한 뒤 고친 스크립트에 적용했다.

## 고친 규칙

| 형태 | 처리 | 근거 |
|---|---|---|
| `#if 0 ... #endif` | **지운다** (조건부 안에 있어도) | 감싼 조건이 어느 쪽이든 컴파일되지 않는다 |
| `#if 1` 의 `#else` 가지 | 최상위면 지운다 | 동 |
| **`#if 1` 언랩** | **조건부 안에서는 안 한다** | 지시자만 없애는 미용 변경이라 얻는 것이 없고, 반복되는 `#if 1`/`#endif` 줄이라 **diff 기반 검증이 엉뚱한 위치로 귀속**시켜 판정이 흐려진다 |
| **조건부 가지 내용** | **절대 안 지운다** | 설정을 바꾸면 살아난다 |

### 남긴 것

| 구분 | 줄 |

## `.text` 검증

```
before 186,516 / after 186,516
cmp -l : 다른 바이트 41개
```

바이트 수가 예측(18)과 어긋나 **두 바이너리를 각각 디스어셈블해 명령어 단위로 diff** 했다.

**바뀐 명령어는 17개**이고, 예측한 «밀린 `__LINE__` 운반체 17개» 와 정확히 같다. 17개 전부 `movs`/`mov.w`/`movw rN, #<줄번호>` 이며 값 변화가 파일별 삭제량과 일치한다(−13·−24·−27·−28·−29·−34·−39·−57).

### 왜 41바이트인가

**Thumb-2 는 즉치를 두 형식으로 싣는다.**

| 형식 | 쓰임 |
|---|---|
| `MOV.W Rd, #imm` | 「modified immediate」 패턴에 맞는 값 |
| `MOVW Rd, #imm16` | 임의의 16비트 값 |

줄 번호가 밀리면서 **한 형식에서 다른 형식으로 넘어가면 4바이트가 통째로** 바뀐다. 실제로 `movw #789 → mov.w #776` 처럼 형식이 뒤바뀐 것이 8건이다.

> [!IMPORTANT]
> **예측은 바이트가 아니라 명령어 수로 해야 한다.** 바이트 수는 인코딩 형식에 좌우된다.
>
> ecap(2바이트)·live(8바이트)에서는 형식이 안 바뀌어 1바이트씩이었고, 그래서 «운반체 1개 = 1바이트» 라는 모델이 통했다. **그 모델은 우연히 맞았던 것이다.**

## 실기

바뀐 것은 오류 보고의 줄 번호 17개뿐이다. **대기 11건 그대로.**

## 자산

### 자산_Y - 검증은 도구와 전제를 공유하면 안 된다

이번 버그가 그것 하나로 설명된다. 스크립트와 검증이 둘 다 «조건부의 첫 가지가 활성» 을 가정해, 그 가정이 틀린 경우를 서로 못 봤다.

**독립 검증기는 다른 각도에서 봐야 한다.** 이번 것은 «지워진 줄이 원본에서 어디 안에 있었나» 를 되짚는다 — 활성/비활성 판단을 하지 않고 **구조만** 본다.

**그리고 검증기는 먼저 «알려진 버그» 로 시험해야 한다.** 버그본을 안 만들어 봤으면 새 검증기가 통과해도 그게 «안전해서» 인지 «검증기가 무딘» 것인지 몰랐다.

### 자산_Z - `#if 0` 과 `#ifdef` 는 성격이 다르다

| | 의미 | 지워도 되나 |
|---|---|---|
| `#if 0` / `#if 1` | **결정적** - 소스에 답이 박혀 있다 | **된다** |
| `#ifdef X` / `#if defined(X)` | **조건부** - 빌드 설정이 정한다 | **안 된다** |

«컴파일되지 않는 줄» 로 뭉뚱그려 세면 둘이 섞인다. **계량 단계에서부터 갈라야 한다.**

`tdc_isd_fpga.c` 는 파일 전체가 `#ifdef CM3_I2C_controls_FPAG` 로 I2C 경로 두 벌을 유지하는 구조다. 그걸 «죽은 코드 15줄» 로 보고한 것이 애초의 잘못이었다.

### 자산_AA - Thumb-2 즉치는 인코딩 형식이 바뀔 수 있다

`.text` 차이를 예측할 때 **«운반체 1개 = 1바이트» 는 우연**이다. `MOV.W`(modified immediate)와 `MOVW`(imm16) 사이를 오가면 4바이트가 통째로 바뀐다.

**예측은 명령어 수로 하고, 바이트 수가 어긋나면 디스어셈블해 명령어 단위로 대조한다.**

## 남은 것

`isd/` 의 진짜 죽은 코드는 **9줄**(조건부 안의 `#if 1`/`#else`). 조건부 비활성 85줄은 **보존이 맞다.**
