# 분석 검증

**TL;DR**: 3축 통과. §3.1 의 «기존 검증이 왜 약한가» 가 이 분석의 값어치다 — **자기가 두 번 쓴 방법의 한계를 짚었다.**

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 근거에 실측 | 통과 - §2 파일별 |
| 추측 배제 | 통과 - 계량 방식 자체를 고쳐 다시 셌다 |

## 축_2 - 논리 정합성

### 정합_1 - 「결정적/조건부」 구분이 완전한가

거의 완전하다. **경계 사례가 하나 있다.**

`#if 0` 이 **조건부 영역 안에** 있으면? 감싼 조건이 어느 쪽이든 그 안은 컴파일되지 않는다. **지워도 된다.**

반대로 `#if 1` 언랩은 지시자만 없애는 미용 변경이라 **조건부 안에서 얻을 것이 없고**, 반복되는 `#if 1`/`#endif` 줄이라 diff 기반 검증이 엉뚱한 위치로 귀속시킨다. **하지 않는다.**

### 정합_2 - 독립 검증기가 정말 독립인가

**부분적으로 독립이다.** 전처리기 지시자를 파싱한다는 점은 같다. 하지만 **활성/비활성을 계산하지 않는다** — 그것이 버그의 원인이었던 가정이다.

완전한 독립은 «다른 컴파일러로 전처리해 비교» 겠지만, 이 검증기는 **틀린 가정을 공유하지 않는다**는 핵심 조건을 만족한다.

### 정합_3 - §4 예측을 「명령어」로 바꾼 것이 맞는가

맞다. live 작업에서 «운반체 1개 = 1바이트» 모델이 통했지만, 그건 **인코딩 형식이 안 바뀐 우연**이었다. Thumb-2 는 `MOV.W`(modified immediate)와 `MOVW`(imm16) 두 형식을 쓰고, 값이 형식 경계를 넘으면 명령어 전체가 바뀐다.

**명령어 수는 운반체 수와 1:1이라 안정적이다.**
