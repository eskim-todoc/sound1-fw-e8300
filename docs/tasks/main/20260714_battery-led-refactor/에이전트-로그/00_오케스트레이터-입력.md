# 오케스트레이터 입력: 배터리·LED 리팩토링 분석 fan-out

**TL;DR**: 배터리 percent→LED 재캡슐화·마진 제거 분석을 4개 병렬 페르소나(현 데이터흐름 / 과거 updateBatteryLevel 해부 / QCC 소스·마진제거 안전성 / 재캡슐화 설계·LED arbiter 결합) + 반증 검증 1노드로 fan-out. 모든 노드 `model: sonnet`, effort 세션 상속. 각 노드는 자기 로그 파일을 직접 Write.

## 위임 설계

| 노드 | 역할 | 핵심 질문 | 로그 파일 |
|---|---|---|---|
| 01 | 현 배터리→LED 데이터 흐름 해부 | 배터리 블록(542~578)·매핑 블록(620~654)의 히스테리시스가 정확히 어떤 상태 전이를 만드는가? 순서 의존·static 상태·override 경로는? | `01_current-flow-analyst.md` |
| 02 | 과거 `updateBatteryLevel()` 해부 + 부활 타당성 | 레거시 함수의 구조(7단계 enum·추세반전방지 마진·CFX 자체측정)는? QCC 구조에서 직접 부활 가능한가, 무엇을 포팅할 가치가 있는가? | `02_legacy-updatebatterylevel-analyst.md` |
| 03 | QCC 배터리 소스 신뢰성 + 마진 제거 안전성 | QCC가 percent/state/level을 어디서 어떻게 주입하는가? 이미 필터링된 값인가? E8300 마진 제거 시 채터링 위험이 실재하는가? | `03_qcc-source-margin-analyst.md` |
| 04 | 재캡슐화 설계 옵션 + LED arbiter 결합 | 신규 `tdc_` 함수 시그니처·상수/테이블 설계 옵션(percent 임계 vs 7단계 레벨). LED_SRC arbiter·override·ISD 재송출 순서 보존 방안은? | `04_recapsulation-design-analyst.md` |
| 06 | 반증 검증 (adversarial) | 01~04 종합을 회의적으로 검증 — 마진 제거 안전성 주장·설계 제안의 동작변경 위험·누락 caller·할루시네이션 적발 | `06_adversarial-verify.md` |
