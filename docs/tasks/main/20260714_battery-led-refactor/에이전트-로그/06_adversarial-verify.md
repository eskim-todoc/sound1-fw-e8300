### 1.8 발견된 사실관계 오류 (할루시네이션은 아니나 부정확)

**오류 A (03) — veryLowBattery 밴드 폭 오기재**: 03은 §3.2 표에서 `systemControl.c:251-255`의 veryLowBattery를 "단일 판정, 다만 **20%p 폭** 저전력 밴드"라 서술했다. 그러나 실제 코드(`systemControl.c:251~253`)를 직접 읽으면:
```c
251  if ((batteryLevel == en__batteryPower_0per)         // 원래 0per만 저전력 인데
252      || (batteryLevel == en__batteryPower_0btw20)    // 0~20per 랑
253      || (batteryLevel == en__batteryPower_20btw40))  // 20~40per 도 저전력으로 처리 즉, 40per 미만이면 저전력
```
코드 자체 주석이 "40per 미만이면 저전력"이라 명시한다 — 즉 3개 티어(0per, 0~20, 20~40)를 OR로 묶어 **밴드 폭은 40%p**(0~40%)이지 20%p가 아니다. **사실관계 오류로 판정(refuted)**. 다만 이 오류는 03의 결론(veryLowBattery는 편도성·비가시성 때문에 마진 없이도 안전하다는 논증)을 훼손하지 않는다 — 오히려 밴드가 더 넓을수록 경계 재통과 빈도는 더 낮아지므로 03의 논지는 그대로 유지된다. 계획 문서 작성 시 이 수치만 정정 권장.

**오류 B (02) — `ci_battery_init()` "지금도 호출" 오기재**: 02는 §5에서 "`calculationBatteryBoundary()`는 `ci_battery_init()`(`ci_battery.c:59`)에서 **지금도 호출되어** `batteryBoundary`를 채우지만... 부수효과 없는 낭비성 호출이다"라고 서술했다. `ci_battery_init()` 심볼을 `src/` 전체에서 재검색한 결과, 정의(`ci_battery.c:28`)·선언(`ci_battery.h:37`)을 제외한 유일한 호출 지점은 `initialize.c:362`이며, 그 줄은 **주석 처리**돼 있다:
```c
361  // 더 이상 EZ에서 배터리 측정하지 않음
362  // ci_battery_init();  // 배터리 측정을 위한 초기화
```
즉 `ci_battery_init()`은 런타임에 **전혀 호출되지 않는다** — "지금도 호출되어"는 사실과 다르다(**refuted**, 부분적). `calculationBatteryBoundary()`가 `ci_battery.c:59`에서 호출되는 것 자체는 맞지만(코드 존재 확인), 그 바깥 함수(`ci_battery_init`)가 죽어있으므로 실행되지 않는다. 이는 02의 **결론을 오히려 강화**한다(dead code 사슬이 02가 판단한 것보다 한 단계 더 깊다: `updateBatteryLevel()`뿐 아니라 그 캘리브레이션 준비 경로 자체도 미실행) — 하지만 "지금도 호출되어"라는 구체적 서술은 정정이 필요하다.

**논증 미비 (02) — 레거시 래칫 "완전 대칭"에 대한 판단 재검토**: 02는 §2에서 방전 분기의 100% 상한 체크(`prev_batteryLevelStatus > en__batteryPower_100per`, 항상 거짓)와 대비해, 충전 분기의 0% 하한(`batteryNPowerControl.c:501~504`)이 `prev_batteryLevelStatus` 비교 없이 무조건 대입되는 것을 "버그라기보다 가장 바깥쪽 티어는 갈 곳이 없다는 자연스러운 귀결"이라 판단했다. 직접 대조 결과, 두 경우는 **대칭이 아니다**:
- 방전 100% 상한 체크(`prev > 100per`, 항상 거짓) — 방전 중 노이즈로 배터리가 100%로 "역주행"하는 것을 막는 정상적 래칫 방향(의도대로 동작).
- 충전 0% 하한(무조건 대입) — 충전 중인데도 전압이 순간적으로 0% 경계 아래로 노이즈성으로 떨어지면 `prev_batteryLevelStatus`가 무엇이든(예: 80%) **무조건 0%로 급락**시킨다. 이는 "충전 중엔 감소하지 않는다"는 래칫의 핵심 전제를 정확히 그 반대 방향(급격한 하락 허용)으로 깨는 코드다 — 방전 100% 케이스처럼 "막다른 방향이라 문제 없음"이 아니라 **그 자체로 래칫에 뚫린 구멍**이다.
이 함수 자체가 dead code(§1.3)이므로 실무 영향은 없으나, "완전 대칭은 아니다"라는 02의 관찰은 맞았지만 그 이유("갈 곳이 없어서")는 부정확한 유추다.

**TL;DR·본문 불일치 (04) — 옵션 C 그리드 "정확히 일치" 과장**: 04의 TL;DR은 "매핑 블록의 LOW 컷(20%)이 [level] 그리드와 **정확히 일치**"라 단언하지만, 본문 §4는 스스로 `en__batteryPower_0btw20`이 `0 < percent < 20`(20 미만, 20 배제)이므로 현재 매핑 컷 `pct <= 20`(20 포함)과 **`pct==20` 경계에서 어긋난다**고 명시한다(실제 `snd_batt_get_level()` 코드 79행 `(0 < percent) && (percent < 20)`으로 재확인 — 정확). TL;DR의 "정확히 일치"는 과장이며, 본문의 정밀한 캐비어트와 모순된다. 할루시네이션은 아니고(본문이 스스로 교정), 향후 `분석.md`/`계획.md`에 이 TL;DR 문구를 그대로 옮기지 않도록 주의가 필요하다.

## 2. 마진 제거 안전성 반박 시도 — 결과: 반박 실패(안전 지지 유지) + 신규 게이트 후보 1건 제안

과제에서 제시된 4개 시나리오를 각각 코드 근거로 공격해봤다.

1. **QCC percent 노이즈 시나리오**: E8300 쪽에 클램프·평활화가 전혀 없음(`batteryNPowerControl.c:42~45` 재확인)은 사실이나, QCC 펌웨어 자체가 이 저장소에 없어 노이즈 유무를 코드로 확정할 수 없다는 03의 판단은 **재검증해도 동일**하다. 반박 실패.
2. **0x34 수신 주기가 느려 pct가 튀는 시나리오**: `func_normal()`의 while(1) 메인 루프는 `iterationFlag`마다 매우 빠르게 반복되는 반면, `pct`는 `snd_batt_get_percent()`로 조회만 할 뿐 0x34 수신 이벤트(`ble_communication.c:227, 250` 재확인 — SPI 이벤트 구동, 고정 주기 아님) 시에만 갱신된다. 즉 두 0x34 메시지 사이의 모든 메인 루프 반복은 **동일한 pct**로 동일한 `batt_st`를 재계산하므로, 마진 유무와 무관하게 chattering이 발생할 수 없는 구간이다 — chattering은 오직 "연속된 0x34 메시지의 percent 값 자체가 경계에서 실제로 오락가락"할 때만 발생 가능하며, 이는 03이 이미 "확인 불가"로 정리한 QCC 내부 동작에 전적으로 의존한다. **새로운 공격 경로를 찾지 못함 — 반박 실패**(오히려 03의 결론을 보강: 메인 루프 속도는 무관 변수임을 확인).
3. **RESET→정상 전이 순간**: RESET 게이트(`main.c:558`)는 마진 제거와 독립적으로 항상 최우선 적용되므로(01·03·04 공통 결론, 코드 재확인 완료), 전이 직후 첫 pct 평가는 "새 상태"로 1회성 분류일 뿐 진동이 아니다. 이후 연속 0x34가 경계에서 실제로 흔들리는지는 다시 시나리오 1과 동일한 미확정 영역으로 귀결된다. 반박 실패.
4. **충전기 착탈 순간(신규 시나리오, 03 미다룸)**: `ble_communication.c:135~152`의 `charger_connected` 분기에는 디바운스가 전혀 없다 — 커넥터가 기계적으로 접촉 불량(바운스)일 경우 0x34 메시지마다 DISCHARGING/CHARGING 상태가 빠르게 토글될 수 있다. 레거시 `updateBatteryLevel()`이 충전/방전 각각 다른 전압-퍼센트 환산 경계를 뒀던 사실(`batteryNPowerControl.c:185~197`, 동일 전압에서도 충전 중엔 내부저항으로 단자전압이 높게 측정됨)에 비추어, **QCC도 유사한 충전상태별 보정을 내부적으로 적용할 개연성**이 있다(단, QCC 펌웨어 미확인 — 추정). 이 추정이 맞다면 커넥터 바운스 시 동일한 실제 SOC임에도 충전/방전 전환마다 percent 값이 순간적으로 몇 %p씩 뛸 수 있고, 그 폭이 임계값을 걸칠 만큼 작다면(±2%p 이내) **현재의 마진(sticky band)은 이를 흡수하지만 마진 제거 후 단일 임계는 매 토글마다 LED를 반짝이게 만들 수 있다**. 이는 03이 명시적으로 열거하지 않은 시나리오다 — **반박 시도는 부분적으로 유효한 신규 위험 후보를 발굴했으나, QCC 내부 동작 미확인으로 확정할 수 없어 "반박 성공"으로 판정하지는 않는다.** §3.4 실측 게이트에 "충전기 커넥터 바운스 중 percent 값 로깅"을 추가 항목으로 제안한다.

**최종 판정**: 03의 "조건부 안전(실측 게이트 필요)" 결론은 **반박되지 않았다(반박 실패 — 안전 지지 유지)**. 다만 실측 게이트 목록에 "충전기 착탈/커넥터 바운스 구간 percent 로깅" 1건을 추가할 것을 권고한다.

## 3. 설계 옵션 검증

### 3.1 옵션 B(테이블 구동) — 현재 동작 보존 여부

04가 제시한 테이블(`{80,READY},{10,MID},{0,CRITICAL}`, 내림차순, `for`+`pct>=min_pct`+`break`)을 pct=0~100 전 구간에 대해 수동 트레이스했다:

| pct | 순회 결과 | 옵션 A(단일 임계) 결과 | 일치 여부 |
|---|---|---|---|
| 85 | i=0에서 85≥80 매치 → READY | READY | 일치 |
| 50 | i=1에서 50≥10 매치 → MID | MID | 일치 |
| 10 | i=1에서 10≥10 매치 → MID | MID(pct<10 아니므로) | 일치 |
| 5 | i=2에서 매치(fallback) → CRITICAL | CRITICAL | 일치 |

**부등호 방향·순회 방향 오류 없음** — 내림차순 정렬 + `>=` + 첫 매치 우선(`break`) 조합이 정확히 "가장 높은 min_pct부터 확인해 처음 만족하는 구간 채택"으로 작동하며, 이는 요구사항이 요청한 단일 임계 매핑(옵션 A)과 **완전히 동일한 결과**를 낸다. RESET→IDLE 최우선 분기는 `for` 루프 진입 전 `if(!ovr_batt_active && batt_is_reset_state)`로 분리돼 있어 보존되고, override 2단 패턴(입력 override는 호출부 계산·출력 게이트는 함수 내부 `led_request` 직전)도 옵션 A와 동일 위치에 유지된다. ISD 재송출용 `return batt_st;`도 보존된다. **04가 스스로 지적한 "정렬 불변식이 깨지면 조용히 오분류"라는 리스크(리뷰 의존)는 실제로 유효한 유일한 취약점**이며, 이는 04가 이미 명시했으므로 새로운 결함은 아니다. **검증 결과: 결함 없음(옵션 B 골격은 안전)**.

### 3.2 옵션 C — 매핑 20% 그리드 일치 주장 재검증

`snd_batt_get_level()`(`batteryNPowerControl.c:47~88`)의 실제 경계는 `(0 < percent) && (percent < 20) → en__batteryPower_0btw20`, `(20 <= percent) && (percent < 40) → en__batteryPower_20btw40`이다. 현재 매핑 블록의 LOW 컷은 `pct <= 20`(진입, 20 포함)이다. `snd_batt_get_level() <= en__batteryPower_0btw20`로 옵션 C를 구현하면 `pct < 20`(20 미만)이 되어, **`pct == 20`일 때 두 방식이 다른 결과**(현재: LOW / 옵션 C: READY)를 낸다. 04는 §4 본문에서 이 어긋남을 정확히 인지·명시했다(§1.8 "TL;DR·본문 불일치" 참조) — **본문 수준에서는 검증 통과, TL;DR 수준에서는 과장 — 앞서 §1.8에 반영**.

## 4. 누락·모순 검증

- **`snd_batt_get_level()`이 히스테리시스 없는 margin-free 함수인지**: `batteryNPowerControl.c:47~88` 전문을 직접 읽어 확인 — `static`/`prev_*` 변수 일절 없이 매 호출 `snd_batt_get_percent()`를 그 자리에서 재분류하는 순수 함수임을 **직접 코드로 확인(confirmed)**. 02·03·04의 공통 주장과 일치.
- **`updateBatteryLevel()` 완전 dead code 주장**: §1.3에서 재확인 — grep 결과 정의·선언·주석 처리된 호출 1곳 외 참조 없음. **확인됨(confirmed)**, 오히려 그 준비 경로(`ci_battery_init`)까지 죽어있음을 추가로 확인(§1.8 오류 B).
