# 오케스트레이터 입력

**TL;DR**: 6노드 fan-out(구역 분석 5 + 검증 1) — `main.c`의 `func_normal()`(320~723행, ~400줄)을 5개 구역으로 나눠 각 구역의 책임·숨은 상태(static 변수)·결합도를 분석하고, 특히 배터리/ISD/매핑 LED 요청 로직(526~643행)의 문제점을 정리해 함수 분해 계획의 근거로 삼는다.

## 원본 입력

> "노말 함수의 코드가 너무 하드코딩 느낌이라 보기가 어려워. 함수로 쪼개든, 코드를 리팩토링 하던 해야할거 같아. 특히 배터리 레벨에 맞춰 led 설정하는게 지저분 해. 새 작업이니 브랜치도 새로따고 작업 폴더도 만들고해서, 새 작업 시작해. 여러 페르소나 돌리고, 분석 및 계획 세워봐"

## 요구 해석

`main.c:320-723`의 `func_normal()`을 grep으로 확인 — 부팅 대기 루프+ISD 정보 출력(320-421), iteration 루프 내부(423-720: 센서 읽기+fake_0x34 디버그(423-473), 시스템 서브모듈 호출 체인(475-524), LED 소스 요청 블록(526-643, 배터리 히스테리시스+ISD+매핑), NRF/UI polling(645-657)), iteration 밖 절전 전이 로직(659-720: QCC 타임아웃, 크래들 뚜껑, systemOff/sleep). 400줄 단일 함수 안에 중첩 `#ifdef`, 매직넘버(주석 처리된 구값), static 변수가 섞여 있어 "하드코딩 느낌"이라는 지적과 부합. 은수님이 "특히"로 지목한 배터리 LED 부분(526-566)이 가장 심각 — pct 임계값(40/41/65/64)에 옛값(10/12/80/78)이 주석으로 남아있고, `prev_batt_st` static 변수와 `#ifdef ENABLE_UI_CMD` 오버라이드가 로직과 뒤섞여 있음.

이번 지시는 "여러 페르소나"(트리거어) → dynamic workflow로 섹션별 분석 후, 분석 결과를 바탕으로 함수 분해 계획(계획.md)까지 세우라는 것으로 해석.

## 위임 설계 근거

- [x] 왜 이 분해(5구역+검증 1) — `func_normal()`이 자연스럽게 5개 순차 구역(부팅/센서읽기/시스템제어호출/LED요청/절전전이)으로 나뉘고, 각 구역이 서로 다른 static 변수·결합 패턴을 가져 독립 조사가 가능함
- [x] 어떤 패턴 — **parallel**(01~05, 서로 다른 코드 구역 read-only 탐색) → **adversarial-verify**(06, 분해 시 누락될 수 있는 숨은 상태/결합을 반증). 단계②는 read-only라 승인 게이트 이전에도 허용
- [x] 모델·effort — 전 노드 `Sonnet`, effort 미지정(세션 상속)
