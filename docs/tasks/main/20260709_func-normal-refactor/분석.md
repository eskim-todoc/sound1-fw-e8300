# 분석: func_normal() 리팩토링

**TL;DR**: `func_normal()`(`main.c:334-742`, ~408줄)은 부팅당 정확히 1회만 실행되는 단일 거대 함수로, 5개 구역(부팅시퀀스·센서읽기+QCC타임아웃감지·시스템서브모듈 호출·LED 3분기 요청·절전전이)이 한 스코프에 뭉쳐 있다. 은수님이 지목한 배터리 LED 블록은 배터리→ISD→매핑 순서 의존 체인이며 각각 독립된 `static` 상태(`prev_batt_st`/`s_map_low_active`)를 갖고 있어 그대로 함수로 캡슐화 가능하다. 5페르소나+반증검증으로 모든 static/지역변수 생명주기와 구역 간 결합을 확인했고, 검증 과정에서 원 지시 라인 범위가 실제보다 19줄 짧아 `fake_func_sleep()` 탈출 경로가 분석 밖에 남는 빈틈을 발견해 직접 보완했다.

## 1. 현 상태 (Current State)

### 1.1 `func_normal()` 실행 모델 — "재진입"이 아니라 "매번 리부팅"

`main.c:323-327`의 최상위 구조:
```c
while (1)
{
    func_normal();
    func_sleep();
}
```
`func_sleep()`은 ULP 루프에서 정상 반환하지 않고 항상 `SYS_WATCHDOG_RESET()`(워치독 리셋, 칩 재시작)으로 끝난다(`main.c:1158`, "도달 불가" 주석 명시). 즉 **`func_normal()`은 부팅(또는 절전 중 리셋)당 정확히 1회만 실행**되며, "절전 복귀 후 함수가 다시 도는" 멘탈 모델은 이 아키텍처와 다르다 — 매번 완전히 새로운 스택/전역 초기화 상태에서 시작한다. 이 사실이 이후 모든 static 변수 분석의 전제가 된다.

### 1.2 5개 구역 + 누락분 발견

| 구역 | 실측 라인 | 담당 | 핵심 내용 |
|---|---|---|---|
| ① 부팅시퀀스 | 334-435 | 01 | CFX 시작 대기 busy-wait, `Initialize()`, ISD1 정보 RTT 로그 |
| ② 센서읽기+QCC타임아웃감지 | 437-485 | 02 | 5종 센서 읽기 + `#if 1`(상시 컴파일) fake_0x34 QCC 대체 디버그 블록 |
| ③ 시스템제어 오케스트레이션 | 492-536 | 03 | `systemControl→update_mapNum→isd_interface→bleCommunication→stimulation/PMIC` 호출 체인 + 모드 플래그 분기 |
| ④ LED 3분기 요청 (핵심) | 538-655 | 04 | 배터리/ISD/매핑 LED 상태 결정 — 은수님이 직접 지목한 부분 |
| ⑤ 절전전이 (전반) | 657-728 | 05 | NRF/UI polling, QCC 타임아웃→POWER_OFF, 크래들 뚜껑, systemOff 가드+`break` |
| ⑥ 절전전이 (누락분, 직접 보완) | 730-742 | 오케스트레이터 | `fake_func_sleep()` 탈출 경로 + 마무리 watchdog refresh/wait-for-interrupt |

> [!IMPORTANT]
> **반증 검증에서 발견된 프로세스 실수**: 페르소나 fan-out 설계 시, 직전 작업(LED ISR 리팩토링)의 다른 브랜치에서 라인 번호를 확인한 뒤 브랜치를 전환해 이번 브랜치(`claude_develop` 기준)에 그대로 전달하는 바람에 지시 범위(320~723행)가 실제 함수 범위(334~742행)와 어긋났다. 대부분의 페르소나는 파일을 직접 읽으며 스스로 라인을 정정했으나, 05번 담당 구역만 지시받은 상한(723행)을 그대로 따라 실제 함수 끝(742행)까지 19줄을 다루지 못했다. 검증 노드가 이를 정확히 짚어 §1.2 ⑥으로 직접 보완했다 — adversarial-verify 패턴이 실제로 값을 발휘한 사례.

### 1.3 누락분 보완 — `fake_func_sleep()` 탈출 경로 (직접 확인)

```c
730  if (tdc_get_fake_op_mode() == 1)  // fake sleep mode가 맞을 때
731  {
732      ci_printw("[GD] try to enter fake sleep mode. \r\n");
733      led_force_fade_off();
734      fake_func_sleep();
735  }
736
737  SYS_WATCHDOG_REFRESH();
738  SYS_WAIT_FOR_INTERRUPT;
739  }  // 끝, while
740
741  return 0;
742  }
```

`fake_func_sleep()`(`main.c:810-1031`)을 직접 확인한 결과, 이 함수도 `func_sleep()`과 동형으로 **정상 반환하지 않는다** — 내부 `while(1)` ULP 대기 루프로 진입하고 함수 말미의 `return 0;`(1030행)에는 "도달 불가" 주석이 달려 있다. 즉 `func_normal()`에는 `break`(726행, systemOff 경로)와 별개로 **`fake_func_sleep()` 진입이라는 두 번째 비반환 탈출 경로**가 존재한다.

> [!NOTE]
> **작업 간 연계 사항**: `fake_func_sleep()`/`tdc_get_fake_op_mode()`/`tdc_set_fake_op_mode()`는 별도 진행 중인 `claude_feature_led-isr-table-refactor` 브랜치에서 이미 **전체 삭제**하기로 은수님이 결정한 코드다("더 이상 필요 없어서 제거하자, BLE 쪽에서도 안 써"). 그 브랜치가 먼저 병합되면 이 탈출 경로 자체가 사라진다. 이번 작업(`func_normal()` 분해)을 그 브랜치 병합 전에 진행할지 후에 진행할지에 따라 §4 결정_7의 처리 방식이 달라진다 — §3.2 선택지 참조.

### 1.4 발견된 죽은 코드 (검증 노드가 지적)

| 대상 | 위치 | 내용 |
|---|---|---|
| `conneded_ISD` | `main.c:347` | 지역변수 선언 후 프로그램 어디서도 읽거나 쓰이지 않음(구조체 필드 `isd_state.conneded_ISD`와 이름만 겹침) |

세 항목 모두 컴파일 결과에 영향 없는 단순 삭제 대상(behavior-preserving)이나, 이름이 실제 사용 중인 구조체 필드와 겹쳐 향후 grep/치환 작업 시 혼동 소지가 있다.

## 3. 가설·선택지

### 3.2 선택지 (설계 결정)

**선택지 A — 분해 범위**

| 선택지 | 장점 | 단점 |
|---|---|---|
| LED 3분기(④)만 분해 | 은수님이 지목한 부분에 집중, 위험 최소 | 나머지 구역(①②③⑤)의 "하드코딩 느낌"은 그대로 남음 |
| 5구역 전부 분해(권장) | 함수 전체가 읽기 쉬워짐, 페르소나 분석이 이미 전 구역 완료 | 변경 범위·commit 수 증가, 회귀 검증 부담 증가 |

**선택지 B — `fake_func_sleep()` 3번째 탈출 경로 처리**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 이번 작업에서 반영(3-state 반환값) | 지금 당장 완결된 분해 | 다른 브랜치 병합 후 곧바로 삭제될 코드에 설계 공수 투입 |
| 이번엔 최소 처리(원본 그대로 남겨두고 함수 분해 대상에서 제외) | 낭비 공수 없음, 다른 브랜치 병합 후 자연스럽게 정리 | 이 부분만 여전히 원본 인라인 코드로 남아 완전한 리팩토링은 아님 |

**선택지 C — dead 변수/매직넘버 정리**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 이번에 같이 정리(삭제/상수화) | 한 번에 깔끔 | 순수 구조개선 범위를 살짝 넘음(그래도 동작 불변) |
| 정리 안 하고 그대로 이관 | 최소 변경 | "하드코딩 느낌" 일부 잔존 |

## 4. 핵심 결정

- 결정_1: **분해 범위는 5구역 전부**로 한다 — 페르소나 분석이 이미 전 구역을 커버했고, 은수님 지시("함수로 쪼개든 리팩토링 하던")가 LED 부분에 한정되지 않음.
- 결정_2: **LED 3분기(④)를 최우선 1번 커밋**으로 — `tdc_led_request_battery()`/`tdc_led_request_isd()`/`tdc_led_request_mapping()` 3개 함수, 04번 문서의 구체 코드 제안 채택(시그니처·순서·static 처리 전부 검증 완료).
- 결정_3: **센서읽기+QCC타임아웃(②)** — `tdc_read_sensor_snapshot()`(구조체 반환) + `tdc_qcc_batt_check_timeout()`(bool 반환). 호출부는 반드시 `if (tdc_qcc_batt_check_timeout()) { qcc_batt_timeout = true; }` **sticky OR-누적 패턴**으로 호출(직접 대입 금지 — 회귀 버그 원인, 02번 문서 §3 핵심 경고).
- 결정_4: **시스템제어 오케스트레이션(③)** — A~F(systemControl~PMIC)는 하나의 함수(`tdc_update_subsystem_states()`)로 묶고, G(모드 플래그 분기)만 `tdc_update_system_mode_flag(bool)`로 분리. `update_mapNum()`의 위치(현재 A와 C 사이)는 **절대 이동 금지**(1-iteration 지연 구조가 의도된 동작, 03번 문서 §1 WARNING).
- 결정_5: **부팅시퀀스(①)** — `tdc_cfx_wait_started()` + `tdc_isd_log_boot_info()` 분리. 결합도가 가장 낮아 회귀 위험 최저.
- 결정_6: **절전전이(⑤+⑥)** — 단일 거대 함수 대신 책임별로 작게 분리: (a) QCC 타임아웃→systemOff 변환, (b) 크래들 뚜껑(비반환 특성 때문에 별도 분기 유지), (c) systemOff 가드+`break`(3-state 반환으로 치환), (d) NRF/UI polling. `fake_func_sleep()` 처리는 §3.2 선택지 B를 계획.md에서 사용자와 함께 확정.
- 결정_7: **dead 변수(`conneded_ISD`/`mappingConnection`/`p_isd_info`)와 매직넘버 6종은 정리 대상으로 계획.md에 포함**하되, 최종 정리 여부는 계획.md 승인 시 사용자 확인(요구사항.md §5 위임 범위 밖 항목).

## 5. 위험·제약

| 위험 | 가능성 | 영향 | 완화 |
|---|---|---|---|
| `isd_state`/`BLE_communicationState`가 루프 캐리 변수(직전 iteration 값을 이번 iteration 앞부분이 소비)인데, 분해된 함수 내부에서 잘못 재초기화하면 매 iteration 항상 stale 상태로 동작 — 회귀 | 중 | 높음(연결 상태 오판정) | 계획.md에서 이 두 변수는 반드시 `func_normal()` 지역변수로 유지, 신규 함수는 in/out 파라미터로만 취급하도록 명시(03번 문서 §1 IMPORTANT) |
| `qcc_batt_timeout` sticky 패턴을 직접 대입(`=`)으로 잘못 구현 시 QCC 타임아웃 감지 다음 iteration부터 파워오프 시퀀스 중단 | 중 | 높음 | 계획.md에 OR-누적 호출 패턴 명시(결정_3), 검증 체크리스트에 포함 |
| `led_set_isd_conn_state()` 호출 순서(ISD LED 확정 직후)가 깨지면 1-tick 잔상(race) 재발 | 낮음 | 중 | `tdc_led_request_isd()` 내부 마지막 statement로 캡슐화, 호출자에 노출 안 함(04번 문서 §2.2) |
| `func_cradle_lid_closed_loop()`/`fake_func_sleep()`이 정상 반환하지 않는 특성을 분해된 함수가 인지 못 하고 반환값을 기대하면 미정의 동작 | 낮음 | 중 | 두 호출 모두 "반환 안 할 수 있음"을 함수 doc에 명시, 별도 분기로 격리(05번 문서 §4) |
| `claude_feature_led-isr-table-refactor` 브랜치와 병합 순서에 따라 `fake_func_sleep()` 관련 코드가 중복 작업이 될 수 있음 | 중 | 낮음(작업 낭비 수준) | 계획.md에서 병합 순서 또는 최소 처리 방식을 사용자와 확정(§3.2 선택지 B) |
