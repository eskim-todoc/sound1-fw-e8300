# 요구사항: func_normal() 리팩토링

**TL;DR**: `main.c`의 `func_normal()`(320~723행, ~400줄)이 부팅 시퀀스·센서 읽기·시스템 서브모듈 호출·LED 소스 요청(배터리/ISD/매핑)·절전 전이까지 한 함수 안에 전부 뭉쳐 있어 하드코딩처럼 보이고 가독성이 떨어진다는 지적. 특히 배터리 레벨 기반 LED 상태 결정(히스테리시스·매직넘버·`#ifdef` 오버라이드가 뒤섞인 블록)이 가장 지저분하다고 지목됨. 5페르소나 fan-out으로 섹션별 분석 후 함수 분해 계획을 수립한다.

## 1. 사용자 요청

> "노말 함수의 코드가 너무 하드코딩 느낌이라 보기가 어려워. 함수로 쪼개든, 코드를 리팩토링 하던 해야할거 같아. 특히 배터리 레벨에 맞춰 led 설정하는게 지저분 해."

> "새 작업이니 브랜치도 새로따고 작업 폴더도 만들고해서, 새 작업 시작해. 여러 페르소나 돌리고, 분석 및 계획 세워봐"

"노말 함수"는 `main.c:320` `func_normal()`로 확인(코드 grep, `func_sleep()`과 대비되는 정상 동작 루프). 모호점 해소: 사용자가 "특히"로 배터리 LED 부분을 콕 집었으나, "함수로 쪼개든 리팩토링 하던"이라는 문구는 함수 전체 구조 개선도 포함하는 것으로 해석 — 분석 단계에서 전체 섹션을 다 조사하되, 계획 단계에서 우선순위를 배터리/ISD/매핑 LED 요청 블록에 둔다.

## 2. 목표

- 목표_1: `func_normal()`의 전체 구조(부팅 시퀀스, iteration 루프 내 섹션들, 절전 전이)를 섹션별로 분석해 각 섹션의 책임·숨은 상태(static 변수)·결합도를 파악
- 목표_2: 배터리/ISD/매핑 LED 요청 로직(526~643행)을 우선순위로 함수 분해 방향 도출 — 매직넘버(주석 처리된 구값 40/41/65/64 등), `#ifdef ENABLE_UI_CMD` 중첩, 정적 상태 변수(`prev_batt_st`, `s_map_low_active`)를 어떻게 정리할지
- 목표_3: 계획.md까지 작성해 실행 순서·atomic commit 단위 확정 (구현은 별도 승인 후)
