# 이력 및 결과 - 이월_I 구조 지표 측정 통일

**TL;DR**: `tests/metrics.sh` 를 신설해 «조건 분기 총수 보존» 검증을 스크립트로 고정했다. 지표는 **같은 방식으로 두 번 재는 것**이 전부인데, 손으로 `grep` 을 칠 때마다 패턴이 조금씩 달라져 거짓 판정이 두 번 났다. 측정 규칙과 **한계**를 코드에 박아 재사용한다. 코드 무변경이라 실기가 필요 없다.

## 배경 - 두 번의 거짓 판정

| 시점 | 사고 | 원인 |
|---|---|---|
| 2026-07-30 이월_D | `case` 19 → 21 **거짓 FAIL** | `grep -o "case "` 가 **주석 안의 "case"** 를 셌다. 기준선 19 자체가 실제 레이블 17 + 주석 언급 2 였다 |
| 2026-08-05 이월_2 | `reply` 호출 «50» → 실제 **49** | `grep -c "tdc_ble_reply"` 가 **`#include` 줄**을 셌다 |

> [!IMPORTANT]
> **두 사고 모두 «지표가 틀렸다» 가 아니라 «재는 방법이 매번 달랐다» 가 원인이다.** 기준선과 재측정을 다른 패턴으로 재면 차이가 코드 변화인지 패턴 차이인지 구별할 수 없다.
>
> 이월_D 는 *"기존 작업들의 «조건 분기 총수 보존» 검증도 같은 취약점을 갖는다 — 주석 증감이 없어 오염이 상쇄됐을 뿐"* 이라고 적었다. 그것이 이월_I 다.

## 산출물 - `tests/metrics.sh`

```sh
bash tests/metrics.sh <파일...>                  # 지표 출력
bash tests/metrics.sh --save <이름> <파일...>     # 기준선 저장
bash tests/metrics.sh --diff <이름> <파일...>     # 기준선과 대조 (변화 시 exit 1)
bash tests/metrics.sh --func <함수명> <파일>       # 함수 범위만 측정
```

### 측정 규칙

| 부류 | 패턴 | 배제하는 오염 |
|---|---|---|
| 구조 (`case`·`switch`·`default`·`if`·`else`·`for`·`while`·`return`) | 행 앵커 `^[[:space:]]*` | **주석 안의 단어** |
| 연산자 (`\|\|`·`&&`) | 주석 **행** 제외 후 개수 | 주석 줄의 연산자 |
| 참고 | `lines` | (대조에서 실패로 치지 않음) |

### 함수 범위 추출

`--func` 는 **«여는 중괄호가 다음 줄»** 규약으로 함수를 찾는다. 이월_2 에서 `tdc_ble_remote_step()` 을 놓쳤던 원인이 **시그니처 줄에 행말 주석이 붙어 정규식에 안 걸린 것**이었다. `awk` 로 시그니처 후보와 다음 줄 `{` 를 짝지어 그 형태도 잡는다.

## 검출력 확인 (뮤테이션)

기준선 저장 후 `if (1) { }` 한 줄을 주입해 대조했다.

```
  if       56 -> 57  ** 변화 **
1 개 지표가 변했습니다. 의도한 변화인지 확인하세요.
```

무변경 대조에서는 10지표 전부 «불변» 이고 종료코드 0 이다. **검출력과 오탐 없음을 둘 다 확인했다.**

## 한계 (알고 쓸 것)

스크립트 주석에도 적었다. 지표를 맹신하지 않기 위해 명시한다.

| # | 한계 |
|---|---|
| 한계_1 | **행말 주석에 `\|\|` 를 쓰면 연산자 계수가 오염된다.** 이 프로젝트는 행말 주석에 연산자를 쓰지 않는 관례라 현재는 안전하다 |
| 한계_2 | **매크로 안에 숨은 분기는 세지 못한다.** 이 프로젝트는 분기 매크로를 쓰지 않는다 |
| 한계_3 | **지표 불변은 필요조건이지 충분조건이 아니다.** 분기를 서로 맞바꾸면 총수는 같다. 테스트와 실기가 나머지를 덮는다 |

## 부수 발견 - `.elf` 바이트 비교의 함정

이 작업 직후 이월_E(주석 6줄 갱신)를 검증하다 **주석만 바꿨는데 `.text` 가 11바이트 달라지는** 것을 만났다. 원인은 두 가지다.

| # | 원인 | 실측 |
|---|---|---|
| 1 | **`TDC_PRINTF_*` 매크로가 `__LINE__` 을 품는다** (`util/tdc_printf.h:36`) | 소스에서 `grep __LINE__` 은 3곳만 보이지만, 편집 지점 뒤 `TDC_PRINTF` 가 **21건**이라 줄이 밀리면 즉치 21개가 함께 바뀐다 |
| 2 | **`main.c:115` 의 `__DATE__`** | 날짜 경계를 넘겨 빌드하면 그것만으로 1바이트 달라진다 (이월_A 에서 `Aug  5` -> `Aug  6`) |

> [!CAUTION]
> **이 발견은 방금 적은 «한계_2 - 매크로 안에 숨은 것은 못 센다» 와 정확히 같은 유형이다.** 한계를 적어 놓고 바로 그 함정에 빠졌다.
>
> **이월_F 의 검증 문구도 과했다.** 당시 *"바이트 차이는 `__LINE__` 즉치 하나뿐"* 이라 적었으나, 디스어셈블리에서 `#442` 가 1회임만 확인했고 `.text` 전수 비교는 하지 않았다. 그 파일들에도 `TDC_PRINTF` 가 19·23건 있어 실제로는 더 밀렸을 것이다. **크기 불변과 431 PASS 는 사실이므로 결론은 유지되지만 «1바이트뿐» 은 근거가 부족했다.**

**규칙으로 고정한다** (스크립트 주석에도 반영).

| 상황 | 대응 |
|---|---|
| «바이트 동일» 을 주장할 때 | `cmp -l` 로 **전수 비교**. 특정 즉치 하나를 찾은 것으로는 부족하다 |
| 줄 수가 바뀌는 편집 | `.text` 변화를 **예상해야 한다**. 바이트 동일을 기대하지 말 것 |
| 줄 수를 보존할 수 있는 편집(선언 이동 등) | 보존하면 이 문제를 통째로 피한다 (이월_2 커밋_1 이 그렇게 했다) |
| 소량 바이트가 어긋날 때 | `__DATE__` 를 먼저 의심 |
