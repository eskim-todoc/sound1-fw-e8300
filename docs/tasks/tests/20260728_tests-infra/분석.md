# 분석 - tests 오프라인 테스트 인프라

**TL;DR**: 미결 6건을 해소했다. **범위는 `mapping/` 3파일 전부**(스텁 8개면 커버). 러너는 **셸 스크립트**(Bash·PowerShell 양쪽 진입점 필요 없이 Bash 하나) + 컴파일러 경로 자동 탐색. 스텁은 **공용 모듈 1개**로 모으고 검사 상태를 조회할 수 있게 만든다. 테스트 케이스는 **코드에서 역추출한 범위 검사 표**를 근거로 삼되, 프로토콜 문서와 대조해 어긋나면 기록한다.

## 1. 하네스 구조 (미결_4·미결_6)

```
tests/
├── unit/
│   ├── run.sh                    러너 (빌드 + 실행)
│   ├── tdc_test.h                검사 매크로 (CHECK/CHECK_EQ 등)
│   ├── stub_ble.c/.h             프로덕션 심볼 스텁 8개 + 조회 API
│   ├── test_map_measure.c        0x62~0x64
│   ├── test_map_flash.c          0x68~0x71
│   └── test_map_stim.c           0x65~0x66
└── (기존 문서들은 그대로)
```

**컴파일 대상**

| 구분 | 파일 |
|---|---|
| 실제 소스 (사본 아님) | `src/2__cm3/source/ble/mapping/tdc_ble_map_*.c` · `src/2__cm3/source/ble/tdc_ble_reply.c` |
| 스텁 | `tests/unit/stub_ble.c` |
| 테스트 | `tests/unit/test_*.c` |

`tdc_ble_reply.c` 는 **스텁이 아니라 실물**을 쓴다. 응답 조립 결과까지 검증 대상이기 때문이다.

## 2. 스텁 설계 (미결_1·미결_4 해소)

### 2.1 필요한 스텁 8개

요구사항-검증 결함_1 에서 확정했다. `mapping/` 3파일을 전부 커버한다.

| 스텁 | 역할 | 테스트가 조회할 것 |
|---|---|---|
| `tdc_ble_mapping_get_packet` | 정적 `ST__MAPPING_PACKET` 반환 | 파싱 결과 전체 |
| `tdc_ble_mapping_get_seq_index` / `set_seq_index` | 정적 int | 연속성 카운터 값 |
| `tdc_sys_error_send_to_app` | 호출 기록 | **호출 횟수 · major · minor** (라인 번호는 제외 - §4) |
| `tdc_hal_spi_write_tx_buffer` | 송신 바이트 복사 | **응답 바이트열 · 길이** |
| `tdc_shm_get_pointer_repository_..._isd_info` | 정적 `int[64]` 반환 | 적재된 내부기 정보 |
| `tdc_shm_get_pointer_repository_..._stimul_para` | 정적 `int[256]` 반환 | 적재된 자극 파라미터 |
| `tdc_shm_get_pointer_current_map_data` | 정적 구조체 반환 | stim 이 읽는 맵 데이터 (테스트가 미리 채움) |

> [!IMPORTANT]
> **`tdc_hal_spi_write_tx_buffer` 스텁이 이 인프라의 핵심 가치다.** 실기에서는 로그로만 확인하던 **응답 바이트열을 오프라인에서 바이트 단위로 단언**할 수 있다. 단계_3 에서 디스크립터 테이블로 바꿀 때 이것이 회귀 안전망이 된다.

### 2.2 배열 크기 근거

`p_RepositoryFor_ISD_info` 는 인덱스 45 까지(`map_flash.c` 0x6C 데이터 인덱스 3), `p_RepositoryFor_stimulPara` 는 자극 파라미터 12 + 전극 64 + T/C 레벨 64 + xmin/xmax 64 로 200 대까지 쓴다. **여유를 두어 64 / 256 으로 잡고, 스텁에 경계 검사를 넣어 넘치면 테스트가 실패하도록 한다.**

## 3. 러너 (미결_2·미결_5 해소)

### 3.1 형태 - **Bash 스크립트**

| 안 | 판정 |
|---|---|
| Makefile | make 는 SDK 에만 있고 PATH 에 없다. 호스트 테스트가 SDK 에 의존할 이유가 없다 |
| **Bash 스크립트** | **채택** - Git Bash 가 이미 있고 프로젝트 표준 셸이다 |
| Python | 3.12 가 있으나 C 빌드를 셸로 부르는 래퍼가 되어 층만 는다 |

### 3.2 컴파일러 탐색

하드코딩 금지(제약_6). 다음 순서로 찾는다.

1. `CC` 환경변수
2. `PATH` 의 `gcc`
3. 알려진 winget 설치 경로: `$LOCALAPPDATA/Microsoft/WinGet/Packages/BrechtSanders.WinLibs.*/mingw64/bin`

셋 다 실패하면 **설치 안내 메시지와 함께 비0 종료**한다.

### 3.3 include 경로

PoC 에서 확정된 목록이다.

```
src/2__cm3/source/{ble, ble/mapping, sys, cfx_link, isd, stim, board, util, lib/SEGGER_RTT, .}
<SDK>/include/{cm3, shared}
```

SDK 경로도 환경변수(`EZAIRO_SDK`) -> 기본 설치 경로 순으로 찾는다.

## 4. `__LINE__` 을 검증에서 제외한다

`tdc_sys_error_send_to_app` 의 4번째 인자는 `__LINE__` 이고 **소스가 한 줄만 밀려도 바뀐다**. 직전 두 작업에서 이미 확인한 성질이다.

**스텁은 라인 번호를 기록하되 테스트는 단언하지 않는다.** 대신 **호출 횟수 · major · minor** 를 단언한다 - 이 셋이 에러의 의미를 결정한다.

## 5. 테스트 케이스 근거 (미결_6)

**코드에서 역추출한 범위 검사 표**를 1차 근거로 삼는다. 이유는 두 가지다.

1. 이 인프라의 목적은 **현재 동작을 고정**하는 것(회귀 안전망)이지 사양 준수 검증이 아니다
2. 프로토콜 문서와 코드가 어긋난 사례가 이미 있다(예: 텔레코일 범위를 문서는 1~2, 코드는 0~2 로 허용 - `map_flash.c` 잠수함 패치)

**대조 결과 어긋나면 기록만 한다**(원칙_4 - 결함 수정과 인프라 구축을 섞지 않는다).

### 5.1 케이스 설계 패턴

명령마다 최소 3종을 만든다.

| 유형 | 목적 |
|---|---|
| 정상 | 필드가 올바른 위치에서 올바른 값으로 적재되는가 |
| 경계 | 범위 검사의 상·하한 (`min`, `min-1`, `max`, `max+1`) |
| 순서 | 멀티 패킷 명령의 데이터 인덱스 연속성 (0x68·0x6C·0x6D·0x66 하위 1) |

멀티 패킷은 **연속 호출로 시퀀스를 재현**한다 - 스텁의 `seq_index` 가 상태를 유지하므로 가능하다.

## 6. 명명 규칙 (요구사항-검증 결함_2 해소)

| 대상 | 규칙 | 예 |
|---|---|---|
| 프로덕션 심볼 스텁 | **원래 이름 그대로** (링크 대체라 필연) | `tdc_ble_mapping_get_packet` |
| 스텁 조회 API | `stub_` 접두어 | `stub_error_count()`·`stub_tx_buffer()` |
| 테스트 헬퍼 | 짧은 이름, `tdc_` 없음 | `CHECK`·`CHECK_EQ` |

`tdc_` 는 프로덕션 접두어이므로 테스트 전용 심볼에는 붙이지 않는다.
