# 요구사항 검증

**TL;DR**: 3축 통과. **은수님 전제가 틀렸다는 것을 요구에서 미리 확정하지 않고 «검토» 로 남겨 둔 것**이 이 문서의 값어치다 — 결론을 요구사항에 박아 넣으면 분석이 그것을 정당화하는 절차로 전락한다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 지시 원문 인용 | 통과 - §1 |
| 완료 조건이 측정 가능 | 통과 - 9개 전부 |
| HW 5게이트 제약 명시 | 통과 - 제약_6 |
| 은수님 로컬 파일 보호 | 통과 - 제약_8 (`main.c` 호출 활성화 미커밋) |

## 축_2 - 논리 정합성

### 정합_1 - 요구_1(검토)의 답이 «틀렸다» 여도 요구_3·4 가 성립하는가

**성립한다.** 두 요구는 독립이다.

은수님 전제가 틀렸어도 «모드를 확인하고 바꾸는 명령» 은 그대로 필요하다. 오히려 **전제가 틀렸기 때문에 더 필요하다** — 실기에서 각 모드가 실제로 어떻게 동작하는지 눈으로 봐야 이해가 교정된다.

### 정합_2 - 「제약_4 경고만 하고 막지 않는다」가 안전한가

안전하다. **이것은 측정용 테스트 콘솔이고 은수님이 의도적으로 진입하는 경로다.** 막으면 요구_4(원하는 모드로 변경)를 부정하게 된다.

다만 **RESERVED(제약_1)는 막는다.** 차이는 근거다 — Forced Bypass 는 데이터시트가 «쓸 수 있으나 이런 성질이 있다» 고 한 모드이고, `0x1` 은 «쓰지 말라» 고 한 값이다. **데이터시트가 금지한 것만 막는다.**

### 정합_3 - 제약_2(읽고-고쳐-쓰기)가 과한가

과하지 않다. `CONV_CFG` 한 바이트에 **모드 외 5개 필드**가 산다. 통째로 쓰면 `EN_AND`·`TYPE1` 을 덮어써서 **변환기가 꺼지거나 오차증폭기가 바뀐다.** 지금 값이 `0x81` 이라 우연히 «`0x81|FMODE`» 가 맞아떨어지지만, **그 우연에 기대면 나중에 `DVSRATE` 를 바꾸는 순간 깨진다.**

## 축_3 - 근거 검증

| 주장 | 확인 |
|---|---|
| `FMODE=0x1` 이 RESERVED | **데이터시트 Table 5 실측 인용** |

| 현재 `CONV_CFG = 0x81` | **코드 실측** — `TDC_DRV_PMIC_DEFAULTVALUE_CONV_CFG` |
