# 분석

**TL;DR**: 본보기 `main.c` 에 현행 설정을 돌리면 **차이가 16줄뿐**이라 설정 자체는 은수님 스타일에 이미 잘 맞는다. **다만 `ColumnLimit: 320` 이 조건_6 을 무력화**하고 있었고, v22 는 조건_2·5 를 자동화할 수 있는데 **기존 README 의 처방(`KeepEmptyLinesAtTheStartOfBlocks`)은 v22 에서 사라진 이름**이다.

## 1. 도구 실태

| 항목 | 값 |
|---|---|
| 실행 파일 | `C:\Program Files\LLVM\bin\clang-format.exe` |
| 버전 | **22.1.8** |
| 설정 위치 | `src/.clang-format` (하위 6개 Eclipse 프로젝트 전부에 적용) |
| 설정 인식 | **확인됨** - `--dump-config -assume-filename=...` 이 `ColumnLimit: 320` 등 프로젝트 값을 낸다 |

## 2. 본보기 역산 - 현행 설정은 이미 잘 맞는다

`src/2__cm3/source/main.c`(= `docs/참고/clang-format/example.c`, 1,121줄)에 현행 설정을 돌린 결과.

| 항목 | 값 |
|---|---|
| 차이 | **16줄** (1.4%) |

차이는 셋뿐이고 **전부 도구가 못 맞추는 것**이다.

| # | 차이 | 원인 |
|---|---|---|
| 1 | 구조체 배열 후행 `/* */` 주석 열이 2~4칸 → 1칸 | clang-format 동작 (§4) |
| 2 | 빈 줄 2개 → 1개 (2곳) | `MaxEmptyLinesToKeep: 1` (LLVM 기본) |
| 3 | `return 0;  /* */` → `return 0; /* */` | §4 와 같은 원인 |

> [!IMPORTANT]
> **은수님 스타일은 이미 설정에 담겨 있다.** «다듬는다» 의 실체는 **덜 담긴 조건을 마저 담는 것**이지 스타일을 새로 정하는 것이 아니다.

## 3. 조건 11개 재판정 (v22 기준)

기존 README 는 «자동 4 · 수동 7» 이었다. **v22 에서 다시 재면 «자동 5 · 부분 2 · 수동 4» 다.**

| # | 조건 | 기존 판정 | **v22 재판정** | 설정 |
|---|---|---|---|---|
| 1 | 변수 자료형·이름 줄맞춤 | 자동 | **자동** | `AlignConsecutiveDeclarations` |
| 2 | 제어문에 모두 `{}` | 수동 | **자동으로 바뀜** | **`InsertBraces: true`** (v15+) |
| 3 | `case` 는 `{}` 안 · `break` 뒤 공백 줄 | 수동 | **수동** | 해당 옵션 없음 |
| 4 | `{}` 시작·끝은 새 줄 | 자동 | **자동** | `BreakBeforeBraces: Allman` |
| 5 | `{` 다음 의미 없는 줄바꿈 금지 | 미설정 | **자동으로 바뀜** | **`KeepEmptyLines: {AtStartOfBlock: false}`** |
| 6 | 인자 많으면 각 인자 새 줄 | 자동(오판) | **조건부 자동** | `BinPackArguments: false` **+ 유한한 `ColumnLimit`** |
| 7 | 주석 형태 · 시작 위치 | 수동 | **부분** | 위치는 `AlignTrailingComments`, 형태는 수동 |
| 8 | `/* */` 중첩 금지 | 수동 | **수동** | C 문법 |
| 9 | 배열 초기화 나눔·정렬 | 부분 | **부분** | `ColumnLimit` 으로 나눔만. 정렬은 §5 |
| 10 | 제어문 위 **코드**와 공백 줄 | 수동 | **수동** | 해당 옵션 없음 |
| 11 | 제어문 위 **주석**과 공백 줄 | 수동 | **수동** | 해당 옵션 없음 |

### 3.1 기존 README 의 처방이 v22 에서 안 먹는다

README §4 는 `KeepEmptyLinesAtTheStartOfBlocks: false` 를 넣으라고 적었다. **그 이름은 v22 에 없다.**

```
KeepEmptyLines:
  AtEndOfFile:     false
  AtStartOfBlock:  true     <- 여기로 옮겨졌다
  AtStartOfFile:   true
```

옛 이름을 쓰면 clang-format 이 **조용히 무시**한다(에러도 안 난다). 처방대로 했어도 조건_5 는 안 지켜졌을 것이다.

## 4. `SpacesBeforeTrailingComments` 가 `/* */` 에는 안 걸린다

최소 재현으로 확인했다.

```c
int f(void)
{
    return 0;  // line comment      <- 2칸 (설정대로)
}

int g(void)
{
    return 0; /* block comment */   <- 1칸 (설정 무시)
}
```

`SpacesBeforeTrailingComments: 2` 인데도 **블록 주석은 1칸**이다. 구조체 배열 안에서도 같다.

**설정으로 못 고친다.** 본보기의 `/* */` 후행 주석 4곳이 1칸으로 줄어드는 것을 감수한다. 조건 문서가 «칸 수» 를 규정하지 않았으므로 조건 위반은 아니다.

## 5. `AlignArrayOfStructures` 는 넣으면 안 된다

조건_9 의 «각 요소의 시작 위치를 맞춤» 을 자동화할 후보지만, **본보기와 어긋난다.**

```c
// AlignArrayOfStructures: Left 적용 시
{A_LONG_NAME,        B_NAME},
{A_MUCH_LONGER_NAME, BB    },   <- 닫는 중괄호 앞을 패딩한다
```

본보기 `main.c` 의 `s_tdc_batt_led_table[]` 은 **내부를 정렬하지 않는다.** 은수님 실물이 기준이므로 넣지 않는다.

## 6. `ColumnLimit: 320` 이 조건_6 을 무력화하고 있었다

### 6.1 실증

`isd/tdc_isd_fpga.c` 에는 손으로 2줄로 나눠 둔 매크로 호출이 있다.

```c
TDC_ISD_DEBOUNCE_FAIL(error_cnt, "[FPGA]", "tdc_isd_fpga_read_version", "RD",
                      en__FPGA_COMMUNICATION_ERROR, en__I2C_FPGA_ReadingError);
```

`ColumnLimit: 320` 으로 돌리면 **한 줄(137자)로 도로 붙는다.** `BinPackArguments: false` 는 «한 줄에 안 들어갈 때» 만 작동하므로 320 아래로는 발동하지 않는다.

### 6.2 `ColumnLimit: 0` 도 답이 아니다

«저자의 줄바꿈을 보존» 을 기대하고 시험했으나 **똑같이 한 줄로 붙였다.** 조건_6 을 도구가 지키게 하려면 **유한한 폭**이 필요하다.

### 6.3 본보기가 말하는 폭

| 파일 | 최대 | >120 | >140 | >160 | >180 |
|---|---|---|---|---|---|
| **`main.c`** (본보기) | **181** | 27 | 7 | **1** | 1 |
| `2__cm3/source` 전체 | 350 | 1,133 | 544 | 315 | - |

**본보기가 160 을 넘는 줄은 1개뿐**이고, 그 1개는 인자 4개짜리 `TDC_PRINTF_D` 호출로 **조건_6 이 나누라고 하는 바로 그 형태**다.

### 6.4 폭별 변경량 (149파일 실측)

| ColumnLimit | 변경 줄 | 변경 파일 |
|---|---|---|
| 320 (현행) | 3,214 | 110 |
| 200 | 3,707 | 111 |
| **160 (선택)** | **4,027** | **113** |
| 140 | 4,570 | 115 |
| 120 | 5,862 | 116 |

**은수님이 160 을 선택했다.**

## 8. `InsertBraces` 안전성 - 전량 검토

전처리기가 빽빽한 코드라 여기가 유일한 위험 지점이다. **`InsertBraces` 기여분만 분리해 전량을 봤다.**

| 항목 | 값 |
|---|---|
| 바뀐 파일 | **4개** (`hal/tdc_hal_i2c.c` · `led/tdc_led_output.c` · `stim/tdc_stim_para_cal.c` · `ui/tdc_ui_command.c`) |
| 추가된 줄 | **104** |
| **삭제된 줄** | **0** |

> [!NOTE]
> **삭제 0 이 결정적이다.** 이 도구는 `{` 와 `}` 줄을 **삽입만** 하고 기존 코드를 한 줄도 옮기거나 지우지 않는다. 코드 이동이 없으면 의미가 바뀔 통로가 없다.

전처리기 인접 지점도 확인했다.

```c
#ifdef CM3_I2c_TestMode
    I2C_statusRegister_dump[dumpIndex++] = (int) i2cStatus.status;
    if (dumpIndex >= 32)
    {                          // <- 삽입
        dumpIndex = 0;
    }                          // <- 삽입
#endif
```

**여는 것과 닫는 것이 같은 전처리기 영역 안**이다. 조건부를 가로지르는 삽입은 한 건도 없다.

## 9. 개행 - 작업 트리 4파일만 CRLF, 저장소는 LF

| 파일 | 작업 트리(발견 시) | 저장소 blob |
|---|---|---|
| `ble/mapping/tdc_ble_map_flash.c` | 839/839줄 CRLF | **LF** |
| `ble/remote/tdc_ble_remote.c` | 1,679/1,679줄 CRLF | **LF** |
| `isd/tdc_isd_map_ecap.c` | 1,187/1,187줄 CRLF | **LF** |
| `isd/tdc_isd_map_live.c` | 755/755줄 CRLF | **LF** |
| 나머지 145파일 | LF | LF |

`.gitattributes` 가 `* text=auto eol=lf` 를 걸고 있어 **git 은 비교할 때 양쪽을 정규화한다.** 그래서 작업 트리가 CRLF 여도 `git status` 는 깨끗하다. **어긋남이 git 에게는 안 보이고 clang-format 에게는 보인다.**

공교롭게도 CRLF 인 4파일은 **이번 세션에 스크립트로 통째로 다시 쓴 바로 그 4파일**이다. PowerShell 의 출력 계열은 기본이 CRLF다.

### 9.1 왜 이것이 이번 작업의 문제인가

`LineEnding: LF` 를 넣으면 이 4파일이 **통째로 개행 변환**되어 clang-format 이 보고하는 변경 줄이 **4,027 → 12,261** 로 뛴다. 8,234줄이 순수 개행 잡음이다.

**작업 트리를 먼저 LF 로 되돌린 뒤 포맷한다.** git 에게는 무변경이라 커밋이 생기지 않는다.

### 9.2 자산 - `git show HEAD:경로` 로 개행을 판정하면 안 된다

처음에 `git show HEAD:<경로> | grep -c $'\r'` 로 재어 **«저장소 blob 이 CRLF»** 라고 판정했다. **틀렸다.**

| 명령 | 같은 객체에 대한 결과 |
|---|---|
| `git show HEAD:<경로>` | **CRLF 라고 보고** (작업 트리가 CRLF 일 때) |
| **`git cat-file -p HEAD:<경로>`** | **LF** (필터를 안 거치는 유일한 읽기) |

작업 트리를 LF 로 고치자 `git show` 도 LF 를 내놓았다. **`git show` 는 개행 변환을 적용하므로 blob 의 실제 바이트를 묻는 용도로 쓸 수 없다.**

이 오판 위에서 «`.gitattributes` 도입 전부터 CRLF 였다» 는 이력 추적까지 했는데, 그 추적도 같은 `git show` 를 썼으므로 **근거 전체가 같은 결함을 공유하고 있었다**(자산_3 과 같은 형태 — 검증이 도구와 전제를 공유하면 안 된다).

## 10. 검증 설계

### 10.1 불변량

순수 포맷이므로 **동작 무변경**이 불변량이다. 구조 지표(`if`·`for` 수)는 `InsertBraces` 가 `{}` 를 늘리므로 쓸 수 없고, 줄 수도 바뀐다.

**쓸 수 있는 자는 셋이다.**

| 자 | 무엇을 잡나 |
|---|---|
| ARM 빌드 에러 0 · 경고 0 | 문법 파괴 · `InsertBraces` 오삽입 |
| 호스트 514 PASS | ble/ 로직 회귀 |
| **`.text` 명령어 단위 diff** | **코드 생성이 정말 같은가** |

### 10.2 `.text` 예측은 명령어 수로 한다 (자산_2)

`data`·`bss` 는 **불변**이어야 한다. `.text` 는 `__LINE__` 운반체가 밀린 만큼 명령어가 바뀐다.

운반체 = **명시 `__LINE__` + `TDC_PRINTF_E`** 뿐이다(자산_1 정정본). `_W`·`_I`·`_D`·`_V` 는 `__LINE__` 을 안 싣는다.

바이트 수는 Thumb-2 인코딩 형식 전환(`MOV.W` ↔ `MOVW`) 때문에 예측할 수 없다. **명령어 수로 센다.**

> [!CAUTION]
> 이번엔 밀리는 줄이 4,027줄 규모라 **거의 모든 운반체가 밀린다.** 「몇 개가 바뀌는가」 예측은 의미가 없고, 판정 기준은 **«바뀐 명령어가 전부 즉치 적재(`movs`/`mov.w`/`movw`)이고 다른 종류의 명령어 변화가 0» 이다.**
