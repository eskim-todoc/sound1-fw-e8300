# 분석 검증

**TL;DR**: 3축 통과. §3.1(기존 README 처방이 v22 에서 무효)과 §8(`InsertBraces` 삭제 0)이 이 분석의 값어치다 — **하나는 문서의 오류를 잡았고 하나는 위험을 수치로 지웠다.**

## 축_2 - 논리 정합성

### 정합_1 - 「본보기와 16줄 차이」가 「설정이 맞다」의 근거가 되는가

된다. 본보기는 **은수님이 «이렇게 써라» 로 지정한 실물**이다. 설정을 돌린 결과가 실물과 1.4% 차이면, 그 설정이 실물을 재현한다는 뜻이다.

**다만 역은 성립하지 않는다** - 본보기가 조건을 다 지키고 있다는 보장은 없다. 실제로 `TDC_PRINTF_D` 한 줄(181자)이 조건_6 위반이었고 `ColumnLimit: 160` 이 그것을 잡았다. **본보기도 완벽하지 않다는 것이 드러났다.**

### 정합_2 - 「삭제 0」이 안전의 충분한 근거인가

**충분하지 않지만 결정적이다.**

삭제가 0이면 기존 코드 줄이 하나도 옮겨지거나 사라지지 않았다는 뜻이고, `{`·`}` 만 끼워 넣은 것이다. 이때 의미가 바뀔 통로는 **매달린 `else` 재결합** 하나뿐이다.

그것마저 남는데, 그 경우 **컴파일 결과가 달라지므로 심볼 크기 표가 잡는다.** 정적 근거(삭제 0)와 동적 근거(크기 표)가 서로 다른 층을 본다.

### 정합_3 - 왜 구조 지표를 안 쓰는가

`InsertBraces` 가 `{}` 를 52쌍 늘리고 `ColumnLimit` 이 줄 수를 바꾼다. **지표의 전제(줄·분기 보존)가 이 작업에는 성립하지 않는다.**

죽은 코드 제거에서 지표를 못 쓴 것과 같은 구조다(자산_10) — 도구의 결함이 아니라 **자를 잘못 고르는 문제**다.

### 정합_4 - CRLF 4파일을 이번에 건드리는 것이 범위 확대인가

**아니다. 건드릴 수밖에 없다.** `LineEnding: LF` 를 넣으면 자동으로 바뀌고, 안 넣으면 파일별로 결과가 갈려 **설정이 비결정적**이 된다.

선택지는 «섞어서 한 커밋» 이냐 «나눠서 두 커밋» 이냐뿐이고, 나누는 쪽이 낫다.

## 축_3 - 근거 검증

| 주장 | 확인 |
|---|---|
| `KeepEmptyLinesAtTheStartOfBlocks` 가 v22 에 없음 | **`--dump-config` 실측** - 출력에 그 키가 없고 `KeepEmptyLines.AtStartOfBlock` 이 있다 |
| `SpacesBeforeTrailingComments` 가 `/* */` 에 안 걸림 | **최소 재현** - 같은 파일에서 `//` 는 2칸, `/* */` 는 1칸 |
| `ColumnLimit: 0` 도 줄을 붙임 | **실측** - fpga 에서 동일하게 합쳐짐 |
| `InsertBraces` 삭제 0 | **149파일 전수** |
| ~~CRLF 가 저장소 blob 에 있음~~ | **오판이었다 → 정정** - `git show` 가 개행 변환을 적용해 속았다. `git cat-file -p` 로 다시 재니 blob 은 LF. 분석 §9.2 참조 |
| 폭별 변경량 | **실측**. 단, 1차 측정에서 `LineEnding: LF` 포함본이 12,261 로 튀어 원인(CRLF 4파일)을 규명한 뒤 재측정 |
