# 요구사항 검증

**TL;DR**: 3축 통과. 모호했던 둘(줄 폭 · 범위)을 **추측하지 않고 은수님께 물어 확정**한 것이 이 문서의 값어치다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 지시 원문 인용 | 통과 - §1 |
| 모호하면 질문 (명령 해석 규칙) | **통과** - 줄 폭·범위 2건을 선택지로 제시해 확정 |
| 완료 조건이 검증 가능한 형태 | 통과 - 8개 전부 측정 가능 |

## 축_2 - 논리 정합성

### 정합_1 - 「전체 소스」를 2__cm3 로 좁힌 것이 지시 축소인가

**아니다.** 은수님이 선택지 셋 중 «2__cm3 만» 을 직접 골랐다. 좁힌 주체가 은수님이다.

좁히는 근거도 제시했다 - `1__cfx` 는 chess 컴파일러라 여기서 빌드 검증이 불가하고, `3__hear/microcode.c` 는 도구 생성 코드라 **재생성하면 포맷이 되돌아온다.** 검증할 수 없는 변경을 넣지 않는 것은 이 프로젝트의 일관된 원칙이다(ecap 분해 제외와 같은 성격).

### 정합_2 - 제약_1(동작 무변경)과 `InsertBraces` 가 충돌하지 않는가

충돌하지 않는다. `{}` 추가는 **문법 그룹핑을 명시할 뿐 의미를 바꾸지 않는다.** 단일 문장을 블록으로 감싸도 C 의미론상 동일하다.

유일한 예외는 **매달린 `else`**(dangling else)인데, clang-format 은 자기가 계산한 파스 트리대로 삽입하므로 결합을 바꾸지 않는다. 그리고 바뀐다면 **심볼 크기 표**가 잡는다(계획 §4).

### 정합_3 - 제약_5(`example.c` 바이트 동일)를 지킬 수 있는가

지킬 수 있다. `example.c` 는 `main.c` 의 사본이므로 포맷 후 **다시 복사**하면 된다. 순서만 지키면 된다.
