## 4. 잔여 결함 (본 검증에서 신규 검출)

| ID | 결함 | 완화 |
|---|---|---|
| 잔여_1 | **단계_2 가 `lib/`(SEGGER_RTT·tiny-AES-c) 내부 include 도 치환**한다. G0 에서 라이브러리는 "원본 유지" 예외로 두었으므로 방침 마찰 소지. 다만 include **표기**는 심볼이 아니고, 해당 폴더가 `-I` 에 등록돼 있어 해소도 동일하다 | **예외의 경계를 "원본 API 심볼"로 한정**한다고 명문화 — ⑧ 검증에서 확인한 `ci_aes_*` 사례(라이브러리 파일 안의 자작 래퍼)와 동일한 판정 기준. 치환 후 `lib/` 파일의 **심볼 diff 0** 을 검증_구조_2 에 추가 |
| 잔여_2 | **게이트를 1회로 집약**해 회귀 발생 시 3단계 중 어느 것이 원인인지 특정이 느려진다 | 단계별 커밋이 분리돼 있어 `git revert` 로 **이분 탐색 가능**. 또한 단계_1(이동)·단계_3(설정)은 빌드 실패로 즉시 드러나고, 단계_2(표기)는 컴파일 단계에서 드러나므로 **실기 회귀 위험은 구조적으로 낮다**(로직 무변경). 게이트 분할의 실익 < 은수님 실기 3회 부담 → 1회 유지 |

## 5. 반증 시도 — 순서를 바꾸면 더 나은가

| 대안 순서 | 평가 |
|---|---|
| 단계_2(include) 를 먼저 | ❌ 이동 전 치환하면 단계_1 의 `git mv` 가 rename+modify 로 뭉쳐 **rename 인식률이 떨어진다**(비기능_4 훼손) |
| 단계_3(설정) 을 먼저 | ❌ 존재하지 않는 `source/` 를 가리키게 되어 중간 상태가 빌드 불가. 롤백 지점으로서 무가치 |
| 현행 1→2→3 | ✅ 각 커밋이 **독립적으로 의미**를 갖고, 마지막 커밋에서 처음으로 빌드 가능 상태가 된다 |

중간 커밋이 빌드 불가인 점은 감수한다 — 3커밋이 하나의 게이트로 묶이므로 `claude_develop` 에는 항상 빌드 가능 상태만 병합된다.
