## 4. [전처리동등성] 실측 (핵심 근거)

계획 §3 의 **방법_A(강)** 를 실행했다. 툴체인을 SDK 에서 확보해 실제 전처리 산출물을 비교했다.

| 항목 | 내용 |
|---|---|
| 컴파일러 | `ON Semiconductor/Ezairo 8300 SDK/arm_tools/bin/arm-none-eabi-gcc.exe` |
| 옵션 | `-E -P -mcpu=cortex-m3 -mthumb -DSK5_CID=101` + `-I` 20경로 + SDK 2경로 |
| 비교 대상 | 작업 전 트리(`HEAD~2`, board 29파일)를 `git worktree` 로 꺼내 동일 조건 전처리 |
| 대상 파일 | `.c` 68개(`lib/` 제외) + `board/processorDirective.h` = **69** |
| 정규화 | `__FILE__` 이 전개하는 소스 절대경로만 제거(`sed -E 's#[^"]*src/2__cm3/source/##g'`) |
| **결과** | **동일 69 / 차이 0** |

선행 단계에서 선택자 3개만 따로 검증한 결과도 기록한다: `board.h` 6,849줄 · `FPGA.h` 87줄 · `internalStimulationChip.h` 22줄 — **정규화 없이도 바이트 동일**.

> [!NOTE]
> 이로써 "동작 보존"이 논증(도달 불가 코드는 결과에 기여할 수 없다)을 넘어 **실측으로 확정**됐다. 단계_2 의 선택자 편집까지 포함해 컴파일러가 보는 텍스트가 한 글자도 달라지지 않았다.

## 5. 축 3 — 구현 중 검출 사항

| ID | 사항 | 처리 |
|---|---|---|
| 검출_1 | **심볼 방어검사가 5종을 경보.** 삭제본에만 정의된 심볼 137종 중 `LED_IS_ACTIVELOW` · `df_I2C_ADDR_FPGA_BackTel` · `_Error_Flag` · `_FIFO_counter` · `_System_State` 가 코드에서 발견 | **전부 안전 확인**. FPGA 4종은 사용처가 **전부 주석 처리된 코드**. `LED_IS_ACTIVELOW` 는 `#if defined()` 활성 사용이나 **현재 보드(`Board_OTE_ver1_5.h:129`)에서 주석 처리돼 이미 미정의** — 다른 보드를 지워도 불변이고 토글 자체는 1.5 헤더에 존치 |
| 검출_2 | 첫 전처리 비교 시도에서 `-I source/lib/tiny-AES-c` 누락으로 `aes.h` 를 못 찾아 산출물이 비었다. `2>/dev/null` 로 오류를 가려 "차이 발생"으로 **오판** | stderr 를 살려 원인 확인 후 `-I` 전체(20경로)로 재실행. **"검증이 실패했다"와 "검증 도구가 실패했다"를 구분해야 한다** |
| 검출_3 | 2차 시도에서 `__FILE__` 이 워크트리 절대경로를 전개해 6파일이 차이로 잡혔다. `sed` 정규화 패턴이 Windows 형식(`C:/Users/...`)을 못 잡음 | 패턴을 `[^"]*src/2__cm3/source/` 로 일반화해 해결. **정규화 후 차이 0** |

> [!NOTE]
> **학습**: 자동 검증에서 "차이 발생" 보고가 나오면 **먼저 검증 도구 자체의 결함을 의심**해야 한다. 이번엔 3번의 "차이" 보고 중 3번 모두 도구 문제(include 누락·경로 정규화)였고, 실제 코드 차이는 0이었다. 전면 리팩토링에서 반복된 "자동 검출 오탐" 패턴과 동종이다.
