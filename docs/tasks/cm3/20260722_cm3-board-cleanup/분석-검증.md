# ④ 분석-검증

**TL;DR**: 삭제 안전성 증명의 3전제가 전부 실측으로 확인됐고, 증명은 연역적으로 타당하다. **결함 2건 검출** — 증명이 "선택자 편집"에는 적용되지 않는다는 점(단계 분리로 해소), `git rm` 후 Eclipse 미갱신 위험(게이트 절차 추가).

## 1. 축 1 — 지침 준수

| 지침 | 검증 | 결과 |
|---|---|---|
| 사장 코드는 실증 후 제거 (전면 리팩토링 학습) | 도달 가능성 연역 증명 + 전수 grep | ✅ 추측 아님 |
| 리팩터링 계층 분해 (루트 §7) | [구조검사]→[전처리동등성]→[빌드]→[통합테스트] | ✅ 의존 순서 명시 |
| root cause 가설 cross-check | 결함 A·B·C 각각 근거 라인 명시 | ✅ |
| Mermaid 사용 (§6) | 참조 관계도 | ✅ |

## 2. 축 2 — 증명의 타당성 검토

| 검증 | 결과 |
|---|---|
| 전제_1 이 참인가 (직접 include 0건) | ✅ 전수 grep — `Board_*`·`FPGA_ver*`·`isd_ver*` 를 include 하는 것은 선택자 3개뿐 |
| 전제_2 가 참인가 (하나만 활성) | ✅ `board.h:55-63` `#if/#elif/#else` · `FPGA.h:7-25` · `internalStimulationChip.h:6-22` — 전부 배타 분기 |
| 전제_3 이 참인가 (현 조합 빌드 성공) | ✅ 은수님 확인 (2026-07-22, 어셈블러 경로 조치 후) |
| 결론이 전제에서 따라 나오는가 | ✅ 도달 불가 코드는 전처리 결과에 기여할 수 없다 — 항진 |
| **증명의 적용 한계** | ⚠️ 증명은 **파일 삭제**만 보장한다. **선택자 텍스트 편집**(단계_2)은 별도 검증이 필요 (결함_1) |

## 3. 축 3 — 근거 검증 (실측 대조)

| 분석 주장 | 방법 | 결과 |
|---|---|---|
| `board/` 29파일 | `ls` | ✅ 29 |
| Board 10 · FPGA 7 · ISD 4 · 선택자 3 · 공통 5 | 파일명 분류 | ✅ 10+7+4+3+5 = **29** |
| `Board_*` 7개가 선택자에 분기 없음 (결함_A) | `board.h` 분기 3개(`TD_DEV_ver_1_4`·`OTE_VER_1_3`·`OTE_VER_1_5`) 대조 | ✅ 10 − 3 = **7** |
| `OTE_VER_1_4` 함정 (결함_B) | `processorDirective.h:11` 주석 존재 + `board.h` 분기 부재 | ✅ 확인 |
| `FPGA_Ver_is_230` → `2_1_0` (결함_C) | `FPGA.h:15-16` | ✅ 확인 |
| FPGA 2.7/2.8 레지스터 차이 | 두 파일 직접 대조 | ✅ bit 6/5/4 재배치 + `backterConfiguration_resetValue` 0x2D→0x31 |
| 2.7/2.8 차이 심볼이 코드에서 미사용 | `CarringCaseOpen`·`BakcktelPause` 등 grep | ✅ **헤더 정의만, 코드 참조 0** |
| `board.h` `#else` 블록의 `ENABLE_NRF_ADV_LowPower` 가 현재 미정의 | 1.5 분기에 부재 확인 | ✅ 제거해도 전처리 불변 |

## 4. 검출 결함

| ID | 결함 | 조치 |
|---|---|---|
| 결함_1 | **삭제 안전성 증명이 단계_2(선택자 편집)를 덮지 못한다.** 증명은 "도달 불가 파일 삭제"에만 유효하고, 선택자 텍스트를 바꾸면 활성 분기가 달라질 수 있다 | ⑤ 계획에서 **단계_1(삭제)과 단계_2(편집)를 커밋 분리** + **[전처리동등성] 검증**을 별도 라벨로 신설 (`계획.md §3`) |
| 결함_2 | **`git rm` 후 Eclipse 가 리소스를 갱신하지 않으면** Project Explorer 에 유령 파일이 남고 인덱서가 stale 심볼을 유지한다. 직전 작업에서 겪은 이중 경로 문제와 동종 | 게이트 절차에 **F5 Refresh** 명시 (⑧ 에서 안내) |

## 5. 반증 시도 — 삭제가 위험한 시나리오가 있는가

| 가설 | 검토 | 판정 |
|---|---|---|
| 가설_1: 어떤 `.c` 가 버전 헤더를 직접 include 한다 | 전수 grep | ❌ 0건 |
| 가설_2: 빌드 시스템(`.cproject`)이 개별 파일을 참조한다 | `resourcePath` 검사 | ❌ 이동 후 `resourcePath=""` 뿐 (Eclipse 가 stale `fileInfo` 자동 정리) |
| 가설_3: 다른 프로젝트(`1__cfx`·`5__calibration`)가 이 헤더를 공유한다 | `-I` 경로는 각 프로젝트 독립, `2__cm3/source/board` 는 CM3 전용 | ❌ 공유 없음 |
| 가설_4: 삭제 파일의 심볼이 공유 ABI(`tdc_shm.h`)에 노출된다 | `tdc_shm.h` 는 `board.h`·`internalStimulationChip.h` 를 include — **선택된 것만** 경유 | ❌ 선택본 유지되므로 무영향 |

4개 가설 전부 반증됐다. **삭제 안전성 결론을 유지한다.**

## 6. 결론

분석은 **⑤ 계획 수립에 충분**하다. 결함 2건은 계획·게이트 절차로 흡수한다.
