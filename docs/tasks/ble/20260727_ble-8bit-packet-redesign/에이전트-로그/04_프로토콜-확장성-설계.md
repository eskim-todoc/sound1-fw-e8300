# 04 프로토콜 확장성 설계

**TL;DR**: 0x8C 게인 제어 추가 이력을 역추적해 "명령 하나 추가 = 최소 4개 파일" 기준선을 세웠다. 이를 명령-핸들러 테이블과 데이터인덱스-필드 디스크립터 테이블, 응답 조립 공통 함수로 대체하는 설계를 제시한다. 0x66 서브커맨드1(인덱스 1~15)이 디스크립터 23행으로 흡수되는 구체 예시를 포함한다. 프로토콜 규약(명령 코드·페이로드·응답 순서)은 바꾸지 않는다.

## 0. 읽기 범위와 전제

- `src/`는 읽기만 했고 수정하지 않았다. 아래 코드는 전부 **설계 스케치**이며, 실제 파일명·행 위치는 예시다.
- 배경 지시대로 **패킷 버퍼가 `uint8_t[]`로 전환된다는 전제**로 설계한다. 전환이 무산되면 §3.1의 구조체·알고리즘은 그대로 두고 `tdc_ble_parse_by_descriptor()`의 첫 인자 타입만 `const int *`로 바꾸면 된다 - 오프셋 단위가 바이트에서 워드로 바뀔 뿐 디스크립터 자체 스키마는 영향받지 않는다.
- 불가침 확인: 명령 코드 값 · 서브커맨드 값 · 데이터 인덱스 순서 · 페이로드 바이트 위치 · 응답 바이트 순서, **전부 그대로**. 이 설계는 "그 규약을 C 코드로 어떻게 표현하는가"만 바꾼다. `tdc_ble_protocol.h`·`ST__MAPPINGPAYLOAD_*`는 미참조 항목 포함 전량 유지(`cm3-소스-트리-규약.md §2.1`).
- 페이로드 구조체 필드 타입은 프로젝트 관행대로 전부 `int`를 유지한다. 아래 디스크립터 구조체 자신의 `min`/`max` 열만 `int16_t`로 좁혔는데, 이는 새로 추가되는 메타데이터 자신의 내부 타입 선택이지 기존 페이로드 필드 타입을 좁히는 것이 아니다 - 프로토콜 전체 실측 범위값(최대 1800, `en__mapping_live_stimulation` 알림 자극 uA)이 `int16_t` 상한(32767)에 전혀 근접하지 않아 잘림 위험이 없음을 확인했다.

## 1. 개선 전 기준선 - 명령 하나 추가 비용 실측 (0x8C 게인 제어)

0x8C(`EN__SND_BT_CMD_GAIN_CONTROL`)는 2026-07-20 커밋 2개(`1f6ecc0`·`37242be`)로 추가됐다. 리네임 전 파일명 기준 실제 diff를 그대로 추적했다.

| # | 파일(당시 이름 → 현재 이름) | 변경 내용 | 줄 수 | 성격 |
|---|---|---|---|---|
| 1 | `ble_commonProtocol.h` → `tdc_ble_protocol.h` | `EN__SND_BT_CMD_GAIN_CONTROL = 0x8C` enum 값 1줄 추가 | +1 | **프로토콜 배선(필수)** |
| 2 | `ble_communication.c` → `tdc_ble_communication.c` | 디스패처에 `else if (p_Rx_dataPacket[0] == EN__SND_BT_CMD_GAIN_CONTROL) { tdc_ble_remote_fetch_packet(...); }` 추가 | +4 | **프로토콜 배선(필수)** |
| 3 | `remoteControl.c` → `tdc_ble_remote.c` | `case EN__SND_BT_CMD_GAIN_CONTROL:` 블록 추가(핸들러 호출 + SPI 송신 + 명령 클리어) | +15 | **프로토콜 배선(필수)** |
| 4 | `tdc_remote_gain_control.c/.h`(신규) → `tdc_ble_gain_control.c/.h` | 핸들러 본체 신규 작성(Read/Write 검증 + 응답 조립) | +172 | **프로토콜 배선(필수, 신규 파일)** |
| 5 | `shared_memory.h`(cfx) + `cfx_cm3_sharedMemory.h`(cm3) | 게인 인덱스·크래들 플래그를 CFX로 넘기기 위한 공유 메모리 필드 3개, **양쪽 구조체 끝에** 동시 추가 | +8×2 | 기능 특수(영속 상태가 필요해서) |
| 6 | `initialize.c` | 부팅 시 게인 인덱스 기본값(유니티) 초기화 호출, **`enable_CFX_trigger_for_iteration()`보다 앞**이어야 하는 순서 제약 | +6 | 기능 특수(초기값이 필요해서) |

**정리**: 커밋 2개, 파일 8개(신규 2개 포함), diff 약 220줄. 이 중 **"명령을 프로토콜에 배선"하는 데만 필요한 최소 집합은 1~4번(파일 4개, 신규 파일 포함 약 192줄)**이고, 5~6번(공유메모리 필드·초기화 순서)은 이 명령이 **CFX와 상태를 공유해야 하는 특수성** 때문에 추가로 필요했던 것으로 모든 신규 명령에 공통은 아니다. 데이터 인덱스 분할까지 있는 명령(0x66류)이라면 여기에 §3의 디스크립터 행 추가가 하나 더 얹힌다.

> [!IMPORTANT]
> 4번(핸들러 본체 172줄)은 이미 "패킷 포인터 주입 + `tx_index` 반환" 검증 템플릿(`tdc_ble_general_debug.c`)을 재사용했다 - 응답 조립 자체는 이미 최소 비용이었다. **진짜 비용은 1~3번의 "3곳에 나뉜 배선"**이다: enum 추가 따로, 디스패치 조건 추가 따로, case 추가 따로. 이 3곳을 한 곳(§5 핸들러 테이블)으로 합치는 것이 이번 설계의 목표다.

## 2. 설계 개요

| 구성요소 | 대체하는 것 | 상세 |
|---|---|---|
| 명령→핸들러 테이블 | §1의 2·3번(디스패치 if-else + case) | §5 |
| 패킷 디스크립터 테이블 | `fetch_packet` 안의 필드별 오프셋·범위검사 코드(복잡도 최대 기여자) | §3 |
| 응답 조립 공통 함수 3종 | 명령마다 손으로 짜는 `tx_buf[tx_index++] = ...` 반복 | §4 |
| enum 추가 | (그대로 유지) | §1의 1번은 원래도 1줄이라 더 줄일 게 없음 |

## 3. 패킷 디스크립터 테이블

### 3.1 구조체 정의

```c
/* tdc_ble_field_desc.h (신규) */

typedef struct
{
    uint8_t  offset;        /* 패킷 내 시작 오프셋(0~20, 헤더 포함 절대 위치) */
    uint8_t  width;         /* 1 또는 2 (바이트). 2바이트는 상위<<8|하위 조립 */
    uint8_t  count;         /* 이 엔트리가 채우는 원소 개수. 스칼라 필드는 1 */
    int16_t  min;           /* 범위 검사 최소값 */
    int16_t  max;           /* 범위 검사 최대값. min==max==0 이면 범위 검사 생략 */
    uint16_t field_offset;  /* offsetof(대상 구조체, 필드) 또는 offsetof(대상 구조체, 배열[시작인덱스]) */
} tdc_ble_field_desc_t;

typedef struct
{
    uint8_t  command;       /* 헤더값(예: en__mapping_live_stimulation) */
    uint8_t  subCommand;    /* 서브커맨드 없으면 0 */
    uint8_t  data_index;    /* 데이터 인덱스 없으면 0(단일 패킷) */
    uint8_t  field_count;   /* 이 (command, subCommand, data_index) 조합에 속한 필드 엔트리 개수 */
    uint16_t field_start;   /* tdc_ble_field_table[] 안에서 이 조합의 첫 엔트리 위치 */
} tdc_ble_index_desc_t;
```

`field_offset`은 `offsetof()`에 배열 첨자를 그대로 넣어 계산한다(예: `offsetof(ST__MAPPINGPAYLOAD_LIVE_STIMULATION, usableStimulationElectrodIndex[17])`) - 이 프로젝트가 쓰는 GCC 계열 툴체인에서 표준적으로 허용되는 관용구이며, 배열 몇 번째 원소부터 채우는지를 별도 열 없이 이 한 필드로 표현한다.

### 3.2 범용 파서 의사코드

```c
/* tdc_ble_packet_parser.c (신규), 의사코드 */

typedef enum
{
    TDC_BLE_PARSE_OK = 0,
    TDC_BLE_PARSE_NOT_FOUND,     /* (command, subCommand, data_index) 조합이 테이블에 없음 */
    TDC_BLE_PARSE_RANGE_ERROR,   /* 필드 범위 검사 실패 */
} tdc_ble_parse_result_t;

tdc_ble_parse_result_t tdc_ble_parse_by_descriptor(const uint8_t *packet, uint8_t command,
                                                    uint8_t subCommand, uint8_t data_index,
                                                    void *dest_struct)
{
    const tdc_ble_index_desc_t *idx = tdc_ble_find_index_desc(command, subCommand, data_index);

    if (idx == NULL)
    {
        return TDC_BLE_PARSE_NOT_FOUND;
    }

    for (int i = 0; i < idx->field_count; i++)
    {
        const tdc_ble_field_desc_t *entry = &tdc_ble_field_table[idx->field_start + i];
        const uint8_t *p = packet + entry->offset;

        for (int k = 0; k < entry->count; k++)
        {
            int raw = (entry->width == 2) ? ((p[0] << 8) | p[1]) : p[0];
            p += entry->width;

            if (((entry->min != 0) || (entry->max != 0))
                && ((raw < entry->min) || (entry->max < raw)))
            {
                return TDC_BLE_PARSE_RANGE_ERROR;
            }

            *(int *) ((uint8_t *) dest_struct + entry->field_offset + (k * sizeof(int))) = raw;
        }
    }

    return TDC_BLE_PARSE_OK;
}
```

`tdc_ble_find_index_desc()`는 (command, subCommand, data_index) 3중 키로 `tdc_ble_index_desc_t[]`를 선형 탐색한다. 명령 하나당 데이터 인덱스가 많아야 15개 안팎이라 선형 탐색으로 충분하고, 정렬 후 이진 탐색으로 바꾸는 최적화는 실측 없이 하지 않는다(과도한 추상화 금지 원칙).

### 3.3 구체 예시 - 0x66 서브커맨드1(전체 파라미터, 데이터 인덱스 1~15)

현재 코드(`tdc_ble_mapping.c:341-739`, 약 400줄)를 그대로 디스크립터로 옮기면 다음과 같다. 데이터 인덱스 1은 스칼라 9개(그중 1개는 2바이트), 인덱스 2~15는 32채널 배열 7종을 절반씩 나눠 싣는다(17+15원소).

|---|---|---|---|---|---|---|---|

| 1 | audioVolume | 4 | 1 | 1 | 1 | 10 | `:388-389` |

| 1 | stimulationIndicatorAmplitude_uA | 6 | 2 | 1 | 0 | 1800 | `:402-403` |

| 1 | stimulationMode | 9 | 1 | 1 | 1 | 6 | `:416-417` |
| 1 | firstPulsePhase | 10 | 1 | 1 | 0 | 1 | `:423-424` |
| 1 | stimulationPulsePhaseWidth | 11 | 1 | 1 | 13 | 255 | `:430-431` |
| 1 | numFrequencyBand | 12 | 1 | 1 | 1 | 32 | `:437-438` |
| 2 | usableStimulationElectrodIndex[0..16] | 3 | 1 | 17 | 1 | 100 | `:448-457` |

**23개 필드 엔트리 + 15개 인덱스 엔트리로 약 400줄이 흡수된다.** 배열이 인덱스 2/3, 4/5, 6/7처럼 "17개+15개"로 쪼개지는 것은 `count` 열이 그대로 표현하고, 어느 원소부터 채우는지는 `field_offset`이 `usableStimulationElectrodIndex[17]`처럼 배열 첨자를 그대로 받아 표현한다 - 별도의 "배열 시작 인덱스" 열이 필요 없다.

이 예시에서 살아남는(테이블 밖) 코드는 세 가지뿐이다.

1. **순차성 검사** - "받은 데이터 인덱스가 `prev+1`인가"(`:352-357`). 이건 필드 범위검사가 아니라 **전송 순서 규약**이라 테이블 개념과 안 맞는다. 0x66·0x68·0x6C·0x6D·0x4C·0x4D 6개 명령이 토씨 하나 안 틀리고 복붙한 로직이므로, 테이블 대신 **공용 헬퍼 함수 하나**로 뽑는다: `bool tdc_ble_check_sequential_index(int received, int *prev_state)`. 디스크립터 테이블 자체보다 이쪽이 실은 더 즉각적인 중복 제거 효과가 있다.
2. **완료 시점 훅** - 인덱스 15(=`Live_AllParameter_payloadNum`) 도달 시 `audio_input_x_mim/max[]`를 기본값으로 채우고 `subCommand`를 `en__allParameter`로 승격하는 로직(`:710-736`). 이건 "필드"가 아니라 "이 서브커맨드가 끝났을 때의 부수효과"라서 테이블에 억지로 넣지 않고, case 블록에 `tdc_ble_live_all_param_complete_hook()` 명시 호출로 남긴다.
3. **응답 조립** - §4로 이관.

### 3.4 특수 검사(단순 min/max가 아닌 것)는 테이블 밖 훅으로

같은 0x66 안에서도 서브커맨드 3(자극 볼륨 조절)·4(마이크 감도 조절)·5(알림 자극)는 디스크립터로 옮기지 **않는다**. 이유:

| 서브커맨드 | 왜 min/max 테이블로 표현이 안 되는가 | 근거 |
|---|---|---|
| 3, 4 | 범위 검사 이전에 **"현재 `subCommand`가 `en__HoldOn`인가"라는 상태 게이트**가 선행한다. 실패 시 에러 종류도 `en__OutOfDataRange`가 아니라 `en__Command_Order`로 달라진다 | `:750,767` |
| 5 | 상한값 자체가 상수가 아니라 **런타임 공유메모리 값**(`p_mapDataSharedMemory->numFrequencyBand`)이라 컴파일 타임 테이블에 못 넣는다 | `:807-817` |

이 셋은 필드 1개짜리 짧은 손코딩이라 테이블화해도 이득이 적다. **"단순 min/max로 안 끝나는 검사는 테이블에 억지로 넣지 않고 기존 손코딩을 그대로 둔다"**를 원칙으로 삼는다 - 데이터 인덱스 1처럼 필드 수가 많고 검증이 전부 정적 범위인 경우에만 테이블 전환의 이득이 크다.

### 3.5 ROM/RAM 비용 추정

| 항목 | 크기 | 계산 근거 |
|---|---|---|
| `tdc_ble_field_desc_t` 1행 | 10바이트 | `uint8_t×3 + 패딩1 + int16_t×2 + uint16_t×1` (2바이트 정렬) |
| `tdc_ble_index_desc_t` 1행 | 6바이트 | `uint8_t×4 + uint16_t×1` |
| 테이블화 대상(0x66 서브1·0x68·0x6C·0x6D·0x4C·0x4D) 필드 행 수 | 약 100~150행(추정) | 0x66 서브1 실측 23행을 기준으로, 나머지 5개 명령의 fetch 줄 수 비례 외삽(실측 아님) |
| 필드 테이블 총합 | 약 1.0~1.5KB | 100~150행 × 10바이트 |
| 인덱스 테이블 총합(약 60~70행) | 약 400바이트 | 필드 행마다 평균 2행 정도로 묶인다고 가정 |
| 파서 함수 코드(`tdc_ble_parse_by_descriptor` 등) | 약 0.3~0.6KB(추정) | Thumb2 컴파일 기준 개략치, 실측 아님 |
| **총 추가 ROM** | **약 2~2.5KB(추정)** | 위 합산 |
| 제거되는 손코딩(6개 명령 fetch 부분, 현재 약 847줄 중 대다수) | 미확정, 감소 방향 | 반복되는 범위검사 if 블록(비교+분기+에러콜) 1개당 대략 수 바이트~십수 바이트의 Thumb 코드를 발생시키므로, 정량 비교 없이도 **테이블 추가분과 상쇄되거나 순감소할 가능성이 높다** |
| 추가 RAM | **0에 가까움** | 디스크립터 테이블은 `const`라 `.rodata`(플래시)에 상주. 파서 지역 변수는 스택 수십 바이트 이내(일시적) |

> [!NOTE]
> 이 수치는 0x66 서브1 하나만 실측하고 나머지 5개 명령은 fetch 줄 수 비례로 외삽한 추정치다. **도구로 검증된 값이 아니며**, `복잡도 실측.md`와 같은 방식으로 "정성적 방향(ROM 소폭 증가 또는 중립, RAM 거의 무영향)은 신뢰하되 소수점 단위 수치에는 의존하지 않는다."

## 4. 응답 조립 공통화

에러 응답은 이미 `tdc_sys_error_send_to_app()`(`tdc_sys_error.c:147`)로 공통화되어 있다. 정상 응답만 명령마다 손으로 `tx_buf[tx_index++] = ...`를 반복한다. `tdc_ble_general_debug.c`·`tdc_ble_gain_control.c`가 이미 "패킷 포인터 주입 + `tx_index` 반환" 패턴으로 검증됐으므로 이를 함수 3종으로 승격한다.

```c
/* tdc_ble_reply.h (신규) */
static inline int tdc_ble_reply_header(uint8_t *tx, int header)
{
    tx[0] = (uint8_t) header;
    return 1;
}

static inline int tdc_ble_reply_put_u8(uint8_t *tx, int idx, int v)
{
    tx[idx] = (uint8_t) v;
    return idx + 1;
}

static inline int tdc_ble_reply_put_u16(uint8_t *tx, int idx, int v)
{
    tx[idx]     = (uint8_t) ((v >> 8) & 0xFF);
    tx[idx + 1] = (uint8_t) (v & 0xFF);
    return idx + 2;
}
```

`tdc_ble_reply_send()`는 만들지 않는다 - 기존 `tdc_hal_spi_write_tx_buffer(tx_buf, tx_index)` 호출을 그대로 쓰면 되고, 굳이 한 겹 더 감싸는 것은 "단순·특화" 원칙에 어긋난다. 0x30(`setting_nrf_ble_adv_info`)처럼 헤더를 생략하는 유일한 예외는 `tdc_ble_reply_header()`를 호출하지 않고 바로 `tdc_ble_reply_put_u8()`부터 쓰면 그만이라 별도 분기를 둘 필요가 없다.

**적용 예(0x66 서브1 완료 응답, `:700-708`)**:

```c
int tx_index = tdc_ble_reply_header(bufferForSPI_tx, en__mapping_live_stimulation);
tx_index      = tdc_ble_reply_put_u8(bufferForSPI_tx, tx_index, en__allParameter);
tx_index      = tdc_ble_reply_put_u8(bufferForSPI_tx, tx_index, subCommandData_Num_index);
tdc_hal_spi_write_tx_buffer(bufferForSPI_tx, tx_index);
```

**검증**: 응답 바이트열이 실측 RTT 로그 7종과 완전 일치(재구조화 설계안.md 단계_2와 동일 기준).

## 5. 핸들러 등록 구조 - 명령→핸들러 테이블

### 5.1 왜 희소 배열이 안 되는가

헤더값은 0x30~0x36 · 0x40~0x59 · 0x60~0x72+0x91 · 0x8C·0x8F · 0xC0~0xC3로 흩어져 있다. 0x00~0xFF 전체를 배열 하나로 잡으면 256행 중 실제로 쓰이는 건 63개뿐이라 대부분이 빈 슬롯이다(`void *` 포인터 2개 기준 256×8=2KB, 그중 약 1.5KB가 낭비). **그룹별로 쪼갠 작은 배열**을 쓰면 이 낭비가 사라진다 - 이미 `tdc_ble_communication.c`의 최상위 범위 분기가 이 역할을 하고 있으므로, 그 구조를 유지한 채 **그룹 안쪽만** 테이블화한다.

### 5.2 그룹별 명령 테이블

```c
/* tdc_ble_mapping_table.c (신규) */
typedef struct
{
    void (*fetch_fn)(const uint8_t *packet);  /* NULL = 미구현(0x90처럼 default 낙하) */
} tdc_ble_command_desc_t;

#define TDC_BLE_MAPPING_TABLE_SIZE (en__mapping_waiting_for_BleOff - en__mapping_connect + 1)

static const tdc_ble_command_desc_t tdc_ble_mapping_table[TDC_BLE_MAPPING_TABLE_SIZE] =
{
    [en__mapping_connect          - en__mapping_connect] = { mp_fetch_connect },
    [en__mapping_disconnect       - en__mapping_connect] = { mp_fetch_disconnect },
    [en__mapping_impedanceChekck  - en__mapping_connect] = { mp_fetch_impedance },
    [en__mapping_live_stimulation - en__mapping_connect] = { mp_fetch_live_stimulation },
    /* ... 0x62~0x71 나머지도 동일 형태로 한 줄씩 ... */
    [en__mapping_waiting_for_BleOff - en__mapping_connect] = { NULL },  /* Rx 명령 아님, 내부 전이 전용 */
};
```

**배열 크기·인덱스를 하드코드 hex가 아니라 enum 상수 차로 계산**하는 것이 핵심이다. 명령 카탈로그 문서가 지적하듯 `en__mapping_waiting_for_BleOff`(0x72)·`en__mapping_read_Connected_ISD_id`(0x91)는 명시 hex 없이 컴파일러 자동 증가에 의존한다 - 앞에 새 값이 끼어들면 실제 hex가 밀린다. 배열도 hex 리터럴이 아니라 `en__mapping_disconnect - en__mapping_connect`처럼 **같은 enum 상수로 인덱스를 계산**하면 hex가 밀려도 테이블은 자동으로 따라간다.

0x91(`en__mapping_read_Connected_ISD_id`)은 0x73~0x8F 사이 29칸이 통째로 비므로 테이블에 끼워 넣으면 오히려 희소해진다. 이런 **"그룹 범위 안인데 멀리 떨어진 외톨이"는 테이블 밖에서 명시 분기 하나로 남긴다**:

```c
void tdc_ble_mapping_fetch_packet(const uint8_t *packet)
{
    int header = packet[0];
    int idx    = header - en__mapping_connect;

    if (header == en__mapping_read_Connected_ISD_id)  /* 0x91 - 외톨이, 테이블 밖 */
    {
        mp_fetch_read_connected_isd_id(packet);
        return;
    }

    if ((idx < 0) || (TDC_BLE_MAPPING_TABLE_SIZE <= idx) || (tdc_ble_mapping_table[idx].fetch_fn == NULL))
    {
        tdc_ble_mapping_send_undefined(header);  /* 기존 default: 낙하와 동일한 2바이트 응답(0xF0 아님, §명령 카탈로그.md §5.2) */
        return;
    }

    tdc_ble_mapping_table[idx].fetch_fn(packet);
}
```

0x40~0x59(32개, 빈틈 없음)·0xC0~0xC3(4개, 빈틈 없음)도 같은 패턴을 그대로 적용할 수 있다. 0x8C·0x8F(단 2개, 서로 멀리 떨어짐)는 테이블화 이득이 없으므로 **현행 개별 `else if` 두 줄을 그대로 둔다** - 이미 최소 형태다. 0x30~0x36(QCC 상태 통지)은 "명령→응답"이 아니라 "상태 알림 수신"에 가까운 성격이라(명령 카탈로그.md §3.1) 이번 테이블화 범위 밖으로 남긴다.

### 5.3 (command, subCommand) 2단 테이블이 필요한 경우

0x66은 헤더 하나에 서브커맨드 9개가 물려 있다. `fetch_fn` 하나(`mp_fetch_live_stimulation`)가 내부에서 서브커맨드별로 다시 분기해야 하는데, 이 안쪽 분기까지 테이블화할지는 §3.4 기준을 따른다 - 서브커맨드 1(전체 파라미터)만 §3의 디스크립터로 가고, 서브커맨드 2~9는 상태 게이트가 섞여 있어 손코딩을 유지하는 `switch(liveSubCommand)`로 남긴다. 즉 **명령→핸들러는 테이블, 핸들러 내부의 서브커맨드 분기는 하이브리드**다.

## 6. 신규 프로토콜 추가 절차

### 6.1 예시 - 새 매핑 명령 0x73(가상, 데이터 인덱스 없는 단일 패킷 3필드) 추가

| 단계 | 손댈 위치 | 내용 |
|---|---|---|
| 1 | `tdc_ble_protocol.h` | `EN__MAPPING_COMMAND` enum 끝(`en__mapping_waiting_for_BleOff` 다음)에 `en__mapping_read_battery_calib,` 한 줄 추가(자동으로 0x73) |
| 2 | `tdc_ble_field_table.c` | 이 명령의 필드 3개 행 추가 + `tdc_ble_index_desc_t` 1행(`{ en__mapping_read_battery_calib, 0, 0, 3, <field_start> }`) |
| 3 | `tdc_ble_mapping_table.c` | `[en__mapping_read_battery_calib - en__mapping_connect] = { mp_fetch_battery_calib },` 한 줄 추가. `TDC_BLE_MAPPING_TABLE_SIZE`는 매크로라 자동으로 1 늘어남 |
| 4 | (신규 static 함수) | `mp_fetch_battery_calib()`는 `tdc_ble_parse_by_descriptor()` 호출 1줄 + 실패 시 에러 전송 + 성공 시 §4 응답 조립 3줄 - 약 10줄 |

**끝.** 데이터 인덱스가 없는 단순 명령이면 손댈 파일이 3개(enum·필드테이블·명령테이블)와 짧은 함수 하나뿐이다.

### 6.2 개선 전후 대조

| 항목 | 개선 전(§1 실측, 0x8C 기준) | 개선 후(위 예시) |
|---|---|---|
| 건드리는 파일 수(프로토콜 배선만) | 4개(enum·디스패처·case·신규 핸들러 파일) | 3개(enum·필드테이블·명령테이블) + 짧은 함수 |
| 디스패치 로직 변경 위치 | 2곳(`tdc_ble_communication.c`의 if-else, `tdc_ble_remote.c`의 case) | 0곳(테이블 행 추가만, 분기 코드 자체는 불변) |
| 범위 검사 코드 | 명령마다 손으로 if 블록 작성 | 테이블 행의 min/max 열만 채움 |
| 응답 조립 코드 | 명령마다 `tx_buf[tx_index++]=...` 반복 작성 | §4 공통 함수 호출 3줄 |
| 데이터 인덱스 분할 명령일 경우 추가 비용 | fetch_packet 안에 새 case + switch(index) 통짜 작성(수십~수백 줄) | 필드테이블에 데이터 인덱스별 행 추가(§3.3처럼 1행/필드) |

## 7. 기존 프로토콜 수정 절차

### 7.1 범위 값만 바뀌는 경우(가장 흔함)

예: "0x66 서브1 데이터 인덱스1의 `audioVolume` 상한을 10 → 15로 변경". 테이블 해당 행의 `max` 열 값 하나만 고치면 끝난다(§3.3 표에서 `audioVolume` 행의 `max=10`을 `15`로).

### 7.2 페이로드 레이아웃 자체가 바뀌는 경우(원칙적으로 발생하면 안 됨)

프로토콜 규약은 앱·리모콘과 공유되는 불가침이라(§0) 필드 폭·오프셋이 바뀌는 일은 원래 있어서는 안 된다. 그래도 발생한다면: 해당 필드의 `offset`/`width`를 고치고, **같은 데이터 인덱스 안에서 그 뒤에 오는 모든 필드의 `offset`도 함께 밀어야 한다** - 이는 이 설계의 정직한 약점이다(§8에서 다시 다룬다). 손코딩 시절에도 동일하게 뒤따르는 `Rx_dataPacket[index++]` 전부를 밀어야 했으므로 위험이 새로 생기는 것은 아니고, 다만 **연쇄 수정 범위가 테이블 행 단위로 눈에 더 잘 띈다**(같은 data_index를 가진 행을 모아보면 몇 바이트씩 밀렸는지 즉시 계산 가능).

## 8. 트레이드오프

| # | 단점 | 완화책 |
|---|---|---|
| 1 | **흐름 추적이 어려워진다** - "이 바이트가 이 필드"가 switch-case에서 바로 안 보이고 테이블 조회를 한 번 더 거친다 | 테이블 행 주석에 데이터 인덱스·코드 원본 줄 번호(§3.3처럼)를 병기하고, `명령 카탈로그.md`를 프로토콜 문서 대응표로 계속 유지(재구조화 설계안.md §3 "가독성 대응"과 동일 원칙) |
| 2 | **디버깅 시 스택 트레이스가 덜 친절해진다** - 범위 위반이 나면 모든 필드가 `tdc_ble_parse_by_descriptor()`라는 같은 프레임에서 실패해 "어느 필드인지"가 콜스택만으론 안 보인다 | 실패 시 `entry`의 인덱스(테이블 내 위치)를 함께 반환해 디버그 빌드에서 `TDC_PRINTF`로 실패 필드명을 즉시 찍게 한다(릴리즈 빌드는 기존처럼 `tdc_sys_error_send_to_app()`만) |
| 3 | **ROM이 늘어난다** | §3.5 추정 약 2~2.5KB. 제거되는 반복 손코딩과 상쇄될 가능성이 있으나 정밀 측정 전이라 확답은 못 한다 |
| 4 | **특수 케이스가 많으면 테이블이 오히려 복잡해진다** - 상태 게이트·런타임 의존 범위를 억지로 테이블에 넣으려 하면 훅 플래그·예외 열이 난립해 "또 다른 스파게티"가 된다 | §3.4 기준대로 **정적 min/max만으로 끝나는 필드만 테이블화**하고, 상태 게이트가 있는 서브커맨드(0x66 서브3·4·5 등)는 손코딩 유지 |
| 5 | **테이블 주도가 안 맞는 명령이 있다** - 0x60/0x61/0x71처럼 "파싱"이 아니라 "워치독 강제 리셋 루프" 같은 부수효과 시퀀스인 명령, 자극 FSM을 직접 건드리는 명령 | 하이브리드: §5의 명령→핸들러 테이블에는 그대로 등록하되 `fetch_fn`이 가리키는 함수 본체는 현행 손코딩을 그대로 둔다 - 등록 구조와 내부 구현 방식은 독립적이라 섞어도 무방하다 |
| 6 | **페이로드 레이아웃이 바뀌면 같은 데이터 인덱스의 뒤따르는 모든 행을 함께 밀어야 한다**(§7.2) | 발생 빈도 자체가 낮음(프로토콜 불가침). 발생 시 같은 data_index 행을 모아 보면 밀림량 계산이 손코딩보다 오히려 쉬움 |

## 9. 적용하지 않는 것(단순·특화 원칙)

- 전 프로토콜 일괄 테이블화. 0x8C·0x8F처럼 이미 최소 비용인 개별 핸들러, 0x60/0x61/0x71처럼 부수효과 중심인 명령은 그대로 둔다.
- `tdc_ble_reply_send()` 같은 추가 래퍼. 기존 `tdc_hal_spi_write_tx_buffer()` 호출로 충분하다.
- 이진 탐색·해시 기반 디스크립터 조회. 명령당 데이터 인덱스가 최대 15개 안팎이라 선형 탐색으로 충분하고, 실측 없이 최적화하지 않는다.
