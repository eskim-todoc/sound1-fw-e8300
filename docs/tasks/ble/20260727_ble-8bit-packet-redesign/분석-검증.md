# ④ 분석 검증

**TL;DR**: [`분석.md`](분석.md) 를 3축 검증했다. **논리 결함 0건, 근거 보강 1건.** 가장 중요한 판정(`transferLength` 는 워드 수)을 부트로더 코드로 **직접 재검증해 확정**했고, 그 과정에서 **`TRANS_LENGTH_SEL` 이 메모리 쪽 기준이라는 사실을 추가 확인**해 판정을 더 단단하게 만들었다. 5게이트 원칙에 따라 **미확인 2건이 남았으므로 "가능"이 아니라 "조건부 가능"** 결론을 유지한다.

### 2.1 반증 시도

| # | 반증 | 결과 |
|---|---|---|
| 반증_1 | "SPI 가 이미 8비트인데 DMA 가 32비트면 지금도 잘 동작하지 않나? 굳이 바꿀 이유가 있나" | **성립하지 않음.** 현재도 정상 동작하는 것은 맞다. 문제는 동작이 아니라 **버퍼가 `int[21]`(84바이트)이 되어 바이트 프로토콜을 워드 배열로 다루게 강제**된다는 점이다. 메모리 4배 낭비 + 접근 코드 복잡화가 비용이다 |

## 축_3 - 근거 검증

### 3.1 최중요 판정의 직접 재검증

`transferLength` 의 단위는 이번 분석 전체를 좌우하는 판정이다. 노드 결과를 그대로 채택하지 않고 부트로더 코드로 직접 확인했다.

| 코드 | 값 |
|---|---|
| `bootloader.c:280` | `word_size = WORD_SIZE_32BITS_TO_32BITS` |
| `bootloader.c:282` | `dma_len_mul = 0` |
| `bootloader.c:314`·`:326` | `word_size = WORD_SIZE_8BITS_TO_24BITS` |
| `bootloader.c:316`·`:328` | `dma_len_mul = 2` |
| `bootloader.c:450` | `Sys_DMA_ChannelConfig(..., read_size << dma_len_mul, ...)` |

`read_size` 는 32비트 워드 수 단위로 관리되는데(`:368` `read_size = remainder`, `:431` 의 `remainder << 2` 가 워드->바이트 변환), **소스 워드가 8비트가 되면 `<< 2`(×4)로 곱해 넘긴다.**

**결론: `transferLength` 는 "소스 워드 크기 기준 전송 개수"다.** 노드 판정 확인.

**우리 경우 대입**

| 설정 | transferLength | 실제 전송량 | 필요한 버퍼 |
|---|---|---|---|
| 현재 32->32 | 21 | 32비트 워드 21개 = **84바이트** | `int[21]` (84바이트) |
| 변경 후 8->8 | 21 (그대로) | 8비트 워드 21개 = **21바이트** | `uint8_t[21]` (21바이트) |

값 21 을 바꾸지 않아도 되는 이유가 여기서 명확해진다. **개수는 같고 단위가 바뀐다.**

### 3.2 근거 보강 - `TRANS_LENGTH_SEL` 의 기준

분석 본문이 다루지 않은 사실을 검증 중 확인했다.

| DMA | 플래그 | 기준 |
|---|---|---|
| DMA0 (RX, SPI -> 메모리) | `DEST_TRANS_LENGTH_SEL` (`tdc_hal_dma.h:7`) | **목적지 = 메모리** 기준 |
| DMA1 (TX, 메모리 -> SPI) | `SRC_TRANS_LENGTH_SEL` (`:13`) | **소스 = 메모리** 기준 |

**양쪽 모두 메모리 쪽을 길이 기준으로 삼는다.** 8->8 전환 시 메모리 쪽 워드도 8비트가 되므로 21개 = 21바이트로 일관된다. **이 사실이 §3.1 의 판정을 독립적으로 재확인해 준다** - 보강_1 로 분석.md 에 반영한다.

| # | 주장 | 재확인 |
|---|---|---|

| 3-2 | SPI 가 이미 8비트 워드 | 확인 (`tdc_hal_spi.h:17`) |
