# 분석 - BLE 패킷 디스크립터 테이블 (단계_3)

**TL;DR**: 데이터 인덱스 1~15 를 **23개 필드 디스크립터**로 완전히 표현할 수 있음을 전수 확인했다. 핵심 설계 결론은 **필드 폭을 손으로 적지 않고 `sizeof(((구조체 *)0)->필드)` 로 컴파일러에게 계산시키는 것** — ARM 과 호스트의 `sizeof(enum)` 이 **1 대 4** 로 다르기 때문에, 손으로 적으면 호스트 테스트가 통과해도 실기에서 깨진다.

## 1. 대상 구조 전수 분해

### 1.1 데이터 인덱스 1 - 스칼라 9필드 (유형_A)

패킷 오프셋은 `index` 진입값 3 기준이다(0=명령 0x66, 1=하위명령 `en__allParameter`, 2=데이터 인덱스).

| # | 패킷 오프셋 | 필드 | 읽기 폭 | min | max | 파싱 | 검사 |
|---|---|---|---|---|---|---|---|
| 1 | 3 | `stimulVolume` | 1 | 1 | 4 | `:153` | `:167` |
| 2 | 4 | `audioVolume` | 1 | 1 | 10 | `:154` | `:174` |
| 3 | 5 | `stimulationIndicatorChannelNum` | 1 | 1 | 32 | `:155` | `:181` |
| 4 | 6~7 | `stimulationIndicatorAmplitude_uA` | **2** | 0 | 1800 | `:156~158` | `:188` |
| 5 | 8 | `stimulationStrategy` | 1 | 1 | 3 | `:160` | `:195` |
| 6 | 9 | **`stimulationMode`** | 1 | 1 | 6 | `:161` | `:202` |
| 7 | 10 | `firstPulsePhase` | 1 | 0 | 1 | `:162` | `:209` |
| 8 | 11 | `stimulationPulsePhaseWidth` | 1 | 13 | 255 | `:163` | `:216` |
| 9 | 12 | `numFrequencyBand` | 1 | 1 | 32 | `:164` | `:223` |

> [!IMPORTANT]
> **패킷 순서와 구조체 선언 순서가 다르다.** 패킷은 `strategy` -> `stimulationMode` -> `firstPulsePhase` 순이나, 구조체는 `strategy`(offset 20) -> `firstPulsePhase`(24) -> `stimulationMode`(28) 순이다(`tdc_ble_mapping.h:60~62`). 따라서 **구조체 선언 순서를 훑어 테이블을 자동 생성하는 접근은 성립하지 않는다.** 테이블은 패킷 순서로 나열하고 대상 필드를 오프셋으로 지목해야 한다.

### 1.4 항상 거짓인 범위 검사 (보존 대상)

패킷은 `uint8_t` 배열이므로 읽은 값은 항상 0~255(1바이트) 또는 0~65535(2바이트)다. 따라서 다음 검사는 **결코 참이 되지 않는다.**

| 검사 | 위치 | 사유 |
|---|---|---|
| `stimulationIndicatorAmplitude_uA < 0` | `:188` | u16 소스라 음수 불가. 코드에 `< 0 /*1*/` 주석 - 원래 하한 1 을 0 으로 완화한 흔적 |
| `firstPulsePhase < 0` | `:209` | u8 소스 |
| `255 < stimulationPulsePhaseWidth` | `:217` | u8 소스라 최대 255 |
| `T_level_uA[i] < 0` · `C_level_uA[i] < 0` | `:336`·`:408` 등 8곳 | u16 소스 |

> [!NOTE]
> **이들을 "죽은 코드"라고 제거하면 안 된다.** 테이블에 `min`/`max` 로 그대로 표현하면 동일하게 항상 거짓이 되어 **동작이 자동 보존**되고, 프로토콜 문서상의 명목 범위도 테이블에 남는다. 요구사항_5(문서 1:1 대응)에도 부합한다.

## 2. 구조체 레이아웃 실측

프로젝트 실제 헤더(`tdc_ble_mapping.h`)를 양쪽 툴체인으로 컴파일해 측정했다.

| 측정 | ARM (Cortex-M3, 프로젝트 플래그) | 호스트 (MinGW x86_64) |
|---|---|---|
| `sizeof(stimulationMode)` | **1** | **4** |
| `sizeof(stimulVolume)` | 4 | 4 |
| `sizeof(T_level_uA[0])` | 4 | 4 |
| `offsetof(stimulVolume)` | 4 | 4 |
| `offsetof(stimulationStrategy)` | 20 | 20 |
| `offsetof(firstPulsePhase)` | 24 | 24 |
| `offsetof(stimulationMode)` | 28 | 28 |
| `offsetof(stimulationPulsePhaseWidth)` | 32 | 32 |
| `offsetof(numFrequencyBand)` | 36 | 36 |
| `sizeof(구조체 전체)` | 944 | 944 |

### 2.1 이 표에서 나오는 3가지 결론

**결론_1 - 오프셋은 양쪽이 같다.** `stimulationMode`(28) 뒤 3바이트가 ARM 에서 정렬 패딩이 되고, 호스트에서는 enum 자체가 4바이트를 차지한다. 그 결과 다음 필드가 양쪽 다 32 에서 시작한다. **인접 필드 침범 위험은 현재 필드 배치에서는 없다.**

**결론_2 - 그럼에도 폭을 손으로 적으면 안 된다.**

> [!CAUTION]
> **호스트 테스트는 이 오류를 잡지 못한다.** 디스크립터에 `stimulationMode` 의 폭을 4 로 적으면 호스트(4바이트 필드)에서는 정확히 동작해 테스트가 **통과**한다. ARM 에서는 1바이트 필드에 4바이트를 쓰게 되고, 지금은 뒤가 패딩이라 우연히 동작하지만 **필드 순서가 한 번 바뀌면 즉시 인접 필드를 파괴**한다. 게다가 구조체 필드를 다른 타입으로 접근하는 것 자체가 정의되지 않은 동작이라 최적화 수준에 따라 결과가 달라질 수 있다.

**결론_3 - 해법은 컴파일러에게 계산시키는 것이다.**

```c
sizeof(((ST__MAPPINGPAYLOAD_LIVE_STIMULATION *)0)->stimulationMode)
```

이 식은 **각 타깃에서 컴파일러가 스스로 1 또는 4 를 산출**한다. 손으로 적는 순간 생기는 플랫폼 불일치가 원천 소멸한다. 요구사항_3("디스크립터에 필드 폭 명시")의 올바른 구현이 이것이다.

## 3. 테이블 설계 대안 비교

### 3.1 디스크립터 엔트리 구조

```c
/* 개념 - 확정 시그니처는 계획에서 */
typedef struct
{
    uint16_t dst_offset;  /* 페이로드 구조체 기준 바이트 오프셋 */
    uint8_t  dst_size;    /* 대상 필드 폭 (sizeof 로 자동 산출) */
    uint8_t  src_width;   /* 패킷에서 읽을 폭 - 1 또는 2 (빅엔디안) */
    uint8_t  count;       /* 연속 원소 수 - 스칼라 1, 배열 청크 8/15/17 */
    int16_t  min;
    int16_t  max;
} tdc_ble_field_desc_t;
```

`min`/`max` 실측 범위는 0~1800 이므로 `int16_t` 로 충분하다(최대 1800 < 32767).

**`dst_size` 와 `src_width` 는 별개다.** 전자는 구조체 필드 폭(1 또는 4), 후자는 패킷에서 읽는 바이트 수(1 또는 2). 인덱스 8~15 는 `src_width`=2, `dst_size`=4 인 조합이다.

엔트리는 매크로로 생성해 `offsetof` 와 `sizeof` 를 결합한다.

```c
/* 스칼라 */
#define TDC_BLE_DESC_FIELD(f, w, mn, mx)  \
    { offsetof(TDC_LIVE_T, f), sizeof(((TDC_LIVE_T *)0)->f), (w), 1, (mn), (mx) }

/* 배열 청크 */
#define TDC_BLE_DESC_ARRAY(f, start, n, w, mn, mx)                     \
    { offsetof(TDC_LIVE_T, f) + (start) * sizeof(((TDC_LIVE_T *)0)->f[0]), \
      sizeof(((TDC_LIVE_T *)0)->f[0]), (w), (n), (mn), (mx) }
```

### 3.2 인덱스 -> 디스크립터 매핑 방식

| 대안 | 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| 대안_1 | **인덱스별 배열 + 개수를 담은 2계층 테이블** | 조회 O(1), 인덱스 유효성 검사가 배열 범위 검사 하나로 끝남, 문서 대조 시 "인덱스 N 행"이 명확 | 테이블이 둘 | **채택** |
| 대안_2 | 단일 테이블 + 각 엔트리에 `data_index` 를 넣고 선형 스캔 (설계안 §3 스케치) | 테이블 하나 | 매 수신마다 23엔트리 스캔, 인덱스 유효성 판정이 "매치 0건"이라는 간접 조건이 됨 | 미채택 |
| 대안_3 | 유형_A / 유형_B·C 를 각각 다른 테이블·다른 루프로 분리 | 각 루프가 단순 | 루프가 둘로 늘어 흡수 효과가 반감, 유형_A 도 결국 `count`=1 인 특수 케이스라 통합 가능 | 미채택 |

> [!NOTE]
> 설계안의 개념 스케치는 대안_2(`data_index` 필드) 였으나, **실측 결과 인덱스가 1~15 로 조밀한 정수라 배열 인덱싱이 자연스럽다.** 스케치를 그대로 따를 이유가 없다.

> [!CAUTION]
> **다만 함수에 도달하는 인덱스는 1~15 로 한정되지 않는다.** 데이터 인덱스 연속성 카운터가 `map_flash` 와 공유되고 flash 는 인덱스를 **34** 까지 쓰므로, 실제 도달 범위는 **1~35** 다(상세: [`분석-검증.md §3.2 발견_2`](분석-검증.md)). 현재 코드의 `default:`(`:471~475`)는 죽은 코드가 아니라 **살아 있는 방어 코드**이며, 테이블 방식에서는 **인덱싱 전 상한 검사로 반드시 대체**해야 한다. 생략하면 `.rodata` 범위 밖을 읽어 임의 오프셋에 쓰기가 발생한다.

### 3.3 예상 `.rodata` 비용

| 항목 | 계산 | 크기 |
|---|---|---|
| 필드 디스크립터 23개 | 23 x 8바이트 | 184 B |
| 인덱스 테이블 15개 | 15 x (포인터 4 + 개수 4, 정렬 포함) | 120 B |
| **합계** | | **약 304 B** |

대체되는 코드는 `switch` 본문 328줄이다. `-O0` 빌드 기준 순감이 유력하나 **크기는 판정 지표가 아니다**(요구사항 기준_4 참조). 계획에서 상한만 정해 둔다.

## 4. 미결 항목 해소

### 미결_1 - 범위 검사를 테이블에 넣을 것인가 -> **넣는다**

근거: §1.1~1.3 실측상 **모든 필드가 `min`/`max` 두 정수로 완전히 표현된다.** 예외가 될 뻔한 것은 0x65 의 `bipolarReferenceElectrodeNum` 99 예외(`tdc_ble_map_stim.c:86`)뿐인데 **이번 범위 밖**이다(요구사항 제외_3). §1.4 의 항상 거짓인 검사도 `min`/`max` 로 그대로 표현된다.

### 미결_2 - 유형_A 와 유형_B·C 를 통합할 것인가 -> **통합한다**

근거: 유형_A 는 `count`=1 인 배열 청크로 볼 수 있다. `count` 필드 하나로 두 유형이 같은 루프에 들어간다. 대안_3 미채택 사유와 동일하다.

### 미결_3 - 테이블 배치 위치 -> **`tdc_ble_map_stim.c` 내부 `static`**

근거: 이번 범위가 0x66 하위 1 단일 명령이다(요구사항 제외_1·2). 별도 파일·공개 헤더는 사용처가 하나뿐인 API 를 만들어 결합만 늘린다. **flash 계열로 확장할 때 그때 승격**하면 되고, 그 판단은 단계_3 완료 후의 별도 트랙이다.

> [!NOTE]
> 다만 **순회 루프 함수 자체는 확장 시 재사용 가치가 있다.** 테이블은 `static` 으로 두되 루프 함수는 다른 명령에서도 쓸 수 있는 시그니처(구조체 베이스 포인터 + 디스크립터 배열 + 개수)로 설계한다. 승격 비용을 미리 낮춰 두는 것이지 지금 공개하는 것이 아니다.

### 미결_4 - 신규 테스트 케이스 설계 -> **14개 case 전수 + 유형별 경계**

근거: 인덱스 2~15 는 본문이 동일해 보이지만 **틀리기 쉬운 것은 본문이 아니라 각 청크의 시작·개수**다(`[0..16]` 17개 vs `[17..31]` 15개, `[16..23]` 등). 유형 대표만 검사하면 **바로 그 지점을 놓친다.**

| 테스트 축 | 내용 | 케이스 수(예상) |
|---|---|---|
| 축_1 적재 위치 | 인덱스 2~15 각각에 대해 청크 **첫 원소·마지막 원소**가 배열의 올바른 위치에 들어가는지 | 14 x 2 = 28 |
| 축_2 청크 경계 침범 없음 | 청크 밖 원소가 오염되지 않았는지 (인접 원소 확인) | 14 |
| 축_3 16비트 조립 | 인덱스 8~15 의 빅엔디안 조립 (상위<<8 \| 하위) | 8 |
| 축_4 범위 경계 | 유형_B 하한 1·상한 100·초과 101 거부, 유형_C 상한 1800·초과 1801 거부 | 약 10 |
| 축_5 순차 수신 | 인덱스 1~15 를 순서대로 전부 넣어 15 에서 완료 처리(`subCommand`·`audio_input_x_*` 초기화) | 약 5 |

**축_5 가 특히 중요하다.** 현재 테스트는 인덱스 1 만 넣고 끝나므로 `Live_AllParameter_payloadNum`(15) 도달 시의 완료 처리(`:496~518`)가 **한 번도 실행된 적이 없다.**

## 6. 검증 설계

요구사항 기준_4("파싱 대상 필드·경계 상수 집합 동일")를 측정 가능하게 구체화한다.

| # | 검증 | 방법 |
|---|---|---|
| 검증_1 | 디스크립터 23개가 §1.1~1.3 표와 완전 일치 | 대조표를 `구현-검증.md` 에 전수 게재 (엔트리 <-> 원본 코드 라인) |
| 검증_2 | 경계 상수 집합 불변 | 전환 전후 소스에서 범위 상수를 전수 추출해 다중집합 비교 |
| 검증_3 | 신규 테스트가 **전환 전 기존 코드에서 통과** | 테스트 추가 커밋을 전환 커밋보다 **앞에** 두고 그 시점 실행 결과를 기록 |
| 검증_4 | 전환 후 전체 테스트 통과 | `bash tests/unit/run.sh` |
| 검증_5 | ARM 빌드 에러 0 · 경고 0 | CLI 빌드 |
| 검증_6 | `dst_size` 가 ARM 에서 기대대로 산출 | 컴파일 타임 단언 + 필요 시 `.rodata` 덤프로 실제 엔트리 값 확인 |
| 검증_7 | 실기 게이트 | 은수님 - 라이브 15단계 수신 후 자극 정상 |

> [!IMPORTANT]
> **검증_3 이 이번 단계의 안전망 그 자체다.** 신규 테스트가 기존 코드에서 통과한 사실이 기록돼야 "전환 후에도 통과 = 동작 보존"이 성립한다. 순서를 뒤집으면 테스트가 새 구현에 맞춰 작성됐을 가능성을 배제할 수 없다.
