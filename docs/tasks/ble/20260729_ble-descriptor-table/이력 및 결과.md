### 이 작업에서 배운 것

> [!IMPORTANT]
> **지표가 좋은 설계가 기각될 수 있다.** 1차 구현은 `text` **-1,276B**, 대상 함수 **409 -> 101줄**로 모든 정량 지표가 우수했고 검증 6종을 전부 통과했다. 그럼에도 기각된 이유는 **읽는 사람이 매크로 정의를 찾아가야 한 줄을 이해할 수 있었기 때문**이다.
>
> 확정 구현은 정반대로 크기가 **+588B 늘었다.** 유지보수 대상은 지표가 아니라 사람이 읽는 코드라는 판단이다.

**설계 판단의 실질 기준** — 프로토콜이 바뀌었을 때 **몇 곳을 고쳐야 하는가.**

| 설계 | 인덱스 1 에 필드 하나 추가 시 |
|---|---|
| 1차 (디스크립터 테이블) | 필드 배열 1줄 + **슬롯 14줄 연쇄** + 단언 1줄 = **3곳** |
| 확정 (계층 네이밍) | `tdc_ble_cmd_0x66_sub01_idx01_parameters` **한 함수** = **1곳** |

### 구현 방식과 무관하게 남는 사실

발견_1·2 는 1차 구현 과정에서 나왔으나 **어떤 설계를 쓰든 유효**하다.

- **발견_1** — `stimulationMode` 는 ARM 1바이트 · 호스트 4바이트. 앞으로 이 구조체를 **폭 기반으로 다루는 코드**(직렬화 · memcpy · 오프셋 접근)를 쓸 때 반드시 고려해야 한다
- **발견_2** — 데이터 인덱스 카운터를 `map_flash`(최대 34)와 공유하므로 0x66 하위 1 에 **16~35 가 실제 도달**한다. 확정 구현도 `default` 로 방어하며, 테스트 그룹_6 이 이를 검증한다

## 발견

### 발견_1 - 페이로드 구조체에 비-`int` 필드가 존재한다 (2026-07-29)

> [!CAUTION]
> **디스크립터 테이블 설계의 근간을 흔드는 사실이다.** `offsetof` + `int *` 캐스팅으로 필드에 접근하는 통상적 디스크립터 구현이 **그대로는 성립하지 않는다.**

**설계안의 서술** ([`재구조화 설계안.md:149`](../../../참고/ble/재구조화/재구조화%20설계안.md)):

> 페이로드 구조체 필드도 전부 `int` 다(`tdc_ble_mapping.h:10-107`)

**인수인계 문서의 서술** ([`20260728 인수인계 §6.2`](../../../세션_인수인계/20260728_ble-재구조화-단계1-2-테스트인프라.md)):

> 패킷은 `uint8_t[21]` 이고 페이로드 구조체 필드는 여전히 `int` 다

**실측 결과**: `ST__MAPPINGPAYLOAD_LIVE_STIMULATION` 의 `stimulationMode` 만 `int` 가 아니다.

| 위치 | 필드 | 타입 |
|---|---|---|
| `tdc_ble_mapping.h:62` | `stimulationMode` | **`EN___STIMULATION_MODE`** (`tdc_shm.h:67-76`, 값 0~6) |
| 그 외 | 전부 | `int` |

**enum 폭 실측** (ARM 타깃, 프로젝트와 동일 플래그 `-mcpu=cortex-m3 -mthumb -O0`):

```c
typedef enum { a0=0,a1,a2,a3,a4,a5,a6 } E;   /* EN___STIMULATION_MODE 와 동일 값 범위 */
typedef struct { int x; E m; int y; } S;
```

| 측정 | 값 |
|---|---|
| `sizeof(E)` | **1** |
| `offsetof(S,m)` | 4 |
| `offsetof(S,y)` | 8 (정렬 패딩 3바이트) |
| `sizeof(S)` | 12 |

**원인**: `-fshort-enums` 가 **ARM EABI 타깃의 GCC 기본값**이다. 프로젝트 컴파일 플래그
(`src/2__cm3/Debug/source/ble/mapping/subdir.mk:29`)에 `-fno-short-enums` 가 **없다**.

**함의**: 디스크립터가 `stimulationMode` 를 `int` 로 간주해 4바이트를 쓰면 뒤따르는 정렬 패딩까지 덮는다.
현재 값 범위(0~6)와 리틀엔디안 특성상 우연히 동작할 수 있으나 정의되지 않은 동작이며, 필드 순서가
바뀌면 즉시 인접 필드를 파괴한다. **타입 정합 결정(인수인계 §6.4 항목 1)의 실질 내용이 여기에 있다.**

**더 위험한 파생**: 호스트 테스트 러너는 MinGW x86 을 쓰는데(`tests/unit/run.sh:32~44`) 그쪽에서는
`sizeof(enum)` 이 **4** 다. 폭을 손으로 적으면 **호스트 테스트는 통과하고 실기에서만 깨진다.**
해법은 `sizeof(((구조체 *)0)->필드)` 로 컴파일러에게 산출시키는 것이다(계획 §2.2).

### 발견_2 - `default:` 는 도달 가능한 방어 코드다 (2026-07-29)

> [!CAUTION]
> 테이블 인덱싱 전 **상한 검사를 생략하면 배열 범위 밖을 읽어 임의 오프셋에 쓰기**가 발생한다.

데이터 인덱스 연속성 카운터(`tdc_ble_mapping_get/set_seq_index`)가 `map_stim` 전용이 아니라
**`map_flash` 와 공유**된다. 그리고 **`map_flash` 의 데이터 인덱스는 34 까지 간다**(`case` 최대값 실측).

flash 명령이 카운터를 15~34 로 올려 둔 상태에서 0x66 하위 1 이 그 다음 번호로 도착하면
`switch` 에 **16~35** 가 들어온다. 현재 코드는 `default:`(`tdc_ble_map_stim.c:471~475`)가 이를 받는다.

**도달 가능 인덱스 범위: 1~35.** 상세: [`분석-검증.md §3.2`](분석-검증.md).

2026-07-28 세션은 이 공유 상태를 "파일 경계를 넘기 위한 접근자" 문제로만 기록했으나,
실제로는 **파싱 유효 범위에까지 영향을 준다.**
