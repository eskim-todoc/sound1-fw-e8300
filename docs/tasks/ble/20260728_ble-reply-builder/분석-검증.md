## 4. 발견 결함

### 결함_1 (중대) - 16비트 분해 표기가 4가지이며 등가성이 증명되지 않았다

분석 §1.3 은 "마스크 표기가 통일돼 있지 않다(`& 0x00FF` vs `& 0xFF`)"고만 적었으나, 실측 결과 **변형이 4가지**다.

| # | 표기 | 위치 |
|---|---|---|
| 변형_1 | `0xff & (value >> 8)` / `0xff & (value)` | `mapping.c:592-593` |
| 변형_2 | `(char) ((x >> 8) & (0xFF))` / `(char) ((x) & (0xFF))` | `remote_sp_para.c:63-64`·`:121-122` |
| 변형_3 | **`x >> 8`** (마스크 없음) / `x & 0xFF` | `remote_sp_para.c:188-189`·`:209`·`:230`·`:251` |
| 변형_4 | `(x >> 8) & 0x00FF` / `x & 0x00FF` | `general_debug.c:87-93` |

**등가성 판정**

버퍼가 `uint8_t` 배열이므로 대입 시 **하위 8비트만 남는다**(암묵적 절단). 따라서

- 변형_3 의 마스크 부재: `x >> 8` 이 8비트를 넘어도 대입에서 절단되므로 `(x >> 8) & 0xFF` 와 **동일**
- 변형_2 의 `(char)` 캐스팅: `uint8_t` 대입 전 `char`(이 툴체인은 `-fsigned-char`)로 변환되나, 최종 저장은 하위 8비트라 **동일**
- 변형_1·4 의 마스크 순서·폭 차이: 결과 **동일**

**즉 네 표기 전부 빌더 `(v >> 8) & 0xFF` / `(v & 0xFF)` 로 대체 가능하다.**

> [!CAUTION]
> **단, `x` 가 음수일 때는 다르다.** `-fsigned-char` 환경에서 `int` 음수의 `>> 8` 은 산술 시프트(부호 확장)이고, 절단 결과는 여전히 하위 8비트라 동일하다. 그러나 변형_2 의 `(char)` 캐스팅은 구현 정의 동작을 거친다. **실제로 음수가 들어올 수 있는 값인지**(`adc_inputMax`·`isd_id`·`stimulationLevel_uA`)를 ⑤ 계획 착수 시 확인한다.

**조치**: ⑤ 계획에 "16비트 전환 지점 21곳의 입력값 부호 가능성 확인"을 검증 항목으로 넣는다.

### 결함_2 (경미) - `reply_bytes` API 의 필요성이 검토되지 않았다

§2.3 초안에 `tdc_ble_reply_bytes`(배열 복사)가 있으나, 유형_4(배열 복사)가 `ble/` 에 **몇 곳인지 세지 않았다.** 쓰이는 곳이 한둘이면 API 를 만들 이유가 없다.

**조치**: ⑤ 계획에서 유형_4 건수를 세고 3곳 미만이면 API 에서 제외한다.
