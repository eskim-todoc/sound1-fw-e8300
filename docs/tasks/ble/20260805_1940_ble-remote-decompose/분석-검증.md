# 분석 검증 - 이월_2 리모콘 분해

**TL;DR**: 추출 실현 가능성을 실측으로 확인했다. **경계를 넘는 지역 상태가 사실상 없다** — `fetch_packet` 은 `switch` 직후 함수가 끝나 각 case 가 자족하고, `step` 의 `RemoteControlState` 는 `switch` 안에서 한 번도 대입되지 않는다. `tx_index` 는 단계_2 가 확정한 «switch 배타성» 덕에 각 추출 함수가 지역 `0` 초기화로 등가다. **결함 1건** — 분석 §6 의 분기 지표 기준선이 파일 전체 값이라 함수별 대조가 불가능하다.

## 1. 지침 준수

| 항목 | 판정 |
|---|---|
| 계층 네이밍 규약 (`tdc_ble_cmd_0xNN_...`) | PASS — 층 구분자 삽입은 §4 에서 근거와 함께 결정 |
| 테이블 주도 금지 | PASS — 함수 추출만 |
| 과분해 금지 | PASS — 발견_1 이 플래시 6건·6줄 이하 case 를 제외 |

| Mermaid / 한글 라벨 | PASS |

## 2. 논리 정합

### 결함_1 (해소) - 분기 지표 기준선이 대조에 못 쓰인다

분석 §6 은 *"조건 분기 총수 보존 (`case` 65 · `if` 56 …)"* 을 지표로 들었다. 그런데 이 값은 **파일 전체** 수치다.

**문제**: 커밋을 나눠 `fetch_packet` 만 먼저 분해하면, 파일 전체 값은 그대로여도 «`fetch_packet` 안에서 옳게 옮겨졌는가» 를 알 수 없다. 반대로 값이 틀어져도 어느 함수 탓인지 짚지 못한다.

**조치**: 기준선을 **함수별로 나눠** 재측정하도록 계획에 넘긴다. 파일 전체는 합계 검증용으로만 쓴다.

### 정합성 확인 (이상 없음)

| 확인 | 결과 |
|---|---|
| 발견_1(플래시 6건 미추출)이 목표_1 과 모순인가 | 모순 아님. 목표는 «디스패치만 남긴다» 이고 4줄 위임은 디스패치의 일부로 읽힌다 |
| 층 구분자가 불가침 규약을 어기는가 | 어기지 않음. 규약은 `0xNN` 세그먼트를 요구하며 뒤 이름은 자유 |
| 파일 분할 미포함이 이월_2 를 미완으로 만드는가 | 만들지 않음. 이월_2 의 문구는 «분해» 이지 «분할» 이 아니다 |
| 0x59 하위 분해가 과분해인가 | 아님. 151줄 4중 중첩이라 한 함수로도 여전히 크다 |

## 3. 근거 검증 - 추출 시그니처 실현 가능성

**분석이 다루지 않은 가장 중요한 질문**: 각 case 를 함수로 빼려면 **어떤 지역 상태가 경계를 넘어야 하는가.** 이것이 크면 추출이 지저분해지고 인자 목록이 폭발한다. 실측했다.

### 확인_1 - `fetch_packet` 의 각 case 는 자족적이다

```c
        }
        break;
    }        // :619  switch 종료
}            // :620  함수 종료
```

**`switch` 직후 함수가 끝난다.** 후처리가 없으므로 case 가 갱신한 `index` · `tempValue` · `dataRangeError` 는 **되돌려줄 필요가 없다.**

| 넘겨야 할 것 | 내용 |
|---|---|
| `Rx_dataPacket` | 원본 패킷 포인터 |
| `index` | 시작 오프셋 (헤더 1바이트 뒤 = 1). **값 전달로 충분** |

나머지(`tempValue`·`subCommandData_Num_index`·`p_RepositoryFor_*`·`intFromByte`·`i`·`dataRangeError`)는 전부 **case 내부 스크래치**라 추출 함수의 지역 변수가 된다.

### 확인_2 - `step` 의 반환 상태는 `switch` 안에서 건드리지 않는다

```
:644   ST__REMOTECONTROL_STATE RemoteControlState = {en__isdStatus_NA, false};
:1389  return RemoteControlState;
```

**전 파일에서 이 두 줄이 전부다.** `switch` 의 어떤 case 도 `RemoteControlState` 를 대입하지 않는다. 따라서 추출 함수가 반환 상태를 만질 필요가 없다 — **결합 0**.

### 확인_3 - `tx_index` 는 지역 초기화로 등가다

`tx_index` 는 71회 등장하며 `:648` 에서 한 번만 `0` 이 된다. 각 case 는 `tdc_ble_reply_header()` 로 쌓고 `tdc_hal_spi_write_tx_buffer(buf, tx_index)` 로 비운다.

**단계_2(응답 조립 공통화)가 이 구조를 이미 규명했다**:

> `tx_index` 가 함수 진입 시 한 번만 0 이 되고 각 응답 후 리셋되지 않는 구조(**switch case 가 배타적이라 성립**)

배타성은 이번에도 성립한다 — 0x40 패스키 블록(`:697`)은 `if`, `switch` 는 `else` 안이라 **둘 중 하나만 실행된다.** 따라서 추출 함수가 각자 `int tx_index = 0;` 을 두는 것은 **동작 등가**다.

### 확인_4 - `remoteCommandStartFlag` 는 미추출 대상에서만 쓰인다

사용처 6곳(`:1114`·`:1120`·`:1126`·`:1132`·`:1138`·`:1146`)이 **전부 플래시 case** 이며, 발견_1 에 따라 추출하지 않는다. 추출 함수에 넘길 필요가 없다.

### 확인_5 - `bufferForSPI_tx` 는 각 함수가 자기 것을 가진다

`:646` 의 `uint8_t bufferForSPI_tx[BLE_DataPacketSize]` 는 case 안에서 조립 → 즉시 송신 → 재사용 없음이다. 추출 함수마다 20바이트 지역 배열을 두어도 동작이 같다.

**부작용**: 동시에 존재하는 배열이 늘지는 않는다(호출이 중첩되지 않으므로 스택 최대 깊이는 오히려 감소 가능). 크기 지표에서 확인한다.

## 4. 종합 - 추출 난이도가 낮다

| 공유 `static` | 2개만 파일 수준 승격 |

**단계_1b(매핑)보다 쉽다.** 그쪽은 `prev_subCommandData_Num_index` 가 3그룹 23곳에 얽혀 접근자와 어셈블리 대조가 필요했다. 리모콘은 파일 분할을 하지 않으므로 그 단계가 통째로 빠진다.
