# 분석 - 이월_2 리모콘 분해

**TL;DR**: `fetch_packet`(파싱 570줄)·`step`(실행 752줄)을 각각 명령별 함수로 분해한다. 계층 네이밍에 **층 구분자**(`_parse_` / `_step_`)를 넣어 같은 명령의 두 층을 구별한다. **파일 분할은 하지 않는다** — 같은 파일 안에서 추출하면 `static` 문제가 «파일 수준으로 올리기» 로 끝나고, 파일 분할은 접근자를 요구해 위험이 커진다(단계_1a/1b 가 위험을 나눈 것과 같은 취지).

## 1. 분해 지도 - `fetch_packet()` (파싱)

`:71` 헤더 추출 → `:74` 이전 명령 미완료 가드 → `:80` `switch (tempCommand)`.

| case | 줄 범위 | 줄수 | 명령 | 내부 구조 |
|---|---|---|---|---|
| `:82` | 82~101 | 20 | 0x4A read_SlotData | 단순 |
| `:102` | 102~340 | **239** | 0x4C write_SlotData | **3중 중첩** (`subCommandData_Num_index` → `i` → `index`) |
| `:341` | 341~372 | 32 | 0x4B read_Mapdata | 단순 |
| `:373` | 373~574 | **202** | 0x4D write_Mapdata | **2중 중첩** (데이터 인덱스 1~15) |
| `:575` | 575~583 | 9 | 0x4E erase_SlotData | 단순 |
| `:584` | 584~592 | 9 | 0x4F erase_mapData | 단순 |
| `:593` | 593~602 | 10 | 0x50 erase_except_slot1 | 단순 |
| `:603` | 603~609 | 7 | 0x57 recover_ALL | 단순 |
| `:610` `default` | 610~618 | 9 | 일반 명령 페이로드 복사 | 단순 |

**0x4C(239) + 0x4D(202) = 441줄이 537줄 중 82%** 다. 분해 효과가 이 둘에 몰려 있다.

## 2. 분해 지도 - `step()` (실행)

`:668` 연결 카운터 → `:682` 시작 플래그 → `:697` **0x40 패스키(게이트 밖)** → `:770` 패스키 게이트 → `:781` `switch`.

| case | 줄수 | 명령 | 비고 |
|---|---|---|---|
| `:697` | 71 | **0x40 패스키 확인** | **게이트 밖.** 이벤트 로그 기록 포함 |
| `:783` | 6 | 0x41 readInfoOfExtenalDevice | 본문 없음(nRF 처리) |
| `:789` | 34 | 0x42 readInfoOfMap | |
| `:823` | 27 | 0x43 readStatusOfExtenalDevice | |

| `:934` | 38 | 0x45 adjustStimulationVolume | |
| `:972` | 38 | 0x46 adjustMicVolume | |
| `:1010` | 21 | 0x47 OnOffTelecoil | |
| `:1031` | 21 | 0x48 OnOffStimulationIndicator | |
| `:1052` | 21 | 0x49 OnOffLED | |
| `:1073` | 6 | 0x52 readSoundSignal | |
| `:1079` | 21 | 0x54 read_Ezairo_FirmwareInfo | |
| `:1100`~`:1147` | 48 | 플래시 6건 | **각 4줄** - `tdc_isd_map_*` 위임만 |
| `:1187` | 14 | 0x8F GENERAL_DEBUG | 이미 별도 모듈 위임 |

| `:1367` | 4 | IDLE | 빈 case |

**0x59(151) + 0x44(84) + 0x40(71) = 306줄** 이 큰 덩어리다.

### 발견_1 - 플래시 6건은 추출 실익이 없다

`step()` 의 `:1100`~`:1147` 여섯 case 는 **각 4줄**이며 전부 `tdc_isd_map_*()` 한 줄 호출이다.

```c
case en__remoteControl_read_SlotData_ISD_N_USER:
{
    tdc_isd_map_read_info_setting(remoteCommandStartFlag, en__remoteControl_read_SlotData_ISD_N_USER,
                                  remoteDataPacket.remocon_ReadWriteMapData_Flash.slot_index);
}
break;
```

**함수로 빼면 «한 줄 호출을 감싼 한 줄 함수» 가 되어 오히려 읽기 나빠진다.** 단계_3 이 «3줄 x 8개 과분해» 를 기각한 것과 같은 판단이다. **그대로 둔다.**

## 3. 공유 상태 - 실질 위험은 2개

[`요구사항-검증.md` 근거_1](요구사항-검증.md) 의 실측을 그대로 쓴다.

| 변수 | `switch` 안? | 분해 위험 | 처리 |
|---|---|---|---|
| `prev_subCommandData_Num_index` (`:53`) | **안** — 0x4A·0x4C·0x4D | **높음** | 파일 수준으로 승격 |
| `stimulPara_index` (`:54`) | **안** — 0x4C·0x4D | **높음** | 파일 수준으로 승격 |
| `writingStartSlot_index` (`:49`) | 안 — 0x50·0x57 | 낮음 | 이미 파일 수준. 무변경 |
| `noCommandTime_counter` (`:641`) | **밖** | **없음** | `step()` 본체에 잔류 |
| `prev_remotegCommand` (`:642`) | **밖** | **없음** | 동 |
| `disconnectionCounter` (`:643`) | **밖** | **없음** | 동 |

> [!IMPORTANT]
> **`step()` 의 static 3개는 디스패치 이전 구간에서만 쓰인다.** case 를 함수로 빼도 본체에 남으므로 손댈 필요가 없다. 요구사항이 «static 5개» 를 같은 무게로 본 것은 과대평가였다.

### 발견_2 - 승격의 부작용은 «초기화 시점» 뿐이다

함수 지역 `static int x = 0;` 을 파일 수준 `static int x = 0;` 으로 올리면 **저장 수명·초기값·링크 가시성이 모두 같다**. 유일한 차이는 **이름 충돌 가능성**이며, 이 파일에 동명 심볼은 없다(실측).

동작 등가이므로 이 승격은 **`.elf` 바이트 동일까지 기대할 수 있다** — 커밋을 나누면 그 자체로 검증된다.

## 4. 네이밍 - 층 구분자가 필요하다

불가침 규약은 `tdc_ble_cmd_0xNN[_subMM_idxKK]_<이름>` 이다. 그런데 **리모콘은 같은 명령이 두 층에 모두 있다**(0x4A 가 파싱에도, 실행에도).

| 방안 | 판정 |
|---|---|
| 층 구분 없이 `tdc_ble_cmd_0x4A_read_slot()` | **불가** — 파싱·실행 두 함수가 같은 이름이 된다 |
| **`_parse_` / `_step_` 층 구분자 삽입 (채택)** | `grep "0x4A_"` 로 두 층이 함께 나오고, 어느 층인지 이름만으로 안다 |

```
tdc_ble_cmd_0x4A_parse_read_slot()      파싱 (fetch_packet 에서 호출)
tdc_ble_cmd_0x4A_step_read_slot()       실행 (step 에서 호출)
```

매핑 쪽(0x66)은 층이 하나뿐이라 구분자가 없었다. **리모콘의 구조적 차이가 이름에 드러나는 것이 맞다.**

### 4.1 확정 이름 - `fetch_packet` 계열

| 대상 | 함수명 |
|---|---|
| 0x4A | `tdc_ble_cmd_0x4A_parse_read_slot()` |
| 0x4C | `tdc_ble_cmd_0x4C_parse_write_slot()` |
| 0x4B | `tdc_ble_cmd_0x4B_parse_read_mapdata()` |
| 0x4D | `tdc_ble_cmd_0x4D_parse_write_mapdata()` |
| 0x4E | `tdc_ble_cmd_0x4E_parse_erase_slot()` |
| 0x4F | `tdc_ble_cmd_0x4F_parse_erase_mapdata()` |
| 0x50 | `tdc_ble_cmd_0x50_parse_erase_except_slot1()` |
| 0x57 | `tdc_ble_cmd_0x57_parse_recover_all()` |
| `default` | `tdc_ble_remote_parse_general_payload()` |

`default` 만 명령 번호가 없으므로 `0xNN` 세그먼트를 붙이지 않는다.

### 4.2 확정 이름 - `step` 계열

| 대상 | 함수명 |
|---|---|
| 0x40 | `tdc_ble_cmd_0x40_step_check_passkey()` |
| 0x42 | `tdc_ble_cmd_0x42_step_read_map_info()` |
| 0x43 | `tdc_ble_cmd_0x43_step_read_device_status()` |
| 0x44 | `tdc_ble_cmd_0x44_step_change_map_num()` |
| 0x45 | `tdc_ble_cmd_0x45_step_adjust_stim_volume()` |
| 0x46 | `tdc_ble_cmd_0x46_step_adjust_mic_volume()` |
| 0x47 | `tdc_ble_cmd_0x47_step_onoff_telecoil()` |
| 0x48 | `tdc_ble_cmd_0x48_step_onoff_stim_indicator()` |
| 0x49 | `tdc_ble_cmd_0x49_step_onoff_led()` |
| 0x54 | `tdc_ble_cmd_0x54_step_read_firmware_info()` |
| 0x59 | `tdc_ble_cmd_0x59_step_system_operation()` + 하위 분해 |

0x41·0x52·IDLE(본문 6줄 이하)과 플래시 6건은 **추출하지 않는다**(발견_1).

### 4.3 0x59 하위 분해

151줄 4중 중첩이라 한 함수로 빼도 여전히 크다. `data[0]`(옵션) 기준으로 나눈다.

| 하위 | 함수명 | 내용 |
|---|---|---|
| `data[0] == 1` | `tdc_ble_cmd_0x59_sub01_read_state()` | 현재 상태 응답 |
| `data[0] == 2` | `tdc_ble_cmd_0x59_sub02_write_setting()` | 쓰기 (내부에서 `data[1]`·`data[2]` 분기) |

## 5. 파일 분할을 하지 않는 이유

| 항목 | 판단 |
|---|---|
| `static` 처리 | 같은 파일이면 **파일 수준 승격으로 끝**. 분할하면 접근자 필요 |
| 위험 분리 | 단계_1a(이동)·1b(추출)가 위험을 나눈 것과 같은 취지. **한 커밋에 둘을 섞지 않는다** |
| 규모 | 매핑은 2,196줄이라 분할 실익이 컸다. 리모콘은 1,390줄이며 분해 후에도 한 파일로 감당 가능 |
| 이월 | 분할이 필요해지면 **별도 작업**으로 등록한다 |

## 6. 부작용 검토

| 항목 | 판정 |
|---|---|
| 정상 경로 동작 | 불변. 함수 추출은 호출 규약만 바꾼다 |
| `.elf` | **바이트 동일 불성립** (단계_1b 확정). 크기 증가 예상 — `-O0` 호출 오버헤드 |
| `__LINE__` 24곳 | **전부 이동한다.** 계약이 아님은 단계_4 가 확정 |
| 안전망 | 리모콘 57 케이스가 회귀를 잡는다 |
| 검증 지표 | 조건 분기 총수 보존 (`case` 65 · `if` 56 · `else` 40 · `for` 17 · `\|\|` 15 · `&&` 6) |
