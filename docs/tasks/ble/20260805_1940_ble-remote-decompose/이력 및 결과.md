## 판단 기록

### 판단_1 - 안전망을 먼저 깔았다

`static` 5개가 얽힌 1,300여 줄을 정적 지표만으로 분해하는 것은 위험했다. **상태 오류는 분기 총수에 나타나지 않는다.**

인프라 구축 중 **호스트 컴파일 장벽이 의존 21개가 아니라 SDK 헤더 한 줄**임을 규명했다.

```c
/* SDK ff.h:38 */
#if defined(_WIN32)   /* Windows VC++ (for development only) */
#include <windows.h>
```

MinGW 가 `_WIN32` 를 정의하니 이 가지가 열려 `STORAGE_DEVICE_DESCRIPTOR` 충돌과 `SPI_Type` 미정의가 난다. ARM 빌드에선 발생하지 않는다. `tdc_ble_remote.h` 가 거기 닿는 경로 셋을 `tests/unit/` shim 으로 끊었다 — **`src/` 무변경**.

**이 판단이 즉시 값을 했다.** 테스트를 쓰다가 예상과 다른 동작 2건을 발견했고, 그중 하나는 분해 때 거의 확실히 놓쳤을 것이다.

### 판단_2 - 위험을 재평가했다

요구사항은 `static` 5개를 같은 무게로 봤으나 실측하니 **실질 위험은 2개**였다. `step()` 의 셋은 전부 `switch` **밖**(디스패치 이전)이라 case 를 빼도 본체에 남는다.

또 **접근자는 파일 분할 시에만 필요하다** — 단계_1b 가 접근자를 만든 것은 파일을 나눴기 때문이지 함수를 뺐기 때문이 아니다. 파일 분할을 하지 않기로 하면서 그 단계가 통째로 빠졌다.

### 판단_3 - 570줄을 손으로 옮기지 않았다

스크립트로 기계 추출했다 — 중괄호 깊이로 본문 경계를 찾고, 본문에 나타나는 지역 변수만 골라 각 함수로 선언을 옮겼다.

**대가도 있었다**: 패턴에 안 맞는 예외(0x40 은 case 가 아니라 `if` 블록)가 조용히 빠졌다. 이월_F 의 «0x64 경계 케이스 4건 누락» 과 같은 유형이 **두 번 반복**됐다.

### 이 작업의 자산

| # | 내용 |
|---|---|
| 자산_1 | **호스트 컴파일 장벽은 대개 «의존이 많아서» 가 아니라 «헤더 한 줄» 이다.** 21개 include 를 보고 포기할 뻔했으나 실제 원인은 `_WIN32` 가지 하나였다. **오류 메시지의 include 사슬을 끝까지 따라가면 절단점이 나온다** |
| 자산_2 | **순수 승격·개명의 진짜 불변량은 «`.elf` md5» 가 아니라 «로드 섹션 바이트 동일» 이다.** md5 는 심볼 이름 변경에 민감해 과잉 검출한다. 깨졌을 때 `nm -n` 으로 주소를, `objcopy --only-section` 으로 내용을 대조하면 등가를 증명할 수 있다 |
| 자산_3 | **«static 이 몇 개인가» 가 아니라 «switch 안인가 밖인가» 가 위험을 가른다.** 5개 중 3개는 디스패치 이전 구간이라 분해와 무관했다 |
| 자산_4 | **접근자의 필요조건은 함수 추출이 아니라 파일 분할이다.** 이 구분을 못 하면 하지 않아도 될 작업을 한다 |
| 자산_5 | **기계 추출은 «패턴에 맞는 것» 만 처리한다.** 예외 항목(0x40)이 조용히 빠졌다. 계획 목록과 결과물을 **항목 단위로 대조**하는 절차가 필요하다 — 두 작업 연속 재발 |
| 자산_6 | **테스트를 먼저 쓰면 미문서화 동작이 드러난다.** «이전 명령 미완료» 가드가 주석과 달리 직전 명령까지 지우는 것을 분해 전에 발견했다 |
