## 2. 주 불변량이 실증한 것

개명 후 `text` · `data` · `bss` **세 값이 모두 동일**하다. ⑤ 계획이 예측한 대로다.

| 근거 (③ 분석 §3.1) | 결과로 확인됨 |
|---|---|
| `.rodata` 별도 섹션 없음 (`.text` 병합) | 파일명 27자 -> 18자 차이가 크기에 **미반영** |
| 파일명 문자열은 `.debug_*` | 동 |
| 심볼명 문자열은 `.strtab` | 함수명 25자 -> 29자 차이가 크기에 **미반영** |
| 대상 파일에 `TDC_PRINTF` 0건 | `__FILE__` 경로가 로드 섹션에 박히지 않음 |

**개명은 새 리팩토링 유형이며 그 불변량은 `text` 완전 동일**임이 실증됐다(인수인계 §5 노하우_2 표에 추가 대상).

### 검증 절차에서 정정한 것

| # | 문제 | 대응 |
|---|---|---|

## 3. 부수 발견_1 - 바이폴라 기준전극 99 결함이 0x65 경로에 무방비 (2026-07-30)

> [!CAUTION]
> **은수님 지적으로 조사했다.** *"`tdc_isd_map_specific_stim_step()` 에도 전에 바이폴라 관련해서 인덱스 99 이슈가 있었잖아. 그게 여기 함수에도 있을텐데"* - **사실로 확인됐다.** 이번 개명 범위 밖(요구사항 제외_4)이므로 코드는 손대지 않고 기록만 한다.

### 3.1 라이브 경로는 2중 방어, 0x65 경로는 0중

| 방어 | 라이브 0x66 (`tdc_isd_stim_para_setting.c`) | **특정자극 0x65 (`tdc_isd_map_specific_stim.c`)** |
|---|---|---|
| 전극번호 범위 검사 | **있음** `:486~496` - 99 를 걸러 `continue`, 더미값(31) 유지 | **없음** |
| 레지스터 `0x1F` 마스크 | **있음** `:577` · `:605` - `(0x1F & bipolarReferenceElectrodeNum[i])` | **없음** `:258` · `:284` - 마스크 없이 OR |

범위 검사는 2026-07-27 에 추가됐고 주석(`:475~485`)에 경위가 남아 있다. **같은 세션이 0x65 경로는 손대지 않았다.**

### 3.2 발현 조건

```c
// tdc_isd_map_specific_stim.c:206  - 모노폴라면 case 3 을 건너뛴다
if (stimulatonMode != en__bipolar) { flowCounter = flowCounter + 6; }

// tdc_isd_map_specific_stim.c:224-225  - case 3 (바이폴라 전용)
bipolarReferenceElectrodeNum[electrodeMap[stimulationElectrodeNum - 1]] =
    electrodeMap[bipolarReferenceElectrodeNum - 1];   // 99 면 electrodeMap[98]
```

| 조합 | `case 3` 실행 | 결과 |
|---|---|---|
| 모노폴라 + 기준전극 99 | **건너뜀** (`:206`) | **안전** |
| **바이폴라 + 기준전극 99** | **실행** | **`electrodeMap[98]` 범위 밖 읽기** |

**통로는 0x65 파싱이다.** `tdc_ble_cmd_0x65_specific.c:86` 이 99 를 **`stimulatonMode` 와 무관하게** 허용한다.

```c
if ((bipolarReferenceElectrodeNum < 1) || (32 < bipolarReferenceElectrodeNum))
{
    if (bipolarReferenceElectrodeNum != 99)  // 99인 경우 예외 (for 모노폴라)
    {
        dataRangeError = true;
    }
}
```

주석은 *"99인 경우 예외 (for 모노폴라)"* 라고 의도를 밝히지만 **모노폴라인지 검사하지 않는다.** 바이폴라+99 가 그대로 통과한다.

### 3.3 침범 대상 특정 - `s_tdc_table`

| 항목 | 실측 |
|---|---|
| `electrodeMap` | `0x200080d0`, **128바이트** (32 x 4), 유효 첨자 `[0..31]` |
| `electrodeMap[98]` | `0x20008258` - 배열 끝에서 **+264바이트 초과** |
| 그 주소를 품는 심볼 | **`s_tdc_table`** `0x200081d0`, **384바이트** |
| `s_tdc_table` 정체 | `ui/tdc_ui_command.c:120` - `static command_entry_t s_tdc_table[32]` |
| `command_entry_t` | `{ const char *name; command_fn_t fn; const char *help; }` = **포인터 3개** (12바이트 x 32 = 384 확인) |

**즉 전극번호 자리에 문자열 포인터 또는 함수 포인터 값이 들어온다.**

### 3.4 실기 로그값 교차 검증 - 인과 확정

`tdc_isd_stim_para_setting.c:479` 주석이 기록한 실기 관측값:

```
REF ELEC NUM : 99 (PCB : 70378)
```

| 검산 | 결과 |
|---|---|
| 70378 을 16진수로 | **0x112EA** |
| `.text` 범위 | `0x00010000 ~ 0x0003d244` |
| 0x112EA 가 그 안인가 | **그렇다** |

**쓰레기값이 `s_tdc_table` 의 포인터 값임이 수치로 확인된다.** `const char *name` 은 `.rodata`(`.text` 병합)를 가리키므로 정확히 이 범위다.

> [!IMPORTANT]
> `tdc_isd_stim_para_setting.c:471~473` 의 TODO 는 *"쓰레기값이 BIPOLAR REF READ BACKTEL COUNT IS 0 의 직접 원인인지 미확정"* 이라 했다. 이 검산은 **인과의 한 축(쓰레기값의 출처가 `s_tdc_table` 의 포인터)을 확정**한다. 남은 미확정은 그 값이 백텔 COUNT 0 으로 이어지는 뒷단이다.

### 3.5 마스크 부재가 피해를 증폭한다

`0x112EA` 급 값이 `:258` · `:284` 에서 **마스크 없이** OR 된다.

| 경로 | 최악의 오염 범위 |
|---|---|
| 라이브 (`0x1F &`) | 하위 5비트 = 전극번호 필드 안 (0~31) |
| **0x65 (마스크 없음)** | **전극번호 필드를 넘어 레지스터 주소·명령 필드까지** |

`w_isd_registerValue` 는 `주소 << 1 | R/W` 를 `<< 8` 한 뒤 데이터를 OR 하는 구조다. 상위 비트가 오염되면 **의도하지 않은 레지스터에 쓰기**가 될 수 있다.

### 3.6 안전한 지점 (오탐 배제)

| 위치 | 인덱스 | 판정 |
|---|---|---|
| `:224` 좌변 | `electrodeMap[stimulationElectrodeNum - 1]` | **안전** - 파싱이 1~32 로 검사(예외 없음), `electrodeMap` 값이 0~31 |
| `:455` 로그 | 동 | **안전** |
| `:534` | 동 | **안전** |

**`bipolarReferenceElectrodeNum` 만 99 예외를 갖는다.** 위험 지점은 `:225` 단 한 곳이다.

### 3.7 조치 판단

| 항목 | 판단 |
|---|---|
| 이번 작업에 포함? | **아니다** - 요구사항 제외_4, 원칙_4(결함 수정과 구조 리팩토링을 섞지 않는다). 섞으면 `text` 불변량이 깨져 개명 검증이 무효가 된다 |
| 별도 작업 필요? | **필요** - 이월_D 로 등록 |

## 4. 실기 게이트 (검증_13) - 은수님 확인 요청

> [!CAUTION]
> **Eclipse F5 Refresh -> Clean -> Build 가 필수다.** 파일 1개가 사라지고 1개가 새로 생긴다(`tdc_ble_map_stim.c/.h` -> `tdc_ble_cmd_0x65_specific.c/.h`). Refresh 없이 빌드하면 사라진 파일을 찾다 실패하거나 새 파일이 빌드에서 빠진다.

| # | 항목 | 기대 |
|---|---|---|
| 1 | Eclipse **F5 Refresh -> Clean -> Build** | 에러 0 · 경고 0, text **184,908** - **단계_3·4 와 같은 값**(개명은 크기를 바꾸지 않는다) |
| 2 | 매핑 프로그램으로 **0x65 특정 자극 실행** | 자극 정상 출력 (전극 · 자극 크기 · 유지 시간 반영) |
| 3 | **범위 외 값**으로 0x65 전송 (예: 자극 크기 2000uA) | 범위 외 에러 응답 (`en__OutOfDataRange`) |
| 4 | 라이브 자극(0x66) **회귀 확인** | 15단계 전송 + 자극 시작 정상 (같은 폴더·디스패치 공유) |

**2번과 3번이 짝**이다 - 정상 경로와 거부 경로를 모두 봐야 파싱이 살아 있음이 확증된다.

**text 184,908 이 그대로여야 한다는 점이 이번 작업의 특징**이다. 값이 다르면 개명 외의 변경이 섞인 것이므로 2번 이후를 진행하지 말고 알려 주십시오.
