### 정합_3 - `__LINE__` 이 정말 불변인가

| 파일 | 주석 편집 | `.c:109` 영향 |
|---|---|---|
| `.h` (12~14) | 3줄 -> 3줄 | **없음** - `.h` 와 `.c` 는 별개 컴파일 단위 파일이고, `__LINE__` 은 `.c` 의 물리 줄 번호다 |
| `.c` | **무편집** (`:5` include, `:24` 함수명만) | **없음** - `:5`·`:24` 는 치환이라 줄 수 불변 |

**결론: `__LINE__` 완전 불변.** 미결_2 가 "기록만"에서 **"불변 확인"(검증_12)으로 강화**됐다. 이는 계획이 요구사항보다 강한 보장을 제공하는 경우다.

> [!NOTE]
> `.h` 주석 줄 수 보존이 `.c` 의 `__LINE__` 에 **원래 무관**하다는 점을 계획 §2.2 가 다소 모호하게 서술했다("`.h` 와 `.c` 는 별개 파일이라 원래 무관하지만"). 정확히는 **줄 수 보존은 불필요한 안전장치**이나, 헤더 자체의 diff 를 최소화하는 이점이 있어 유지한다.

### 3.2 잘못된 전제 1건 발견 - include 정렬

**계획 §2.4 의 CAUTION 이 "`:25` 는 알파벳 순 위치일 수 있다"고 썼는데, 실측 결과 include 블록은 알파벳 순이 아니다.**

```
:18 tdc_isd_map_live.h        <- isd
:19 tdc_isd_init.h
:20 FPGA.h                    <- 외부
:21 tdc_sys_control.h         <- sys
:22 tdc_ble_remote.h          <- ble
:23 tdc_ble_map_measure.h
:24 tdc_ble_map_flash.h
:25 tdc_ble_map_stim.h        <- 개명 대상
:26 tdc_ble_cmd_0x66_live.h
:27 tdc_ble_reply.h
```

**모듈 그룹 순**(isd -> 외부 -> sys -> ble)이며 그룹 안에서도 알파벳이 아니다(`measure` -> `flash` -> `stim`).

| 항목 | 판정 |
|---|---|
| 전제 | **오류** - 알파벳 순 아님 |
| 결론 (`:25` 유지 = 0x66 바로 앞) | **유지** - 우연히 맞다 |
| 정정된 근거 | `:25` 를 그대로 두면 `tdc_ble_cmd_0x65_specific.h`(`:25`) -> `tdc_ble_cmd_0x66_live.h`(`:26`) 로 **계층 네이밍 두 파일이 명령 코드 순으로 인접**한다. 이동 불필요 |

### 3.3 clang-format 위험 - 실측으로 2건 제거

프로젝트 `.clang-format` 을 확인해 계획이 놓친 위험 2건을 검토했다.

| 잠재 위험 | 실측 | 판정 |
|---|---|---|
| clang-format 이 include 를 **재정렬**해 `:25` 위치가 바뀐다 | `SortIncludes: false` (`.clang-format:35`) | **위험 없음** - 재정렬 안 함 |
| clang-format 이 3줄 주석을 **재줄바꿈**해 줄 수가 깨진다 | `ColumnLimit: 320` (`.clang-format:6`) | **위험 없음** - 신규 주석 3줄 모두 320열 미만 |

`IncludeBlocks: Regroup`(`:34`)이 있으나 `SortIncludes: false` 와 함께면 블록 재그룹만 하고 순서는 보존한다.
