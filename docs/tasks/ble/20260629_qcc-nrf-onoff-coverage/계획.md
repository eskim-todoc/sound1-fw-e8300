# 계획 — 다페르소나 커버리지 분석

**TL;DR**: 6개 분석 페르소나 병렬 + 2개 adversarial 검증 노드로 NRF_On_OFF의 BLE 결정 로직을 QCC 제어가 커버하는지 교차검증. 사용자 "알아서 해" 위임 → 코드 변경 없으므로 승인 게이트 없이 진행.

## 수행 방식

순수 분석(코드 변경 없음) → 분석 자체가 산출물. Workflow 오케스트레이션(adversarial-verify 패턴).

## 페르소나 설계 (분석 6 + 검증 2)

| # | 페르소나 | 책임 |
|---|---|---|
| 분석_1 | 아키텍처 패러다임 비교가 | NRF(직접 GPIO 제어) vs QCC(핀 미러링+자율 판단) 구조 차이 규명 |
| 분석_2 | NRF_On_OFF 조건 해부가 | 4입력·5조건·출력 완전 분해, 死코드 함의 |
| 분석_3 | QCC 호출처 추적가 | `snd_qcc_*` 전 호출처 + 호출 조건·상태 컨텍스트 전수 |
| 분석_4 | 커버리지 갭 분석가 | NRF 조건 → QCC 경로 1:1 매핑, 커버/부분/미커버/위임 분류 |
| 분석_5 | 타이밍·상태전이 분석가 | 0.6초 지연 off·절전·OTA·부팅 시퀀스 타이밍 비교 |
| 분석_6 | 통합 평결가 | 5개 결과 종합 → 커버리지 최종 평결 초안 |
| 검증_1 | 할루시네이션 검증가 | 라인 인용 진위·호출처 누락 전수 대조 |
| 검증_2 | 반증가(adversarial) | "전부 커버한다/안한다" 결론 양방향 반박 시도 |

## 단계

1. **②분석**: 분석_1~5 병렬 기동(schema 구조화 반환) → 분석_6 통합.
2. **검증**: 검증_1·2가 통합 결과를 adversarial 검증.
3. **종합**: 검증 반영해 `분석.md` 작성(매핑표 + 평결).
4. **단계_4 검증**: broken link·라인 일관성 점검.
5. 작업 목록.md·모듈 현황.md 갱신.
