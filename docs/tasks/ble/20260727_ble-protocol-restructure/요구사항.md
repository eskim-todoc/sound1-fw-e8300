# ① 요구사항 - BLE 프로토콜 구조 분석 및 재구조화 설계

**TL;DR**: `src/2__cm3/source/ble` 는 파일 13개 중 `tdc_ble_mapping.c`(2,196줄)·`tdc_ble_remote.c`(1,389줄) 두 개에 무게가 쏠려 있고, 복잡도의 주원인으로 **동일 명령 안에서 데이터 인덱스에 따라 패킷 구조와 동작이 갈라지는 구조**가 지목됐다. 이번 작업은 **코드를 변경하지 않고**, 프로토콜 카탈로그·현행 코드 해부·라이브모드 상태머신 규명·재구조화 설계안까지를 문서로 산출한다. 앞으로의 모든 BLE 리팩토링의 기준 문서가 된다.

## 1. 배경

BLE 통신 계통은 인공와우 Sound1 에서 자극 펄스 생성 못지않게 중요한 컴포넌트다. 매핑 프로그램·리모콘 앱이 이 경로로 자극 파라미터를 쓰고 라이브 자극을 제어한다. 오동작은 곧 환자에게 잘못된 자극이 전달되는 것을 의미하므로, 구조 개선은 **동작 보존을 절대 전제**로 정밀하게 이뤄져야 한다.

2026-07-23~27 의 2차 리팩토링에서 CM3 전반의 사장 코드가 정리됐으나, `ble/` 는 **구조 자체는 손대지 않았다**. 오히려 그 작업에서 "BLE 프로토콜 정의는 미참조여도 전량 유지"([`참고/cm3-소스-트리-규약.md §2.1`](../../../참고/cm3-소스-트리-규약.md))가 확정되어, 프로토콜 영역은 신중히 다뤄야 할 대상으로 명문화됐다.

은수님이 2026-07-27 오전 매핑 프로그램 시나리오 7종의 RTT 로그를 [`docs/참고/ble/`](../../../참고/ble/) 에 확보해 두었다. 코드 정독만으로는 확신하기 어려운 **실제 패킷 시퀀스와 상태 전이**를 이 로그로 대조할 수 있다.

## 2. 문제 정의 (은수님 진술)

| # | 진술 | 성격 |
|---|---|---|
| 문제_1 | `ble/` 코드가 너무 복잡하다. 파일 수는 적은데 파일 하나당 내용이 길고 구조가 복잡하다 | 관측 |
| 문제_2 | 원인은 **프로토콜 패킷에서 데이터 인덱스에 따라 그 구조가 세부적으로 변하기 때문**인 것으로 보인다 | 가설 |
| 문제_3 | 가장 복잡한 것은 **라이브모드**다. 라이브모드 + 알람 재생 + 볼륨 변경이 가장 복잡한 구조일 것이다. 동일 패킷으로 데이터 인덱스에 따라 동작이 달라지고, 코드 내부에서는 라이브모드 진입 후 Idle · HoldOn 등 세부 상태머신에 따라 동작하기도 한다 | 관측 + 가설 |
| 문제_4 | 은수님 본인도 라이브모드 구조는 분석이 잘 되지 않아 어렵다 | 난이도 신호 |

> [!NOTE]
> 문제_2 · 문제_3 은 **가설로 취급한다.** 이번 분석이 이를 검증하거나 반증해야 한다. 가설을 결론으로 전제하고 설계를 세우면 잘못된 구조로 귀결된다.

## 3. 요구사항

### 3.1 필수 요구사항

| # | 요구사항 | 수용 기준 |
|---|---|---|
| 요구사항_1 | **프로토콜 헤더 전량 카탈로그화** | CM3 소스에 정의된 모든 명령 코드를 헤더 값·이름·소속 그룹·CM3 처리 여부(핸들러 존재/미존재)와 함께 표로 산출. 소스 근거는 `파일:라인` 명시 |
| 요구사항_2 | **헤더 그룹 체계 확정** | 은수님이 제시한 6개 그룹(§4)에 실제 코드를 대조하고, **누락·불일치 구간을 식별해 보고**. 최종 그룹 정의(이름·범위·주체·용도)를 확정안으로 제시 |
| 요구사항_3 | **BLE 경로 전체 해부** | 패킷이 CM3 에 도달하는 경로(QCC ↔ SPI 수신)부터 디스패치·핸들러·인접 모듈(isd/stim/fs 등) 호출까지의 제어 흐름을 규명. 계층 경계와 결합 지점을 명시 |
| 요구사항_4 | **복잡도 원인 규명** | 문제_2 가설(데이터 인덱스 분기)을 정량 근거로 검증 또는 반증. 복잡도 기여 요인을 순위화하고 각각의 규모(줄 수·분기 수·중첩 깊이)를 실측 |
| 요구사항_5 | **라이브모드 상태머신 규명** | 라이브모드의 상태 집합·전이 조건·트리거 패킷·부수효과(자극 활성/해제·파라미터 재계산 등)를 Mermaid 상태도로 완전 기술. 알람 재생·볼륨 변경이 라이브 상태와 어떻게 교차하는지 포함 |
| 요구사항_6 | **실측 로그 대조** | [`docs/참고/ble/`](../../../참고/ble/) 로그 7종을 패킷 단위로 디코드하고, 코드 분석 결과와 일치하는지 대조. 불일치는 전부 기록 |
| 요구사항_7 | **재구조화 설계안 산출** | 폴더·파일 분할안, 계층 구조, 공통화 대상, 적용 순서를 제시. 각 단계의 동작 보존 위험도와 검증 방법을 함께 명시 |
| 요구사항_8 | **참고 문서 정비** | 분석 결과를 [`docs/참고/ble/`](../../../참고/ble/) 하위 세부 폴더에 영속 레퍼런스로 정리. 후속 세션이 이 문서만 보고 작업할 수 있어야 한다 |

### 3.2 제약 조건

### 3.3 범위

**포함**
- `src/2__cm3/source/ble/` 13개 파일 전량
- BLE 패킷 수신·송신 경로상의 인접 모듈 (QCC/SPI 통신, 디스패처, 핸들러가 호출하는 isd·stim·fs 등)
- [`docs/참고/ble/`](../../../참고/ble/) RTT 로그 7종

**제외**
- QCC 펌웨어 자체 (소스 없음). QCC 전용 헤더는 카탈로그에 존재 사실만 기록
- 실제 코드 수정·빌드·실기 검증 (후속 작업)
- 프로토콜 규약 자체의 변경 제안 (앱·리모콘과 공유하므로 CM3 단독 결정 불가)

## 4. 은수님 제시 헤더 그룹 (검증 대상 입력)

| 그룹명 | 범위 | 주체 | 용도 |
|---|---|---|---|
| Ezairo_BT_30 | 0x30~0x3F | QCC <-> E8300 | MCU 간 내부 정보 교환 (외부 프로토콜보다 내부 성격) |
| 통신 프로토콜_40 | 0x40~0x5F, 0xF0 | 리모콘 앱 | 리모콘 앱 패킷이 주. **0xF0 은 별개로 각 프로토콜 인터페이스의 공통 에러 응답 헤더** |
| 매핑 프로토콜_60 | 0x60~0x7F **+ 0x91** | 매핑 프로그램 | **매핑 프로토콜 범위** (2026-07-27 은수님 추가 확인). `0x91`(`en__mapping_read_Connected_ISD_id`)은 대역 밖이지만 **예외적으로 실사용되는 매핑 헤더**라 그룹에 편입한다 (2026-07-27 은수님 확인) |
| SOUND1_80 | 0x80~0x8F | 주로 QCC <-> 폰/크래들 | Sullivan1.5 -> Sound1 전환(BLE -> BLE+Classic) 시 추가. **0x8C · 0x8F 만 E8300 까지 도달** |
| OP_C0 | 0xC0~0xCF | QCC | Operating Mode 제어. OTA 등 펌웨어 업데이트가 주 |
| Security | 0xE0~0xEF | QCC <-> 폰/크래들 | 암호·보안 인증 |
| 믹싱 게인_A0 | 0xA0~0xAF | E8300 | 각 오디오 입력에 대한 믹싱 게인 제어 |

> [!IMPORTANT]
> **코드에 없는 헤더는 미구현이거나 QCC 자체 사용분**이라는 것이 은수님 설명이다. 반대로 **코드에 있으나 위 표에 없는 대역**이 발견되면 그룹 체계의 공백이므로 요구사항_2 에 따라 보고한다.
>
> 착수 직후 [`tdc_ble_protocol.h`](../../../../src/2__cm3/source/ble/tdc_ble_protocol.h) 1차 확인에서 **매핑 명령이 0x60~0x71 및 0x90~0x91 대역**(`EN__MAPPING_COMMAND`)에 있음을 확인해 보고했고, 은수님이 **0x60~0x7F = 매핑 프로토콜**임을 확인해 주셨다(위 표에 반영).
>
> **0x90 대역 2건의 처리 (2026-07-27 확정)**
>
> | 헤더 | 열거값 | 실태 | 결정 |
> |---|---|---|---|
> | `0x91` | `en__mapping_read_Connected_ISD_id` | fetch·step **양쪽 모두 정상 처리** | **매핑 프로토콜_60 에 편입** (은수님 확인 - 예외적이지만 실사용) |
> | `0x90` | `en__mapping_testStimulation` | 디스패처는 매핑으로 라우팅하나 **핸들러 case 부재** -> 매번 에러 응답 | 그룹 미편입. 결함으로 기록 (분석 §7 결함_1) |
