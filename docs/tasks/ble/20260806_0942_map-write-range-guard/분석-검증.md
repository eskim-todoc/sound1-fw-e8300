# 분석 검증

**TL;DR**: 3축 통과. **누락 1건을 잡았다** — §4 루프 가드 전수에서 `numFrequencyBand` 만 봤는데, 같은 저장소를 쓰는 다른 개수 필드(`usableElectrodeNum` 등)도 상한이 될 수 있다. 확인 결과 이 작업 범위에서는 추가 대상이 없었으나, **찾는 방식이 필드 이름에 묶여 있던 것은 사실**이라 한계로 남긴다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 근거에 `파일:라인` | 통과 - §3·§4 표 |
| 과분해 금지 | 통과 - §2.3 에서 인자 없는 두 함수를 인덱스 받는 형태로 통일하지 않은 이유를 명시 |
| 계층 네이밍 | **해당 없음** - `tdc_ble_cmd_0xNN_*` 는 명령 처리 함수 규칙이다. 이 모듈은 명령이 아니라 필드 검사라 `tdc_ble_map_field_*` 가 맞다 |
| 테이블 주도 재도입 금지 | **통과** - `switch` 로 두었다. 필드-범위 표를 배열로 만들면 «사람이 눈으로 보고 관리하기 쉬운가» 기준에 걸린다 |
| 새 의존 최소화 | 통과 - §3 IMPORTANT |

## 축_2 - 논리 정합성

### 정합_1 - 「가」 배제 논리가 「나」 를 정당화하는가

한다. «복제가 원인» → «복제를 늘리지 않는다» 는 직접 연결된다. 다만 **「나」 가 유일한 대안은 아니다** — 리모콘만 고치고 매핑 앱은 그대로 두는 «절반의 나» 도 가능하다.

**배제 근거**: 그러면 검사가 여전히 두 곳에 있고, 다음에 경계값을 바꿀 때 또 갈라진다. 결함의 원인이 그대로 남는다.

### 정합_2 - §2.1 「무거워진다」 가 실제 문제인가

**약한 근거였다.** 다른 스위트가 파일 하나 더 링크한다고 실질적 문제는 없다. 진짜 이유는 다른 데 있다.

**보완**: `ble/mapping/tdc_ble_map_flash.c` 안에 두면 **리모콘 테스트가 매핑 파일을 링크**하게 된다. 그러면 `map_flash` 의 전역 상태·스텁 요구가 `remote` 스위트로 번져 **두 스위트의 격리가 깨진다**(`tdc_test.h` 주석이 밝힌 설계 의도 - «상태가 격리되어 한 테스트의 실패가 다른 테스트에 번지지 않는다»). 새 파일이 맞다.

### 정합_3 - §5 회귀 완화가 충분한가

**부분적이다.** `map_flash` 75 PASS 가 무엇을 덮는지 확인해야 한다. 스위트가 맵 쓰기 12필드 경계를 실제로 검사하지 않는다면 회귀를 못 잡는다.

**보완**: 그래서 이 작업이 **신규 스위트로 경계값을 직접 고정**한다. 기존 75건에만 기대지 않는다.

## 축_3 - 근거 검증

| 주장 | 확인 |
|---|---|
| `tdc_ble_reply.c` 가 `COMMON_SRC` 실물 | **코드 확인** - `run.sh:129~132`, 주석 «스텁이 아니라 실물이다» |
| `df_MaxNumOfElectrode` 를 두 호출부가 이미 include | **코드 확인** - `map_flash.c:12` · `remote.c:10` 둘 다 `<tdc_stim_definitions.h>` |

| `numFrequencyBand` 루프 3곳 | **grep 전수** |
| `:515` 가 이미 안전 | **코드 확인** - `for (i = numFrequencyBand; i < df_MaxNumOfElectrode; i++)` |

### 누락 - 전수의 기준이 필드 이름이었다

> [!WARNING]
> §4 는 `grep "numFrequencyBand"` 로 루프를 찾았다. **«개수를 담는 다른 필드가 상한으로 쓰이는 경우»는 이 방식으로 안 잡힌다.**

확인했다. 같은 구조체에서 개수 성격 필드는 `numFrequencyBand` 하나이고, `usableElectrodeNum` 은 이 구조체가 아니라 0x65 특정자극 패킷 소속이며 그쪽 루프(`map_specific_stim.c:564`)는 상한이 `TransferabelChannelNum`(내부 계산값)이라 앱값이 아니다.

**이번 범위에서 추가 대상은 없다.** 다만 **찾는 방식이 이름에 묶여 있던 것은 사실**이므로 한계로 남긴다. 자산_6(«검증 도구의 실패 모드는 매번 다른 방식»)의 연장선이다.
