# 계획

**TL;DR**: 신규 파일 2 · 수정 5. 순서는 **공통 모듈 → 테스트 → 리모콘(신규 방어) → 매핑 앱(전환) → 루프 가드**. 매핑 앱 전환을 뒤로 미루는 이유는 **그 시점에 이미 테스트가 있어야 회귀를 잡기 때문**이다.

## 2. 순서와 각 단계의 검증

| 단계 | 내용 | 검증 |
|---|---|---|
| **1** | 공통 모듈(1·2) 작성 | 컴파일 |
| **2** | 호스트 테스트(3·4) | **신규 스위트 통과** |
| **3** | 리모콘(5) - 순수 추가 | `remote` 스위트 57 PASS 유지 |
| **4** | 매핑 앱(6) - 전환 | **`map_flash` 75 PASS 유지 = 회귀 없음** |
| **5** | 루프 가드(7·8) | `map_stim` 174 PASS 유지 |
| **6** | 빌드 배선(9) | ARM 링크 성공 |

> [!IMPORTANT]
> **단계 2가 단계 4보다 앞서는 것이 핵심이다.** 자산_7(«테스트 선행이 미문서화 동작을 잡는다»)의 적용이다. 테스트 없이 매핑 앱을 건드리면 경계값이 하나 어긋나도 알 수 없다.

## 4. 불변량

리팩터링 유형별 불변량 표(누적)에 따라 이 작업의 유형을 정한다.

| 유형 | 이 작업에서 |
|---|---|
| **결함 fix · 방어 추가** | **정상 경로 불변 + 예측한 분기만 증가** |

| 항목 | 기대 |
|---|---|
| 기존 호스트 테스트 | **431 PASS 유지** (매핑 앱·리모콘 정상 경로 불변) |
| 신규 테스트 | 경계값 고정 |
| ARM 빌드 | 에러 0 · **경고 증가 0** |
| `data` · `bss` | **불변** (새 전역 없음) |
| `text` | **증가** - 검사 코드가 늘어난다. 감소하면 오히려 이상 |

> [!NOTE]
> **`.elf` 바이트 동일을 기대하지 않는다.** 동작을 바꾸는 변경이다. 자산_1·자산_2 는 «순수 개명·승격» 에 적용되는 것이고 여기엔 해당하지 않는다.
