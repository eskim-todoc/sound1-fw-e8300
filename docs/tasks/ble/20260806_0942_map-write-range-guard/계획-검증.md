# 계획 검증

**TL;DR**: 3축 통과. 보완 2건 — ① `subdir.mk` 를 «수정» 목록에 넣었으나 그것은 **Eclipse 자동 생성물**이라 성격이 다르므로 구분했고, ② 불변량에서 **`text` 증가폭의 상한을 안 정해** 두면 «증가하면 통과» 라는 무의미한 기준이 되므로 근거를 붙였다.

## 축_1 - 지침 준수

| 항목 | 판정 |
|---|---|
| 검증 방법이 단계마다 있는가 | 통과 - §2 표 |
| 불변량 명시 | 통과 - §4 |
| 실기 항목 준비 | 통과 - §6 |
| 코드 포맷 조건 | **계획에 없었다** → 구현 시 [`참고/clang-format/README.md`](../../../참고/clang-format/README.md) 수동 7개 적용. 특히 `case` 를 `{}` 블록에 두고 `break` 와 다음 `case` 사이 공백 줄 |
| CP949 금지 문자 | 구현 시 `.c`/`.h` 에서 회피 |

## 축_2 - 논리 정합성

### 정합_1 - 단계 순서가 실제로 회귀를 잡는가

잡는다. 단계 4(매핑 앱 전환) 시점에 단계 2의 신규 스위트와 기존 `map_flash` 75건이 **둘 다** 있다. 경계값이 하나라도 어긋나면 신규 스위트가 즉시 잡는다.

**다만 한계가 있다** — 신규 스위트는 **공통 함수**를 검사하지, `map_flash` 가 그 함수를 **올바른 인자로 부르는지**는 검사하지 않는다. 필드 인덱스를 잘못 넘기면 신규 스위트는 통과한다.

**완화**: 그 부분은 `map_flash` 75건이 덮는다. 두 스위트가 서로 다른 층을 본다.

### 정합_2 - §1 목록 9번(`subdir.mk`)의 성격

> [!WARNING]
> **다른 8개와 성격이 다르다.** `subdir.mk` 는 헤더에 «Automatically-generated file. Do not edit!» 라고 적힌 Eclipse 생성물이다. 소스 변경이 아니라 **내 빌드 검증을 위한 임시 조치**다.

**보완**: 은수님이 Eclipse 에서 프로젝트를 새로고침하면 Eclipse 가 다시 생성한다. 커밋에는 포함하되 **보고에서 «Eclipse 새로고침 필요» 를 명시**한다. 안 하면 은수님 빌드에서 링크 에러가 난다.

### 정합_3 - 불변량 「text 증가」 가 검증 기준이 되는가

**되지 않는다.** «증가하면 통과» 는 사실상 아무것도 검증하지 않는다.

**보완 - 증가폭에 근거를 붙인다**:

| 항목 | 예상 |
|---|---|
| 신규 함수 3개 | 비교 분기 위주라 수백 바이트 |
| 리모콘 검사 추가 12지점 | 호출 + 분기 |
| 매핑 앱 전환 | 인라인 비교 → 호출로 **감소** |
| 루프 가드 2곳 | 비교 1개씩 |

**수백 바이트 규모면 정합적이고, 수 KB 면 무언가 잘못된 것**이다(예: 헤더 include 로 다른 모듈이 딸려 들어옴).

### 정합_4 - 「실기 대기 6건」 을 감수할 가치가 있는가

있다. 이것은 **리팩터링이 아니라 결함 조치**다. 대장 §1 알림_2 가 경계하는 것은 «검증 없이 쌓이는 변경» 이고, 그 취지는 위험을 줄이는 데 있다. **위험을 남겨 두는 것이 오히려 취지에 반한다.**

또한 이 변경은 **호스트로 상당 부분 검증된다** — 다른 5건과 달리 신규 52케이스가 붙는다.
