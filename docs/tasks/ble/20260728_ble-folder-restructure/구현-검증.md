### 2.1 1차 대조 실패와 원인 규명

첫 대조는 **FAIL** 이었다. 크기는 완전히 같은데(184,076 / 4,668 / 21,804) md5 가 달랐다.

원인은 **링크 순서**였다. 폴더를 나누면서 `makefile` 의 `-include` 순서에 따라 오브젝트 나열이 바뀌었고, 섹션 배치 주소가 밀렸다. 순서를 이동 전과 같게(`ble` -> `sound1` -> `mapping` -> `remote`) 맞추자 md5 가 정확히 일치했다.

> [!NOTE]
> **이것 자체가 유용한 증거다.** 크기가 같은데 md5 가 다르면 코드가 아니라 배치가 바뀐 것이고, 배치 원인을 제거하니 바이트 동일이 성립했다. 파일 이동이 코드에 아무 영향을 주지 않았음을 두 방향으로 확인한 셈이다.
>
> 실제 산출물의 링크 순서는 Eclipse 가 정한다(역알파벳 추정: `sound1` > `remote` > `mapping` > `ble`). 배치가 베이스라인과 달라지지만 **코드 내용은 동일**하므로 동작에 영향이 없다.

## 8. 검증 노하우 (이번 세션의 자산)

### 노하우_1 - 경로가 바뀌면 바이너리가 바뀐다. `-ffile-prefix-map` 으로 중화한다

`__FILE__` 을 쓰는 코드가 하나라도 있으면 소스 경로가 `.rodata` 에 박힌다. 이 프로젝트는 `TDC_PRINTF_E` 가 `__SHORT_FILE__`(내부적으로 `__FILE__`)을 쓴다.

```
A 원래 경로            md5 897D60B2…  20,904B
B 하위 폴더            md5 1576A2BA…  20,912B  (+8)
C 원래 + prefix-map    md5 0454F23F…  20,888B
D 하위 + prefix-map    md5 0454F23F…  20,888B  <- A/B 와 달리 완전 일치
```

파일 이동 리팩토링에서 "바이트 동일"을 검증하려면 **양쪽 빌드에 폴더별 `-ffile-prefix-map=<경로>/=` 를 걸어** `__FILE__` 을 basename 으로 정규화한다.

### 노하우_2 - 바이트 동일 실패 시 크기를 먼저 본다

크기가 같은데 md5 만 다르면 **코드가 아니라 배치**다. 이번엔 링크 순서였고, 순서를 맞추자 일치했다. 크기까지 다르면 그때 코드를 의심한다.

### 노하우_3 - 함수 추출은 "조건 분기 총수 보존"으로 검증한다

함수를 추출하면 디스어셈블 구조는 반드시 달라지므로 단순 비교로는 판정할 수 없다. 대신 **조건 분기 총수**는 추출로 변하지 않는다(이동할 뿐). 4단계 모두 `+0` 이었다.

여기에 **호출 대상 집합 차이**(추가분이 전부 추출 함수·접근자로 설명되는가)와 **범위 검사 상수 보존**을 더하면, 크기 증감만 보는 것보다 훨씬 강한 증거가 된다.

### 노하우_4 - 접근자 호출 수를 소스의 읽기/쓰기 지점 수와 대조한다

공유 상태를 접근자로 바꿀 때 가장 위험한 것은 **한 지점을 빠뜨리는 것**이다. 컴파일러가 잡아주지 않는다(원래 변수가 같은 파일에 남아 있으면 조용히 옛 경로를 쓴다).

소스에서 읽기/쓰기를 세어 표로 만들고 어셈블리의 `bl get_seq_index`/`bl set_seq_index` 개수와 대조하면 누락이 즉시 드러난다. flash 12 / stim 5 로 정확히 일치했다.
