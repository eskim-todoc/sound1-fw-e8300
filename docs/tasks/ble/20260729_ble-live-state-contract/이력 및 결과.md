# 이력 및 결과 - BLE 라이브 상태 계약 명시 (단계_4)

**상태**: 구현·정적 검증 완료, 실기 게이트 대기 (단계_3 과 함께).

**TL;DR**: [`재구조화 설계안.md`](../../../참고/ble/재구조화/재구조화%20설계안.md) 단계_4 실행. 라이브 상태 4층의 층간 규칙이 각 `case` 안 조건문에만 암묵적으로 존재하는 것을 **코드에 계약으로 승격**한다. **설계안이 제안한 "허용 선행 상태 테이블"은 채택하지 않는다** - 2026-07-29 단계_3 에서 테이블 주도 방식이 가독성 문제로 기각됐기 때문이다. 대신 **계층 네이밍 철학을 그대로 이어간다.**

> [!IMPORTANT]
> **실기 게이트가 단계_3 과 함께 밀려 있다.** 분석·계획은 실기 대기 중 코드를 건드리지 않는 범위로 선행했고(2026-07-29), 구현은 은수님 지시로 2026-07-30 에 진행했다. 계획 §8 이 걸었던 "단계_3 실기 통과 선행" 조건은 지시로 완화된 것이며, **두 단계가 함께 실기를 기다린다.**
>
> 안전망은 호스트 테스트 **301 PASS** 다. 게이트 4곳이 가드 하나로 수렴했으므로 그 가드가 틀리면 4개 명령이 동시에 깨지는데, 커밋_1 의 26 케이스가 그 위험을 덮는다.

## 핵심 판단

### 설계안의 제안을 그대로 따르지 않는다

[`재구조화 설계안.md §3 단계_4`](../../../참고/ble/재구조화/재구조화%20설계안.md) 는 다음을 제안한다.

| 설계안 제안 | 이 작업의 판단 |
|---|---|
| "볼륨은 HoldOn 일 때만" 을 **서브커맨드별 허용 선행 상태 테이블**로 선언 | **미채택.** 단계_3 에서 같은 성격의 테이블이 기각됐다 |
| 층별 상태 조회·전이 인터페이스 명시 | **채택** - 접근자 방식 |
| 재진입 가드를 명령별 수락 조건의 일부로 편입 | **조건부** - 동작 변경 위험이 커서 분리 |

**기각 사유의 재확인** (2026-07-29 단계_3): 테이블은 지표가 좋아도 *"배열에 숫자를 집어넣어 한참 분석해야 하는"* 코드가 된다. 은수님 판단 기준은 **사람이 눈으로 보고 관리하기 쉬운가**이며, 그 기준을 단계_4 에도 그대로 적용한다.

### 대안 - 전제를 함수 이름으로 선언한다

현재 4개 하위 명령이 똑같은 게이트를 각자 품고 있다.

```c
if (p_mappingPacket->tdc_isd_map_live_step.subCommand == en__HoldOn)
{
    ... 본문 전체가 여기 들여쓰기 안에 ...
}
else
{
    tdc_sys_error_send_to_app(..., en__Command_Order, __LINE__);
    p_mappingPacket->tdc_isd_map_live_step.subCommand = en__Standby;
}
```

이를 이름 있는 가드로 바꾼다.

```c
if (!tdc_ble_cmd_0x66_require_hold_on(p_mappingPacket, __LINE__))
{
    return;
}
```

**테이블을 만들지 않고도 "이 명령은 라이브 자극 중에만 받는다"가 코드에 선언된다.** 들여쓰기도 한 단계 걷힌다. 상세는 [`분석.md`](분석.md).
