# 분석 - BLE 라이브 상태 계약 명시 (단계_4)

**TL;DR**: `en__HoldOn` 게이트 4곳이 **완벽하게 균일**함을 실측 확인했다(차이는 포맷상 줄바꿈뿐). 이름 있는 가드 하나로 수렴 가능하다. 다만 **에러의 `lineNumber` 는 어떻게 하든 값이 바뀐다** - 보존할 수 있는 것은 "명령마다 서로 다른 값"이라는 성질뿐이며, 프로젝트는 이미 이 값을 단언 대상에서 제외하고 있다.

## 1. 게이트 4곳 구조 대조

네 함수가 동일한 골격을 각자 품고 있다.

| 하위 명령 | 함수 | 게이트 | 에러 전송 | Standby 복귀 |
|---|---|---|---|---|
| 3 자극 볼륨 | `..._sub03_volume_adjust` | `:554` | `:573` | `:576` |
| 4 마이크 감도 | `..._sub04_mic_sensitivity` | `:587` | `:605` | `:606` |
| 5 알림 자극 | `..._sub05_indicator` | `:624` | `:695` | `:697` |
| 6 이퀄라이저 읽기 | `..._sub06_read_equalizer` | `:709` | `:750` | `:753` |

```c
if (p_mappingPacket->tdc_isd_map_live_step.subCommand == en__HoldOn)
{
    /* 본문 - sub03 은 14줄, sub05 는 60줄, sub06 은 20줄 */
}
else
{
    tdc_sys_error_send_to_app(en__mapping_live_stimulation, en__EN__BLE_PROTOCOL_ERROR, en__Command_Order, __LINE__);
    p_mappingPacket->tdc_isd_map_live_step.subCommand = en__Standby;
}
```

**네 곳의 유일한 차이는 `tdc_sys_error_send_to_app()` 호출이 한 줄이냐 두 줄이냐**다(`sub04` 만 한 줄, 나머지는 `__LINE__` 이 다음 줄). 인자 · 순서 · 부수효과는 전부 같다.

> [!NOTE]
> **이 균일성이 단계_3 의 성과다.** 단계_1b 이전에는 이 네 블록이 `fetch_packet` 1,724줄 안의 `case` 였고, 단계_3 에서 각자 함수가 됐다. 이제 "네 함수가 같은 전제를 공유한다"가 한눈에 보이고, 그래서 수렴시킬 수 있다.

## 2. 설계 대안 비교

### 대안_1 - 이름 있는 가드 함수 (채택)

```c
// 라이브 자극 유지 중(en__HoldOn)에만 수락되는 명령인지 확인한다.
//
// 거부할 때는 앱에 명령 순서 에러를 보내고 서브커맨드를 Standby 로
// 되돌린다. lineNumber 는 호출 지점의 __LINE__ 을 그대로 받아 어느
// 명령이 거부됐는지 로그에서 구분할 수 있게 한다.
static bool tdc_ble_cmd_0x66_require_hold_on(ST__MAPPING_PACKET *p_mappingPacket, int lineNumber)
{
    if (p_mappingPacket->tdc_isd_map_live_step.subCommand == en__HoldOn)
    {
        return true;
    }

    tdc_sys_error_send_to_app(en__mapping_live_stimulation, en__EN__BLE_PROTOCOL_ERROR, en__Command_Order, lineNumber);
    p_mappingPacket->tdc_isd_map_live_step.subCommand = en__Standby;

    return false;
}
```

호출부.

```c
static void tdc_ble_cmd_0x66_sub03_volume_adjust(const uint8_t *Rx_dataPacket, int index)
{
    ST__MAPPING_PACKET *p_mappingPacket = tdc_ble_mapping_get_packet();
    int                 value;

    if (!tdc_ble_cmd_0x66_require_hold_on(p_mappingPacket, __LINE__))
    {
        return;
    }

    value = Rx_dataPacket[index++];
    ...
}
```

**장점**

- "이 명령은 라이브 자극 중에만 받는다"가 **함수 이름으로 선언**된다. 테이블도 주석도 필요 없다
- 본문이 `if` 밖으로 나와 **들여쓰기가 한 단계 걷힌다.** `sub05` 는 60줄 본문이 통째로 평탄해진다
- 새 하위 명령을 추가할 때 **한 줄만 쓰면 같은 계약에 편입**된다
- 게이트 판정이 한 곳이라 **테스트 한 번으로 4개 명령이 보증**된다

**단점**

- 게이트가 한 곳이라 **틀리면 4곳이 동시에 깨진다**(요구사항-검증 §3.2). 테스트 선행이 필수
- `lineNumber` 값이 바뀐다(§3)

### 대안_2 - 허용 선행 상태 테이블 (설계안 원안, 미채택)

```c
static const struct { int subCommand; int requiredState; } s_live_accept[] = { ... };
```

**미채택 사유**: 2026-07-29 단계_3 에서 같은 성격의 디스크립터 테이블이 **가독성 문제로 기각**됐다. 지표(`text` -1,276B, 함수 409->101줄)가 전부 우수했음에도 *"배열에 숫자를 집어넣어 한참 분석해야 한다"* 는 판단이었다. 게다가 이번 대상은 **게이트가 4개뿐**이라 테이블의 규모 이점도 없다.

### 대안_3 - 매크로 가드 (미채택)

```c
#define TDC_BLE_CMD_0X66_REQUIRE_HOLD_ON(p) do { if (...) { ...; return; } } while (0)
```

`__LINE__` 이 자동으로 호출 지점 값이 되는 장점이 있으나, **매크로 안에 `return` 이 숨는다.** 호출부만 봐서는 함수가 거기서 끝날 수 있다는 것이 드러나지 않는다. 대안_1 이 `if (!...) { return; }` 로 반환을 눈에 보이게 하는 것과 대조된다.

## 3. `lineNumber` 영향 분석

> [!CAUTION]
> **어떤 설계를 택하든 `lineNumber` 값은 바뀐다.** 현재는 `else` 절 안 에러 호출 줄이고, 가드로 빼면 각 함수의 가드 호출 줄이 된다. 값 자체의 보존은 불가능하다.

### 3.1 현재 값

| 함수 | 현재 `__LINE__` 평가 위치 |
|---|---|
| `sub03` | `:574` (호출이 두 줄이라 `__LINE__` 은 둘째 줄) |
| `sub04` | `:605` (한 줄) |
| `sub05` | `:696` |
| `sub06` | `:751` |

### 3.2 이 값이 계약인가

**아니다.** 근거 셋.

| # | 근거 |
|---|---|
| 1 | `tests/unit/stub_ble.h` 가 명시한다 - *"라인 번호는 소스가 한 줄만 밀려도 바뀌므로 단언 대상이 아니다. 디버깅용으로만 노출한다"* |
| 2 | 2026-07-28 단계_1a·1b 폴더 개편에서 이미 이 값들이 전부 바뀌었다. 실기 확인을 통과했다 |
| 3 | [`명령 카탈로그.md`](../../../참고/ble/프로토콜/명령%20카탈로그.md) 도 2026-07-29 에 라인 참조를 전량 폐기했다 - 프로젝트가 라인 번호를 불안정한 값으로 취급하는 방향으로 일관되게 가고 있다 |

### 3.3 보존해야 할 성질

값이 아니라 **"명령마다 서로 다른 값이 나온다"** 는 성질이다. 이게 있어야 로그에서 어느 명령이 거부됐는지 구분된다.

`__LINE__` 을 인자로 넘기면 각 함수의 가드 호출 줄이 되므로 **네 값이 여전히 서로 다르다.** 성질은 보존된다.

> [!NOTE]
> 대안_1 이 `lineNumber` 를 인자로 받는 유일한 이유가 이것이다. 가드 안에서 `__LINE__` 을 쓰면 **네 명령이 전부 같은 값**이 되어 구분이 사라진다.

## 4. 미결 항목 해소

### 미결_1 - 가드 시그니처 -> **패킷 포인터 + `lineNumber` 를 받는다**

호출자가 이미 `tdc_ble_mapping_get_packet()` 으로 포인터를 갖고 있다. 가드가 다시 부르면 중복 호출이고, 인자로 받으면 **가드가 무엇을 건드리는지 시그니처에 드러난다.**

### 미결_2 - 접근자 이름과 배치 -> **이번 범위에서는 도입하지 않는다**

요구사항_2 는 `subCommand` 직접 접근을 접근자로 감싸자고 했다. 분석 결과 **이번에는 하지 않는다.**

| 근거 |
|---|
| `ble/` 24곳 중 **게이트 4곳은 가드로 흡수**되고, 나머지는 전이 설정(쓰기)이다 |
| 쓰기 쪽은 `isd/` 19곳과 짝을 이루므로, `ble/` 만 접근자로 감싸면 **한쪽만 캡슐화된 비대칭**이 된다 |
| 진짜 소유권 정리는 `ble/`-`isd/` 역결합 해소(단계_5)와 함께 해야 의미가 있다 |

**이번 작업은 "읽기(게이트)"만 정리하고, "쓰기(전이)"는 손대지 않는다.** 범위를 좁혀 되돌릴 수 있게 유지한다(설계 원칙_6).

### 미결_3 - 조건 없는 명령에 "조건 없음"을 명시할지 -> **주석 한 줄로 명시한다**

침묵하면 "조건이 없는 것"과 "가드를 빠뜨린 것"이 구분되지 않는다. 함수 위 주석에 한 줄로 적는다.

```c
// 하위 명령 2 - 라이브 모드 시작 (en__Start)
// 선행 상태 조건 없음 - 어느 상태에서도 수락한다.
```

테이블을 만들지 않고도 9개 하위 명령의 수락 조건이 **각 함수 머리에 전부 적히게 된다.**

### 미결_4 - 테스트 확장 -> **게이트 4곳 전수 + 수락/거부 양방향**

현재 하위 3·4 만 덮고 5·6 은 커버리지가 0 이다(요구사항-검증 §3.2).

| 축 | 내용 | 예상 케이스 |
|---|---|---|
| 축_1 | 하위 3·4·5·6 각각 - `en__HoldOn` 아닐 때 **거부** + `en__Command_Order` + `Standby` 복귀 | 12 |
| 축_2 | 하위 3·4·5·6 각각 - `en__HoldOn` 일 때 **수락** | 4 |
| 축_3 | 조건 없는 하위 2·7·8 이 **어느 상태에서도 수락**되는지 | 6 |
| 축_4 | 거부된 명령이 **상태를 바꾸지 않는지**(볼륨 값 등이 그대로인지) | 4 |

**축_3 이 중요하다.** 가드를 잘못 붙이면(예: `sub07` 에도 실수로 붙이면) 조건 없던 명령이 갑자기 거부된다. 현재 테스트에는 이를 잡을 케이스가 없다.

## 5. `isd/` 쪽 쓰기 지점 (참고 - 단계_5 준비)

이번 범위 밖이지만, 소유권 문제의 실체를 기록해 둔다.

| 파일 | 건수 | 성격 |
|---|---|---|
| `isd/tdc_isd_map_live.c` | 19 | 실행 완료 후 `en__HoldOn` 으로 되돌리는 전이가 대부분 |

`ble/` 가 "HoldOn 인가"를 묻고 `isd/` 가 "HoldOn 으로 만든다". **묻는 쪽과 만드는 쪽이 다른 폴더**이고, 그 계약이 코드에 없다. 단계_5 에서 다룰 핵심이다.

## 6. 위험 분석

| # | 위험 | 영향 | 대응 |
|---|---|---|---|
| 위험_1 | 가드 한 곳이 틀리면 4개 명령이 동시에 깨짐 | 높음 | 미결_4 축_1·2 테스트를 **전환 전 코드로 먼저 통과** |
| 위험_2 | 조건 없는 명령(2·7·8)에 가드를 잘못 붙임 | 높음 - 정상 명령이 거부됨 | 축_3 테스트 |

| 위험_5 | `sub05`·`sub06` 은 본문 안에도 `Standby` 복귀가 있음(`:635`·`:684` / `:729`·`:737`) - 가드의 것과 혼동 | 중 | 가드는 **게이트 실패 시**만 담당. 본문 안 복귀는 범위 검사 실패용이라 그대로 둔다 |

## 7. 예상 결과

| 항목 | 현재 | 예상 |
|---|---|---|
| 게이트 코드 | 4곳 x 약 8줄 = 32줄 | 가드 1개 14줄 + 호출 4 x 4줄 = 30줄 |
| `sub05` 본문 들여쓰기 | 3단 | 2단 |
| 조건 분기 | `if/else` 4쌍 | 가드 내 `if` 1 + 호출부 `if` 4 |
| `.text` | - | 소폭 증가 예상 (함수 호출 1회 추가) |

> [!IMPORTANT]
> **줄수는 거의 줄지 않는다.** 이 작업의 목적은 축약이 아니라 **전제의 명시**다. "볼륨은 HoldOn 일 때만"이 각 함수 안 조건문에서 함수 이름으로 올라오는 것, 9개 하위 명령의 수락 조건이 각 함수 머리에 전부 적히는 것이 성과다.
