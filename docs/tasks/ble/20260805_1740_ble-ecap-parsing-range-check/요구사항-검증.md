# 요구사항 검증 - 0x63·0x64 eCAP 파싱 범위 검사

**TL;DR**: 3축 검증에서 **결함 2건**을 잡았다. ① 수용_2 «기존 테스트 무수정 통과» 는 **달성 불가** — 기존 테스트 패킷의 `adcSamplingFreq = 12` 가 레지스터 3비트 폭을 이미 넘는다. ② `bipolarReferenceElectrodeNum` 에 **99 예외를 넣지 않으면 과잉 차단**이 된다(0x65 선례). 둘 다 요구사항에 반영했다.

## 2. 논리 정합

### 결함_1 (해소) - 수용_2 가 달성 불가능했다

**원문**: *"기존 테스트(0x63·0x64 전 필드 적재) 무수정 통과"*

**반례**: `test_map_measure.c:175` 가 `pkt[14] = 12; // adcSamplingFreq` 를 쓴다. 그런데 `isd/tdc_isd_map_ecap.c:730~731` 과 `:764~765` 는 이 필드에 **3비트만 내준다**.

```c
w_isd_registerValue = w_isd_registerValue << 3;
w_isd_registerValue = w_isd_registerValue | mappingPacket->eCapMeasurement.adcSamplingFreq;
w_isd_registerValue = w_isd_registerValue << 2;
```

`12 = 0b1100` 은 3비트를 넘어 **상위의 `adc_measurementMode_eCAP` 필드를 오염**시킨다. 즉 **기존 테스트 패킷 자체가 이미 유효하지 않은 값**이다.

**원인**: 그 테스트는 범위 검사가 없던 시절에 작성돼 값이 11·12·13·14 처럼 **필드 구분용 순번**으로 정해졌다. 스펙 유효성을 고려한 값이 아니다.

**조치**: 수용_2 를 *"유효 범위 안 값의 파싱 결과가 전후 동일"* 로 바꾸고, 기존 테스트 값의 유효성 감사를 명시적 작업으로 추가했다. 이는 **동작 변경이 아니라 테스트 데이터 정정**이며, 정정 사실을 `구현-검증.md` 에 남긴다.

> [!NOTE]
> 이 결함은 조치의 정당성을 오히려 **강화**한다. 사람이 임의로 고른 값이 실제 레지스터 폭을 넘었다는 것은, 범위 검사가 없으면 그런 값이 그대로 하드웨어까지 간다는 실증이다.

### 결함_2 (해소) - `bipolarReferenceElectrodeNum` 에 99 예외가 필요하다

0x65 는 이 필드에 **99 를 명시적으로 허용**한다(`tdc_ble_cmd_0x65_specific.c:86`, 주석 *"99인 경우 예외 (for 모노폴라)"*). 같은 이름·같은 의미의 필드를 0x63·0x64 에서 **99 를 거부**하도록 만들면, 앱이 0x65 와 같은 관례로 보내는 순간 **정상 입력을 막는다** — 노하우_5 가 경고한 과잉 차단이다.

한편 0x63 에서 이 필드는 **배열 인덱스가 아니다**. `isd/tdc_isd_map_ecap.c:461`·`:494` 가 루프 변수와 **비교만** 하고, 일치하지 않으면 `:469`·`:501` 의 `electrodeMap[31]` 로 폴백한다. 따라서 99 를 허용해도 메모리 안전성은 훼손되지 않는다.

**조치**: 0x65 의 검사 형태를 **그대로** 이식하기로 요구사항에 명시(제약_7 신설).

### 정정_1 - 필드 수

대장 §2.2 와 인수인계 §4.2 가 0x63 을 *"15개 필드"* 로 적었으나 구조체는 **14개 멤버**다. 파싱 함수도 14회 대입한다(16비트 필드 2개가 2바이트씩 차지해 페이로드는 16바이트). 0x64 는 **7개**다. 문서 갱신 시 함께 정정한다.
