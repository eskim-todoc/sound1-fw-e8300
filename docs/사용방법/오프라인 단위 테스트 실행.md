# 오프라인 단위 테스트 실행 방법

**TL;DR**: `bash tests/unit/run.sh` 한 줄이면 된다. 보드 없이 PC 에서 BLE 파싱 로직을 실제 소스 그대로 컴파일·실행해 검증한다. 처음이라면 MinGW-w64 설치가 필요하다.

## 1. 실행

```sh
bash tests/unit/run.sh
```

정상이면 이렇게 끝난다.

```
======== test_map_measure ========
---- 52 PASS / 0 FAIL ----
======== test_map_flash ========
---- 75 PASS / 0 FAIL ----
======== test_map_stim ========
---- 59 PASS / 0 FAIL ----

########  전체 통과  ########
```

종료 코드는 전부 통과면 `0`, 하나라도 실패하면 `1`, 환경이 갖춰지지 않았으면 `2` 다.

## 2. 처음 한 번 - 컴파일러 설치

호스트 C 컴파일러가 필요하다. 없으면 러너가 안내와 함께 멈춘다.

```sh
winget install --id BrechtSanders.WinLibs.POSIX.UCRT --exact
```

설치 후 **새 터미널**을 열어야 `PATH` 가 반영된다.

다른 컴파일러를 쓰려면 `CC` 로 지정한다.

```sh
CC=/path/to/gcc bash tests/unit/run.sh
```

SDK 헤더 위치가 기본 경로와 다르면 `EZAIRO_SDK` 를 지정한다.

```sh
EZAIRO_SDK="D:/Ezairo 8300 SDK" bash tests/unit/run.sh
```

## 3. 무엇을 검증하나

| 대상 | 명령 |
|---|---|
| `test_map_measure` | 0x62 임피던스 · 0x63 eCAP 마스킹 · 0x64 eCAP 교대 |
| `test_map_flash` | 0x68~0x71 슬롯·맵 데이터 읽기/쓰기/삭제/복구 |
| `test_map_stim` | 0x65 특정 자극 · 0x66 라이브 자극(하위 1~8) |

검증하는 것은 **패킷 파싱**이다.

- 필드가 올바른 오프셋에서 올바른 값으로 적재되는가
- 범위 검사가 경계에서 정확히 동작하는가
- 멀티 패킷 명령의 데이터 인덱스 연속성이 지켜지는가
- 응답 바이트열이 기대와 일치하는가

> [!IMPORTANT]
> **이 테스트가 통과해도 실기 동작을 보장하지는 않는다.** 파싱 로직만 검증하며 자극 타이밍·하드웨어 연동은 여전히 실기 확인 소관이다. 반대로 **여기서 실패하면 실기에서도 반드시 문제가 된다.**

## 4. 구조

```
tests/unit/
├── run.sh              러너 (컴파일러·SDK 탐색 + 빌드 + 실행)
├── tdc_test.h          CHECK / CHECK_EQ / CHECK_BYTES 매크로
├── stub_ble.c/.h       하드웨어·공유메모리 의존을 대신하는 스텁
├── test_map_*.c        명령군별 테스트
└── build/              산출물 (git 추적 안 함)
```

**실제 펌웨어 소스를 그대로 컴파일한다.** 사본이 아니므로 `src/` 가 바뀌면 다음 실행에 즉시 반영된다.

`tdc_ble_reply.c`(응답 조립 빌더)는 스텁이 아니라 실물을 함께 컴파일한다. 응답 바이트열까지 검증 대상이기 때문이다.

## 5. 테스트 추가하기

`test_map_measure.c` 를 본뜨면 된다.

```c
stub_reset();                 // 각 케이스 앞에서 상태 초기화
make_packet(pkt, 0x62);       // 패킷 준비 (인덱스 0 = 명령 헤더)
pkt[1] = 10;                  // 페이로드는 인덱스 1 부터

tdc_ble_map_measure_impedance_check(pkt);

CHECK_EQ("iterationNum", tdc_ble_mapping_get_packet()->impedanceCheck.iterationNum, 10);
CHECK_EQ("에러 없음", stub_error_count(), 0);
```

스텁이 제공하는 조회 API 는 `stub_ble.h` 에 있다 - 에러 횟수·major·minor, 송신 바이트열·길이, 공유 메모리 저장소 내용 등.

> [!CAUTION]
> **`__LINE__` 은 단언하지 않는다.** `tdc_sys_error_send_to_app()` 의 4번째 인자는 소스가 한 줄만 밀려도 바뀐다. 에러의 의미는 `major`/`minor` 가 정하므로 그 둘을 단언한다.

## 6. `src/` 경고 보고

러너는 프로덕션 코드의 컴파일 경고 건수를 함께 보고한다.

```
참고: src/ 컴파일 경고 11 건 (프로덕션 코드 - 이 러너는 고치지 않는다)
      상세는 tests/unit/build/build_*.log
```

ARM 빌드에는 `-Wall` 이 없어 드러나지 않는 것들이 여기서 보인다. 실제로 이 인프라를 도입하면서 미사용 변수 11건을 발견해 [`알려진 결함 목록.md`](../참고/ble/재구조화/알려진%20결함%20목록.md) 결함_14 로 기록했다.

테스트 코드 자체의 경고는 **0 이어야 하며**, 발생하면 실패로 처리된다.
