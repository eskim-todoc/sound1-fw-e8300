tdc_ble_map_stim.c/.h        ->  tdc_ble_cmd_0x65_specific.c/.h

## 4. eCAP·impedance 잠재 위험 (신규 등록)

> [!IMPORTANT]
> **전문은 [`상시 점검 대장.md §2`](../상시%20점검%20대장.md) 가 단일 출처다.** 여기는 요약과 다음 행동만 적는다.

### 4.1 조사 결과 - `electrodeMap[32]` 접근 전수

| 명령 | 파싱 검사 | `isd/` 실행 | 인덱스 | 앱 사용 | 등급 |
|---|---|---|---|---|---|
| 0x62 impedance | 있음 (1~32 또는 255) | 실행 | **안전** (255->0 분기 + 상한 검사) | 사용 | 낮음 |
| **0x63 eCAP masking** | **0건** | **실행됨** | **무검증 0~255** | 사용 X | **중** |
| 0x64 eCAP alternative | **0건** | 주석 처리 | 도달 안 함 | 사용 X | 낮음 |

### 4.2 위험_1 (중) - 0x63 eCAP masking

**파싱에 범위 검사가 단 한 건도 없다.** `tdc_ble_map_measure_ecap_masking()` 이 15개 필드를 읽고 곧바로 `fetched_command` 를 설정하는데, 그 값이 `isd/tdc_isd_map_ecap.c:688`·`:749`·`:906`·`:1130` 에서 `electrodeMap[... - 1]` 로 쓰인다.

| 입력 | 인덱스 | 침범 대상 |
|---|---|---|
| 0 | `electrodeMap[-1]` | `name.1` |
| 255 | `electrodeMap[254]` | **`s_manu_table`** (`pwr/tdc_pwr_clock.c:15`, 256바이트) |

**바이폴라 99 보다 범위가 넓다** — 그쪽은 99 라는 특정 값이 통로였으나 여기는 **0~255 전 구간 무검증**이다. `0x1F` 마스크도 없다.

**완화**: `tdc_ble_protocol.h:91` 에 `// 현재 버전 매핑 앱에서 사용 X` 표기. 앱이 보내지 않아 현재 발현하지 않으나, **실행 경로는 살아 있다**(`mapping.c:389`).

**조치안**: 0x65 와 동일 방식 — 범위 검사 + `0x1F` 마스크. 0x65 작업([`20260730_bipolar-99-specific-stim`](../tasks/ble/20260730_bipolar-99-specific-stim/))이 그대로 본보기다.

### 4.3 위험_2 (낮음) - 0x64 실행부 주석

`mapping.c:403` 이 주석이라 현재 무해하나, **주석을 푸는 순간 위험_1 과 동급**이 된다. 파싱 검사가 0건이고 같은 구조체를 공유한다. **0x64 를 되살리려면 범위 검사가 선행 조건이다.**

### 4.4 위험_3 (낮음) - impedance 마스크 비대칭

`map_impedance.c:363`·`:410` 이 마스크 없이 OR 한다. **인덱스는 안전**하므로 무해하지만 라이브·0x65 와 비대칭이다.

## 6. 검증 노하우 (이 세션의 자산)

### 노하우_1 - 리팩토링 유형마다 불변량이 다르다 (표 확장)

| 유형 | 불변량 |
|---|---|
| 파일 이동 | `.elf` 바이트 동일 (`-ffile-prefix-map` 필요) |
| 함수 추출 | 조건 분기 총수 보존 |
| 테이블 주도 전환 | 파싱 필드·경계 상수 집합 |
| 가드 수렴 | 게이트 관련은 수렴, 본문은 불변 |
| **개명** (신규) | **`text` 완전 동일** |
| **결함 수정(방어 추가)** (신규) | **정상 경로 불변 + 예측된 분기만 증가** |

**개명의 근거**: `objdump` 로 `.rodata` 가 별도 섹션이 아니고(`.text` 병합) 파일명은 `.debug_*`, 심볼명은 `.strtab` 에만 있어 로드 섹션 기여가 0 임을 사전 확정. 파일명 18->27자, 함수명 25->29자로 길어졌는데 **1바이트도 안 변했다.**

**방어 추가의 근거**: 증가분을 **미리 못 박는다**(`if`+1 · `else`+1 · `||`+3). 예측과 다르면 의도 밖 편집이 섞였다는 신호다.

### 노하우_2 - 검증 지표가 오염된다 (2건)

> [!CAUTION]
> **`grep -rn` 이 아니라 `git grep` 을 쓸 것.** 이 프로젝트는 Eclipse 워크스페이스가 `src/` 안에 있어(`src/.metadata/`, gitignore) `grep -rn` 이 **203건 오탐**을 냈다. `git grep` 은 gitignore 를 자동 제외한다.
>
> **구조 지표는 행 앵커(`^\s*`)로 재라.** `grep -o "case "` 가 **주석 안의 "case" 언급까지 세어** 19->21 거짓 FAIL 을 냈다. 기준선 19 자체가 실제 레이블 17 + 주석 2 였다. 연산자는 주석 라인(`^\s*[/*]`) 제외가 필요하다.
>
> **기존 작업들의 "조건 분기 총수 보존" 검증도 같은 취약점을 갖는다** — 주석 증감이 없어 오염이 상쇄됐을 뿐이다(이월_I).

### 노하우_3 - 개명 작업에서 `grep` 일괄 치환은 금물

`docs/` 의 구 심볼 참조 **57건 중 갱신 대상은 기준표 1건**뿐이다. 나머지 56건은 과거 작업 기록이라 고치면 *"단계_1b 가 `cmd_0x65_specific.c` 를 만들었다"* 는 거짓이 된다.

**자기 참조 집계 함정**도 있다 — 개명 작업의 문서는 구 이름을 인용하므로 `grep` 총계가 **문서를 쓰는 동안 움직인다**(77->91 실측). 집계 기준을 **자기 폴더 제외**로 고정해야 한다.

### 노하우_5 - 방어 추가의 실패 모드는 누락이 아니라 과잉

정적 지표는 **과잉 차단**을 못 잡는다. 조건 부등호를 잘못 쓰면 정상 입력이 거부되는데 크기·분기 지표는 전부 통과한다. 실기 항목에 **"정상 입력에서 방어 로그가 뜨지 않을 것"** 을 명시해야 덮인다.
