## 4. 검증 노하우 (이 세션의 자산)

### 노하우_1 - 리팩토링 유형마다 "변하지 않아야 할 지표"가 다르다

| 유형 | 지표 | 이번 결과 |
|---|---|---|
| 파일 이동 | **`.elf` 바이트 동일** (`-ffile-prefix-map` 정규화 필요) | md5 일치 |
| 함수 추출 | **조건 분기 총수 보존** (파일 간 이동은 허용) | 4단계 전부 `+0` |
| 조립 공통화 | **조건 분기 총수 `+0`** (이동도 없어야 함) | 5커밋 전부 `+0` |

크기 증감만 보면 아무것도 판정할 수 없다. **무엇이 변하면 안 되는지를 먼저 정하는 것**이 검증 설계의 핵심이다.

### 노하우_2 - 경로가 바뀌면 바이너리가 바뀐다

`__FILE__` 을 쓰는 코드가 하나라도 있으면 소스 경로가 `.rodata` 에 박힌다. 이 프로젝트는 `TDC_PRINTF_E` 가 그렇다.

파일 이동 리팩토링에서 바이트 동일을 검증하려면 **양쪽 빌드에 폴더별 `-ffile-prefix-map=<경로>/=` 를 걸어** `__FILE__` 을 basename 으로 정규화한다.

### 노하우_3 - 바이트 동일 실패 시 크기를 먼저 본다

크기가 같은데 md5 만 다르면 **코드가 아니라 배치**다. 단계_1a 의 1차 대조 실패 원인이 링크 순서였고, 순서를 맞추자 일치했다.

### 노하우_4 - 접근자 호출 수를 소스의 읽기/쓰기 지점 수와 대조한다

공유 상태를 접근자로 바꿀 때 가장 위험한 것은 **한 지점을 빠뜨리는 것**이다. 원래 변수가 같은 파일에 남아 있으면 컴파일러가 잡아주지 않는다.

소스에서 세어 표로 만들고 어셈블리의 `bl get_*`/`bl set_*` 개수와 대조한다. flash 12 / stim 5 로 정확히 일치했다.

### 노하우_5 - 설계안과 자기 분석을 모두 의심한다

이번 세션에서 **설계안 전제 4건과 내 분석 2건**이 실제와 달랐다.

| 틀린 것 | 실제 |
|---|---|
| ".elf 바이트 동일 성립" | `__FILE__` 때문에 불성립. 정규화 필요 |
| "함수 지역 static 없음" | 4개 존재. 그중 하나는 3그룹 공유 |
| "`mapping/` 3분할 = 5+3+2 명령" | 5개 누락 |
| "16비트 분해만 존재" | 32비트 3곳 존재 |
| "`map_stim` 의존 17개" | 자기 static 포함. 실제 7개 |
| "범위 = 송신 지점 33곳" | 조립·송신이 분리된 `sound1/` 25곳 누락 |

**검증 단계를 형식적으로 넘기지 않은 것**이 매번 도움이 됐다. 특히 `grep` 으로 셀 때 **무엇을 세고 있는지**(자기 함수 포함 여부, 주석 기준 vs 코드 기준)를 확인해야 한다.

### 보조 - 도구 함정 (누적)

| 함정 | 대응 |
|---|---|
| **PowerShell `Copy-Item` 은 타임스탬프를 보존한다** | 소스를 갈아끼우고 `make` 하면 **재컴파일이 스킵된다.** 대조가 통째로 무효가 된다. `.o` 삭제 + `touch` 필수 |

| 배치 파일 UTF-8 | cmd 는 CP949 로 읽는다. `.bat` 은 **ASCII 전용** |
| `Get-Content \| Measure-Object -Line` | 빈 줄을 세지 않는다 (이전 세션부터 반복) |

### 6.3 이제 안전망이 있다

