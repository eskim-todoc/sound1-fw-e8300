## 2. 잠재 위험 (주기 점검 — 해소되지 않은 채 남아 있음)

> [!IMPORTANT]
> **은수님 지시(2026-07-30)**: *"ecap 쪽과 impedance 쪽에서도 배열 인덱스 이슈가 있다면 그것도 해야할 잠재 위험으로 정리해서 관리좀 해줘. 나한테 주기적으로 해야한다고 알려주면 좋겠어."*
>
> 아래는 2026-07-30 전수 조사 결과다. **바이폴라 99 결함**(`specific_stim`·`para_setting` 은 해소)과 **같은 구조**의 위험이 `ecap` 에 남아 있다.

### 2.1 조사 결과 요약 — `electrodeMap[32]` 접근 전수

| 명령 | 파싱 범위 검사 | `isd/` 실행 | 인덱스 안전성 | 앱 사용 | **위험 등급** |
|---|---|---|---|---|---|
| 0x62 impedance | **있음** — 1~32 또는 255 (`map_measure.c:31~33`) | 실행 | **안전** — 255 를 `electrodeNum = 0` 으로 분기(`map_impedance.c:81~88`), 증가 시 상한 검사(`:604`) | 사용 | **낮음** (마스크 비대칭만) |
| **0x63 eCAP masking** | **0건** | **실행됨** (`mapping.c:389`) | **무검증** — `measurementElectrodeNum - 1` · `stimulationElectrodeNum - 1` 이 `uint8_t` 원값 | **사용 X** (헤더 표기) | **중** |
| 0x64 eCAP alternative | **0건** | **주석 처리** (`mapping.c:403`) | 도달 안 함 | 사용 X | **낮음** (주석 풀면 즉시 중) |

### 2.2 위험_1 (중) — 0x63 eCAP masking 의 무검증 전극번호

**파싱에 범위 검사가 단 한 건도 없다.** `tdc_ble_map_measure_ecap_masking()`(`map_measure.c:59~91`)은 15개 필드를 읽고 곧바로 `fetched_command` 를 설정한다.

그 값이 배열 인덱스로 쓰인다.

| 위치 | 표현 |
|---|---|
| `isd/tdc_isd_map_ecap.c:688` | `if (electrodeMap[(mappingPacket->eCapMeasurement.measurementElectrodeNum - 1)] < 16)` |
| `:749` | `... \| (electrodeMap[(... measurementElectrodeNum - 1)])` |
| `:906` · `:1130` | `... \| ((electrodeMap[(... stimulationElectrodeNum - 1)]) ...)` |

`Rx_dataPacket[]` 은 `uint8_t` 이므로 **0~255 전 범위**가 그대로 들어온다.

| 입력 | 인덱스 | 주소 | 침범 대상 |
|---|---|---|---|
| `electrodeNum = 0` | `electrodeMap[-1]` | `0x200080cc` | `name.1` (`0x200080c4`, 11바이트) |
| `electrodeNum = 255` | `electrodeMap[254]` | `0x200084c8` | **`s_manu_table`** (`0x20008474`, 256바이트) = `pwr/tdc_pwr_clock.c:15` 의 `uint32_t s_manu_table[]` |

> [!CAUTION]
> **바이폴라 99 결함보다 범위가 넓다.** 그쪽은 99 라는 특정 값이 통로였지만, 여기는 **0~255 전 구간이 무검증**이다. 또 `0x1F` 마스크도 없어(`ecap` 파일에 `0x1F` **0건**) 오염이 레지스터 상위 비트까지 번질 수 있다.

**완화 요인**: `tdc_ble_protocol.h:91` 에 `// 현재 버전 매핑 앱에서 사용 X` 로 표기돼 있다. **앱이 보내지 않으므로 현재 발현하지 않는다.** 다만 `isd/` 실행 경로는 **살아 있다**(`mapping.c:389` 가 `tdc_isd_map_ecap_step()` 호출, 주석 아님).

**조치안**: 0x65 에 적용한 것과 동일 — 파싱에 범위 검사를 넣거나(`isd/` 에서 막는 대칭 유지가 나으면 `isd/`), 레지스터 조합에 `0x1F` 마스크 추가.

### 2.3 위험_2 (낮음) — 0x64 eCAP alternative 의 주석 처리된 실행부

`mapping.c:403` 이 `// tdc_isd_map_ecap_step(mappingCommandStartFlag);` 로 **주석 상태**라 현재 `electrodeMap` 에 도달하지 않는다.

> [!WARNING]
> **주석을 푸는 순간 위험_1 과 동급이 된다.** 파싱(`map_measure.c:93~113`)에 범위 검사가 0건이고 같은 `eCapMeasurement` 구조체를 공유한다. **0x64 를 되살리려면 범위 검사가 선행 조건이다.**

### 2.4 위험_3 (낮음) — impedance 의 `0x1F` 마스크 비대칭

`isd/tdc_isd_map_impedance.c:363` · `:410` 이 마스크 없이 OR 한다.

```c
w_isd_registerValue = w_isd_registerValue | electrodeMap[electrodeNum];                                    // :363
w_isd_registerValue = w_isd_registerValue | (electrodeMap[electrodeNum] << electrodIndexPositionAtPCM_Mold);  // :410
```

**인덱스는 안전하다** — `channel` 이 1~32 또는 255 로 검증되고, 255 는 `electrodeNum = 0` 으로 분기되며, 증가 시 `df_MaxNumOfElectrode` 상한 검사가 있다. 따라서 `electrodeMap[]` 값이 0~31 이라 마스크가 없어도 무해하다.

**다만 라이브·0x65 경로가 마스크를 갖는 것과 비대칭**이다. 방어 관례를 통일하려면 함께 넣는 것이 맞다.
